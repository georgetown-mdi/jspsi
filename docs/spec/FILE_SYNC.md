# File-sync transport state model

This is the single source of truth for the *intended* state mechanics of `FileSyncConnection` (the `sftp` and `filedrop` channels). It exists because the rendezvous and message-loop behavior is an implicit state machine spread across several enforcement sites in one file, and because each change that adds a file type or a transition would otherwise re-derive the mechanics from prose and let the enforcement sites drift apart. This document is the shared target every such change is reconciled against.

This is a developer/design document. For the user-facing configuration reference and the canonical filename grammar see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md); for the high-level channel and synchronization overview see [COMMUNICATION.md](../COMMUNICATION.md); for the cryptographic protocol see [PROTOCOL.md](PROTOCOL.md). Where this document and EXCHANGE_REFERENCE overlap, EXCHANGE_REFERENCE owns the filename grammar and this document owns the state machine. This is a deliberate tier inversion: the filename grammar -- this document's single critical invariant -- stays in the overview-tier [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md) because that is the document an operator authoring a `psilink.yaml` opens, so this spec-tier document references *up* into the overview tier for it. Do not "tidy" the grammar down into `docs/spec/`; doing so would silently break the grammar references throughout this document. (The boundary is recorded in [docs/spec/README.md](README.md).)

## Core principle: the directory is the state machine

Two parties share one directory (an SFTP path or a local filedrop path) and never hold a lock on the directory itself. Each party mutates the shared state only by `put`, `delete`, and `rename`, and observes the peer only by `list`. The protocol state is therefore exactly **the set of filenames present in the directory**. Everything else -- roles, modes, who has consumed what -- is inferred from that set.

Two consequences follow, and they are the reason this document exists:

1. Correctness reduces to agreement on two things: which filenames are legal at each phase, and how each file is routed (treated as a message, a control signal, or ignored). A bug is almost always a disagreement about one of those two between the two parties, or between two of this code's own enforcement sites.
2. Every new file type is a new symbol in the state machine's alphabet, and must be accounted for at *every* site that reads the directory. Adding one without updating all of them is the standard failure mode.

## The single critical invariant: the filename grammar

Routing safety rests entirely on one rule, defined in full under [EXCHANGE_REFERENCE.md "Filename grammar"](../EXCHANGE_REFERENCE.md#filename-grammar) and restated here as the discriminant the state machine depends on:

> A protocol file is named `<id>-...-<token>.json`. If `<token>` is all digits the file is a **message** and `<token>` is its declared byte count. Otherwise `<token>` is a type word (`hello`, `ack`, `joining`, `lock`) and the file is a **control file** that is never routed as a message.

In code this discriminant is `parseMessageByteCount(name) !== undefined` (applied by the `poll()` scan in [fileSyncMessageLoop.ts](../../packages/core/src/connection/fileSyncMessageLoop.ts)). Only the protocol's own in-flight temp write `temp-<uuidv4()>.tmp` is excluded earlier, matched by `isProtocolTempName` (its `temp-` prefix and a v4-UUID stem, the exact shape `send()`/`writeAck()` produce) -- a *foreign* `temp-*.tmp` whose stem is not a UUID is not excluded here; it fails the grammar and is treated as a foreign file. Every `.json` control file -- `hello`, `ack`, `joining`, and the `lock` tiebreaker -- is excluded by the discriminant instead, because its terminal token is non-numeric. The grammar is what lets the message scan ignore a renamed hello, an ack, or a lock file without an explicit per-type exclusion -- so every new control file gets a non-numeric terminal token *for free*, provided the site that reads the directory uses the discriminant rather than a bare prefix glob. Two sites name control types explicitly anyway, and neither narrows the discriminant. The `poll()` peer-message scan tests `!name.endsWith("-ack.json")` ahead of `parseMessageByteCount`; it narrows nothing, an ack's terminal token being non-numeric, so the discriminant behind it rejects the same names. The entry guard's grammar classifier (`isProtocolGrammarName` in [fileSyncNames.ts](../../packages/core/src/connection/fileSyncNames.ts)) lists the control suffixes -- `hello`, `lock`, `joining`, `ack`, `abort` -- because it answers the opposite question: not "is this a message" but "is this a protocol artifact at all". So a leftover control file is recognized (rejected at the no-flag entry guard, swept under `--sweep-exchange-files`) rather than failing the directory-clean check as a foreign file. A new control file therefore rides the discriminant for free where routing is concerned, and has to be added to that classifier to be recognized at entry.

**Message body format.** A message file's body is a binary envelope `version || type || seq || payload`: a 1-byte version/format marker (`MESSAGE_ENVELOPE_VERSION`), a 1-byte `type` discriminator (`0` = JSON object, `1` = raw binary frame), an 8-byte big-endian per-session `seq`, then the payload -- UTF-8 JSON parsed through the `parseBoundedJson` chokepoint for `type 0`, or the raw frame bytes delivered as-is for `type 1`. `type` is the outer, cleartext discriminator the reader keys on, because an encrypted frame's own JSON/binary tag is inside the AEAD ciphertext (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#application-layer-aead)) and cannot drive the transport read. The payload is stored verbatim -- no base64url and no whole-frame string conversion -- so the on-disk size is the raw frame plus the 10-byte header (the byte count the filename declares and the sync-gate waits for), and a frame larger than Node's maximum string length can be read. The send-time timestamp is not in the body (a timestamped filename records it); the `seq` is cross-checked against the filename NNN in retain mode. Byte 0 is the whole compatibility check on this path, and it is checked before anything else is believed: a value that is not this build's `MESSAGE_ENVELOPE_VERSION` yields a terminal `likely incompatible partner version` hint naming the real cause -- both parties must run the same psilink version -- rather than a silent misparse. Two foreign values reach it. A JSON-text body leads with `{` (0x7B), which is what a peer too old to speak the envelope writes and cannot be taught a handshake to avoid; a version above this build's is what a newer peer writes. Only a byte 0 that coincidentally equals this build's marker falls through to the generic malformed-envelope error. The forward-looking clean check is the terms exchange's `protocolVersion` reconcile ([PROTOCOL.md](PROTOCOL.md#protocol-version-reconcile-at-the-terms-exchange)), which is transport-agnostic; it rides these message frames rather than preceding them, so on the file-sync path this envelope-version-byte hint is what first catches a foreign envelope, while the reconcile covers skews whose envelope stays readable.

**Send-path framing (peak-shaving, not a wire change).** `send()` does not concatenate the header and payload into one buffer. It builds only the 10-byte header (`serializeFileSyncMessageHeader`, defined in `fileSyncFraming.ts`) and hands `put` the `[header, payload]` pair as an ordered two-chunk list (the `Uint8Array[]` arm of the `FileTransportClient.put` src type); the transport writes the parts back-to-back, so the on-disk bytes are byte-identical to the concatenated form above but the payload is never copied. This holds a binary frame's live footprint at ~1x its size on the send path rather than ~2x, which a header-prepending whole-buffer copy would cost. Each transport realizes the two-chunk write without a memory-side concat: the SFTP adapter streams the parts through the same `createBoundedPutSource` idle-window-bounded source it uses for a lone `Buffer` (so the stall window and retry cover the hottest, largest binary frame -- a chunk list is re-iterable, so the source is rebuilt per retry attempt), and `LocalFSClient` writes them with one positional `writev`. `serializeFileSyncMessage` (the whole-buffer form) exists only for the transport tests, which inject a complete message file's bytes; a receiver reads the whole file and decodes it with a `subarray` view regardless of how it was written. The send path is channel-hardening surface -- it is the `put` liveness/stall window and the crash-safe atomic write -- so a change to it is security-review scope under the CONTRIBUTING Dependency Policy.

**Foreign and snapshotted files (a classification, not a new file type).** A name that fails the grammar above -- a conflict copy, a partial download, an unrelated file -- is *foreign*: it has no `<id>-...-<token>` shape, sits outside the NNN alphabet, and is never a protocol file. Foreign names present at `synchronize()` entry are recorded in an in-memory snapshot and tolerated for the session; a foreign name that first appears *after* entry is a newcomer handled by `unexpected_files`. Neither is prefix-screened at `poll()`: a foreign name that coincidentally matches `<peerId>-<digits>.json` matches the message grammar, so it is a protocol file (a message), not foreign -- rejected at the entry guard with no flag, or swept under `--sweep-exchange-files`, and never snapshotted. Two of these rows are read at *entry* as well, by the pre-sweep retain-signal inspection (site 1): the hello row's payload supplies `retain_files`, and a retain-only message ack's mere presence is itself a retain signal (the shape that distinguishes one is in [I0](#invariants)).

**Hello temp disposition (why one temp shape is swept at entry and the other is not).** Both temp shapes are `isProtocolTempName`, so both are grammar-recognized, recognized for the loop, and tolerated at entry rather than refused. They differ only in whether the entry guard deletes them, and the split is the reason the hello publish has its own name shape at all.

- A `temp-<uuidv4()>.tmp` is a message or ack write, and writing either requires having already seen the peer's hello -- which this party publishes only *after* its entry scan. So one visible at entry is orphaned by construction, and the sweep deletes it unconditionally.
- A `temp-hello-<uuidv4()>.tmp` shares none of that: publishing a hello requires nothing from the peer, so a party starting at the same instant can have one in flight in this very listing. Deleting it would break that party's rename and fail its exchange, so it is added to `ignored` and left alone. `--sweep-exchange-files` does not reach it either: the flag is an assertion about the durable protocol files in the directory, not about a write in flight at this instant.

The cost is that this party's own crash residue -- a hello temp left by a kill between the `put` and the `rename` -- is indistinguishable from that live peer's write by name, and so is also left. It is inert: it matches the grammar (never counted as a foreign file), no reader opens it, and the operational sync glob already excludes `temp-*.tmp`. In *split* mode the outbound directory takes the opposite disposition -- both shapes are swept there -- because the routing rule ("no peer file lands in outbound") makes a hello temp there necessarily this party's own.

**Limit -- a hello temp in a shared inbound directory has no in-protocol removal path.** The disposition above is stated for crash residue, but it is keyed on the name shape alone, so it covers every file of that shape whatever produced it. In a shared (non-split) directory the shape is writable by the partner, or by anyone else with write access, and once present it is reachable by no removal mechanism the protocol owns. The entry sweep spares it by construction, `--sweep-exchange-files` does not reach it, it never enters `responsibleFiles` so `cleanup()` never sees it, and because `isProtocolTempName` accepts it `isRecognizedLoopFile` does too. So `unexpected_files` (default `error` on plain delete-mode transports) treats one appearing mid-loop as recognized rather than flagging it. The residual is accumulation of inert names, re-listed and re-logged on every subsequent run in that directory, not a read, a delete, or a routing decision: no reader opens a hello temp and no branch acts on one. The remedy is out-of-band directory hygiene. Narrowing `isRecognizedLoopFile` to exclude the shape would restore the mid-loop flag, but it belongs with the `unexpected_files` policy rather than here, because a hello temp legitimately tolerated at entry must not then be flagged mid-loop by the same run.

**Abort-marker lifetime (one writer, one remover, and the reader is neither).** The marker is the one protocol file whose removal belongs to a *later* exchange, so its lifetime is stated here rather than inferred from the sweeps that touch it.

- **Written** by the failing party, best-effort, on a terminal post-handshake fault with its directory still writable -- one `<writerId>-abort.json` per failing party.
- **Not removed by the session that wrote it.** It is absent from `responsibleFiles`, so `cleanup()` leaves it: a peer that has not yet polled must still find it after the writer has closed.
- **Not removed by the peer that reads it, either.** Consuming a marker is a read; the peer that verifies one stops its poller and reports a `PeerAbortError`, leaving the file exactly as it found it. So a fast-failed peer leaves no on-disk trace of having read it, and the writer cannot observe whether it was read.
- **Removed** by the entry scan of the next delete-mode exchange to use the directory (site 1(d)), which sweeps any well-formed marker whichever id wrote it -- including one named by neither party of that exchange, the shape a retry after a failed exchange always presents, since both parties draw fresh ids. In retain mode nothing removes it automatically: it is refused by the strict-empty guard and cleared only by `--sweep-exchange-files --force-retain-sweep`.

Sweeping a marker no id in the entering session names is safe because no marker visible at entry can *belong* to that session. A marker is written only post-handshake, and a party cannot reach post-handshake before its peer has passed this same entry scan, so a marker present here is residue of a prior session, whose token cannot authenticate under the entering session's key. What is swept and what is believed stay separate: the sweep changes only what is deleted at entry, never what is accepted as a peer abort, which is still the token check in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#authenticated-abort-marker).

**Limit.** In a directory a live peer is still using -- a violation of [directory exclusivity](../EXCHANGE_REFERENCE.md#directory-exclusivity), which the protocol has no entry-time liveness signal to detect -- the sweep can delete that peer's marker before it polls, costing it the fast-fail and dropping it back to the peer-inactivity timeout and its generic hedge. That is a degradation of an optimization, never a false success: an absent marker is strictly uninformative.

## The five enforcement sites

The state machine is enforced -- and therefore must be kept consistent -- at exactly these five places, split across three modules. Site 2 (`responsibleFiles`/`cleanup()`) lives in [fileSyncConnection.ts](../../packages/core/src/connection/fileSyncConnection.ts). Sites 3 and 4 (the `poll()` scan and `hasOutstandingMessage` in `send()`) live in its message loop [fileSyncMessageLoop.ts](../../packages/core/src/connection/fileSyncMessageLoop.ts), which the connection composes and delegates `poll()`/`send()` to. Sites 1 and 5 (the entry guard/sweep and the rendezvous role-commit logic) live in its rendezvous coordinator [fileSyncRendezvous.ts](../../packages/core/src/connection/fileSyncRendezvous.ts), which the connection's `synchronize()` delegates to after validating entry. The connection remains the composition root that owns the shared `responsibleFiles`/`foreignFileSnapshot` state both coordinators mutate by reference. Adding or changing a file type is a change to *all applicable rows of the taxonomy at all five sites*; this is the anti-drift checklist.

1. **Preexisting-file guard** (`synchronize()` start). Three distinct mechanisms, kept separate. **(a) Foreign snapshot (tolerate, both modes, always).** A name that fails the grammar is foreign; foreign names present at entry are recorded in an in-memory snapshot and tolerated, deleting nothing (safe in retain mode, where sync-mediated conflict copies are expected noise). The snapshot feeds the recognized-for-the-loop set at site 3 so a pre-existing foreign name is not re-flagged mid-loop. **(b) Default strict-empty guard (no flag).** Three mechanisms compose it: `isPeerHelloName`/`peerIdFromControlName` for the one file kind that may legitimately predate entry, the grammar discriminant for protocol-versus-foreign, and (a)'s snapshot for what does not count as present. Anything else is a terminal `UsageError` whose text points at `--sweep-exchange-files`. Full rule -- what is tolerated, the rejection list, and the abort marker's mode-dependent disposition: [I0](#invariants). This is what code-enforces retain mode's fresh-directory precondition (see [Fresh directory in retain mode](#preconditions-for-a-correct-exchange)). **(c) Opt-in sweep (`--sweep-exchange-files`).** Before any delete, a *pre-sweep retain-signal inspection* checks whether the directory belongs to a retain exchange. It reads three signals, whose shapes [I0](#invariants) defines: local retain mode, a retain-only message ack (a filename scan only -- no body is read), and a peer hello advertising `retain_files=true`, read through the I5a gate under a near-future deadline so a non-resolving body cannot stall the sweep; an unresolved or unparseable body is retain-uncertain. On any signal the bare flag refuses and `--force-retain-sweep` is required; otherwise the sweep deletes every protocol-grammar file (this party's and the peer's) via `client.delete` rather than `safeDelete`, which is what puts a transport that cannot delete in the transport-failure class (see [Error taxonomy](#error-taxonomy)) instead of falsely reporting a clean slate, and entry proceeds against a clean slate. Foreign files are never swept. Finally, the `ignored` set remains the extension point for the in-flight temp writes: a crashed message or ack write is `safeDelete`d and added to `ignored` rather than rejected, and a hello publish's `temp-hello-<uuidv4()>.tmp` is added to `ignored` *without* being deleted (see *Hello temp disposition* above). The sweep therefore matches `isProtocolTempName` minus `isHelloTempName`; a foreign `temp-*.tmp` whose stem is not a v4 UUID fails the grammar and is handled by the foreign snapshot in (a), tolerated like any other foreign name rather than deleted. The flag's protocol-file deletion and the temp sweep are kept separate; the temp logic is not forked. **(d) Leftover abort-marker recognize-and-sweep (delete mode, always).** Because every authenticated terminal failure leaves a `<writerId>-abort.json` that must persist for the peer to read, a directory reused for a later exchange would otherwise reject "directory not clean". This guard `safeDelete`s a leftover marker and adds it to `ignored` -- like the orphaned temp -- matching any *well-formed* marker: the `<id>-abort.json` grammar (`isAbortMarkerName`) narrowed to a non-empty recovered id (`peerIdFromControlName`), under whichever id wrote it. Matching by id would recognize nothing on the case that matters: after a failed exchange both parties retry under fresh ids, so the leftover names neither of them and neither of their hellos. The two names the widened match does not reach keep their existing dispositions: a bare `-abort.json` recovers no id, is attributable to no party, and stays an unexpected protocol file (exit 64, the same fate as a bare `-hello.json`); a name that fails the grammar is foreign and is never touched. The sweep runs in delete mode only: in retain mode the marker sits beside a durable audit transcript, so it is left for the strict-empty guard to refuse (exit 64) and the existing `--force-retain-sweep` gate to clear -- reusing that machinery rather than a parallel retain check so the two cannot drift. This is a scoped, documented loosening of the entry guard: the match is on the name alone and the body is never read, so a malformed or garbage token -- or a file that merely ends in `-abort.json` and has no marker envelope at all -- is swept/ignored rather than named and refused by the strict-empty guard. That is acceptable under the threat model, because such a name is inside the protocol namespace the directory is reserved for and is never a foreign name, which (a) still tolerates untouched; it is bounded by the safety argument and the live-peer limit in *Abort-marker lifetime* above.
2. **`responsibleFiles` + `cleanup()`**. The set of files this party created and must remove on `close()`/`cleanup()`. Pre-track before writing so a crash mid-write is still swept. Retain mode is the sole exception: exchange files are intentionally not swept. No interaction with the entry sweep (site 1): the files it deletes predate the session and were never tracked here, and `synchronize()` prunes `responsibleFiles` against the live listing before the guard runs.
3. **`poll()` scan**. Reads the peer's messages: `<peerId>-` prefix, `.json`, numeric terminal, and `size >= declaredSize`. In retain mode the scan additionally selects only the message whose `<NNN>` equals the in-memory `recvSeq` counter, so an already-consumed message still on disk (retain mode never removes it) is skipped rather than re-delivered. A `<peerId>-...-<byteCount>.json` whose NNN segment is non-numeric is a malformed protocol file -- a correctly configured retain peer cannot produce it once both sides have agreed on retain/timestamp at rendezvous. It is a terminal `UsageError` raised *before* the `recvSeq` selection, reported regardless of the `unexpected_files` policy (and *not* a `BilateralModeMismatchError`, since by this point the bilateral agreement is settled). Beyond message selection, the scan classifies *every* file in the listing against a baseline of files legal during the loop -- the **recognized-for-the-loop** set. That set is both hellos, both acks, the lock, both parties' messages and message-acks, our own writes, and an in-flight `temp-<uuidv4()>.tmp` (only the protocol's own temp shape; a foreign `temp-*.tmp` with a non-UUID stem is not recognized and falls to the unexpected-file policy unless snapshotted at entry). A file that is not recognized for the loop is an **unexpected** file, whose disposition is `unexpected_files`' to decide; the enum and its mode-coupled default are in [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#connectionoptions). What belongs to this model is the scope: the policy decides disposition only, never routing ([I2](#invariants)), and it is local and unilateral rather than bilateral, so the two parties may run different values. A fully-synced message that fails to parse or validate is terminal and stops the poller (see [I5b](#invariants)); transient transport and ack-write failures reschedule (an `emit`-handler throw would too, but the production consumer cannot throw -- see [I8](#invariants)). The entry foreign snapshot feeds this site: pre-existing foreign (grammar-failing) names are added to the recognized-for-the-loop set so they are tolerated rather than warned as newcomers. It does not suppress a grammar-matching `<peerId>-<digits>.json`: that name is a message by the discriminant, so it is selected and terminally rejected by the message scan (see [I8](#invariants)), never snapshotted -- the foreign snapshot and the message scan are disjoint by construction.
4. **`hasOutstandingMessage`** (in `send()`). The delete-mode sender waits here for the peer to consume (delete) its last message, and it matches that message by **exact name**: `lastSentFile` -- the name this party itself wrote -- present in the listing. Under the one-outstanding-per-direction rule ([I9](#invariants)) that is the only legitimate unconsumed own-message, and it is undefined before the first send, when there is nothing to wait for. The exact match subsumes the grammar exclusion the site would otherwise need, since the party's own hello and ack markers are not `lastSentFile` whatever their terminal token, and it holds where the discriminant alone would not. A foreign `<thisId>-<digits>.json` (this party's own id as prefix, numeric terminal) matches the message grammar but is not the name this party wrote, so it cannot hold the sender in the wait. This site therefore consults neither the grammar nor the entry foreign snapshot. `close()`'s terminal-frame drain matches `lastSentFile` the same way (see [Phase 3](#phase-3----cleanup-and-close)), so the two waits cannot disagree about which file is outstanding.
5. **Rendezvous role and collision logic** (`synchronize()`: lock path, lockless path, and role commit). Assigns `role`/`handshakeRole`/`peerId`, detects the two-hello collision, and recovers the peer id by fixed-suffix slicing (never by parsing). The recovered id must be **non-empty**: a bare `-hello.json` slices to `""`, which is never a usable peer identity, so it is not a peer hello -- and the sibling bare `-joining.json` is not a joiner arrival. Both the entry guard and the in-flight lock/lockless peer-hello scans (and the lock-path joining-sentinel handling) route their slicing through one helper (`peerIdFromControlName`, via `isPeerHelloName`/`isPeerJoiningName`) so the non-empty check holds at every site, not just at entry; the post-rendezvous prefix-collision guard additionally fails closed on an empty committed `peerId` as a last gate. This closes a gap where the entry guard rejected a bare `-hello.json` but the in-flight scans did not, so one injected after entry (mid-rendezvous, the directory being unauthenticated) could be adopted as `peerId=""`. That lets `poll()` key its peer scan on `${peerId}-` = `-` and the lockless ack barrier wait on an ack no honest peer writes, or lets a bare `-joining.json` force the bounded `joinerRecoveryMs` starter stall. Unaffected by session-start directory hygiene: the foreign snapshot, the pre-sweep inspection, and the sweep all run *before* role logic, and the snapshot is read-only. After a sweep the directory is clean, so this site sees no pre-existing peer hello and the party proceeds as if it arrived first.

## Two orthogonal mode axes

The transport has two independent binary modes. They are bilateral: both parties must choose the same value, and there is no negotiation (see [Bilateral configuration](#bilateral-configuration-detect-and-fail-never-negotiate)).

- **Rendezvous mode** -- how the two parties meet:
  - *Lock* (default, `lockless_rendezvous: false`): atomic exclusive-create plus a `-lock.json` tiebreaker; the joiner deletes the peer hello and writes its own. Requires deletion visibility and exclusive-create.
  - *Lockless* (`lockless_rendezvous: true`): an ack-handshake barrier that uses neither exclusive-create nor delete; both hellos and both acks coexist. For sync-mediated transports where both sides "win" a local create or deletions do not propagate.
- **Message-loop mode** -- how send/consume is signaled:
  - *Delete-as-signal* (default): the receiver deletes the sender's message file; the sender waits for that deletion before sending the next.
  - *Retain* (`retain_files: true`): no exchange file is deleted; the receiver writes a zero-length `ack` marker the sender waits for instead. For transports that do not propagate deletions, and for audit transcripts.

Not all combinations are valid. Retain mode requires lockless rendezvous: lock rendezvous is delete-based (the joiner deletes the peer hello as a role-assignment signal) and cannot produce the whole-directory no-delete transcript retain mode guarantees. The three valid combinations are lock + delete-as-signal (default), lockless + delete-as-signal, and lockless + retain. Lock + retain is rejected by schema validation.

## Split inbound/outbound directories

By default one directory is both read and written. A *split* configuration names two: this party reads the peer's files from the **inbound** directory and writes its own to the **outbound** directory, with no single shared path. It is for deployments where inbound and outbound folders are separate -- a managed share, or an SFTP server with distinct drop and pickup directories -- bridged so one party's outbound is the other's inbound. Configured as `inbound_path`/`outbound_path` (filedrop top-level, or under `server` for sftp), the pair mutually exclusive with the single `path`/`server.path`; see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#connectioninbound_path--connectionoutbound_path).

**Routing rule.** Every *peer-file read* -- the hello, message, ack, and abort-marker listings and reads -- comes from the inbound directory; every *self-write* -- this party's hello, messages, ack markers, abort marker, in-flight `temp-*.tmp` files, and the lockless self-bookkeeping scan -- goes to the outbound directory. A message's temp write and its atomic rename both occur within the outbound directory, so **no rename ever crosses the two directories** (cross-filesystem rename is not atomic). In shared mode inbound and outbound are the same directory, so this reduces to the single-directory behavior exactly. `this.path` is the inbound directory throughout the code; the outbound directory is resolved via `outboundPath` (which falls back to `this.path` in shared mode).

**Split mode requires retain mode** -- a deliberate constraint, not a mechanical necessity in every topology. On a shared store a delete-mode sender could poll its outbound (which is the peer's inbound) and observe the peer's delete; but that only holds when deletions propagate back, which fails across the one-way or delete-suppressing bridge that motivates separate folders. Retain mode signals with ack/abort markers that are always retained, and keeping the files directly serves the separate-folders goal of an auditable record of what flowed each way. Lock rendezvous is excluded for the same reason it is excluded from retain mode generally: its lock/tiebreaker file must exist in one shared location for the delete-based handshake. Because retain mode already implies lockless rendezvous and timestamped filenames, **only the lockless+retain code paths ever observe split directories** -- the lock and delete-mode paths are unreachable with an outbound directory configured (rejected at config validation), so they stay on `this.path` unchanged.

**Both directories must be fresh.** Retain mode's [fresh-directory precondition](#preconditions-for-a-correct-exchange) is enforced on the inbound *and* the outbound directory at `synchronize()` entry: peer files never land in outbound (the peer writes to its own outbound, which is this party's inbound), so any protocol-grammar file there is this party's own leftover from a crashed prior session and fails the clean-start guard exactly as on the inbound side. An orphaned `temp-*.tmp` is swept from both directories; a foreign file in either is snapshotted and tolerated. The two directories must differ, checked by one shared textual-normalization rule (`pathsResolveToSameDir`) at both config validation and `open()`, so the schema and the live connection give the same verdict (the `open()` check additionally guards a caller that constructs a connection directly, bypassing the schema). On both channels it catches redundant separators, `.` segments, trailing slashes, and backslashes (the fold is unconditional, not filedrop-gated), so e.g. `/x` vs `/x/`, `/x//y` vs `/x/y`, and `/x/./y` vs `/x/y` are all caught. The normalization is textual only: `..` segments (which may cross a symlink), case (Windows is case-insensitive), and a relative-vs-absolute SFTP path under the unknown login home cannot be resolved client-side and remain the operator's responsibility, not a guaranteed reject.

**Invitation-borne role swap.** Split directories are a per-party choice the deployment bridges (one party's outbound is the other's inbound), so an invitation cannot hold a single shared path -- but it can hold the *role mapping*. The invitation connection-endpoint wire format therefore holds the split pair: the sftp and filedrop endpoint sub-schemas (`packages/core/src/config/invitation.ts`) have `inboundPath`/`outboundPath` beside the single `path`, under the same directory-mode rules the connection config uses (both halves together, mutually exclusive with `path`, the two halves distinct, and filedrop must name a directory in one form). Like every field of the token, and like the top-level `disclosedPayloadColumns` below, these are **camelCase on the wire**: the encoder `JSON.stringify`s the validated token verbatim with no snake_case pass, and the sub-schemas are `z.strictObject`, so a token minted with `inbound_path`/`outbound_path` is rejected by the decoder rather than read. The snake_case spellings belong to the connection config on disk, not to the endpoint. They remain credential-free locators. Distinctness is enforced on the endpoint itself -- it survives the mirror swap (equal inviter halves yield equal acceptor halves), unlike the absolute-path rule, which is a per-party property the acceptor remaps and so stays deferred to the connection config's own validation. The token records the **inviter's own** pair verbatim; the cross-party swap happens at exactly one consumer, `connectionFromEndpoint` in apps/cli, which sets the acceptor's `inbound_path` from the inviter's `outbound_path` and its `outbound_path` from the inviter's `inbound_path`, so the two parties start as mirror images. Centralizing the swap at that single seeding site keeps the token a faithful record of the inviter's config rather than a pre-swapped acceptor view, and forecloses a double-swap -- the offline invite path calls the same function with no endpoint, so it never reaches a seeded branch. The seeded block also holds the retain-mode trio a split exchange requires (so it is runnable once credentials are filled in); the inviter's literal paths are a starting point the operator reconciles, since the swap fixes the *roles*, not the literal names -- in an asymmetric topology the paths, host, and even channel differ between parties. An SFTP login-home (unset) path has no concrete value to mirror, so such an endpoint conveys roles with no suggested path rather than erroring. Two accept paths consume that swap, both through this one function so the single-swap-site invariant holds across them: the **offline** accept seeds its whole connection block from `connectionFromEndpoint` directly, and the **online** accept (`applyEndpointSplitDirectories` in apps/cli) calls the same function only to lift out the swapped pair, then grafts that pair onto the connection it built from the acceptor's own URL. The online merge keeps the channel, host, port, and credentials from the URL (the endpoint is credential-free, and a bridged acceptor may reach the rendezvous over a different host or even channel). It takes the split `inboundPath`/`outboundPath` from the endpoint -- fully replacing the URL's single path, which cannot express a role mapping and whose inbound leg, if it won, would break the mirror. It also layers the retain-mode trio over any URL-derived options. An explicit `--outbound-path` (which instead routes through `applyConnectionOverrides`) is the override and wins, so the merge is skipped whenever it is set. The grafted split connection is re-validated through the connection schema before any network activity, so a degenerate endpoint (e.g. relative filedrop paths the endpoint schema defers) fails with the schema's own message rather than at connect time. The accept-time reconcile of a pre-existing config diffs against this merged connection, not a URL-only target, so a location disagreement still aborts before any acceptance is sent.

**No token-version bump.** Adding `inboundPath`/`outboundPath` to the `z.strictObject` endpoint sub-schemas is in principle an incompatible wire-format change -- an older decoder rejects the unknown keys rather than ignoring them, unlike a non-strict top-level addition. The invitation-token `version` was nonetheless left at `"1"`: the change landed while psilink is pre-release with no decoder deployed in the field, so no reader can observe the incompatibility and a bump would only churn the version. This is a one-time pre-release allowance, recorded in the `version` policy comment in `invitation.ts`; a strict-endpoint addition made *after* a release ships must bump the version (or otherwise stage compat). What is newly disclosed on the wire is the inviter's own inbound/outbound directory paths -- public locators with no credential or server-identity material, exactly as the single `path` already did.

## Disclosed-columns subset on the token

**The `disclosedPayloadColumns` top-level field.** The invitation token has an optional top-level `disclosedPayloadColumns: string[]` (camelCase on the wire, beside `connectionEndpoint`): the inviter's disclosed-columns subset -- exactly the column names `disclosedColumnNames(inviterMetadata)` / `isDisclosedToPartner` selects and `preparePayload` transmits for matched records. It is the set the acceptor will receive, in the **inviter's** column namespace. Only that consent-relevant subset is included; the inviter's linkage/identifier/ignored columns are not transmitted post-match, so they are not in the subset and do not leave the inviter's machine. Each name is bounded to `MAX_NAME_LENGTH` and the count to `MAX_PAYLOAD_ENTRIES` (the same bounds a `payload.send`/`receive` list has), atop the whole-token structural bound `parseBoundedJson` already applies at decode.

This closes a structural decoupling: the acceptor's consent display and its runtime enforcement derive from the **wire's own transmission predicate** rather than from a separately-authored `terms.payload.send` dictionary each mint path had to remember to write. The displayed/consented set therefore cannot drift from the bytes that flow -- both are `isDisclosedToPartner` over the same metadata. (`disclosedPayloadColumns` is distinct from the acceptor's own `payload.send`, which is the inviter's `receive` mirrored into the acceptor's namespace; the transmitted subset is the inviter's *send* set, consumed by the acceptor as a receive-side declaration.) The field is omitted -- and the acceptor reconciles lazily -- only when the mint path does not know its metadata (a config-as-source invite whose config has no explicit `metadata` block). When the metadata is known the subset is copied verbatim, including the empty set when nothing is disclosed: an empty transmitted set locks the acceptor in to "receive nothing" (a later non-empty payload aborts), it is a constraint, not the absent/lazy case.

**No token-version bump (top-level, unlike the split pair above).** `disclosedPayloadColumns` is an optional field at the *top* level, which the non-strict `z.object` token schema simply ignores in an older decoder -- the backward-compatible case the `version` policy comment in `invitation.ts` describes, the same path `connectionEndpoint` took. So it does not bump the version on the documented rule (not the one-time strict-endpoint allowance the split pair needed). What is newly disclosed on the wire is the names of the columns the inviter would already transmit post-match -- already shown for consent and written into the [exchange record](EXCHANGE_RECORD.md) -- not any new category of data.

The consent machinery this field feeds -- the runtime enforcement it establishes, the send-side commitment that mirrors it, the acceptor's own outbound-consent record, and the no-output send gate -- is specified in [EXCHANGE_FILE.md](EXCHANGE_FILE.md#payload-disclosure-consent), which owns the artifact those fields are persisted in. None of it is transport state: the gates run at prepare time and after the payload exchange, never at a directory read.

## Retain-mode declaration on the token

**The `inviterRetainsFiles` top-level field.** The invitation token has an optional top-level `inviterRetainsFiles: boolean` (camelCase on the wire, beside `connectionEndpoint` and `disclosedPayloadColumns`): the inviting party's statement that its own `retain_files` is on, so the exchange keeps every file it writes and the rendezvous location becomes a permanent transcript rather than being emptied as each message is consumed. It is the one disclosure of this transport that outlives the run, and the invitation is the only artifact that always reaches a partner, so it is stated where the partner decides.

**It is a declaration, and nothing applies it.** No accept path reads it into a connection: the accepting party sets its own half exactly as before, and a disagreement fast-fails at the hello with `BilateralModeMismatchError`, identically to an invitation with no declaration at all. The enforcement model is untouched -- see [Bilateral configuration](#bilateral-configuration-detect-and-fail-never-negotiate), which records why disclosing a bilateral flag stays inside the detect-and-fail boundary.

**Three states, and absence is not the negative.** `true` is the declaration; `false` is a stated delete mode; an omitted field is *no declaration*. psilink's mint paths write only `true`, and only from a configuration that has retain mode on -- the online `psilink invite` reads its post-override connection, the config-as-source invite reads `connection.options.retain_files` off the config the exchange will run, and the console reads the options block the run holds. That is a description of the three producers rather than a rule they are held to, with one exception the mint checks: where the endpoint holds the split pair, the declaration is not theirs to omit (below). Every other path omits it: an offline invite whose written connection block is still a placeholder scaffold has no settled mode to declare, a `webrtc` mint has no retain mode to declare, and a token minted before the field existed has nothing. Of the three, only `true` is stated: `false` and absent render nothing on the declaration's own account, because delete mode is not the mirror claim (a run killed outright, or one that fails after the handshake, leaves files behind in either mode) and a stated negative would promise a cleanup this transport does not make. The endpoint beside the field is the second ground on which the same line renders.

**The display's second ground: the endpoint's shape.** An acceptance surface states the retention where the token declares `true`, and also where its `connectionEndpoint` holds the split `inbound_path`/`outbound_path` pair -- a shape no connection can be built from without retain mode, since a separate outbound directory requires `retain_files: true` ([Split inbound/outbound directories](#split-inboundoutbound-directories)) and the accept paths seed exactly that trio. Both the seeding and the display read one predicate, `endpointRequiresRetainedFiles` in `packages/core/src/config/invitation.ts`, so the shape that puts a party into retain mode and the shape that is stated to it cannot drift apart. The case it covers is a token with a split endpoint and no declaration: psilink's own mints cannot produce that pair, because the mint-only refusal below rejects it, but a foreign or older token can, and on the declaration alone the accepting party would be seeded into retain mode with the consent line silent. The rendered sentence is the same fixed first-party copy on either ground: a split rendezvous cannot be run in delete mode on either side, so the mode the copy states is the mode any run of it is in.

**One flag only.** `lockless_rendezvous` is equally bilateral and equally fast-failing and is not included: nothing about it changes what an acceptor consents to, and the token's declaration list is held to facts with consent weight. That limit is the recorded line against flag-advertisement drift; adding a second flag means revisiting it here rather than following the precedent.

**Refused on a webrtc endpoint.** A token pairing `inviterRetainsFiles: true` with a `webrtc` `connectionEndpoint` is rejected at both encode and decode by the token schema's own refine: retain mode is a file-sync setting the WebRTC transport does not have, so the pair would state a mode no run of that token could be in. This is the operative gate, not a mirror of one on the connection side. `ConnectionConfigSchema` has a corresponding defense-in-depth refine over a webrtc connection's `options.retainFiles`, but a webrtc connection's `options` parses through `SharedOptionsSchema`, which declares no `retainFiles` field and so strips it before that refine ever sees it. A hand-authored `psilink.yaml` pairing `channel: webrtc` with `options: {retain_files: true}` loads successfully and runs in delete mode, with the field silently dropped rather than refused. A token with no endpoint at all is unconstrained -- the offline file-sync invite holds the declaration with no locator beside it.

**Refused as a false declaration on a split endpoint.** The mirror refusal on the file-sync side, by a second refine on the same schema and likewise at both encode and decode: a token pairing `inviterRetainsFiles: false` with a `connectionEndpoint` holding the split `inbound_path`/`outbound_path` pair is rejected. That endpoint's shape seeds the acceptor into retain mode whatever the token says -- the refine reads `endpointRequiresRetainedFiles`, the same predicate the accept path's own seeding reads -- so the negative states a mode no run of that token could be in, exactly as a `true` on webrtc does. Scoped to the explicit negative: a token omitting the field on the same endpoint stays valid to decode, since absence is *no declaration* rather than a contradicted one, and it is the very pair the display's second ground above exists to cover. The refusal is keyed on the shape, not the channel: a single shared `path` runs in either mode, so a stated `false` beside one decodes. And it binds the field's declared spelling only: the token body is non-strict and folds case for no key but `linkage_terms`, so an unrecognized spelling of the declaration -- `inviter_retains_files` among them -- is dropped in decode rather than read, landing the token in the no-declaration state the display's second ground covers.

**Refused at mint when a split endpoint leaves it undeclared, and only at mint.** The one rule that is not symmetric between encode and decode: `encodeInvitation` validates against a mint-only schema (`MintedInvitationTokenSchema` in `packages/core/src/config/invitation.ts`) that requires `inviterRetainsFiles: true` on any token with a split `inbound_path`/`outbound_path` endpoint. Emitting such an endpoint hands the partner a permanent transcript that only the locator's shape reveals, and any artifact composed from the declaration rather than from the shape -- an accept kit's file-handling disclosure among them -- would then state nothing about it. The rule lives at the single boundary every mint path reaches, the CLI's three and the web app's alike, rather than as a gate each producer restates.

Decoding is untouched: the same token still decodes, and the acceptance surfaces still state the retention on the endpoint's shape (the display's second ground above). Absence is *no declaration* on a decode path, every psilink read path derives the retention from the shape rather than from the declaration, and the token is a public protocol surface -- so refusing it there would reject a foreign token psilink already handles and displays correctly, buying nothing. The asymmetry is the point: psilink holds itself to declaring what it hands over without demanding the same of an implementation it does not control.

**No token-version bump (top-level, like `disclosedPayloadColumns`).** An optional field at the *top* level is ignored by an older decoder's non-strict `z.object`, so it takes the backward-compatible path the `version` policy describes rather than the one-time strict-endpoint allowance the split pair needed. What the field puts on the wire is a setting the inviter advertises in its hello a few seconds later regardless; what it moves is the point at which the partner sees it, from after the acceptance to before it.

The classification the two acceptance surfaces render it under -- enforced on the mode agreement, the inviter's word on what becomes of the transcript -- is the `retainedFiles` entry of `packages/core/src/consent/consentFacts.ts`, with the reasoning in [shared-consent-summary.md](../notes/shared-consent-summary.md).

## Phases and legal directory contents

Read each phase as "given this mode, the directory may legitimately contain exactly this set; anything else is an error or a not-yet-synced transient."

### Phase 0 -- clean start

Legal contents at entry: nothing this protocol owns, except at most one **peer** hello (the other party may have arrived first), plus any foreign files, which are snapshotted and tolerated. The preexisting-file guard (site 1) aborts in both modes, with one `UsageError`, on any other protocol file (full list in [I0](#invariants)). Tolerating the peer hello is what lets whichever party arrives second -- it always sees the first party's hello -- proceed instead of failing. With `--sweep-exchange-files`, the legal-contents rule is replaced by a clean slate: once the pre-sweep retain-signal inspection clears (or `--force-retain-sweep` is supplied), every protocol file is deleted and entry proceeds as if the directory held only the untouched foreign files.

### Phase 1 -- rendezvous, lock path

```
sequential arrival -- no lock is created
  A put A-hello.json
  B list -> sees A-hello.json            (B is the joiner)
  B put B-joining.json ; B delete A-hello.json ; B rename B-joining.json -> B-hello.json
  A list -> its own hello gone, B-hello.json present ; A reads it, commits
            starter/responder, deletes it

simultaneous arrival -- the two-hello collision, and the only path that writes a lock
  A put A-hello.json ; B put B-hello.json   (neither had seen the other's)
  both list -> both hellos present
  both assign roles by hello filename order and reconstruct
    <first>-<second>-lock.json, then race createExclusive on it
```

Legal transient contents: one self hello, optionally one peer hello, optionally one lock file, optionally one joiner sentinel. The joiner closes the one observable inconsistency window -- peer hello gone, joiner hello not yet written -- with a `<id>-joining.json` sentinel: it publishes the sentinel (holding its hello body), deletes the peer hello, then renames the sentinel to its own hello. The rename is atomic at the SFTP layer, so on a delete-visible transport the sentinel spans exactly that window. A sync-mediated transport may briefly expose both the sentinel and the renamed hello, which the peer tolerates because the lingering sentinel's id matches the peer hello it is completing against (a sentinel whose id matches *no* peer hello is third-party contamination and is rejected as a usage error, like a second peer hello or lock file). The peer's wait loop treats a `<peerId>-joining.json` as "joiner mid-arrival" and waits a bounded recovery window (`joinerRecoveryMs`, default 30s) for the rename to land. If the sentinel persists past the window the joiner failed mid-arrival -- after writing the sentinel but before publishing its hello, on either side of the delete -- and the peer aborts with a distinct transport error (CLI exit 69) instead of polling to the full `peerTimeoutMs`. The joiner releases the sentinel from `responsibleFiles` the moment it deletes the peer hello, so a failure after that point leaves the sentinel on disk as the peer's recovery signal (and, if the joiner process dies, for the next run's Phase 0 guard to reject); a failure before that point is swept by `cleanup()` with the peer hello still intact. The peer never re-creates its own deleted hello on recovery -- that would race the joiner's rename and trip the two-hello collision check ([I1](#invariants)). The filename-order rule is scoped to the collision branch: there, and only there, role is derived from hello *filename order* (`thisFile.name < otherFile.name`), which is also the order both parties encode into the lock name so they reconstruct the same one. It is never a fresh id comparison, because for ids where one is a prefix of the other the two orders can diverge. The sequential branches compare nothing -- the joiner that consumed the peer hello commits `initiator`/`joiner` and the party whose hello it consumed commits `responder`/`starter`, each unconditionally.

### Phase 1 -- rendezvous, lockless path

```
A put A-hello.json ; B put B-hello.json   (neither deletes the other)
each, on seeing the peer hello, writes a zero-length ack named after it
  (A writes A-B-hello-ack.json; B writes B-A-hello-ack.json)
each completes when the ack of its OWN hello exists in the listing
  (A waits for B-A-hello-ack.json; B waits for A-B-hello-ack.json)
```

Each party publishes its own hello temp-then-rename (`temp-hello-<uuidv4()>.tmp` -> `<id>-hello.json`), on this path and the lock path alike, so the final name never appears with a partial body and a hard kill mid-publish leaves only the temp.

The ack is a zero-length marker matched by name existence -- no body is read, and there is no read gate (a zero-byte file has no partial-sync window: its name appearing is completion). Legal contents: both hellos and both acks coexist and persist into the message loop (they are not deleted at rendezvous). This is why the `poll()` scan (site 3) must rely on the grammar discriminant: the party's own `<id>-hello.json` and ack share its message prefix and would be false positives under a bare `<id>-*` glob. Site 4 excludes the same files by waiting on `lastSentFile` by exact name (see [I2](#invariants)).

### Phase 1 -- terminal rendezvous failure

A rendezvous that fails terminally rolls back **this party's own rendezvous artifacts and nothing else**: its `<id>-hello.json`, the `<myId>-<peerId>-hello-ack.json` it wrote if it had already seen a peer hello, and its lock file on the lock path. The peer's hello and ack are left untouched -- they are the peer's to remove -- as are foreign files. This holds in **both** message-loop modes, and in retain mode it is the third of the three sites that can remove a file from the directory, alongside `cleanup()` (a no-op there) and the `--force-retain-sweep`-gated entry sweep ([I4b](#invariants)).

Deleting them is correct in retain mode, where every other deletion is reserved for an explicit operator escalation, for three reasons:

- **There is no transcript.** A terminal rendezvous failure means the message loop was never entered, so what is on disk is the failed attempt's own scaffolding -- a hello with two booleans, and a zero-length ack -- not the durable record retain mode exists to preserve. Retain's no-delete contract governs an exchange; this attempt produced none.
- **The artifacts are indistinguishable from a live peer's.** The directory has no entry-time liveness signal ([I1](#invariants)), so an abandoned hello reads to the next entrant exactly as a peer that arrived first, and the real partner's later arrival trips the at-most-one-peer-hello guard -- attributing the operator's own residue to a third session. What the entrant then does with it is mode-dependent (see *Entry-present peer hello* below); in neither mode does it produce an exchange.
- **It is retain mode's only rollback.** `responsibleFiles` is never populated in retain mode (every `add` is guarded -- see [I4a](#invariants)) and `cleanup()` returns before deleting, so nothing downstream removes these files. Without this site the mode with the strictest entry precondition ([Fresh directory in retain mode](#preconditions-for-a-correct-exchange)) would have no unwind at all, and every failed attempt would block the next one.

The one carve-out is a `BilateralModeMismatchError`, whose advertised hello is kept as the directory's terminal state in both modes (see [Bilateral configuration](#bilateral-configuration-detect-and-fail-never-negotiate)).

The rollback is issued through `safeDelete`, which swallows a transport-level delete failure, and it runs in-process: a hard kill (SIGKILL, OOM, power loss) leaves the artifacts behind, exactly as it leaves a delete-mode session's `responsibleFiles` unswept. Crash residue is this rollback's stated limit, not a case it covers; what the next run makes of it is the entry-present peer hello case below.

### Phase 1 -- entry-present peer hello

A peer hello already in the inbound directory when a run scans it is the one protocol file [I0](#invariants) tolerates, and the only one whose writer has demonstrated a propagation leg. It is also exactly what an interrupted run in this directory leaves behind, and the two are indistinguishable on disk. What the entrant does with it turns on the mode:

- **Lock rendezvous (the default).** The joiner fast path consumes it -- reads the body, deletes the hello, renames its own sentinel into place, and commits role/peerId -- against a party that may not exist. Nothing in the rendezvous waits, so the stall lands in the key exchange. The directory is left holding nothing of the leftover, which is why this failure is self-limiting after one run.
- **Lockless rendezvous (and therefore retain).** Both hellos coexist; the entrant writes its ack of the leftover and waits for an ack of its own that no one will write. Its own terminal rollback then removes exactly what it wrote, returning the directory to the same single leftover -- so without a bound this repeats on every invocation for as long as the directory is reused.

What each mode's failure looks like to the operator, and the recovery for it, are in [EXCHANGE_REFERENCE.md "Directory exclusivity"](../EXCHANGE_REFERENCE.md#directory-exclusivity).

**The bounded window.** That repetition is why the lockless barrier bounds the wait when the peer hello was present at entry: if it has not acknowledged this party's hello within the window, the rendezvous fails terminally (a `UsageError`, naming the file and the recovery step) instead of polling to `peer_timeout_ms`. It is armed on the entry-present case alone -- a hello that appears after entry is an ordinary peer arriving and is never timed -- and the leftover is **not** deleted: a hello this party cannot prove is its own is not its to remove, and `--sweep-exchange-files` remains the operator's assertion that no concurrent session is using the path. The terminal rollback of this party's own artifacts is unchanged.

The window is derived from the operator's own remaining budget rather than fixed, so it is never longer than they asked for and scales with the transport they configured:

```
window = max(rendezvousBoundMs(ENTRY_HELLO_ACK_WINDOW_MIN_POLL_CYCLES),
             remaining budget * ENTRY_HELLO_ACK_WINDOW_FRACTION)

deadline = now + window, armed only while window < remaining budget
```

with `ENTRY_HELLO_ACK_WINDOW_FRACTION` = 1/8 and `ENTRY_HELLO_ACK_WINDOW_MIN_POLL_CYCLES` = 6 (`fileSyncRendezvous.ts`, the only place either is set). At the defaults that is 7 m 30 s, against the full hour it replaces on every invocation. The measurement is taken from the moment this party's own hello is on disk: before that there is nothing for a live peer to acknowledge.

The deadline is armed strictly inside the peer budget or not at all: arming requires the window to fit strictly inside the remaining budget, so `now + window` cannot reach the peer timeout. That guarantee comes from the strictness of the comparison, not from `now` and the remaining budget sharing one clock reading -- a second, later reading only shrinks the remaining budget the window is checked against, so a window that clears the stricter check still leaves the deadline strictly under the budget. `now` and the remaining budget are read once regardless, as the simpler shape to reason about: a budget that cannot hold the window arms nothing, and an exhausted budget is therefore reported by the peer timeout rather than as a residue reading.

**The wall-clock floor under every rendezvous bound.** `rendezvousBoundMs(cycles)` is `max(cycles * poll interval, joinerRecoveryMs)`, and it holds both this window's floor and the I5a rendezvous read bound below. A poll interval is how often a party *looks*, which is independent of how long the transport takes to *answer*; a bound counted purely in cycles therefore expires inside a single round trip whenever the configured cadence sits well below the server's latency. Measured against two live connections over a latency-asymmetric transport, a purely cycle-derived window aborted a genuinely live partner mid-round-trip in about 650 ms and named its hello for removal. A party cannot calibrate this from observation either -- the slow side is the *partner*, whose operations it never sees -- so the floor is wall-clock. It reuses `joinerRecoveryMs` (default 30 s) rather than introducing a second constant, because that value already answers exactly this question for the lock path: how long a peer's publish-and-rename may take to land on this transport. Neither use extends a wait past what the operator configured -- the I5a read bound is capped at the remaining peer budget, and the window above is armed only while it fits strictly inside that budget -- modulo the transport operation already in flight when the budget expires, because the budget is checked *between* transport operations and never inside one. On a high-latency transport that overshoot is measurable: a lockless rendezvous against an entry-present hello, at a 5 s `peer_timeout_ms` and 2 s per transport operation, runs a little over 8 s before the ordinary timeout is reported. It is a property of the loop's between-operations budget check, which every wait here shares, rather than of the floor. On a budget too small to hold the floor, the ordinary peer timeout fires instead, with its ordinary message rather than a residue attribution.

**Limit -- the window remains a wall-clock heuristic.** The floor makes a false abort improbable, not impossible: a partner whose round trip exceeds `joinerRecoveryMs` on a budget large enough for the window to fire is alive and mid-answer when it fires. Nothing local distinguishes that partner from residue, which is why the terminal text names residue as a reading rather than a finding, puts a re-run ahead of the removal, and conditions the removal on the file surviving that re-run.

**Attribution.** Because the lock path commits role/peerId with no observation attributable to a live peer, the connection states the fact it does hold: `unconfirmedEntryPeerHello` names the entry-present hello until the first such observation clears it (the peer's ack of this party's own hello, or a peer message delivered to the application). A consumer that would otherwise attribute a later silence to the peer -- the CLI's peer-silence guidance -- reads it first and names the leftover and the local recovery instead, rather than sending the operator to a partner that may never have been there.

**A configured `peer_id` sidesteps all of this**: the leftover then holds this party's own id, so it is a self-hello the entry guard refuses immediately (exit 64) naming the file, before any wait. Being filename-based, that refusal is unaffected by a torn body. When an operator should set it is in [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#connectionoptions).

### Phase 2 -- message loop, delete mode

The sender writes `temp-<uuid>.tmp`, renames it to the final numeric-terminal name (so a watcher never sees a partial file under its final name), and then blocks in `hasOutstandingMessage` until the peer deletes it. The receiver's `poll()` reads one peer message once its on-disk size reaches the declared byte count, parses it, deletes it, and only then emits `data`. Parsing first leaves a corrupt fully-synced message on disk for inspection instead of destroying it ([I5b](#invariants)); deleting before the emit keeps the sender's go-ahead independent of whether the local hand-off succeeds. Legal contents: at most one outstanding message per direction.

### Phase 2 -- message loop, retain mode

The write path is the same as delete mode, but the receiver never deletes the message file. Instead it writes a zero-length `ack` marker named after the consumed message (`<myId>-<consumedMessageName>-ack.json`) before emitting `data`. This is the same construct as the lockless rendezvous ack, applied to a message instead of a hello: only the receiver writes one (delete mode signals the same thing by deleting the file).

This ack is a **durable-received** acknowledgment, not an application-consumption one. By the time it is written the message is a fully-synced file that retain mode never deletes, so it is already durable. That is what licenses writing the ack before the `data` hand-off, and it keeps the sender's go-ahead independent of whether the local hand-off succeeds. The order must not be flipped to emit-before-ack: an ack-write failure after a successful `emit` would re-deliver an already-consumed message. Conversely, because the ack precedes `emit` while `recvSeq` advances only after a successful `emit`, the ack write is idempotent per `<NNN>` -- a message reprocessed after a transient receive failure is not acked twice. The marker name is also deterministic per message (a pure function of the consumed message's fixed name), so even if the per-`<NNN>` write guard were bypassed the re-write would reuse the identical name and create no duplicate file; the guard only saves a redundant `put`+`rename`.

The sender gates its next send on the existence of the ack of its just-sent message, located by constructing the expected name `<peerId>-<lastSentStem>-ack.json` from the stem it already holds in `lastSentFile` -- not by parsing a marker on disk. The ack is zero-length, so the gate is name existence rather than a byte-count comparison. No exchange file is deleted as a protocol step.

Because no message is ever deleted, every consumed message stays on disk on every transport -- not only those that fail to propagate deletions. The receiver therefore tracks the next unprocessed message with an in-memory per-session counter, `recvSeq`: it processes only the peer message whose `<NNN>` equals `recvSeq`, then increments it. That counter stays aligned with the peer's monotonic `<NNN>` sequence only because of the clean-directory precondition ([I0](#invariants)), on which the [I8](#invariants) counter shadow rests.

### Phase 3 -- cleanup and close

`close()` calls `cleanup()`, which removes every file in `responsibleFiles`. In retain mode it removes nothing at all: it returns before deleting, because the directory is the durable transcript. The in-flight `temp-*.tmp` is outside `cleanup()` in both modes -- it is never tracked in `responsibleFiles`, so `cleanup()` never sees it; it is swept inline in `send()`/`writeAck()` instead (see [I4b](#invariants)). `close()` and `cleanup()` must not diverge on this.

Before `cleanup()`, in delete mode the side that sent the terminal frame **drains** it: it polls the directory until the peer consumes (deletes) `lastSentFile`, so a clean close never sweeps a frame the peer has not yet read. The drain is bounded by a short fixed budget `TERMINAL_FRAME_DRAIN_TIMEOUT_MS` (60s), applied as `min(TERMINAL_FRAME_DRAIN_TIMEOUT_MS, peer_timeout_ms)` measured from when the drain begins (after the abort-marker decision gate, not the first instruction of `close()`) -- **not** the full `peer_timeout_ms` (default one hour). At teardown the exchange result is already computed and persisted, and on timeout `cleanup()` deletes the frame as a fallback, so the drain protects nothing durable (durability is decoupled from deletion). A longer bound would only make a clean close against a crashed or departed peer block for up to the hour before exiting, with no gain, while a peer that legitimately needs the frame reads it from `cleanup()`'s fallback delete on its own next listing. The constant is sized to a sync tool's flush latency (the peer's poller listing, consuming, and the deletion propagating back), on the order of the per-operation liveness bounds, and is internal-only (not a config setting) like `joinerRecoveryMs`; it would only need revisiting if a transport's round-trip propagation routinely exceeded it, re-introducing the premature-sweep race the drain exists to avoid. Each drain `list()` is additionally raced against the time remaining to the deadline (not its own fresh `peer_timeout_ms` `boundTransport` budget, which may now be far larger than the drain window), so a list issued late in the drain cannot run past the deadline. Retain mode skips the drain entirely: it never deletes a `*.json`, so the final send persists as transcript and the peer reads it whenever it next lists. The `min()` cap means a `peer_timeout_ms` configured below the fixed budget still bounds the drain at the smaller value, never longer than the operator asked.

`close()` ends the transport last, after `cleanup()`. That wait is bounded on the same terms as the drain and for the same reason, by `CONNECTION_CLOSE_TIMEOUT_MS` (30s) applied as `min(CONNECTION_CLOSE_TIMEOUT_MS, peer_timeout_ms)`, internal-only rather than a config setting. It bounds core's **wait** for a transport it does not own, not the connection itself -- abandoning the wait closes nothing -- so a transport holding a session is obliged to bound its own close and close from its own side (`FileTransportClient.end`); the SFTP channel's forced close is specified in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md). A rejection is logged at debug and teardown proceeds, so a transport that cannot finish closing never changes what the run produced or reported.

## Session lifetime across an idle boundary

The state machine above holds whether the transport keeps one session for the whole exchange or releases it at the loop's idle boundaries. What a releasing transport adds is stated here: when the loop's session exists, and how teardown obtains one. On the `sftp` channel the `connection_per_poll` option selects that behavior; when an operator should choose it is in [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#sftp-only-options), and what a run counts and warns about in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#sftp-mid-exchange-session-recovery).

**The option is local, not bilateral, and so is outside the state machine's shared alphabet.** How a party dials leaves no trace in the shared directory: it writes no file, and the hello envelope holds the two bilateral flags only (see the [file taxonomy](#file-taxonomy)), so `connection_per_poll` is not advertised and a difference between the parties cannot be detected -- or fail -- at rendezvous. One party may cycle its session while the other holds one, with no effect on which filenames are legal at any phase. This is why the option appears nowhere in the phases, the invariants, or the [preconditions](#preconditions-for-a-correct-exchange), and why it is not subject to the bilateral stance in [Bilateral configuration](#bilateral-configuration-detect-and-fail-never-negotiate).

**The per-cycle lifetime is the poll loop's property.** A session is established at the start of each poll cycle and released before the loop goes idle again, so it need only survive that cycle's operations rather than the whole exchange. Two idle stretches are still spanned by one session: the rendezvous that precedes the loop, which holds one across its wait for the partner, and a boundary reached while an operation this side has issued is still unsettled, which keeps its session rather than cutting that operation off the wire. What a boundary is held for, and what ends a hold, are in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#sftp-mid-exchange-session-recovery).

**Every boundary has exactly one outcome.** One invocation of the transport's idle release is one boundary, and it concludes in exactly one of the outcomes below -- the first of them that applies, in the order given. What belongs here is which of them leave the loop a session and which do not; what each does to the operator-facing accounting, and what is counted, capped, exempt and bounded, is in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#sftp-mid-exchange-session-recovery). A new outcome appends a row. A transport that keeps one session for the whole exchange releases nothing, so it reaches no boundary at all.

| outcome | reached when | the loop's session after |
| --- | --- | --- |
| `declined` | its bounded wait for the session transition ahead of it expired | unchanged, and possibly still live -- whatever that transition leaves |
| `skipped` | it reached the front of the queue with teardown already latched | teardown's |
| `held` | an operation this side had issued was still unsettled | live, and spanning this gap |
| `alreadyEnded` | no session to release, its generation already ended and charged to whatever took it | none |
| `noSession` | no session to release, its generation still live -- a partner-side drop this boundary is the first thing to observe | none |
| `closedByPeer` | the peer's FIN was already consumed, so the release's own `end()` closed nothing, and the session cleared | released |
| `releasedOverEndedTransport` | this side's write half had ended without this release -- the withheld-close drop's shape -- and the session cleared | released |
| `released` | neither half had ended, so the release's own `end()` ended the transport, and the session cleared | released |
| `didNotClose` | the session did not clear and the transport is still writable, which that `end()` should have ended | live, and held across this gap |
| `destroyDidNotClear` | this side destroyed the transport and the session still did not clear | live; the release raises |
| `forced` | this side destroyed the transport past the release's bound and the session cleared | released |

The three that turn on who ended the transport are classified before the close is driven, because an operation already on the wire is torn by that close and reads the boundary while the release is still running; `forced` leaves that classification standing, since the forcing says how the boundary concluded rather than who ended the transport beneath it.

**Teardown obtains a session ahead of the drain's deadline.** The release runs at the reschedule and only while the poller is still active, so a cycle whose poller was stopped before it reached that boundary -- by `close()` or by a terminal error -- keeps its session, while a `close()` reached from the inter-poll gap finds the session the last boundary released. `close()` therefore drives the transport's re-establishment before the terminal-frame drain's clock starts: billed to that budget instead, a re-dial handshake could expire the drain and drop the terminal frame to `cleanup()`'s fallback delete. It establishes nothing where a session is already live, and nothing on a transport that keeps one for the whole exchange or holds none at all; it is best-effort and non-throwing, as `close()` must be -- a failed or refused re-dial leaves teardown exactly where a still-released session leaves it.

**The abort-marker write obtains one the other way.** It is not preceded by that re-establishment: it rides the transport's own within-cycle recovery instead, because a re-establishment ahead of it would race the write's own re-dial on the one shared session. The two teardown writes are asymmetric by construction -- the drain's session is established for it, the marker's is recovered under it -- and the marker write is the earlier of the two, running ahead of both the drain and that call.

## Invariants

These are the testable properties the state machine must preserve. New work should be checkable against this list.

- **I0 -- clean entry (classification with an opt-in override).** At `synchronize()` start (enforcement site 1), with no sweep flag, the directory must be empty except for at most one *peer* hello (a `-hello.json` whose recovered id is non-empty and not this party's own; a bare `-hello.json` slices to an empty id and is an unexpected protocol file, not a peer hello -- see site 5) and any foreign files. Foreign files are snapshotted (in-memory) and tolerated in both modes. Any other protocol file -- a second or self hello, a lock file, an ack marker, a `joining` sentinel, or a message (including a message-shaped `<id>-<digits>.json`, which matches the grammar and is therefore a protocol file, never foreign) -- is a terminal `UsageError`. The abort marker is the one kind whose disposition here is mode-dependent: in delete mode a well-formed `<id>-abort.json` under any id is swept by site 1(d) before this guard runs and so never reaches the rejection, while in retain mode it is rejected exactly like the kinds above. A bare `-abort.json` recovers no id, is swept in neither mode, and is rejected in both. With `--sweep-exchange-files`, the directory is first inspected for a retain signal (local retain mode, a peer hello advertising `retain_files=true`, or a retain-only message ack -- an `-ack.json` whose two trailing dash segments, the NNN and byte count, are both numeric); if none, every protocol-grammar file is deleted and entry proceeds against the resulting clean slate. Foreign files are never deleted by the sweep. When a retain signal is present the bare flag refuses; sweeping then requires `--force-retain-sweep`. This is the precondition the counter arguments in I8 rest on (a swept directory holds no message at entry, and a snapshotted foreign file is never counted -- see [I8](#invariants)); it also code-enforces retain mode's fresh-directory requirement (see [Fresh directory in retain mode](#preconditions-for-a-correct-exchange)), which holds unless the retain guard is passed. The `ignored` set remains the entry point for the orphaned-temp sweep (a crashed in-flight write is `safeDelete`d and added to `ignored` rather than rejected), which targets only the protocol's own `temp-<uuidv4()>.tmp` shape (`isProtocolTempName`); a foreign `temp-*.tmp` with a non-UUID stem fails the grammar and is a grammar-failing name handled by the foreign snapshot, not deleted. The foreign snapshot is a sibling tolerance mechanism for grammar-failing names. What either refusal can name when it fires, and the budget that bounds the enumeration, are in [Bounded error enumeration](#bounded-error-enumeration) below.
- **I1 -- one peer at rendezvous.** More than one peer hello is a terminal usage error ("other sessions using this path?"), in both rendezvous paths. **Carve-out:** `--sweep-exchange-files` overrides this -- and a wider set than just "a second hello". Under lockless rendezvous a live peer the operator wrongly believed dead may have written its hello and its `-hello-ack.json` and a first message/ack; the sweep deletes every peer-prefixed protocol file, not only a second hello. The flag is the operator asserting the directory is theirs to clear and no concurrent session is live -- a responsibility the protocol cannot take on, since the directory has no entry-time liveness signal (a stale hello is byte-identical to a fresh one; `modifyTime` is unreliable). The residual is real: a delete-mode sweep of a peer the operator misjudged as dead silently corrupts that peer's exchange. The pre-sweep retain-signal inspection narrows only the cross-mode case (it refuses to destroy a retain transcript without `--force-retain-sweep`); it does not make the sweep safe against a live delete-mode peer.
- **I2 -- grammar routing.** A file is routed as a message iff its terminal `.json` segment is all digits. Control files (`hello`, `ack`, `joining`, `lock`) are never routed. An ack marker is the case that makes this critical: a message ack holds the acked message's `<NNN>` and `<byteCount>` mid-name (both all-digit), but its terminal segment is `ack`, so right-anchored parsing routes it as a control file. Routing is what this invariant governs, and nothing else touches it: neither `unexpected_files`, which decides only the *non-routing disposition* of a non-message file during the loop, nor the entry foreign snapshot, which is a non-routing tolerate and belongs to [I0](#invariants).

  A party's **own** files fall out of the same rule -- its hello and ack have non-numeric terminals, so site 3 never routes them as self-messages, which matters because under lockless rendezvous they persist into Phase 2. Site 3 holds that with the discriminant itself (`parseMessageByteCount(...) !== undefined`), never a bare `<id>-*` glob or a per-type suffix list. Site 4 (`hasOutstandingMessage`) holds it more strongly, and by a different mechanism: it waits on the single exact name in `lastSentFile`, so every other file this party owns -- control file or earlier message -- is excluded whatever its terminal token.
- **I4a -- delete-mode crash safety.** In delete mode, every committed file a party creates is tracked in `responsibleFiles` so a mid-write fault still leaves it swept by `cleanup()` at the next `close()`. *When* the `add` happens depends on the write discipline, and the two are not interchangeable. A **direct-write** to the final name (`lock` via `createExclusive`) is pre-tracked *before* the call, because the final name can be left on disk by a call that then throws (e.g. `createExclusive` creates the file on the server but the handle-close fails). A **temp-then-rename** write (`hello` in the rendezvous publish, `message` in `send()`, `ack` in `writeAck()`, and the lock joiner's rename of its sentinel into `<id>-hello.json`) is tracked *immediately after* the rename, because the final name only appears at that atomic step and the `add` follows it with no throwable statement between. So there is no reachable orphan window short of a rename that throws-but-succeeded -- a pathological mode the message write has always accepted identically. The joiner's `joining` sentinel is the one direct-write tracked *after* its call rather than before, on that same reasoning: a plain `put` leaves the final name behind only by throwing-but-succeeding, and its `add` follows with no throwable statement between. (`responsibleFiles` is in-memory and `cleanup()` only runs in-process at `close()`, so a hard process kill loses the set and sweeps nothing regardless of add timing; pre-tracking guards the *caught-exception* path, not a kill.) Every `add` is guarded by `!retainFiles`, because retain mode never sweeps (I4b) so tracking would serve no purpose. Two files are direct-written to their final name: the `lock`, which has no payload at all, and the joiner's `<id>-joining.json` sentinel, which holds the hello envelope. Every file whose body another party reads -- the `hello` on both rendezvous paths, the `message`, and the `abort` marker (tracked in neither mode, but published on the same discipline) -- is published temp-then-rename, so no reader can observe one under its final name before it is complete, which is what makes a torn body unrepresentable rather than merely unlikely (see I5a). The sentinel does not weaken that: no party ever reads it (the peer matches it by name existence -- see the `joining` taxonomy row), and it is itself the staged body the joiner renames into `<id>-hello.json`, so that hello appears atomically like any other. A sentinel torn by a crash is caught by the next run's entry guard (I0), which classifies by name -- tolerable because nothing gates on its body, not because it cannot be torn.
- **I4b -- retain mode never sweeps (except at two bounded sites).** In retain mode `cleanup()` is a global no-op: the directory is the durable transcript, so no `*.json` is removed by `cleanup()` and `responsibleFiles` membership is irrelevant. `close()` and `cleanup()` must not diverge on this. The literal statement (about `cleanup()`) survives, but its spirit ("retain never deletes a `*.json`") does not, at exactly two sites. **(a) The gated entry sweep.** A `--sweep-exchange-files --force-retain-sweep` entry sweep deletes `*.json` transcript files at *entry*, wiping a prior transcript before a fresh exchange -- an entry-time operation under explicit operator escalation, not a `cleanup()` deletion. **(b) A terminally failed rendezvous.** The failing party removes its own hello, and its rendezvous ack if it wrote one, before the failure propagates ([Phase 1 -- terminal rendezvous failure](#phase-1----terminal-rendezvous-failure)), the `BilateralModeMismatchError` carve-out excepted; it is retain mode's only rollback, and it fires only where the rendezvous produced no exchange. Corollary the inspection relies on, stated to what those two sites leave standing: a directory holding a retain **transcript** advertises itself via the `retain_files=true` hello of the party that wrote it, which is what makes the pre-sweep retain-signal check reliable for a transcript already on disk at inspection time. (b) cannot remove such a hello, because a party whose rendezvous failed terminally wrote no transcript. What the corollary does not claim, and must not be widened back into, is that *every* retain directory advertises itself: a terminally failed retain rendezvous advertises nothing, and holds nothing the inspection needs to protect. In both modes the in-flight `temp-*.tmp` is never tracked in `responsibleFiles`; it is cleaned inline (best-effort) in `send()`/`writeAck()` and in the rendezvous hello publish, independent of `cleanup()`. That inline sweep is best-effort at the core layer only: a session-holding transport whose session is momentarily gone records the cleanup and re-issues it at its next re-establishment, so neither mode's run ordinarily ends holding a temp without it ever entering `responsibleFiles`. The re-issue is itself best-effort, under stated limits (the run, and the transport's cap on how many it records) -- see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#sftp-mid-exchange-session-recovery).
- **I5a -- partial-sync read safety.** A file whose body is read for content must not be read before the sync tool has finished writing it. The message is the only payload-bearing file that is byte-count gated: it self-describes its full size in the filename and the receiver waits until the on-disk size reaches it. The hello has no byte-count segment, so it uses a read gate (`readControlFileWithGate` in `fileSyncRendezvous.ts`) that retries on a short or unparseable read until its deadline, then validates `HelloEnvelope`. **Every caller passes a bounded deadline, never the peer timeout.** At the rendezvous reads that is `rendezvousBoundMs(RENDEZVOUS_HELLO_READ_POLL_CYCLES)` -- six poll cycles under the wall-clock floor described above -- capped at the remaining peer budget so it is never longer than the operator asked for. Six cycles is three times the pre-sweep inspection's two, because this read races a peer that is actively publishing rather than inspecting a stale directory. It is not larger still because the hello is published temp-then-rename: the final name appears only at the atomic rename, so the body is complete before the name is visible, and what a rendezvous read waits out is propagation, never a write in progress. The floor is what keeps the bound meaningful when the configured cadence sits below the transport's round trip -- six cycles of a 10 ms poll is 60 ms, which abandons a hello a slow transport has merely not finished propagating. Exhausting the bound is terminal for that rendezvous. The message it throws states the *hello's provenance* (`PeerHelloProvenance`), which every caller supplies and which is the same distinction the bounded ack window is armed on. The hello the entry scan found is named as *possible* residue, while one that appeared *after* that scan gets no residue attribution at all -- the run watched it arrive, so a peer whose publish is still landing explains it as well as a leftover does. Both prescribe a re-run first and condition any removal on the file surviving it; neither asserts which of the two indistinguishable causes it found, and only the entry-present text states the additional "no session shares this path" condition on the removal. Both texts are terse: the fixed text and the path share one rendered cause-chain link, so every character of text is one the path -- which is what the recovery step acts on -- does not get, and the budget each leaves is pinned by a test rather than asserted in a comment. A call site the entry-present hello cannot reach classifies by that comparison rather than by asserting its own unreachability. The throw is **not** a `UsageError`, because the pre-sweep inspection classifies a `UsageError` from this gate as terminal and everything else as retain-uncertain, so promoting it would turn that bounded read into a hard refusal. The ack marker needs neither: it is zero-length, so its name appearing *is* completion -- there is no body to gate or read. The hello is therefore the only control file whose body a *peer* reads through this gate, which is not the same as being the only one with a payload. The `joining` sentinel holds a hello envelope but is matched by name and never read, and the abort marker is read under its own `ABORT_MARKER_MAX_BYTES` cap and a pre-`get()` listed-size refusal rather than a partial-sync gate (see the [file taxonomy](#file-taxonomy) for both). **Control-file payload fields are camelCase on disk** (`locklessRendezvous`, `retainFiles`) -- a control file is a protocol message, not user-facing schema, so the snake_case-in-YAML config convention does not apply and there is no `camelizeKeys` conversion on the serialize or parse path. A later envelope-field addition must stay camelCase to match. **The gate is reached at *entry* as well**: the pre-sweep retain-signal inspection reads the peer hello body through `readControlFileWithGate` to check `retain_files`, validating against the hello schema (not a strip-unknowns base, which would read an absent flag as a false "no signal"). That read MUST be bounded -- a near-future `timeToLive` of a small multiple of the polling frequency, never the full `peer_timeout_ms` -- so a non-resolving body cannot stall the sweep; an unresolved read is treated as retain-uncertain and refuses the bare flag. I5b still holds at this site: a fully-synced hello body that fails the schema is a terminal `UsageError`, the same classification as any malformed-hello-payload rejection. (The message-ack half of the inspection is filename-only and reads no body.)
- **I5b -- a completed body that fails validation is terminal (an instance of I6).** Once a body has reached its declared size the partial-sync excuse is exhausted: a parse or schema failure is genuine corruption, not a retryable short read, and is a terminal `UsageError`. For the hello this is the `HelloEnvelope` schema check after the gate. For messages in `poll()` it is an envelope-deserialize failure (`deserializeFileSyncMessage`, including an unrecognized version byte), a `parseBoundedJson` failure on a `type 0` payload, a body-`seq`/filename-`NNN` mismatch, or a duplicate `NNN`; each stops the poller. Transient transport failures (and the unreachable emit-handler throw, see I8) are *not* `UsageError`s and reschedule instead.
- **I6 -- terminal failure, no caller retry.** `synchronize()` and `send()` always present a terminal failure to the caller; the caller does not retry. Any bounded retry is internal. The I5b classification and the I8 counter discipline are instances of this contract at specific read/write sites. The "fail, then re-run with `--sweep-exchange-files`" recovery is an *operator re-invocation of the CLI with different flags*, not an in-process caller retry: `synchronize()` stays terminal per invocation, so I6 is preserved -- "on a re-run" means a new process, not a new in-process retry path.
- **I7 -- filename order, never id order, wherever the lock path compares the two parties.** There are exactly two such places: the two-hello collision's role assignment, and the lock name both parties reconstruct. Both compare hello *filenames*; neither compares ids, because for ids where one is a prefix of the other the two orders can diverge. The sequential branches assign roles unconditionally and compare nothing, so the invariant has no claim to make about them.
- **I8 -- in-memory counters are a shadow of on-disk NNN state, not an independent source of truth.** `seq` (next NNN to write), `recvSeq` (retain: next NNN to read), `lastAckedNNN` (retain: ack idempotency guard), and `lastSentFile` (the name of the last message this party sent -- read by the delete-mode drain and the retain-mode ack construction) are all in-memory projections of the shared directory's NNN sequence. Three rules keep the shadow aligned; breaking any one silently desynchronizes the two parties:
  - `seq` advances only after a message's durable `rename` in `send()`, so a failed write never leaves the counter past an NNN the peer cannot have. The counter's position is not a licence to reuse the slot: a `send()` can reject over a message the peer did receive. A transport whose publish landed durably and was consumed before it could confirm that rejects with `TransportPublishIndeterminateError` ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#sftp-mid-exchange-session-recovery)). The peer may already have emitted that message to its application, and nothing on the receive path would reject a second message arriving under the same NNN (delete mode does not read the body `seq` at all, and retain mode's NNN filter silently skips it). So the loop latches that publish and the next `send()` fails with a terminal `UsageError` naming the spent NNN, rather than writing a second message the peer would read as a first. The latch is per-session and cleared by `resetSessionState()`.

    Both messages the operator can reach here -- the rejection of the torn publish itself and the refusal of the next `send()` -- prescribe one recovery: re-run the exchange in a clean directory, both parties starting the new exchange fresh. They share a single sentence in `fileSyncMessageLoop.ts` so they cannot diverge, and each holds `psilinkRecoveryHintEmitted`, which suppresses the CLI's generic post-handshake "retry the exchange without re-inviting" advisory. A plain retry is not sufficient for this condition, because what is unsettled is the publish's fate rather than the directory's contents. The failed attempt's abort marker does not stand in the way -- site 1(d) sweeps it whatever ids the retry draws -- so a retry into the same directory runs a whole fresh exchange whenever the message never landed or the partner had already consumed it. A publish that landed and was *not* consumed instead leaves that message file behind, which I0's clean-entry guard refuses on both sides -- the abort-marker sweep matches only the control grammar, so a leftover message is untouched by it. The publishing party cannot tell the two apart -- that is exactly what its transport could not settle -- so it prescribes the recovery that holds either way. The tag makes each message's length critical -- with the generic advisory suppressed, the remedy is the only next step printed, and it has to clear the display boundary's per-error cap. The transport's own rejection is caller-neutral (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#sftp-mid-exchange-session-recovery)), so `send()` restates it as a message-specific, tagged rejection holding the transport's as its `cause`, which keeps the destination and the transport status on their own rendered lines under their own caps.
  - In retain mode, `recvSeq` advances only after a successful `emit` in `poll()`. The ack marker (and `lastAckedNNN`) is written before `emit`. So a transient (non-`UsageError`) failure during receive -- e.g. an ack-write transport hiccup -- reprocesses the never-deleted message on the next poll and acks it exactly once: never skipped, never double-acked. (The ack name is a pure function of the message's fixed name, so even a bypassed `lastAckedNNN` guard re-derives the identical name and writes no duplicate file; the guard only saves a redundant `put`+`rename`.) A `UsageError` reaching `poll()`'s catch is terminal and stops the poller instead (I5b). This reprocess path covers a failure *during* receive, not a throw from the `data` consumer. The sole production consumer (`deliver()` in `messageConnection.ts`) latches an overflow as a non-throwing failure and never throws synchronously, so an emit-handler throw is unreachable defense-in-depth.
  - All four counters -- and the spent-slot latch above -- reset together via `resetSessionState()` at every session-boundary path: the rendezvous outer catch, the joiner prefix-at-dash error, and `close()`. A partial reset that left any counter non-zero would corrupt the next session on the same instance.

  The shadow is only safe because of I0 (clean entry): both counters begin at 0 against an empty directory and therefore stay aligned with the peer's monotonic NNN sequence, which also starts at 0. The I0 relaxation preserves this by rejection, not by exclusion from message selection. The grammar discriminant is digits-terminal, not prefix-gated, so a `<peerId>-<digits>.json` does pass `parseMessageByteCount` and is selected at `poll()` -- the foreign snapshot does not make it inert there (that is the mid-loop unexpected-file policy's concern). Alignment holds for two reasons: a swept directory holds no message at entry (counters start at 0 against a clean slate), and a message-shaped name is never snapshotted -- with no flag it is rejected at the entry guard, so no pre-existing message reaches the loop. Should such a name reach `poll()` by another path (appearing after entry, or surviving a sweep), it is selected and then terminally rejected as a non-conforming `Message` body (I5b) without advancing `recvSeq`: alignment holds because the file is *rejected, not counted*.

  Enforcement sites: `resetSessionState()` (session-boundary resets), the post-rename `this.seq = seq + 1` in `send()` (I8 write rule), the `indeterminatePublish` latch set at that same `rename` and read at `send()` entry (the spent-slot rule), and the post-emit `this.recvSeq++` guarded by the pre-emit ack write in `poll()` (I8 receive rule).

  **Production composition note.** The reschedule-on-transient half of the second rule is a property of `poll()` *in isolation*. In the CLI a `FileSyncConnection` is never consumed directly: `apps/cli/src/protocol.ts` always bridges it through `fromEventConnection` (`messageConnection.ts`), whose `error` listener routes every emitted `poll()` error into `QueuedMessageConnection.fail()`. `fail()` synchronously calls `hooks.close()` -> `conn.close()`, and `conn.close()`'s first statement -- before any `await` -- is `conn.stop()`, so `pollerActive` is cleared within that synchronous prefix, before `poll()`'s `finally` runs (`conn.close()` is itself `async`, but only its leading `stop()` must run synchronously for this to hold, and it does) -- so the reschedule that `finally` would otherwise perform never happens. Under composition, therefore, the *first* emitted `poll()` error is terminal: the parked `receive()` rejects exactly once (naming the underlying cause, which `asConnectionError` copies into the reported error's message and attaches as `cause`, rather than the bridge's generic peer-silence inactivity message), the connection stops, and the never-deleted retain message is not reprocessed. A hypothetical retry counter on `poll()` could never reach 2 in production for this reason. So the rule above (and the isolation unit tests that drive `poll()` without the bridge -- e.g. the transient-`list()`-recovery test in `packages/core/test/connection/fileSyncConnection.test.ts`) describes the module standalone; the composed contract is pinned by the bridged test that lives alongside them.
- **I9 -- one outstanding message per direction (delete mode).** The delete-mode sender blocks in `hasOutstandingMessage` until the peer deletes its last message, so at most one message per direction is ever in flight; this is the channel's flow control and the property that bounds legal directory contents in Phase 2 delete mode. Retain mode imposes no such bound -- messages accumulate as the transcript and the receiver selects the next by `recvSeq` (I8).
- **Untouched by session-start directory hygiene.** I2 (routing discriminant -- the foreign snapshot is a non-routing tolerate; only the post-entry classification was extended, by the mid-loop unexpected-file policy), I3 (the snapshot adds no `<id>-`-numeric file), and I4a (swept files predate the session and never entered `responsibleFiles`, which `synchronize()` prunes against the live listing before the guard) are untouched. So are I7 (sweep and inspection run before role logic) and I9 (entry precedes Phase 2). I5a is not in this list: the pre-sweep inspection reads the hello body through its gate (see I5a above).

## Preconditions for a correct exchange

These operator-level requirements are part of the model: violating any of them silently corrupts or stalls the exchange, and several are not otherwise enforced in code. They are collected here so they live in one place rather than scattered across feature docs.

- **Dedicated directory.** One active exchange, exactly two parties, per directory, for *protocol* use. The requirement is on the protocol-grammar namespace rather than the directory as a whole, because foreign names are tolerated; what that tolerance covers is in [EXCHANGE_REFERENCE.md "Directory exclusivity"](../EXCHANGE_REFERENCE.md#directory-exclusivity), and where this model enforces it is [I0](#invariants) and enforcement site 3.
- **Matching builds.** The file-sync control-file (hello) schema has no `protocol_version` field; both parties run compatible builds and the payload schema is a hard contract. A payload-schema change (e.g. adding hello flags) is a flag-day that both sides must deploy together. This precondition is about the hello control file; the transport-agnostic terms exchange separately includes a build-level `protocolVersion` that fail-closes with an actionable message on a mismatch, and a foreign message-envelope version byte is named as a likely version mismatch (see the [message body format](#the-single-critical-invariant-the-filename-grammar) above and [PROTOCOL.md](PROTOCOL.md#protocol-version-reconcile-at-the-terms-exchange)).
- **Identical bilateral flags.** `lockless_rendezvous` and `retain_files` must match on both sides.
- **Fresh directory in retain mode.** Retain mode never deletes, so a reused directory leaves a prior exchange's files: a stale message would be mis-consumed against the `recvSeq` counter and a stale ack marker could prematurely release the sender's gate, corrupting or stalling the exchange with no error. The entry guard (site 1) rejects a non-clean start in both modes, which is what protects retain specifically -- so this is advisory-unless-the-retain-guard-is-passed: `--sweep-exchange-files --force-retain-sweep` lets a non-clean retain start proceed by wiping the prior transcript first. Without that explicit escalation the guard still rejects, so the precondition holds for any normal invocation. In a [split configuration](#split-inboundoutbound-directories) the check runs on **both** the inbound and the outbound directory.
- **Distinct, non-prefix peer ids.** When `peer_id` is configured, the two ids must be distinct, and neither may be the other extended by `-` (e.g. `site` / `site-2`), which would break message prefix-routing. UUIDs (the default) satisfy this automatically.

## Bilateral configuration: detect and fail, never negotiate

`lockless_rendezvous` and `retain_files` are bilateral agreements with no negotiation step. The deliberate stance is **mismatch detection and clear failure, not capability negotiation**: a party advertises its own flags in its hello (`HelloEnvelope`, the two required fields) and fails fast with a both-sides-named error when the peer's differ. It never adapts to the peer's mode. This boundary is intentional and critical -- advertising flags is one step toward negotiation, and the design explicitly stops there. Do not let mismatch detection grow into capability negotiation without revisiting this decision.

**A declared flag on the invitation stays inside that boundary, and this is the decision revisited on the record.** The invitation states the inviter's `retain_files` as [`inviterRetainsFiles`](#retain-mode-declaration-on-the-token), which is a *third* home for a bilateral flag beside the connection config and the hello -- so the stance above has to answer for it rather than be quietly eroded. The boundary the stance draws is **adaptation**: what it forbids is a party changing its own mode to match the peer's, because that turns a misconfiguration the operator must fix into a silent behavior change neither operator chose. A declaration changes no mode. Nothing on the accept path reads the field into a connection, the accepting party still sets its own half from its own config, and a disagreement still reaches the hello and still fast-fails there with both sides named. Every mismatch that failed before this field fails after it, in the same place, with the same error. Disclosure is not negotiation.

What it buys is a consent fact, not a capability. Retain mode is the disclosure of this transport that outlives the run -- the rendezvous location becomes a permanent transcript -- and without the declaration a partner learns of it from a failed run, from an accept kit the inviter may not send, or from word of mouth: never before the point at which they consent. The declaration is therefore scoped to that justification and no further. It is not read, not applied, and not answered; the token holds `retain_files` alone and not `lockless_rendezvous`, which is equally bilateral and equally fast-failing but has no disclosure content of its own.

That scope is the line to hold. The next flag proposed for the invitation is admitted only if it discloses something an acceptor consents to, and the mechanism stays declaration-only: an accept path that *reads* a declared flag into its own configuration -- even to pre-fill it, even to warn -- has crossed from disclosure into adaptation and needs this section rewritten, not extended.

One derivation sits inside that line, which is why the sentence above says *declared* flag: a split-directory `connection_endpoint` seeds the acceptor's connection with the retain trio -- `retain_files`, `lockless_rendezvous`, `timestamp_in_filename` -- at `connectionFromEndpoint` and `applyEndpointSplitDirectories`, which logs the seeding. That trio is derived from the endpoint's shape, not from any flag the inviter declared: a separate outbound directory is unusable without it, since `ConnectionConfigSchema` refuses the pair unless retain mode is on, so what the acceptor is seeded with is entailed by the locator it was handed rather than adopted from a mode the peer announced. It is written into the acceptor's own connection block, where the operator reviews it, and the acceptance surfaces state it as a consent fact ([Retain-mode declaration on the token](#retain-mode-declaration-on-the-token)). A newly proposed flag is weighed against the sentence above, never against this derivation.

The same bilateral-vs-local split governs the CLI surface: `lockless_rendezvous`, `retain_files`, and `timestamp_in_filename` get command-line flags (`--lockless-rendezvous`, `--retain-files`, `--timestamp-in-filename`) because an operator must coordinate them with the peer at invocation, whereas a purely-local tuning preference such as `unexpected_files` -- which the two parties may set differently -- is configured in YAML only. CLI flags are otherwise reserved for bilateral settings that must match across parties; local tuning lives in the connection config.

`--outbound-path` is the deliberate exception to that rule: a local setting (each party chooses its own inbound and outbound directories, which the deployment bridges) that is nonetheless a CLI flag. The justification is that it is a *locator*, not a tuning preference -- the companion to the inbound directory, which is already a command-line argument (the server URL or positional path) -- so pairing it with that argument on the command line is the natural surface, where a per-party tuning flag would not be. The CLI maps the URL/positional path (or, for `psilink exchange`, the loaded config's directory) to `inbound_path` and `--outbound-path` to `outbound_path`, for both `sftp` and `filedrop`, in the single `applyConnectionOverrides` chokepoint every bootstrap command routes its connection through (so the four commands share one mapping). It then validates the assembled connection through the same `ConnectionConfigSchema` a hand-written `psilink.yaml` is parsed with, so the split-mode preconditions -- the pair set together, the two directories distinct ([`pathsResolveToSameDir`](#split-inboundoutbound-directories)), the filedrop-absolute rule, and the retain-mode requirement -- reject identically whether a split arrived from flags or from YAML. Only the retain-mode requirement is additionally fast-failed at the CLI, with a `--retain-files`-named message, before the schema runs; the rest surface with the schema's own messages. The invitation-borne role swap for a split exchange (one party's outbound seeding the other's inbound) is a separate mechanism from this local CLI surface: it rides the invitation connection-endpoint wire format and is applied once at accept-seed time through `connectionFromEndpoint`, not through `applyConnectionOverrides`. Both accept modes consume it -- offline seeds the whole block from it, online grafts only its swapped pair onto the URL-built connection -- and an explicit `--outbound-path` (which does route through `applyConnectionOverrides`) overrides it on the online path. See [Invitation-borne role swap](#split-inboundoutbound-directories) above. (The inviter-side complement -- emitting that endpoint from online `psilink invite` -- is `endpointFromConnection`, defined in `packages/core/src/config/endpointProducer.ts` and re-exported by the CLI, the producer inverse of `connectionFromEndpoint`: it derives the endpoint from the connection the invite is using and records the inviter's pair verbatim, with no pre-swap at emit, so the single accept-side swap runs end-to-end. The acceptor mirror-swap is in place regardless of which inviter produced the endpoint. The producer is typed to the file-sync channels only: a webrtc locator names a signaling server, authored from the browser location rather than derived from a connection config, so a webrtc connection cannot reach it.)

The entry-sweep flags (`--sweep-exchange-files`, `--force-retain-sweep`) are a third category that does not fit that split: they are **CLI-only, unilateral, and non-persistable**. CLI-only not because they are bilateral but because "always sweep" must never be a persisted state -- they thread to the connection's runtime options on a path separate from config construction, never as `FileSyncOptions`/`psilink.yaml` fields. Unilateral: one party sweeps its own view of the directory, no peer must pass them, and they have none of the bilateral-mismatch *stall* risk of `retain_files`/`lockless_rendezvous`. They do, however, interact destructively with the bilateral `retain_files` agreement: because the sweep runs before rendezvous, a *blind* sweep would delete the peer hello that the bilateral flag check reads to detect a `retain_files` mismatch -- destroying a retain peer's transcript and bypassing the fast-fail that would have caught the misconfiguration. The pre-sweep retain-signal inspection (site 1) is what closes this; it must not regress to a blind sweep.

**Detection is symmetric (two-sided), via durable hellos.** The flag check sits at *every* peer-hello read site, not just one, and a detecting party leaves its own advertised hello in the directory (writing it first if it had not yet done so) and does not delete the peer's hello. The two rendezvous protocols are not symmetric in *who reads whom* -- a `lockless_rendezvous` mismatch pairs a lockless ack-barrier against a delete-based lock rendezvous -- so a check at one site alone would fast-fail only the party that happens to read the peer hello, leaving the other to hit the peer timeout. Because the advertisement is durable on both sides, the peer (whatever protocol it runs) reaches a peer-hello read site, reads the flags, and fails the same way. This holds in both arrival orders and for both flags, including a `retain_files` mismatch where both parties run the lockless ack-barrier. Leaving an already-written hello so the peer can read it is **not** adaptation: the boundary the bilateral stance forbids is adaptation, not durability, so symmetric detection stays inside it.

**A mismatch leaves both hellos as the directory's terminal state.** The mismatch path does not sweep the hellos: a party that advertised a mode has its advertisement respected as the terminal state rather than silently swept, and the peer needs the file on disk to reach the same conclusion. In-memory session state is still reset (`resetSessionState()`) so the instance is not wedged; only the on-disk sweep is skipped. The cost is that a rerun against the same directory is rejected by the entry guard ([I0](#invariants)) -- a terminal usage error, not a silent stall. Which of I0's two refusals fires turns on the ids: with the default fresh id per run, both leftover hellos are *peer* hellos to the rerunning party, so it is the at-most-one-peer-hello check ("are there other sessions using this path?") that rejects. Only with a configured `peer_id` does this party's own leftover read as a self hello and take the unexpected-protocol-file refusal instead. Either way the operator clears the directory and reruns with corrected flags. This is consistent with retain mode's fresh-directory precondition. The mismatch is reported as a distinct typed error (`BilateralModeMismatchError`, a `UsageError` subclass) so the two cleanup sites -- the rendezvous outer catch and the joiner fast-path, which has no enclosing catch -- branch on it deterministically rather than by string-matching the message.

**The symmetric guarantee is best-effort, contingent on the advertising write landing.** Leaving a durable hello presumes the `put` that writes it succeeds. The joiner fast-path -- the one mismatch site that must write a new hello at detection time -- retries that write up to a bounded budget (`ADVERTISE_HELLO_RETRY_ATTEMPTS`, at the polling cadence), so a transient failure has more chances to land. The peer polls concurrently, so the advertisement need not arrive on the first try, only before the peer would otherwise time out, and the budget stays far under `peerTimeoutMs`. If the write still fails every attempt (a transport error sustained across that whole window), no write ordering can recover -- there is no durable file for the peer to read, so the peer falls back to the ordinary peer-timeout on that one side. The detecting party still fails locally and correctly: it swallows the write failure and throws the typed `BilateralModeMismatchError` (CLI exit 64) rather than letting a transport rejection mask the actionable cause as a generic error (exit 69). This degradation is the floor, never the target -- it is no worse than the pre-advertisement behavior (a silent stall until the peer timeout), and it only occurs when shared storage is failing writes, in which case the exchange could not have proceeded regardless.

## Error taxonomy

Errors out of `synchronize()` and `send()` fall into two classes, and the distinction is part of the contract with the CLI:

- **Usage / configuration error** -> CLI exit `64` (`EX_USAGE`). Wrong directory state (preexisting files), multiple concurrent sessions, a stale lockless ack, a message-consumption timeout, a bilateral-mode mismatch (`BilateralModeMismatchError`), and a malformed control payload (a fully-synced hello missing a required flag or with an out-of-type value) belong here. So does a `--sweep-exchange-files` refusal on a retain signal (local retain mode, a peer `retain_files=true` hello, a retain-only message ack, or a retain-uncertain hello body that did not resolve within the inspection budget -- the error names the file(s) and the signal and points at `--force-retain-sweep`), and so does `--force-retain-sweep` passed without `--sweep-exchange-files`.
- **Transport failure** -> CLI exit `69` (`EX_UNAVAILABLE`). The peer went silent past `peer_timeout_ms`, `list`/`get`/`put` rejected, the listing will not converge, or a `--sweep-exchange-files` delete rejected (the sweep uses `client.delete`, which rejects -- not `safeDelete`, which swallows -- so a transport that cannot delete is exposed here instead of falsely reporting a clean slate).

This distinction is expressed by a typed `UsageError` (exported from `@psilink/core`, defined in [errors.ts](../../packages/core/src/errors.ts)): the usage class is anything `instanceof UsageError`, and everything else is a transport failure. The CLI inspects it at its catch sites -- the blocks in [exchange.ts](../../apps/cli/src/commands/exchange.ts) and [zeroSetup.ts](../../apps/cli/src/commands/zeroSetup.ts) map `err instanceof UsageError ? 64 : 69`. New throw sites in `synchronize()` or `send()` should throw `UsageError` for the usage bucket rather than a plain `Error`, classifying into one of these two buckets from the start.

### Bounded error enumeration

Both refusals the entry guard raises -- the unexpected-protocol-file one in [I0](#invariants) and the at-most-one-peer-hello one in [I1](#invariants) -- name the files they refuse over, and what they can name is bounded. They are composed under the display-budget convention [I5a](#invariants) states for the hello-read messages, resolved the other way: the refusal and its recovery step are the error's own message, holding no variable text at all, while the directory scope and the offending filenames ride in a `cause` link of their own, so each gets a full per-link budget rather than sharing one. The enumeration is bounded by that budget rather than by a count -- a protocol filename runs from roughly 47 characters to 112, so no fixed count both fills the budget and fits inside it -- and is reported as the true total plus the names that fit, taken in listing order.

**Two things make that arithmetic hold at the rendered boundary rather than only on the way in.** First, every fragment is costed *as rendered*: the composed link is sanitized again when it is shown, and sanitizing is not idempotent (each pass doubles a literal backslash), so an arithmetic done on raw lengths under-counts any name with escapes. Second, the names hold a reserved floor -- 112 characters, the longest name the protocol's own constructors build from UUID identities (a retain-mode message ack over a timestamped message at the maximum frame size, `<uuid>-<uuid>-<YYYYMMDDTHHMMSS>-<NNN>-<byteCount>-ack.json` at a three-digit counter), plus the `(and N more)` suffix -- held back before the directory scope is fitted into what is left. An operator-chosen path (two of them in split mode) is therefore trimmed with the display truncation marker rather than crowding the enumeration out. That value is computed by calling those two constructors, so it follows a change to either name shape. Each name is then fit-checked on its own and in listing order: one that does not fit is skipped and the next is tested. A long name early in the listing therefore costs only itself, and a name that does not fit is counted rather than shown in part, since a partial name reads like a whole one the operator could act on.

**A name goes unshown for either of two reasons, which are different outcomes for the operator.** It may be too long for the budget even as the first name tested -- the floor does not make every name fit, since a configured `peer_id` has no length bound and a session past message 999 widens the counter -- and then no delivery at that scope and count shows it. Or it may be a name that would be shown whole on its own, omitted only because earlier names spent the budget: in the suite's own deliveries, 11 of 12 message acks and 2 of 3 split-scope lock files are omitted for that reason, and each of those names is shown whole when it is the only file present. A refusal reports the count with no names at all only when the first reason holds for every name it contains.

**A name's private-key shape is not a second way to lose it.** What spends the budget is rendered cost -- length plus whatever escaping the name's own code points add, as costed above -- and redaction does not add to it. The entry guard redacts each name, and the directory scope, through `redactPrivateKeyMaterial` before it fits them to the budget (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#display-sanitization-escape-format)). A protocol-grammar filename shaped like a PEM private-key header is therefore replaced inside its own name: it displays as `[redacted private key]` in full. The redaction is fail-closed to the end of the fragment, so a name that is key material is taken whole rather than leaving a tail, while the count, the directory scope, and every name behind it stand. The replacement is shorter than the shortest marker it can stand in for, so redacting before the fit never widens a fitted name and the budget still holds. The scope clip is not a second limit either: the guard budgets in rendered cost over the raw path and admits a code point only when its whole escape cost fits, so the operator sees the escaping of a whole code-point prefix of the real path rather than a cut inside one code point's escape. What each message measures at the rendered boundary is pinned by a test rather than asserted here.

## SFTP rename retry

Every atomic write this model specifies is published by a `rename` to the final name: the joiner's `<id>-joining.json` -> `<id>-hello.json` and the hello publish's `temp-hello-<uuidv4()>.tmp` -> `<id>-hello.json` in Phase 1, a message's `temp-<uuidv4()>.tmp` -> its numeric-terminal name and an ack's temp -> `<writerId>-<originalName>-ack.json` in Phase 2. Every one of them therefore inherits the SFTP adapter's `rename` retry, bounded the same as `put`: one initial attempt plus up to five re-issues, 100 ms apart. Unlike `put` it is not idempotent, so it fires only on the generic `SSH_FX_FAILURE` (status 4), the status reporting that the rename did not take effect; every other status is terminal and is reported at once. Why that numeric status is the safe one to re-issue on, and how a stack bump can silently retire the retry, are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md#upgrading-the-sftp-stack-ssh2--ssh2-sftp-client). What matters to the state machine is only that the retry cannot produce a second final name: a re-issue fires only where the source still exists.

## Sender-side peer-silence attribution

The peer-silence timeout is asymmetric, by necessity rather than by oversight. When the peer dies mid-exchange -- the canonical case being its exchange directory going read-only so it can never write the next message or its ack -- the *receiver* (the failing party) names its own cause locally. `poll()` emits the underlying transport error, the `fromEventConnection` bridge makes it terminal on first emit, and `asConnectionError` copies that cause into the reported error (see the I8 [production-composition note](#invariants)). The *sender* (the waiting party) has no equivalent signal. It observes only that nothing arrived within the inactivity budget (`peer_timeout_ms`) and fails with the generic peer-silence `transport` error.

That budget is **armed per send**, not measured against one deadline fixed when the connection opened. It bounds silence *from the peer*, so each wait -- the delete-mode wait for the peer to consume `lastSentFile`, and retain mode's wait for the ack of the last message -- gets the whole of it, exactly as every transport await is raced against a fresh budget (the whole-exchange budget in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#whole-exchange-budget)). It is therefore not a cap on how long an exchange may run: an exchange that takes longer than `peer_timeout_ms` reaches its next send with a full budget rather than one its own progress has spent, which matters because the protocol sends twice in a row with no receive between the two, so this wait is reached on every exchange. What stays bounded is the failure it exists for: a peer that never consumes or never acks ends that send within one budget, plus whatever poll step was in flight when it expired.

A cross-party signal -- the failing party writing a marker the waiting party reads -- cannot cover the headline case: an exchange directory that has become unwritable is precisely what stops the peer from writing *any* file, so for that mode (and a hard kill) the channel is absent in exactly the scenario it would serve. For the modes where the directory is still writable (a transport-op fault, a terminal parse error, a graceful crash) the authenticated `<writerId>-abort.json` marker covers it, letting the waiting party fail fast with a definitive `PeerAbortError` (CLI exit 69) rather than waiting out the full timeout. It is additive to the filename grammar: the non-numeric `abort` terminal token routes it as a control file (the `parseMessageByteCount` discriminant), never mis-consumed as a message (see [the filename grammar](#the-single-critical-invariant-the-filename-grammar)). Its wire envelope, the session-key-derived token that makes it unforgeable, the no-cause decision, and the small read cap are specified in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#authenticated-abort-marker); the key point for attribution here is that its absence stays strictly uninformative -- a missing, unreadable, or non-matching marker falls back to the hedge below and is never treated as success.

The operator guidance is the baseline beneath the marker, not a claimed ceiling, and remains the floor whenever the marker is absent. The sender's timeout error includes a transport-supplied hint (`PEER_SILENCE_GUIDANCE` in [protocol.ts](../../apps/cli/src/protocol.ts), threaded through `fromEventConnection`'s `inactivityHint` option) that names the likely receiver-side causes -- the peer exited, or its directory became unwritable -- directs the operator to the peer's own logs where the real cause was recorded, and notes the slow-large-dataset case so the timeout is not misread as a death. It hedges rather than asserting a specific cause. The hint is file-sync-specific and supplied by the caller, so the WebRTC transport, which shares the same core inactivity message but passes no hint, is unaffected. The authenticated marker above *upgrades* this hedge to a definitive peer-abort error for the writable-directory modes only; it complements the guidance rather than replacing it, so the read-only-directory headline, a hard kill, and a lost best-effort write all still degrade to this floor.
