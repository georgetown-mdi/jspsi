# Web server job API

This document specifies the web application's server-side job API. It specifies the HTTP endpoints through which a supervisor creates, observes, cancels, and deletes a job -- an ordinary exchange or a zero-setup exchange -- that the Nitro server drives as a `psilink` CLI subprocess, and the two typed job-create intents the client submits and the validation that makes both injection-closed. It also specifies the SFTP connection (authored in-app through a separate endpoint) and its validation, the secrets-mount browse contract, the on-disk workdir layout and modes, and the SSE event relay and its full-history replay. It further specifies the exit-code reconciliation and cancellation escalation, the environment variables that gate and configure the feature, the memory-only job lifetime, and the two artifacts a console exchange hands the operator to carry away -- the recurring-run hand-off this API serves, and the partner accept kit it does not. It is the spec-tier complement to the operator-facing overview in [CONSOLE.md](../CONSOLE.md), which says what the feature is for and how to turn it on; this document says how each request, file, and event is constructed. It consumes -- and re-validates at the trust boundary -- the CLI's fd-3 event stream specified in [CLI_EVENTS.md](CLI_EVENTS.md); it does not respecify that stream's construction (see there). It does not cover the exchange protocol that produces the events (see [PROTOCOL.md](PROTOCOL.md)) or the display-sanitization escape format the fields reuse (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#display-sanitization-escape-format)). Intended readers are implementors writing a supervisor against this API and security auditors.

The job API exists for the console-appliance deployment: a container serving one party, inside that party's trust boundary, that drives the party's own `psilink exchange` runs without the operator invoking the CLI by hand. It is not a shared rendezvous between parties; the trust invariant it rests on and what would violate it are in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#single-party-console-trust-boundary). The API is dark unless the deployment enables it (see [Feature gate](#feature-gate)), and its whole design -- server-composed CLI inputs, memory-only state, no per-request authentication -- is calibrated to that single-operator posture; the deployment reaches it only from the operator's own machine by publishing the container port to host loopback. The console facilitates a single exchange at a time, and this API holds at most one (see [Job lifetime and orphan handling](#job-lifetime-and-orphan-handling)).

## Feature gate

The API is dark by default. Enablement requires two conditions together: a `console` deployment build (`VITE_DEPLOYMENT_PROFILE=console`, the one signal read the same way server-side as the client reads it) and a data root configured (`JOB_DATA_ROOT` non-empty). Every endpoint resolves this feature gate uniformly, before the job id is even parsed and before any filesystem access or subprocess spawn: if either condition is unmet -- a hosted build (any non-`console` profile, unset included) or no data root -- the endpoint answers `404` and consults nothing further. On a deployment where the gate is unmet, the endpoint is not reached at all: the server entry refuses the whole `/api` namespace outside the broker's subtree ahead of the router (see [The `/api` namespace's refusal](#the-api-namespaces-refusal)), so the API's presence is not observable to a caller. That refusal reads this same enablement, so the two are one control applied at two altitudes rather than two independent ones -- a mis-set profile darkens or lights both together. Gating on the deployment profile is the app-layer defense-in-depth safety check that keeps the hosted build from ever serving the routes even when built with `JOB_DATA_ROOT` set. There is no per-request authentication: the deployment publishes the container port to host loopback (see the reachability rule below), so its only reachable caller is the local operator.

Every job response has `Cache-Control: no-store` and no CORS headers -- the API is same-origin appliance-local, so a cross-origin caller is never granted access. These are additive to the defense-in-depth response headers the server entry already applies globally (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security)).

### The `/api` namespace's refusal

On a deployment where the job API is not enabled, no request the server entry (`apps/web/src/server.ts`) handles reaches the router under `/api` unless it addresses the peer-coordination broker. The entry answers every other path there with the feature gate's own empty `404` -- `Cache-Control: no-store`, no content type, no body -- before the framework's handler runs. A request form that is answered without the entry running is outside this and is listed below.

What that settles:

- The router's own answers are not observable under `/api`. A path with no route would render the app's 404 document, a declared route reached by a method it declares no handler for would render that document with a `200`, a trailing or doubled slash would answer with a canonicalizing `307`, and a request whose `Accept` excludes HTML would answer with the SSR path's JSON `500`. Each of those tells a probe which paths have a route behind them, and the set of them belongs to the framework rather than to this app, so it can grow with a version bump. The refusal stands ahead of all of them.
- No job route module runs. The request is answered without the router matching it, so no handler, its feature gate included, is entered.
- Response timing does not separate a declared route from an unknown path, because the discarded document render that separated them is not performed.

Which paths pass: `/api/peerjs` and the paths under it, the broker routes the app serves on every deployment profile. The peer server attaches its WebSocket upgrade listener on the first `GET` under that subtree (`apps/web/src/peerServer.ts`), so refusing it would stop public signaling rather than harden anything.

How a path is decided: over every spelling of the request path -- as written, case-folded, dot-resolved, and repeatedly percent-decoded -- refusing when **any** of them lands under `/api` outside that subtree. The refusal is therefore wider than the router's own resolution and never narrower, and over-refusal is its safe direction: a spelling that resolves to the broker route but is written some other way (`/api/PEERJS/id`, `/api/%70eerjs/id`) is refused rather than admitted, and the spellings a client writes are pinned as passing. A path still decoding after four rounds is refused on being under `/api` at all.

Three checks hold it, none standing in for another. `scripts/api-namespace-allowlist.test.mjs` holds the allowlist against the route tree -- every route directory under `src/routes/api` is either allowlisted or has the job gate imported by every module it holds -- and against the public asset tree, which Nitro serves without running the server entry. `apps/web/test/integration/apiNamespace.test.ts` drives the request forms above against the real built server under both `Accept` values, requiring one answer from all of them; that matrix, rather than an assertion per shape, is what catches a framework version that adds a shape. It re-drives the rows that spell a job route against a console-profile server, where nothing refuses them, so a spelling the router stops resolving fails there rather than leaving its hosted row asserting nothing. `apps/web/test/unit/utils/apiNamespace.test.ts` pins that nothing downstream of the refusal runs.

#### What the refusal leaves

- **The console's route modules stay in the hosted bundle.** This is a request-level refusal, not code removal. Excluding the route files from the build needs a per-profile generated route tree, which the pinned router generator cannot produce.
- **The broker's subtree is routed to as before**, so the router's answers remain observable under `/api/peerjs`. What they disclose is the broker's own surface, which the hosted deployment serves by design.
- **`/api` stays distinguishable from the rest of the site.** An unknown page renders the app's 404 document; an unknown `/api` path answers empty. This is unavoidable while the broker answers under `/api`.
- **The two layers fail together.** The refusal and the per-route feature gate read the same enablement, so a mis-set profile moves both. Neither is independent depth over the other.
- **Timing is leveled in process only.** It was measured single-client over loopback against the built server, where the refused paths sit within the run-to-run spread of each other. Behavior under load, behind the load balancer, and on the dev server is not measured.
- **The server entry as the sole HTTP ingress is upstream's documented design, not a measurement made here.** Nitro's static asset handler is a documented bypass of that entry (`apps/web/src/utils/securityHeaders.ts`), which is why the allowlist check holds the public asset tree empty under `/api`; a future framework or Nitro path answering ahead of the entry would bypass the refusal, and would do so silently.
- **The console profile itself is enumerable.** With the API enabled the refusal does not apply and the router answers as it otherwise would. That is accepted under the single-operator trust boundary ([SECURITY_DESIGN.md](../SECURITY_DESIGN.md#single-party-console-trust-boundary)).
- **A path whose first segment is `api` only as written is outside the namespace.** `/api%20/jobs/slot` decodes that segment to `api `, so no spelling of it lands under `/api`; it resolves to no route on either deployment profile and answers the site's ordinary shapes. The matrix pins it there rather than to the refusal.
- **Overlong UTF-8 and mixed-encoding spellings are not measured.** The spellings the matrix drives are case-varied, percent-encoded, dot-segment, and encoded-space forms. How the entry and the router each read a path spelled with an overlong UTF-8 sequence, or with more than one encoding layered, is not measured here.
- **A front end may rewrite the path before the entry reads it.** The refusal decides over the request target the entry receives. The Elastic Beanstalk proxy in front of the hosted deployment, and an HTTP/2 client's `:path` pseudo-header, can normalize or rewrite a target on the way in, so what the entry reads is not always what the client wrote.
- **Two request forms are answered without the entry running, and the matrix drives neither.** A `TRACE` request is answered with the framework's `500` before the `Request` is constructed (undici forbids the method). An absolute-form request target (`GET http://host/api/jobs/slot HTTP/1.1`) reaches h3's router and is answered with its own `404`. Neither tells a probe whether a route exists: each answers a declared job route, an unknown path under `/api`, and a path outside the namespace with the same status and body shape, differing only in the request URL the body echoes. Both answer past the refusal, though, so a change in that layer would go unnoticed here.

### Browser-CSRF gate

The shared route gate applies two complementary browser defenses to every route, after the feature gate's `404` (so a disabled API stays a uniform `404`, its presence unobservable) and before any filesystem access or spawn. Each refuses with an empty-bodied `403`, matching the gate's `404`.

- **Loopback Host-allowlist.** The request's `Host` hostname -- port-stripped, IPv6 brackets removed, lowercased -- must be a loopback literal (`127.0.0.1`, `localhost`, or `::1`) or an entry in the `JOB_ALLOWED_HOSTS` environment variable (comma-separated hostnames, each trimmed and lowercased, empties dropped); any other value is refused, as is an absent or unparseable `Host` (fail closed). The match is on the hostname only, so any published-port remapping (`-p 127.0.0.1:8080:3000`) passes. `0.0.0.0` is never a loopback literal. A rejection is logged server-side naming the `Host` and pointing at `JOB_ALLOWED_HOSTS`, so a misconfigured operator gets a self-service diagnosis rather than a silent break. The check keys on the `Host` header, never the socket peer address (under Docker Desktop the peer is the gateway, not loopback).
- **Origin / `Sec-Fetch-Site` check.** In order: if `Sec-Fetch-Site` is present and is neither `same-origin` nor `none`, the request is refused; else if `Origin` is present and its origin (scheme+host+port) does not equal the request's own origin -- derived from the `Host` header, since the console is served over http on loopback -- it is refused; if neither header is present the request is allowed.

The Origin/`Sec-Fetch-Site` check closes plain cross-origin CSRF: a page the operator visits while the console runs can issue a CORS "simple" request (no preflight) to a job route and drive a side effect -- e.g. make the console connect out to an attacker-chosen host via `POST /api/jobs/sftp/probe`. Browsers send `Origin` on state-changing requests and `Sec-Fetch-Site` on every fetch, and page JavaScript cannot set either (both are forbidden header names), so a visited page cannot forge its way past the check; the console's own UI fetches relative same-origin URLs and passes unchanged; a non-browser client on loopback (curl, the operator's CLI) sends neither header and is allowed. The check is on the request's origin metadata, not its body, so it is content-type-agnostic and covers every route uniformly regardless of body shape.

The loopback Host-allowlist closes DNS rebinding, a standard technique the Origin/`Sec-Fetch-Site` check alone does not stop. A page at `http://attacker.example` whose name the attacker rebinds to `127.0.0.1` reaches the API with `Host` and `Origin` both naming `attacker.example` -- genuinely same-origin, so the Origin check passes -- and, being same-origin, the page can then _read_ the response (job results, keys, the SFTP projection), not merely drive a side effect. Requiring the `Host` to be a loopback name refuses it. This is what makes the no-CORS "cross-origin caller is never granted access" posture above actually hold: without the loopback-`Host` requirement, rebinding would render an attacker page same-origin and CORS-exempt. `JOB_ALLOWED_HOSTS` is the deliberate-exposure override for an operator who fronts the console behind a reverse proxy or reaches it by a LAN name -- deployment paths marked unsupported / an explicit choice in [CONSOLE.md](../CONSOLE.md).

**"Every endpoint" is a check rather than a claim.** The feature gate and both browser defenses reach a request only through the shared route gate, so an endpoint that omits the call is exposed on all three counts while each endpoint's own test still passes. `scripts/job-route-gate.test.mjs` (run by `npm run test:scripts`, a CI static check) walks the route directory rather than a maintained list, enumerates each module's inline `handlers` map per HTTP method rather than per module -- a module-level reading would pass one that gates `GET` and misses `DELETE` -- and fails on a handler that never calls the gate or calls it somewhere other than its first statement. There is no allowance list. Its reach is syntactic and its header states the limits exactly: a handler written in any shape other than inline in that map is reported as unread rather than passed over, as is a module in that directory with no such map. The gate is matched by imported name and specifier rather than resolved. The check also decides whether a handler acts on that outcome. A handler that binds the call to a name in its first statement and tests that name's discriminant against the outcome's two kinds in the next statement is read. That holds for either polarity, with the refusing side exiting by `return` or `throw`, including a success-first guard clause whose fall-through is treated as the implicit refusal. One that discards the call, tests late or not at all, or lets a refusing branch fall through is named. Any other shape (a destructured binding, a helper predicate, a `switch`, a ternary) joins the unreadable report. It still does not decide that the refusing branch returns the gate's own response specifically, or that a branch exits by anything other than a syntactic `return` or `throw` -- the per-endpoint tests are what cover those. A second check, `scripts/api-namespace-allowlist.test.mjs`, reads the same tree for a different claim: that every route directory in it is accounted for by the namespace refusal above, allowlisted or gated. One decides which routes a deployment serves at all, the other whether each handler gates; neither stands in for the other.

### Job id and the traversal guard

The job id is a server-generated v4 UUID; the client never supplies it. Every id-bearing endpoint validates the parameter against the exact canonical v4 UUID pattern before any filesystem use, and a value that is not a canonical v4 UUID (a traversal payload, an absolute path, an empty string) is `404` without touching disk. Resolving a workdir applies a second, defense-in-depth check: the id is joined to the resolved data root and the result confirmed to stay strictly under `<dataRoot>/`, so even a validated id that resolved outside the root is refused. An unknown-but-well-formed id (never created, already deleted, or belonging to an exchange the server forgot on restart) is `404` identically, so id validity is not distinguishable from job existence.

### The `GET /api/jobs/:jobId` status body

```json
{
  "id": "<uuid>",
  "status": "running" | "succeeded" | "failed" | "cancelled",
  "terminal": { "outcome": "succeeded" | "failed" | "cancelled" | "completedWithPersistenceLoss",
                "exitCode": <int|null>, "signal": "<sig|null>" } | null,
  "terminalEmitted": <bool>,
  "eventCount": <int>,
  "resultAvailable": <bool>,
  "recordAvailable": <bool>,
  "recordCreatedAt": "<iso-8601>",  // present only when recordAvailable is true
  "recordOutcome": "completed" | "receipt-swap-terminated",  // same
  "recordUnavailableReason": "not-settled" | "no-record" | "undescribable-record",  // present only when recordAvailable is false
  "logRequested": <bool>,
  "logAvailable": <bool>,
  "receiptRequested": <bool>,
  "receiptAvailable": <bool>
}
```

`terminal` is null until the child exits; `resultAvailable` is true exactly when `status` is `succeeded`.

`recordAvailable` is true only when the run has settled (`status` is anything but `running`), both the record and its verification-keys file are on disk, and the record validates into a `createdAt` and a recognized [`outcome`](EXCHANGE_RECORD.md#when-a-record-is-owed); the record pair is offered all-or-nothing. Three properties fix that gate.

- **It turns on the record's existence, not on the run having succeeded.** A record is owed from the moment the payload exchange returns, so a run that disclosed and then terminated writes one to the same destination a completed run's takes, and it is precisely the disclosure-accounting artifact that run's operator needs. A failure before that point owes no record and writes none, so it reports `recordAvailable: false` on the file's own absence rather than on a status test standing in for it.
- **Settling is a separate claim from the file being there, and both are required.** The CLI writes the pair near the end of a run, so a mid-run read could take a half-written state for the run's answer; a complete pair sitting in a running job's workdir does not open the routes.
- **A record that has no recognized `outcome` is treated as unavailable.** Every record this console's own CLI writes states one, so a file without it is not a record the console can describe -- and describing it is required, per `recordOutcome` below. Unavailable is not absent, though, and the body says which: such a file is reported `undescribable-record` per `recordUnavailableReason` below.

`recordUnavailableReason` says which negative a withheld pair is, present exactly when `recordAvailable` is false. The three are separate answers because what a client may safely do with them differs:

- `no-record` -- nothing is at the record path. This is the console's definitive denial, and the only one that licenses a console control to destroy the run's workdir without asking first.
- `undescribable-record` -- a record file is in the workdir and the console cannot offer it: its `outcome` is not one this server bundle knows (a data root a differently-versioned CLI wrote), it does not parse into a `createdAt` and an `outcome` at all, or the verification-keys half beside it is missing so the pair cannot be served whole. A record of a disclosure is on disk, so a client neither offers it nor treats it as an absence.
- `not-settled` -- the run is still going and the CLI writes the pair near the end of it.

The field refines the boolean rather than replacing it: `recordAvailable` stays the single gate the download routes share, so an undescribable record is withheld there too (the console does not serve a pair it cannot read whole) and the client's own version-skew guard remains the one below on `recordOutcome`. What the field removes is a client having to read one negative as two things: a body denying availability without naming a reason is a console that predates the field, and is treated as the plain denial it was.

A client's classification still guards only the body it receives, not what is on disk: the reason is the console's reading of the workdir, and a record file that counts as absent to it -- unreadable to the server process, say -- is reported absent.

`recordCreatedAt` is the record's own timestamp and `recordOutcome` its own outcome, both present exactly when `recordAvailable` is true. A client derives the download filenames from the timestamp, matching the in-browser exchange path, and reads the outcome to say what it is offering. A terminated record's commitments re-supply from a result file that run never wrote, so the keys beside it have nothing to open ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#when-a-record-is-owed)) -- a client that offered the two alike would make a claim the record does not.

Because the CLI's record write is non-fatal (a disk failure after a successful exchange is warned, not thrown), a job can be `resultAvailable: true` with `recordAvailable: false`.

`logRequested` is true exactly when this job's intent asked for a diagnostic run, and `logAvailable` is true exactly when it did and the log file is on disk. Both are read off the log path the server set at job creation from that intent, never from anything the reading request holds. Neither is gated on status: the run a diagnostic log exists for is the one that misbehaved, so a still-running or failed job reports the log as soon as the CLI has opened it. A run that did not ask for one has no log path at all, so no file planted at that name in its workdir can make `logAvailable` true.

`receiptRequested` and `receiptAvailable` are the same pair for the dual-signed receipt, read off the receipt path the server set at job creation from the intent's signing mode. A run whose intent asked for no signed receipt has no receipt path at all, so no file planted at that name in its workdir can make `receiptAvailable` true.

The pair is what a client watching for a log reads: `logAvailable: false` alone does not say whether the file is still coming, and `logRequested: false` is what lets a client stop asking after one request instead of polling an ordinary run for its whole duration.

An ask that yields neither field -- a non-`200`, a body that is not this status body, or a request that never completed -- is not an answer about the log at all, and a client does not read it as "not yet". A job the server forgot across a restart, or a route that keeps failing, answers that way for as long as the client keeps asking. A client bounds how many such asks it makes in a row -- the console's seat spends a few seconds on them, not the run -- and tells its operator the server stopped answering for that run, rather than watching silently for a log that will never be reported. An answered ask ends the run of them, whatever it answered.

`status` and `terminal.outcome` answer different questions and are read together. `status` is the artifact promise, set by the terminal event the CLI emitted, and it is what the result route gates on (the record and keys routes read it only for the settled-versus-running distinction above). `terminal.outcome` is the run classification, set by the child's exit (see [Exit-code reconciliation](#exit-code-reconciliation)). They diverge on exactly one condition: `completedWithPersistenceLoss`, the CLI's persistence-loss exit ([CLI_EVENTS.md](CLI_EVENTS.md#persistence-loss)) -- the exchange completed and a local write did not. A run that took one and still emitted its `result` terminal is `succeeded` with `terminal.outcome: "completedWithPersistenceLoss"`, and its artifacts are served: the exchange happened and the result file is on disk. The `warning` events that preceded the terminal name what was lost; the outcome is what tells a supervisor -- or the console seat -- that the run must not be repeated, because repeating it would re-send this party's data for an exchange that already happened.

### The `GET /api/jobs/:jobId/result` response

Served only when `status === "succeeded"` and the output file exists and is readable; any other case (unfinished, failed, cancelled, or missing file) is `404` rather than leaking whether an unfinished job exists. The gate is on `status` alone, never on `terminal.outcome`, which is what makes a persistence loss servable rather than withheld: such a run completed its exchange and usually wrote its result file, and the loss is an audit artifact or a configuration record beside it. The one persistence loss that is the result file itself arrives as the CLI's own `output` `error` terminal, so its `status` is `failed` and this route `404`s -- decided by the terminal event the CLI actually emitted, not by the exit code both cases share. The body is the job's server-chosen output file inside its workdir -- never a client-named path. Headers: `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="result-<id>.csv"` (a fixed, server-derived download name), and `X-Content-Type-Options: nosniff`, plus the `no-store` discipline.

### The `GET /api/jobs/:jobId/record` and `/api/jobs/:jobId/keys` responses

Both are served under the status route's own `recordAvailable` rule above -- the run settled, both files (`record.json`, `record.keys.json`) readable, and the record validating into a `createdAt` and a recognized `outcome` -- and `404` otherwise, an `undescribable-record` included. The console withholds a pair it cannot read whole rather than serving material it cannot describe, and the status body's reason is what tells the client the file is nonetheless there. One gate for the two routes and the status field means a client that offers a download whenever `recordAvailable` is true never links a `404`, and the pair is never split. Unlike the result response this is not gated on `status === "succeeded"`: a run that disclosed and then terminated exits non-zero and still owes the record of that disclosure, so gating on success would withhold the accounting artifact from the run whose operator most needs it -- while the console's own recovery controls remove the workdir it sits in.

The bodies are the job's server-chosen record and keys files inside its workdir, never a client-named path. Headers: `Content-Type: application/json; charset=utf-8`, a fixed `Content-Disposition: attachment; filename="psilink-record.json"` / `"psilink-record.keys.json"` (a server-side fallback; the browser's save name is set by its download control and includes the record's timestamp), and `X-Content-Type-Options: nosniff`, plus the `no-store` discipline. The verification keys are private material -- a salt plus the record's commitment can open a committed value -- so `/keys` is gated and `no-store` identically to `/record` and `/result`; see [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md).

What the keys are usable for is the client's to state, not this route's to withhold. A terminated run wrote no result file and all three of the record's commitments re-supply from one, so nothing can be opened against that run's keys; the file is still the operator's own material, written beside the record it pairs with, so it is served and `recordOutcome` is what lets the surface say so.

### The `GET /api/jobs/:jobId/receipt` response

Served when the run asked for a signed receipt (`signing.mode: certificate`) and the file exists at the workdir path the composed configuration pinned; `404` otherwise, including for every run that signed nothing. The body is that server-chosen file, never a client-named path. Headers: `Content-Type: application/json; charset=utf-8`, a fixed `Content-Disposition: attachment; filename="psilink-receipt.json"` (a server-side fallback; the browser's save name is set by its download control and includes the run's stamp), and `X-Content-Type-Options: nosniff`, plus the `no-store` discipline.

Unlike the record and keys routes, this one is not gated on `status === "succeeded"`. The receipt is written from the mutually-verifiable facts once the signature swap completes, independently of the local record build and of the run's eventual exit code -- a persistence-loss exit is a completed exchange whose receipt may be precisely the artifact that survived. Gating on success would withhold the one third-party-verifiable artifact of the run most in need of one. What the receipt does and does not reveal to a holder is in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md).

A client reads the `receiptRequested`/`receiptAvailable` pair independently of how the run ended, not off a successful terminal: the run whose result file was the persistence loss reports its `output` `error` terminal and `status: "failed"`, and it is exactly that run whose receipt may be the only third-party-verifiable artifact left. It asks once the run has settled, which is a different condition -- the file appears at the signature swap, so an earlier ask would read a receipt not yet written as one the run does not have, while a settled run's receipt is written or never will be.

A client offers the download only when `receiptAvailable` on the status route is true, so it never links a `404`, and it names the file on the record downloads' stamped convention -- `psilink-receipt-<stamp>.json`, the CLI's own default receipt name off the `createdAt` the record downloads are stamped from. Where the same status body reports no record there is no `createdAt` to stamp from, and the job id stands in: the receipt outlives the record's build (the reason this route is not success-gated), so the name falls back rather than the download being withheld. The two status fields are read together and separately from availability: `receiptRequested` true with `receiptAvailable` false is a run that asked for a receipt and has none, which a client states rather than rendering as no control at all, while a body with neither as `true` answers nothing about a receipt and leaves the client with nothing to say.

### The recurring-run hand-off

`GET /api/jobs/:jobId/handoff` returns the portable material an operator carries from a prototyped console exchange to a scheduled command-line `psilink` run. It is composed at job creation from that run's intent and resources and held on the in-memory record, so it is served for the whole lifetime of a live record, and the panel is available over that whole lifetime too -- collapsed while the run is in flight, expanded once it completes. The endpoint keys its `404` on job existence, not status: a malformed, unknown, or already-deleted id is `404` identically to the other id-bearing routes. It is JSON with the `no-store` discipline. The body is:

```json
{
  "mode": "exchange" | "zeroSetup",
  "channel": "sftp" | "filedrop",
  "usedKeyFile": <bool>,
  "credentialPasted": <bool>,
  "usedSigningIdentity": <bool>,
  "template": { "kind": "config", "yaml": "<psilink.yaml text>" }
             | { "kind": "command", "argv": [ "<token>", ... ] }
}
```

`usedKeyFile` is true for the exchange mode (a `.psilink.key` the operator must copy), false for the zero-setup mode (which has no shared secret). `credentialPasted` is true only for an sftp run whose credential was a pasted, materialized value (the panel then tells the operator to save it to a file); it is always false on the filedrop channel. `usedSigningIdentity` is true for a `certificate`-mode exchange, and drives the panel's carry-the-key caveat: the signing key is a file rather than a setting, and the scheduled run must load the same one -- a fresh `psilink fingerprint` on the scheduling machine mints a different key with a different fingerprint, which the partner's pin then rejects. The `template` is discriminated on `kind`: an exchange run yields a `config` (the `psilink.yaml` document, recomposed through the same functions the live run used), a zero-setup run a `command` (the argv tokens of the `psilink URL INPUT OUTPUT` form).

Two invariants hold by construction and are pinned by tests:

- **No secret.** The response never includes the shared secret, the key-file body, or an inline credential value. The exchange config holds the credential only as an `@path` reference (the secret rides the key file, which never crosses this API), and the zero-setup command has no secret at all.
- **No container path.** The response never includes a container-internal path. The credential `@path` (sftp) is replaced with the fixed placeholder `@/path/to/your/credential-file` (a private-key passphrase with `@/path/to/your/passphrase-file`), the filedrop rendezvous directory with `/path/to/your/shared-directory` in a config or `file:///path/to/your/shared-directory` in a command, and `signing.identity_file` with `/path/to/your/signing-identity.json`. The portable values -- host, port, username, the remote SFTP working directory, the host-key fingerprint pin, the linkage terms, and the run's tuning `options` -- are emitted verbatim as they ran; only the machine-specific local paths become placeholders.

The tuning options transfer across in whichever form the mode uses: the exchange template's `options` block is the one the live run composed, and the zero-setup template's flags are built by the same builder the live argv used. A run that kept its exchange files therefore graduates to a scheduled run that keeps them too -- which matters because the trio is a bilateral agreement, so a scheduled run that silently dropped it would stall against a partner still retaining. The same holds for the connection tuning: a run prototyped against a slow peer or a session-capping server graduates to a scheduled run with the same polling, timeouts, retry budget, and session mode, rather than one that quietly reverts to the defaults. The signing block transfers across the same way -- the mode and the pinned partner fingerprint are portable and emitted verbatim -- with one deliberate exception: `signing.receipt_output` is omitted rather than placeholdered. With the key absent the CLI writes a timestamped receipt into the run's own working directory, so a schedule accumulates one receipt per run; transferring the console's single fixed name over would have each run overwrite the last, which is the opposite of what a non-repudiable trail is for.

### The partner accept kit

The accept kit is the console's second graduation artifact: a plaintext, printable, ASCII instruction sheet composed in the browser at invitation-mint time -- from the values captured there and the build's own release version, the named values below and nothing else -- and written to the operator's disk through the same client-side blob download as the exchange file. It is specified here beside the hand-off because the two artifacts share the invariants below and must not drift, **not** because the job API serves it: no endpoint returns it. What the sheet is for, what it walks the partner through, and which channels get one are in [CONSOLE.md](../CONSOLE.md).

Its contents are fixed text apart from two kinds of interpolated value:

- The **rendezvous locator** minted into that invitation -- the sftp host, optional port, and either the shared remote directory or the split inbound/outbound pair; or, on filedrop, the shared folder's name or a split rendezvous's two folder names -- printed back for the partner to check. It is taken from the same values that built the invitation's `connectionEndpoint`, so the sheet can never name a rendezvous the token does not hold. On the filedrop channel it prints the shared folder's name only where the console can name it (`folderName` in [The filedrop rendezvous report](#the-filedrop-rendezvous-report)); where it cannot, the sheet omits the name entirely and says so, rather than printing the container mount point the folder was bound at as though it were the folder's name. The sheet therefore prints a subset of what the token holds, never a different value. What it asks for is a check and not a match: the same shared folder can have a different name on each side -- a share root mapped to a drive letter is the ordinary case. So the sheet asks the partner to check the name against the folder they were told to use rather than asserting their own name for it will be the same. The step that repoints the partner's own config at their copy of the folder follows the same branch: named, it says accepting wrote the inviter's name for the folder; unnamed, it calls what accepting wrote a placeholder, because what the token held there was the console's mount point. Either way it directs the same replacement, so the sheet never tells the partner a value is a name neither side chose.

  A split rendezvous -- on either channel -- names its two directories by what the reader does with each ("You write to" the inviter's inbound, "You read from" the inviter's outbound) rather than by "inbound"/"outbound", which the endpoint states from the inviter's side and which the partner's own tool mirrors. The filedrop split keeps its shape independently of its names: a console that cannot name either folder still describes a two-folder rendezvous, since falling back to the single-shared-folder body would send the partner to set up the wrong thing. That body directs a two-mount run (`inbound_path`/`outbound_path` against two fixed container mount points), and its network-drive branch says plainly that the PowerShell launchers provision a single shared folder and cannot start a split exchange, offering the two ways forward rather than routing the reader to a console that could not run it.
- The **release version** of the build that composed it, which decides two things together: the image tag every `docker run` line includes, and the release page the filedrop launcher branch links. A kit minted on a released console image names `docker.io/vdorie/psi-link:X.Y.Z` in every command and links that release's own page, so the partner runs the version that minted their invitation and takes the launchers from the release that built it. The image build reads the version from `apps/cli/package.json`, the canonical release version (see [RELEASES.md](../RELEASES.md)), and bakes it into the client bundle as `VITE_PSILINK_VERSION`; the kit therefore names whatever version the manifest held at image build. The published image's own tag comes independently from the pushed git tag, and on the release path their agreement is checked rather than left to the release process's step ordering. The publish job refuses a tag whose version disagrees with the manifest, naming both values, before anything is built or pushed, and the image build itself refuses a manifest read that yields no version rather than baking an empty one into the bundle.

  A value is interpolated only in the release shape -- `X.Y.Z` with semver's optional prerelease and build suffixes, excluding the `0.0.0` marker held by the manifests that have no release version. Anything else, including an absent value, names the floating `latest` tag a release publishes alongside `X.Y.Z` and links the releases index, so a build that passes no version -- the continuously deployed hosted deployment, or any web build outside the image build -- prints a working command rather than an empty, partial, or placeholder tag. That gate is also what holds the sheet's ASCII contract for this value: unlike the rendezvous locator, it is never filtered, because no value outside the shape reaches the sheet at all.

  Two limits hold as measured. The tag check binds a tag push and nothing else, and the image build takes whatever version the CLI manifest holds, which between releases is the last published one. An image built from a non-release tree therefore names that release rather than the build that minted the invitation, and a release-branch tree built after the version bump but before the tag is published names a release that does not exist yet. And the gate holds the value to release shape, not to Docker's tag grammar: a semver suffix -- which the release process never sets, publishing bare `X.Y.Z` only (see [RELEASES.md](../RELEASES.md)) -- would render into the tag verbatim.

The exchange's own settings reach the sheet as **selectors, never as values**, which is what keeps the count at two. The ones the partner must be told about are the bilateral, non-negotiated file-sync settings the run uses -- retain mode and the lockless rendezvous -- because their own run must use the same ones or the two sides stop at rendezvous (see [FILE_SYNC.md](FILE_SYNC.md)). Retain mode additionally leaves every protocol file in the rendezvous location afterwards, which is the partner's to know before they join. The kit takes each as a boolean, resolved as the run resolved it (so retain mode's implication of the lockless rendezvous is already folded in), and each picks between fixed paragraphs and a fixed flag on the exchange command the sheet prints: `--retain-files` under retain mode, `--lockless-rendezvous` where the rendezvous setting resolved on with retain mode off. One flag rather than the trio, and never both, because the CLI resolves what retain mode implies, so the sheet cannot state a rule the CLI does not enforce. Rendering the option block instead would make a third value representable and void the property above, so any later setting the partner must know about is disclosed the same way. With both settings at their defaults the sheet is byte-identical to one composed with no such setting at all, and under retain mode it is byte-identical however the rendezvous setting resolved.

What the retain paragraphs state, in the channel's own terms and without reprinting the locator, is that the exchange keeps every file it writes as a permanent transcript. They also state where those files persist -- the directory the two parties meet in on the SFTP server the sheet has already named, or the shared folder, or, on a split rendezvous of either channel, both directories the sheet named above -- and that nothing removes them, so both sides must start from an empty one. They state that the message bodies stay ciphertext there while the rendezvous control files do not, so a later reader of that location learns that an exchange happened, when, how many messages each side sent and how large they were, the name each side ran under, and the settings each side announced. And they state that the agreement is bilateral, the flag on the printed command being the partner's half of it. The filedrop launcher branch hands the partner to the console's accept flow rather than to the sheet's commands, so on that branch the disclosure names the console control ("Keep every exchange file") instead of the flag, and both routes off the sheet include the setting.

The lockless rendezvous leaves nothing behind, so it contributes no section of its own. The whole of what it has to state is the agreement, and the sheet states it where the reader meets the flag -- that the setting is their half of one the inviting side runs, and that dropping it stops the two of them with an error when they meet. The launcher branch is covered the same way as retain mode's, naming the console control ("Lockless rendezvous") in place of the flag, so both routes off the sheet include this setting too.

Four invariants hold by construction -- nothing else is representable as an input -- and each is pinned by a test:

- **No secret.** The sheet has no shared secret, key-file body, or credential value. The credential an sftp partner needs is theirs, not the inviter's: the sheet names the placeholder username acceptance seeds (see [EXCHANGE_FILE.md](EXCHANGE_FILE.md#mint-layer-guarantees)) and the `@path` convention for pointing at a credential file, and states that the invitation has no credential by construction.
- **No invitation token.** The sheet shows the fixed placeholder `PASTE_YOUR_INVITATION` where the invitation string goes, never the encoded token or its deep link. The invitation travels on its own confidential channel; the sheet is safe to pass around and to print.
- **No container path.** The only container paths on the sheet are the fixed mount points of the commands the *partner* will run (`/work`, `/sync`, `/run/secrets`); no path inside the inviter's console appears.
- **No inviter-machine path.** Nothing from the inviting operator's filesystem appears beyond the rendezvous locator the invitation already holds -- on the filedrop channel that is a single path segment naming the shared folder, never the console's resolved absolute path. The mount path does not cross the job API at all (see [The filedrop rendezvous report](#the-filedrop-rendezvous-report)), so no composition step in the browser has one to leak.

### The single-slot occupancy probe

`GET /api/jobs/slot` reports whether the console's single exchange slot is occupied, and by which job: `{ "occupied": false }` when free, else `{ "occupied": true, "id": "<uuid>" }` naming the occupying exchange. Occupied is exactly the state in which a create is refused with a `409` (see [Job lifetime and orphan handling](#job-lifetime-and-orphan-handling)), so this probe and the busy create disclose the same occupant and cannot drift.

The console lobby's recovery panel reads it when the browser holds no stored attachment: a browser that never started the exchange -- a second machine, or one whose recovery record was lost -- can then still see the slot is taken and re-attach to the running exchange or discard it, closing the gap the attachment-only recovery left. It is gated identically to the rest of the job API -- the feature gate, the loopback Host-allowlist, and the browser-CSRF check all apply, and a disabled API is `404` -- so it adds no new perimeter. It discloses exactly what a busy `POST /api/jobs` `409` already does (occupied plus the occupant's id, a non-secret v4 UUID reachable only over the loopback-local origin) and nothing more: it is not a job listing (`GET /api/jobs` stays absent), has no run detail, and adds no destructive endpoint -- clearing the slot rides the existing per-id `DELETE /api/jobs/:jobId` through the panel's Discard. The static `slot` segment cannot be captured as a job id: ids are validated as canonical v4 UUIDs before any use, which `slot` is not.

### The filedrop rendezvous report

`GET /api/jobs/rendezvous` reports whether a filedrop exchange can run on this console, over one shared folder or a split inbound/outbound pair, and what an invitation minted here may say about each folder. The body is `{ "configured": false }` when no rendezvous mount resolves (neither `JOB_RENDEZVOUS_DIR` nor `JOB_DATA_ROOT` is set), or `{ "configured": false, "problem": "..." }` when the mounts resolve but cannot run an exchange as provisioned, else `{ "configured": true, "sharesDataRoot": <bool>, "split"?, "locator"?, "folderName"?, "outboundLocator"?, "outboundFolderName"? }`:

- `locator` -- the advisory locator the invitation's filedrop endpoint holds: the shared folder's name where the console has one, else the resolved mount's own last path segment. Always a single path segment, never the resolved mount path. A mint needs one whether or not the folder can be named, because core's endpoint schema requires a filedrop directory. Absent only for a mount with no last segment at all, which the browser client treats as unavailable.
- `folderName` -- the shared folder's own name (see `JOB_RENDEZVOUS_NAME` under [Environment variables](#environment-variables)), present only where the console can name it. It is the only one of the two that may be shown to anyone as the shared folder's name: the inviting console's confirm line and the accept kit take this field and say nothing where it is absent, so neither presents a mount point the operator did not choose as a folder the partner could recognize. A console accepting an invitation holds to the same rule from the other side: an invitation's locator is the inviter's folder name where their console had one and their launcher's mount segment where it did not, and the accepting console cannot tell those apart, so its confirm line renders no part of the locator at all. It names the directory mounted on the accepting console instead -- this field, from that console's own report -- and asks the operator to check it with their partner rather than to match a name. Presence: the launchers emit `JOB_RENDEZVOUS_NAME` unconditionally, an empty value where no name is derivable, and an empty value resolves to no name rather than the mount segment. That emptiness path rests on the engine passing `--env NAME=` through as set-but-empty, and an engine that dropped the empty value instead would leave the console on the mount segment. Measured on a real Docker engine, a set-but-empty `--env NAME=` value reaches the container as an empty-valued environment variable rather than being dropped, so the emptiness path holds beyond the launcher tests' stub engine.

- `split` -- present and `true` exactly when `JOB_RENDEZVOUS_OUTBOUND_DIR` names an outbound mount, so this console rendezvouses over a pair. `outboundLocator` and `outboundFolderName` are that leg's counterparts to the two fields above, under the same rules, and `locator`/`folderName` then describe the inbound leg alone. A `split` body always includes `outboundLocator`: an invitation's split endpoint needs a locator per leg, so the browser client reads a split body without one as unavailable, exactly as it reads a configured body with no `locator` at all.
- `sharesDataRoot` -- whether a rendezvous leg holds the data root, so the folder the partner syncs into is also the folder this party's signing key, config, input, and results live in. Always present on a `configured: true` body, and a bare boolean: it is the single-mount layout as a fact, never the path that decided it. True on the `JOB_DATA_ROOT` fallback and for any leg an operator pointed at the data root or at a folder containing it; false where the rendezvous has a mount of its own. The test is directional -- a leg mounted inside the data root does not hold it, since the sync reaches that subfolder rather than the key beside it -- and runs over each leg both as configured and as its `realpath`, on the terms the split pair's containment refusal above uses. Where the paths leave the layout open it then compares filesystem identity: the leg's `(st_dev, st_ino)` pair against that of the data root and of every ancestor of it, up to the filesystem root. That is what extends the verdict to aliasing no path expresses -- one host directory bind-mounted at two container paths (`-v /host/psilink:/data` beside `-v /host/psilink:/mnt/share`) presents two distinct real paths for the one directory a partner's sync writes into while `stat` identity joins them. Measured 2026-08-26 under Docker, the two aliased mounts kept distinct real paths, reported one `(st_dev, st_ino)`, and a write through one alias read back through the other. That measured shape is what the walk is built for; the fail direction is benign, since an engine that resolved both container paths to a single real path instead would have the lexical comparison decide the layout, leaving the identity walk a no-op and the advisory raised either way. The identity comparison keeps the same direction the path comparison has, since it is the data root's ancestors that are walked and not its contents. A leg or a data root whose real path cannot be read counts as holding, as does a directory the console cannot `stat`: the aliasing that would join them is what could not be resolved, and this field decides whether a warn-and-guide advisory is raised, so what cannot be ruled out is reported. The browser reads an absent or non-boolean field as `true` for the same reason. What stays invisible is aliasing that neither `realpath` nor the identity of the data root's own ancestor chain can see -- a leg bound onto a directory whose contents reach the data root by a route that chain does not pass through -- so the field is a best-effort answer about the layout, not a proof of separation. The separate mount is what makes the layouts different, not this report. Its one consumer is the console's receipts card, which raises the advisory about the shared mount on this layout alone; where the rendezvous is separately provisioned the hazard that advisory names is not live, and the warning channel keeps its meaning. The card's other word about the signing key -- that it is written into the mounted folder and how to look after it -- is true on every layout and is shown on every layout, so a `false` here withholds the hazard rather than the key's location.
- `problem` -- why a filedrop exchange cannot run as this console is provisioned, in the operator's own terms and naming the environment variable to set. It accompanies `configured: false`, because the console cannot run one; the surfaces that report the unavailable state relay it in place of their generic "nothing is mounted" copy, so an operator who mounted two folders is not told to mount a first. The faults it reports are the ones a split pair can be provisioned into and no exchange could survive. They are two legs that are the same directory or nested one inside the other (this party would read its own writes as the partner's), and two legs whose derived locators resolve alike (core refuses such an endpoint at the mint, with nothing an operator can act on). They are also a leg the console can put no locator on at all (an invitation minted here would hold none for it). They are also an outbound mount with no inbound one of its own (the inbound leg's `JOB_DATA_ROOT` fallback does not provision the inbound half of a split, so `JOB_RENDEZVOUS_OUTBOUND_DIR` set while `JOB_RENDEZVOUS_DIR` is unset is half a pair whatever the data root resolves to).

What the first of those faults -- two legs that are the same directory or nested one inside the other -- resolves, and what it does not:

- It compares each leg both as configured (lexically resolved) and as its `realpath`, in every pairing of the two forms, so an outbound leg symlinked onto or into the inbound one is refused exactly as a lexically nested one is -- the same refusal, in the same words. The inbound leg is partner-written, so a pair provisioned as two folders that silently resolves onto one is outside the layout latitude the console leaves the operator, however the collapse is spelled.
- A leg that does not exist yet is resolved through its nearest existing ancestor with the missing tail re-appended, so a mount not created until the first exchange is still compared through a symlinked parent. A component that does not exist cannot be the symlink that joins the legs; its parent can.
- A leg whose real path cannot be read (a permission or I/O failure on the way to the mount, as opposed to a component that is simply absent) narrows the comparison back to the configured paths and warns at startup naming the variables that could not be resolved. It never becomes a refusal of its own: a filesystem that cannot answer is not evidence the legs are one directory, and the lexical verdict still stands on its own.
- It does not follow a dangling symlink (there is no directory at the far end for an exchange to write into), and it resolves each leg once, when the provisioning is read at startup, so a symlink created or repointed while the console runs is not seen. The exchange's own entry guard remains the safety check.

The resolved mount paths are not in the body -- neither leg's, and not inside `problem`, which names variables rather than paths. Nothing in the browser needs them, and leaving them server-side is what makes the "No inviter-machine path" invariant above a property of the API boundary rather than of every consumer remembering to reduce a path before minting.

### The `GET /api/jobs/:jobId/log` response

Served when the job exists, its intent asked for a diagnostic run, and the log file is readable; `404` in every other case, including a run that captured no log. Unlike the result response this one is not gated on `status === "succeeded"`, nor even on the run having settled: the run a diagnostic log exists for is the one that failed or stalled, and withholding the log until success -- or until the stall ends -- would withhold it exactly when it is wanted.

The body is `run.log` inside the job's own workdir. The path is composed from the workdir and that fixed name and then confirmed to resolve strictly under the workdir (`resolveWorkdirFile`), so no operator-typed or intent-supplied value reaches it -- the intent's control is a bare boolean, and the client never names a file.

Headers: `Content-Type: text/plain; charset=utf-8`, `Content-Disposition: attachment; filename="psilink-run-<id>.log"`, and `X-Content-Type-Options: nosniff`, plus the `no-store` discipline. It is served as an attachment rather than inline for two reasons: a debug-level log is private material -- it can contain partner identity, linkage keys, and data categories, which is why the CLI creates the file owner-only -- and it holds text the partner and the transport chose, which an attachment keeps off the console's own page.

## The job-create intent

`POST /api/jobs` accepts a JSON body validated against a strict schema, discriminated first on `mode` -- `"exchange"` or `"zeroSetup"` -- and, within each mode, on `channel`. The discriminant is optional on the exchange arm alone: a body that omits `mode` defaults to `"exchange"`, while a zero-setup body must name itself explicitly, so an omitted `mode` is never routed there. Both modes are injection-closed by construction, on identical grounds: no field on either becomes an argv string, a filesystem path, a host, or a credential reference, and every leaf arm is `.strict()`, so a smuggled `connection`, `server`, or `remote` key fails the parse regardless of mode. On the sftp arm of either mode, connection material is drawn exclusively from the authored server-side connection (see [The authored SFTP connection](#the-authored-sftp-connection)); the client contributes no connection field on either mode. `POST` stays closed to connection material even where the connection is operator-authored in-app: authored material flows only through `PUT /api/jobs/sftp` (a separate endpoint whose body is validated by the same connection chain), never a field on either mode's intent. Every arm of both modes additionally has exactly one input source -- inline `inputCsv` content or a mounted `inputFile` reference -- enforced by a union-level refine after each arm's own strict parse, so a body naming both or neither fails identically regardless of mode.

### The exchange intent

An exchange intent (`mode: "exchange"`, or `mode` omitted) drives `psilink exchange` against a composed config and key file: the linkage terms and the shared secret are pre-agreed and stated on the intent itself, so the exchange runs against a partner already holding the same secret.

| Field | Type / validation | Why it cannot inject |
| ----- | ----------------- | -------------------- |
| `mode` | optional literal `"exchange"` | Defaults to `"exchange"` when omitted (see above); an explicit `"exchange"` is also accepted. |
| `channel` | `"filedrop"` or `"sftp"` | The closed discriminant. A filedrop exchange has no host and no credential field at all, so the connection block the server composes holds nothing injectable. An sftp exchange draws every piece of connection material from the operator-authored connection; the sftp arm has no connection field at all (the console runs exactly one authored connection). A `webrtc` or other value is rejected as unknown. A `remote` field on either arm is rejected as an unknown key by the strict parse. |
| `linkageTerms` | core's `LinkageTermsSchema` | Bounded partner-authored vocabulary (field names, key elements, transforms). It has no filesystem path, host, or command field, so a hostile value cannot escape into argv or the filesystem. Its `identity` is optional to core, and required by this surface only under `signing.mode: "certificate"` (see the `signing` row). |
| `sharedSecret` | base64url 32-byte pattern (`/^[A-Za-z0-9_-]{42}[AEIMQUYcgkosw048]$/`) | Credential material matching the CLI key-file shape. It is written into a fixed-name key file, never used as a path or argv fragment; a malformed secret is rejected here rather than crashing the child at load. |
| `inputCsv` | non-empty string, length-capped | content written to a fixed, server-chosen filename in the workdir. The client never names a file. The cap is anchored to the browser intake's own 100 MiB file-size gate, so a CSV that passed that gate is never rejected here (see [Size caps](#size-caps)). The alternative to `inputFile`; exactly one of the two is set. |
| `inputFile` | `{ "name": "<segment>" }` | A reference to a file in the mounted work-input directory (`JOB_INPUT_DIR`, see [Environment variables](#environment-variables)), not content: `name` is a single admissible path segment (the same shape rule the work-input listing applies) and is resolved against the mounted directory at create time -- a name that resolves to no regular file is refused before any workdir exists. The CLI reads the file in place; nothing is copied into the workdir. The alternative to `inputCsv`; exactly one of the two is set. |
| `metadata` | optional; core's `MetadataSchema` | The operator's per-party column metadata (each column's name, semantic type, role, and payload flag). Structured data written into the config as YAML values, never an argv fragment, path, host, or credential. Included so the CLI honors the operator's disclosure edits (which columns are sent vs ignored) instead of inferring metadata from the column names. |
| `standardization` | optional; core's `StandardizationSchema` | The operator's per-party standardization pipeline (per-field transform steps). Structured data written into the config as YAML values, never an argv fragment, path, host, or credential. |
| `expectedPayloadColumns` | optional `string[]` | The acceptor's received-payload commitment: the partner-namespace column names it will enforce it receives, mirrored from the invitation's disclosed set. Column names only, never a path, host, or credential. An empty array is a strict "receive nothing" (a non-empty partner payload then aborts); an omitted field reconciles lazily. Set on the acceptor path only; the inviter omits it. |
| `expectedPartnerDeduplicate` | optional boolean | The acceptor's terms-side commitment: the `deduplicate` the accepted invitation declared for the inviting party's own side. A schema boolean -- never a path, host, credential, or argv fragment. `false` is a real declaration and is forwarded verbatim; only an omitted field binds nothing. Set on the acceptor path only; the inviter omits it. |
| `side` | optional `"inviter"` or `"acceptor"` | Which side of the partnership the submitting party runs. A closed enum that selects a composition rule rather than contributing a value: it decides only whether the composed config holds an `outbound_payload_consent` record (see [Composed CLI configuration](#composed-cli-configuration)). It is never a path, host, credential, or argv fragment. An omitted `side` composes no record, which is the state every non-acceptor is in regardless; the console's server-job driver config requires it, so a console acceptance cannot be built without one. |
| `options` | tuning subset (below) | Every field is a number, boolean, closed enum, or a bounded single-label `peerId` -- none can hold a path, host, credential, or command. |
| `eventStream` | optional boolean (default true) | Whether `--event-stream` is passed. |
| `diagnosticRun` | optional boolean (default false) | Run at the CLI's debug log level with its sub-library verbosity, capturing the whole log to `run.log` in the workdir (see [Subprocess invocation](#subprocess-invocation)). A bare boolean that selects fixed flags: it names no path, and the log's location is the server's. |
| `sweepExchangeFiles` | optional boolean (default false) | Pass `--sweep-exchange-files`, the CLI's own pre-rendezvous recovery of a directory a crashed prior run left protocol files in. What counts as a protocol file, and whether a retain-mode transcript may be deleted, are the CLI's decisions entirely; the escalation past that guard (`--force-retain-sweep`) is not representable on this surface. |
| `signing` | optional `{ "mode", "partnerFingerprint"? }`, strict | The receipt-signing choice. `mode` is `"none"` or `"certificate"` -- an allowlist of the two modes an exchange honors, matching core's own `assertSigningModeImplemented`, so `session-derived` (and any mode later added to the format but not yet implemented) is refused here rather than accepted into a job whose child then exits 64 on the very config it exists to run. `partnerFingerprint` is admitted only under `certificate`, is required there (matching core's `assertCertificateModePinsPartner`, so the job is refused rather than started as a run that reaches the signature swap -- after this party's payload has crossed -- and terminates against the missing pin), and must be a canonical 43-character unpadded base64url SHA-256 digest -- a public digest of a public certificate, never a credential, and no separator, path, or flag-shaped value fits the shape. `certificate` also requires a non-blank `linkageTerms.identity`, the one cross-field rule of this surface that spans two blocks (matching core's `assertCertificateModeNamesLocalParty`): a certificate is trusted by the identity its holder used in the agreed terms, so an unnamed party's job is refused for the same reason and at the same point, with the issue on `linkageTerms.identity` rather than on the signing block. Neither path field of the CLI's `signing` block is representable: `identity_file` and `receipt_output` are supplied by the server at composition (see [Composed CLI configuration](#composed-cli-configuration)). |
| `retentionDisposition` | optional non-empty string, capped at core's `MAX_TEXT_LENGTH` (1024), no control characters beyond tab/LF/CR | This party's own retention/disposition note, written into the composed config as a YAML value and from there into this party's exchange record -- never swapped with the partner, cross-validated, or folded into the agreed-terms hash. The cap is the record schema's own ceiling, so a note that passes here cannot pass config validation only to fail the record build. The note is composed verbatim, so it is held to a control-character rule of its own: the C0 and C1 ranges and DEL are refused apart from tab, LF, and CR -- the whitespace a multi-line note legitimately holds -- since a NUL or an ESC would compose into the YAML and land in the record. That rule is this field's own, not one the surface applies uniformly: every other bounded string here is held to a shape rule drawn for its own sink (`peerId`'s single-label pattern, `inputFile.name`'s path-segment rule) rather than to a common control-character policy. Never a path, host, credential, or argv fragment. |

Both channel arms are `.strict()`: an unknown key (a smuggled `path`, `host`, `server` block, or `@path` credential reference) fails validation, and each arm admits only its own fields. The `options` subset is the tuning settings only -- `pollIntervalMs`, `peerTimeoutMs`, `serverConnectTimeoutMs`, `maxReconnectAttempts` (0..604800), `timestampInFilename`, `locklessRendezvous`, `peerId`, `retainFiles`, and `unexpectedFiles` (`error`/`warn`/`ignore`) -- plus `connectionPerPoll` on the sftp arm alone. The path and directory fields of the CLI's file-sync options are intentionally not exposed: the server owns every directory.

`connectionPerPoll` is admitted on the sftp arm only, mirroring where the CLI applies it: the ephemeral-session mode dials a real SFTP session, and a filedrop client holds none, so the filedrop arm's strict parse refuses the key rather than accepting a value the run cannot honour.

`pollIntervalMs` has no floor beyond core's own positive-integer rule, on either channel. An sftp poll is a directory listing against a remote server, so a sub-second interval can trip that server's anti-flood protection -- but the interval is the operator's own choice about a connection they authored on their own console, and the CLI warns about it rather than refusing it. The boundary therefore matches the CLI: the value is admitted and the authoring surface raises the anti-flood advisory at the threshold core exports as `LOW_POLLING_FREQUENCY_WARN_MS` (1000 ms), where the operator can still act on it. A demo against a controlled server legitimately polls sub-second, and a floor here would make the advisory unreachable on the one channel it is about.

`peerId` is the subset's one free-text field, and it is bounded rather than passed through. It becomes the filename prefix of every file this party writes into the shared rendezvous directory, so this boundary admits only a single label: at most 64 characters, matching `/^[A-Za-z0-9](?:[A-Za-z0-9 _-]*[A-Za-z0-9])?$/` -- ASCII letters, digits, spaces, `-`, and `_`, beginning and ending with a letter or digit. That refuses the separators, dot runs, and leading dash a filename component must never contain, and it is stricter than core's own field (which admits any non-empty string, because a CLI operator authors their own configuration by hand and their filename-safety note is advisory there).

Every rule about the option values is core's, not this boundary's: the validated block is re-parsed through core's file-sync options schema, and its issues are raised as this parse's issues. So `peer_id` requires `timestamp_in_filename: true`, `peer_id` may not be the reserved `temp`, and `retain_files` requires both `timestamp_in_filename: true` and `lockless_rendezvous: true` -- each refused at create time, in core's own wording, rather than at config composition or at rendezvous. Retain mode's implication (that stating `retain_files` alone turns on the other two) is resolved by the same core helper the CLI's `--retain-files` uses, applied by the authoring client before it POSTs; a body stating `retain_files` alone, with neither implication, is a `400` rather than a silently corrected intent.

The `metadata` and `standardization` fields are validated structured data -- core's `MetadataSchema` and `StandardizationSchema`, respectively -- and have no injectable field. Core bounds each column `name` and closes `role`/`type` to enums; the arrays and the free-text `description`, `output`, and `input` are additionally bounded web-side at this boundary (see [Size caps](#size-caps)). A standardization step's `params` is a `Record<string, unknown>`, unbounded by nature and left uncapped at the field level -- the boundary body cap is its safety check. The linear-time regex-dialect gate (`docs/spec/PROTOCOL.md`, "Transform regular-expression dialect") -- which caps and dialect-checks transform-pattern sources -- applies to the negotiated `linkageTerms` transforms, not to the standardization pipeline's raw-pattern steps. That is a compile/size cost, not a ReDoS hole: every standardization raw-pattern step still compiles and runs under core's linear-time RE2 engine (RE2JS), so it cannot backtrack catastrophically. It remains a resource bound, not an injection escape: no metadata or standardization value becomes an argv fragment, a path, a host, or a credential.

### The zero-setup intent

A zero-setup intent (`mode: "zeroSetup"`, required and literal) drives the CLI's zero-setup command instead of `psilink exchange`: both parties run the CLI against the same server they agreed on out of band, and the CLI infers linkage terms, metadata, and standardization from each party's own input file rather than either party pre-authoring them for both. It therefore has none of the exchange mode's `sharedSecret`, `linkageTerms`, `metadata`, `standardization`, `expectedPayloadColumns`, or `expectedPartnerDeduplicate` fields, and no connection field at all: on the sftp arm connection material is drawn exclusively from the effective server-side connection, exactly as the exchange arm; the filedrop arm's connection is the configured rendezvous directory, again exactly as the exchange arm.

| Field | Type / validation | Why it cannot inject |
| ----- | ----------------- | -------------------- |
| `mode` | literal `"zeroSetup"` | Required and literal -- a zero-setup intent names itself; a body that omits `mode` is routed to the exchange arm instead, never here. |
| `channel` | `"filedrop"` or `"sftp"` | The closed discriminant, identical in meaning to the exchange arm's. |
| `inputCsv` / `inputFile` | as the exchange mode | content or a mounted-file reference, exactly as the exchange mode's fields of the same name; exactly one of the two is set. |
| `options` | tuning subset, narrowed to what an argv can hold | The exchange mode's fields less `unexpectedFiles`, with the same `peerId` bound, the same core-sourced cross-field rules, the same absence of a poll floor, and the same sftp-only `connectionPerPoll`. Every admitted field reaches the run as a flag -- see below. |
| `eventStream` | optional boolean (default true) | As the exchange mode. |
| `diagnosticRun` / `sweepExchangeFiles` | optional booleans (default false) | The per-run controls, identical in meaning and effect to the exchange mode's fields of the same name. |
| `linkageStrategy` | optional `"cascade"` or `"single-pass"` | A closed enum forwarded to the CLI's `--linkage-strategy`; never a path, host, or credential. |
| `identity` | optional string, 1 to 1024 characters, no leading `-`, no control character | A bounded operator label forwarded to the CLI's `--identity` (the party's name/org/contact string). Free text rather than a closed enum, so it takes the two shape rules the shared label contract states: a leading `-` is forbidden so a flag-shaped value cannot masquerade as a CLI flag (the driver also emits it as a single `--identity=<value>` token, which parses a `-`-leading value verbatim regardless), and every C0 control, DEL, and C1 control is refused -- no tab/LF/CR exception, unlike the retention note's rule, because the label is single-line and rides the run into this party's disclosure record. Letters outside ASCII are untouched. |

Both channel arms are `.strict()`, so no `sharedSecret`, `linkageTerms`, `metadata`, `standardization`, `expectedPayloadColumns`, `expectedPartnerDeduplicate`, or any other unmodeled key -- including a `connection`/`server`/`remote` key -- survives validation, and the exactly-one-input-source rule holds exactly as in the exchange mode. Because a zero-setup run has no shared secret, it writes no key file and composes no config document at all: its connection reaches the CLI as argv instead -- see [Composed CLI configuration](#composed-cli-configuration) and [Subprocess invocation](#subprocess-invocation).

**Emit or refuse.** A zero-setup run composes no configuration document, so its `options` reach the child only as flags. Every field the zero-setup arms admit has one, and every value the flag it rides would itself refuse is refused by the schema rather than accepted and dropped -- a job created on a value its own child exits `64` on would occupy the console's single run slot to produce nothing:

- Emitted (see [Zero-setup invocation](#zero-setup-invocation)): `retainFiles`, `locklessRendezvous`, `timestampInFilename`, `peerId`, `pollIntervalMs`, `peerTimeoutMs`, `serverConnectTimeoutMs`, `maxReconnectAttempts`, and -- on the sftp arm -- `connectionPerPoll`.
- Refused: `unexpectedFiles`, a configuration-only key with no CLI flag at all, so the strict parse rejects it as an unknown key on both arms; `connectionPerPoll` on the filedrop arm, exactly as in the exchange mode.
- Refused as unrepresentable: a `peerTimeoutMs` or `serverConnectTimeoutMs` that is not a whole number of seconds when expressed in milliseconds. Those two ride the CLI's coarse duration flags, whose grammar takes a second-or-coarser unit and rejects a millisecond one, so a sub-second remainder has no faithful flag form and is a `400` rather than a value silently rounded into one the client did not send. `pollIntervalMs` has no such rule: its flag accepts a millisecond suffix, so any admitted value is preserved exactly.
- Refused as out of range: a `peerTimeoutMs` or `serverConnectTimeoutMs` above `MAX_TIMEOUT_SECONDS` (604800 s, seven days), the sanity ceiling `--peer-timeout` and `--connection-timeout` are capped at, or a `maxReconnectAttempts` above `MAX_RECONNECT_ATTEMPTS` (604800), the ceiling `--max-reconnect-attempts` is capped at. Both constants live in `packages/core/src/config/connection.ts` -- core is the one module both the CLI's parse guard and this boundary import, so neither pair can drift. Past either ceiling the CLI exits `64` before any side effect, so an over-ceiling value is a `400` here instead of a job created to spawn a command line that refuses it. `pollIntervalMs` has no ceiling, exactly as `--polling-frequency` has none: a long interval is merely slow.

### Size caps

The intent is operator-authored, never partner-supplied, and the API is feature-gated and reached only from the operator's own machine, so the worst case an oversized intent reaches is a single operator exhausting their own console's memory -- not a remote surface. Two defense-in-depth layers bound it anyway, so neither the request nor a persisted artifact can grow without limit:

- **Boundary body cap.** `POST /api/jobs` reads its body under a hard byte cap (224 MiB), streamed off the request and counted chunk by chunk; the read aborts the moment the running total exceeds the cap, and `Content-Length` is never trusted (it can be absent or understated on a chunked request). An oversized body is a `413` before the body is fully buffered or any schema parse runs. The cap sits well above the JSON-encoded size of a realistic schema-valid intent -- real CSV text barely grows under JSON string escaping -- so a legitimate intent reaches a clean schema error rather than a boundary `413`. It is not sized to clear a pathological payload built from control characters that each escape to a 6-byte `\uXXXX` sequence (not valid CSV), nor an unbounded standardization `params`; bounding those here is exactly the memory guard's job. It applies identically to both modes. Within the cap the accumulated bytes reach the shared bounded-JSON chokepoint (`parseBoundedJson`, see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#application-layer-parsed-input-bounds)) undecoded, so its UTF-8-fatal decode applies: a body holding an invalid byte is a `400`, never a value parsed with U+FFFD substituted for it. Every route reading a body under a cap -- each `413` in the table above -- shares that read.
- **Schema caps.** The intent schema bounds `inputCsv` (anchored to the browser intake's 100 MiB file gate), the `expectedPayloadColumns` array and its entries, the `metadata` array and each `description`, and the `standardization` array, each transformation's `steps`, and its `output`/`input`. The bounds are generous -- far above any legitimate intent -- and apply to both channel arms. They are enforced web-side at this boundary rather than in core's shared schemas, so they do not tighten core's partner-facing validation. The `inputCsv` cap applies identically to a zero-setup intent's `inputCsv` field; the `expectedPayloadColumns`, `metadata`, and `standardization` caps are exchange-mode only, since a zero-setup intent has none of those fields.

The browser's read of the console's ANSWERS is bounded the same way. Every job-API client reads a response body under a per-endpoint byte cap and parses the accumulated bytes through `parseBoundedJson` (`readBoundedJson` / `readJsonOrNull` in `apps/web/src/psi/jobClient/jobApiBody.ts`, over the shared read in `apps/web/src/utils/boundedJsonBody.ts`), so an answer that is not the one the endpoint returns -- a proxy's error page, a truncated stream, a console at a different version -- costs a bounded read and the client's own malformed-body state rather than an unbounded buffer in the operator's tab. Two of the four caps follow from what the body holds: the fixed-shape status bodies (16 KiB, every field a boolean, number, closed-set member, id, fingerprint, or one bounded path or message) and the SFTP connection projection (64 KiB, matching the authoring body's own cap, which is what decides how long the projected fields can be). The hand-off cap (32 MiB) follows the create intent's own caps, since the template recomposes the intent's blocks: the metadata columns and their descriptions, the expected payload columns, and the standardization outputs and inputs are each count- and length-capped at the create boundary, and the margin above their sum holds the rest of the document. A standardization step's `function` name and `params` record are the one part no field-level cap bounds, so a template inflated through them exceeds the cap and reads as no hand-off. Only the listing cap (8 MiB) follows no code-level bound -- the operator's own mount contents and CSV header decide the listing, profile, and coverage bodies -- so it is headroom over any answer this console plausibly returns rather than a derived bound. `Response.json()` is banned in `apps/web/src` and `apps/web/server` (`no-restricted-properties`, beside the raw-`JSON.parse` ban) so a new client cannot read one unbounded. That ban reaches the `.json()` route only: a `response.text()` or `response.arrayBuffer()` read buffers the whole body before any parse and no lint rule refuses it, so taking the bounded read rather than either is a convention, not something the ban enforces.

The `expectedPayloadColumns` field is a list of partner-namespace column names -- no path, host, or credential -- validated as a string array. Its empty-vs-absent distinction is preserved end to end (an empty array is forwarded verbatim as a strict commitment; only an omitted field stays lazy); see the composed-config note below. `expectedPartnerDeduplicate` needs no cap: it is a schema boolean, and its present-vs-absent distinction is preserved the same way.

### Composed CLI configuration

This section covers the exchange mode only: a zero-setup intent composes no config document and no key file at all, so a zero-setup job's workdir has neither -- see [Subprocess invocation](#subprocess-invocation) for how its connection and tuning reach the CLI instead, as argv.

From a validated filedrop intent the server composes the CLI config document (snake_case YAML the CLI loads verbatim) through core's `mintExchangeFile`, so the assembled spec is validated by the CLI's own schema before it is written. The composition is fixed:

- The connection is a credential-free `filedrop` locator whose one path field is set to the resolved rendezvous mount (`JOB_RENDEZVOUS_DIR`, or `JOB_DATA_ROOT` when it is unset) -- server-side environment configuration, never a client value. By core's `ExchangeFileInput` typing no credential is representable in a filedrop connection. On a split-provisioned console (`JOB_RENDEZVOUS_OUTBOUND_DIR` set) the connection instead holds `inbound_path` (the inbound mount) and `outbound_path` (the outbound one), never the single `path` beside them; `mintExchangeFile` validates the pair through core's own directory-mode rules, so the pair-set-together, must-differ, and retain-mode preconditions are stated once, in core, rather than restated here. Because every filedrop exchange on such a console holds the pair, the retain-mode precondition is a precondition of running one at all: the console states it at each authoring gate in its own words, and `POST /api/jobs` refuses a filedrop intent whose `options.retain_files` is not `true` with a `400` before any workdir exists, rather than letting core's refusal be reported as a compose failure.
- No `authentication` block is ever assembled; the shared secret rides the separate key file.
- The intent's `linkageTerms` reach the document only after core's schema validation.
- The intent's `metadata` and `standardization`, when present, are attached as the config's `metadata` and `standardization` blocks (omitted when absent). Including them is what makes the operator's data-prep edits authoritative on this path: the CLI's `prepareForExchange` uses the composed metadata instead of falling back to `inferMetadata`, which would default an unrecognized column to disclosed payload and could silently disclose a column the operator marked ignored.
- The intent's `expectedPayloadColumns`, when present, is attached as the config's `expected_payload_columns` (an empty array is attached verbatim; only an omitted field is left off). Including it makes the acceptor's received-payload commitment explicit: the CLI prefers `expected_payload_columns` over the `linkageTerms.payload.receive` fallback, which is undefined for a token that discloses columns but has no `payload.send` -- a shape where the fallback would fail open (silently ingesting extra partner columns) while the browser acceptor aborts. The inviter path omits it.
- The intent's `expectedPartnerDeduplicate`, when present, is attached as the config's `expected_partner_deduplicate` (a `false` is attached verbatim; only an omitted field is left off). Including it is what makes the acceptance's terms binding survive to the run: the console conducts the exchange at a separate CLI invocation holding no invitation, so without the field the CLI would hold the inviter's presented `deduplicate` to nothing and an inviter that declared `false` could present `true` -- widening what this party's own records disclose. The inviter path omits it. The field itself is specified in [EXCHANGE_FILE.md](EXCHANGE_FILE.md).
- The config's `outbound_payload_consent` is derived, not copied, and only for `side: "acceptor"`. It is core's `deriveOutboundPayloadConsent` over the same `linkageTerms.output` and `metadata` the same composition writes into the config, so the recorded consent and the config it rides in cannot name different sets. The three states are core's: the field is absent where `output.share_with_partner` is false (nothing crosses, so there is no disclosure to consent to), `pending` where the intent held no metadata (no set was resolvable), and `confirmed` with the disclosed set otherwise -- disclosed in the `disclosed_payload_columns` sense, so a column the operator roled ignored is not in it. Any other `side`, and an omitted one, composes no record. The record is what makes a later unattended `psilink exchange` against this config subject to the pre-connect outbound-consent gate rather than passing it as "no record"; the field itself is specified in [EXCHANGE_FILE.md](EXCHANGE_FILE.md).
- The tuning `options`, if any were set, are narrowed to the CLI's file-sync options and attached; when none were set the block is omitted entirely.
- The `signing` block is attached only for `signing.mode: "certificate"`. `mode: "none"` -- and an intent stating no choice at all -- composes no block, which is the absent block the CLI already treats as "sign nothing", so an operator who authors no receipt composes a config with no signing key at all. When attached, the block holds the intent's `mode` and its `partner_fingerprint` verbatim -- the create schema requires the pin under this mode, so an attached block always holds one -- plus two server-chosen paths the intent cannot name: `identity_file`, the long-lived identity in the mounted data root, and `receipt_output`, the fixed `receipt.json` in this job's workdir (see [Workdir layout](#workdir-layout)). A `certificate` intent reaching composition with no resolved paths is a hard error, never a silently unsigned run.
- The intent's `retentionDisposition`, when present, is attached as the config's `retention_disposition` verbatim. It is per-party and local: the CLI writes it into this party's own exchange record and it is never swapped with the partner, cross-validated, or folded into the agreed-terms hash. The field itself is specified in [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#retention-and-disposition).

An sftp intent is composed differently. `mintExchangeFile`'s input type cannot represent a credential -- an invariant shared with the browser's exchange-file minting that must not be widened -- so the server assembles the exchange spec directly. The connection's `server` block is the authored entry verbatim (its `@path` credential references land in the YAML as references, resolved only by the CLI child), and the client's `linkageTerms`, `metadata`, `standardization`, `expectedPayloadColumns`, `expectedPartnerDeduplicate`, `retentionDisposition`, and tuning options attach exactly as on the filedrop path. The `signing` block is composed by the same rule from the same server-chosen paths, and the acceptance's `outbound_payload_consent` is derived by the same rule. The assembled spec is validated through core's exchange-spec schema before serialization, with only the schema's own fields reaching the YAML. The intent contributes nothing to the connection. No `authentication` block is assembled on either path.

The key file body is `{"sharedSecret":"<value>"}` with no `expires` stamped, so a server-driven job has no invitation-token lifetime of its own.

## The authored SFTP connection

An sftp job's connection material -- for either mode -- never comes from the create intent; the operator authors it in-console through `PUT /api/jobs/sftp` ([Authoring the SFTP connection](#authoring-the-sftp-connection)). The console is a single-owner prototyping tool -- the person who runs the container, authors the connection, and runs the exchange is the same person -- so there is no deploy-time provisioning step and no server file to pin in advance. The console conducts one exchange and is not a store of named connections, so there is exactly one effective outbound SFTP connection at a time, held in a single in-memory slot scoped to the one exchange. It is never persisted, so a restart forgets it, and deleting the exchange it was authored for (`DELETE /api/jobs/:jobId`) clears it, so it never lingers into the next.

The authored connection resolves to an internal server block (`host`, `port`, `username`, a remote directory as either `path` or the `inbound_path`/`outbound_path` pair, one primary credential `@path`, an optional `private_key_passphrase` `@path`, `keyboard_interactive`, and `host_key_fingerprint`) validated by these rules, each critical:

- **Strict field allowlist.** The block admits exactly `host`, `port`, `username`, `path`, `inbound_path`, `outbound_path`, `password`, `private_key`, `private_key_passphrase`, `keyboard_interactive`, and `host_key_fingerprint`; any other key is a validation error. This is stricter than the CLI's connection schema, which is non-strict and admits blocks the console must never hold: `provision` (whose auth block holds inline HTTP credentials and drives pre-connect egress) and the detected-but-rejected `certificate`/`known_hosts`. Strictness also turns a typo into a validation error instead of a silently dropped field.
- **One remote-directory form, chosen by core.** The remote directory is either the single shared `path` or the split `inbound_path`/`outbound_path` pair -- a server with distinct drop and pickup folders. Which combinations are coherent is not restated here: the composition check below runs core's own directory-mode rules, so `path` alongside the pair, half a pair, and two paths that resolve to one directory are each rejected rather than reconciled.
- **Mandatory literal pin.** `host_key_fingerprint` is required (a string or a list) and every element must be a literal OpenSSH SHA256 fingerprint; an `@path` reference is rejected. The job child is non-interactive (stdin ignored), so first-use trust can never happen there; requiring the pin makes every console SFTP connection host-key-pinned, verified before authentication. A host-key rotation is staged by listing the old and new fingerprints together.
- **Credential must be an existing `@path` (hard); containment is a warning.** `password`, `private_key`, and `private_key_passphrase`, when present, must be `@path` references to an absolute path, and the referenced file must exist at validation time (checked by `realpath` only; the bytes are never read into the server) -- each a hard error. Inline values are rejected, so no secret enters server memory or any composed job file; the CLI child resolves the reference at config load. A reference that resolves inside the data root or -- when configured distinctly -- the rendezvous directory is a non-blocking warning, not a rejection: the console is a single-owner prototyping tool, so referencing a credential in the operator's one mounted folder is guided-against, not forbidden. The containment is checked on both the lexically resolved path and its realpath (so a symlink cannot resolve into an excluded directory undetected), producing at most one warning per credential field. Each warning names the field and the directory only -- never the reference, resolved path, or secret -- and points at the fix: mount a separate read-only secrets directory (`JOB_SECRETS_DIR`) and reference the file there. The warnings ride the connection's projection so both the `PUT` response and a later `GET` (a console reload) include them.
- **Composition check.** The block is additionally parsed through core's connection schema as `{channel: "sftp", server: <block>}`, so the CLI's cross-field refines (one primary auth method, a passphrase requires a key, keyboard-interactive requires a password, canonical fingerprint form, and the directory-mode rules above) hold at authoring time rather than first inside a job. A split block is composed with the retain-mode option block, because core's remaining directory rule -- a split requires `retain_files` -- is a rule over the exchange's tuning options, which a connection does not hold and this endpoint cannot know. That precondition is enforced everywhere the connection and the options are known together, since the two are authored separately and either can change after the other. The console's authoring form states it while the operator is still at the controls, and its create and continue gates re-ask it before an invitation is minted or a run is started, so a retain toggle flipped after the connection was authored blocks there rather than reaching the job. `POST /api/jobs` composes the whole spec through core and so refuses a split job created without retain mode, and a zero-setup run meets the CLI's own `--outbound-path` guard.

The connection is frozen once authored: changing the host or pin means re-authoring (`PUT` again) or clearing it. The referenced credential files are live -- the CLI child re-reads them at each job's config load -- so rotating a secret in place takes effect without re-authoring.

### `GET /api/jobs/sftp`

Returns the authored connection as an explicitly mapped, credential-free projection: `{ "configured": false }` when none is authored, else `{ "configured": true, "host": "...", "port"?: <int>, "path"?: "...", "inboundPath"?: "...", "outboundPath"?: "...", "credentialWarnings": [ "..." ] }` and nothing else -- no username, no credential references (which would reveal the secret-mount filesystem layout), no fingerprint. The remote directory appears in whichever single form the connection holds; the browser reads a half pair, or a pair beside `path`, as no connection at all rather than half a layout. `credentialWarnings` holds the non-blocking credential-containment warnings the credential rule above produces (empty when every credential resolves outside the excluded directories), so a console reload re-surfaces them. An enabled API with no connection serves `200 { "configured": false }`, the same shape family and gate as `GET /api/jobs/rendezvous` (a `404` there means the API is disabled). The console web build uses this to gate the run-SFTP-here behavior and to author an invitation's sftp endpoint from the locator. The static `sftp` segment cannot be captured as a job id: ids are validated as canonical v4 UUIDs before any use, which `sftp` is not.

## Authoring the SFTP connection

`PUT /api/jobs/sftp` authors the connection from a JSON body with a file-reference credential or a pasted value the server materializes to a file (see [Materializing a pasted credential](#materializing-a-pasted-credential)). The body is read under a small byte cap (`65536`) -- a pasted password or SSH private key rides it but is far under the cap -- so an oversized body is a `413` before any parse. Fields:

| Field | Type / validation |
| ----- | ----------------- |
| `host` | non-empty string (required) |
| `port` | integer `0..65535` (optional) |
| `username` | non-empty string (optional) |
| `path` | non-empty string (optional) -- the remote shared directory |
| `inboundPath` / `outboundPath` | non-empty strings (optional, set together) -- the split remote directories, this party reading the peer's files in the inbound one and writing its own to the outbound one. Mutually exclusive with `path`; the two must differ |
| `hostKeyFingerprint` | a literal OpenSSH SHA256 fingerprint or a non-empty list of them (required); an `@path` reference is rejected |
| `credential` | a credential in one of three forms (all tagged with `credType: "password" \| "private_key"`, which maps the resolved reference to the `password` or `private_key` field): a typed `{ "kind": "ref", "ref": "@/absolute/path", "credType" }` -- the documented exception for a credential outside any listable mount -- a secrets-mount locator `{ "kind": "mountRef", "mount": "secrets", "subPath": ["seg", ...], "credType" }` the operator picked in the browser, or a pasted value `{ "kind": "raw", "value": "<secret>", "credType" }` the server materializes to a file (see [Materializing a pasted credential](#materializing-a-pasted-credential)). Any other `kind` is refused. |
| `privateKeyPassphrase` | an `@path` reference (optional) |
| `keyboardInteractive` | boolean (optional) |

The body is strict: an unknown key (a `provision`, `certificate`, `known_hosts`, or a bare inline credential field) fails validation, with one spelling this rule does not report -- a key literally spelled `__proto__` is neither rejected as unrecognized nor copied into the job (measured against the route: `200`, no prototype pollution). A `mountRef` credential is resolved server-side against the resolved `JOB_SECRETS_DIR` via the same mount-file resolver the browse listing uses (`resolveMountFile`) and rewritten to `@<realpath>`, so no container-absolute path ever transits the browser. The mount is a single id (`secrets`, a cross-mount locator is out of scope), and an unset mount, an unknown id, or a `subPath` naming no readable regular file (or one escaping the mount) is a `400` naming the credential field only -- never a path. A `raw` credential is materialized to a server-owned file whose `@path` replaces it (below). The resolved (materialized, typed, or picker-resolved) `@path` credential and the passphrase are then folded into a server block and run through the validation chain of [The authored SFTP connection](#the-authored-sftp-connection) -- the strict field allowlist, mandatory literal fingerprint, credential-must-be-an-existing-`@path`, and the core-schema compose -- so every source is held to identical rules, containment warning included. A hard-validation failure is a `400` whose body is `{ "error": "<field path>: <reason>" }` naming a field path only -- never a submitted value, credential reference, or secret. An unmodeled key crosses as the fixed reason `unrecognized key` rather than the caller's own spelling of it, taken from the same formatter the probe and fingerprint routes use (see [Probing the server host key](#probing-the-server-host-key)). A malformed `raw` credential is rejected on shape (a non-string or empty `value`) before any write, and its `400` does not echo the value. Where the probe and fingerprint bodies report their first issue, this one reports every issue at fault, joined by `; `, each rooted at the sub-object it was raised against. The roots are `connection` or `connection.credential` for the field- and credential-shape checks, and a doubled `server.server` root -- e.g. `server.server.keyboardInteractive: ...` -- for an issue the core-schema compose raises against the composed block, since that block's own issue path already begins with `server` before the formatter prepends its root a second time. The response length is therefore proportional to the issue count and bounded only by the request-body cap (`MAX_SFTP_AUTHOR_BODY_BYTES`) -- a pathological body measured near 25x amplification -- which is acceptable on the loopback single-operator surface but is not a bounded contract. On success the response is the authored connection's credential-free projection, including `credentialWarnings` (the same body `GET` returns).

### Materializing a pasted credential

The `{ "kind": "raw" }` credential is the de-emphasized fallback for a secret that exists nowhere on the console as a file. It widens the credential threat model -- a pasted value transits the loopback API and is briefly held in server memory -- but only within the single-party-appliance trust boundary: a loopback-only browser on the operator's own machine, where the value crossing same-origin loopback and living momentarily in memory is on-host. The at-rest and partner-facing boundaries stay closed:

- **Materialize once, then rewrite.** The server writes `value` once to a server-owned file under a fixed, container-internal scratch directory (`/run/psilink/sftp-credentials`), then rewrites the credential to `{ "kind": "ref", "ref": "@<that file>" }` and runs the same credential checks the file-reference forms run. The scratch directory is asserted outside the data root and rendezvous directory at boot (below), so a materialized paste never raises a containment warning. Server memory holds `value` only transiently -- between request parse and the file write -- and never logs it, places it in argv or the child environment, or returns it in any response, projection, or SSE event; a JS string cannot be zeroized, so this is best-effort minimization rather than a guaranteed wipe. The composed `psilink.yaml` holds the resulting `@path`, never the value.
- **The scratch directory.** It is not `JOB_DATA_ROOT` and not the resolved `JOB_RENDEZVOUS_DIR`, and needs no extra operator mount, so a paste works with only the data root mounted. Its path defaults to a fixed container-internal location and is relocatable server-side with `JOB_SFTP_CREDENTIAL_DIR` (the image ships that default directory owned by the unprivileged account it runs as and uses it; a deployment under another account, or the test harness, points it at another writable, non-partner-syncable directory, since the default's parent `/run` is root-owned and the directory cannot be created at boot). It is created mode `0700`; each secret is written under a server-generated name (a v4 UUID) at mode `0600`, `chmod`-enforced after the write. A pasted secret exists at rest only as this file, and only as long as the connection it belongs to: it is deleted on the connection's `DELETE`/reset, on a re-author that replaces it, and when the exchange it was authored for is deleted (`DELETE /api/jobs/:jobId`). Unlike a workdir, it does not linger until deleted -- see the boot sweep below. A `raw` credential on a console with no scratch directory (the API disabled, or the boot setup skipped) is refused rather than composed inline.
- **Boot sweep and containment assertion.** At server startup, when the job API is enabled, the currently-configured scratch directory is swept clean (covering a secret orphaned by a restart -- an SSH credential must not inherit the workdir's persistence). It is asserted to resolve strictly outside the data root, the rendezvous directory, the secrets mount, and the work-input directory, on both the lexical resolve and the realpath and in both nesting directions (a sweep of an excluded directory would destroy operator or partner data). The "no pasted secret lingers across a restart" guarantee therefore holds only while the job API stays enabled and `JOB_SFTP_CREDENTIAL_DIR` is unchanged between runs -- a since-removed override location is not the one swept. The containment check runs on the realpath before the directory is created or re-moded, so a symlinked scratch path resolving into an excluded mount is refused before any `mkdir`/`chmod` can touch that mount. A directory that fails the assertion refuses the boot, fail-closed, matching the console's posture. So does one that can be neither created nor swept, and that refusal names `JOB_SFTP_CREDENTIAL_DIR` alongside the (server-side, non-secret) path and the errno. The console run as an account other than the one the image built the default directory for reaches this with the default, where every operator mount is excluded and the variable is the only place left to point it. A tmpfs keeps pasted secrets off disk entirely and is preferred; the boot sweep is the fallback when the container does not arrange one. The boot creates the scratch directory `0700` and `chmod`s it, so that directory has to be one the unprivileged runtime account owns: a tmpfs mounted straight onto the scratch path arrives owned by root unless its mount options say otherwise, and the `chmod` then fails `EPERM` and refuses the boot. Mount the tmpfs at the parent (`/run/psilink`) and let the server create the scratch directory inside it, or mount it at the scratch path with `uid`/`gid` options naming the runtime account (uid 1000 in the shipped image). An override moves what that guidance applies to along with the directory. A deployment naming an account with `--user` points `JOB_SFTP_CREDENTIAL_DIR` at a directory that account can create -- `/tmp/psilink-sftp-credentials` is what the published POSIX launcher passes -- so the tmpfs goes at that path's parent (`/tmp`), or at the path itself with `uid`/`gid` naming the account the container was given rather than uid 1000. The image arranges a tmpfs at no path, the default's included, so an override left without one is on whatever filesystem the engine gives the container for its own writes, and the boot sweep is the fallback exactly as it is at the default.

If any validation step after the write rejects the entry (a bad host or fingerprint), the just-written file is deleted before the `400` returns, so a rejected paste leaves nothing at rest.

## Probing the server host key

`POST /api/jobs/sftp/probe` reads the host-key fingerprint an SFTP server presents, so the console can offer it beside the paste field for the operator to compare against the value the server operator published. It authors nothing: it never touches the authored connection, records nothing, and returns the observation for the caller to forget. The manager spawns the CLI's `probe-host-key --json` subcommand (the same binary the exchange runs; the server cannot probe SSH in-process -- see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#sftp-host-key-verification)) under the shared no-shell spawn discipline, caps and parses its stdout, and discards its stderr.

The child's budget fits inside the server's: a 10 s connect timeout plus the child's own 2 s bounded read of the peer's first bytes, against a 15 s SIGTERM watchdog. Crossing the watchdog would flip the typed result from `unreachable` to `timeout` and lose the diagnosis with it, so the ordering is held by an arithmetic check over the three constants rather than by this sentence.

The SSRF bounds are the module contract, pinned by tests:

- **Request holds host + port only.** The body is `.strictObject({ host, port? })` -- `host` a non-empty string, `port` a `0..65535` int -- so no username, path, or credential field is representable; an unmodeled key is a `400`. `host` additionally passes the shared bare-host predicate (no scheme, userinfo, path, or whitespace), the same rule `PUT /api/jobs/sftp` applies, so it cannot smuggle a URL. The body is read under a tight cap (4 KiB, `413` above it).
- **Response holds fingerprint + key type only.** A completed attempt is always a `200` with a discriminated body: `{ "status": "ok", "fingerprint": "SHA256:...", "keyType": "..." }` on success, or `{ "status": "unreachable" | "timeout" | "error" }` for a probe that ran but yielded no key. The fingerprint is re-validated against `HOST_KEY_FINGERPRINT_REGEX`, and the key type is length- and charset-capped (server-controlled bytes). No stderr, latency-beyond-category, saved-hosts list, or re-probe-on-change is exposed, and there is no credentialed "test connection". An `unreachable` may additionally include the peer-answer diagnosis below.
- **A diagnosed `unreachable` names what answered.** The console's guided audience is the likeliest to sit behind an intercepting middlebox, where a bare `unreachable` sends an operator to check an address that is right. On the exit-69 path the CLI's `--json` form emits its own diagnosis line on stdout (see [CLI.md](../CLI.md#when-something-other-than-an-ssh-server-answers-the-port)), and this endpoint states it structurally: `{ "status": "unreachable", "peerAnswer": "closedUnanswered" }`, or `{ "status": "unreachable", "peerAnswer": "nonSsh", "peerAnswerShape": "http" | "tls-alert" | "unrecognized", "peerAnswerExcerpt": "<escaped>" }`. The route is structural rather than a stderr forward for the same reason stderr is discarded at all: what crosses is a closed vocabulary plus one field of the peer's own bytes. That field is re-validated at the trust boundary -- the discriminant and shape against closed sets, the excerpt escaped through the display escape and capped at 512 characters (four times the CLI's 128-byte excerpt bound, since the escape expands a non-printable byte to `\xHH`) -- so nothing past that boundary holds a raw control byte or an unbounded span. A line outside that vocabulary degrades to the bare `unreachable` rather than to an error, which is also what a CLI without the line produces.
- **Single-flight and stateless.** One probe child runs at a time; a concurrent request is a `409` (empty body). The flag is claimed synchronously, independent of the exchange slot. The probe reconciles the child's exit -- CLI exit `69` to `unreachable`, a watchdog kill (SIGTERM at ~15 s, SIGKILL after a grace) to `timeout`, any other non-zero or malformed line to `error` -- and forgets it.

Non-2xx is reserved for HTTP-level conditions only: `400` for a bad body, `409` for a probe in flight, `404` when the feature gate is off, and `500` for an unexpected internal fault. A probe that ran and failed is a `200` category, never a `502`. A `400` message names a field path and a shape reason and nothing else: neither a submitted value nor the caller's own spelling of an unmodeled key, which the schema's own rejection message would otherwise quote. Every message a route derives from A schema issue -- this one, `POST /api/jobs/signing/fingerprint`, and `PUT /api/jobs/sftp` -- composes it through the same formatter module, so none can come to echo more than another. A handful of hand-written fixed strings (a bare-host or literal-fingerprint check, a credential-kind fallthrough, an `@`-file or missing-file credential error, the connection- and server-mapping-shape checks, and the probe route's own inline bare-host rejection) are composed at their own throw sites instead -- caller-byte-free as measured, but not covered by the module's rule.

## The signing identity

`POST /api/jobs/signing/fingerprint` creates-or-reuses this party's long-lived signing identity in the mounted working directory and returns its fingerprint, so the operator can share it out-of-band before a signed exchange. It is anchored here, at an explicit operator action, rather than at run time for the reason the CLI anchors it at `psilink fingerprint`: the partner must pin the fingerprint before the exchange, so the identity has to exist before the run rather than during it.

The manager spawns the CLI's `fingerprint` subcommand (the same binary the exchange runs) under the shared no-shell spawn discipline, caps and parses its stdout, and discards its stderr -- which names filesystem paths inside the container. Whether the identity already existed is read from the file's presence before the spawn, not from the child's own "Created"/"Loaded" banner, which is on that discarded stream.

The child's working directory is pinned to the mounted data root, never inherited from the server process. The argv has no `--config-file`, and with it omitted the CLI reads its default `./psilink.yaml` for identity hints -- resolved against the directory the child runs in, so the pin is what decides which document that is. It makes the mount the only place a hint config can come from: a `psilink.yaml` in the server's own working directory is never the one read (the flags override every hint it could supply, but a malformed one is a usage error the child exits `64` on). The data root is created if missing, since a spawn cannot start in a directory that does not exist.

The bounds mirror the host-key probe's:

- **Request holds a label and a boolean only.** The body is `.strictObject({ identity, exportCertificate? })` -- `identity` the operator's own `linkage_terms.identity`, held to the same shared label contract the zero-setup intent's `identity` is (the cap, no leading `-`, no control character), `exportCertificate` a bare toggle. The control-character rule is critical on this route rather than defensive: what the label is bound into is a long-lived certificate the partner pins and displays, and rebinding it costs a `psilink fingerprint --force` and a re-pin by every partner, so the input rule is where a stray byte is caught. Both server surfaces refuse the same set through one pattern, so neither can drift from the browser guard that mirrors it. No path field is representable, and an unmodeled key is a `400` whose message takes the same field-path-and-reason shape the probe's does. The body is read under a tight cap (4 KiB, `413` above it).
- **Response holds a fingerprint, a flag, and file names only.** A completed attempt is always a `200` with a discriminated body: `{ "status": "ok", "fingerprint": "<43 chars>", "created": <bool>, "identityFileName": "...", "certificateFileName"? }`, or `{ "status": "refused" | "timeout" | "error" }`. The fingerprint is re-validated against core's canonical `FINGERPRINT_REGEX` on both sides of the boundary. The two names are file names, never paths, so no container location crosses.
- **`refused` is the CLI's exit 64, reported as one category.** The request cannot be its cause: the body schema requires a non-empty `identity` (an absent one is a `400` before any child runs) and every path is server-composed. What remains are conditions in the mounted working directory -- an identity file that cannot be read or parsed, a first-time exclusive create that kept losing a create/delete race, a failed certificate-export write, or a malformed `psilink.yaml` in that same folder, which the pinned working directory makes the only config the child can read. The discarded stderr is the only place the CLI says which. So the boundary reports the class rather than a cause it cannot observe, and the console's copy points at the mount and at running `psilink fingerprint` there for the reason.

  Not every member of that class is the operator's own doing. `JOB_RENDEZVOUS_DIR` falls back to the data root (see [CONSOLE.md](../CONSOLE.md#mounted-work-input-directory)), so on a single-mount console running a `filedrop` exchange the pinned working directory is the partner-synced folder, and a `psilink.yaml` a partner writes there deterministically refuses identity creation. The scope of impact stops at that denial: the argv passes `--identity-file` and `--identity` explicitly, and both beat any hint the config could supply, so a planted document cannot redirect where the key is written or which identity a new key binds. The console's copy therefore names the file as a cause and tells the operator to read it rather than assume their own error.
- **Single-flight.** One fingerprint child runs at a time; a concurrent request is a `409` (empty body). The flag is claimed synchronously, independent of the exchange slot. Single-flight matters more here than for the probe: two concurrent runs would both create-or-load the same file, and the CLI's first-time create is exclusive precisely so a race cannot silently discard a generated key.
- **No regeneration.** There is no `--force` on this surface and no body field that reaches one. A re-key mints a new key with a new fingerprint and invalidates every pin a partner holds, so it is a coordinated action that stays on the command line, where the flag names what it does. This refuses the operator nothing: `psilink fingerprint --force` is theirs to run against the same mounted file whenever they mean to. The console states that, rather than offering the button.
- **The export never overwrites the identity.** `--export-certificate` writes the public certificate (never the private key) to a second fixed name in the same mount. The CLI refuses an export path that resolves to the identity file itself, and the console holds the same rule as its own check before it spawns, so the two server-composed names can never collide silently.

## The secrets mount and browsing

`JOB_SECRETS_DIR` names an operator-mounted directory the console browses to pick a connection's credential file. Unlike `JOB_INPUT_DIR` and `JOB_RENDEZVOUS_DIR`, it has no `JOB_DATA_ROOT` fallback: when it is unset the secrets mount is simply unavailable -- a fallback would default the credential-browse surface into the per-job, client-writable data root, the one place a credential directory must never be. It is server-side configuration, never a browser-sent path.

Browsing does not widen the credential-reference rule: a typed `{ "kind": "ref" }` reference a `PUT` holds is validated only against the data-root and rendezvous exclusions (above), not required to lie under the secrets mount. The mount is the browse surface; it is not an allowlist that authorizes a path. A `{ "kind": "mountRef" }` locator (see [Authoring the SFTP connection](#authoring-the-sftp-connection)) confines only in the tightening direction: it is resolved to a realpath under the mount before it becomes a reference, so a picker selection cannot escape the mount, yet the resolved path still runs the same data-root/rendezvous exclusion checks a typed reference does. So the mount confines a browsed pick without authorizing one.

### `GET /api/jobs/mounts/secrets/entries`

Lists one directory of the secrets mount. `subPath` is a repeated query parameter -- one value per path segment (`?subPath=.ssh&subPath=keys`), never a single slash-joined string -- so a `/` inside a value can never compose a traversal. Each segment is admitted by a single-segment shape rule identical to the work-input name rule except that a leading dot is allowed, so `.ssh` and other dotfiles that hold SSH key material are navigable; the separator, `.`/`..`, control-character, and `1..255` length checks are shared with the input rule and cannot drift from it. The resolved directory is confined to the mount twice -- lexically (the `resolve` + `startsWith(root + sep)` idiom) and then by `realpath`, so a symlink cannot escape the mount. No file bytes are ever read; an entry's `kind` comes from `stat` only.

The body mirrors the input listing's shape family:

- `{ "configured": false, "readable": true, "entries": [] }` when `JOB_SECRETS_DIR` is unset (the mount is unavailable).
- `{ "configured": true, "readable": true, "entries": [ { "name": "...", "kind": "dir" | "file" }, ... ] }` for a readable directory, entries sorted by name and filtered to admissible names.
- `{ "configured": true, "readable": false, "entries": [] }` when the subpath is inadmissible, escapes the mount (lexically or by realpath), or cannot be enumerated -- reported as a bare boolean, so a mis-mount or a traversal attempt reveals neither the errno nor the absolute path.

## Workdir layout

Each job gets a workdir at `<dataRoot>/<jobId>/`, created mode `0o700` (owner-only, `rwx------`), with an explicit `chmod` after `mkdir` because a restrictive umask is not guaranteed. Creation fails if the directory already exists, so a reused id cannot clobber an existing job. The data root itself is created (recursively) if missing. Inside the workdir, files are written at fixed, server-chosen names, each mode `0o600` (owner-only, `rw-------`, again `chmod`-enforced after write):

| Name | Contents |
| ---- | -------- |
| `psilink.yaml` | The composed CLI config document (exchange mode only; see [Composed CLI configuration](#composed-cli-configuration)). |
| `.psilink.key` | The key file holding the shared secret (exchange mode only), owner-only on the same discipline as the CLI's own key-file write (see [CREDENTIAL_STORAGE.md](CREDENTIAL_STORAGE.md#posix-write-discipline)). |
| `input.csv` | The client's input CSV content, written only for an inline `inputCsv` intent; a mounted `inputFile` is read in place. |
| `output.csv` | The CLI's matched-result output (written by the CLI on success). |
| `record.json` | The self-attested exchange record (written by the CLI on every run that disclosed, whether it then finished or terminated; the write is non-fatal, so it may be absent). |
| `record.keys.json` | The private verification keys paired with the record (owner-only; written alongside the record under the same non-fatal write). |
| `run.log` | The CLI's own diagnostic log, written only when the intent asked for a diagnostic run. The CLI opens it itself (`--log-file`, append, created owner-only), so the mode is its write discipline rather than this server's. |
| `receipt.json` | The dual-signed receipt, written only when the intent asked for `certificate` signing. The CLI writes it itself at the path the composed `signing.receipt_output` pins, owner-only on its own discipline. The name is pinned rather than left to the CLI's default timestamped one so the server knows the path to serve. |

The client never supplies a filename: submitted content is written to these constant names, and the CLI is pointed at them by absolute path. Keeping the names constant is what makes "a client string never becomes a file path" hold.

The long-lived signing identity does not live in a workdir. A workdir is removed with its job, while one signing identity serves every exchange and every partner and must keep matching the fingerprint a partner pinned, so it lives at `<dataRoot>/.psilink-signing-identity.json` -- in the operator's mounted working directory, where it outlives the job and is a file the operator still has on their own host. It is dot-prefixed for the reason `.psilink.key` is: it holds a private key, and the work-input listing's own admissibility rule excludes a leading dot, so it cannot turn up in the operator's input picker. A `--export-certificate` writes the public certificate beside it at `psilink-certificate.json` (not dot-prefixed: it is the artifact the operator is meant to find and hand over).

Neither channel's rendezvous lives in the workdir. A filedrop job's rendezvous is the resolved `JOB_RENDEZVOUS_DIR` mount (which defaults to `JOB_DATA_ROOT` when unset; see [Composed CLI configuration](#composed-cli-configuration)) -- or, on a split-provisioned console, that mount and `JOB_RENDEZVOUS_OUTBOUND_DIR` together -- shared across jobs and held by the single-holder latch; an sftp job's rendezvous is the authored connection's own directory. An sftp job's workdir has the same fixed-name layout, and its `psilink.yaml` holds the authored connection's block -- locator, pinned fingerprint, and `@path` credential references, never a credential value.

## Subprocess invocation

The CLI is spawned with `spawn` (not a shell, `shell: false`) and an argv array assembled only from fixed templates plus server-generated absolute paths and, for a zero-setup job, the server-side connection fields described below -- never a client string beyond the bounded values the intent schema already validated. Both invocation forms share the same post-spawn plumbing (the fd-3 event reader, the stderr tail, and terminal reconciliation); they differ only in the argv each builds.

### Exchange invocation

An exchange job drives the `exchange` subcommand against its composed config and key files:

```
<node> <binaryPath> exchange --config-file <configPath> --key-file <keyPath> --record-file <recordPath> [--sweep-exchange-files] [--log-level=debug --verbose --log-file=<logPath>] [--event-stream] <inputPath> <outputPath>
```

`--record-file` pins the self-attested record to the server-known `record.json` in the workdir (the CLI derives the keys path as `record.keys.json` alongside it), so the server can serve both from a fixed path; without it the CLI would write to a timestamped default name the server could not locate. Records are on by default, so no `--no-record` is passed.

### The per-run controls

Both invocation forms have the same two bracketed groups, emitted from the intent's `diagnosticRun` and `sweepExchangeFiles` booleans and from nothing else.

A diagnostic run emits all three log tokens together: `--log-level=debug` raises the CLI's own logging, `--verbose` adds the sub-library logging `-v` enables, and `--log-file` names `run.log` in the job's workdir. The console offers one control rather than three, so a diagnostic run is the whole set or none of it. `--log-file` is preferred over reading the child's stderr, which the driver already tails: the file gets the CLI's own append and owner-only-create semantics, and it is a whole run's log rather than a rolling tail. The consequence is that a diagnostic run's stderr tail is empty -- the log has the output instead.

The sweep emits `--sweep-exchange-files` and nothing else. Protocol-file classification and the retain-mode guard stay entirely the CLI's, so the console cannot drift from what a command-line run would delete; `--force-retain-sweep` is never emitted, and no intent field can produce it. A refusal by that guard reaches the console as the CLI's own terminal `error` event, classified `exchange`, and is reported exactly as any other terminal of that category: the alert's title and recovery come from the category, never from the message's text. What the console says about the escalation is fixed copy on the card, shown from the operator's own draft rather than from anything a run reports.

Every value-bearing token here uses the `=value` form, so a path cannot be misparsed by yargs as its own flag.

### Zero-setup invocation

A zero-setup job drives the CLI's literal `$0` (no-subcommand) form instead: there is no subcommand token, no `--config-file`, no `--key-file`, and never `--save` -- a zero-setup run infers its terms from the input file, has no shared secret, and persists nothing beyond the single job's record. The connection rides the positional URL and, on the sftp arm, `--server-*` flags, in place of the composed config's connection block:

```
<node> <binaryPath> sftp://<host>[:<port>][/<path>] [--server-username=<value>] [--server-password=<value> | --server-private-key=<value>] [--server-private-key-passphrase=<value>] [--server-keyboard-interactive] --server-host-key-fingerprint=<fp> [--retain-files] [--lockless-rendezvous] [--timestamp-in-filename] [--peer-id=<value>] [--polling-frequency=<n>ms] [--peer-timeout=<n>s] [--connection-timeout=<n>s] [--max-reconnect-attempts=<n>] [--connection-per-poll] [--identity=<value>] [--linkage-strategy=<value>] --record-file=<recordPath> [--sweep-exchange-files] [--log-level=debug --verbose --log-file=<logPath>] [--event-stream] <inputPath> <outputPath>
```

```
<node> <binaryPath> file://<rendezvousDir> [--retain-files] [--lockless-rendezvous] [--timestamp-in-filename] [--peer-id=<value>] [--polling-frequency=<n>ms] [--peer-timeout=<n>s] [--connection-timeout=<n>s] [--max-reconnect-attempts=<n>] [--identity=<value>] [--linkage-strategy=<value>] --record-file=<recordPath> [--sweep-exchange-files] [--log-level=debug --verbose --log-file=<logPath>] [--event-stream] <inputPath> <outputPath>
```

The URL and every `--server-*` flag are built server-side from the same effective resource an exchange job's connection block draws on -- the authored SFTP connection ([The authored SFTP connection](#the-authored-sftp-connection)), turned into an `sftp://` URL plus flags, or the configured rendezvous directory, turned into a `file://` URL (the filedrop channel has no host or credential, so the URL is the whole connection). A split-directory connection puts its inbound directory on the URL and its outbound one on `--outbound-path`, the mapping that flag defines; the CLI's own guard on it then holds the run to retain mode, which the operator's file-handling choice supplies. A split-provisioned filedrop console uses the same mapping: the `file://` URL names the inbound mount and `--outbound-path` the outbound one, as a plain absolute directory rather than a second URL, because the CLI copies that value straight into the connection's `outbound_path`. Every credential flag takes an `@path` reference verbatim -- the same reference the authored entry holds -- never a resolved secret, so no secret byte is ever on argv; the CLI child resolves the reference at live use. The host-key fingerprint is mandatory and always emitted: a zero-setup run has no TTY, so trust-on-first-use is impossible and the pin is the only host-key defense; a multi-fingerprint authored entry is a compose-time error instead of a silently dropped pin, since the CLI flag is single-valued. `--record-file` pins the record exactly as on the exchange invocation, so the record is written and served identically regardless of mode. `identity` and `linkageStrategy`, when the intent set them, are the bounded label and closed enum from [The zero-setup intent](#the-zero-setup-intent), forwarded unchanged. Every value-bearing flag -- including `--record-file` -- uses the single `=value` token form, never a two-token pair, so a value that begins with `-` cannot be misparsed by yargs as its own flag.

The tuning flags stand in for the composed config's `options` block, which this mode has no document to hold, and the set is exactly the fields the zero-setup arms admit (see [The zero-setup intent](#the-zero-setup-intent)). Each boolean toggle is emitted only when the intent set it `true`: they default to `false` in core and a zero-setup run loads no configuration file for a flag to override, so an explicitly-off toggle and an unset one select the same behaviour, and the negated forms would add tokens that change nothing. `--peer-id` takes the bounded single label the intent schema admitted, so it is never a path, a separator, or a flag-shaped value.

Each duration is emitted in the unit its own flag's grammar takes. `--polling-frequency` accepts a millisecond suffix, so `pollIntervalMs` is written verbatim as `<n>ms`; `--peer-timeout` and `--connection-timeout` take a second-or-coarser unit, so those two are written as `<n>s` -- exact, because the arms admit only a whole-second value for them. `--max-reconnect-attempts` takes the count, `0` included (which means connect once and do not retry, and is therefore emitted rather than treated as unset). Whether each emitted token is in its flag's grammar is settled against the built CLI's own parser rather than asserted here: a web unit suite spawns it over the argv the console builds.

### Shared spawn discipline

`spawn` is used rather than `execFile` by design: `execFile` caps stdio at three pipes and cannot pass fd 3, which the event stream requires. The child's `stdio` is `["ignore", "pipe", "pipe", "pipe"]` (fd 3 wired for the event stream), `cwd` is the workdir, and the environment is minimal -- only `PATH`, `HOME`, `LANG`, `LC_ALL`, and `TZ` are forwarded from the server process, so the child inherits no ambient secret. The job's inputs reach the child through the workdir files (or, for a mounted `inputFile`, the operator's own mount), never the environment.

A bounded tail of the child's stderr (up to 8192 UTF-16 code units, kept as a rolling tail) is retained for diagnostics. It reaches the client only inside a synthesized terminal event (see [Exit-code reconciliation](#exit-code-reconciliation)), never as a stream of its own, and it is bounded again to a display budget and escaped where it is shown.

The console's other two spawn boundaries drain the child's stderr and DISCARD it -- the captured-child probes behind the host-key and signing-identity endpoints, which are reached unauthenticated over loopback and return a value the console then acts on, so a probe's own diagnosis crosses structurally (a closed vocabulary plus a bounded, escaped excerpt) rather than as forwarded stderr. This route forwards instead because nothing it returns is derived from the tail: the tail is not a value the console acts on but the CLI's own diagnostic output, which it escapes where it writes it, shown once to the operator whose machine ran it -- redacted of private-key blocks and bounded to a display budget on the way.

## Event relay over SSE

`GET /api/jobs/:jobId/events` streams the job's events as server-sent events. Each frame is:

```
id: <n>
data: <json>

```

The `id` line holds the event's monotonic id (so a browser `EventSource` echoes it as `Last-Event-ID` on reconnect), the `data` line the JSON event, terminated by the blank line that ends a frame.

**Full-history replay.** Every job retains its complete event list in memory for its lifetime. On connect, the stream replays every buffered event with an id strictly greater than the resume offset. The offset is the `Last-Event-ID` request header when present and a non-negative integer, else the `?lastEventId=` query fallback (for a client that cannot set the header), else `0` (replay from the start). A malformed value is treated as `0` rather than rejected, so a bad reconnect replays the full history instead of failing. Because the full history is retained, a reconnect resumes losslessly.

**Keepalive.** The stream writes a keepalive frame every 15 seconds for its whole life, indifferent to real traffic -- the SSE comment `: keepalive` followed by the blank line that ends a frame; a fixed cadence needs no reset bookkeeping, and a redundant comment frame beside real events costs a few bytes that every client drops. It has no `data:` line, so it is no event: an `EventSource` ignores it and the console's own client parser drops it. An exchange is legitimately silent for minutes (a party waiting on its partner emits nothing), while a proxy or load balancer in front of the console cuts an idle response far sooner, so without the keepalive the operator's view of a waiting run would end while the run continued. The interval is a constant rather than a setting, sized well under the idle windows an intermediary defaults to; raising the deployment's idle window instead only moves the cliff and needs that deployment's cooperation.

**Stream close.** After the terminal event (a `result` or an `error`) is delivered, the stream closes. When the terminal event is already in the replay (the job finished before this connect), the stream closes immediately after replaying rather than holding an idle connection open. A client disconnect (`request.signal` abort), and a consumer cancelling the response body, each release the subscription and the keepalive timer.

**Client reconnect.** A stream can still be cut -- a proxy restart, a network fault, a tab the browser suspended -- and the browser-side client treats a body that ends before its terminal event as a drop rather than a completed run. It re-opens the stream with `Last-Event-ID`, the id of the last frame it delivered, so the replay above resumes exactly where it stopped; the run itself is untouched, since re-attaching only reads. The retries are bounded: five attempts at 250, 500, 1000, 2000, and 4000 ms, with the budget reset whenever a connection advances the stream past the id the previous one reached, so a long run survives repeated drops while a server that answers but never progresses does not loop. Two failures are not retried: a fault on the first connect, which is reported immediately since nothing has been established to resume, and a `404` at any point, which is the confirmed "the console no longer has this exchange". When the budget is spent the client raises a stream-lost terminal that says the run may still be in progress and to reload to re-attach -- not a claim that the exchange failed.

### Relay validation at the trust boundary

The CLI is a separate workspace driven as a subprocess; the server does not import its event types. It re-validates every fd-3 line independently against the v1 vocabulary -- all seven event types [CLI_EVENTS.md](CLI_EVENTS.md#event-types) defines -- requiring `v === 1` and a known `type`. Every string field is re-sanitized -- recursively, through arrays and nested objects -- through the display escaper before the event is buffered or relayed, deliberate defense in depth at the trust-boundary crossing on top of the CLI's own construction-time sanitization. For fd-3 events, sanitization precedes serialization, so the `\n` that frames an SSE line is the writer's own terminator. Manager-composed events (the preflight warnings above, and the synthesized terminal's stderr cause link below) bypass that re-sanitization by design -- their text is composed raw for the console sink's single escape -- so for them the frame's integrity rests on `JSON.stringify` alone escaping every newline class inside the serialized string. That property is held by a check rather than by this sentence: `apps/web/test/unit/jobWarningFraming.unit.test.ts` puts a directory entry whose name holds an LF, a CR, and a complete forged `data:` event on a real rendezvous mount. It then drives the preflight warning it raises through the real manager, the real SSE route, and the real browser-side client, and fails unless every physical line the stream emitted is one the writer produced and the forged text is still inside one JSON string when a seat escapes it.

**The terminal error's cause chain.** A terminal `error` event's `message` is a whole rendered cause chain rather than one value ([CLI_EVENTS.md](CLI_EVENTS.md#sanitization)), so the relay states it structurally: beside the `message` field it re-sanitizes as any other value, the relayed event holds `messageChain`, derived by splitting the child's raw `message` text on the renderer's own `\ncaused by: ` framing. That derivation is unconditional and always the relay's own, never a value a child supplies. The field pass drops a key of that name off any event it validates, whatever the event's type, and an `error` event is then assigned the split of its rendered `message`, or an empty chain when the event has no string `message` to split, which is where the seat reads the flat field instead. So a child that puts a field of that name on the event cannot substitute its own chain for the derived one. Each link the split produces is escaped at the composed-message cap the renderer itself uses (1024 output characters, and as many as 1038 for a link the cap cut, since the 14-character truncation marker is appended on top of it). The last link of a chain past the depth bound holds the 26-character elision marker on top of that, at as many as 1065. The link count is held to the renderer's own depth bound (`MAX_ERROR_CAUSE_DEPTH`), a longer chain marked as elided rather than shortened in silence, and a chain the child's own renderer already cut arriving with that marker keeps it, and the marker is unauthenticated text the child can forge. What a forged one buys stays inside the presentational bound stated below -- whole-escaped, so no relayed field holds an unescaped control character and the framing newline is re-introduced only where the chain is rendered. Those guarantees -- the field always being the relay's own derivation, the per-link escaping, the per-link cap, and the depth-bound count -- hold on every path, a subverted CLI child's included, so the volume and the byte content a hostile child can put in front of the operator are bounded exactly as a well-behaved child's are. What they do not authenticate is where a boundary falls inside the derived chain. The split looks for the same `\ncaused by: ` text the renderer's own escape-then-join emits, and only for a well-behaved child does that text mark a real cause link -- a subverted child can spell the same framing straight into its raw `message` and thereby present one message as several links at the seat. The escalation available to it is presentational only: extra line breaks inside a message that is still capped and escaped exactly as above, never a wider budget, an unescaped byte, or a substituted chain. The console seat rebuilds the chain from the links and renders them on their own lines, a link with no text of its own rendered as `[no message]` so the rebuilt chain keeps the length the relay delivered, which is what delivers a terminal error's recovery step. Charged to the per-value cap instead, the chain is cut wherever 256 characters fall, and on a refusal that partitions by chooser that is inside the partner-chosen fragment on its first link.

That depth bound governs the chain field and nothing else. Every other field is escaped per value -- recursively, each string of an array or nested object at the per-value cap -- and has no entry-count bound of its own, so an array field arrives at whatever length the child sent it, escaped entry by entry. What bounds a field the relay does not derive is the line the child wrote -- the fd-3 reader discards a partial line past 1,048,576 UTF-16 code units -- not this pass.

Degradation is fail-safe, never a crash:

- A non-JSON line, or one outside the known schema, is reported as a synthesized `warning` event with `degraded: true` and dropped -- the relay continues.
- An oversized fd-3 line (the reader buffers up to 1,048,576 UTF-16 code units before discarding the partial line) is reported as a degradation warning and the partial buffer discarded.
- fd 3 being unavailable, or a read error on it, is reported as a degradation warning.

**Buffer cap.** The event buffer is capped at 10,000 entries (a runaway safety check; a real CLI stream is dozens of lines). On overflow the job is failed rather than dropping events silently: a synthesized `error` terminal is appended, the child is `SIGKILL`ed, and status becomes `failed`, so a supervisor never observes a truncated history.

## Exit-code reconciliation

The child's exit is classified from the exit code and signal, per the CLI's terminal contract ([CLI_EVENTS.md](CLI_EVENTS.md#terminal-event-guarantees)): exit `0` is `succeeded`; an interrupt -- exit `130` or `143`, or death to `SIGINT`/`SIGTERM` -- is `cancelled`; exit `73` is `completedWithPersistenceLoss`; any other exit or signal is `failed`, with the exit code recorded. An interrupt legitimately produces no terminal fd-3 event, so a `cancelled` job's stream is not a broken one.

`completedWithPersistenceLoss` is the CLI's persistence-loss code ([CLI_EVENTS.md](CLI_EVENTS.md#persistence-loss)): the exchange completed and a local write did not. It is a terminal outcome of its own rather than a `failed` one because the two demand opposite operator responses -- a failed run is re-run, and this one must not be, since re-running re-sends this party's data for an exchange that already happened. The classifier reads only the exit code, so it does not distinguish the two shapes the code covers; the terminal event does, and it is what sets `status` (see [The `GET /api/jobs/:jobId` status body](#the-get-apijobsjobid-status-body)). The value `73` is mirrored from the CLI rather than imported -- the CLI is a separate workspace this server drives as a subprocess -- so nothing in the module graph holds the pair together, and each side's own suite pins only its own copy. `scripts/persistence-loss-exit-code.test.mjs` (run by `npm run test:scripts`, a CI static check) is what does: it reads both declarations out of source and fails when they diverge, reporting a declaration shape it cannot read rather than passing it over. What it decides is that the two agree, not that either is the right value; that is each side's own suite, against the exit-code contract in [CLI.md](../CLI.md#exit-codes).

**Close-not-exit ordering.** The classifier fires on the child's `close` event, not `exit`. `close` fires only after every stdio stream has drained, so the CLI's own terminal fd-3 event is always parsed before the exit is classified. On `exit` the terminal line can still sit in the pipe buffer, and the manager would synthesize a misclassified terminal in its place. A spawn or process `error` classifies as `failed` (exit code recorded as 1) with a sanitized diagnostic, so a terminal state is always reached.

**Synthesized terminal events.** Whether the CLI emitted its own terminal event is the manager's concern. If it did, that stands. If it did not, the manager synthesizes one matching the exit so the supervisor is always guaranteed a terminal event:

- `cancelled`: a `cancelled`-flavored `error` terminal (`category: "exchange"`, `cancelled: true`, message naming SIGINT or SIGTERM).
- `succeeded` with no terminal event: a `result` terminal (`resultWritten: true`).
- `completedWithPersistenceLoss` with no terminal event: an `error` terminal with `category: "output"`, the local-output-stage category, whose message states that a local write was lost and that the console cannot say which one. The category is critical rather than cosmetic: it is the one a console seat renders with no way to run the exchange again, while the `exchange` category below is retryable and would invite the re-run this exit code exists to prevent.
- any other exit with no terminal event: a `failed` terminal (`category: "exchange"`) noting the stream broke and, when known, the exit code.

The two synthesized terminals that stand in for a diagnosis the run never emitted -- the persistence-loss one and the stream-broke one -- name what the child wrote on stderr when it wrote any, so the cause the CLI printed crosses to the client even though fd 3 stayed empty. It rides a labelled cause link of its own on `messageChain` rather than being composed into the message, so the flat `message` field stays this console's own text at every width of tail: bytes composed into that sentence can spell whatever delimiter closes them and read on as console copy, which on the persistence-loss terminal is a do-not-repeat instruction. The link holds the END of the retained window, redacted of private-key blocks and then fitted by rendered cost to the per-value display budget (256 output characters, the truncation marker in FRONT of what is kept and paid for out of that budget), because a run writes its diagnosis last and a cut taken from the front deletes exactly the final error line. A private-key block whose BEGIN marker fell outside the retained window is not recognized, and its bytes reach the operator's alert unredacted. It crosses raw and the console seat rendering the chain escapes each link once, which is the single escape the tail is due ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#display-sanitization-escape-format)); a tail spelling the renderer's own `\ncaused by: ` framing therefore reads there as further links of the chain, escaped and capped exactly as the first is. Which seats show it follows the category: the persistence-loss alert renders that chain, while the retryable stream-broke alert shows fixed copy and keeps the chain for the diagnostics console. The interrupt terminal names none: the operator asked for that exit, so no diagnosis is missing. A run that emitted its own terminal event is synthesized nothing, so the tail is never a second copy of a diagnosis the CLI already sent. The escape count and the end-of-window cut are held end to end, from the child's stderr to the string a seat renders, by `apps/web/test/unit/jobs/stderrTailBudget.test.ts`.

A synthesized `result` terminal sets `status` to `succeeded` and a synthesized `error` to `failed` -- except the interrupt case above, whose `status` is already `cancelled` before synthesis and keeps it. A persistence loss with no terminal event is therefore `failed`: the console never saw an artifact announced, so it promises none, which is the rule every broken stream takes regardless of exit code. The outcome still states the do-not-repeat signal, and the synthesized message points the operator at the workdir.

## Cancellation escalation

`POST /api/jobs/:jobId/cancel` requests cancellation and returns `202` (idempotent -- `202` even for an already-terminal job). It delivers a signal escalation to the running child:

1. `SIGINT` immediately.
2. `SIGTERM` after a 5000 ms grace, if the child is still running.
3. `SIGKILL` after a further 5000 ms grace, if still running.

The escalation timers are cleared when the child exits, so a child that stops on `SIGINT` is never over-signaled; the timers are `unref`ed so they never hold the process open. The job's final `cancelled`/`failed` state reflects which signal took effect (a `SIGINT`-ignoring child that only stops on `SIGTERM` records exit `143`).

| `JOB_RENDEZVOUS_DIR` | The mounted synced-folder rendezvous directory a filedrop exchange reads and writes. Empty or unset -> falls back to `JOB_DATA_ROOT`, so one mount runs the filedrop transport; the fallback provisions the shared mount of an unsplit console only, and never the inbound leg of a split (see `JOB_RENDEZVOUS_OUTBOUND_DIR`). Non-empty -> resolved to an absolute path. At filedrop job start the manager emits a non-fatal warning when this directory overlaps (equals, contains, or is contained by) the work-input directory or the data root -- as it does in the single-folder layout, where a partner's sync writes would reach the operator's key, input, or results -- but the operator's own directory layout is theirs to choose, so the exchange still runs. That overlap is decided over each path as configured (lexically resolved) and as its `realpath`, in every pairing of the two forms, so a mount symlinked onto the data root raises the same notice a lexically nested one does: what a partner's sync writes reach is the directory at the far end of the link. It stays a warning either way -- the resolution decides which notice to raise, never whether the exchange runs. A directory on either side of that comparison whose own real path cannot be read (as opposed to one that does not exist yet, which is resolved through its nearest existing ancestor exactly as a split pair's legs are) narrows the comparison back to the configured paths and adds one further notice saying so, naming the side that could not be resolved and the read access to restore, so a narrowed check is never silent about which side narrowed it: the mount raises that notice for itself, and the data root and the work-input directory each raise their own, naming the leg they were compared with (they are compared once per leg, and the notice would otherwise reach a split console's operator twice over with nothing to tell the two apart). It stays a warning on every side, exactly as the overlap itself does. The mount that does not exist yet raises its own notice alone. It emits two further non-fatal warnings, in order, when the directory is not empty: a lead with the recovery -- every filedrop job rendezvouses out of this one mount, so a completed retain-mode run leaves a transcript the next run's entry guard refuses, with no crash involved; the recovery is the console's own sweep control (`Clear leftover exchange files before starting`, named in the notice by as much of that label as fits beside the mount path) rather than a host-side deletion, and the operator's own input and results are not what the guard refuses over -- and then a listing of what the mount holds (sorted, at most 10 named and the rest counted). Which of two recoveries the lead states is decided by this launch's own `sweepExchangeFiles` intent, the same value that reaches the child as `--sweep-exchange-files`: a launch without it is told to turn the control on and re-run, and a launch already with it is told that the control is on, that the sweep runs first, and that the operator's own input and results are not what it sweeps -- the control's state and what the sweep spares, never a prediction of its outcome, since the CLI's sweep refuses a retain-mode transcript and `--force-retain-sweep` is unrepresentable in a job intent. The lead and the listing are composed raw, because a manager-composed event bypasses the [relay's re-sanitization](#relay-validation-at-the-trust-boundary) (which covers the CLI's fd-3 lines) and the console warning sink escapes the message it renders exactly once through `sanitizeForDisplay`, so escaping a partner-chosen entry name here as well would reach the operator doubled. That sink caps what it renders at the whole-warning budget (`WARNING_MESSAGE_MAX_DISPLAY_LENGTH`, 4096 characters), but every notice this preflight raises -- the two above and the missing, non-directory, non-writable, unlistable, overlap, and unresolved-real-path notices alike -- is fitted where it is composed to the tighter per-value `DEFAULT_MAX_DISPLAY_LENGTH`, measured as rendered cost, so none can truncate at either boundary. That fitting is why the not-empty case is two messages rather than one, why an entry name that does not fit whole is counted rather than clipped (a clipped name reads like a whole name the operator could go and delete), and why a rendezvous path too long to fit beside a notice's sentence is left out of it whole -- the path is the operator's own server-side configuration for the one mount, while the sentence around it is what they cannot reconstruct. The warnings do not sort protocol files from foreign ones -- that grammar belongs to the exchange, and the operator's own input and results are tolerated by the guard -- and they do not gate the launch; an inadmissible directory still fails with the exchange's own refusal. A directory that cannot be listed warns that it could not be checked rather than reading as empty. The listing is one synchronous `readdirSync` on the job-create request path, and the partner influences its cost by syncing files in; the bound on that read is the single-owner console model (one operator, one exchange at a time, on their own machine) rather than any cap on the entry count. Read trimmed; set only server-side, never derived from a request. |
| `JOB_RENDEZVOUS_OUTBOUND_DIR` | The mounted outbound (self-written) rendezvous directory of a split filedrop rendezvous, the companion to `JOB_RENDEZVOUS_DIR`'s inbound leg. Non-empty requires a non-empty `JOB_RENDEZVOUS_DIR` beside it: a split takes each leg from its own variable, and an inbound leg resolved through the `JOB_DATA_ROOT` fallback is reported as the `problem` below rather than provisioned -- the data root is the API's own feature gate, so it resolves on every console that runs at all, and accepting it here would sync the directory holding every job workdir's config, key, input, and results to the partner as the inbound folder. Non-empty with both -> resolved to an absolute path, and every filedrop exchange the console composes then holds `inbound_path`/`outbound_path` (see [Composed CLI configuration](#composed-cli-configuration)) and `--outbound-path` on a zero-setup argv (see [Subprocess invocation](#subprocess-invocation)). At filedrop job start the manager preflights each leg independently, with every notice naming which of the two it is about ("the inbound rendezvous directory", "the outbound rendezvous directory"); on a single-mount console the same notices keep the unqualified wording. Both legs join every containment list the single mount is on -- the pasted-credential scratch assertion and the credential-`@path` warning -- since either is a folder the partner syncs. A pair that cannot run an exchange (two legs that are one directory or nested, two legs whose locators resolve alike, a leg with no locator at all, or an outbound leg with no inbound one of its own) is reported through `GET /api/jobs/rendezvous` as `configured: false` with a `problem`, and `POST /api/jobs` refuses every filedrop create while it stands; SFTP on the same console is unaffected, and the boot logs the same sentence non-fatally rather than refusing to start. The same-directory-or-nested half of that is decided over each leg's configured path and its `realpath`, so a symlinked leg meets the refusal too (see [The filedrop rendezvous report](#the-filedrop-rendezvous-report)); a leg whose real path cannot be read narrows the comparison to the configured paths and adds a second non-fatal boot warning naming the variables that could not be resolved, never a refusal of its own. ### Startup and reachability

Startup constructs the manager exactly when the [feature gate](#feature-gate) is satisfied; otherwise no manager is constructed and no child is ever spawned. Because the work-input and rendezvous directories both fall back to `JOB_DATA_ROOT`, that one variable (on a console build) also lights up the input listing and the filedrop transport, so a single mount runs a full console. When `JOB_DATA_ROOT` is set but the profile is not `console`, the server logs one non-fatal startup warning that the data root is ignored and boots with the job API dark rather than refusing to start. The server does not inspect its own bind interface -- there is no loopback bind check and no bind-derived startup refusal. Reaching the unauthenticated API only from the operator's own machine is a deployment concern: the console container publishes its port to the host loopback (`-p 127.0.0.1:PORT:PORT`), so exposure is governed by that publish binding and the host firewall rather than by an app-level bind check (see [CONSOLE.md](../CONSOLE.md)). The profile gate is the app-level safety check that keeps a hosted build from serving the API even when the publish binding or a fronting proxy would reach it.

When the job API is enabled, startup also prepares the pasted-credential scratch directory: the containment assertion, the owner-only creation, and the sweep specified under [Materializing a pasted credential](#materializing-a-pasted-credential) run here. It is a no-op when the API is disabled (no manager is constructed, so no paste can be authored).

## Job lifetime and orphan handling

The exchange lives in server memory only and is never persisted:

- **One exchange in one slot.** The manager holds at most one exchange at a time. A second create -- of either channel -- is refused with a `409` naming the occupying exchange's id (`{ "id" }`, so the browser re-attaches to the running exchange rather than dead-ending) while the slot is occupied. The slot is claimed before any workdir exists, and frees only when both hold: the exchange was explicitly `DELETE`d, and the child's exit was observed (or no child was ever spawned). Keying the release on the child's confirmed exit -- not merely on the terminal event, which the buffer-overflow path emits while a `SIGKILL`ed child may still be running -- is what keeps a successor exchange from rendezvousing with a still-dying child over the authored connection or rendezvous directory. A settled but undeleted exchange keeps the slot: the reject-until-`DELETE` rule means a create never silently destroys the previous exchange's undownloaded result.
- **Restart forgets the exchange.** The in-memory slot -- running state, the terminal reconciliation, and the full event history -- does not survive a server restart, and no in-flight exchange is resumed or persisted (a restart cancels it rather than persisting another party's material). The workdir remains on disk; it is not re-discovered, listed, or re-surfaced, so a restarted server serves `404` for the forgotten id. The files stay until removed by an explicit `DELETE` of that id or by hand.
- **DELETE removes the disk.** `DELETE /api/jobs/:jobId` is the only operation that removes the workdir. For the active exchange it `SIGKILL`s a still-running child first so the delete leaves no orphan, marks the exchange deleted (the surface `404`s from that point), and `rm -rf`s the workdir (idempotent); the slot stays occupied until the child's exit is observed. A disk-only arm removes a workdir named by a valid v4 UUID but orphaned by a restart: it reads no artifacts and serves nothing, applies the same containment and real-directory (`lstat`, so a symlinked leaf is refused not followed) guards the live routes apply, and refuses the active slot's own id. Nothing is auto-deleted.
- **Shutdown signals the child.** On server shutdown (`SIGINT`/`SIGTERM`), the active exchange's running child is sent `SIGTERM` so no orphaned CLI outlives the server. The shutdown hook is registered before the graceful-shutdown handler (signal listeners run in registration order), so the child is signaled before any handler that may end the process. It is a no-op when the API was never enabled or no exchange is active.
