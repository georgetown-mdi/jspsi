# Exchange record format

This document specifies the self-attested exchange record: the local audit artifact each party produces once an exchange has disclosed. It covers the record and verification-keys file shapes, the format version and reader-rejects-unknown rule, the point at which a record becomes owed and what it states about the run that produced it, the commitment scheme and the agreed-terms hash, the readable governance metadata, the result-size and per-direction disclosure framing, the count-only (`psi-c`) rows, the value that pairs a signed receipt to one run of an exchange, and the record's privacy properties. It does not cover the PSI protocol that produces the exchange (see [PROTOCOL.md](PROTOCOL.md)), the exchange-agreement format that supplies the record's governance fields (see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md)), or the canonical byte encoding the commitments and the agreed-terms hash are computed over (see [CANONICAL_ENCODING.md](CANONICAL_ENCODING.md)). The separate certificate-backed [signed receipt](#signed-receipt) reuses this record's commitment scheme and on-disk format, so the commitment-scheme and file-shape sections below are written to stand on their own. Intended readers are security auditors, external implementors, compliance reviewers, and developers.

Each party produces a self-attested record of what it disclosed, on every exchange path and on every run that disclosed, whether or not that run finished (see [When a record is owed](#when-a-record-is-owed)). The record is designed to stand on its own as a disclosure-log entry: an operator can use it to populate a HIPAA accounting of disclosures or a FERPA disclosure record without separately retaining and re-matching the original linkage-terms config. It is **not** evidence against the partner, and -- being built from data both sides already hold -- it needs no private key and adds no protocol round-trip. It is deliberately unsigned: a session-derived MAC is not non-repudiation, so an unsigned record is an honest, local audit artifact rather than one that overstates what it proves. Non-repudiation is the separate signed receipt's job -- a mutually-verifiable dual-signed artifact, its own file, produced alongside the record on the CLI's authenticated exchanges when a signing identity is configured.

## When a record is owed

A record is owed from the moment this party's **payload exchange completes**. That is the point at which the disclosure the record attests has provably occurred: the linkage keys have been exchanged and matched, the payload columns have been sent and received, and nothing after it can undo any of that. The record is therefore produced on every path out of the exchange from that point on -- the run returning normally, and the run terminating in either step that follows: the received-payload check that holds the partner's transmitted columns to the set this party consented to receive, and then the [signed-receipt step](PROTOCOL.md#the-signed-receipt-step).

A failure BEFORE that point produces no record, and owes none. The point is the payload exchange's RETURN, not its first frame: the initiator sends its payload before it receives the partner's, so a failure inside the exchange can leave this party's payload already across the wire and still leave no record behind. That residual window is a stated limit of where the durability point sits rather than a claim that nothing flowed -- a run cut off inside the exchange holds no received payload, one of the three values the record commits to -- and the failure itself is reported through the run's error and the [machine-readable event stream](CLI_EVENTS.md). The record's own build is the one exception in the other direction -- it is a secondary artifact, so a build that fails leaves the run's result untouched and reports that no record could be produced.

The asymmetry runs the other way on the responder leg: its payload send is the exchange's terminal frame, fire-and-forget on a buffering transport (`packages/core/src/payloadExchange.ts`), so the return this party observes confirms only its own hand-off of that send, not the partner's receipt of it -- the record attests this party's own disclosure rather than confirmed delivery, which is the conservative direction for an accounting: it can over-report a disclosure whose last frame never arrived, never omit one that did.

**Every record states which of the two it is**, in a mandatory `outcome`:

| Value | What it states |
| --- | --- |
| `completed` | The run finished. A run that signed exchanged its receipt; a run with no signing identity had none to exchange, and says so by carrying no [`receiptBinder`](#pairing-a-receipt-to-one-run). |
| `receipt-swap-terminated` | The disclosure occurred and the run then terminated without this party holding a receipt for it. |

Five properties fix how the row is read.

**It is stated, never inferred from silence.** A completed run's record asserts that it completed rather than leaving a reader to conclude it from an absent marker, on the same rule the [count-only](#count-only-psi-c-records) payload commitments follow: a load-bearing fact is recorded explicitly so a reader never has to guess whether a field is absent because nothing happened or because the writer left it out. It is also why the format version moves with the field -- an earlier record could only have been written for a run that finished, so reading its silence either way states something its writer never did.

**A terminated record attests the disclosure in full.** It is not a partial or provisional artifact: it carries the same commitments, the same governance metadata, the same exposed-record count, and the same result size under the same entitlement gate as a completed run's. What it does not carry is a receipt, because none was exchanged.

What it carries and what can later be opened are separate questions, and the second has a limit worth stating. A terminated run returns no result, so no result file is written -- and all three of the record's commitments re-supply from one ([No data snapshot in the keys](#no-data-snapshot-in-the-keys-data-minimization)): the association table from the result's pairing columns, and each payload from the result's rows on its own side of that pairing. So a terminated record's commitments cannot be reproduced and opened, and the keys file beside it has nothing to open. They still bind what this party disclosed, and the record stays readable, citeable, and pairable to a receipt the partner holds; what does not follow is that a holder can demonstrate that binding by opening one. What a terminated record is for is the accounting entry, not the opening.

**A terminated record keeps the binder its run derived.** The binder is derived from the session key before the swap runs, so it is a true value for the run whatever the swap then does, and by the swap's [wire ordering](PROTOCOL.md#the-signed-receipt-step) the PARTNER may hold a completed receipt bearing it. A record that dropped the binder would leave that genuine receipt reading as [`unpaired`](#pairing-a-receipt-to-one-run) against it. The binder's presence rule is therefore "the run derived one", not "this party holds a receipt": a run that terminated before it derived one carries no `receiptBinder`, exactly as an unsigned run's record does, and what says this party holds no receipt is the `outcome` beside it.

**It is this party's own statement, like the rest of the record.** The two parties of one run can legitimately record different outcomes -- the swap's wire ordering lets one side complete while the other terminates -- and nothing compares them. A reader must not take one party's `outcome` for the other's.

**It states that the run terminated after disclosing, not why.** One value covers every way the post-disclosure region can end: a received payload refused against the set this party consented to receive, a fingerprint-pin or signature refusal in the swap (where who received the disclosure is in doubt), and an ordinary transport drop (where the partner is presumed to be the one agreed with). A compliance reader cannot tell them apart from the record alone, and the record does not claim to: the cause is in the operator's own run log and [machine-readable event stream](CLI_EVENTS.md), which are where an incident is reconstructed. What the field is for is the accounting-of-disclosures question -- did a disclosure occur, and did this party come away with a receipt for it -- which it answers on its own.

Where a terminated record is written is not distinguished: it takes the same destination, filename, and owner-only permissions a completed run's takes ([Record and verification-keys files](#record-and-verification-keys-files)). The distinction belongs in the document, which travels with it wherever it is copied, rather than in a filename, which does not.

## Record fields

The record captures: a format `version` (`psilink-exchange-record/v6`, a single recognized literal which a reader rejects rather than migrates if unrecognized -- it moves with the field set, so a record written before the `receiptBinder` below, before the governance block's [rule-set citation](#the-rule-set-citation) or the writer's [verdict](#the-writing-partys-verdict) on it, before either `identity` became omittable, or before the `outcome` below, is refused on the discriminant rather than read as one whose absent field means something else; pre-release, no migration is offered); the run's [`outcome`](#when-a-record-is-owed); the local timestamp (a UTC datetime ending in `Z`, in the form fixed under **The timestamp's form** below; a timestamp carrying a numeric offset is rejected); a hash, over the canonical encoding, of the agreed exchange terms (both parties' linkage terms in a fixed, canonical-sorted order, so both parties and an independent third party derive the same hash); both parties' self-asserted `identity` strings, each present only where that party supplied one (see **The parties' identities** below); the number of records this party contributed to the exchange (`recordsExposed`) -- its own input row count, recorded on every record as a per-direction statement of what it put in; the result size, but only in the both-output case; an optional self-facing retention/disposition pointer recording where this party filed its copy of the result and under what retention schedule (see below); a per-exchange binding nonce (CSPRNG-generated, at least 128 bits) so two runs with identical terms still produce distinct records; and, on an exchange that derived a [signed receipt](#signed-receipt)'s binder, that `receiptBinder`, repeated verbatim so the two artifacts pair to one run (see [Pairing a receipt to one run](#pairing-a-receipt-to-one-run)). The binding nonce is the unsigned record's own per-exchange value and is distinct from both the per-commitment salts below and the receipt binder: it is generated locally, so the two parties' records for one run carry different nonces, and nothing outside the record it sits in is derived from it or compared against it. The `receiptBinder` is the opposite on both counts -- both parties derive the identical value from the run's session key, and comparing it is the whole point. Do not conflate the three.

**The parties' identities.** `localIdentity` and `partnerIdentity` each carry that party's self-asserted [`linkage_terms.identity`](../EXCHANGE_REFERENCE.md#linkage_termsidentity), which is optional. A party that supplied no name sends terms carrying none, and this record OMITS its field rather than writing an empty string or a stand-in label: psilink names no party the operator did not name. The distinction is structural in the record DOCUMENT -- the member is present or it is not -- so a reader of the file tells "nobody gave a name" from "a name was given" by the member's presence, and never by its value. It does not survive rendering, and no surface makes it: `identity` is unauthenticated free text a party chooses for itself, so a party that names itself the absence marker's own text displays exactly as a party that named nobody. What a surface shows is a self-asserted label in either case. The two fields are independent -- one party may be named and the other not -- and the format version moves with the omission for the reason every other omittable field moves it: an earlier record could not have been written without both, so its silence would have meant a writer that dropped the field. A surface rendering the record shows an explicit absence marker where a field is absent rather than a blank (`(no name given)` in this implementation's own surfaces). The agreed-terms hash is taken over the terms as sent, so an absent `identity` is absent from the hashed document too -- not hashed as an empty string.

**The timestamp's form.** A written `createdAt` is what the Date Time String Format of [ECMA-262](https://tc39.es/ecma262/) fixes -- `YYYY-MM-DDTHH:mm:ss.sssZ`, the output of `Date.prototype.toISOString`. A read `createdAt` is looser: the validator requires the trailing `Z` and rejects every numeric offset, `+00:00` included, but accepts any sub-second precision, so `2026-08-10T12:00:00Z` and `2026-08-10T12:00:00.000Z` are both valid records for one instant. What the UTC-only rule buys is therefore one reading of an instant rather than one string for it, and nothing cross-party rests on the string: the timestamp is each party's own, and it enters neither the agreed-terms hash, nor a commitment, nor the [receipt content](#receipt-content) both parties sign. This document states the form rather than resting on the name ISO 8601, a publication the project does not hold and so cannot cite a clause of.

**The free-text fields a reader accepts.** The two `identity` strings, the agreement `purpose`, each payload column `description`, and `retentionDisposition` are bounded in length by the reader but are not held to the [terms document's control-character rule](../EXCHANGE_REFERENCE.md#linkage-terms) -- the record is a frozen log, so its reader stays permissive toward what a possibly-different-version writer recorded -- and how such a value renders is governed by display escaping at the surface that shows it, not by this format. `retentionDisposition` is the one of them written from this party's own local note rather than from either side's terms, and its authoring rule is drawn differently for that: it admits tab, LF, and CR, the whitespace a multi-line note holds (see [the exchange intent](SERVER_JOB_API.md#the-exchange-intent)).

## Result size and per-direction disclosure

The two disclosure figures -- `recordsExposed` and the result size -- are gated differently, and the difference is deliberate. `recordsExposed` is the count of records this party contributed to the exchange -- its input row count, counting every contributed record rather than only those that resolve to a usable linkage key, so it is an honest upper bound on what the party exposed rather than a derived match figure; it is known from the party's own input alone, so it does not depend on the result or on the partner, and it is recorded for every party regardless of role. The result size (the intersection cardinality) is recorded only when both parties' agreed terms have them both receive output, so it is stored only when both sides are entitled to the result, and omitted when only one party does. The gate is the terms agreement (entitlement), not what a party happens to learn during the exchange: in a single-output exchange the helper that does not receive output can still observe its match count during the [clean cascade](PROTOCOL.md#psi), but the record deliberately does not surface it. Privacy here is enforced by what the tool writes down, not by what is theoretically discoverable; the helper's own outbound disclosure is carried by `recordsExposed` instead. Framing the helper's figure as "records I exposed" rather than "the result size" is also what keeps the record meaningful under a future matching algorithm that discloses neither the result size nor the partner's set size -- the figure comes only from the party's own input, which any such algorithm still leaves it knowing.

Reading the disclosure direction off a record: a PSI exchange discloses the membership of matched records mutually -- each party reveals its matched membership to the other to make the match -- so direction is not a flag but a reading of the fields together. `recordsExposed` is the magnitude of what this party put in (its outbound exposure); the `algorithm` says what kind of disclosure occurred (`psi` revealed matched identifiers, `psi-c` only a count); `payloadSent` and `payloadReceived` give the payload categories per direction; and the presence of the association-table commitment (below) marks whether this party itself received the matched pairing. So "what this party disclosed" reads off `algorithm` + `recordsExposed` + `payloadSent`, and "what it received" off `payloadReceived` and the association-table commitment -- without consulting the output configuration, which the record does not carry.

The `algorithm` field is bound to what the run actually did, not to an unvalidated terms value. Core admits an algorithm only where a run path honors it (`assertAlgorithmImplemented` in `packages/core/src/exchange.ts`, at both the local prepare step and the run boundary), so an algorithm the exchange cannot conduct is refused before any identifier is revealed rather than written into a record. A `psi-c` (count-only) record therefore attests a run that disclosed a count and no identifier, and the same two points refuse a count-only document outside the shape a count-only run admits, so the record can never attest a run the exchange did not conduct. This is the run-side half of the guarantee; a pure record-side clamp is rejected because it would keep the record honest while silently ignoring an operator's stated intent to disclose only a count. The rows a count-only record carries are fixed under [Count-only (`psi-c`) records](#count-only-psi-c-records) below.

### Result size under a deduplicating cardinality

Under `one-to-one` the three figures a result could be counted in -- the association table's pairs, this party's matched records, and the partner's matched records -- are one number, so the field's meaning needs no statement. A [deduplicating cardinality](PROTOCOL.md#deduplicating-cardinalities-many-to-x-matching) separates them: several of the declaring party's records link to one of its partner's, so that party has more matched records than its partner does, and both figures sit under a single pair count. Where both parties declare it a fourth figure appears, the count of [entity clusters](PROTOCOL.md#the-many-to-many-entity-closure) the table resolves into, and the reading is unmoved: the pair count is the sum of `m * n` over the clusters, which is at least either party's matched-record count, which is in turn at least the cluster count.

The recorded result size is the **pair count** -- the number of entries in the association table, a repeated row index on one side of a pair still being a pair. Two properties decide it. It is the figure both parties derive identically from the single table the exchange produced, so the two records of one exchange state the same size, as they do under `one-to-one`; a per-party matched-record count would put two different result sizes on one exchange and leave a reader of either unable to say which was meant. And it is the count of disclosed linkages, which is what the field is for: each entry sets one record of this party against one record of the partner's, and a disclosure accounting is over those linkages rather than over the entities behind them.

No second count is recorded beside it. Each holder can derive its own matched-record count from its retained result, so a field carrying it would disclose nothing new to that holder while adding a figure to the artifact it hands an auditor; a reader that needs the entity-level figure reads the result file. The entitlement gate above is unchanged: the pair count is recorded only when both parties' agreed terms have them both receive output. The reasoning behind the choice is in [deduplicate-matching-semantics.md](../notes/deduplicate-matching-semantics.md).

### What verification binds about the result size

No commitment covers the result size. The figure sits in the record in cleartext under the gate above, so a commitment beside it would bind the same integer without hiding anything, and the record's [privacy properties](#privacy-properties) already state that a reader learns the size when it is present. What stands behind the figure instead is the **association-table commitment**, because the field is a count *of that table*: its entries are the pairs the size counts, so a table re-supplied and opened against its commitment carries the figure's correct value.

Verification therefore **recounts** the size rather than opening anything for it. Where the record carries a result size and its association table opened, the opened table's pair count is compared against the cleartext field; a disagreement is a definite failure, reported against the result size and distinct from a commitment mismatch. The two differ in what they mean, not only in where they are reported. A commitment mismatch is ambiguous: the record was altered, or the re-supplied file does not belong to this exchange, and nothing in the artifacts tells the two apart. A result-size mismatch is not: a file that did not belong to this exchange would have failed the table's own commitment first, so an opened table carrying a different number of pairs means the record's cleartext figure does not state the size of the pairing the record itself commits to.

Where no opened pairing stands behind the figure it is reported as **unchecked**, never verified, on the fail-safe rule the commitment statuses follow. Five states reach that: the result was not re-supplied, the keys carry no salt for the table, the re-supplied table did not reproduce its commitment, the re-supplied table opened but is not shaped as a pairing (anything other than two equal-length halves of non-negative integer row indices carries no pair count, so there is nothing to recount -- a state a record built by an exchange never reaches, since the table it commits to is that shape), or the record carries no association-table commitment at all -- the state every [count-only record](#count-only-psi-c-records) is in, since a count-only exchange commits to no such table. A record carrying no result size is neither checked nor at fault: the field's absence is what the entitlement gate produces whenever only one party receives output.

## Count-only (`psi-c`) records

A count-only exchange ([PROTOCOL.md](PROTOCOL.md#psi-c)) writes a record of the same shape as a `psi` exchange. Four of its rows are fixed by what a count-only run does and does not produce.

**`algorithm` is `psi-c`.** The record then attests that this exchange disclosed a count and no identifier -- the disclosure an auditor reads off the field. As under `psi`, the value is bound to what the run did rather than to the terms value alone.

**The result size carries the count, under the unchanged entitlement gate.** The count is the run's whole result, and it is recorded in the result-size field under exactly the gate [Result size and per-direction disclosure](#result-size-and-per-direction-disclosure) sets: present when both parties' agreed terms have them both receive output, omitted when only one does. For psi-c that gate coincides with the protocol's count-report leg, the both-entitled case being precisely the case in which both parties hold the count. In a one-sided run the receiver therefore holds a count its own record does not carry: the conservative rule `psi` applies to the result size is carried over unchanged, not relaxed because psi-c's whole result happens to be one integer.

The cleartext field is the count's whole attestation in the record. No commitment is added for it: the figure is already recorded in cleartext under that gate, so a commitment beside it would bind the same integer without hiding anything, and the record's [privacy properties](#privacy-properties) already state that a reader of the record learns the result size when it is present. Under `psi` the figure is still checkable -- verification [recounts it](#what-verification-binds-about-the-result-size) from the association table the record commits to -- but a count-only run produces no such table, so that recount has nothing to run against here and the count reports as unchecked. That is the honest reading of a figure no retained artifact reproduces, not a gap in the format.

**No association-table commitment, and its absence is normative.** A count-only run produces no pairing, so neither party holds one to commit to, whatever its entitlement -- a psi-c record carries no association-table commitment on either side. The absence is load-bearing rather than incidental: the presence of that commitment is the record's marker that this party received the matched pairing (see [Result size and per-direction disclosure](#result-size-and-per-direction-disclosure)), so a psi-c record carrying one would assert a disclosure the run did not make. This is the one row where psi-c departs from the `psi` rule, which commits the table whenever this party received output.

**Payload commitments are present and empty.** psi-c refuses payload in either direction, so both directions commit the empty committed payload `{ "columns": [], "rows": [] }` -- present, salted, and domain-separated exactly as a populated one would be, never omitted. The readable `payloadSent` and `payloadReceived` lists are likewise the explicit empty list. Recording the no-payload case explicitly rather than by omission is the rule the `psi` no-payload case already follows, and it is what keeps a reader from having to guess whether a field is absent because nothing flowed or because the writer left it out.

What the separate signed receipt does and does not attest for such a run is under [A count-only run's receipt](#a-count-only-runs-receipt) below.

## Governance metadata

Alongside those fields the record carries readable **governance metadata** so it is self-describing as a disclosure record. This is: the governing data-sharing agreement -- its reference (for example `MOU-2025-0042`), the purpose of the disclosure under it (a brief readable statement of why the disclosure was made, as a HIPAA 164.528 accounting and a FERPA 99.32 record both require; a single agreement can authorize several purposes, and this names the one this exchange was for), and its expiration date -- identifying the authority for, and the purpose of, the disclosure; the `algorithm` (`psi`, which revealed matched identifiers, or `psi-c`, which revealed only a count), so the record shows whether identifiers or only a count were disclosed; the categories of data exchanged -- the payload columns this party committed as sent and received, each recorded as its name (the column actually transmitted by the metadata disclosure gate, not a name from the optional declared data dictionary) plus any data-dictionary description that dictionary supplies for it, with the no-payload case (no columns disclosed, or no matched records) recorded explicitly as an empty list rather than by ambiguous omission; and the matching basis -- the linkage fields the match keyed on, each recorded as its standardized field name and semantic type (for example `last_name`, `date_of_birth`, `ssn4`), documenting the PII on which shared membership was determined. The standardized name (not the raw source column) is the identifier the linkage keys and the standardization config both reference, so it is the anchor for tracing the basis back through standardization to the data; the basis covers only the fields the linkage keys actually reference, so a declared-but-unused field is not listed (it was not matched on). The legal agreement reference, purpose, and expiration, the algorithm, and the linkage-field set come from terms both parties validated at exchange time, so both parties' records carry consistent values for them. The payload column-name sets are not read from the (cross-checked) declared dictionary at all but from the committed payloads -- the columns the `isDisclosedToPartner` metadata gate actually transmitted -- so the readable list cannot drift from the committed bytes (a record can never read "sent nothing" while real columns were committed, the failure mode when no dictionary is authored). They are still consistent across the two parties, by a stronger route than cross-checking: the two directions' payload commitments cover byte-identical data, so one party's `payloadSent` equals the other's `payloadReceived` by construction (see [Commitment scheme](#commitment-scheme)). The data-dictionary description, looked up by committed column name, is the one governance field not cross-party-validated -- the two parties may annotate the same column differently, and a committed column the dictionary does not describe carries a bare name. The metadata is names, categories, descriptions, and references only -- never a payload value, a linkage-field value, or a matched identifier -- so the record stays free of protected data at rest, with the data exchanged bound by the commitments below rather than embedded.

### The rule-set citation

Beside the matching basis, the governance block records the **named rule set the agreed terms cited** (`linkageRuleSet`), when they cited one: the name and content version of the field set and of the key set, copied from the terms. Where the basis enumerates the fields the match keyed on, the citation is the artifact a data-sharing agreement or a governance review can name, so "which rules did this linkage match on" is answerable from the record without quoting the key list. Its source is [`linkage_terms.linkage_rule_set`](../EXCHANGE_REFERENCE.md#linkage_termslinkage_rule_set).

Three limits on what it asserts:

- **It is a citation, not the account of the run.** A run matches on a subset of the cited set -- terms derived from an input file leave out any key that input cannot supply -- so the citation bounds what was tried above; the matching basis beside it is what the keys actually referenced.
- **It is the authoring party's declaration**, recorded verbatim -- an acceptor adopts the inviter's citation into its own record unaltered. Nothing on the exchange path resolves the name to a set. What the exchange holds both parties to is the linkage fields and keys, which are cross-checked byte for byte; what the writing party could check about the name it recorded is the separate [verdict](#the-writing-partys-verdict) beside it.
- **Its cross-party consistency is the terms' own.** Two parties that both cite a set are required to cite the same one before any data moves, so their records carry the same names; where one cites none, its record omits the field while the other's carries its own citation. The verdict beside it carries no such guarantee, for the reason given below.

Omitted when the agreed terms cited no set (their rules were authored rather than drawn from one) -- absent by omission, never a null, which is why the record's format version moves with it.

**Where it is read.** The web disclosure-accounting screen and the CSV it exports present it beside the matching basis, each half named and versioned, so a governance reader answers "which rules did this linkage match on" from the accounting alone. Both carry a caveat with it, since a citation shown bare would read as a checked provenance: the caveat states that the citation is the authoring party's own declaration recorded as written, sends the reader to the [verdict](#the-writing-partys-verdict) recorded beside it for what the writing party could establish about the names, and names the matching basis as what the exchange held both parties to. A record whose terms cited no set reads as that rather than as a blank.

#### The writing party's verdict

Beside the citation, and present exactly when it is, the record carries `linkageRuleSetVerdict`: **the writing party's own verdict** on whether the linkage fields and keys the agreed terms declare are drawn from the sets those terms cite them to. It is per half -- `fieldSet` and `keySet` -- and each half takes one of three values:

| Value | What it states |
| --- | --- |
| `consistent` | The cited half names a rule set this build ships, and the declared rules for that half are drawn from it. |
| `contradicted` | The cited half names a rule set this build ships, and the declared rules are **not** drawn from it: the citation states a provenance the rules beside it do not have. |
| `unchecked` | The cited half names a set this build does not ship. Nothing resolved the name, so nothing was compared. |

Three values rather than two, because the absence of `contradicted` must not read as verification: a build that could not resolve a name has checked nothing, which is a different statement from having checked and found the rules to match. The halves are decided independently, for the same reason they are named and versioned separately -- a document can truthfully cite the shipped field set while its keys are not the shipped key set.

**Drawn from** means exactly what the implementation's own predicate means by it: every declared key byte-identical to a key the set declares, in the set's cascade order, and every declared field byte-identical to a distinct field it declares. A narrowed emission passes -- what an input file cannot supply is left out -- while an added, edited, or repeated rule, or a reordered cascade, does not.

Four properties fix how the row is read.

**It is per party and build-relative.** The verdict is written locally from the sets the writing build ships, not agreed between the parties and not folded into the agreed-terms hash. Two parties running different builds may therefore write different verdicts for one run and neither is wrong: a set one of them ships is a set the other may not. Nothing in the exchange compares the two, and a reader must not read one party's verdict as the other's.

**The set identity it was checked against is the citation beside it.** A `consistent` or `contradicted` half is reached only where the cited name *and* content version resolve to a set the build ships, so that half's own recorded name and version identify what it was compared against. An `unchecked` half resolved to nothing.

**The citation is annotated, never replaced.** A record carrying a `contradicted` half still records the citation verbatim. Dropping or rewriting a refuted citation would launder the declaring party's claim out of the artifact and leave the record silent about a claim that was made; annotating it keeps both the claim and the finding in the disclosure record an auditor reads.

**It changes nothing about the run.** The verdict is written after the exchange, from terms both parties already agreed; which fields and keys a run matches on, and what it discloses, are settled entirely by the declared rules. Both parties write it on the same rule -- the inviting party over its own citation, the accepting party over the inviter's citation as adopted -- so the row means the same thing in either record.

Besides the record, the verdict is surfaced beside the citation on the pre-consent accept prompt (CLI) and consent review screen (web), before either party commits: [`linkage_terms.linkage_rule_set`](../EXCHANGE_REFERENCE.md#linkage_termslinkage_rule_set) and [the design note behind it](../notes/rule-set-citation-verdict.md) cover where and why. The disclosure accounting is not among those surfaces: it presents the citation under its caveat, whose pointer to the verdict beside it in the record is as far as it goes -- the value itself is not a row there.

## Retention and disposition pointer

Distinct from that governance metadata, the record can also carry an optional **retention/disposition pointer**: a free-text note recording where this party filed its copy of the result (the association table and any received payload) and under what retention schedule it is held or disposed of, so the record answers an auditor's first operational question -- where did the result go -- without a separate lookup. Unlike the governance fields, it is **not** drawn from the agreed terms: it is sourced from this party's own local exchange config, so it is per-party (the two parties' pointers are independent and need not match), is never exchanged with the partner, and is not folded into the agreed-terms hash. It is metadata only -- never a payload value, a linkage-field value, or a matched identifier -- and is recorded only when configured; its absence is explicit (the field is omitted, never an empty string). Configured via [`retention_disposition`](../EXCHANGE_REFERENCE.md#retention-and-disposition) in the exchange spec.

## Commitment scheme

The record commits to the data exchanged rather than embedding it: the payload columns this party sent, the payload columns it received, and -- when this party holds it (it received output) -- the association table. A bare `SHA-256` of a low-entropy result (for example an association table over identifiers; cf. the SSN brute-force warning in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)) would be brute-forceable by anyone holding the record, leaking the intersection. Instead each commitment is

```
commitment = HMAC-SHA-256(key = salt, message = canonical({ domain, data }))
```

with a fresh per-commitment `salt` (CSPRNG-generated, at least 128 bits) and a per-kind `domain` label that separates the three commitment kinds. Keying HMAC with the secret salt gives computational hiding (the commitment reveals nothing about the data, and a low-entropy data set cannot be brute-forced from the commitment without the salt); binding follows from the collision resistance SHA-256 lends HMAC, so the committer cannot open one commitment to two different data sets. The committed `message` is the canonical encoding ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)) of `{ domain, data }`, so both parties commit over byte-identical serializations of the same logical data (row order, encoding, and null handling all fixed) and an independent implementation reproduces the bytes; that serialization is specified in [CANONICAL_ENCODING.md](CANONICAL_ENCODING.md). The two payloads are committed in a canonical representation owned by the record format rather than the transport encoding: `{ columns, rows }`, with the wire `hasData` discriminant dropped and a no-data payload the empty value `{ "columns": [], "rows": [] }`. A committed payload binds the disclosed column names and the row values only -- **not** any party's internal row indices. The received-payload commitment would otherwise bind the partner's row numbers, which the holder does not retain in a reproducible form (its result file records the received values, not the partner's row numbers), leaving the holder unable to reopen its own commitment; which records matched is bound separately, by the association-table commitment -- an ordered `[our row indices, partner row indices]` pair, one entry per matched pair -- whose partner side the result file retains (see the partner row-index column in [PROTOCOL.md](PROTOCOL.md#output)) so the holder can reproduce it. Under a [deduplicating cardinality](PROTOCOL.md#deduplicating-cardinalities-many-to-x-matching) a row index repeats on one side of that pair, once per link, and the commitment binds the repeated entries as it binds any others; the payload commitments are unaffected, holding one row per matched RECORD (a payload row is addressed by the sender's own row index, so a record that stands in several pairs contributes one row). Because both payloads normalize to this one shape, a sender's payload-sent commitment and the receiver's payload-received commitment cover byte-identical data for the same logical payload. That byte-identical-data property lets a verifier re-supply the shared payload when it opens a commitment. It does not, on its own, let one party recompute the *other* party's commitment: the sent and received kinds use different domain labels and independent per-commitment salts, so cross-verifying a partner's record additionally requires that partner's per-commitment salt (its verification keys, which are otherwise kept private) or a purpose-built cross-commitment step -- neither of which this format delivers by itself. The record is local and self-attested, so its commitments are never compared between parties; the mutually-verifiable artifact is the separate [signed receipt](#signed-receipt), whose content deliberately excludes these salted commitments.

## Signed receipt

The certificate-backed **signed receipt** reuses this document's canonical encoding and committed-payload shape but is a *separate* artifact from the self-attested record: it is a single **dual-signed record** carrying facts *both parties derive byte-identically*, over which each party makes an ECDSA P-256 signature that a third party can verify against either party's view. Where the self-attested record is a per-party, salted, hiding artifact, the signed receipt is a mutually-verifiable attestation of what flowed, whose directional payload values are session-keyed MACs (see below) rather than salted commitments. The signing/exchange step that produces it, its trust model, and the fingerprint-pin-before-signature check are specified in [PROTOCOL.md](PROTOCOL.md#the-signed-receipt-step), and the checks a holder runs against a stored copy in [Verifying a stored dual-signed record](PROTOCOL.md#verifying-a-stored-dual-signed-record); this section fixes the byte layout so an independent implementation reproduces it.

### Receipt content

The **receipt content** is the object both parties sign. Its canonical bytes are folded into the per-signer signed bytes below; the content object has exactly these keys (the canonical encoder sorts them):

- `termsHash` -- the agreed-terms hash (unpadded base64url `SHA-256`), computed exactly as the self-attested record's `termsHash` above, so both parties produce the same value.
- `initiatorToResponderPayload` and `responderToInitiatorPayload` -- the **directional payload MACs**, each an unpadded base64url `HMAC-SHA-256` over the canonical encoding of the `<committedPayload>` that flowed in that direction, under a per-direction key derived from the session key. The MAC key is `HKDF-SHA-256` of the session key with a zero salt and the info string `psilink-signed-receipt-payload-v1:<direction>`, where `<direction>` is `initiator-to-responder` or `responder-to-initiator`; the label is prefix-free against every other session-key label. `<committedPayload>` is the record's [committed-payload shape](#commitment-scheme). Both parties hold both directions (each sends one payload and receives the other, and a sender's committed payload is byte-identical to the receiver's) *and* both hold the session key, so both compute the same two MACs; keying them by the fixed handshake direction (not by local/partner) makes the two content objects byte-identical. The MAC key is derived at sign/verify time and **never stored** in the receipt file -- the file carries only the resulting MAC value. Keying off the session key (not a bare hash) is what stops a third-party receipt holder, who has neither the session key nor the flowing data, from recomputing a directional MAC or brute-forcing a low-entropy payload from it; the no-data direction is likewise a session-keyed MAC, not a public constant, so it does not leak payload presence. The salted record commitments remain the record's hiding artifact.
- `binder` -- the per-exchange replay binder (unpadded base64url over 32 bytes): `HKDF-SHA-256` of the session key with a zero salt and the info string `psilink-signed-receipt-binder-v1:initiator`. Both parties fold in the *initiator-role* label, so both derive the same binder (see [PROTOCOL.md](PROTOCOL.md#the-signed-receipt-step)). The exchange record of the same run repeats this value in its `receiptBinder` field, which is what pairs the two artifacts offline: [Pairing a receipt to one run](#pairing-a-receipt-to-one-run).

The salted record commitments and the association-table pairing are **not** part of the receipt content; the rationale (they are not byte-identical across parties, or not held by both) is in PROTOCOL.md. The terms-exchange envelope fields carried beside `linkageTerms` -- the record count, the `save` and `disclosesPayload` advertisements, the observed host key, and the protocol version -- are outside the content and outside the agreed-terms hash on the same rule: each is asserted by its own party rather than derived byte-identically by both. A receipt therefore attests the agreed terms and nothing about the run's envelope, including the payload-intent flag that drives the association-table withhold and the host key each party independently observed.

### Receipt signature

Each party signs its own **signer-bound bytes**: the RFC 8785 canonical encoding of `{ "domain": "psilink-signed-receipt-content/v2", "content": <content>, "signer": { "fingerprint": <signer fingerprint>, "role": <signer role> } }`, where `<content>` is the shared receipt content above, `<signer fingerprint>` is the signer's OWN certificate fingerprint ([the same value a partner pins](PROTOCOL.md#signing-identity-and-certificate-pinning)), and `<signer role>` is `initiator` or `responder`. The signature is an ECDSA signature over those bytes under that party's signing key -- P-256 with SHA-256, encoded as the fixed-length 64-byte raw `r || s` (IEEE P1363) in unpadded base64url, exactly as a certificate self-signature is ([PROTOCOL.md](PROTOCOL.md#signing-identity-and-certificate-pinning)). A signature field that decodes to any other length is refused rather than decoded, so a DER `SEQUENCE` of the same two field elements does not verify. Signing is randomized, so the same content signed twice under one key yields different signature bytes and both verify; what reproduces across implementations is the signed bytes above, not the signature. Binding the signer's fingerprint and role into the signed bytes makes the two `{ certificate, signature }` blocks **non-interchangeable**: a holder cannot swap them to re-attribute a direction's payload to the wrong party, since each signature binds its own signer (the shared content alone would otherwise verify under either key). A verifier reconstructs the partner's signed bytes from the shared content, the partner's *pinned* fingerprint, and the partner's role (the opposite of the local role). The `content` domain (`psilink-signed-receipt-content/v2`) is domain-separated from the certificate signature and fingerprint domains, so a receipt signature can never be confused with a certificate self-signature.

### Dual-signed record file

The dual-signed record carries a format `version` (`psilink-signed-receipt/v2`, a single recognized literal a reader rejects rather than migrates -- it moves with the certificate format the record embeds), the shared `content` above, and one `{ certificate, signature }` block per party keyed by the fixed handshake role (`initiator`, `responder`).

**Agreement between the two parties' copies.** Both parties write the same record: roles are fixed by the handshake rather than by local/partner, and each party stores the signature the partner sent rather than re-deriving it, so the two files agree byte for byte even though ECDSA signing is randomized. That agreement is a property of how the two parties assemble the file, **not** a property of the format: ECDSA signatures are malleable in `s`, so a third party holding a record can replace either signature with its negation and produce a differing copy that still verifies, attesting the same facts. Two records are therefore compared by verifying them against the pinned fingerprints, never by hashing the file or comparing bytes.

**Contents and custody.** The record holds **no payload contents and no private keys**: only public certificates, signatures, the agreed-terms hash, and the two session-keyed payload MACs (from which a holder without the session key can recover neither the payload nor its presence). Both parties' identities and the terms are bound into it -- that is its purpose, a mutually non-repudiable attestation -- so it is not anonymous; see [Receipt privacy properties](#receipt-privacy-properties) for exactly what a holder learns. The CLI writes it owner-only by default (an operator shares it by copying the file, matching the record's conservative default) and atomically (temp file then rename), to a timestamped `psilink-receipt-<stamp>.json` path sharing the exchange's `createdAt` stamp with the record, overridable via `signing.receipt_output`. Serialized as ordinary pretty JSON with a trailing newline (the human-readable persisted form, not the canonical encoding, which is only the bytes that are signed), like the self-attested record.

### Receipt privacy properties

A third-party holder of the dual-signed record (without the session key and without either party's retained input or result) learns:

- the two parties' `identity` strings (each carried in a certificate the record embeds);
- that an exchange occurred between them under a given agreed-terms hash;
- the mutual, non-repudiable attestation itself -- each party's ECDSA P-256 signature binding it to the terms and this exchange;
- the per-exchange binder, from which it can tell whether an exchange record it also holds is the record of this same run ([Pairing a receipt to one run](#pairing-a-receipt-to-one-run)) -- and nothing further: the binder is a one-way value over a session key it does not have.

It does **not** learn:

- payload contents -- the directional payload values are session-keyed MACs, not the data;
- payload presence -- the no-data direction is a session-keyed MAC, not a public constant, so a holder cannot tell an empty direction from a non-empty one, nor recover a low-entropy payload by brute force (both require the session key, which the record never carries);
- any private key -- only public certificates travel in the record.

The session key, the per-direction MAC keys, and the flowing data all stay off the receipt, so recovering a payload from it is not possible for anyone but the two data holders. Retention and access control of the receipt remain the holder's responsibility.

### Pairing a receipt to one run

A verified verdict on a dual-signed record establishes who signed it and that the signed content -- the agreed-terms hash, the two directional payload MACs, and the per-exchange binder -- was signed by both named parties. On its own that does not say *which* run of a partnership the receipt attests: recurring runs under the same agreed terms produce a byte-identical agreed-terms hash and carry the same two certificates, and the two content fields that do vary per run -- the binder and the payload MACs -- are [reported, not recomputed](PROTOCOL.md#verifying-a-stored-dual-signed-record), an offline verifier having neither the session key they derive from nor the data the MACs cover.

What pairs a receipt to one run is the **`receiptBinder`** the [exchange record](#record-fields) repeats: the same 32-byte value the receipt content's `binder` carries, written verbatim into the record of the exchange that produced that receipt. Both parties derive it from the run's session key with the initiator-role label, so both records carry the same value; a different run has a different session key and so a different value. A verifier handed a receipt and a record -- `psilink verify-receipt` with both artifacts, the web verify bench with both loaded, or a third party given the two files -- compares the two and reports one of four outcomes:

- `verified` -- the record and the receipt carry the same value: they are one run.
- `mismatch` -- they carry different values: the two artifacts are from different runs, and the whole verdict is `failed`. Every other check may pass; the pairing is what separates two runs of one partnership.
- `unpaired` -- the record carries no `receiptBinder` at all. A record omits the field exactly when its exchange derived no binder (no signing identity, or a path with no session key), so no receipt can belong to it: also `failed`.
- `not-checked` -- no record was supplied. Nothing is contradicted and nothing fails, but which run the receipt attests stays open, so the verdict is held at `incomplete` and never reaches `verified`. This is the case for a holder legitimately in possession of only the receipt; the remedy is the run's record, not a weaker verdict.

A record whose [`outcome`](#when-a-record-is-owed) is `receipt-swap-terminated` takes the same three record-bearing outcomes as any other: where its run derived a binder it carries it, so a receipt held beside it pairs or mismatches on the value. What the outcome adds is that the WRITING party held no receipt of its own -- a genuine receipt pairing to such a record is the partner's copy, whose own signatures and anchors the verdict reports as it does for any receipt. The record's outcome is not itself a verification input and changes no verdict; it is a fact about the run, read from the record.

The check is an equality comparison of two public values, not a derivation: the verifier still cannot compute the binder (that needs the session key, which only the two parties ever held and neither retains), so a binder substituted into *both* artifacts by a party that holds them both is out of its reach. That residual is detectable only during the live exchange, where each party derives the value independently and a partner that signed a different one fails the [signed-receipt step](PROTOCOL.md#the-signed-receipt-step). What the pairing does close is the offline case a holder of two genuine artifacts can otherwise pass off: one run's receipt read beside another run's record.

The record's own per-exchange [binding nonce](#record-fields) is not this value and could not be. It is generated locally, so the two parties' records for one run carry different nonces, while the receipt content admits only facts both parties derive byte-identically -- so folding a nonce into the signed content would need both parties' nonces exchanged during the receipt step, and each would be a value its party asserts rather than derives. Carrying the receipt's already-shared, already-derived binder in the record instead leaves the signed format untouched; the reasoning is recorded in [receipt-run-binding.md](../notes/receipt-run-binding.md).

**Privacy of the repeated value.** Carrying the binder in the record widens neither artifact's disclosure of the linked data. It is a one-way `HKDF-SHA-256` output over the session key that the signed receipt already publishes in cleartext, so a holder of the receipt learns nothing new from the record's copy, and a holder of the record learns a value that discloses nothing about the data: the session key is not recoverable from it and it covers no payload. Its presence or absence adds one fact to that record -- whether the exchange produced a signed receipt -- which is a statement about the two parties' own configuration, not about the data or the people in it. The one capability it confers is the intended one: a holder of both parties' records for one run can tell that the two are that same run, rather than only that they name the same parties and terms. Both privacy lists carry that difference: the [receipt privacy properties](#receipt-privacy-properties) list the binder among what a third-party holder of the receipt learns, and the record's own [privacy properties](#privacy-properties) list what a present `receiptBinder` adds to the record. Those enumerated pairing facts are the whole of what a holder of either artifact learns from the repeated value; neither list gains anything about the linked data or the people in it.

### A count-only run's receipt

The receipt is a separate artifact from the record and binds neither the record, nor its commitments, nor its result-size field -- for a [count-only run](#count-only-psi-c-records) or any other. Its content is the agreed-terms hash, the two directional payload MACs, and the per-exchange binder, and nothing else. For a count-only run those three resolve as follows.

- The agreed-terms hash binds `algorithm: psi-c` along with the rest of the agreed terms, the algorithm being a mandatory-consistency term both parties fold into the same hash. The receipt is therefore third-party-verifiable evidence that this exchange was agreed and conducted as count-only.
- Both directional payload MACs are taken over the empty committed payload, computed and carried exactly as a populated direction's would be. A holder without the session key cannot distinguish an empty direction from a populated one, so the receipt does not disclose that no payload flowed.
- The count itself is not part of the receipt content and is not added to it. The content admits only facts both parties derive byte-identically, and the count is not one: in a one-sided run only the receiver holds it, and in a both-entitled run the sender holds it as the receiver's report rather than as its own derivation. The same rule already excludes the association-table pairing.

A count-only receipt therefore attests what was agreed and that an exchange occurred under it -- not what the count was. A party that needs the count itself third-party-attested has no artifact here that supplies it.

## Record and verification-keys files

The artifact is split across two files, on the CLI and the web app alike. The **record** holds the commitments and the non-secret summary above; it does not contain the matched data or the salts, so it does not reveal -- or allow brute-force recovery of -- the intersection, and it is the part safe to retain or hand to an auditor. The **verification keys** hold, per commitment, only the salt (base64url, at least 128 bits) needed to open that commitment later; the file carries its own format version (`psilink-exchange-keys/v1`), rejected-if-unrecognized like the record's. The keys carry **no snapshot of the committed data** -- they are not a second at-rest copy of the matched data (see [No data snapshot in the keys](#no-data-snapshot-in-the-keys-data-minimization) below). They are still sensitive and must be kept private: a salt together with the record's commitment can open -- and brute-force a low-entropy -- committed value, notably the intersection, so anyone holding both the keys and the record could open the commitments.

Both files are written owner-only. The CLI writes them atomically (temp file then rename; see [CREDENTIAL_STORAGE.md](CREDENTIAL_STORAGE.md#posix-write-discipline)) to a timestamped default path (overridable, or skipped with `--no-record`): the record as `psilink-record-<stamp>.json` and the keys as `<name>.keys.json` alongside it. The web app offers the two as two separate downloads -- the shareable record and the private verification keys -- mirroring the CLI split, so the record can be shared with an auditor without the keys. The record is written owner-only even though it is shareable: "shareable" means it carries no secret material (no salts, no matched data), not that it is world-readable on disk. It still names both parties, the governing agreement, the data categories, this party's exposed-record count, and (when present) the result size in cleartext (see below), so the conservative default keeps it private to the owner; share it by copying the file, not by loosening its permissions. The verification keys are not shareable at all -- keep them private and separate from the record.

`--no-record` suppresses the record and its keys, not the signed receipt: a signing-configured run writes its [dual-signed record](#signed-receipt) either way. That receipt's pairing check then has no record to pair against, so it is permanently in the `not-checked` case of [Pairing a receipt to one run](#pairing-a-receipt-to-one-run) and verifies at most `incomplete` on every verifying surface -- and the record that would resolve it cannot be reconstructed after the exchange. An operator retaining receipts as evidence retains the record too. Because nothing after the run can repair the combination, the CLI warns about it before the exchange runs, on both the operator log and the `warning` event of the [machine-readable event stream](CLI_EVENTS.md#warning); the run then proceeds, since which artifacts to keep is the operator's choice.

### No data snapshot in the keys (data minimization)

The verification keys deliberately hold only salts. Storing, per commitment, a snapshot of the exact committed data alongside the salt would make verification self-contained at the price of a **second copy of the matched data at rest** -- a copy an operator would not expect from a tool built for a transient exchange, and outside any accounting of where data is stored. Salts-only keys leave the matched data persisted only in the result file the operator chose to write. The cost is that verification is not self-contained: it must **re-supply** the committed data (from the holder's own retained input and result) and re-canonicalize it. Because a commitment is `HMAC-SHA-256(key = salt, message = canonical({ domain, data }))`, the re-supply path MUST reproduce the exact RFC 8785 canonical bytes (see [CANONICAL_ENCODING.md](CANONICAL_ENCODING.md)) the original commit used -- the committed-payload shape (column names and row values) for a payload, or the `[our row indices, partner row indices]` pair for the association table -- or every opening fails. The committed payload holds no row indices, so it re-supplies from the retained input, config, and result; the association table's partner side re-supplies from the partner row-index column the result file carries for every matched pair. Because the table is committed per pair while the payloads are committed per record, the re-supply is not uniform across the three data sets under a deduplicating cardinality: the table takes one entry per result row, while each payload takes the result's DISTINCT rows on its own side of the pairing -- the distinct local rows for the sent payload, the distinct partner row indices for the received one, each in the order that side sent them. Reproducing from those files requires them **unmodified**: the commitments bind the matched-row order the result was written in, so a re-sorted or re-exported result does not reproduce them (the "hash a file, check it later" constraint any file verifier has). Three reproduction edges are surfaced as warnings rather than silently mis-reconstructed: an identifier column with duplicate values makes the our-side row index ambiguous when a result row is mapped back to an input row (the first occurrence is used, and every later duplicate then reproduces the first row's values, so the commitments report a mismatch -- an input whose identifier names the individual rather than the row carries such duplicates by construction, which is the input a deduplicating exchange sets out to group), a result referencing an identifier the supplied input does not carry signals that the input does not match this exchange, and repeated result rows for one partner record whose received values disagree mean the result no longer carries the single row those values were committed as. That last one is a requirement on the re-supply, not merely a diagnostic: taking the distinct partner rows MUST be conditional on every copy of a repeated row agreeing cell for cell, and a disagreeing copy is reproduced beside the first rather than collapsed onto it, so the record fails verification. Which commitment surfaces the divergence depends on what else the edit touched: with the pairing (partner row-index) columns intact, a disagreeing copy mismatches the received-payload commitment; an edit that also moves a pairing column can reproduce the committed received payload exactly, and there it is the association-table commitment that mismatches instead. Either way the record as a whole does not verify. A collapse that kept the first copy unconditionally would leave every later copy's value cells reproduced by nothing and so bound by no commitment in the record, while the result file writes one such row per pair. A fourth edge cannot be seen during reconstruction, because nothing in the re-supplied files distinguishes it: a result value cell cannot tell a committed empty string from a committed null -- the result writes both as an empty cell -- so a genuinely-null received cell reproduces as an empty string and its commitment reports a mismatch. It is named after the verdict instead: when the received-payload commitment mismatches and the re-supplied received payload carries an empty cell, the empty-versus-null difference is reported as a possible cause of that mismatch. Both conditions are required -- with no empty cell that cause is impossible, and with no mismatch there is nothing to explain -- and the verdict itself is untouched, since the record cannot say which of the two values was committed. The sent-payload commitment is not subject to the edge: it re-supplies from the retained input file, which the send side read through the same reader, so an empty cell there was an empty string at commit time and reads as one again. The commitments' order-dependence could be lifted by committing the pairing as a canonically ordered set -- deferred, since it changes the committed bytes and warrants its own review. That re-supply path is owned by the verification consumer, `verify-receipt`; this document fixes only the artifact shape it consumes.

A corollary of re-supply: opening a commitment is a data-holder capability. A third party who lacks the holders' retained input and result can still check the signatures and identity bindings on the [signed receipt](#signed-receipt) but cannot open the record's commitments itself -- only a party that already holds the data can. The salts-only keys hand no one the data.

### Keys written by default (with the record)

Writing the verification keys is default-on: whenever recording is enabled the keys are written alongside the record under the single `--no-record` control (the web app offers both downloads together the same way), with no separate suppressor for the keys alone. This is a deliberate default, worth recording because the keys are private, non-shareable material whose only consumer is `verify-receipt`.

The default turns on an asymmetry in recoverability. Each salt is CSPRNG-generated at commit time and stored nowhere but the keys file, so if the keys are not written at the exchange the salts cannot be reconstructed and the commitments can never be opened -- and the exchange generally cannot be re-run to mint fresh ones. An operator cannot know at exchange time whether they will later want to open a commitment; writing the keys at the exchange is the only way to keep that capability open, while not writing them forecloses it irrecoverably. Default-on costs one extra owner-only file the operator can delete at any time; default-off costs a capability that cannot be recovered after the fact.

The keys being cheap and low-risk to retain is what makes that asymmetry decisive. They hold only salts and no matched data (above), so default-on does not persist a second copy of protected data; the record is itself written owner-only and default-on, so a second owner-only, salts-only file is a marginal at-rest increase, not a new category of exposure. The keys' one real risk -- that with the record they open the commitments (the brute-force concern above) -- materializes only if both files leak, and both are 0600; an operator who wants neither uses `--no-record`, which suppresses the pair. Keeping them under one control also avoids a record whose commitments can never be opened -- a partial state with no use and a trap for the verifier. This default would only need revisiting if the keys came to hold more than salts, or a concrete need emerged to retain the shareable record while deliberately withholding its opening material.

One case reaches that unopenable state whatever is written, and the default does not pretend otherwise. A [terminated run](#when-a-record-is-owed) writes no result file, so its record's commitments have nothing to re-supply from and the keys beside them open nothing. They are written there all the same, on the same single control: the write stays one rule rather than acquiring a condition, and what it costs is an owner-only file of salts the operator can delete. The terminated case supplies no second reason for the default -- the recoverability asymmetry above is about the runs that produce a result -- and it is not a reason against it either.

## Privacy properties

Privacy of the record itself: it stores the terms hash, each `identity` string that was supplied, this party's exposed-record count, the result size (when present), any retention/disposition pointer, the run's `outcome`, and the governance metadata above (the agreement reference, purpose, and expiration, the algorithm, and the data categories) in cleartext, so anyone who reads it learns that an exchange with that partner occurred, under which agreement, over what categories of data, how many records this party exposed, where it filed the result (when a pointer is configured), whether the run ran to completion, and -- when both sides were entitled to it -- its size, but no protected values. The `outcome` adds one fact about the run's own conduct and none about the data: both of its values describe a disclosure that occurred, and they differ only in whether the run got through the steps after it and left this party a receipt. The `receiptBinder`, when present, adds only that the exchange produced a signed receipt and the means to tell whether a given receipt is that run's; it is a one-way value over the session key and discloses nothing about the data ([Pairing a receipt to one run](#pairing-a-receipt-to-one-run)). As with the receipt, retention and access control of the record (and the strict protection of the verification keys) are the holder's responsibility.
