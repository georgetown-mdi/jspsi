# Channel security construction

This document specifies the construction and implementation of PSI-Link's
channel-security controls, the section headings below indexing the individual
controls. It is
the implementation-level complement to the **Channel security** overview in
[SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security), which covers what
each control protects against and why the design is sufficient; this document
covers the wire formats, the derived constant values and their justification, the
enforcement points, and the dependency premises each control rests on. It does
not cover the threat model or authentication design (see
[SECURITY_DESIGN.md](../SECURITY_DESIGN.md)), the PSI and key-exchange wire
protocol (see [PROTOCOL.md](PROTOCOL.md)), or the network channels and transport
contract (see [COMMUNICATION.md](../COMMUNICATION.md)). Intended readers are
security auditors and implementors.

Every net-new control specified here is subject to the explicit pre-release
security review required by
[CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy); the per-section notes
below repeat this only where a control carries an extra scope nuance (an
internet-facing surface, a new security-relevant dependency, or a modification
layered on an existing control).

# Application-layer AEAD

Both parties use the HMAC-based Extract-and-Expand Key Derivation Function (HKDF) to derive AES-GCM keys from the 32-byte key-exchange session key - two directional keys, one per direction (HKDF info strings `psilink-aead-v1:initiator-to-responder` and `...responder-to-initiator`) rather than a single common key - so that every key has a single sender, and messages are encrypted using Authenticated Encryption with Associated Data (AEAD). Each message carries a per-direction sequence number as its nonce, preventing replay and reordering. The separate per-direction keys are what keep that nonce construction safe: both directions number their messages from zero, so a single common key would encrypt two different messages under the same key and nonce - a reuse that is catastrophic for AES-GCM - whereas one key per sender keeps every key-nonce pair unique. The server admin sees only opaque ciphertext files, and tampering with a file causes the authentication tag to fail and the exchange to abort. The AEAD context is restricted to this fixed pair of per-direction labels (a closed union, guarded at runtime), not an open string. Both parties must derive identical per-direction keys from identical labels; a variable, non-ASCII, or non-NFC label would make the two sides derive different keys and fail the AEAD with an opaque error rather than a clear authentication failure, so the label set is closed by construction.

The concrete envelope the `EncryptedMessageConnection` decorator emits is a binary frame `version || IV || ciphertext || 16-byte GCM tag`, carried as raw bytes (no base64url, no JSON wrapper). `version` is a single leading format/version marker (`AEAD_ENVELOPE_VERSION`, currently `1`); the 12-byte IV is four leading zero bytes (authenticated, but not separately validated) followed by the 8-byte big-endian sequence number; and the encrypted plaintext is a one-byte type tag (`0` for a JSON object, `1` for a `Uint8Array`) ahead of the payload. The type tag stays inside the authenticated ciphertext and is never promoted to a cleartext envelope field, so a transport admin cannot flip JSON/binary routing without failing the GCM tag. The version marker turns a format mismatch -- an envelope from an incompatible build, or an inbound that is not the binary shape at all (the clean break from the prior base64url-in-JSON `{ enc }` format) -- into a clean `security` rejection rather than a silent misparse. This wire format is pinned byte-for-byte by a checked-in known-answer vector at [`packages/core/test/vectors/aead-envelope-vectors.json`](../../packages/core/test/vectors/aead-envelope-vectors.json), following the cross-implementation vector precedent of `canonical-vectors.json` and `exchange-record-vectors.json`: each vector fixes a session key, role, sequence number, and plaintext and records the exact `envelopeHex`, so an independent implementation can reproduce it from those inputs and any change to the version marker, nonce construction, byte order, envelope shape, or tagging is caught. The vectors are regenerated by `generate-aead-envelope-vectors.mjs` in that directory and asserted against the decorator in `packages/core/test/encryptedMessageConnection.test.ts`, which separately pins the per-direction HKDF key derivation (`deriveAeadKey`).

Because the type tag is encrypted, the file-sync transport beneath the AEAD layer cannot read it to route a frame, so it carries its own outer, cleartext discriminator: every data-plane message file is a binary envelope `version || type || seq || payload` (built and read by `send()`/`poll()` in `fileSyncMessageLoop.ts`), where `type` selects a JSON control payload (UTF-8 JSON, parsed through the `parseBoundedJson` chokepoint) or a raw binary frame (delivered as-is). This too carries the frame as raw bytes -- no base64url and no whole-frame string conversion -- so the read path no longer depends on `Buffer.prototype.toString()` and a frame larger than Node's maximum string length can be read.

## Associated data is deliberately not bound

The envelope binds no Associated Data (AAD), and this is a deliberate, recorded decision rather than an omission. AAD would matter only to stop a frame authenticated under one context (role/direction, session, or transcript) from being spliced or replayed into a different context that shares the same key. Here every such context is already separated below the AAD layer by a distinct key. Direction is bound by the key: each direction uses its own AES-GCM key, derived with a distinct HKDF info string (`psilink-aead-v1:initiator-to-responder` versus `...responder-to-initiator`), so a frame presented to the opposite direction decrypts under the wrong key and the tag fails. Session is bound by the key: both keys derive from the per-session key-exchange session key, which is transcript-bound and mixes in each run's random ephemeral scalars, so it is distinct even across two runs of the same shared secret - a frame from one session decrypts under the wrong key in another. Ordering within a single direction of a single session is bound by the sequence-number nonce and the strict-increasing replay guard. The only set of frames that share one AEAD key is those one sender emits in one direction of one session, and the decorator carries exactly one logical stream there - it does not multiplex sub-channels or protocol phases, and the one-byte payload type tag that distinguishes binary from JSON lives inside the authenticated plaintext. There is therefore no second logical context under a shared key for AAD to separate, so binding the direction (or a session id) as AAD would only restate what the key already enforces. The sequence number is the GCM nonce, not a substitute for AAD: the reason AAD is unnecessary is the absence of a second context under one key, not that the nonce stands in for AAD. Practically, the decorator holds only its inner connection, the session key, and the role - no session or transcript id is in scope to bind without new plumbing that belongs to the not-yet-wired caller integration.

Revisit this decision if a future change multiplexes more than one logical stream or protocol phase over a single direction's key, or collapses the per-direction key split into one shared key. In either case a context or sub-stream id bound as AAD would stop being redundant: it would still block cross-direction splicing, though not the key-nonce reuse that collapsing the key split would itself make catastrophic (AAD does not protect against nonce reuse). Until then, the per-direction key plus the sequence nonce are sufficient and no AAD is bound.

## Inbound integrity, replay, and ordering checks

Now that this layer is wired in (recurring CLI exchanges), its AEAD/MAC and sequence-number (replay and ordering) checks run at the protocol layer, on the output of a `receive()` call: the decorator validates and decrypts each inbound envelope inside `receive()` and rejects with a `security` `ConnectionError` on any integrity, replay, or ordering failure. These checks are deliberately not latched into the inner connection as a transport control (the `fail`/`finish` teardown signals) behind a buffered inbound frame. The message queue drains an already-received frame to the consumer ahead of any terminal error, whether the close was clean or abnormal (see [Message delivery and teardown](../COMMUNICATION.md#message-delivery-and-teardown)), so a check wired as a transport-level latch could hand a suspect frame to the consumer before the integrity alarm fires. The decorator honors this - it raises the failure from `receive()` itself, and the inner transports raise only `transport` and `protocol` terminal errors with no integrity check latched behind a frame - so the constraint holds and remains one to preserve.

Two channel-hardening concerns attach to this layer once it is wired into live recurring CLI exchanges, where each becomes live residual risk against a transport-level attacker (for SFTP, the server admin). One - the inbound frame-size bound - is now enforced (described below, alongside the companion directory-listing bound that closes the related directory-enumeration vector). The other - detection of dropped, withheld, and truncated frames - is now split: strict mid-stream gap detection is enforced (described next), and end-of-stream / truncated-tail detection is a deliberate accepted deferral on the reasoning recorded below. The gap-detection half was the release-blocking concern and is resolved (pending the explicit security review); the truncated-tail deferral does not block release on its own; the reasoning below records why it stands on the matching loop's self-driven lockstep.

Mid-stream gap detection is now enforced. The sequence-number check previously rejected only a number that was not strictly greater than the last accepted, which stopped replay and reordering but not omission: a gap (a sequence number that skips ahead) was accepted. The decorator now rejects any inbound sequence number that is not exactly the last accepted plus one, so a frame dropped or withheld between two delivered frames is caught here as a `security` failure on the output of `receive()` - the same protocol-layer surfacing as the replay and tag checks, never a transport-level latch. This did not require the once-feared send-path change ("advance the counter only on a fully successful send"): a send that consumes a counter value but then fails to transmit (an encrypt fault or an inner transport failure) already latches the wrapper terminal, so no later frame is ever sent, and a consumed-but-unsent value can only truncate the tail, never leave a gap between two delivered frames. Strict gap detection therefore raises no false alarm while the synchronous `sendSeq++` before the encrypt is retained - which is what keeps two concurrent sends from peeking the same counter and reusing an AES-GCM nonce.

## End-of-stream and truncated-tail detection

End-of-stream / truncated-tail detection is a deliberate accepted deferral, not a coverage gap to be closed with a marker. A truncated tail - a stream that simply stops, including a dropped final frame - is indistinguishable at the AEAD layer from a clean end, and no AEAD tag can authenticate the *absence* of a frame: an omitted frame can be detected only by expecting one and not receiving it. The PSI protocol is self-driven lockstep (see [PROTOCOL.md](PROTOCOL.md)): each party drives a deterministic script of matched send/receive calls, so the receiver always knows from its own script whether another frame is due. In the symmetric case a truncated tail therefore surfaces - as a stalled `receive()` that hits the inactivity timeout - and an explicit, integrity-protected end-of-stream marker could only reclassify that timeout from `transport` to `security`, not detect the omission any sooner. Reclassification alone does not justify net-new, security-reviewed cryptographic surface, so the marker is not built. The lockstep is unconditional within the implemented one-to-one cardinality: the matching loop runs `identifyIntersection` for every agreed key on both parties -- the key set is fixed by the linkage terms, and the PSI library returns an empty intersection without error for an empty input set, so a locally-empty round is a correct no-op that both sides still perform. A per-party-data-gated skip (`if (data_j.length === 0) continue;`) would break this: `data_j` is built from a party's own still-unmatched records, so one side can empty a later key while its partner does not, and skipping there drops a send/receive the partner still performs and desyncs the exchange. Any future cardinality loop must therefore not reintroduce such a skip. This is a protocol-loop invariant, not an absent-frame one: no AEAD-layer marker could detect or repair a lockstep desync, so the end-of-stream marker's deferral is independent of it.

## Inbound frame-size bound

The enforced control is the inbound frame-size bound. Left unbounded, the transport read path loads an entire frame into memory before any integrity check runs, so a hostile filedrop/SFTP server admin -- an adversary under the threat model (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)) -- could write an arbitrarily large file and exhaust memory: a denial of service that allocates a byte array proportional to the attacker-chosen file size. The transport now refuses any inbound file larger than a maximum frame size of **536,870,888 bytes (~512 MiB)** before it is read into memory, surfacing a clear terminal error (a `FrameSizeExceededError`, exit 64) rather than allocating proportionally to the attacker-chosen size.

**The value is a chosen memory bound, not a derived platform ceiling.** It once equalled Node's maximum string length (`buffer.constants.MAX_STRING_LENGTH` on 64-bit): the read path `.toString()`d each frame before parsing it (through `parseBoundedJson`), and `Buffer.prototype.toString()` throws above that length, so the string limit was the true hard ceiling and anchoring the cap there avoided rejecting any frame the transport could otherwise decode. That anchor is now void -- the transport carries a frame as raw bytes and never stringifies it (the AEAD envelope and the file-sync message body are both binary; see [Application-layer AEAD](#application-layer-aead) above) -- so a frame larger than the former string limit can be read. The numeric value is retained unchanged, still a reasonable ~512 MiB single-frame memory cap.

This is the static backstop for every frame. The single-pass reply is bounded by a tighter per-exchange cap derived from the exchanged record counts (see [Single-pass per-exchange cap](#single-pass-per-exchange-cap) below), which can only ever tighten this value for that one read, never widen it. As a headroom check against the realistic worst-case legitimate frame: the largest PSI frame is one party's full encrypted set sent as raw elliptic-curve points (~35 bytes per element serialized on the wire; see [PROTOCOL.md](PROTOCOL.md#psi)), now carried with no base64url expansion, so 512 MiB is on the order of 15 million elements -- already more than the single-frame single-pass transport practically ships before the separate single-pass dataset ceiling binds.

**Enforcement.** The bound is enforced at the transport read layer, which is the meaningful enforcement point: the poll loop and rendezvous gate refuse a file whose listed/declared size exceeds the cap before calling `get()`, and -- so a server that under-reports a file's size in its directory listing cannot slip past that check -- each `FileTransportClient` adapter also enforces a hard per-read byte cap. The local-filesystem adapter `fstat`s the open handle and reads exactly that many bytes, closing the append-after-stat TOCTOU; the SFTP adapter streams into a counting sink that aborts the transfer once the running total crosses the cap, buffering at most one stream chunk past it. A binary length check on the AEAD decorator's inbound envelope caps it at the same single value -- the equivalent of the former `.max()` on the base64url `{ enc }` string, now a byte-length check on the raw envelope -- but that is documented defense-in-depth only, not the primary control: by the time the decorator runs, the inner transport has already read the frame, so the dominant allocation has already happened.

The bound is a fixed constant rather than a configurable option: a configurable bound risks an operator raising it high enough to reintroduce the DoS.

### Single-pass per-exchange cap

The single-pass reply (message 2 of the single-pass strategy) carries both parties' encrypted value sets and the sender's index table in one frame, whose legitimate size grows with the dataset. Rather than bound it by the static ~512 MiB cap above, single-pass derives a **per-exchange cap from the exchanged record counts and the agreed key count** -- authenticated session state both parties hold after the terms exchange, never any byte, name, or transport-listed size of the inbound file. So a small exchange's reply is held to a small bound (a hostile transport admin cannot pad it up to the static ceiling) while a large legitimate one is admitted up to a fixed maximum dataset size.

The derivation, its constants, and the deterministic operation order are specified in [PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute). The security-relevant properties here:

- **One shared computation, two enforcement points.** A single exported integer function (`singlePassReplyByteCap`, `packages/core/src/connection/frameSize.ts`) yields the value the receiver enforces at its transport read gate and the value the sender checks its built reply against before sending. The receiver threads it into the file-sync poll loop's `get()` read gate (via `setInboundFrameCap`), where it **replaces** the static `MAX_FRAME_SIZE_BYTES` for that one read rather than layering a second check above a still-static cap; the threaded value is clamped so it can only tighten, never widen, the static backstop.
- **The real ceiling is a memory budget, fixed and non-configurable.** An exchange aborts when either party's `keyCount * recordCount` (the upper bound on its distinct-value count) exceeds `MAX_SINGLE_PASS_CELLS` (3,000,000), a per-party budget set against the heavier party's peak RSS -- the sender at scale, not against what the frame format allows. The value's derivation and its 2M-to-3M revision are specified in [PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) (the single-pass dataset ceiling), which also records that after the churn relief the nearer constraint is the WebRTC per-frame envelope below, not memory. It is a fixed constant, not an operator-configurable option, for the same reason as the frame-size bound: a configurable maximum risks being raised high enough to reintroduce the memory-exhaustion DoS.
- **Transport-aware via per-transport clamps.** File-sync gets the `MAX_SINGLE_PASS_CELLS`-derived bound up to `MAX_FRAME_SIZE_BYTES`; the WebRTC data channel keeps its fixed browser-tab envelope `MAX_WEBRTC_FRAME_BYTES` (256 MiB) at its reassembly read gate (`apps/web/src/psi/boundedReassembly.ts`) and relies on the shared count-budget check, run identically on both transports, plus the decode-time coherence checks below. At the ceiling the derived reply frame is ~240 MiB -- below both envelopes, though the 256 MiB WebRTC envelope is now the nearer one -- so a legitimate single-pass reply the count budget admits is never rejected by a transport clamp; an over-ceiling exchange fails closed with the same actionable guidance -- which does not recommend cascade -- on both transports. The cap is held below the point where the derived reply cap would reach the WebRTC envelope precisely so this stays true; raising it past that point would require reworking the WebRTC reassembly path to fail closed rather than mid-frame.
- **Decoded counts are validated against authenticated state before allocation.** The receiver checks the sender record count packed into the reply against the count the sender carried on the terms exchange, and checks the index-table length the frame actually carries, both before either count drives any allocation. Combined with the existing truncated/oversized-length decode guards, the reply decode stays bounded against malformed or adversarial framing. Each decoded record count additionally carries an explicit `MAX_RECORD_COUNT` (1,000,000,000,000) upper bound at its wire schema (`recordCountField` on the terms-exchange envelope, `packages/core/src/protocolSetup.ts`), so a count above it is a clean `protocol` abort at decode; this keeps the `keyCount * recordCount` gate's product exact (below 2^53) as an executable check rather than an implicit reliance on the schema's `.int()` safe-integer ceiling (see [PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute)).
- **Declared PSI element counts are bounded by a wire-format scan BEFORE deserialization.** Both the single-pass and the cascade decode paths hand a partner-supplied PSI setup / request / response to `@openmined/psi.js` `deserializeBinary`, which allocates one JS byte-slice object -- **measured ~211 bytes** -- per declared repeated `bytes` entry. A minimal ~2-byte wire entry thus amplifies ~105x in memory, so a frame *within* the byte cap yet packed with empty entries (up to ~frameBytes/2 of them) would exhaust memory -- tens of GiB -- **inside `deserializeBinary` itself**, before any post-deserialize count could run. The participant therefore scans the protobuf wire format and counts the declared elements WITHOUT materializing them (`countDeclaredPsiElements`, `packages/core/src/connection/psiElementScan.ts`), rejecting an over-declared frame at the seam in `participant.ts` **before `deserializeBinary` is called**; the scan stops as soon as the count exceeds the ceiling, so an over-declared frame costs O(ceiling), not O(frame). The ceiling is the smaller of two bounds: the authenticated `keyCount * recordCount` upper bound for the relevant party (the sender's set for a setup, the receiver's for a request or the response that re-encrypts it -- `psiElementBounds`, `frameSize.ts`), which reads only authenticated session state so both parties compute it identically and never rejects a legitimate frame; and the absolute `MAX_PSI_DECODE_ELEMENTS` (16,777,215 = `MAX_FRAME_SIZE_BYTES` / 32), which no legitimate ~512 MiB frame of real (~35-byte) elements can exceed and which is what binds a cascade frame whose partner over-declares its record count (the authenticated bound alone is inflatable there, up to `MAX_RECORD_COUNT`). Together they cap the worst-case deserialize allocation at about 3.3 GiB -- the same order as a legitimate near-cap cascade frame of real curve points -- rather than tens of GiB. The scan reads only the stable protobuf wire format (never the library API) but assumes the message structure (the element list is top-level on a Request/Response, one submessage deep on a ServerSetup); an equivalence test pins the scan count against the library's and must be re-verified on an `@openmined/psi.js` upgrade. This is the raw-protobuf analogue of the WebRTC path's BinaryPack structure scan below, and it governs both transports (the web path carries the PSI frame as a `bin` whose SIZE the WebRTC bound caps, but whose inner protobuf this scan is what bounds). A non-Raw server setup carries a single bounded byte blob rather than a repeated element list, so it cannot amplify; it is rejected downstream as a clean protocol abort (it is not the reveal-intersection Raw structure this protocol uses), not by the scan.

As net-new security behavior modifying the channel-hardening frame-size control, this is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

## Directory-listing bound

A companion transport-read control bounds the directory listing itself. This one is independent of the AEAD layer and of file contents: the two parties rendezvous through a shared directory the adversary controls, and the transport's `list()` call enumerates it. Left unbounded, a hostile filedrop/SFTP server admin can write a very large number of files, or files with very long names, and drive the listing to allocate an array and per-entry metadata proportional to the attacker-chosen directory contents - the same memory-exhaustion impact class as the frame-size DoS, reached through a different vector (directory enumeration - entry count and name length - rather than a per-file body read). The transport now refuses a listing that breaches either of two bounds - more than **8,192 directory entries**, or any single entry whose filename exceeds **255 characters** - with the same kind of terminal, typed error as the frame-size bound (a `DirectoryListingBoundsError`, a `UsageError` subclass, exit 64). The refusal fails the exchange rather than silently truncating the listing to the cap and processing it: against a hostile rendezvous directory, refusal is the safer default, since truncation risks dropping a legitimate exchange file an attacker buried under filler.

Both bounds are derived, not round numbers, and both comfortably exceed what a legitimate exchange produces. The **8,192-entry** cap is set from a memory envelope: the worst-case at-cap allocation is the retained entries, each carrying a name of up to the 255-character limit plus per-entry object overhead (~600 bytes), so the listing allocation is bounded to roughly 5 MiB - about two orders of magnitude below the 512 MiB single-frame budget the frame-size bound already governs, so directory enumeration cannot become the dominant memory vector - while still exceeding the order-of-ten files a legitimate exchange produces (the two `-hello.json` files, at most one `-lock.json` or the `-ack.json` markers, transient `-joining.json` sentinels and `temp-*.tmp` writes, and the bounded set of PSI message frames) by roughly three orders of magnitude, with generous headroom for a retain-mode directory that accumulates message and ack files across many sequential exchanges before the operator rotates it (retention is an out-of-band operator responsibility). The **255-character** filename cap is the POSIX `NAME_MAX`, the per-path-component limit every mainstream filesystem enforces (ext4, XFS, APFS, NTFS): the longest filename a legitimate exchange writes - the ack marker of a timestamped message - is on the order of 120 characters, and a name longer than 255 cannot exist on a conformant filesystem, so it is necessarily synthetic (the SFTP protocol imposes no name-length limit, so a hostile server can return such a name in a READDIR response even though its own filesystem could not hold it). Both bounds are fixed constants rather than configurable options, for the same reason as the frame-size bound: a configurable cap risks an operator raising it high enough to reintroduce the DoS.

The bound is enforced at the transport `list()` layer in both adapters - the point before the listing is materialized - not at a higher layer that has already consumed it. The local-filesystem adapter streams entries through `fs.opendir` (which yields entries in bounded batches) rather than `fs.readdir` (which materializes the whole directory into one array, on top of the per-file `stat` fan-out that follows), so the entry-count check stops the walk - capping both the retained array and the stat fan-out - at the bound regardless of how many entries the directory holds. The SFTP adapter does not delegate to ssh2-sftp-client's `list()` (which passes the directory path to `readdir`, accumulating the entire remote listing into one array before returning); it opens a directory handle and reads one server batch at a time through the low-level `opendir`/`readdir`/`close` protocol, applying the checks as entries arrive, so a single READDIR response - itself bounded by the SSH transport's maximum packet size - bounds the allocation to at most the cap plus one batch. Guarding only the local adapter would leave the SFTP path - the one with the explicitly in-scope adversary, the server admin - exposed, so both adapters are bounded.

## Rendezvous symlink refusal

A companion control on the same partner-writable rendezvous directory refuses a symlink planted at an entry, rather than following it. The two parties rendezvous through a shared directory an adversary can write into; in the filedrop / synced-folder case the partner's writes sync into the local operator's own copy of that directory. An entry planted there as a **symlink**, if the transport followed it, would redirect a rendezvous read or write out of the directory to an arbitrary path on the local filesystem the partner does not otherwise control: a followed read could pull a local file (a credential, an unrelated document) into the read path, and -- the sharper impact -- a followed write could truncate or clobber a local file outside the rendezvous directory with exchange bytes. The directory's contents are partner-supplied but the surrounding local filesystem is the trusted operator's, so this is a partner-reachable path-redirection vector distinct in kind from the memory and liveness bounds above (a confidentiality/integrity break, not a resource exhaustion).

The local-filesystem adapter refuses it at the open: every rendezvous read/write primitive -- `get()`, `put()`, and `createExclusive()` -- opens its target through `openNoFollow` (`localFSClient.ts`), which adds `O_NOFOLLOW` to the open flags, so an open whose final path component is a symlink is refused (POSIX `ELOOP`) rather than resolved to the link target. This mirrors the `O_NOFOLLOW` temp-file discipline the credential and result writers use (see [CREDENTIAL_STORAGE.md](CREDENTIAL_STORAGE.md#posix-write-discipline)). `O_NOFOLLOW` is absent on Windows, where it drops from the open mask and leaves the open otherwise unchanged. It refuses only a symlinked final *entry*, not an intermediate directory component, so a legitimately symlinked share root or mount point is still traversed and a rendezvous directory that is itself a mounted symlink is unaffected.

The load-bearing control on the read path is not `O_NOFOLLOW` but the directory listing's own symlink filter: `list()` enumerates through `fs.opendir` and retains only `Dirent.isFile()` entries (see [Directory-listing bound](#directory-listing-bound) above), so a symlink is dropped before its name is ever handed to `get()`, and every `get()` call site -- the poll loop's message reads and the rendezvous gate's hello read alike -- reads only a name the listing surfaced. `O_NOFOLLOW` is the primitive-level backstop there, for a symlink swapped in at a name the listing already committed as a regular file, a time-of-check/time-of-use race the filter alone cannot close. On the write path there is no such filter: `put()` and `createExclusive()` destinations are built from authenticated protocol state at predictable rendezvous names, never from a listing, so `O_NOFOLLOW` is the *primary* defense against a symlink pre-planted at one of those names, not a backstop. `createExclusive()` additionally opens with `O_EXCL`, which already refuses any pre-existing entry -- a planted symlink included -- so its `O_NOFOLLOW` is redundant defense in depth on the same open.

The control is scoped to the local-filesystem adapter. The SFTP adapter resolves every path on the server, where the server admin is already the in-scope adversary with full control of the files it serves (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)), so a server-side symlink grants no capability the threat model does not already cede; the local-filesystem adapter is the one case where the rendezvous directory's contents are adversary-supplied while the surrounding filesystem is the trusted operator's.

## Per-operation liveness bounds

A third transport control bounds these operations for liveness rather than memory. It is the **per-operation fast-fail layer** - covering both the reads and, as of the write-path bounds described with them below, the always-executed write/stat/delete operations - beneath the whole-exchange budget described next (which is the universal backstop over every transport await). The size bounds above stop a hostile directory or file from exhausting memory, but they do not stop a hostile server admin from hanging the operation itself. Every SFTP read awaits a callback the server drives, so the server can make one never terminate: a `list()` can return valid but empty (`count = 0`) non-EOF READDIR responses forever (advancing neither size bound, since no entry accumulates and the end-of-directory status never comes, so the batch loop recurses without end) or simply never invoke a readdir/close callback; a `get()` can hold the read stream open and withhold data, or trickle under-cap bytes without ever ending it, so the transfer never completes; a `createExclusive()` can withhold its open or close callback. Because `list()` and `get()` run on the poll loop - which awaits them with no per-call timeout - and `createExclusive()` drives the rendezvous lock path, any of these is a liveness / non-termination denial of service: the exchange stalls forever (and a directory or file handle opened before the stall is leaked) instead of failing. Each read is now bounded by the mechanism its shape allows and surfaces a single terminal, typed `TransportOperationStalledError` - a `UsageError` subclass, exit 64, the liveness sibling of the memory-bound `DirectoryListingBoundsError` and `FrameSizeExceededError` - so the consumers that await these reads, the poll loop and the rendezvous control-file gate (`readControlFileWithGate`, which reads the peer hello over `get()`) alike, treat it as terminal and fail the exchange rather than retrying into the same hang. The gate keys this on the typed `UsageError` rather than a single error class, so a stalled hello read is terminal there exactly as an over-cap `FrameSizeExceededError` is - without it, a server that stalls the hello `get()` would be retried at the polling cadence until the one-hour peer budget instead of failing in a minute. The streamed `list()` carries a **16,384 readdir round-trip** cap for the empty-batch flood plus a **60-second wall-clock deadline** for the withheld-callback case, and closes the open directory handle on the bounded-failure path. The capped `get()` bounds the **60-second idle gap between chunks** (reset on each chunk), not the total transfer, so a legitimately large but slow-and-progressing read is never failed while a withheld or stalled one is. `createExclusive()` and the rarely used uncapped `get()` - neither of which has a progress loop - carry the **60-second whole-operation deadline**. The always-executed write/stat/delete operations are bounded by this same layer, each in the mode its shape allows. The metadata ops `rename()`, `delete()`, and `exists()` - each a single server round-trip with no payload - carry the same **60-second whole-operation deadline** as `createExclusive()`, with the same negligible false-fail profile, since a metadata round-trip completes in well under a second on any honest server. `put()` instead carries a **60-second progress idle window**, reset on each uploaded chunk: a tight flat deadline is wrong for `put` specifically, because a legitimately large ciphertext upload over a slow link can exceed it while still progressing, so - exactly as the capped `get()` bounds its idle gap rather than its total transfer - `put` bounds the gap between upload-progress chunks. The payload is streamed in bounded chunks so a withheld write acknowledgement stalls the source and trips the window while a slow-but-progressing one keeps resetting it; this uses ssh2-sftp-client's stream interface rather than driving the raw `SFTPWrapper`, so it adds no new internal-API coupling. The bounded source accepts either a single `Buffer` or the message send path's `[header, payload]` chunk list (streamed part-by-part, never concatenated in memory -- see [FILE_SYNC.md](FILE_SYNC.md)), so the same window AND retry cover the largest, hottest binary frame; a chunk list is re-iterable, so the source is rebuilt per retry attempt exactly as it is from a `Buffer`.

The bounds are derived, not round numbers, and all comfortably exceed any legitimate operation. The **16,384 round-trip** cap is twice the 8,192-entry size cap, so the two move together: a compliant server sends at least one name per non-EOF READDIR response (an empty non-EOF response is not protocol-conformant - a server out of names sends end-of-directory instead), so a legitimate listing makes at most 8,192 batches before the entry-count bound would already refuse it, and only in the pathological-but-legal case of one entry per batch; an honest server packs many entries per packet and finishes a normal rendezvous directory in a single batch, so the cap only ever fails a progress-free flood. The **60-second** budget is a single coarse "the server has gone silent" threshold, applied as a whole-operation deadline for `list()`, `createExclusive()`, the metadata write/stat/delete ops `rename()`/`delete()`/`exists()`, and uncapped `get()`, and as a progress-reset idle window for the capped streaming `get()` and for `put()`. It sits well above any legitimate operation - a normal listing, a lock-file create, and each chunk of a healthy transfer all complete in well under a second - at roughly twice this project's 30-second per-attempt connect bound (`serverConnectTimeoutMs`, applied as ssh2's `readyTimeout` even when the operator leaves it unset; ssh2's own default `readyTimeout` is 20 seconds), so a transiently slow but live server is not cut off, yet more than an order of magnitude below the one-hour (3,600-second) peer-inactivity budget, so a withheld response fails the exchange in a minute rather than after an hour; applied as an idle window it never rejects a slow-but-progressing large transfer, only one that stops sending. All bounds are fixed constants, not configurable, for the same reason as the other bounds: a configurable budget risks an operator raising it high enough to reintroduce the denial of service. These per-operation bounds are on the SFTP adapter, whose every call crosses the network to the in-scope server admin; they cover its reads and its write/stat/delete operations alike. They do not cover the local-filesystem adapter (an earlier framing held its reads to face only a trusted kernel, `fs.opendir`/`fs.stat`, that exhibits none of these failure modes - but a stalled NFS/CIFS hard mount breaks that premise). That remaining gap is closed not here but by the whole-exchange budget described next.

## Whole-exchange budget

A fourth liveness control is the **whole-exchange budget**: the universal backstop beneath the per-operation bounds above, and the *only* per-operation-free liveness bound for the local-filesystem adapter. The per-operation bounds fast-fail a stalled SFTP read or write in 60 seconds; the budget is the layer they were added *beneath*, not in place of. The always-executed critical-path write/stat/delete operations - `put` (every message and every hello/sentinel write), `rename` (every durable publish), `delete` (message consumption and rendezvous cleanup), and `exists` (the lock-path race check) - now each carry their own 60-second per-operation bound (above), but before those bounds existed this budget was all that stood between a hostile or dead server that withheld any of their callbacks and an exchange hung for an hour: `synchronize()` and `send()` awaited the call directly so it never returned, and the poll loop's reschedule sits in a `finally` a hung await never reaches, so the poller stopped silently with no error. The peer-inactivity budget (`peerTimeoutMs`, default one hour) was checked only between loop iterations, never over an in-flight await, so a single withheld callback escaped it entirely. The connection now races **every** transport await - reads, writes, stat, delete, and the local-filesystem path alike - against that budget at the single consumer seam they all flow through, surfacing the same terminal, typed `TransportOperationStalledError` on expiry. Because it wraps the transport interface rather than any one operation, it is op-agnostic (it covers operations not individually enumerated and any added later) and adapter-agnostic (it bounds the SFTP adapter and the local-filesystem `LocalFSClient` identically, closing the stalled-mount gap). It bounds a stalled await against a *fresh* budget per await (silence from the peer), not the total exchange duration, so it never caps a healthy long-running exchange; the budget is the same single coarse knob an operator already tunes, and it stays deliberately coarse as the backstop: the tight, false-fail-safe per-operation bound a slow `put` needs is the progress idle window above, not a flat budget timeout, which is exactly why the budget itself can remain one coarse knob rather than being split per operation. The capped `get()` slow-drip (under-cap bytes trickled forever, which resets the per-chunk idle window and so never trips the 60-second read bound) is caught here too, since total elapsed eventually crosses the budget - as is the symmetric `put` slow-drip, whose progress idle window the budget likewise backstops.

## Send-window liveness guard

A fifth liveness control makes the four bounds above effective in a window none of them covered on its own. Every liveness timer among them - the per-operation SFTP deadlines and the whole-exchange budget (and the connect-probe bounds below) - is `.unref()`'d, deliberately, so a completed or cancelled exchange exits promptly rather than lingering until a safety timer expires. The consequence is a subtlety the fourth control's "races **every** transport await" glosses: an `.unref()`'d timer can only *fire* while some **other, ref'd** handle is holding the Node event loop open. A parked `receive()` supplies one - `QueuedMessageConnection` (`@psilink/core`) arms a **ref'd** inactivity timer (the same `peerTimeoutMs` budget) while a receive waits on an empty queue - so a peer that goes silent mid-read is caught and the unref'd whole-exchange budget behind it gets to fire. The sender's encrypt-then-send window parks no `receive()`: it builds and encrypts the next frame, then awaits the outbound `send()` (a `put` then a `rename`). A connection dropped in exactly that window - the motivating incident was an SFTP server dropping the link in reaction to an over-aggressive poll cadence, but an idle timeout or a network blip is identical - leaves the in-flight write's callback unfired; every timer that would reject it is `.unref()`'d; and with no ref'd handle left the event loop drains and the process exits **0**, mid-log, indistinguishable from a crash - the awaited `send()` never returns, so no `catch`, `finally`, or teardown line runs.

The guard is one **ref'd** timer, armed in `QueuedMessageConnection.send()` across the in-flight transport hand-off (`sendWithLiveness`) and cleared the instant it settles. Being ref'd it holds the loop open, which lets a lower, faster `.unref()`'d per-operation deadline (the 60-second SFTP `put` idle window) or the whole-exchange budget fire first and reject the write; that rejection - a `TransportOperationStalledError` naming the server's withheld acknowledgement - is re-tagged by `send()` as a `transport` `ConnectionError` (its message and cause preserved) so the operator sees the real cause. Absent any per-operation bound (a transport that has none), the guard is itself the transport-agnostic backstop: on expiry (the connection's `inactivityTimeoutMs`, the peer budget) it rejects the send with a `transport` `ConnectionError` that names the lost connection, so the awaited call returns instead of orphaning. Either way a mid-exchange drop in the send window now terminates **non-zero** (a `transport` `ConnectionError` maps to exit 69 / `EX_UNAVAILABLE`) rather than a silent exit 0. It lives in core, not the SFTP adapter, so it covers every transport (`sftp`, `filedrop`, and the web WebRTC channel) at the one `send()` seam they share. Every terminal path (`fail`/`finish`/`close`) *rejects* an outstanding send -- not merely cancels its timer -- as well as clearing it on the hand-off's own settlement; this is load-bearing, since a terminal transition (an inbound-overflow `fail`, a peer half-close via `finish`, or a signal-driven `close`) can race an in-flight hand-off, and a hand-off orphaned in exactly that window would, if the guard were only cancelled, leave the awaited `send()` hanging forever -- the same silent stall, relocated. Rejecting it there (as the terminal error, or a cancelled `closed` on a deliberate close, the send-side twin of the parked-receive rejection) makes the "terminates rather than orphans" guarantee hold in the racing case too, and keeps the same "never hold a healthy process open at teardown" property the `.unref()`'d timers have -- reached here by settling every guard rather than by `unref`, because this one timer must, uniquely, hold the loop open just long enough to reject the orphaned write, then release it. Its message carries no `inactivityHint`: that receive-side guidance ("the peer... has sent nothing since") misdescribes a stalled outbound write.

## Connect-probe bound

A sixth liveness control bounds the connect probe itself, the one transport call deliberately outside the whole-exchange budget's seam. `connect()` runs before the exchange begins and is wrapped by neither the per-operation bounds nor the whole-exchange budget - it passes through `boundTransport` unwrapped - so each adapter bounds its own connect attempt instead: the SFTP adapter by ssh2's `readyTimeout`, which tears down the socket on expiry and strands nothing (an unresponsive SFTP connect is retried, so its total caller-visible latency stacks to roughly `maxReconnectAttempts + 1` such per-attempt windows - bounded wait, not accumulating resource, since each expiry strands nothing - unlike the local-filesystem timeout below, which is terminal at one window), and the local-filesystem adapter by a per-attempt `withTimeout` deadline around its `fs.access` reachability probe. On the local-filesystem adapter a stalled NFS/CIFS hard mount turns that probe into the same liveness hazard the post-connect bounds address, with a sharper resource cost: `fs.access` blocks a libuv thread-pool worker (not the event loop), and nothing in-process can cancel an already-dispatched blocking syscall - `fs.access` does not honor an `AbortSignal`, and libuv's `uv_cancel` only removes still-queued work, never work a pool thread is already executing - so the worker stays pinned until the OS releases the syscall, minutes on a hard mount. The per-attempt timeout fires on the event loop and fails the attempt, but retrying it (the prior behavior) launched a fresh probe each time, so under the default `maxReconnectAttempts` of 3 up to four such probes could stack, exhausting the default four-thread pool and starving every other `fs`/DNS/crypto operation in the process - a process-wide denial of service induced by a single unreachable mount. The connect now treats a per-attempt timeout as terminal: it fails fast after one timeout window, surfacing a `TimeoutError` (which extends `Error`, not `UsageError`, so it classifies exit 69 / `EX_UNAVAILABLE` like any transport-unavailable failure), rather than dispatching further probes; a fast-returning transient error - `EACCES`/`ENOENT` while a share or its permissions are still settling - still retries under `max_reconnect_attempts`. For the local-filesystem adapter that budget governs only this initial connect: `filedrop` holds no persistent session, so it has no mid-exchange reconnection. The SFTP adapter is the exception - it holds one long-lived session that a server can drop mid-exchange - so the same budget also bounds each of its mid-exchange re-dial bursts (see [SFTP mid-exchange session recovery](#sftp-mid-exchange-session-recovery)). This bounds concurrent stalled workers to one and the caller-visible latency to roughly one `serverConnectTimeoutMs` window; it does not bound the lifetime of that one worker, which only the OS reclaims, because no in-process mechanism can free a thread wedged in a single blocking syscall - only a killable worker thread or child process could, which is disproportionate for a connect pre-check.

The per-attempt windows above bound each connect attempt, but the *count* of attempts had no ceiling: `max_reconnect_attempts` was validated only as a non-negative integer (up to `Number.MAX_SAFE_INTEGER`). Against an endpoint that refuses fast - `ECONNREFUSED` on `sftp`, `EACCES`/`ENOENT` on `filedrop`, exactly the fast transients the retry budget exists to ride out - the retry loop spaces attempts with a fixed one-second inter-attempt delay and the fast-fail attempts themselves are near-instant, so the wall clock is essentially the delay total (the `maxReconnectAttempts` delays across the `maxReconnectAttempts + 1` attempts above) - about that many seconds, a linear self-inflicted hang. The count is therefore capped at `MAX_RECONNECT_ATTEMPTS = 604800` (defined in `packages/core/src/config/connection.ts`), derived as the CLI's seven-day timeout ceiling `MAX_TIMEOUT_SECONDS` divided by the one-second delay (`604800 s / 1 s = 604800`): the largest count whose fast-fail delay total stays within the same seven days the duration flags already cap. A value past it is rejected with a flag-named `UsageError` (exit 64) at both validation boundaries that already agree on this field - the connection schema's `.max()` and the CLI's `nonNegativeIntFlag` parse guard, which imports the constant - so an over-ceiling value is refused whether it arrives from `psilink.yaml` or `--max-reconnect-attempts`. This bounds a proxy: the count equals wall clock only at the one-second floor (the fast-fail case), so it does not tightly bound a slow-but-answering endpoint, whose attempts each run up to `serverConnectTimeoutMs` and are already bounded per attempt by it; a direct wall-clock deadline on the whole connect phase is the stronger control left for if that case ever proves to matter. This is a usability/self-DoS sanity bound, not a cross-party control - the operator only hangs their own command - in the same class as the `MAX_TIMEOUT_SECONDS` duration-flag cap.

## Consumer-side terminal-error rule

These transport bounds share one consumer-side rule that ties them together, stated here because the bounds above each describe their enforcement in isolation. Every one surfaces as a `UsageError` subclass - the memory bounds as `FrameSizeExceededError` and `DirectoryListingBoundsError`, the liveness bounds as `TransportOperationStalledError` - and any consumer that awaits a transport call must treat a `UsageError` as terminal: it propagates the rejection and never retries it, swallows it, or proceeds as if the call had succeeded. This binds the read consumers (a `list()`/`get()`/`createExclusive()` in the poll loop or the rendezvous gate) and, now that the write/stat/delete ops carry their own per-operation bounds, the write consumers too - the `put`/`rename` publish in `send()`, the rendezvous lock-path `createExclusive`/`exists`, the consume-`delete` that signals a message consumed, and the retain-mode ack-write (`writeAck`'s `put`/`rename`) that signals it on a transport that never deletes. Retrying loops straight back into the hang or the over-allocation the bound exists to prevent, and swallowing-then-proceeding turns a stalled consume into a re-emitted duplicate - a swallowed bound is no bound - so the only effective response is to fail the exchange, which is why the poll loop stops on a `UsageError` (including from the consume-`delete`, which rethrows it rather than swallowing it as it does a transient delete failure), the rendezvous control-file gate (`readControlFileWithGate`) rethrows it, and the `send()`/joiner write paths propagate it. The terminal behavior keys off the `UsageError` base class rather than each subclass, so a future bound added to the family inherits it. This consumer rule is what makes the transport-layer bounds effective end to end. The consumers are pinned by behavioral tests in `packages/core/test/fileSyncConnection.test.ts` that drive each with a `UsageError` from a transport call - a stalled read in the poll loop and the gate, a stalled consume-`delete` in the poll loop, and a stalled retain-mode ack-write in the poll loop - and assert it is surfaced once and propagated (the exchange fails), never retried at the poll/gate cadence and never swallowed into a duplicate delivery. A new transport-call consumer must uphold the same rule; it is not enforced automatically, so adding one is a change to review against this rule.

## Slow-operation warning

Distinct from both controls is a non-fatal **slow-operation warning**, which is observability, not a security control. At a fixed, generous elapsed-time threshold (30 seconds, below the 60-second read fast-fail) the SFTP adapter logs one warning naming the operation, the elapsed time, and - where a cheap progress signal already exists - the observed progress (bytes-so-far and rate for a `get`, entries-so-far for a `list`, the payload size for a `put`; elapsed-only for the atomic operations), then lets the operation continue unchanged. It needs no duration estimate: a slow-but-honest transfer and a deliberately slow or withholding server are observationally identical (intent is not on the wire), so a false warning is cheap and the line reports observed signal for a human to judge. It does nothing on a headless run with no human watching - the whole-exchange budget defends that run - and it stays entirely outside the terminal-error paths, so it can never affect correctness or the liveness gate. It introduces no new required configuration.

## SFTP session heartbeat and TCP keepalive

Distinct again, and opposite in direction to the bounds above: those cap how long a **hostile** server can make an operation hang; this keeps a **friendly** server from dropping a session that has gone legitimately quiet. An SFTP server enforcing a strict idle timeout closes the control connection when no SFTP command has arrived within its window - Azure Blob SFTP's window is a **fixed two minutes**, not operator-adjustable. A single-pass PSI round spends long stretches with no file traffic on the side that is computing rather than polling (the receiver polls for the reply, so its session stays warm; the sender computes the reply and issues no SFTP command meanwhile), and on weak hardware (old agency laptops) that masking can run for minutes even on the native backend (see [PROTOCOL.md](PROTOCOL.md)). Before the masking moved off the event-loop-owning thread (board item 208035324, the same item as this heartbeat), a multi-minute round blocked the event loop outright, so no timer could fire during it; with the masking now in a worker thread the loop is free, and this heartbeat is what fills the gap.

The heartbeat is a self-rescheduling timer on the SFTP adapter that issues a real no-op SFTP command - `realPath(".")`, the cheapest single REALPATH round-trip (a path the server always resolves) - once the session has been idle for the interval. It must be a real **SFTP** command, not an SSH-transport or TCP keepalive: a server keys idleness on the last SFTP protocol **request**, so transport-level traffic does not reset its timer. The interval is **60,000 ms (60 s)**, half of the tightest idle timeout it must survive (Azure's fixed two minutes), so a beat always lands with a full interval of margin even if one is delayed; the idle window is measured from the last observed activity, so a beat never fires more than one interval after the session actually went quiet. It is a **fixed constant, not operator-configurable**, for the same reason as the liveness bounds above - a knob set too high silently stops defeating the timeout, with no upside a fixed sub-timeout value lacks.

A beat is suppressed while any adapter operation is in flight (real traffic is already keeping the session alive) and while a previous beat has not settled, and only fires after a full interval of genuine idleness. Overlap itself is not the hazard that suppression covers: two operations in flight on one client at once is unsafe only in the narrow respect below. Measured against a real server, overlap on a **healthy** session is safe: over the operation pairs driven, the beat's own among them, each member returned its own correct result with no cross-talk and no mis-routed error, and a non-fatal failure of one member left the other undisturbed. What overlapping operations do cross is the **session-loss rejection**, which the library hands to the operation issued LAST while suppressing the earlier one's - so issuance order decides which of two concurrent operations takes which path out of a loss, and the two paths do not have the same outcome. That crossing is not the beat's to close: the adapter issues concurrent operations of its own with no suppression of any kind - a `send()` resuming from the protocol continuation runs its `put`/`rename`/`safeDelete` alongside the poll cycle's `list`/`get`/`delete`, and core's connection cleanup and rendezvous orphan sweeps fan `safeDelete` out with `Promise.all` - so the suppression covers the beat and nothing else and is not a control over concurrent operations generally. Leaving them unsuppressed is the posture rather than a gap for the beat's suppression to grow into, and what carries them through a session loss is the recovery re-dial's transport retirement: an operation outstanding when a CONCURRENT operation's recovery runs is settled by the transport close that retirement waits out -- and, against a partner that withholds it, drives itself -- rather than being left for its own per-operation liveness deadline. A drop that tears several operations at once therefore costs the exchange one tear, not one deadline per operation, and every torn operation inside the recovery chokepoint is re-issued with its own correct result. What it is still worth is narrower: it keeps the beat off a session that already has an operation on it, so the beat - whose own outcome is deliberately swallowed - never takes a session-loss rejection away from a real operation in flight beside it. The one residual overlap - a real operation that begins in the same event-loop turn a just-issued beat is still on the wire - is covered by the healthy-session measurement, and at a loss the rejection reaches that operation rather than the beat, which was issued first. (The library mechanism, the measured numbers, and the pairs and states the runs did not cover are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md), re-verified there on any ssh2 / ssh2-sftp-client upgrade.) The `realPath` itself is bounded by the same 60-second per-operation deadline as the metadata ops, so a dead or hostile session cannot leave a beat hanging; a beat's outcome is swallowed (logged at trace), never surfaced to the exchange, so a failing keepalive can never itself fail a round. The heartbeat timer is cleared on **every** terminal path - session `end()` and the fatal-'error' guard (a dead channel needs no keepalive) - and is `.unref()`'d, preserving the deliberately-unref'd SFTP-liveness-timer teardown contract (board item 208026498) so it never holds a winding-down process open.

Beneath the heartbeat, the adapter enables kernel **TCP keepalive** on the underlying socket (`net.Socket.setKeepAlive(true, 30_000)`, reached through the ssh2 Client's `_sock` since ssh2 exposes `setNoDelay` but not `setKeepAlive`, the same access-past-the-public-API premise the fatal-'error' guard rests on). This is a transport-layer backstop, **not** a substitute for the heartbeat: it keeps NAT/firewall flow state warm and lets the kernel detect a silently dead peer, but because it rides below the SFTP protocol it does not reset the server's SFTP-command idle timer. The **30,000 ms (30 s)** initial delay (Node sets only `TCP_KEEPIDLE`; the probe interval and count keep their OS defaults) sits below common NAT idle windows and below the application heartbeat interval, so probes keep the flow alive between beats. Both settings are re-applied on every reconnect (a fresh socket per attempt) and both are guarded and non-fatal, exactly like the existing `setNoDelay`: an upstream that relocates the socket degrades to no-keepalive, never to a failed connect.

## SFTP mid-exchange session recovery

The heartbeat above keeps a *friendly* server from dropping a quiet session, but some servers enforce a **max-session or idle cap the operator cannot change** (observed at ~10 minutes) and drop the one long-lived session regardless. Under the persistent-single-session model this adapter runs by default, that drop would otherwise be terminal: the next operation fails and the exchange aborts. Mid-exchange session recovery is the robustness floor beneath that model: on a **clean session loss** the adapter transparently re-dials and re-issues the operation before failing terminally. It is adapter-local - core's rendezvous, `fileSyncConnection`, and `send()` are unchanged. The `connection_per_poll` mode is a separate thing that composes with it, releasing the session at the poll loop's idle boundaries rather than holding one for the whole exchange; when that mode's session exists, and the idle stretches one still spans, are in [FILE_SYNC.md](FILE_SYNC.md#session-lifetime-across-an-idle-boundary). What is counted, capped, exempt and bounded is this section's, and the tables below carry it: a new bound, trigger or exemption appends a ROW rather than a clause to a paragraph.

See [sftp-adapter-state-machine.md](../notes/sftp-adapter-state-machine.md) for the state-machine model these rows project from -- what a session, an idle boundary and an operation each are, and the design decisions behind the accounting.

### What is re-dialed, and what stays terminal

**Trigger, by post-state not error text.** Recovery re-dials only on a clean loss, read off the connection state after an operation rejects: ssh2-sftp-client clears its internal `sftp` session property on a clean close/end (both its per-operation temp listeners and its global `'close'`/`'end'` listener null it), so a cleared property is the reliable "the session dropped" signal. It unifies the adapter's own `!sftp` throw in `list()`/`createExclusive()` with ssh2-sftp-client's `ERR_NOT_CONNECTED` ("No SFTP connection available") on a high-level `get`/`put`/`delete`/`rename`/`exists` issued against a session already gone, and with the `Unexpected end event` those same per-operation listeners deliver when a drop tears one IN FLIGHT. These stay **terminal, never re-dialed**: a fatal SFTP protocol error (the wrapper is destroyed and cannot recover -- the `fatalSftpError` guard); any liveness **stall** (`TransportOperationStalledError`), both over a transport still live and on a CLEARED session whatever the transport reads, since re-dialing on a timeout would hand a withholding server a free liveness reset -- the one stall that IS a trigger is the withheld-close loss below, a session still set over an ENDED transport; the memory bounds (`FrameSizeExceededError`, `DirectoryListingBoundsError`); and a host-key mismatch on the re-dial itself.

**A session still set over an ENDED transport is a loss, not a live session.** The session property alone does not settle the reading, because one partner class leaves it set over a session that is gone: a server that drops the SFTP session and then withholds its connection close leaves the transport half-open -- this side's write half ended, and no `'close'` for ssh2-sftp-client's global listener to clear the property from -- so the operation on the wire cannot complete and rides the per-operation deadline to a terminal stall. The trigger therefore reads the TRANSPORT alongside the property: a session still set over a transport either half of which has ended is the loss it is, whatever the operation rejected with, and is recovered exactly as a clean loss is -- one re-dial, one re-issue, counted in `reconnects` and its mid-exchange sub-count, and warned and charged on the terms its own row in the trigger table below states. Reaching that re-dial means clearing the dead session first, which the recovery does by forcing the ended transport closed -- the mechanism the `connection_per_poll` release uses, with its own seam resolution and none of its accounting, so a drop is never reported as an idle release. Every way that forced close can fail (a relocated seam, a destroy that raises, a session that does not clear, a transport that does not close) warns naming what broke and the upgrade checklist, then leaves the operation to fail with the loss it already had -- the outcome it had before recovery reached it at all. The internals and the measurements are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md).

**The two operation routes are torn a full event apart, and at the pinned versions both read as the clean loss they are.** A RAW-WRAPPER operation (`list`, `createExclusive`, which drive the `SFTPWrapper` directly) is failed by ssh2, which fails outstanding channel requests ONLY from the socket's `'close'` handler -- the socket's `'end'` emits and cleans the protocol up but leaves them outstanding -- and does so after its own `emit('close')` has already run, by which point both ssh2-sftp-client listeners that emit reaches (the per-operation temporary `closeListener` and the constructor's global one) have cleared the `sftp` property; such an operation therefore reaches recovery with the whole sequence run. One of ssh2-sftp-client's own HIGH-LEVEL operations (`get`, `put`, `delete`, `rename`, `exists`) does not wait for any of that: its per-operation listeners settle the operation, and clear the same property, from the `Client`'s `'end'`, so it reads as the clean loss it is a full event earlier, with the transport's `'close'` still owed. Which side of the `'close'` an operation lands on is a property of the route rather than of the drop, and a route can still settle late -- the chunked `put`'s bounded source is a further hop, which can carry its settlement past the `'close'`. A tear of a counted outstanding operation is the partner's doing or the terminal close's, never a boundary's, and this ordering settles what the loss READS as, never what a dial may safely follow. The terminal "not a loss" readings -- the adapter's own stall deadline over a session and a transport both still live, and a stall on a CLEARED session whatever the transport reads -- stay reachable by both routes; what the idle boundary's own precondition closes is the boundary case, which rests on the ordering not at all.

**A CLEARED session can still leave a transport a re-dial must not be issued over.** A dial issued while the `'close'` is owed is failed by ssh2-sftp-client's own connect-time listeners -- they fail a dial on ANY lifecycle event that reaches them mid-handshake -- while the handshake it started keeps running, unowned, at the server, whose later events fail the next dial in turn. So the re-dial RETIRES the transport whether or not the session property is still set: the same forced close as above, then a wait for the `'close'` to land, and only then the dial. Nothing on the socket separates the two states -- a torn high-level operation rejects over a socket that already reads destroyed with both halves ended, which is what it reads once the whole sequence has run too -- so the reading comes from the `Client`'s own `'end'`/`'close'` pair, watched by one listener pair attached once per adapter. Where nothing is owed the retirement drives nothing and returns, so the raw-wrapper class pays no wait for it. A transport that cannot be retired refuses the dial and leaves the operation the loss it already had, warning for its own cause, on the same terms as the withheld-close paragraph above; a `Client` that exposes no `on()` to watch leaves no reading to take at all, which the retirement treats as *cannot tell* rather than as *nothing owed* -- the flag's unwritten default is the same value a delivered sequence leaves, so the two are separated by whether the watch attached. It warns for the lost reading, naming the seam and the upgrade checklist, and retires the transport rather than dialing into a window it cannot see: a drop that would have recovered still recovers, at the cost of the forced close's bound on a transport whose `'close'` had already landed. Where the same relocation took the forced close's own seams with it there is nothing left to retire, and the dial is refused on the terms above. The ordering premise, the measurements behind it and their bound, and what a version bump must re-verify are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md).

**Re-dial goes through `connect()`, never a bare `client.connect()`.** The adapter retains the full original connect options (including the pinned host key and stored credentials) and re-invokes its own `connect()`, so the re-dial re-runs the entire post-connect sequence on the fresh wrapper: it re-attaches the guarded fatal-`'error'` listener (a listener-free wrapper would turn the next malformed packet into a process crash - see the crash-safety control below), clears `fatalSftpError`, re-runs the enforcing fail-closed host-key verifier that rides the options, re-verifies the raw `sftp` methods, advances the heartbeat epoch, and re-applies `setNoDelay`/keepalive. There is **no re-prompt**: the pinned fingerprint and credentials are reused. A host-key mismatch on the re-dial is terminal for free via `connect()`'s existing "Host denied" retry predicate. (Residual: a mid-exchange host-key mismatch surfaces as a raw transport error rather than the security-kind `ConnectionError` that `fileSyncConnection.open()`'s catch produces via `hostKeyVerifier.mismatchDetails()` on the initial connect - the exchange still fails closed, but the error kind is coarser on the re-dial path.)

### What each bound protects

**One recovery round per operation invocation.** Re-dial once (that one `connect()` internally makes up to `max_reconnect_attempts` dial attempts), re-issue once; if the re-issued operation also hits a clean loss it rejects terminally rather than looping. The whole operation-plus-re-dial is enclosed by `boundTransport`'s per-operation `peerTimeoutMs` budget in core (a `Promise.race`), so no bespoke total-time timer is added here. Core's three tight teardown budgets - the terminal-frame drain (`min(TERMINAL_FRAME_DRAIN_TIMEOUT_MS, peerTimeoutMs)`), the abort-marker write (`ABORT_MARKER_WRITE_BUDGET_MS`, ~5 s), and the connection's own final close (`min(CONNECTION_CLOSE_TIMEOUT_MS, peerTimeoutMs)`, the last of the three to run, and short enough to abandon core's wait on a teardown re-dial still in flight) - are `Promise.race` bounds of the same kind, so a re-dial during teardown cannot overrun them; and `end()` latches a `closing` flag that suppresses any further re-dial once teardown has begun.

### What the accounting counts

**The accounting unit is one lost session, not one interrupted operation.** A session is a GENERATION: established by a dial, ended by exactly one recorded cause, and never replaced while it is still live. A drop tears every operation the adapter has on the wire, so a concurrent fan of them -- a `send()` resuming from the protocol continuation alongside the poll cycle's own operations, or the rendezvous sweep in core fanning the rejecting `delete` out -- all enter recovery together over the one session they lost. The transition queue serializes their re-dial requests: the first to reach the front finds that generation still live and charges it, the rest find it already ended and charge nothing, and the drop costs ONE handshake whichever of them dialed. The charge is made by the transition that ENDS a generation and never by an operation arm that merely observes one gone, so this side's own ends -- the `connection_per_poll` idle release, the connection's terminal close, a fatal SFTP protocol error -- are each charged where they happen, and a generation still live when a recovery re-dial reaches its critical section is one the partner took. An accounting per arm would spend an operator's configured budget at N times the configured rate and report one survived drop as N; an accounting keyed to a high-water mark over the generations already charged would do the opposite and report two genuine losses of two sessions as one.

**The cumulative budget bounds sessions LOST.** It is read and spent in the same critical section that charges the loss, under the transition lock, so no further drop can land between the read and the charge. What that means for an operator: a drop whose recovery re-dial fails, and a drop the exhausted budget refuses, each spend their unit exactly as a recovered drop does - which is what the exhaustion message already says (`has already been transparently re-dialed the maximum N times`). The count is strictly cumulative and never resets on a successful operation, because a server enforcing a session-lifetime cap makes progress every cycle and a reset-on-progress budget would never bound it. Once it is spent the next loss raises a terminal `UsageError` naming the exhausted budget and its two remedies instead of re-dialing. Measured against a partner dropping every session it opens: a fan of 40 concurrent deletes bought no more handshakes than the budget allowed, the arms draining the transition queue behind the one dial.

**Two exemptions keep that cap from cutting where it should not**, each for a measured reason the table's row cannot carry. `connection_per_poll` is exempt in every phase because the rendezvous that precedes its loop holds one un-heartbeated session across its wait for the partner, so a server cap cuts it there on a wait long enough to outlive the cap; the exemption is what carries the rendezvous across such a drop (measured: the rendezvous re-dials as often as the cap cuts it and the exchange completes, where the held-session default in the same scenario exhausts the budget and fails terminally). A teardown re-dial - the authenticated abort-marker write and the terminal-frame drain, marked by core's `beginTeardown()` signal at `close()` and at the marker write itself - is exempt so the fast-fail marker still lands when the budget is exactly what was just exhausted.

### Re-issuing an operation

**Per-operation idempotency, applied only on the re-issue.** The relaxations below never touch the first attempt, so genuine lock-conflict and absence detection are unchanged. `list`/`get`/`exists`/`put` re-issue verbatim (`put`'s `flags:"w"` truncate-overwrite is effect-idempotent, and its bounded source is rebuilt from the retained Buffer/chunk list; a one-shot stream source is never re-issued). `delete` maps a source-absent re-issue (`SSH_FX_NO_SUCH_FILE`) to success, since a pre-drop delete that landed reports the source gone. `rename` treats a re-issue whose source is gone (or a code-4 dest-exists) as success when `exists(dest)` confirms the destination, sound because every rename destination is self-prefixed and so unambiguously this party's own landed attempt. The CONVERSE does not hold and is not relied on: an ABSENT destination is not evidence the rename failed. In delete mode the partner's consume-delete removes exactly this party's own self-prefixed publish, so a rename that landed durably and was consumed inside the recovery window reports the state a rename that never landed reports -- source gone, destination absent, `SSH_FX_NO_SUCH_FILE` -- and no reading the adapter can take separates them (see "A publish the transport cannot settle" below). `createExclusive` resolves its own normalized `EEXIST` on re-issue as success, reusing the existing code-11 / code-4-via-`exists()` normalization; the narrow rendezvous-phase "two winners" race this admits is documented at the call site and verified benign (roles commit from hello-filename order before the lock, which only gates eager cleanup).

**A publish the transport cannot settle is rejected as undetermined, never as a determined non-delivery.** One state survives the recovery above unresolved. A `rename` torn after its filesystem work landed at the server but before its reply was written is a durable publish the sender never learned of; if the partner consumes it inside the sender's recovery window -- in delete mode, the consume-delete of a message is the partner's normal receipt path -- the re-issue then reports `SSH_FX_NO_SUCH_FILE` over an absent destination, which is exactly what a publish that never landed reports. A source still on the server is the one signal that does separate them, and the adapter probes for it: a re-issue whose source survived is a publish that never landed, classified determinately. Once the source is gone the two converge, and measurement found no adapter-observable signal that separates them there -- the torn first attempt's error text and code are identical either way, the re-issue's SFTP status is `SSH_FX_NO_SUCH_FILE` in both, `exists(destination)` is false in both, the consumption leaves no durable trace in delete mode (after the REMOVE the receiver writes nothing), probing earlier within recovery does not help since the replacement session's first operation is a full SSH handshake behind the consumption, and the adapter's own knowledge that a drop occurred with a rename in flight identifies the class, not the outcome. The runs behind that reach the source-absent state by the landed-and-consumed route; a never-landed publish whose source some third party then removed is the same state by another route, and is not staged. Separating them would take a durable artifact created by the publish or by the consumption -- a change to the publish shape or the protocol, not to this recovery. So the adapter rejects that state with a distinct error type (`TransportPublishIndeterminateError`) carrying the re-issue's own error as its `cause`, rather than resolving it (which would report an unpublished message as sent) or propagating the raw `SSH_FX_NO_SUCH_FILE` (which states a non-delivery it cannot know). Every neighbouring state is unchanged: a confirmed destination resolves, a re-issue failing with the source still on the server propagates its own error, and a non-`SSH_FX_NO_SUCH_FILE` failure -- including the code-4 generic failure, the server's answer that the rename did not take effect -- propagates unchanged. A server reporting a missing rename source as code 4 rather than `SSH_FX_NO_SUCH_FILE` would therefore be classified determinate; the pinned stack does not (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)). The rejection is caller-neutral, and deliberately so: `rename` is shared machinery, and four publishes reach it -- the message loop's `send()`, its ack, the rendezvous `joining` -> `hello` rename, and the abort marker -- which share no recovery. So its message names a *publish* rather than a message, prescribes no next step, and carries no `psilinkRecoveryHintEmitted` tag; a caller whose recovery is established restates it as its own tagged error holding this one as the `cause`. The consumer-side consequence is in [FILE_SYNC.md](FILE_SYNC.md) (I8): the sequence number such a publish spent is not reusable, the next `send()` is refused rather than writing a second message under a sequence number the peer may already have delivered one under, and `send()` is the one caller that does restate this rejection with a remedy.

### Operations concurrent with a re-dial or a release

**Issuance is not serial, and the re-dial does not rest on its being so.** Within one operation the first attempt's promise has settled before its recovery catch fires the re-dial -- that catch is where it settled -- but other operations are not serialized against it: a `send()` resuming from the protocol continuation issues its operations alongside the poll cycle's own, so a second adapter operation can be unsettled while a re-dial runs. The re-dial neither waits for one nor is made unsound by one, and the measurement says where such an operation goes rather than only that it is harmless: the retirement that precedes the dial waits out -- and against a withholding partner drives itself -- the transport close that tears it, so it is settled ahead of the dial with a drop-shaped rejection of its own and re-issued through its own recovery round, rather than left to ride the per-operation liveness deadline. Where a route settles later than that -- the chunked `put`'s bounded source -- it is fenced instead: it was issued against the session being torn down, and the heartbeat epoch that `connect()`'s re-arm advances is what keeps its late settlement off the fresh session's in-flight count. That is measured against a real partner, driven for a raw-wrapper `list` alongside a high-level `get` in both issue orders, for a forty-way `Promise.allSettled` `delete` fan-out (the rendezvous orphan sweep's shape), for the never-reject `Promise.all` `safeDelete` fan-out beside it, and for a keepalive parked on the wire under both partner classes. Three shapes are stated limits rather than covered ones: the `safeDelete` fan-out never reaches this window at all, sitting outside the recovery chokepoint by its never-reject contract, and what covers a cleanup delete that did not take effect is the record the adapter keeps for it (below); a partner that drops the SFTP session while WITHHOLDING its connection close produces no tear to settle anything, so both operations ride to the first deadline that expires and the forced close that follows settles the rest, which is the withheld-close path above rather than this one; and core's own `send()`-alongside-`poll()` interleaving, driven across a sweep of cut points, put two operations on the wire at the tear in only some of them and reached this window in none, so what the shapes above measure is the adapter's behavior under such concurrency and not a demonstration that the poll loop produces it at a drop. The numbers, the cut positions, and the pairs the runs did not reach are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md).

A second concurrency is core's per-operation `peerTimeoutMs` budget (a `Promise.race` in `boundTransport`), which can reject a stalled operation to the caller while the adapter operation keeps running, so an abandoned operation may still be inside its re-dial's `connect()` when the aborting caller reaches `close()` -> `end()`. Both share the one `Ssh2SftpClient`, and a fresh handshake must never overlap `end()`'s `client.end()`. Two guards close that. (1) Both take the adapter's session-transition lock (below), so `end()` runs behind the re-dial rather than under it; the post-re-dial `closing` check then surfaces the original loss rather than re-issuing into a closing adapter, and teardown's own place in the queue is what ends whatever session that re-dial established, so none outlives the close. That wait carries whatever bounds the dial itself (`connect()` carries its own retry budget and each attempt its `readyTimeout`), and above it `end()` inherits the ceiling of whoever called it, which for a teardown is core's teardown budget. (2) The re-dial stops the heartbeat before calling `connect()`, so the dropped session's still-armed keepalive timer -- which a clean drop, unlike a fatal error, does not stop -- cannot post a `realPath` on the client mid-handshake; `connect()` re-arms a fresh heartbeat at the end of its sequence.

**The `connection_per_poll` idle boundary is a third such concurrency, and is serialized the same way.** Its release drives the ssh2 `Client`'s `end()` and awaits the `'close'`, and it is that `'close'` -- not the `end()` -- that clears ssh2-sftp-client's `sftp` property. Between the two the session can still read LIVE, over a transport that `end()` has already ended, so an operation rejecting in that window rejects against a session that reads live and is not -- the transport reading above resolves that as the loss it is, while the boundary the release recorded is what decides the accounting; after the window it rejects against a cleared one, which without further information reads as a server drop. An operation reaching the transport at a boundary is driven by the protocol continuation, not by the poll cycle, so it can land on either side of it. The release does not leave the end of that window to the partner: a server that accepts the disconnect and never closes the connection leaves the transport ended with the session still reading live, so past its bound the release destroys the socket itself and the resulting `'close'` clears the session (the internals and the measurements are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)). The window spans that forced close, and the release holds the transition lock across it, so an operation arriving inside it is serialized on exactly the terms below rather than being admitted by a session that can no longer answer.

An operation ISSUED once the release is RUNNING is held off both readings at the adapter's recovery chokepoint -- the entry point of the recovery-wrapped operations, which is all of them but the never-reject cleanup delete (covered instead by the record below) and a `put` whose source cannot be re-issued: with a release in flight, or a boundary still standing that says a release took the session, the operation re-establishes the session before its first attempt, queued behind the release so it runs on the far side of the close rather than racing it. The precondition is adapter-owned rather than spread across the calling sites in core, because the release that opens the window is adapter-owned; a per-call-site precondition would be an invariant held by discipline, which any future operation issued outside the poll cycle would silently break. The re-establishment is best-effort: a dial failure there resolves rather than rejecting, because the gate is a precondition and not the operation -- the attempt that follows is what decides the outcome, and its own recovery round surfaces a transient failure with the real error. A host-key rejection still fails the operation closed one step later through the recovery path's own `connect()`. Both readings are written from INSIDE the release's own transition -- the in-flight reading when it reaches the front of the queue, the boundary just before it drives the close -- so "running" is the operative moment, not the call to `releaseForIdle()`: an operation issued while that release is still QUEUED behind another transition reads neither and is issued against the session that is still live. It is on the wire by the time the release enters, and the outstanding-operation precondition below is what covers it.

**A recovery re-dial and a release are serialized against each other wherever the two meet.** The re-dial queues behind the release on the transition lock, so neither a teardown nor a handshake overlaps the release's own close -- a handshake started inside that window resets ssh2-sftp-client's event flags and installs its own temporary listeners, so the release's stale `'close'` would land on the fresh handshake and reject it, charging the exchange a re-dial retry (or, at `max_reconnect_attempts=0`, a terminal failure) for a session the adapter closed on purpose. Where they meet is the boundary held for the arm's own outstanding operation (below), a boundary reached anywhere inside the arm being held rather than closed: the release enters ahead of the arm and closes, and the arm's re-dial then parks on the lock with that release's `'close'` still owed. The unit case drives exactly that meeting, and measures both halves of it -- the dial not taken while the release holds, and the operation resolving on the session dialed once it lets go. The release queues behind an in-flight dial for the mirror reason: a dial that lands after the boundary would hold its session across the whole idle gap.

### The outstanding-operation hold on an idle boundary

**An operation the adapter has ISSUED and not settled holds the boundary: no release closes over a counted one.** No gate at operation entry can cover an operation already on the wire, so the precondition is the release's own. The adapter counts the server-driven operations issued and not yet settled at the single entry point every one of them passes through, which opens one span per operation from where it is issued to where it finally settles, a recovery arm included -- including the two the recovery chokepoint does not reach, and excluding three round trips issued outside it (the heartbeat's keepalive, the best-effort handle close a listing fires once it has settled, and the cleanup drain's re-issue below). The release reads it once, inside its own transition, with the queue held and nothing yet driven. A non-zero reading returns without closing: the session stays up for the operation it was issued against, and the first boundary past that operation's settlement releases as usual. The count is the adapter's own rather than the SFTP heartbeat's, which the release itself stops as its first statement and which this mode never arms. It is a HOLD and not a drain -- the release does not await the operation -- so nothing gains a wait: the release's own bounds stand unchanged, a teardown queued behind it cannot be parked past them, and the drained-boundary path still drives the ssh2 `end()` synchronously with the call. The precondition applies to the idle release and to no other transition: a teardown closes over whatever is outstanding by design, and a recovery re-dial that waited would park behind the very class of operation that drove it. A held boundary is ordinary rather than anomalous -- a concurrent `send()` straddling a boundary produces it -- so no occurrence is warned, and it is in particular not a declined release, which reports a transition that did not complete within the release's wait.

**What a held boundary costs, and what the run reports.** It costs the mode one idle gap per boundary the operation straddles, and the run's total is accounted rather than left silent: two adapter counters, `heldBoundaryCount` (every boundary a release holds) and `heldBoundaryStretchCount` (the unbroken stretches those boundaries fall in, a stretch opening at a held boundary with none open and closing when the outstanding count next reaches zero), reported together as one end-of-run operator line at default verbosity, the stretch sub-count only where it is strictly below the boundary count. Both stay out of the reconnect total and out of the machine `metrics` event, because nothing was closed and so nothing was lost. What the stretch measure separates is one unbounded transfer holding twenty boundaries (20 boundaries, 1 stretch) from twenty straddling `send()`s that each settle between boundaries (20 and 20) -- the first says the mode has stopped delivering per-cycle sessions for the rest of the run, the second that it is working. Its stated limit is that it measures unbroken hold and not operations: operations that overlap continuously, never letting the outstanding count reach zero, read as ONE stretch however many of them there were.

**The three-entry exclusion set is a check rather than a claim.** `scripts/sftp-tracked-round-trips.test.mjs` parses the adapter with the TypeScript compiler API and fails on any request-issuing call site the adapter's per-attempt bracket does not cover and the three allowances do not name. What it verifies is that bracket's coverage; that every bracket sits inside an operation's outstanding span follows from the per-attempt layer being reached only through the entry point above, which the analysis does not itself decide. Its reach is what it can follow syntactically: a call written as a property access (`receiver.member(...)`) on the client, on the raw `SFTPWrapper`, or on a local aliasing either, with coverage traced through the adapter's promise plumbing. Its header states that reach exactly, and with it the two ways the analysis falls short of a proof -- a callee or a receiver written outside the reach is not decided at all, and inside it a best-effort call that merely names a settler is credited with the bracket.

**What the count is, and what bounds the hold.** Issued-and-unsettled is not the set that is on the wire, and departs from it in both directions. An adapter bound that expires settles the operation on this side while the library request it raced is still outstanding at the server -- every one of these bounds is a race that abandons rather than a cancellation -- so the count returns to zero and the next boundary closes over that request. Symmetrically, an operation the server never answers is never settled from this side at all: core's whole-exchange budget is the same kind of race, so the operation the adapter counted stays counted. The hold therefore lasts exactly as long as the operation is unsettled, and the bound on that is the operation's own: the per-operation deadline where it carries one, and nothing where it does not. Two shapes carry none -- a `put` from a string or stream source, which has no per-operation bound at all, and a progress-reset window (the chunked `put`'s idle window, the capped `get`'s sink) that a server trickling acknowledgement re-arms rather than trips -- and a session held for one of those stays held for the rest of the exchange. Both directions are pinned by adapter unit tests, so a change to either fails a check rather than silently contradicting this paragraph. A third departure is the recovery arm, which the SAME span covers rather than a second one nested inside it: the span opens where the operation is ISSUED and closes when it finally settles, so the first attempt, the re-dial, the re-issue and (for `rename()`) the destination probe that confirms a landed pre-drop rename all fall within one span, while the per-attempt heartbeat brackets open and close inside it. There is therefore no point in an operation's life at which the count reads it settled while it is not, and each of the two seams that would cost a landed publish is covered by construction rather than by placement: between the re-issued attempt's rejection and the probe it drives, where a boundary would tear the probe and an unanswered probe confirms nothing, so a rename that DID land would surface as the undetermined outcome above; and between the re-dial and the re-issue, where a boundary would close the very session the re-dial established and the re-issue would reject with a dead-session error that no per-operation resolver reads at all. Both are pinned by adapter unit tests that sweep a boundary across the whole arm rather than placing it at one named point, since with one span there is no reading of the count that names either seam.

**The heartbeat's activity accounting stays at the per-attempt bracket rather than moving to the span.** It answers a different question -- whether a round trip is ON THE WIRE, which across a recovery arm none of this operation's is -- and widening it to the span would leave the re-issue unmarked: the arm's own re-dial re-arms the heartbeat from scratch and zeroes whatever in-flight count preceded it, so a keepalive could then be posted alongside the very round trip the bracket exists to keep one away from. `connection_per_poll` arms no heartbeat at all, so the question does not arise in the mode the outstanding count serves.

### The deferred cleanup-delete record

**A cleanup delete of this party's own in-flight temp file, issued into the idle gap, is recorded and re-issued.** The never-reject cleanup delete is the one operation that reaches no gate at all: its contract puts it outside the recovery chokepoint, so a delete issued with a release in flight, or with a boundary standing that says a release took the session, reaches no session and removes nothing -- and it resolves all the same, so its caller in core cannot tell that from a delete that landed. Only the adapter can, which is why the record lives there, on exactly the terms the recovery chokepoint's precondition states: a per-call-site check in core would be an invariant held by discipline. What it costs otherwise is a file no later mechanism in the run sweeps -- the in-flight `temp-<uuid>.tmp` a failed `send()` removes from its own catch, which is tracked in no responsible-file set and so never reaches `cleanup()` (see [FILE_SYNC.md](FILE_SYNC.md)). The path is recorded on two readings, either sufficient on its own: the release readings the gate above takes, read before the delete is issued, and the delete's own rejection, which additionally covers a cleanup that failed for a reason of its own. It is re-issued at the tail of each re-establishment (`ensureConnected`), with the session-transition lock released -- the one seam that covers both the cycle-start re-dial and the re-establishment `close()` drives ahead of the terminal-frame drain. A re-issue that fails is offered back to the record -- so a server briefly unreachable at one boundary is swept at the next -- against a bounded per-recording budget rather than for the life of the run, and on the same cap the first record ran. It is not retain-gated and must not become so: a `temp-*.tmp` is a failed in-flight write and never transcript, so a retain-mode run leaves none behind either.

**Only the protocol's own in-flight temp shapes -- `temp-<uuidv4()>.tmp` and the hello publish's `temp-hello-<uuidv4()>.tmp` -- are admitted to the record, and that is what makes deferral sound.** `safeDelete` is a general transport method: core calls it with the shared rendezvous lock path, and with names read back from a listing of the directory the PEER writes into. A record is keyed on a PATH and re-issued at an arbitrary LATER point, so admitting one of those would let a transiently-failed delete remove whatever has since come to occupy that name -- a fresh authenticated abort marker the peer wrote in the interim, say, turning a fast `PeerAbortError` into a wait to the peer-inactivity ceiling. Both temp shapes carry a per-file v4 UUID, so the path a re-issue reaches is the file it was issued for or nothing at all. The recognizer is core's own (`isProtocolTempName`, which spans both shapes), not a copy in the transport, so the two cannot drift; the basename is what decides. (The entry sweep applies a NARROWER predicate -- it excludes the hello shape, which may belong to a concurrently starting peer; see [FILE_SYNC.md](FILE_SYNC.md). So the only hello temp that ever reaches this record is one this party wrote itself, from the publish's own failure path, never a name read back from a listing.) Every other path `safeDelete` is handed keeps the plain best-effort behavior -- issued once, never recorded -- which is also what bounds what an adversary can do to the record: the only names that consume it are protocol temps.

**Each re-issue carries a teardown-scale deadline, and that is what bounds the whole drain.** The re-issues go out CONCURRENTLY, and each is held to **5 s** in place of the 60 s per-operation deadline every other round trip carries, so the drain costs one such wait rather than one per record and needs no ceiling of its own above them. The value is teardown-scale because of where the drain's wait lands: core forwards `ensureConnected` unwrapped and `close()` awaits it with no budget above, and the recovery gate's first attempt after an idle gap waits behind it too. Without it a server that ACCEPTS delete requests and WITHHOLDS their callbacks would add a whole per-operation deadline (60 s) to every close -- an order of magnitude above the teardown bounds beneath it. Cutting a re-issue short there loses nothing real: against such a server the delete was not going to take effect, and the expiry is a rejection like any other, so the path is offered back to the record on the terms below. The drain resolves rather than rejecting, and its result is fenced out of `ensureConnected`'s: core's poll loop treats an `ensureConnected` rejection as a TERMINAL dial error, so a best-effort cleanup sweep must not be able to end an exchange. The DIAL's rejection is deliberately not fenced -- a host-key verification failure still fails the exchange closed through this same method.

**The re-issue is the one UNSETTLED round trip an idle release may tear, and is deliberately left uncounted.** Of the round trips this mode leaves the adapter waiting on, every one but the drain's re-issue passes through the outstanding-operation bracket whose count is the idle release's precondition -- the heartbeat's keepalive is unbracketed as well, and this mode arms no heartbeat -- and that exclusion is what preserves the mode's own guarantee. The third unbracketed round trip is not this case: the best-effort handle close a listing fires once the listing has already SETTLED, which a boundary falling there tears too, at the cost a withheld close callback carries anyway -- a handle leaked until session teardown, which under `connection_per_poll` is that boundary. Already-settled work needs nothing from the release's guarantee; the re-issue is the round trip for which that guarantee had to be reasoned about at all. Counted, a re-issue against a server that accepts DELETE and withholds its callback would hold every idle boundary for its whole bound -- and a boundary that closes nothing leaves the session live, so the next re-establishment finds one, re-runs the drain and regenerates the operation, `connection_per_poll` silently reverting to a held session for the rest of the run. That needs no failed publish to reach: the entry sweep hands every listed `temp-<uuidv4()>.tmp` from a server-supplied listing to the cleanup delete. Two properties make the tear sound. The record survives it -- the torn delete rejects, which offers the path back to the record -- so the release DEFERS the work rather than losing it, which is the very thing the record exists to do. And a torn DELETE of this party's own temp leaves no state its re-issue can misread: the server either performed the unlink or did not, and the re-issue reads the first as the success it is (`notFoundOK`). The bracket's other duty does not reach it either -- the record and the drain exist only in `connection_per_poll`, which arms no heartbeat.

**What bounds the record: a cap on entries, and a re-issue budget per recording.** The record is capped at `MAX_DEFERRED_CLEANUP_DELETES` (**64**), and overflow REFUSES the new record rather than evicting an older one: refusing degrades the overflowing cleanup to exactly the behavior it had before the record existed, while evicting would turn a cleanup this adapter had already promised to re-issue into a silent loss. Each recorded path additionally carries a budget of `MAX_DEFERRED_CLEANUP_REISSUES` (**3**) re-issues: a re-issue that fails records the path again with one fewer, and a spent budget gives up on that RECORDING. Without it the only thing that ever clears a record is a delete this side saw succeed, so a delete that can NEVER succeed -- a peer-owned temp under a sticky-bit directory, which the entry sweep still attempts -- is retried at every re-establishment for the life of the exchange, and with the record full that is a whole record's worth of extra DELETE round trips per poll cycle against the partner's server. A spent budget degrades that cleanup to the pre-record behavior exactly as overflow does, and is logged at debug for the same reason. Re-recording a failed re-issue runs through the same capped, shape-narrowed path a first record does, so a re-record made while the record is full is refused like any other: what the drain guarantees is that a path it could not perform is OFFERED BACK, not that it is always kept -- refuse-not-evict applies to a re-issue's own path as much as to a newcomer's.

**What the budget is a bound on, and the amplification that leaves.** It is per RECORDING and not per path per connection: giving up ends that recording and remembers nothing about the path, so a path that reaches the cleanup delete AGAIN is recorded afresh with the whole budget, by either route into the record. A path re-recorded while its own re-issue is still in flight likewise keeps the budget the re-record wrote, the record leaving an entry that already stands untouched rather than applying the failing re-issue's decrement to it. What that costs a run turns on which call site offers the path, and for the case above -- a temp this party can never delete -- only one does: core sweeps orphaned temps in the rendezvous ENTRY scan, which runs once per exchange rather than once per poll cycle, and the poll loop tolerates a protocol temp without ever sweeping one. Such a temp is therefore recorded ONCE and costs that sweep's own attempt plus `MAX_DEFERRED_CLEANUP_REISSUES` re-issues spread over the re-establishments that follow -- a few round trips for the whole run. The per-cycle reading is what a caller re-offering the same path every cycle would pay, each re-offer being a fresh recording; no call site does that today, and this is the premise to re-check before one is added. The amplification is bounded either way: a drain issues one re-issue per recording, and the cap above bounds how many recordings stand at once, so what a re-establishment can cost is one bounded sweep of the record. Remembering a given-up path -- a tombstone that would make the budget per path per connection -- is deliberately not done, because it would consume a cap slot, which is how a peer would crowd the send path's own cleanups out of the record. What the budget is NOT load-bearing for is the mode's per-cycle session: what keeps an idle release from being pinned off is the re-issue's exclusion from the outstanding-operation bracket, and the budget does not stand in for that exclusion -- counted, a re-issue holds the boundary of every cycle its budget reaches, measured against a server that accepts DELETE and withholds its callback as four handshakes over seven poll cycles where the uncounted re-issue delivers seven.

**The five states that drain nothing, and two stated limits.** The refusals above are logged at debug rather than warned -- they fire only where a drain has repeatedly failed to reach the server, which the operations that needed that server already report. The drain does nothing in five states, each for its own reason:

- the default held-session mode, which keeps no record and issues no drain at all;
- a fatal SFTP protocol error, where a request posted to the destroyed wrapper never calls back -- the very thing the cleanup delete's own short-circuit refuses to do -- so a cleanup recorded BEFORE that error is not reintroduced at teardown after it;
- a latched teardown, where `end()` is already closing the client;
- no live session, the record keeping for the next re-establishment;
- an empty record, the mode's healthy path, which costs no round trip.

Two limits are stated rather than closed. The first is the run: a record left when no further re-establishment happens is never re-issued, so the guarantee is that a cleanup deferred across an idle boundary is performed later IN THE SAME RUN, not that the adapter eventually reconciles the directory. The second is the cap, whose bite the re-issue budget bounds rather than leaving to stand for the run: a directory holding many protocol temps this party cannot delete -- peer-owned files under a sticky-bit directory, which the entry sweep still attempts and whose number is therefore peer-influenced -- can fill the record before the send path needs it, and a send-path cleanup offered while the record stands full is refused. Such a fill clears itself, because the drain clears the record before issuing, each failed re-issue re-records at one below the budget it ran with, and a spent budget is given up on rather than recorded again: a fill made entirely of undeletable temps survives the `MAX_DEFERRED_CLEANUP_REISSUES - 1` re-establishments that follow it, standing full again at the end of each, and is gone by the end of the `MAX_DEFERRED_CLEANUP_REISSUES`th, which admits the send path again. Measured at the cap against a server whose own `unlink` refuses for real: the record stands full and refuses a send-path cleanup after each of the first two drains, and is empty and admits one after the third and after every drain past it. What a refusal inside that window costs is exactly the pre-record behavior -- that cleanup is issued once, never re-issued, and its temp survives the run, which the first limit already excludes from the guarantee -- and it is that degradation, rather than any claim about how hard a peer-influenced fill is to produce, that the cap is accepted on.

### The session-transition lock

**Every session transition runs under one FIFO lock the adapter owns, teardown included.** The five -- the first dial, the cycle-start reconnect, the recovery re-dial, the idle-boundary release, and `end()` -- acquire it through one helper, taking their queue slot SYNCHRONOUSLY at the call, so they run in the order they were requested in and a microtask inserted anywhere on a transition path cannot reorder them. The teardown latch is read at exactly one place, inside that helper, once per transition: `end()` sets it synchronously before enqueuing, so a transition queued behind teardown does not run its body (it returns its caller's stated "nothing to do" value, or refuses a re-open) while one already running is waited out by teardown's own position in the queue. `end()` therefore has no privileged entry and pre-empts nothing. Without that ordering a handshake would run alongside `end()`'s `client.end()` and, because ssh2-sftp-client's `end()` short-circuits on a cleared session, that `end()` would resolve without ending the ssh2 `Client` at all -- `close()` returning over a ref'd socket. The mechanisms driven past the public API -- ssh2-sftp-client's `connect()` and `end()`, the ssh2 `Client`'s own `end()`, and the forced socket destroys -- each present the transition they run inside and check its IDENTITY against the one holding the client, so the chokepoint is a check rather than a reading of the call graph, and it cannot be satisfied by a transition that merely happens to be running. Its single exemption is named and narrow, and is the subject of the paragraph below. The lock also carries the release boundary above: the helper is its only writer, it restores what it found when a transition raises, and it takes any reading that a release took the session back from a transition that leaves a session still live.

The lock is not mode-gated, and two orderings in the default held-session mode follow from that. A teardown concurrent with the FIRST dial never runs ssh2-sftp-client's `end()` under that handshake -- the overlap this whole control exists to stop, and the one that motivated it -- and waits it out only as far as the acquire bound below, past which it destroys the transport and cuts the handshake short (measured against a real ssh2 server that stalls its handshake: `end()` returned about 10.0 s after the teardown was requested and the parked first dial rejected `ERR_GENERIC_CLIENT` 3 ms later). A `connect()` issued while a teardown is IN FLIGHT parks for that teardown's own bounds before refusing the re-open rather than refusing at once; the refusal and its wording are the same either way, and short-circuiting it on a pre-acquire reading of the teardown latch would restore the second, out-of-lock reading that the single in-lock read exists to replace, buying a faster failure on a path no caller in this repository takes (core's `open()` and `close()` are not concurrent). A `connect()` after a teardown has SETTLED does not park at all: the queue is drained, so its transition enters its critical section in the same tick and the refusal is immediate. What core layers above is deliberately not uniform: it wraps a data-plane operation in a fresh `peerTimeoutMs` budget and `end()` in the much shorter teardown budget below, but forwards `releaseForIdle` and `ensureConnected` unwrapped, neither being a peer round trip -- and a bound there would abandon core's WAIT alone in any case, since it cannot close anything the transport owns. What bounds each transition's own wait is the adapter's, next.

**The wait for the transition ahead is bounded by one fixed adapter-owned ceiling, and an expired wait never proceeds.** `TRANSITION_ACQUIRE_TIMEOUT_MS` (10 s) bounds every queued acquire, so no transition can park behind another indefinitely -- the two unattended failures that motivates are a teardown parked behind an abandoned operation's recovery re-dial, which leaves a finished run alive on a ref'd socket, and an idle release parked behind a concurrent `send()`'s re-dial, which stops the poll loop until the hour-scale parked-receive ceiling misattributes it to peer silence. It bounds the WAIT and not the transition being waited on: a ceiling on the dial would make a teardown's wait the dial's whole budget -- `(max_reconnect_attempts + 1)` attempts at `server_connect_timeout_ms` plus the inter-attempt delays, about two minutes at the defaults and unbounded above as the operator raises that timeout -- and would rest on a premise about when ssh2 arms its connect deadline rather than on a number the adapter owns. The value sits above the 6 s a legitimate release can spend (`CLIENT_CLOSE_TIMEOUT_MS` then `FORCED_CLOSE_TIMEOUT_MS`), so a teardown queued behind a normal release does not give up on it -- a relationship between three constants, held by a unit test that drives a release's whole close budget with a teardown queued behind it rather than by the arithmetic. It owes nothing to the budget `end()`'s caller holds, which can sit on either side of it: core's own `min(CONNECTION_CLOSE_TIMEOUT_MS, peerTimeoutMs)` is under this bound exactly where `peer_timeout_ms` is below 10 s and above it at `peer_timeout_ms = 10_500` (`CONNECTION_CLOSE_TIMEOUT_MS` being 30 s), and `peer_timeout_ms` is validated only as a positive integer, which leaves both sides of that crossover reachable. Abandoning core's wait closes nothing in any case: the destroy is what closes the transport, and it runs off the abandon's own timer whether or not anything is still waiting on `end()`, so a caller that gave up is still left an exited process rather than a half-open socket. That timer is left ref'd as the safe default and pinned as such by a unit case, so the ref cannot be dropped silently; unlike the forced close's ref, though, no process-exit difference behind it is measured, the transition being waited on being itself parked on a ref'd socket handle in every state driven.

No waiter proceeds into its own session action when the wait expires -- not the dial, not the ssh2 client's `end()`, not the socket destroy -- because the transition it gave up on still holds the client. Each abandons its OWN transition through the transient-failure path it already owns, and a new transition kind appends a row:

| transition | what its expired acquire reports |
| --- | --- |
| cycle-start dial | a cycle to skip |
| idle release | that it released nothing, under a warning paced like the forced release's |
| recovery re-dial | that no session is live for the re-issue |
| the first dial | a rejection, there being no value that could mean "no session was established" |
| teardown | nothing: it is the one kind whose expiry still closes something, below |

A waiter also gives up its turn WITHOUT resolving its own queue slot, which stays chained to the transition actually holding the client: resolving it would admit that waiter's successor alongside a holder that has not settled, which is the overlap the lock exists to prevent. Teardown is the one exception and only in the narrow form: it may give up ssh2-sftp-client's `end()` -- which a live handshake beneath it resolves having closed nothing -- and destroy the transport itself, which needs nothing from the peer and settles the very dial being waited on. That destroy is the one mechanism driven from outside the transition holding the client, exempt from the identity check above, and what makes it safe is the teardown latch rather than the destroy's own harmlessness: every transition behind the teardown skips its body, so the holder ahead of it is the only one that can be running, and the exemption checks that latch rather than asserting it. Because destroying the socket cuts an in-flight handshake short, `connect()`'s retry loop reads the teardown latch between attempts as well: without that it re-dials on a fresh socket and keeps a torn-down connection, and a process that exits by drain, alive for the remainder of the dial budget. Both halves are measured against a real ssh2 server (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)). Cutting that handshake short also settles it with the exact error a genuine peer close produces, so nothing riding the settled dial may report this side's close as the partner's: the cycle-start re-dial reads the teardown latch before warning (a closing run has no next tick to retry on either), and an operation whose recovery re-dial was the dial destroyed surfaces the session loss it was recovering from rather than that rejection. Both read adapter state -- the latch, and whether an abandoned teardown closed the transport itself -- and neither matches on the error text, which cannot tell the two apart.

### The connection's terminal close

**The connection's terminal close is bounded on the same terms, in both session modes.** ssh2-sftp-client's `end()` settles only from the ssh2 `Client`'s `'close'`, so a partner that accepts the disconnect and then goes quiet leaves it pending indefinitely -- a hang AFTER a fully successful exchange, in the default held-session mode as much as under `connection_per_poll`, since nothing on that path is mode-gated. `end()` therefore races that one call against `CLIENT_CLOSE_TIMEOUT_MS` and, past it, drives a destroy of the socket beneath it, which SETTLES the pending call rather than abandoning it; a second, ref'd `FORCED_CLOSE_TIMEOUT_MS` bound covers the destroy, and the socket's own `destroyed` flag is read back where it is driven. RESOLVING is the only outcome that means the partner closed the connection: a REJECTING call closed nothing (ssh2-sftp-client raises it from a temporary `'error'` listener whose end/close listeners are gated off), so it takes the same forced-close path, and the rejection is re-raised only behind it. Destroying rather than merely bounding the wait is the point of the control: the half-open socket is a ref'd handle and the CLI's success path exits by event-loop drain, so a bound that abandoned the client would return the caller over a process that never exits. The forced path requires only the one seam it drives, `_sock.destroy`, not the wider set the idle release resolves, so a bump relocating a member this path never calls cannot silently disable it.

**Both of that close's operator-facing guarantees are conditional on the destroy landing.** The informational line, and the property that no caller -- including one sharing the memoized close -- sees a rejecting `end()` over a socket still alive, hold on the fully successful path alone. Three degraded branches stand in their place, each warning and returning:

- the one seam this path drives is not available after `connect()`, so nothing is destroyed at all;
- the bounded destroy raises;
- the socket does not report itself `destroyed` afterwards.

Each warning names what broke and the "Upgrading the SFTP Stack" checklist in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md), and each names the same operator consequence: the connection is left to the operating system, may stay half-open, and a half-open connection can keep this process from exiting. None of the three emits the informational line, which reports the close in the PAST tense and follows the close for exactly that reason. A rejecting `end()` is re-raised behind every one of them too, so on the seam-unavailable branch it is re-raised over a socket this side never closed. Nothing on the forced path throws: core treats `end()` as best-effort and logs that rejection at debug, and the exit code is untouched either way. The one informational line at default verbosity is the successful outcome's alone, and the close is not counted as a lost session and not folded into the idle release's forced-release total, which measures that mode's per-cycle boundary instead. Core keeps a backstop of its own: `end()` is the one transport call wrapped by a short teardown budget (`min(CONNECTION_CLOSE_TIMEOUT_MS, peerTimeoutMs)`) rather than a fresh peer-inactivity budget. That backstop bounds core's WAIT for a transport it does not own; it cannot close anything, which is why the adapter-side destroy is what the guarantee rests on.

## Application-layer parsed-input bounds

The transport bounds above stop a hostile *server admin* from exhausting memory or hanging the link; a distinct control stops the authenticated *exchange counterparty* - a mutually-distrusting peer (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)) - from exhausting CPU or crashing the parser with a pathological-count message. The linkage terms (carried in an invitation token and re-parsed off the post-handshake wire by `protocolSetup`) and every post-handshake wire message are validated with Zod, and a frame within the ~512 MiB frame-size cap above can still pack millions of *invalid* elements into a partner-controlled collection. On Zod 4.4.3 that drives one of two `RangeError`s as Zod accumulates one issue per invalid element: a collection nested two or more array/record/tuple frames deep overflows the call stack while Zod spreads that issue array up through the frames (`Maximum call stack size exceeded`, at ~130k elements); a flat collection with no such frame instead makes Zod throw `Invalid string length` while it builds the error string (the `ZodError` message is `JSON.stringify`-d eagerly in the constructor, exceeding V8's maximum string length at ~3.5M issues, after a multi-second CPU burn). A plain `z.array(element).max(N)` closes neither: Zod v4 validates every element *before* the length check, so the issues accumulate before `.max()` can fire.

Two strategies bound the complete set of partner-parsed collections, chosen per field by whether a legitimate value is large:

- A collection legitimately in the millions - the PSI association-table indices, the payload rows / row indices, a partner's original-index list - carries a single-issue validator (`packages/core/src/utils/singleIssueArray.ts`): it validates the element type in one `every` pass that emits at most ONE issue regardless of count, so an arbitrarily large *valid* message still parses while a hostile one fails as a clean, bounded rejection. A count cap is unusable here - any bound low enough to forestall the `RangeError` would reject a real result.
- A collection whose legitimate count is small - the linkage fields and keys, each constraint's `exclude` denylist, a transform step list, a key's elements, the payload `send`/`receive` column lists, the abort-reason list - carries a count gate (`packages/core/src/utils/boundedArray.ts`): a permissive `z.array(z.unknown())` first stage accepts the array unvalidated, a count refine rejects an over-count array with one issue *before* per-element validation runs, and a `.pipe` re-validates the now count-capped array against the real element schema, preserving every per-element check and its issue path for an in-range array. The refine is `abort`, so an over-count value stops rather than letting the still-raw `unknown[]` flow on to a cross-field refine (which would dereference an unvalidated element). The `transform.params` record's key count is bounded by the same permissive-stage + count-refine + pipe shape, but with a bare **key count** (`packages/core/src/utils/objectKeyCount.ts`, `MAX_PARAMS_ENTRIES`) in place of the array length check. That count is still O(n) in the record's key count - a materialized `JSON.parse` object offers no sub-linear own-key count, and `for...in` enumerates eagerly - but it is the *cheapest* O(n) pass, and `for...in` avoids the result array `Object.keys(rec).length` would allocate and stops its body once the bound is passed. For this record the gate also closes a distinct LINEAR event-loop burn, not the `RangeError` class above: a millions-key `params` record otherwise burns multiple seconds *twice* before its count is even checked, once in the snake->camel `camelizeKeys` pre-pass that runs ahead of Zod (`parseLinkageTerms`) and once in the permissive record stage. Each of those is an EXPENSIVE per-key pass (a snake->camel rewrite, a per-key Zod parse); the gate replaces both with the single cheap key count. `parseLinkageTerms` hands the same bound to the camelize pre-pass, which leaves an over-count `params` value verbatim (handing it to the schema's refine, which rejects it) instead of rewriting every key, so the over-count record is counted but neither rewritten by the camelize pass nor per-key-validated by the record stage - cutting the multi-second burn to roughly one key enumeration rather than eliminating it (it stays O(n), bounded above by the frame cap). The `camelizeKeys` pre-pass walks arrays too, so the count-gated arrays above would incur an analogous pre-pass walk this per-record skip does not address; a global node budget in the walker (next paragraph) closes that, bounding the TOTAL the pre-pass rewrites rather than only this one record's width. The per-field count constants - 256 to 4096, each far above any real config and far below the `RangeError` thresholds - live beside their schemas in `packages/core/src/config/linkageTerms.ts` and `packages/core/src/protocolSetup.ts`.

Independently of the count/CPU-burn class above, the partner-supplied payload **column names** carry a per-ELEMENT length bound (`MAX_NAME_LENGTH` = 256, in `config/linkageTerms.ts`), folded into the same single-pass `columns` validator (`payloadExchange.ts`) so it adds no per-element issue accumulation. This is not a DoS control - the frame cap and the single-issue validator already bound a `columns` array of any size - but a data-hygiene one: a received column name flows verbatim into this party's local exchange-record file (the `governance.payloadReceived` categories of the audit artifact in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md)), so the wire bounds its length to the same `MAX_NAME_LENGTH` ceiling the operator's own `terms.payload.receive` names carry, restoring the length bound those received names had before they began deriving from the partner's payload wire message rather than from local terms. Both that upper bound and the `.min(1)` floor those local-terms names also carry are now enforced on the wire. The floor was previously omitted - an empty partner name was left to the record schema, where it is non-fatal (it skips the record rather than failing the exchange) - because an honest sender could emit a `""` column from a trailing-comma CSV header, and flooring the wire would escalate that common case into a full exchange failure on the peer. `inferMetadata` now rejects an empty column name at intake (the disclosure-surface change in [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md)), so an honest sender never emits one; the wire floor can therefore no longer regress an honest exchange, and instead refuses a partner who hand-crafts a `[""]` column to SUPPRESS this party's exchange record - an empty name would otherwise reach the non-fatal record-build guard, which skips the record while the exchange still completes and discloses, erasing the audit of a disclosure that happened. The exchange-record schema (`RecordPayloadColumn.name`) applies both the `.min(1)` floor and the same `MAX_NAME_LENGTH` ceiling independently, so neither an empty nor an over-long name can reach the on-disk record by any path - the write path rejects it at record build (the non-fatal build guard then skips the record, leaving the exchange result unaffected) and the read path rejects it at parse.

The `camelizeKeys` pre-pass carries its own GLOBAL width bound, the running-total analogue of the per-record `params` skip and of the pre-pass's existing `MAX_NESTING_DEPTH` = 256 depth bound. The snake->camel rewrite is O(total nodes) and runs ahead of all Zod validation, so a partner payload wide enough - within the frame and decode-layer caps - would burn multiple seconds before any count gate fires; and for a wide object placed under an UNKNOWN top-level key the non-strict schema then SILENTLY strips it, so the parse SUCCEEDS after the burn rather than rejecting (worse than a rejection, since nothing is surfaced). A single node counter threaded across the WHOLE walk - `MAX_NODE_COUNT` = 262144, one object member or one array element per node - rejects such a payload with a clean, terminal `NodeCountExceededError` (a `UsageError` like the depth bound, fixed message carrying no input bytes) before the rewrite completes: an over-wide array is refused by its O(1) length before `.map`, and an over-wide object by a streaming own-key count before `Object.entries` materializes it, so neither the burn nor the materialization runs. A running total, not a per-container cap, is required to catch BOTH a single wide object (path a) and width spread across many small ones - the count-gated arrays of objects, each walked in full before its `boundedArray` refine could fire (path b). 262144 (2^18) sits far above any realistic operator `ExchangeSpec` - low tens of thousands of nodes at most (the single widest object is a `transform.params` record at `MAX_PARAMS_ENTRIES` = 256, collections cap at 256 to 4096 entries) - and far below the burn, which reaches a multi-second cost only past ~1M nodes (measured); rejecting at this budget caps the wasted walk well under a second. Like the rest of this family it is defense-in-depth, not a semantic limit: the per-collection caps DO compose to a schema-valid maximum above the budget (256 `linkageFields`, each with a 4096-entry `exclude`, is ~1M nodes), so a pathological-but-schema-valid config could trip it - but no real operator config comes within an order of magnitude. It composes with the per-record `params` skip WITHOUT double-counting - a skipped subtree (an opaque value, or an over-count width-bounded value) is not recursed into and so never counts toward the budget - so a massively over-count partner collection is now refused by this budget BEFORE Zod (the boundedArray count gate still rejects a moderate over-count that stays under the budget), and the throw is caught by the same `parseLinkageTerms` parse-error path that already handles the depth bound.

The `MAX_NESTING_DEPTH` = 256 depth bound the `camelizeKeys` pre-pass applies is enforced on all three linkage-terms parse paths, the invitation decode path included. `decodeInvitation` normalizes `transform.params` to camelCase through the bounded `camelizeKeys` chokepoint (the camelize pre-pass in `packages/core/src/config/invitation.ts`) as it validates the token against `InvitationTokenSchema` -- folding before the per-step length and dialect screens so they run on the normalized form -- so a partner-controlled one-key-per-level `params` - bounded otherwise only by the 64 KiB `MAX_ENCODED_INVITATION_LENGTH` cap and `parseBoundedJson`'s `MAX_JSON_NESTING_DEPTH` = 4096 decode ceiling, both ABOVE the ~2000-level native call-stack limit - is rejected at decode with a terminal `NestingDepthExceededError` (a `UsageError`, CLI exit 64 / a clean web decode error via `describeDecodeError`) before it reaches any downstream consumer. The normalization MUST use the bounded `camelizeKeys` walk for exactly this reason: a raw snake->camel recursion over the schema-opaque (`z.unknown()`, decode-unbounded) `params` value would itself overflow the stack. Because the field is now normalized at the decode chokepoint, every consumer of a decoded invitation's terms - the canonical comparison, the reconcile, the agreed-terms hash, the standardization runtime - inherits both the camelCase form and this depth bound, rather than each having to re-impose it. The CLI's invitation-vs-config reconcile (`apps/cli/src/config.ts`, `nfcDeep` reached via `diffLinkageTerms`) nonetheless threads its own depth counter and rejects at the same 256 as a backstop: `nfcDeep` is an independent recursive NFC fold that must not couple its safety to its callers having pre-bounded the input, and an unguarded deep value would otherwise overflow it with a `RangeError` the CLI command boundary maps to a generic internal-error exit (69) - catchable and non-fatal, but ungraceful, and distinct from the uncatchable `JSON.parse` aborts the decode-layer bound below guards. With decode and config load now bounding both sides, that backstop is not normally reachable; it stays as defense-in-depth. The bound fires far below the overflow and far above any real config (the deepest schema path is under a dozen levels, and `params` legitimately holds shallow scalars).

A further bound sits *upstream* of the entire Zod/`camelizeKeys` family above, at the JSON-decode layer, and is enforced as a single chokepoint: every parse of untrusted JSON in the core routes through `parseBoundedJson` (`packages/core/src/utils/boundedJson.ts`), which checks the body's structure against a per-object key ceiling, a per-array element ceiling, and a nesting-depth ceiling (`MAX_JSON_OBJECT_KEYS` = 65536, `MAX_JSON_ARRAY_ELEMENTS` = 16777216, `MAX_JSON_NESTING_DEPTH` = 4096) *before* handing it to `JSON.parse`. A lint rule forbids a raw `JSON.parse` elsewhere in the package, so a new parse site cannot silently reopen the hole. Unlike the rest of the family this is not a CPU-burn or `RangeError` guard: a single object made wide enough, or a single array made long enough, drives `JSON.parse` into a process-terminating internal limit of the JSON engine - a per-object property ceiling, or the array backing-store length limit - that is *not* a thrown exception, so a `try`/`catch` around the parse cannot intercept it. The only defense is to refuse the body before the parse can reach either limit, not to catch its failure. The check is a single O(n) pass over the raw UTF-8 bytes (or the already-decoded string a transport hands over) - the JSON structural markers are unambiguous ASCII in either representation (a single byte in UTF-8, a single non-surrogate code unit in UTF-16) - counting each object's members (by colon) and each array's elements (by comma) against its own ceiling, with early exit; on the byte path an over-budget body is refused without even allocating the decoded string.

This chokepoint covers both threat-model adversaries, not only the counterparty. The post-handshake `TYPE_JSON` frame is decoded through it after AEAD decryption (the *counterparty*'s reach); but the file-sync transport's own reads - the peer-hello control file and every message body - are JSON-parsed off the raw inbound file *before* decryption, so they are shaped by the hostile *server admin*, and the invitation token is parsed from attacker-influenced bytes a victim opens. All route through the same chokepoint, so a wide-object or long-array body from any source is refused rather than crashing the process. Each caller maps the refusal to its own terminal error - a `ConnectionError("security")` on the wire, a `UsageError` on a transport file, a rejected invitation - carrying no attacker bytes.

The unit is per *container*, not per byte or per total count, because that is what fits the data *at this layer*: a decoded-byte or total-count budget here would have to sit below the largest legitimate message and so would reject it, yet no single legitimate container is pathological. (The `camelizeKeys` total-node budget above *can* be a running total precisely because it sees only the small parsed-config family - linkage terms and the like - never these large set frames, which are parsed by other schemas the pre-pass does not touch.) The widest legitimate object is the `transform.params` record at `MAX_PARAMS_ENTRIES` = 256; the longest legitimate array is an association-index, payload-row, or mapped-pair list, one entry per matched record and so transport-bounded to a few million (a larger set cannot reach this layer - the binary set frame itself exceeds the transport's string limit first). So `MAX_JSON_OBJECT_KEYS` sits far above any real object and far below the per-object engine limit, and `MAX_JSON_ARRAY_ELEMENTS` sits above any real array and well below the array-length limit - each fires only on a pathological container and never pre-empts a schema-layer rejection or a legitimate large message. The depth ceiling sits far above any real nesting (the parsed-config ceiling is `camelizeKeys`' `MAX_NESTING_DEPTH` = 256) and exists chiefly to bound the scan's own per-container stack against a degenerate all-`{`/`[` body, which would otherwise exhaust memory in the pre-pass. This bound composes with rather than overlaps the post-parse `camelizeKeys` bounds: it caps any single CONTAINER's width before the walker ever sees it, while the walker's own `MAX_NODE_COUNT` budget (above) caps the TOTAL it then rewrites - a width the per-container ceiling does not bound (a body within every per-container limit can still hold far more nodes in aggregate than the walker should rewrite).

The severity is defense-in-depth, not a live vulnerability: the counterparty is authenticated and can already abort the exchange trivially, and most of these sites already caught the `RangeError` harmlessly - a `receiveParsed` / `parseOrProtocolError` wrap surfaces a `ConnectionError("protocol")`, and the linkage-terms parse-error catch aborts cleanly - so the bound turns an ungraceful internal exception and a one-shot CPU burn into a clean, bounded rejection rather than closing a memory or correctness break. The decode-layer chokepoint is the sharper of the set - it forestalls an uncatchable process crash, an availability loss the others do not reach, rather than a recoverable burn - but rests on the same reasoning: the crash kills only a session its instigator already controls - the counterparty it is party to, or the transport a hostile server admin already mediates and can disrupt at will - so it too is defense-in-depth against a self-limited adversary, not a live vulnerability. The set of accepted messages is unchanged: each single-issue predicate mirrors the element schema it replaces, and each count gate's `.pipe` re-runs the original element schema, so a legitimate exchange parses to a byte-identical structure (the cross-party receipt hash is preserved).

## CSV-read single-line byte ceiling

`CSV_LINE_BYTE_CEILING` (8 MiB, `packages/core/src/file.ts`) is the one bound in this application-layer parsed-input family with no adversary. Every bound above answers a specific attacker -- the authenticated counterparty or a hostile server admin -- and the section's framing turns on which one. This bound answers none of them: it guards the operator's OWN local CSV, an input no partner or transport supplies, so it is operator-local input robustness, low severity and non-gating, NOT a partner- or transport-reachable bound and NOT a threat-model control like the partner-parsed bounds it sits among. It is recorded here only so a parse-surface audit finds it beside the input bounds it belongs with rather than as the lone undocumented one; read it as defense-in-depth on the operator's own file, not as a control any threat-model adversary reaches. The two streamed CSV reads share the one constant: `loadCSVColumnSample` (the `init` column- and date-format inference read) and `loadCSVFile` (the whole-row invite/accept/exchange read). PapaParse must buffer one whole logical line -- a data row, or the entire header -- before it can yield a chunk, so an input whose first terminator is far from the start (a no-newline file, one enormous field, or a multi-megabyte header) would drive memory, and CPU quadratically via repeated re-splitting of that partial line, with the span. The ceiling bounds the bytes pulled between row terminators so those shapes fail fast with a clear, operator-readable error. **8 MiB** sits above any realistic operator CSV's single line -- even a pathologically wide file of tens of thousands of columns is a header of low single-digit MiB and a data row far smaller -- and below the hundred-MiB-plus spans that drove the gigabyte-scale memory growth it guards against.

The enforcement mechanics stay in the code and are not reproduced here: the JSDoc on `loadCSVFile`, `guardStreamLineByteCeiling`, and `assertLeadingLineWithinByteCeiling` (all `packages/core/src/file.ts`) describes the split -- the Node stream's `data`-event byte counter (`guardStreamLineByteCeiling`), which bounds every line by destroying the source past the ceiling, versus the browser-`File` pre-read (`assertLeadingLineWithinByteCeiling`), which bounds only the LEADING line before parsing because a `File` exposes no `data` events to scan.

What the spec carries, because it is classification rather than mechanics, is the one shape this bound does NOT cover. Both enforcement points scan raw bytes and treat ANY LF or CR (`0x0a`/`0x0d`) as a line terminator -- including a byte inside an RFC 4180 quoted field. That is the deliberate fail-safe direction: ignoring quoting can only let a pathological line slip past (a false negative), never wrongly reject a valid file (the false positive a quoting-aware scan could produce on a legitimate quoted newline). The cost is one unbounded shape -- a single logical CSV row that is one enormous quoted field carrying embedded newlines: the scan resets its run at each embedded newline and never trips, while PapaParse buffers that whole quoted field as one logical row, memory proportional to the field with quadratic re-split CPU. That shape is bounded not by this ceiling but by the input being operator-local (the CLI sets no file-size cap) or, on the web, by the web app's `MAX_CSV_FILE_BYTES` intake cap; it is not a regression, since the read was unbounded for that shape before this ceiling existed too. Being operator-local and non-gating rather than a partner- or transport-reachable vulnerability, it is recorded openly here, not withheld. The caveat also lives in the code (the `guardStreamLineByteCeiling` JSDoc and an inline comment in `assertLeadingLineWithinByteCeiling`); this note exists so spec and code agree on what the bound does not cover. Unlike the partner-parsed bounds in this family, the ceiling is not net-new security behavior gated on the explicit security review -- it is operator-local robustness, so it carries no such gate.

## Web linkage-terms import bounds

The web editor's expert tier lets an operator paste a JSON or YAML linkage-terms document to load the editor (`importLinkageTerms` in `apps/web/src/psi/linkageTermsIO.ts`). That document is untrusted free text - an operator could paste a credential into it by mistake, and a partner-supplied terms file could be hostile - so it carries the same parsed-input bounds as the core wire paths, plus two import-specific ones. The raw parse routes through the shared secret-redacting chokepoint (`parseSensitiveJson` / `parseSensitiveYaml` in `packages/core/src/sensitiveFile.ts`), never a raw parser, so a parse error reports a path-only label and never echoes the document's bytes (the leak channels are enumerated in that module's header); the JSON path runs through `parseBoundedJson`, so the structural ceilings above (`MAX_JSON_OBJECT_KEYS` / `MAX_JSON_ARRAY_ELEMENTS` / `MAX_JSON_NESTING_DEPTH`) apply; and the parsed value is validated only by `safeParseLinkageTerms` - the same schema, with the same `camelizeKeys` depth/node bounds, that the Generate gate runs - so an import cannot smuggle a value past the schema into a minted invitation.

The two import-specific bounds:

- A pre-parse length cap, `MAX_IMPORT_CHARS` = 1000000 (UTF-16 code units, in `linkageTermsIO.ts`), refuses an oversized paste before either parser runs, so a pathological document cannot drive the parser ahead of the schema's own structural bounds. It sits far above any real linkage-terms document - the invitation token path itself caps at 64 KiB, and a GUI-exported document carrying every key and transform is well under this - and is sized for an operator workstation, not a constrained tab; tunable.
- The YAML parser's alias-expansion bound, `maxAliasCount` = 100, is pinned explicitly in the chokepoint's parse options (`SAFE_YAML_OPTIONS` in `packages/core/src/sensitiveFile.ts`) rather than left to the `yaml` library default. 100 is the library's current default, so pinning is behavior-preserving; pinning it makes the alias-bomb (billion-laughs) bound an enforced constant here rather than an implicit reliance on a default a future `yaml` release could raise. It would only need revisiting if a legitimate document required more than 100 alias references - none does.

## Signaling-server inbound frame bound

The bound above lives in `@psilink/core` and covers the AEAD application channel and the file-sync transport - a self-limited adversary (the authenticated counterparty, or a hostile server admin). The web app's bundled PeerJS signaling server is a separate surface with a broader adversary: it runs in production under `/api/` to broker the WebRTC rendezvous, and its only authentication gate is the well-known default key `peerjs` (the id and token are free strings), so its inbound parse is reachable by ANY unauthenticated internet client. Its `socket.on("message")` handler in `apps/web/src/contrib/peerjs-server/services/webSocketServer/index.ts` decodes each frame with `JSON.parse(data.toString())`, the same uncatchable-V8-abort class as the core bound above - a single wide-enough object or long-enough array drives `JSON.parse` into a process-terminating internal engine limit that no `try`/`catch` can intercept. Because the broker process is shared by every peer, that abort is an availability loss for all of them, not one self-controlled session; and even short of the crash ceiling, a single oversized frame is independently a memory pin.

This is vendored third-party code, distinct from core and not routed through the `parseBoundedJson` chokepoint, so the bound is applied at the idiomatic `ws` layer instead: the `ws` `Server` is constructed with an explicit `maxPayload` (`MAX_SIGNALING_PAYLOAD_BYTES` = 262144, i.e. 256 KiB) rather than the 100 MiB `ws` default. `ws` enforces it in the receiver as each frame's length header is read, refusing an over-cap frame with a 1009 close (`WS_ERR_UNSUPPORTED_MESSAGE_LENGTH`) before the payload is buffered and before the message handler's `JSON.parse` ever runs - the error surfaces as a handled `error` event the server already routes, not a crash. The cap sits far above any legitimate signaling frame: this server brokers only small control messages - the PeerJS OPEN / OFFER / ANSWER / CANDIDATE / HEARTBEAT family, SDP and ICE that are KB-scale - while the PSI payload itself flows peer-to-peer over the WebRTC data channel and never crosses this socket. It sits far below both the 100 MiB default and the ~109 MB a single 2^23-key object needs to reach the per-object ceiling, so it closes the single-frame crash outright rather than only shrinking the window, and caps each inbound frame against the single-frame memory pin. Like the file-sync frame-size cap above it is a fixed constant, not a configurable option: a configurable bound risks an operator raising it high enough to reintroduce the DoS. It would only need revisiting if the signaling protocol began carrying a legitimately large payload through this socket - it does not, and a redesign that routed bulk data through the broker rather than the data channel would be the change to re-evaluate against. As net-new security behavior on an internet-facing surface, this control is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

## Transform-regex linear-time dialect

A second control against the same mutually-distrusting counterparty bounds the *complexity*, not the count, of one partner-supplied field: the regular-expression pattern in a linkage-key element transform. The four regex step functions (`replace_regex`, `extract_regex`, `filter_regex`, `split_on`) compile their pattern and run it per row over the acceptor's full dataset (`packages/core/src/standardization.ts`); `parse_date` likewise *expands* its partner-controlled `inputFormat` into a per-row regex whose adjacent `(\d{1,2})` groups (one per `MM`/`DD` token) are a catastrophic-backtracking construct - a ~48-character format reaches a hang. On the JavaScript `RegExp` engine a catastrophic-backtracking (ReDoS) pattern would hang the single, non-interruptible thread. The pattern cannot be rewritten - PSI requires byte-identical keys and the terms are canonically hashed into the exchange-agreement receipt, so a unilateral rewrite both breaks matching and surfaces as a terms mismatch.

The control is by construction: these patterns execute under a **linear-time regex engine** (re2js, an RE2-semantics Thompson NFA / lazy DFA - `packages/core/src/utils/linearRegex.ts`) instead of `new RegExp`. Matching is linear in the input length with no backtracking, so the catastrophic-backtracking blow-up is *impossible*, not merely screened for. This includes `parse_date`'s expanded regex, which moves onto the same engine, so its adjacent-group construct is bounded by construction rather than by a separate analysis. The engine is pure JavaScript, so the SAME build runs in the CLI (Node) and the web (browser): both parties and both build targets derive byte-identical keys, with no second engine build whose semantics could diverge on an adversarial pattern. The permitted pattern syntax - the **dialect** - is pinned normatively in [PROTOCOL.md](PROTOCOL.md#transform-regular-expression-dialect); both parties MUST evaluate patterns under it.

What remains at validation is a dialect-conformance gate: a refine on `LinkageTermsSchema` (`packages/core/src/config/transformRegexDialect.ts`), so it covers every path that parses partner terms at once - the initiator/joiner `parseLinkageTerms`, the invitation-token decode (`InvitationTokenSchema`), and `ExchangeSpecSchema`. The refine walks every raw-pattern step (the function-to-pattern-param map `REGEX_STEP_PATTERN_PARAM`, `split_on` keying on `delimiter` rather than `pattern`, kept in parity with the `tier: "regex"` function descriptors by a test), coerces the param to a string exactly as the engine would (`coerceToPatternString`, so a non-string JSON value that stringifies to a pattern is screened as the literal it executes as), and rejects - fail closed, before any row runs - a pattern the engine cannot compile: a backreference, a lookaround, or an unsupported escape, exactly the features RE2 drops. `parse_date` is not screened here: it is not a raw-pattern step and its library-generated regex is always in-dialect; its safety is the engine, not the gate. There is deliberately **no fallback to `new RegExp`** - a pattern outside the dialect is refused, never silently re-run on the backtracking engine, which would reopen the hole. A total wall-clock budget across one validation (`REGEX_DIALECT_TOTAL_BUDGET_MS`, 2000 ms) bounds the gate's own cost so a terms set packed with patterns - the per-collection count caps above still permit a large product - cannot turn validation itself into a denial of service; on exhaustion the remaining patterns reject closed. A separate per-step length cap on the raw pattern (`MAX_TRANSFORM_PATTERN_LENGTH`, 1000) caps the source-parse and one-time compile cost (`applyElementTransform` compiles each step once per distinct transform array, memoized, rather than per row). These constants live beside the code in `transformRegexDialect.ts` and `linkageTerms.ts`.

The bundled default standardization patterns - including the email filter `^[^\s@]+@[^\s@]+\.[^\s@]+$` - are all in-dialect and need no allowlist; a checked-in cross-build vector file (`packages/core/test/vectors/transform-regex-vectors.json`) pins each default pattern's output, on the inputs it covers, as byte-identical to the previous `new RegExp` engine, and asserts the Node and browser builds agree. The few code points where RE2 and JavaScript regex semantics diverge - `\s` is ASCII-only under RE2 but Unicode-broad in JavaScript, `.` excludes only `\n` under RE2 but also `\r` and Unicode line separators in JavaScript, and `.` spans a code point rather than a UTF-16 code unit - are documented in [PROTOCOL.md](PROTOCOL.md#transform-regular-expression-dialect) and are outside that vector domain; they are not cross-party divergences (both parties run the same engine) and, in the bundled defaults, the email filter is preceded by `remove_non_ascii`, so no such code point reaches it.

The severity addressed is a denial of service bounded to the availability of the acceptor's own session - its browser tab or CLI process, on the acceptor's own (typically isolated, periodically-run) hardware - with no data disclosure, no code execution, and no effect on the counterparty or the privacy guarantee: standardization is local key-building, before and independent of the PSI rounds, so a hang neither leaks a non-intersection member nor reaches the peer, and the worst outcome is that the run produces no result and is re-run. The realistic trigger is a foot-gun - a catastrophic-backtracking pattern an operator carries over from a JavaScript engine or mistakenly authors, which a human reviewing the agreed terms cannot reliably vet for cost. The linear-time engine prevents that class by construction, and is the load-bearing control here; because the linkage terms are agreed once and reused, with any later modification surfaced for manual review, it also covers the residual hostile-or-tampered pattern (an attacker would have to subvert the one-time terms agreement for a non-escalating local hang). A deliberately-crafted in-dialect-but-expensive pattern remains possible but is bounded - its source length is capped (`MAX_TRANSFORM_PATTERN_LENGTH`, applied to the coerced source the factory compiles), RE2 caps any single and nested repeat count, and matching stays linear in the input - and non-escalating, so it is accepted under this threat model rather than further bounded with complexity caps. This control is the by-construction successor to, and replaces, an interim best-effort static screen (the `redos-detector` analyzer, board item 199539401): the linear-time engine eliminates the class the heuristic could only estimate, and the heuristic, its allowlist, and that dependency are removed. As net-new security behavior that adds a security-relevant dependency (re2js) and pins a wire-level dialect, this control is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

## Name-constraint character class

One more partner-controlled regular expression reaches the local party outside the transform pipeline: a name field's `allowedCharacters` constraint (`NameConstraints`, `packages/core/src/config/linkageTerms.ts`), a regex character class. It differs from the transform patterns above in two ways that lower its stakes but not its ReDoS exposure: it is **not** key-building and **not** hashed into the agreement receipt, so it carries no cross-party determinism requirement; and the value-level check that evaluates it is a **local, warn-not-enforce advisory** - the web cleaning editor flags a cleaned value whose characters fall outside the class, before any exchange round and with no effect on what is sent. It is still partner-authored (it arrives in the invitation token), so a crafted class is the same ReDoS foot-gun and takes the same by-construction control: the check compiles `^[allowedCharacters]$` under the linear-time engine (`compileLinearRegex`) and tests one code point at a time, each as a full (whole-input) match rather than an unanchored find, after escaping a leading `^` to a literal (so a leading caret is the allow-list the operator wrote, not a class negation that would invert the advisory). A class that breaks out of the brackets therefore can neither backtrack catastrophically nor suppress the warning by matching a multi-character span or by an alternation branch that matches only a zero-width or leading span. What this does **not** defeat is a class that genuinely admits the code point - a character-class shorthand (`\w`, `\p{L}`, `[:alpha:]`) or an alternation breakout whose branch matches a single code point (`a]|.|[b`, effectively allow-all): the effective set diverges from a plain reading, but neutralizing it would take a full character-class parser and would false-flag a legitimately permissive class (`\p{L}` is the natural constraint for international names, indistinguishable at the engine level from a smuggle). Because the check is warn-not-enforce, this is an accepted, documented limit - a suppressed advisory badge, never a data-filtering, match-correctness, or ReDoS effect. `NameConstraintsSchema` validates the class under that **same engine** at parse time - not `new RegExp` - on every path that decodes partner terms, so a class it accepts is guaranteed to compile at check time and the advisory cannot fail open on a native-versus-RE2 dialect gap; the degenerate empty class, which the engine cannot compile, is rejected there with the existing character-class message. `MAX_NAME_LENGTH` (256) is a load-bearing pre-compile length gate on that validation, the compile-cost bound the sibling `MAX_TRANSFORM_PATTERN_LENGTH` is for the transform patterns above: because Zod does not short-circuit chained checks, the refine that compiles `[allowedCharacters]` under re2js runs even on an over-length value, and re2js compile cost is super-linear in source length, so the refine tests the length first and defers an over-length class to the `.max()` rejection rather than ever compiling it. The value-level check is currently web-local (core's `validateStandardizationAgainstTerms` checks names only); promoting it to core for CLI reuse (board item 202994324) must keep it on this engine. Because this path builds no keys and feeds no receipt, it needs no cross-build vector and is exempt from the dialect's byte-identical requirement - here the linear-time engine is purely the ReDoS control, not a determinism guarantee. The display complement to that accepted limit: because the effective set can diverge from a plain reading, the operator-facing consent summary (`describeConstraints`, `apps/web/src/psi/invitationSummary.ts`) does **not** paraphrase the class as a vetted "characters limited to X" allow-list; it labels it as the partner-supplied, unverified regular expression it is (naming the trust boundary, not just the regex syntax family) and shows the raw (sanitized) class, so a crafted class - a leading-`^` negation, a `\p{L}`/`[:alpha:]` shorthand, or a bracket breakout - is no longer *presented* to the operator as a plain-language guarantee (board item 203823458). A non-regex-literate operator can still misread a crafted class, but the copy no longer asserts a promise the value cannot back. One bounded residual remains, unchanged in kind from the prior copy: the class body is itself partner-controlled display text rendered as a suffix, so a value that is a valid character class of printable letters and spaces (e.g. `A-Za-z (checked by our compliance team`) renders as trailing prose after the label - the honest "not verified by psilink" note can be followed by a contradicting partner sentence. It is confined to this warn-not-enforce display surface (the note always precedes the value, and the value is sanitized and length-capped, so it can neither displace the note nor break the constraint list), an accepted residual rather than a hole; a rendering that binds the raw class as a visually distinct, bounded element would close it (board item 208049118). The CLI never renders the class: its `displayInvitation` omits per-field constraints and its warn-not-enforce advisory prints a fixed "disallowed characters" label with a count, not the pattern.

## Unbounded transform-parameter rejection

A third control against the same mutually-distrusting counterparty bounds the *magnitude* of the partner-supplied transform-param values whose size drives unbounded per-row work - the `transform.params` values typed `z.unknown()` above, which the count gates do not reach into. The first is the `length` of a `pad_left` linkage-key element transform. `pad_left` runs per row over the acceptor's full dataset (`packages/core/src/standardization.ts`, `applyElementTransform` driven by `buildKeyStrings`) and allocates `String.prototype.padStart(length, char)` for each row, so an unbounded `length` - a crafted `1e9` - makes every row allocate a ~1 GB string and exhausts memory, hanging or crashing the acceptor (the web acceptor's browser tab, the CLI acceptor's process). It is the memory-allocation analogue of the ReDoS regex above: the same fail-open denial of service reachable from the authenticated counterparty, in the same partner-influenced-terms-executed-at-the-local-party model, driven by an unbounded numeric param rather than a pattern. The value cannot be rewritten - PSI requires byte-identical keys and the terms are canonically hashed into the exchange-agreement receipt, so a unilateral clamp both breaks matching and surfaces as a terms mismatch - so the control rejects an out-of-range value at validation, before any row runs.

Enforcement is a per-step refine on `TransformStepSchema` within `LinkageTermsSchema` (`packages/core/src/config/linkageTerms.ts`), so - like the dialect-conformance refine - it covers every path that parses partner terms at once: `parseLinkageTerms`, the invitation-token decode (`InvitationTokenSchema`), and `ExchangeSpecSchema`. The cap must live on this wire schema rather than on the editor-facing `STANDARDIZATION_FUNCTION_DESCRIPTORS`, which an attacker-authored token never passes through: the partner-supplied `transform.params` values are typed `z.unknown()` and carry no content bound (only their entry count is gated, above). A `pad_left` step whose `length` is a positive integer above `MAX_PAD_LEFT_LENGTH` (**256** - far above any legitimate left-pad, which is tens of characters for a zero-padded SSN or phone, and far below an allocation that matters) is rejected. Only a positive-integer `length` ever reaches `padStart` - `padLeftFactory` throws on a non-number, non-integer, or non-positive value before allocating, and that runtime check remains as the backstop for the operator-local `standardization` path, which never reaches this schema - so bounding positive integers above the ceiling closes the whole allocation vector; a malformed value is left to that runtime check, whose clean-abort path is unchanged. A legitimate `pad_left` parses and runs unchanged, preserving the cross-party receipt hash.

The second is `parse_date`'s `inputFormat` and `outputFormat`. `parse_date` builds a regex from `inputFormat` (compiled once per distinct transform array, memoized like the other steps) and assembles its output from `outputFormat` once per matched row. The size of those values still drives cost: a long `inputFormat` compiles a larger regex, and a long `outputFormat` allocates a larger output per matched row, so a per-step refine on `TransformStepSchema` caps each format string at `MAX_DATE_FORMAT_LENGTH` (**256** - far above any real date layout like `MM/DD/YYYY` or `YYYY-MM-DD`, yet small enough that the compile and per-row output stay cheap). Only a string value drives this cost; the factory treats a non-string as an empty/absent format, so a non-string is left to it unchanged, as a malformed `pad_left` length is. The format's SHAPE - the adjacent `(\d{1,2})` groups its `MM`/`DD` tokens expand into, which catastrophically backtrack on `new RegExp` at a length well under this cap - is no longer a separate control: `parse_date` compiles its regex under the linear-time engine (see [Transform-regex linear-time dialect](#transform-regex-linear-time-dialect)), which bounds the shape by construction. `parse_date` is not screened by the dialect gate (its library-generated regex is always in-dialect); its safety is the linear-time engine plus the 256-character format cap, which keeps the generated regex small and low-ambiguity by construction (only bounded `\d` quantifiers, never an unbounded quantifier over a sub-expression), so its per-row cost stays sub-millisecond on realistic input. This length cap is therefore now a pure work-SIZE bound, not a backstop against a backtracking blow-up.

The severity mirrors the ReDoS sibling: a fail-open denial of service reachable from the authenticated counterparty, bounded to DoS (no data, no code execution), and not meaningfully self-inflicted - a human reviewing the consent screen cannot vet a numeric `length` or a date-format string for an allocation or compile blow-up, and the handshake authenticates identity, not that the authored terms are benign. The bound is fixed defense-in-depth, fail-closed, not a semantic limit. The sibling numeric and expansion vectors audited alongside it are latent, not live, and carry their bound into their own implementation: `substring` reads a partner `length` but slices with `String.slice`, which cannot exceed its input; the `split_on` fan-out cross-product and the `generateFuzzyComparisons` expansion (`transpositions` / `edit_distances` / `adjacent_years`, board item 200737599) are gated behind unimplemented features and must be bounded when that fan-out ships.

## Display sanitization escape format

The display sanitizer escapes a string for operator-facing output by replacing every byte or code point that is not printable ASCII - C0 and C1 control characters, DEL, and any non-ASCII code point - with a hex escape: `\xHH` for a code point <= 0xFF, `\uHHHH` for a code point <= 0xFFFF, and `\u{HHHHH}` for an astral code point above 0xFFFF; a literal backslash is doubled (`\\`), and printable ASCII (0x20 to 0x7E) is otherwise left unchanged. The output is truncated to a bounded maximum length with a visible truncation marker. It is a one-way display transform: the escaped form is never parsed back, never used to build a filesystem path, and never used in an equality or hash comparison - those always use the original bytes - so escaping changes only what an operator sees, not how a value matches or routes.

The transform is applied ONCE per value, at the sink that shows it, on every route the assignment below governs; the routes that do not yet meet it are enumerated at the end of this section rather than left implicit. Every escape doubles a literal backslash, so a value escaped at two altitudes reaches the operator with a backslash count that no longer matches the bytes it names - one backslash in a partner filename shown as four, in a message telling the operator to go and delete that file. The two altitudes are therefore assigned rather than left to each call site: a fragment interpolated into an `Error` message or `cause` is composed RAW and escaped once by `sanitizeErrorForDisplay` where the error is rendered (which also caps each cause-chain link and strips PEM/OpenSSH private-key blocks); a value that reaches a log, a console, or a UI element without ever becoming an `Error` is escaped by `sanitizeForDisplay` at that call site, which is its sink. Rendering a raw error at a sink is banned by an ESLint rule over `packages/core/src` and `apps/cli/src` (excepting the three parse chokepoints those blocks already ignore, which carry no display sink), and the CLI integration console sentinel fails on any captured line carrying a byte outside printable ASCII once the `\ncaused by: ` framing the cause-chain renderer emits between links is removed - the framing is removed before the test rather than exempted from it, so a forged log line of printable ASCII plus a bare newline still fails. Both halves are bounded. The rule matches the raw error where it sits directly in a sink argument and does not follow it through an intermediate local, a method call on the message, or a container the sink unpacks, since that would need taint analysis TypeScript cannot run; the sentinel observes only `console` calls, so a direct `process.stderr.write` is outside it, as is a dependency that writes the file descriptor itself. The sentinel's framing strip is also a literal one with no notion of who emitted the sequence, so a line whose unescaped payload itself contains `\ncaused by: ` passes the byte test. Neither is a claim about every byte that lands on the terminal.

Three routes still escape at composition and are escaped again at their sink, so a value crossing them makes two passes. All three predate the assignment above and are recorded rather than closed, because each fix changes a published surface or needs a split this section's rule does not by itself decide.

The compatibility `warnings` that `validateCompatibility` returns are handed to the caller as display text, so that composition is their sink, while the CLI escapes each warning again as it reaches a log line and the machine-interface event stream. This one is inert: every value interpolated into a warning is schema-constrained to a shape the escape does not rewrite, which is enforced by a test rather than assumed. Closing it means changing either the `@psilink/core` return contract or the escaping the event stream applies to every warning source.

`describeDecodeError` escapes each Zod issue-path segment, and `endpointKeyError` escapes the rejected key names it relays; both then reach the browser directly - where that composition genuinely is the sink, and removing it would put partner-controlled bytes into the DOM - and, on the CLI, an `Error` that `sanitizeErrorForDisplay` escapes a second time. This route is NOT inert: a partner-controlled invitation key carrying one literal backslash reaches a CLI operator showing four. Closing it means splitting the helper per route, as the transports already do for a value that feeds both a log and an error.

`reconcileHostKeyFingerprints` escapes the server-controlled key type, which the CLI then hands to both a log line (correctly single-escaped) and the `--event-stream` warning, where `buildWarningEvent` escapes it again. Closing it is the same published-surface question as the compatibility warnings.

## SFTP fatal-packet crash safety

The size and liveness bounds above turn a hostile server's behavior into a bounded failure, but they leave one behavior unbounded: a process crash, which is neither a memory nor a time exhaustion. The SFTP adapter drives the raw ssh2 `SFTPWrapper` directly (for `list()`, `createExclusive()`, and the streamed `get()`), and after the session connects that wrapper carries no `'error'` listener of its own - ssh2's `Client.sftp()` attaches a setup-time listener but strips it before handing the wrapper back, and `ssh2-sftp-client` attaches `'error'` handlers only to the SSH `Client` object and to per-operation read/write streams, never to the wrapper. So when a server returns a malformed SFTP reply packet (a malformed NAME, HANDLE, or DATA packet, an unknown packet type, or a duplicate VERSION packet after the session is already ready - a malformed *first* VERSION instead rejects `connect()`, whose setup-time listener is still attached then, so it never reaches this listener-free state) - or faults the framing layer itself with an over-long packet, which trips the length-prefix check before any request id is consumed - ssh2's fatal-error path emits `'error'` on a listener-free `EventEmitter`, which Node escalates to an uncaught exception - crashing the CLI outright, before the lock-file and temp-file cleanup and the typed exit-code mapping that an orderly failure runs. The adapter closes this by attaching a single guarded `'error'` listener to the wrapper at connect time (once per wrapper instance, so a reconnect's fresh wrapper is re-guarded and a repeated connect does not duplicate the listener), so a fatal protocol error is handled rather than fatal.

A handled fatal error leaves the session dead but the process alive. ssh2's `doFatalSFTPError` emits the `'error'`, destroys the wrapper, then calls `cleanupRequests`, which fails the callback of every request still registered. What bounds an *in-flight* `list()` or `get()` depends on which request carried the fatal packet, and the realistic case is not `cleanupRequests`: when the malformed packet is the reply to the in-flight request itself, ssh2 has already deleted that request from its pending table by the time `doFatalSFTPError` runs. The `NAME` and `DATA` handlers delete it unconditionally up front, *before* the parse/check that triggers `doFatalSFTPError`; the `HANDLE` handler deletes it inside its own malformed branch (on a defined request id), immediately before triggering it. The placement differs but the net effect is the same: `cleanupRequests` finds nothing left to fail for that request and the in-flight callback never fires - the operation is bounded by the adapter's 60-second wall-clock deadline (`list()`'s deadline, the capped `get()`'s idle window, or the uncapped `get()`'s whole-operation deadline), not by `cleanupRequests`. `cleanupRequests` does fail an in-flight callback promptly only in the other cases: a fatal error that arrives on a *different* request id, or a connection-level fault (such as an over-long packet, which faults the framing/length-prefix layer before any request id is consumed), leaves the in-flight request registered for it to fail. Either way the in-flight operation is bounded - the 60-second deadline is the bound that covers the realistic in-flight case, so it is load-bearing and must not be removed on the assumption that `cleanupRequests` covers in-flight operations. The listener also captures the cause, which bounds the *next* operation: every server-driven method consults this captured error at entry and short-circuits before issuing a request the dead channel can never answer. `list`, `get`, `createExclusive`, `put`, `delete`, `rename`, and `exists` reject promptly with the same terminal `TransportOperationStalledError`; `safeDelete`, whose contract forbids rejecting (callers run it in `catch` blocks), instead resolves promptly as a best-effort no-op. This entry guard matters beyond saving a deadline wait, because after a fatal error ssh2 destroys the SFTP channel but the underlying TCP/SSH socket stays up (a hostile server keeps it alive), so an unguarded write, stat, or delete would buffer its request on the closing channel and hang until its own per-operation bound fires (60 s) rather than failing at once - turning the crash, once fixed, into a teardown that stalls for the full bound, since `FileSyncConnection.close()` drives `safeDelete`/`delete` during cleanup. The guard converts that stall into a prompt, orderly failure.

This bounds the malformed/fatal-packet crash and, once a fatal error is known, every server-driven operation: the entry guard short-circuits the next read or write rather than buffering a request the dead channel can never answer. The one behavior the guard cannot catch - a hostile server that withholds a write, stat, or delete callback *without* any protocol error, so no fatal `'error'` fires and `put`/`delete`/`rename`/`exists` never short-circuit at entry - is not left unbounded: each of those operations now carries its own per-operation bound (the 60-second deadline for `rename`/`delete`/`exists`, the 60-second progress idle window for `put`) that fails the withheld callback terminally, with the whole-exchange budget backstopping beneath. The best-effort `safeDelete` carries the same 60-second deadline so a teardown delete cannot be the soft target left on the coarse budget while every other write op fast-fails, but - because its contract forbids rejecting - it swallows the deadline's stall error and resolves rather than surfacing it, bounding the wait without breaking the never-reject guarantee its `catch`-block callers rely on. The entry guard's role, now that those bounds exist, is to spare the 60-second wait once a fatal error is already known, not to be the sole thing standing between the call and an indefinite hang.

The bounds above reach past the public `ssh2-sftp-client` API and drive ssh2 internals directly, so they rest on premises about ssh2's internal behavior that an upgrade can silently break. Before raising either `ssh2` or `ssh2-sftp-client`, follow the upgrade checklist in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md#upgrading-the-sftp-stack-ssh2--ssh2-sftp-client), which names the internal premises, the source files to re-read, and the contract-assertion test that fails red on a lifecycle change.

## Authenticated abort marker

A distinct channel control is the **authenticated cross-party abort marker**, the one mechanism here that is not a bound on a hostile operation but an authenticated signal between the two honest parties. On the file-sync transports a failed exchange leaves the waiting peer with no in-band notice that its partner has given up: it can only wait out the full peer-inactivity budget (default one hour) and then print a generic peer-silence hedge. When a party fails terminally with its directory still writable, it now writes a best-effort `<id>-abort.json` carrying a 32-byte token `HKDF(sessionKey, "psilink-abort-token-v1:<role>")`; a waiting peer that reads a `<peerId>-abort.json` whose token verifies against its own locally-derived peer token fails fast with a definitive `PeerAbortError` (exit 69) instead. The token is the authentication: a hostile filedrop/SFTP admin can write or rename any file in the rendezvous directory, but cannot produce a token that verifies without the per-session session key, so cannot forge an abort against a live peer. The label is domain-separated from the other session-key derivations - exact-distinct and prefix-free from the AEAD `psilink-aead-v1:<context>` and the `psilink-shared-secret-rotation-v1` labels - so an abort token can never collide with or substitute for an AEAD key or the rotation secret. The comparison is constant-time and length-safe, and the read fails closed on every absent, oversized, malformed, wrong-version, or non-matching input. The per-direction (role) binding makes a captured marker renamed to the other party's name verify under the wrong token and fail; the per-session ephemeral key makes a marker captured from one exchange inert in another.

The marker is best-effort and carries no cause, both deliberate. Its absence is strictly uninformative: a deleted, withheld, or forged marker simply degrades to the pre-existing peer-silence timeout and hedge - it never reads as success - so a hostile admin can at most *suppress* the fast-fail optimization (the behavior before this feature existed), never forge an abort or turn a failure into an apparent success. It carries no cause because the cause is not actionable to the waiting party - which holds no local error and must contact its partner regardless - and a plaintext cause on the untrusted channel would only widen disclosure; the token itself is a one-way HKDF output that reveals nothing about the session key or any other derived key. Because the marker is re-read every poll cycle, it is capped small - a pre-`get()` listed-size refusal and a bounded `get()`, both at 1 KiB rather than the ~512 MiB frame maximum - so an admin-plantable file cannot become an availability vector; the write is short-budgeted on both its `put` and `rename` (a few seconds each) so a sick directory cannot hang teardown. The mechanism is file-sync only: the connectionless file transport is the only one with a parked-waiter problem, since a WebRTC peer's death drops the DTLS data channel and surfaces promptly; a future cross-transport abort would instead carry a protocol-layer error kind rather than an on-disk marker.

## SFTP host-key verification

The controls above defend against a hostile administrator of the server a party has correctly reached; a distinct control defends against reaching the wrong server. On the SFTP channel an operator may pin the server's host key by setting `connection.server.host_key_fingerprint` to its OpenSSH SHA256 fingerprint -- or to a non-empty list of them (see *Multiple pinned fingerprints* below) -- and every connection then verifies the presented host key against the pinned fingerprint(s) before authentication, aborting unless it matches one. This is the SFTP analogue of the certificate pinning the signing identity uses (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#receipt-signing-identities)): trust comes from a fingerprint rather than a certificate authority, and it replaces SSH's *silent* trust-on-first-use with an explicit, enforced pin -- supplied out-of-band, or established by a confirmed first-use prompt (below) and then verified on every subsequent run -- so a man-in-the-middle or a substituted server presenting its own host key is detected rather than silently trusted.

The fingerprint is `SHA256:` followed by the unpadded *standard* base64 (alphabet `[A-Za-z0-9+/]`, not base64url) of the SHA-256 digest of the raw SSH host-key wire blob -- byte-identical to what `ssh-keygen -lf` and OpenSSH clients display, so an operator pins exactly the value those tools print. It is validated at config-parse time by `HOST_KEY_FINGERPRINT_REGEX` (`/^SHA256:[A-Za-z0-9+/]{42}[AEIMQUYcgkosw048]$/`): the final character's class is restricted because the last 6-bit base64 symbol of a 32-byte (256-bit) value carries two low bits that are zero in the canonical encoding, so only those sixteen symbols are valid there. A bare 43-character base64url value -- the shape of a signing `partner_fingerprint` -- is detected separately and rejected with a message naming that confusion, since the two fingerprints use different alphabets and one is easily pasted for the other.

Verification runs in ssh2's `hostVerifier` callback, which the SSH handshake invokes with the raw host-key blob before authentication. psilink always installs a callback (in one of three forms below) and installs it *after* applying `provider_options`, so a provider option can neither override nor disable it; the `provider_options` allowlist is in any case default-deny and drops `host_verifier`/`hostVerifier` and `host_hash`/`hostHash`. `hostHash` is never set: setting it would make ssh2 pre-hash the key before the callback, destroying the raw bytes the fingerprint is computed over. The three forms: with a pin set, an *enforcing* verifier computes `SHA256:` + base64(SHA-256(blob)) once and compares it against each pinned fingerprint with a constant-time byte comparison over the decoded digests, accepting on the first match (nothing secret is compared -- a host key and its fingerprint are both public -- so the constant-time comparison is house-style hygiene for digest comparisons, not a timing-oracle defense, and the short-circuit on the first match is likewise not a timing concern); with no pin, a *fail-closed* verifier computes the presented fingerprint into the error and refuses (see the no-pin default below); and on the deliberate first-use probe, a *capture* verifier records the presented fingerprint and refuses, so the probe learns the key without authenticating (see first-use trust below).

**Multiple pinned fingerprints.** `host_key_fingerprint` accepts either a single fingerprint or a non-empty list, validated entry by entry at config parse (each against `HOST_KEY_FINGERPRINT_REGEX`, with the signing-`partner_fingerprint` confusion detected per entry; an empty list is rejected, since it would pin no key while reading as "pinned"). The enforcing verifier accepts a presented key matching *any* listed fingerprint, which gives zero-downtime host-key rotation: an operator stages the incoming key alongside the current one for the rekey window so either is accepted with no failed exchange in between, then drops the old entry after the cutover. The single-fingerprint form is the one-element case and behaves identically. The verifier records the *matched* pin as the observed host key (`FileSyncConnection.observedHostKey`) -- the one fingerprint the server actually presented, not the whole set -- so the cross-party reconciliation below still compares one observed key per party even when each party pins several. The set membership lives in one tested primitive (`matchHostKeyFingerprint`, the set extension of `verifyHostKeyFingerprint`, which delegates to it), so there is a single decode-and-compare implementation. On a mismatch the error names the presented fingerprint and the entire pinned set.

The control is fail-closed on every path. A mismatch, a malformed or empty blob, or any error inside the callback results in `verify(false)`, which ssh2 raises as a fatal handshake error whose message contains `Host denied (verification failed)` -- before authentication, so no credential is presented to an unverified server. The CLI adapter treats that rejection as terminal and does not retry it: retrying would only re-run the key exchange against the same untrusted host. The `Host denied` message fragment is an ssh2 internal premise recorded in the [SFTP-stack upgrade checklist](DEPENDENCY_PINS.md#upgrading-the-sftp-stack-ssh2--ssh2-sftp-client); even if a future version renamed it, core re-wraps the same rejection into an `SFTP host-key verification failed:` message and the outcome is unchanged, only slower. The mismatch message names the presented fingerprint and key type so an operator can distinguish a legitimate key rotation from an attack; the key type is decoded from the server-controlled blob, so it is quoted in the message and escaped at the display boundary before it reaches the operator's terminal or log. A changed key is never auto-accepted -- there is no standing always-accept flag (which would be permanent trust-on-first-use disguised as protection). The recovery for a legitimate rotation is a deliberate re-pin, modeled on ssh's `known_hosts` flow: verify the new fingerprint out-of-band, then add it to `connection.server.host_key_fingerprint` (alongside the current pin for a staged rotation, or in place of it) or remove that field and re-run interactively to re-establish trust on first use (which overwrites the stored pin).

Each pinned fingerprint may be supplied as an `@`-file reference (`@/path/to/fingerprint`) for operators who keep it in a read-only secrets mount; in a list, entries may freely mix literals and `@`-file references. Because `@`-file resolution runs after parsing, a literal `@path` -- which cannot match the `SHA256:` format -- is exempt from the parse-time format check, and each resolved file's contents are re-validated against `HOST_KEY_FINGERPRINT_REGEX` at resolution: a malformed or empty secrets file fails as a `UsageError` (exit 64) naming the offending reference, rather than as a confusing host-key mismatch at connect time.

Verification applies to the CLI `sftp` channel only. A file-drop makes no SSH connection, and the browser/proxy SFTP path does not run ssh2's `hostVerifier`. An attacker cannot induce the unpinned state to inject their own key, because the pin is configured out-of-band (or established on first use, below) and the invitation endpoint schema rejects a `host_key_fingerprint` field outright (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#transport-layer-authentication)).

**No-pin default: fail-closed.** When no fingerprint is pinned, `FileSyncConnection.open` installs the fail-closed verifier, which refuses the connection before authentication (so no credential reaches an unverified server) with an error naming the presented fingerprint to pin. This replaces the earlier warn-and-proceed default, which trusted any presented key. The flip is deliberately gated on first-use existing (below): a pin can only be reliably obtained once first use exists, so flipping the default earlier would have stranded every unpinned config with no recovery path.

**First-use trust (ssh-style).** An operator who cannot obtain the fingerprint out-of-band can still reach the verified-on-every-subsequent-run state by establishing the pin on a deliberate first connection. Every CLI command that opens an `sftp` connection -- `exchange`, the online `invite`/`accept`, and a zero-setup exchange -- runs this flow before connecting (a shared `establishHostKeyTrust` step):

- On a TTY (interactive), it *probes* the server: a throwaway connection whose capture verifier records the presented host key and immediately refuses, so the key is learned without presenting a credential and without waiting on a user prompt inside the handshake (which would race ssh2's `readyTimeout`). It then surfaces the fingerprint and key type, prompts for confirmation, and on a yes pins the fingerprint into `connection.server.host_key_fingerprint` in memory and proceeds with a real, now-enforcing connection. Because that real connection re-verifies the just-pinned key, a key swapped between the probe and the connect is still caught (the same brief TOCTOU window as `ssh-keyscan`-then-`ssh`).
- Non-interactively (no TTY -- an automated run, or one piping its CSV through stdin), it does not prompt and does not auto-accept: it fails closed with an actionable error naming the recovery (run once interactively to pin, or set `host_key_fingerprint` out-of-band). This is the same fail-closed posture as the no-pin default, surfaced earlier and with CLI-specific guidance.

How the confirmed pin reaches disk depends on the command: `exchange` reads an existing `psilink.yaml` and does not re-write it, so the pin is written there in place (preserving comments); the online `invite`/`accept` and a zero-setup run with `--save` carry the in-memory pin into the configuration they write after the handshake; a zero-setup run without `--save` trusts the key for that one exchange and persists nothing. The probe reuses the exact connect options (algorithms included) the real connection uses, so both negotiate the same host-key type and the pinned key is the one later runs verify.

**`probe-host-key` and console probe-to-fill.** The same capture verifier is exposed as a standalone CLI command, `psilink probe-host-key <sftp-url> [--json] [--connect-timeout <dur>]`: it builds a minimal `{channel: "sftp", server: {host, port?, username}}` connection from the URL -- NO credential, and no operator- or URL-supplied username: ssh2 requires a username string to `connect()`, so a fixed placeholder is set, and because the capture verifier calls `verify(false)` at host-key verification (before the SSH userauth phase), that placeholder is never sent to the server -- runs `probeHostKeyFingerprint`, validates the result against `HOST_KEY_FINGERPRINT_REGEX`, and prints it. `--json` emits exactly one stdout line `{"fingerprint":"SHA256:...","key_type":"..."}` (snake_case, the machine form); the human form escapes the server-controlled key type through `sanitizeForDisplay` as `sftpSession.ts` does. Exit codes mirror `exchange`: a transport failure (unreachable, refused, timeout) is `69`, a usage error (a non-sftp scheme, a malformed URL) is `64`. The command establishes no trust and pins nothing: it only reads a key over the same untrusted network the exchange will use.

The console repurposes it as *probe-to-fill*, the browser analogue of first-use for an SFTP connection authored in-app. The appliance's Node server cannot probe SSH in-process -- core has no SSH implementation and the `ssh2` stack is exact-pinned to `apps/cli` only, which the web app must not import -- so it spawns this command (the image already spawns the CLI for every SFTP op) and re-validates every field at the trust boundary: the fingerprint against the same regex, the `key_type` against a length (<= 64) and charset bound (server-controlled bytes, carried as a JSON string), and it DISCARDS the child's stderr entirely (it can carry server-controlled bytes) and drives a watchdog (SIGTERM at ~15 s, SIGKILL after a grace) so the endpoint's latency is bounded above the child's 10 s `readyTimeout`. The reconciled outcome is a typed result -- `ok` / `unreachable` (exit 69) / `timeout` (watchdog kill) / `error` -- surfaced over `POST /api/jobs/sftp/probe` (the SSRF-bounded, single-flight, stateless endpoint specified in [SERVER_JOB_API.md](SERVER_JOB_API.md#probing-the-server-host-key)). The pin stays MANDATORY: probe-to-fill only fills the one required `host_key_fingerprint` field a paste would, beside the paste field rather than replacing it, and the fail-closed backstop (the `PUT /api/jobs/sftp` literal-pin check, the schema, and the always-emitted `--server-host-key-fingerprint` on a zero-setup run) is unchanged. The confirm is framed as a comparison against the value the server operator published, never a trust judgement; the direct-exchange path -- where the host key is the only protection -- additionally gates the fill behind an out-of-band-checked affirmation, while the invitation path's lighter confirm points at the cross-party reconciliation below.

**Cross-party fingerprint reconciliation.** Pinning above is each party's *local* decision: the two parties pin the same server independently, at different times on different machines, and nothing otherwise compares their views. A one-sided interception -- one party reaching an attacker's server while the other reaches the real one, each having pinned the key it was shown -- is therefore invisible to both, as is a server host-key rotation that happens between the two parties' setups. To close this, each party advertises the fingerprint and key type it observed (`FileSyncConnection.observedHostKey`, recorded by the enforcing verifier on the pin-matched success path) inside the authenticated post-handshake terms exchange, and the two compare. The advertisement rides the terms exchange -- the one bidirectional round-trip both parties always perform, the same carrier as the `--save` intent -- as an optional `hostKey: { fingerprint, keyType }` field on the terms message; a party that observed no host key omits it. Reconciliation lives in `reconcileHostKeyFingerprints` and is wired through `runExchange`.

Placement is load-bearing: the field is consumed only from the terms exchange, which on the authenticated path runs inside the per-direction AEAD (it is keyed from the X25519 session key), so the advertised value is authenticated and an unauthenticated party cannot forge or rewrite it. The CLI threads its observed key into `runExchange` only when that AEAD wrap is in force (`secure` set); a zero-setup (unauthenticated) exchange advertises nothing, because over an unauthenticated channel an active man-in-the-middle could simply rewrite the advertised value to match and suppress the divergence. This is the post-authentication, in-band complement to the endpoint decision in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#invitation-contents-and-confidentiality): the invitation endpoint still carries no server-identity material, and reconciliation adds its check strictly after the authenticated handshake instead.

The comparison is a verbatim string equality on the fingerprint (a host key and its fingerprint are both public, and the result drives only a warning, not a trust decision, so no constant-time compare). It surfaces a divergence -- never an abort, in keeping with the honest-but-curious model -- as a warning naming *both* observed fingerprints, with wording that distinguishes the two cases the difference can represent: when the key *types* match, the difference is narrowed to a server rekey between the two setups or a one-sided interception; when the key types differ, the message additionally surfaces the benign multiple-host-key case, because a server that presents more than one host key may legitimately show each party a different one, so a type difference alone is not evidence of an attack. A party that observed no host key (a file-drop mount or the browser/proxy SFTP path) advertises nothing, and a one-sided absence reconciles to no divergence rather than a false positive. The advertised field is fail-soft: a malformed or over-bound `hostKey` (reachable only from a non-conforming or future-versioned peer, since the field rides the AEAD) is read as absent rather than aborting the linkage, so this advisory check can never turn a valid exchange into a hard failure. That drop is silent toward the protocol, but `exchangeTerms` still distinguishes a present-but-malformed advertisement (a `hostKey` on the wire that fails validation) from a genuine absence and reports it out as `partnerHostKeyMalformed`; the CLI logs the malformed case at debug, so an operator can tell a non-conforming peer from one that simply observed no host key (a file-drop or proxy path), while the benign no-host-key path stays quiet and the level stays low enough that a version-skew does not warn on every exchange. The dropped bytes are deliberately not logged -- they are unusable and partner-controlled, so echoing them would widen disclosure and risk log injection. Both parties' key types are server-controlled and are routed through `sanitizeForDisplay` before they enter the warning. As net-new security behavior layered on the host-key control, this reconciliation is in scope for the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

# Web signaling surface bounds

The bounds above harden the CLI's file-sync transport against a hostile server admin. The web application's bundled PeerJS-compatible signaling server is a separate surface with a different model: it is untrusted by design (see the **Channel security** and **Third parties** overviews in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security)), relaying only opaque rendezvous-setup messages between two browsers that authenticate each other directly, so the residual exposure on its WebSocket upgrade surface is resource exhaustion, not access to any party's data. The guards below are defense-in-depth against that nuisance, enforced in the application unconditionally; the deployment-dependent Origin and per-address controls are the reverse proxy's responsibility and are described operationally in [DEPLOYMENT.md](../DEPLOYMENT.md#hardening-the-signaling-surface), not here. All values are fixed constants, not configurable, for the same reason as the file-sync bounds: a configurable bound risks an operator raising it enough to reintroduce the denial of service.

**Upgrade-handshake timeout.** The shared HTTP server bounds a pre-101 upgrade handshake with a **10-second** header timeout (`SIGNALING_HEADERS_TIMEOUT_MS`) and a **15-second** request timeout (`SIGNALING_REQUEST_TIMEOUT_MS`), set in `apps/web/server/upgradeHardening.ts`. A client that opens a connection and dribbles -- or never finishes -- its request headers is closed server-side rather than held open. The entry attaches its own `clientError` handler to perform the close rather than relying on Node's built-in default close-on-`clientError`, because that default is silently disabled the moment any other `clientError` listener is attached (an embedding framework, or under test a loaded `ws`, may attach one). Node checks the header and request timeouts on a periodic sweep (default 30 seconds), so the effective close is the bound plus up to one sweep interval -- coarse, which is sufficient for a resource-exhaustion guard.

Those two timeouts only arm once HTTP request parsing has begun, so they do not cover the cheapest hold of all: a peer that completes the TCP handshake and then sends nothing, which has no request for them to bound and would otherwise sit until the OS reaps the idle socket. A **10-second** per-socket idle timeout (`SIGNALING_PREHANDSHAKE_IDLE_MS`, applied on each new connection) closes that case, on its own precise timer rather than the periodic sweep. It covers only a socket that reads no bytes: a peer that dribbles actual request bytes resets this idle timer and is instead bounded by the header and request timeouts above (whose deadlines are absolute from the start of the request, not reset by each byte). `ws` resets the socket timeout to `0` the instant a socket completes the 101, so an established WebSocket -- governed by the `ws` close timer and the liveness reaper below -- is never cut by it; only the pre-handshake window is bounded. This guard would need revisiting only if a real client could legitimately take longer than the bound to send its upgrade request, which a single small WebSocket handshake never does, or if `ws` stopped resetting the socket timeout on upgrade (a regression test pins that an established connection outlives the bound).

**Per-message size cap.** Each inbound frame is capped at the `ws` layer so an over-cap frame is refused (close code 1009) before the message handler parses it. This control and its constant (`MAX_SIGNALING_PAYLOAD_BYTES`, in the vendored `services/webSocketServer/index.ts`) are specified above under [Signaling-server inbound frame bound](#signaling-server-inbound-frame-bound), alongside the file-sync frame-size bound; it is one of this surface's bounds, closing the single-oversized-frame crash and memory pin from an unauthenticated peer.

**Two-tier liveness reaping.** A registered client that has not yet sent any inbound frame is reaped after **20 seconds** (`unconfirmed_timeout` in the vendored `config/index.ts`); once it sends its first frame it is marked confirmed and governed by the existing **90-second** `alive_timeout`, refreshed by each heartbeat. The split ties reaping to liveness rather than a flat wall-clock: a socket that registers under the public realm key and then goes silent -- an abandoned or junk registration -- is cleared in 20 seconds instead of squatting a slot for 90, while a real peer is never cut short however slow the human-paced exchange. The reap is keyed on the WebSocket heartbeat, which is independent of and far faster than WebRTC pairing: the PeerJS client sends its first heartbeat one cadence interval after the socket opens and then every interval, so even an inviter that waits minutes for its partner has long since graduated to the generous window. The cadence is psilink-owned, not a transitive dependency default: the web client sets `pingInterval` explicitly to **5 seconds** (`PEER_PING_INTERVAL_MS` in `apps/web/src/psi/rendezvous.ts`) rather than relying on the `peerjs` default, a default parameter inside a bundled file that an upstream version change could shift (now an exact-pinned, review-gated `peerjs` bump rather than a silent caret drift -- see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md#upgrading-the-peerjs-stack-peerjs--peerjs-js-binarypack)). The 20-second value is four times that 5-second first-heartbeat cadence, leaving margin for a slow socket open and one missed heartbeat. The unconfirmed window must stay comfortably above the first-heartbeat delay so a real peer always graduates before it fires; that `unconfirmed_timeout >= 4x PEER_PING_INTERVAL_MS` relationship is pinned by a unit check (`test/unit/signalingReaping.test.ts`), so a change to either value -- the reap window or the cadence -- that narrows the margin fails CI rather than only the weaker `unconfirmed_timeout < alive_timeout` invariant. Because the cadence is now set explicitly, a `peerjs` minor bump no longer shifts it out from under the window at all; tracking a future upstream default change is a deliberate edit to `PEER_PING_INTERVAL_MS`, which the same check then re-validates against the window. The check guards the numeric margin but not the *meaning* of the cadence, so -- as with the SFTP-stack internal premises -- a `peerjs` bump must still re-confirm two behavioral premises this control rests on: that `pingInterval` remains the sole client-originated liveness signal (the reaper keys only on observed inbound frames, and on an otherwise-idle registered peer the heartbeat is what produces them; a field rename instead surfaces as a TypeScript error on the `PeerOptions` literal), and that no upstream WebSocket-layer keepalive was introduced that would hold a socket open independently of that heartbeat -- either change would decouple liveness from the cadence the window is sized against, which neither the type check nor the margin check would catch. The check runs on the existing 300 ms sweep (`checkBrokenConnections`), so the effective reap is within ~20.3 seconds. This bounds the cheap fire-and-forget / register-and-idle flood; a flood that keeps each socket alive with heartbeats is bounded instead at the reverse proxy (per-address limiting, see [DEPLOYMENT.md](../DEPLOYMENT.md#hardening-the-signaling-surface)), since the application cannot distinguish it from a live peer. The only in-application ceiling on such a maintained flood is the global `concurrent_limit` (default 5,000 registered clients), which is shared across all clients, so on a deployment with no proxy a maintained flood degrades to global connection exhaustion rather than per-address throttling -- the reason per-address limiting is delegated to the proxy rather than attempted here.

**Relay queue bounds.** When a client addresses a signaling message to a destination id that is not currently registered, the relay holds it briefly in a per-destination queue for a reconnect. Left unbounded, a registered client could spray messages to arbitrarily many made-up destination ids -- each allocating a queue -- or grow one queue without limit. The realm caps the number of distinct queued destinations at **1,000** (`MAX_OUTSTANDING_QUEUES`) and the depth of any one queue at **100** messages (`MAX_MESSAGES_PER_QUEUE`), both in `models/realm.ts`; a message past either bound is dropped. Both sit far above any legitimate rendezvous, which queues at most a handful of frames for a momentarily-absent peer, so a drop only ever affects a spammer or a peer already far past needing a reconnect hold.

The message-count cap alone, though, leaves a queue's resident ceiling high: a frame is capped at 256 KiB on the wire (`MAX_SIGNALING_PAYLOAD_BYTES`), but V8 stores a JavaScript string as two bytes per character whenever it holds any non-Latin1 character (>= U+0100), so one buffered frame can occupy roughly **512 KiB** of heap -- about **50 MiB** per queue (100 frames), **50 GiB** across the full 1,000 -- since a flood of max-size frames is bounded only in count, not bytes. A third bound, **524,288 bytes** (512 KiB, `MAX_QUEUE_BYTES` in `models/realm.ts`), caps each queue's total buffered bytes directly: before a frame is queued, its resident size is added to the queue's running total, and the frame is dropped if that would exceed the cap. The size (`messageByteSize`) is measured as UTF-16 code units times two, not UTF-8 -- a UTF-8 measure would undercount a non-Latin1 payload by up to 2x and let it occupy roughly twice its measured size, so counting the worst-case two-byte residency bounds the real heap regardless of payload charset. This holds the per-queue ceiling at 512 KiB and the global ceiling at about **512 MiB** (1,000 queues x `MAX_QUEUE_BYTES`). The cap is twice the wire frame cap, so any single legal frame is always holdable, and real signaling frames are KB-scale, so a queue still holds dozens; a queue drained by a reconnecting peer releases the read frames' bytes from the running total, so it accepts fresh frames again rather than staying wedged at the cap. The ~5-second read-cold expiry (the `MessagesExpire` prune) still clears an unread queue regardless, so these caps bound the transient peak within a window rather than a permanent residency.

**Peer-id length cap.** The per-queue byte cap above sizes a queued frame by its string fields' resident bytes, `src` included -- and the server overwrites `src` with the connecting client's own id (the `message.src = client.getId()` stamp in `services/webSocketServer/index.ts`). That id arrives as the `id` query parameter of the WebSocket upgrade request and, left to itself, is bounded only incidentally by Node's ~16 KiB HTTP header-size limit on the upgrade URL, not by any application bound. So a peer that registers a multi-KiB id and then addresses a near-maximum-payload frame to an absent destination produces a single frame whose `src` alone pushes it past `MAX_QUEUE_BYTES` -- the "any single legal frame is always holdable" property above rests on a queued frame's residency staying within twice its wire size, which the `src` overwrite is the one thing that can break. The same unbounded id is also retained in the realm `clients` map, a standing per-client memory surface (up to the `concurrent_limit` default of 5,000 ids x the incidental ~16 KiB ~= ~80 MiB). Each upgrade-handshake parameter -- `id`, `token`, and `key` -- is therefore length-bounded to **256 characters** (`MAX_HANDSHAKE_PARAM_LENGTH`, in the vendored `services/webSocketServer/index.ts`) where it is parsed in `_onSocketConnection`, before the id is stored in `clients` or used as `src`; an over-length parameter is refused with the same error-frame-and-close (`WS_PARAMETER_TOO_LONG`) as a missing one. The cap sits far above any legitimate id -- psilink's rendezvous ids are 32 hex characters (`deriveRendezvousPeerId`) and a PeerJS default id is a UUID (~36), so 256 is ~7x any real id and refuses no legitimate peer -- and well over an order of magnitude below the incidental header limit (~64x).

The `id` bound is the load-bearing one: it holds the `src` contribution to a queued frame at most `2 x MAX_HANDSHAKE_PARAM_LENGTH` = 512 resident bytes, a negligible fraction of the 512 KiB queue cap, so a real KB-scale frame from any accepted id stays holdable. (The byte cap's drop of an *adversarial* near-256-KiB frame is unaffected and stays benign: it loses only that peer's own reconnect-hold frame, never desyncing the accounting or amplifying memory.) `token` and `key` are bounded at the same parse point for a uniform "no handshake parameter is unbounded" invariant: `token` is likewise retained per-client in the `clients` map (the same standing-memory surface the id presents, which the cap cuts to ~5,000 x 512 bytes ~= ~2.5 MiB), while `key` is only compared against the realm key and never stored, bounded for symmetry. The addressed destination id (`dst`) is deliberately left unbounded here, not an overlooked sibling: unlike `src` -- which the server appends after the wire-frame cap is checked -- `dst` rides inside the client's own frame and is therefore already within the 256 KiB wire cap, and its residency both as a queue-map key and as a counted frame field is already governed by `MAX_OUTSTANDING_QUEUES` and `MAX_QUEUE_BYTES` with the read-cold expiry, so a separate length bound would be redundant. As net-new security behavior on an internet-facing surface, this control is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

# WebRTC data-channel inbound bound

The bounds above cover the signaling *socket* -- the broker the two browsers rendezvous through. The PSI payload itself never crosses that socket: it flows peer-to-peer over the WebRTC *data channel*, which is the surface this bound covers. The adversary here is the exchange counterparty, a mutually-distrusting peer (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)) -- authenticated by the X25519 handshake, but free to be hostile or buggy thereafter. The data channel is end-to-end confidential under DTLS, so neither the broker nor a TURN relay is in scope; the peer is.

No existing control reaches this transport. The web path discards the rotated key and declines the application-layer AEAD wrap under DTLS (`apps/web/src/psi/authenticateExchange.ts`, `requestEncryption: false`), so core's `EncryptedMessageConnection` and its ~512 MiB `MAX_FRAME_SIZE_BYTES` envelope -- a file-sync transport control -- never bind on the web path. (If the deferred web-encryption work, board item 195802633, ever forces the AEAD wrap on, that envelope would come into scope and could subsume part of this need; until then the wrap is declined, so this control stands on its own and does not wait on the encryption rework.) The only inbound limiters that do apply are core's count/structure bounds on the *parsed* payload-exchange message (the web wire is BinaryPack, not JSON, but those bounds act on the deserialized structure either way) and the `QueuedMessageConnection` message-count capacity -- none a byte-size bound. The large raw PSI set frame -- one party's full encrypted set as raw elliptic-curve points (~35 bytes/element; see [PROTOCOL.md](PROTOCOL.md#psi)) -- is carried as a single binary `Uint8Array` that, left unbounded, PeerJS reassembles with no byte cap.

The control lives in `apps/web/src/psi/boundedReassembly.ts` and bounds the receive path on several axes, each a fixed constant (not a configurable option, since a configurable bound risks being raised to reintroduce the denial of service) and each fail-closed with a terminal `protocol` `ConnectionError` -- the same class as core's inbound-buffer overflow, since every bound sits far above any legitimate frame so an over-bound frame is never benign. PeerJS chunks a binary frame larger than its ~16 KiB MTU into slices and reassembles them in `_handleChunk` (accumulating slices keyed by message id, `_chunkedData`), and `unpack`s every frame -- an unchunked one directly, or the reassembled buffer on completion -- into a JS structure in `_handleDataMessage`, with no cap on any of total wire bytes, deserialized structure size, retained chunk count, or concurrent reassemblies, and no eviction of a never-completed partial. `boundChunkReassembly` wraps *both* methods to add all of these *before* delegating to the original, so the offending chunk is never stored and the offending frame is never unpacked. Wrapping `_handleDataMessage` -- the sole unpack point, which both an unchunked frame and the reassembled-completion path flow through -- rather than only `_handleChunk` is load-bearing: the deserialized-structure attack below needs only a tiny frame, which is sent unchunked and never reaches `_handleChunk`.

**Wire-byte cap.** A running total of bytes across all in-flight reassemblies is bounded by **`MAX_WEBRTC_FRAME_BYTES` = 268,435,456 (256 MiB)**; a slice that would push it over fails closed rather than allocating proportional to the peer-chosen size. The total spans every in-flight reassembly, so this single bound caps a single oversized frame, a single big never-completed partial, and the aggregate of concurrent partials alike. Unlike the file-sync frame-size cap -- a *decode* ceiling anchored to Node's `MAX_STRING_LENGTH` -- this is a browser-tab *memory envelope*, in the spirit of the directory-listing cap: above the realistic largest legitimate frame, below a tab-crashing allocation. The largest legitimate inbound frame is the raw set frame above, carried as binary with no base64url 4/3 inflation (the data channel is binary, unlike the file-sync JSON-text wire); the 100 MiB CSV upload cap (`MAX_CSV_FILE_BYTES`) bounds a set to at most a few million unique key values, tens to low-hundreds of MiB, so 256 MiB (~4 million elements) sits above any realistic set while half the file-sync 512 MiB cap in deference to the tab's smaller heap. This counts *wire* bytes; the deserialized structure those bytes unpack to is bounded separately, next.

**Deserialized retained-byte budget.** The wire-byte cap alone is insufficient, because BinaryPack `unpack`s a frame into a JS structure *synchronously, before delivery and before any schema validation*, and that structure can be far larger than the wire. BinaryPack encodes an empty object or array in one byte but `unpack` allocates a real JS value per element, and the *retained* cost of that value varies by kind. Worse, an `array32` header eagerly allocates `new Array(N)` for its declared count *even when the elements are absent*, because `unpack` reads past the end of the buffer as zero rather than throwing. So a tiny wire frame of object/array headers -- an in-protocol shape, since the association-table and mapped-element frames are arrays of numbers/objects -- could deserialize to many GiB, and a flat per-value count (the prior value-count budget) charged the heaviest kind no more than the lightest.

Before delegating to `unpack`, `structureOverBudget` scans the frame's BinaryPack bytes and **sums each declared value's per-kind weight** (`WEBRTC_VALUE_WEIGHTS`):

| Kind | Retained weight charged |
| --- | --- |
| object | 64 bytes |
| array | 40 bytes |
| scalar (integer; a `bin`/`raw` value is charged only this slot, its ~1x-wire payload bounded by the wire-byte cap) | 8 bytes |
| string | `16 + 2/byte` (a SeqString header plus its UTF-16 characters) |

It rejects if the running cost would exceed **`MAX_WEBRTC_FRAME_STRUCTURE_BYTES` = 1,073,741,824 (2^30, 1 GiB)** or the structure nests deeper than **`MAX_WEBRTC_REASSEMBLY_DEPTH` = 256**. The scan reads only container headers and scalar length prefixes -- never materializing the payload, so it skips a large binary set frame in O(1) -- and enforces, as it walks, both the running weighted cost (the root plus all containers' children, so a value already committed by an ancestor or earlier sibling is counted, not just the current container's) and that no container declares more elements than the bytes that follow it can encode (each element needs at least one byte, so this ties the value count to the wire size and refuses a `new Array(N)`-from-a-tiny-header). An over-budget frame is caught at the offending header before `unpack` allocates; a read past the end (a truncated frame that passed both checks) is delegated, since its committed structure is already bounded and PeerJS's unpack errors on it.

*Why this budget value.* The budget is derived from the largest legitimate frame's *retained* cost. That is the mapped-element frame (`Array<{theirIndex, iteration}>`, one entry per matched record), which `unpack`s per record to one object (64) + two key strings ("theirIndex" 16+20, "iteration" 16+18) + two integer values (8 each) ~= 150 bytes under the weights above. At the ~4-million-element (2^22) set ceiling the wire-byte cap implies, that is ~4.19M records ~= 629 MiB; 2^30 leaves ~1.6x headroom (matching the prior count budget's ~21M-value-vs-2^25 ratio), so no exchange the wire cap admits is rejected on a downstream frame -- a property a unit test pins against the real frame shape.

*Why the weights are conservative.* The weights are a deliberately *conservative* upper bound -- e.g. every object key string is charged in full, though V8 internalizes repeated property keys to one shared string, so a key-heavy frame's real retained peak is lower -- because a true memory envelope is simpler to audit than one resting on V8 interning/representation choices an engine update could change.

*Residual.* The per-frame worst case for the kinds the budget charges in full is now this budget rather than the ~2 GiB an all-empty-objects frame reached under the flat count. A frame of the heaviest such kind (~16.7M empty objects) reaches ~1 GiB and is rejected there, and reaching even that requires ~16 MiB of proportional wire (the per-container byte check ties cost to wire, so a pathological frame is no cheaper than a legitimate one of the same retained size) and is freed once the schema layer rejects it. One kind is charged below its retained cost: a `float`/`double`/wide-integer value charged the 8-byte scalar slot retains ~24 bytes when a peer forces per-element HeapNumber boxing (an array made general-elements kind by mixing in one non-number), so a number-heavy frame can reach ~1.2 GiB -- slightly above this budget, bounded there by the wire-byte cap rather than by the structure budget, and likewise transient and freed on rejection. (Charging those markers their boxed cost would close that at the structure budget; it is not done because they never appear in a legitimate frame, so it is part of the how-aggressive-the-weights judgment below rather than a correctness fix.) A tighter budget overall would require less-conservative weights (crediting key-string internalization); how aggressive to make them is a security-review judgment, weighed with the queue residual below.

**String-size cap.** The structural budget charges a string its *resident* weight (`16 + 2/byte`), but `unpack_string` builds that string via a per-code-point concatenation whose transient cons-string tree is several times larger again (a ~250 MiB-wire `str32`, whose resident weight stays within the structure budget, measured into the multiple-GiB range *during the build*). The scan therefore refuses any string whose declared length exceeds **`MAX_WEBRTC_STRING_BYTES` = 1,048,576 (1 MiB)**. Binary set frames are `bin` (whose `unpack_raw` copies ~1x its wire size, bounded by the wire-byte cap, not a string), and every legitimate string a PSI frame carries -- the `{theirIndex, iteration}` keys, a `status` value, a payload cell -- is far shorter, so the cap rejects no legitimate frame; the value is orders of magnitude above any of them yet keeps the worst-case build transient in the tens of MiB.

**Retained chunk-count cap.** PeerJS retains each chunk as its own `Uint8Array` (measured ~232 bytes resident even for a one-byte slice), an overhead the wire-byte cap -- which counts only payload bytes -- undercounts, so a flood of tiny chunks could exhaust memory while staying under the byte cap. Each chunk is therefore charged at least **`MIN_CHUNK_RESIDENT_BYTES` = 256** against the byte cap, and the chunks per reassembly are bounded by **`MAX_CHUNKS_PER_REASSEMBLY` = 131,072 (2^17)** -- ~8x the ~16,500 chunks a 256 MiB frame produces at the ~16 KiB (16,300-byte) MTU, so a legitimate frame is never rejected while a tiny-chunk flood is bounded. Legitimate chunks (~16 KiB) far exceed the 256-byte floor, so it never affects them.

**Concurrent-reassembly cap.** The number of concurrent incomplete reassemblies is bounded by **`MAX_CONCURRENT_REASSEMBLIES` = 8**; a new message id beyond the cap evicts the oldest incomplete partial (deleting its `_chunkedData` entry and releasing its bytes). The PSI protocol is strictly lockstep (see [PROTOCOL.md](PROTOCOL.md)) and the data channel is reliable and ordered, so at most one frame is ever mid-reassembly on an honest exchange; 8 is generous headroom, and the cap bounds a flood of partials from many distinct ids -- the metadata-overhead case the byte running-total does not catch, since many tiny partials stay under it. Eviction is silent and non-fatal: a legitimate exchange never has a second partial, so eviction only drops adversarial data, and logging per eviction would itself be a spray-amplified log-flood vector.

**Delivered-frame backstop.** Finally, at the stable `data` event (`checkDeliveredFrameBound`): a fully delivered binary frame (a `Uint8Array`/`ArrayBuffer`) over the byte cap is refused there too, regardless of how -- or whether -- PeerJS chunked it, so the bound holds at the public layer even if the internal reassembly premise below ever breaks. A parsed object/array is not byte-measured here (the reassembly bounds above govern it before delivery, and core's count/structure bounds after); only binary frames are, which is exactly the raw set frame this is sized for.

The bounds above are *per frame*. A delivered frame is then queued in core's `QueuedMessageConnection`, whose capacity is a message *count* (`DEFAULT_CAPACITY` = 1024), so the aggregate retained across queued-but-unconsumed frames is in principle the per-frame budget times that depth. This queue residual was weighed when the per-frame budget was made byte-aware, and the queue was **deliberately left a count bound**: the lockstep protocol drains one frame before sending the next, so the queue sits at depth ~1 in practice, and a peer that floods frames out of turn trips the count capacity (a `protocol` failure) rather than accumulating -- so the theoretical per-frame x depth aggregate requires both proportional wire bytes per frame *and* the consumer to stall, and is the count capacity's concern rather than this control's. A byte-aware queue bound (or a smaller web-transport capacity) would close the theoretical multiplier but buys little against a practical depth of ~1, and -- unlike the per-frame scan, which is web-side because core's transports never `unpack` BinaryPack -- would force a web-vs-core placement choice (a core bound would let a future CLI WebRTC transport inherit it) better made when a transport actually needs it. The per-frame budget is therefore the byte envelope; the queue stays bounded by count.

The wrap reaches past the public `DataConnection` API into PeerJS internals, so it rests on two dependency premises a `peerjs`/`peerjs-js-binarypack` upgrade could silently break. The first is the reassembly/unpack shape on the binary/chunked connection class (the one `peer.connect` and an incoming connection use by default): `_handleChunk` reassembling slices keyed by `__peerData` into `_chunkedData` and deleting the entry on completion, and `_handleDataMessage` as the sole point each frame is unpacked (an unchunked frame directly, the reassembled buffer via the completion recursion). This is encoded as a runtime check, not a comment: `assertChunkReassemblySupported` (called before any listener is attached) throws at install time if any of those internals are absent, so the live browser exchange test -- which installs the guard on every web exchange -- fails loud rather than running with no inbound bound. The second is the BinaryPack wire format the structural scan parses (the marker dispatch in `peerjs-js-binarypack`'s `Unpacker.unpack`: fixint/fixraw/fixstr/fixarray/fixmap and the `0xc0`-`0xdf` markers, with maps declaring two child values per pair). A format change there would not silently disable the bound -- a misparse either over-charges (rejecting early, fail-closed) or runs the cursor off the end (treated as a malformed frame and delegated to PeerJS, which would itself error) -- but it would weaken the scan's precision, so re-verify the marker table on a `peerjs-js-binarypack` bump. On a `peerjs` bump, re-verify both premises.
