# Channel security construction

This document specifies the construction and implementation of PSI-Link's
channel-security controls, the section headings below indexing the individual
controls. It is
the implementation-level complement to the **Channel security** overview in
[SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security), which covers what
each control protects against and why the design is sufficient; this document
covers the wire formats, the derived constant values and their justification, the
enforcement points, and the dependency assumptions each control rests on. It does
not cover the threat model or authentication design (see
[SECURITY_DESIGN.md](../SECURITY_DESIGN.md)), the PSI and key-exchange wire
protocol (see [PROTOCOL.md](PROTOCOL.md)), or the network channels and transport
contract (see [COMMUNICATION.md](../COMMUNICATION.md)). Intended readers are
security auditors and implementors.

Every net-new control specified here is subject to the explicit pre-release
security review required by
[CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy); the per-section notes
below repeat this only where a control has an extra scope nuance (an
internet-facing surface, a new security-relevant dependency, or a modification
layered on an existing control).

# Application-layer AEAD

Both parties use the HMAC-based Extract-and-Expand Key Derivation Function (HKDF) to derive AES-GCM keys from the 32-byte key-exchange session key - two directional keys, one per direction (HKDF info strings `psilink-aead-v1:initiator-to-responder` and `...responder-to-initiator`) rather than a single common key - so that every key has a single sender, and messages are encrypted using Authenticated Encryption with Associated Data (AEAD). Each message holds a per-direction sequence number as its nonce, preventing replay and reordering. The separate per-direction keys are what keep that nonce construction safe: both directions number their messages from zero, so a single common key would encrypt two different messages under the same key and nonce - a reuse that is catastrophic for AES-GCM - whereas one key per sender keeps every key-nonce pair unique. The server admin sees only opaque ciphertext files, and tampering with a file causes the authentication tag to fail and the exchange to abort. The AEAD context is restricted to this fixed pair of per-direction labels (a closed union, guarded at runtime), not an open string. Both parties must derive identical per-direction keys from identical labels; a variable, non-ASCII, or non-NFC label would make the two sides derive different keys and fail the AEAD with an opaque error rather than a clear authentication failure, so the label set is closed by construction.

The concrete envelope the `EncryptedMessageConnection` decorator emits is a binary frame `version || IV || ciphertext || 16-byte GCM tag`, encoded as raw bytes (no base64url, no JSON wrapper). `version` is a single leading format/version marker (`AEAD_ENVELOPE_VERSION`, currently `1`); the 12-byte IV is four leading zero bytes (authenticated, but not separately validated) followed by the 8-byte big-endian sequence number; and the encrypted plaintext is a one-byte type tag (`0` for a JSON object, `1` for a `Uint8Array`) ahead of the payload. The type tag stays inside the authenticated ciphertext and is never promoted to a cleartext envelope field, so a transport admin cannot flip JSON/binary routing without failing the GCM tag. The version marker turns a format mismatch -- an envelope from an incompatible build, or an inbound that is not the binary shape at all (the clean break from the prior base64url-in-JSON `{ enc }` format) -- into a clean `security` rejection rather than a silent misparse. This wire format is pinned byte-for-byte by a checked-in known-answer vector at [`packages/core/test/vectors/aead-envelope-vectors.json`](../../packages/core/test/vectors/aead-envelope-vectors.json), following the cross-implementation vector precedent of `canonical-vectors.json` and `exchange-record-vectors.json`: each vector fixes a session key, role, sequence number, and plaintext and records the exact `envelopeHex`. An independent implementation can therefore reproduce it from those inputs, and any change to the version marker, nonce construction, byte order, envelope shape, or tagging is caught. The vectors are regenerated by `generate-aead-envelope-vectors.mjs` in that directory and asserted against the decorator in `packages/core/test/connection/encryptedMessageConnection.test.ts`, which separately pins the per-direction HKDF key derivation (`deriveAeadKey`).

Because the type tag is encrypted, the file-sync transport beneath the AEAD layer cannot read it to route a frame, so it has its own outer, cleartext discriminator. Every data-plane message file is a binary envelope `version || type || seq || payload` (built and read by `send()`/`poll()` in `fileSyncMessageLoop.ts`), where `type` selects a JSON control payload (UTF-8 JSON, parsed through the `parseBoundedJson` chokepoint) or a raw binary frame (delivered as-is). This too holds the frame as raw bytes -- no base64url and no whole-frame string conversion -- so the read path never calls `Buffer.prototype.toString()` and a frame larger than Node's maximum string length can be read.

## Which channels request it

The wrap is applied when the key exchange's transcript-bound decision says so, and that decision is the OR of the two parties' requests: either party asking for it turns it on for both. What each party asks for is fixed by the channel, not configurable.

| Channel | Requests the wrap | Why |
| ------- | ----------------- | --- |
| `sftp`, `filedrop` | yes | The exchange sits in a server's or a share's filesystem. Its administrator can read and alter every frame, so the confidentiality and integrity have to come from a layer above the transport. |
| `webrtc` | no | A data channel is end-to-end confidential and integrity-protected under DTLS between the two parties. The signaling server introduces them and sees no exchange content, and a TURN relay forwards ciphertext. The wrap would protect nothing the transport has not already protected. |

The `webrtc` posture is also a compatibility requirement rather than only a judgement: the web implementation declines the wrap and refuses a partner that requests it (`apps/web/src/psi/authenticateExchange.ts`), so a CLI peer that asked would abort the exchange rather than upgrade it.

The one case that would change this is a transport leg an intermediary terminates -- concretely, a WebSocket-to-TCP proxy relaying a party's traffic, which would put a third party inside the confidential channel. No such transport exists. If one lands, the request bit is how the party behind it asks for the wrap, and the web side's hard refusal of a true request is what would be revisited then. No negotiation mechanism is built for that case in advance.

The limit that leaves is the browser path's, and it is a stated one: a web exchange has no application-layer encryption of its own, so every frame's confidentiality is the data channel's DTLS and nothing above it. Both connection shapes the web app can form keep that DTLS end to end -- a direct path, and a TURN-relayed one, which forwards without terminating -- so the limit binds only against an intermediary-terminated leg of the kind above, which no shipped configuration can put in the path.

## IV construction and SP 800-38D conformance

The 96-bit IV is the deterministic construction of [SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf) (November 2007) section 8.2.1, laid out as that section suggests for the default 96-bit IV length: the leading 32 bits hold the fixed field and the trailing 64 bits hold the invocation field. Read against section 8.2.1's own stated requirements, the construction **satisfies** them, with one qualification -- stated at the end of this section -- on what the all-zero fixed field rests on.

- **The IV is a fixed field concatenated with an invocation field.** `seqToIv` writes the 8-byte big-endian counter at `IV_SEQ_OFFSET` = 4 into a zeroed 12-byte buffer, giving a 32-bit fixed field followed by a 64-bit invocation field. Section 8.2.1 suggests, but does not require, exactly those lengths and positions for a 96-bit IV.
- **The fixed field identifies the context.** The fixed field is 32 zero bits and identifies nothing by itself, which section 8.2.1 permits where "the entire fixed field may consist of arbitrary bits when there is only one context to identify, such as when a fresh key is limited to a single session of a communications protocol". Each AEAD key here is limited to one direction of one session. It is derived by HKDF from the per-session key-exchange session key, which is transcript-bound and mixes each run's fresh ephemeral scalars, and it is imported non-extractable with a single usage (`encrypt` for the send key, `decrypt` for the receive key) held only by the decorator, so exactly one sender ever invokes the authenticated encryption function under it. One context, so the arbitrary-bit case applies.
- **No two distinct sets of inputs share an invocation field.** `sendSeq` starts at 0 and is consumed by a synchronous post-increment, one value per `send()`, ahead of the encrypt and transport awaits, so two concurrent sends cannot take the same value. A value consumed by a send that then fails is never re-issued: the failure latches the wrapper terminal, so nothing is sent under it or after it. A counter past `Number.MAX_SAFE_INTEGER` is refused with a `security` failure rather than wrapped.
- **The lengths and positions are fixed for the life of the key.** `IV_SEQ_OFFSET` is a module constant and 96 bits is the only IV length this layer supports, so the split is fixed across every key rather than only within one. The known-answer vectors above assert the two fields separately at three sequence numbers across both roles -- that the fixed field is the four bytes `00000000` and that the invocation field decodes big-endian to the vector's sequence number -- so a change to either field's length or position fails the suite.
- **Exactly one construction is used per key (section 8.2).** `seqToIv` is the sole producer of IVs under an AEAD key. The two keys are imported non-extractable with a single usage each -- the receive key cannot invoke the authenticated encryption function at all, which WebCrypto enforces -- and the send key is held in the decorator's private field rather than returned to a caller, so no second instance encrypts under it and no RBG-based IV is produced for it.
- **The invocation constraints hold with margin (section 8.3).** Section 8.3's 2^32 global invocation cap does not reach this construction -- it excludes an implementation that only uses 96-bit IVs generated by the deterministic construction, which is this one. The two constraints section 8.3 does apply at every IV length are both met: the 64-bit invocation field bounds invocations under one key and fixed field at 2^64, against the counter's own ceiling of `Number.MAX_SAFE_INTEGER` (2^53 - 1); and the 32-bit fixed field bounds distinct contexts under one key at 2^32, against the single context each key has.

**The qualification.** Section 8.2.1 attaches a condition to the arbitrary-bit fixed field: "if different participants in the session share a common fixed field, then the protocol shall ensure that the invocation fields are distinct for distinct data inputs". Both participants do use the same all-zero fixed field and both number their messages from zero, so their invocation fields are not distinct. What keeps the construction off that condition is that section 8.2.1's requirements are scoped *for any given key*, and the per-direction key split means the two participants never share one -- each key has exactly one sender, so there are no two participants under it whose invocation fields could collide. The satisfied outcome therefore rests on the key split, not on the IV alone: collapsing the two directional keys into one shared key turns it into a violation of section 8.2.1, which is the conformance statement of the key-nonce reuse the AEAD description above calls catastrophic.

Section 8.2.1 constrains how an implementation generates IVs for the authenticated encryption function, not what it accepts, so the receiver's not separately validating that an inbound IV's leading four bytes are zero is outside the section. Those bytes are covered by the GCM tag either way, so an IV that is not the sender's own fails authentication.

Conformance to section 8.2.1 is a statement about the construction and not about a module certificate's approved services. The FIPS 140-3 certificate this project targets makes AES-GCM with an externally supplied IV a non-approved service whatever construction produced the IV, and a `crypto.subtle` AES-GCM call supplies one by construction; see [COMPLIANCE.md](../COMPLIANCE.md#fips-140) for the scoped claim that follows from that.

## Associated data is not bound

The envelope binds no Associated Data (AAD), and this is a deliberate, recorded decision rather than an omission. AAD would matter only to stop a frame authenticated under one context (role/direction, session, or transcript) from being spliced or replayed into a different context that shares the same key. Here every such context is already separated below the AAD layer by a distinct key. Direction is bound by the key: each direction uses its own AES-GCM key, derived with a distinct HKDF info string (`psilink-aead-v1:initiator-to-responder` versus `...responder-to-initiator`), so a frame presented to the opposite direction decrypts under the wrong key and the tag fails. Session is bound by the key: both keys derive from the per-session key-exchange session key, which is transcript-bound and mixes in each run's random ephemeral scalars, so it is distinct even across two runs of the same shared secret - a frame from one session decrypts under the wrong key in another. Ordering within a single direction of a single session is bound by the sequence-number nonce and the strict-increasing replay guard. The only set of frames that share one AEAD key is those one sender emits in one direction of one session, and the decorator holds exactly one logical stream there - it does not multiplex sub-channels or protocol phases, and the one-byte payload type tag that distinguishes binary from JSON lives inside the authenticated plaintext. There is therefore no second logical context under a shared key for AAD to separate, so binding the direction (or a session id) as AAD would only restate what the key already enforces. The sequence number is the GCM nonce, not a substitute for AAD: the reason AAD is unnecessary is the absence of a second context under one key, not that the nonce stands in for AAD. Practically, the decorator holds only its inner connection, the session key, and the role - no session or transcript id is in scope to bind without new plumbing that belongs to the not-yet-wired caller integration.

Revisit this decision if a future change multiplexes more than one logical stream or protocol phase over a single direction's key, or collapses the per-direction key split into one shared key. In either case a context or sub-stream id bound as AAD would stop being redundant: it would still block cross-direction splicing, though not the key-nonce reuse that collapsing the key split would itself make catastrophic (AAD does not protect against nonce reuse). Until then, the per-direction key plus the sequence nonce are sufficient and no AAD is bound.

## Inbound integrity, replay, and ordering checks

This layer's AEAD/MAC and sequence-number (replay and ordering) checks run at the protocol layer, on the output of a `receive()` call: the decorator validates and decrypts each inbound envelope inside `receive()` and rejects with a `security` `ConnectionError` on any integrity, replay, or ordering failure. These checks are not latched into the inner connection as a transport control (the `fail`/`finish` teardown signals) behind a buffered inbound frame. The message queue drains an already-received frame to the consumer ahead of any terminal error, whether the close was clean or abnormal (see [Message delivery and teardown](../COMMUNICATION.md#message-delivery-and-teardown)), so a check wired as a transport-level latch could hand a suspect frame to the consumer before the integrity alarm fires. The decorator honors this - it raises the failure from `receive()` itself, and the inner transports raise only `transport` and `protocol` terminal errors with no integrity check latched behind a frame - so the constraint holds and remains one to preserve.

Mid-stream gap detection is strict: the decorator rejects any inbound sequence number that is not exactly the last accepted plus one, so a frame dropped or withheld between two delivered frames is caught here as a `security` failure on the output of `receive()` - the same protocol-layer reporting as the replay and tag checks, never a transport-level latch. It raises no false alarm against the send path's synchronous `sendSeq++` ahead of the encrypt (which is what keeps two concurrent sends from peeking the same counter and reusing an AES-GCM nonce). A send that consumes a counter value but then fails to transmit (an encrypt fault or an inner transport failure) latches the wrapper terminal, so no later frame is ever sent, and a consumed-but-unsent value can only truncate the tail, never leave a gap between two delivered frames.

## End-of-stream and truncated-tail detection

End-of-stream / truncated-tail detection is a deliberate accepted deferral, not a coverage gap to be closed with a marker. A truncated tail - a stream that simply stops, including a dropped final frame - is indistinguishable at the AEAD layer from a clean end, and no AEAD tag can authenticate the *absence* of a frame: an omitted frame can be detected only by expecting one and not receiving it. The PSI protocol is self-driven lockstep (see [PROTOCOL.md](PROTOCOL.md)): each party drives a deterministic script of matched send/receive calls, so the receiver always knows from its own script whether another frame is due. In the symmetric case a truncated tail therefore is reported - as a stalled `receive()` that hits the inactivity timeout - and an explicit, integrity-protected end-of-stream marker could only reclassify that timeout from `transport` to `security`, not detect the omission any sooner. Reclassification alone does not justify net-new, security-reviewed cryptographic surface, so the marker is not built. The lockstep is unconditional within the implemented one-to-one cardinality: the matching loop runs `identifyIntersection` for every agreed key on both parties -- the key set is fixed by the linkage terms, and the PSI library returns an empty intersection without error for an empty input set, so a locally-empty round is a correct no-op that both sides still perform. A per-party-data-gated skip (`if (data_j.length === 0) continue;`) would break this: `data_j` is built from a party's own still-unmatched records, so one side can empty a later key while its partner does not, and skipping there drops a send/receive the partner still performs and desyncs the exchange. Any future cardinality loop must therefore not reintroduce such a skip. This is a protocol-loop invariant, not an absent-frame one: no AEAD-layer marker could detect or repair a lockstep desync, so the end-of-stream marker's deferral is independent of it.

# Transport memory and liveness bounds

## Inbound frame-size bound

The first of these transport bounds caps inbound frame size. Left unbounded, the transport read path loads an entire frame into memory before any integrity check runs, so a hostile filedrop/SFTP server admin -- an adversary under the threat model (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)) -- could write an arbitrarily large file and exhaust memory: a denial of service that allocates a byte array proportional to the attacker-chosen file size. The transport refuses any inbound file larger than a maximum frame size of **536,870,888 bytes (~512 MiB)** before it is read into memory, reporting a clear terminal error (a `FrameSizeExceededError`, exit 64) rather than allocating proportionally to the attacker-chosen size.

**The value is a chosen memory bound, not a derived platform ceiling.** No platform limit anchors it: the transport sends a frame as raw bytes and never stringifies it (the AEAD envelope and the file-sync message body are both binary; see [Application-layer AEAD](#application-layer-aead) above), so no string-length ceiling binds the read, and ~512 MiB stands as a reasonable single-frame memory cap on its own terms.

This is the static safety check for every frame. The single-pass reply is bounded by a tighter per-exchange cap derived from the exchanged record counts (see [Single-pass per-exchange cap](#single-pass-per-exchange-cap) below), which can only ever tighten this value for that one read, never widen it. As a headroom check against the realistic worst-case legitimate frame: the largest PSI frame is one party's full encrypted set sent as raw elliptic-curve points, **35 bytes per element** on the wire (see [PROTOCOL.md](PROTOCOL.md#the-memory-ceiling-and-the-csv-intake-cap)), encoded with no base64url expansion. 512 MiB is therefore on the order of 15 million elements -- already more than the single-frame single-pass transport practically ships before the separate single-pass dataset ceiling binds.

**Enforcement.** The bound is enforced at the transport read layer, which is the meaningful enforcement point. The poll loop and rendezvous gate refuse a file whose listed/declared size exceeds the cap before calling `get()`, and -- so a server that under-reports a file's size in its directory listing cannot slip past that check -- each `FileTransportClient` adapter also enforces a hard per-read byte cap. The local-filesystem adapter `fstat`s the open handle and reads exactly that many bytes, closing the append-after-stat TOCTOU; the SFTP adapter streams into a counting sink that aborts the transfer once the running total crosses the cap, buffering at most one stream chunk past it. A binary length check on the AEAD decorator's inbound envelope caps it at the same single value -- a byte-length check on the raw envelope -- but that is documented defense-in-depth only, not the primary control: by the time the decorator runs, the inner transport has already read the frame, so the dominant allocation has already happened.

The bound is a fixed constant rather than a configurable option: a configurable bound risks an operator raising it high enough to reintroduce the DoS.

### Single-pass per-exchange cap

The single-pass reply (message 2 of the single-pass strategy) holds both parties' encrypted value sets and the sender's index table in one frame, whose legitimate size grows with the dataset. Rather than bound it by the static ~512 MiB cap above, single-pass derives a **per-exchange cap from the exchanged record counts and the agreed key count** -- authenticated session state both parties hold after the terms exchange, never any byte, name, or transport-listed size of the inbound file. So a small exchange's reply is held to a small bound (a hostile transport admin cannot pad it up to the static ceiling) while a large legitimate one is admitted up to a fixed maximum dataset size.

The derivation, its constants, and the deterministic operation order are specified in [PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute). The security-relevant properties here:

- **One shared computation, two enforcement points.** A single exported integer function (`singlePassReplyByteCap`, `packages/core/src/connection/frameSize.ts`) yields the value the receiver enforces at its transport read gate and the value the sender checks its built reply against before sending. The receiver threads it into the file-sync poll loop's `get()` read gate (via `setInboundFrameCap`), where it **replaces** the static `MAX_FRAME_SIZE_BYTES` for that one read rather than layering a second check above a still-static cap; the threaded value is clamped so it can only tighten, never widen, the static safety check.
- **The real ceiling is a memory budget, fixed and non-configurable.** An exchange aborts when either party's `effectiveKeyCount * recordCount` -- its value slot count, the upper bound on its distinct-value count, over the effective key count both parties derive from the agreed terms and the record count that party declared, which for a width-free party is its `keyCount * recordCount` -- exceeds [`MAX_SINGLE_PASS_CELLS`](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute). Its value, its derivation from the heavier party's measured peak, and the constraint that binds it -- the WebRTC per-frame envelope below, not memory -- are specified there, under the single-pass dataset ceiling. It is a fixed constant, not an operator-configurable option, for the same reason as the frame-size bound: a configurable maximum risks being raised high enough to reintroduce the memory-exhaustion DoS.
- **Transport-aware via per-transport clamps.** File-sync gets the `MAX_SINGLE_PASS_CELLS`-derived bound up to `MAX_FRAME_SIZE_BYTES`; the WebRTC data channel keeps its fixed browser-tab envelope [`MAX_WEBRTC_FRAME_BYTES`](#webrtc-data-channel-inbound-bound) at its reassembly read gate (`apps/web/src/psi/transport/boundedReassembly.ts`) and relies on the shared count-budget check, run identically on both transports, plus the decode-time coherence checks below. At the ceiling the derived reply frame, whose size there [PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) derives, sits below both envelopes -- the WebRTC one is the nearer -- so a legitimate single-pass reply the count budget admits is never rejected by a transport clamp. An over-ceiling exchange fails closed with the same actionable guidance -- which does not recommend cascade -- on both transports. The cap is held below the point where the derived reply cap would reach the WebRTC envelope precisely so this stays true; raising it past that point would require reworking the WebRTC reassembly path to fail closed rather than mid-frame.
- **Decoded counts are validated against authenticated state before allocation.** The receiver checks the row count packed into the reply against the record count the sender sent on the terms exchange -- no greater, and dividing it into a whole fan-out factor -- and checks the index-table length the frame actually holds, both before either count drives any allocation. Combined with the truncated/oversized-length decode guards, the reply decode stays bounded against malformed or adversarial framing. Each decoded record count additionally has an explicit [`MAX_RECORD_COUNT`](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) upper bound at its wire schema (`recordCountField` on the terms-exchange envelope, `packages/core/src/protocolSetup.ts`), so a count above it is a clean `protocol` abort at decode; its value and what that bound buys the cell-count gate are specified there.
- **Declared PSI element counts are bounded by a wire-format scan before deserialization.** Both the single-pass and the cascade decode paths hand a partner-supplied PSI setup / request / response to `@openmined/psi.js` `deserializeBinary`, which allocates one JS byte-slice object per declared repeated `bytes` entry. So a frame *within* the byte cap yet packed with minimal empty entries (up to ~frameBytes/2 of them) would exhaust memory **inside `deserializeBinary` itself**, before any post-deserialize count could run. The measured per-entry allocation, the amplification factor it implies, and the worst-case allocation this ceiling holds it to are specified in [PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute). The enforcement point is here: the participant scans the protobuf wire format and counts the declared elements without materializing them (`countDeclaredPsiElements`, `packages/core/src/connection/psiElementScan.ts`), rejecting an over-declared frame at the call site in `participant.ts` **before `deserializeBinary` is called**; the scan stops as soon as the count exceeds the ceiling, so an over-declared frame costs O(ceiling), not O(frame). The ceiling is the smaller of two bounds. The first is the value slot count `effectiveKeyCount * recordCount` for the relevant party (the sender's set for a setup, the receiver's for a request or the response that re-encrypts it -- `psiElementBounds`, `frameSize.ts`), read from the agreed terms and the exchanged record counts alone so both parties compute it identically and it never rejects a legitimate frame. The second is the absolute `MAX_PSI_DECODE_ELEMENTS` (its value and derivation in [PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute)), which no legitimate ~512 MiB frame of real 35-byte elements can exceed and which is what binds a cascade frame whose partner over-declares its record count (the authenticated bound alone is inflatable there, up to `MAX_RECORD_COUNT`). The scan reads only the stable protobuf wire format (never the library API) but assumes the message structure (the element list is top-level on a Request/Response, one submessage deep on a ServerSetup); an equivalence test pins the scan count against the library's and must be re-verified on an `@openmined/psi.js` upgrade. This is the raw-protobuf analogue of the WebRTC path's BinaryPack structure scan below, and it governs both transports (the web path sends the PSI frame as a `bin` whose size the WebRTC bound caps, but whose inner protobuf this scan is what bounds). A non-Raw server setup holds a single bounded byte blob rather than a repeated element list, so it cannot amplify; it is rejected downstream as a clean protocol abort (it is not the reveal-intersection Raw structure this protocol uses), not by the scan.

As net-new security behavior modifying the channel-hardening frame-size control, this is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

## Directory-listing bound

A companion transport-read control bounds the directory listing itself. This one is independent of the AEAD layer and of file contents: the two parties rendezvous through a shared directory the adversary controls, and the transport's `list()` call enumerates it. Left unbounded, a hostile filedrop/SFTP server admin can write a very large number of files, or files with very long names, and drive the listing to allocate an array and per-entry metadata proportional to the attacker-chosen directory contents. This is the same memory-exhaustion impact class as the frame-size DoS, reached through a different vector (directory enumeration - entry count and name length - rather than a per-file body read). The transport refuses a listing that breaches either of two bounds - more than **8,192 directory entries**, or any single entry whose filename exceeds **255 characters** - with the same kind of terminal, typed error as the frame-size bound (a `DirectoryListingBoundsError`, a `UsageError` subclass, exit 64). The refusal fails the exchange rather than silently truncating the listing to the cap and processing it: against a hostile rendezvous directory, refusal is the safer default, since truncation risks dropping a legitimate exchange file an attacker buried under filler.

Both bounds are derived, not round numbers, and both comfortably exceed what a legitimate exchange produces. The **8,192-entry** cap is set from a memory envelope: the worst-case at-cap allocation is the retained entries, each with a name of up to the 255-character limit plus per-entry object overhead (~600 bytes), so the listing allocation is bounded to roughly 5 MiB. That is about two orders of magnitude below the 512 MiB single-frame budget the frame-size bound already governs, so directory enumeration cannot become the dominant memory vector. It still exceeds the order-of-ten files a legitimate exchange produces (the two `-hello.json` files, at most one `-lock.json` or the `-ack.json` markers, transient `-joining.json` sentinels and `temp-*.tmp` writes, and the bounded set of PSI message frames) by roughly three orders of magnitude. That leaves generous headroom for a retain-mode directory that accumulates message and ack files across many sequential exchanges before the operator rotates it (retention is an out-of-band operator responsibility). The **255-character** filename cap is the POSIX `NAME_MAX`, the per-path-component limit every mainstream filesystem enforces (ext4, XFS, APFS, NTFS). The longest filename a legitimate exchange writes - the ack marker of a timestamped message - is on the order of 120 characters, and a name longer than 255 cannot exist on a conformant filesystem. So it is necessarily synthetic: the SFTP protocol imposes no name-length limit, so a hostile server can return such a name in a READDIR response even though its own filesystem could not hold it. Both bounds are fixed constants rather than configurable options, for the same reason as the frame-size bound: a configurable cap risks an operator raising it high enough to reintroduce the DoS.

The bound is enforced at the transport `list()` layer in both adapters - the point before the listing is materialized - not at a higher layer that has already consumed it. The local-filesystem adapter streams entries through `fs.opendir` (which yields entries in bounded batches) rather than `fs.readdir` (which materializes the whole directory into one array, on top of the per-file `stat` fan-out that follows). The entry-count check therefore stops the walk - capping both the retained array and the stat fan-out - at the bound regardless of how many entries the directory holds. The SFTP adapter does not delegate to ssh2-sftp-client's `list()` (which passes the directory path to `readdir`, accumulating the entire remote listing into one array before returning). Instead it opens a directory handle and reads one server batch at a time through the low-level `opendir`/`readdir`/`close` protocol, applying the checks as entries arrive, so a single READDIR response - itself bounded by the SSH transport's maximum packet size - bounds the allocation to at most the cap plus one batch. Guarding only the local adapter would leave the SFTP path - the one with the explicitly in-scope adversary, the server admin - exposed, so both adapters are bounded.

## Rendezvous symlink refusal

A companion control on the same partner-writable rendezvous directory refuses a symlink planted at an entry, rather than following it. The two parties rendezvous through a shared directory an adversary can write into; in the filedrop / synced-folder case the partner's writes sync into the local operator's own copy of that directory. An entry planted there as a **symlink**, if the transport followed it, would redirect a rendezvous read or write out of the directory to an arbitrary path on the local filesystem the partner does not otherwise control. A followed read could pull a local file (a credential, an unrelated document) into the read path, and -- the sharper impact -- a followed write could truncate or clobber a local file outside the rendezvous directory with exchange bytes. The directory's contents are partner-supplied but the surrounding local filesystem is the trusted operator's, so this is a partner-reachable path-redirection vector distinct in kind from the memory and liveness bounds above (a confidentiality/integrity break, not a resource exhaustion).

The local-filesystem adapter refuses it at the open: every rendezvous read/write primitive -- `get()`, `put()`, and `createExclusive()` -- opens its target through `openNoFollow` (`localFSClient.ts`), which adds `O_NOFOLLOW` to the open flags, so an open whose final path component is a symlink is refused (POSIX `ELOOP`) rather than resolved to the link target. This mirrors the `O_NOFOLLOW` temp-file discipline the credential and result writers use (see [CREDENTIAL_STORAGE.md](CREDENTIAL_STORAGE.md#posix-write-discipline)). `O_NOFOLLOW` is absent on Windows, where it drops from the open mask and leaves the open otherwise unchanged. It refuses only a symlinked final *entry*, not an intermediate directory component, so a legitimately symlinked share root or mount point is still traversed and a rendezvous directory that is itself a mounted symlink is unaffected.

The critical control on the read path is not `O_NOFOLLOW` but the directory listing's own symlink filter. `list()` enumerates through `fs.opendir` and retains only `Dirent.isFile()` entries (see [Directory-listing bound](#directory-listing-bound) above), so a symlink is dropped before its name is ever handed to `get()`, and every `get()` call site -- the poll loop's message reads and the rendezvous gate's hello read alike -- reads only a name the listing reported. `O_NOFOLLOW` is the primitive-level safety check there, for a symlink swapped in at a name the listing already committed as a regular file, a time-of-check/time-of-use race the filter alone cannot close. On the write path there is no such filter: `put()` and `createExclusive()` destinations are built from authenticated protocol state at predictable rendezvous names, never from a listing, so `O_NOFOLLOW` is the *primary* defense against a symlink pre-planted at one of those names, not a safety check. `createExclusive()` additionally opens with `O_EXCL`, which already refuses any pre-existing entry -- a planted symlink included -- so its `O_NOFOLLOW` is redundant defense in depth on the same open.

The control is scoped to the local-filesystem adapter. The SFTP adapter resolves every path on the server, where the server admin is already the in-scope adversary with full control of the files it serves (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)), so a server-side symlink grants no capability the threat model does not already cede. The local-filesystem adapter is the one case where the rendezvous directory's contents are adversary-supplied while the surrounding filesystem is the trusted operator's.

## Per-operation liveness bounds

A third transport control bounds these operations for liveness rather than memory. It is the **per-operation fast-fail layer** - covering both the reads and the always-executed write/stat/delete operations - beneath the whole-exchange budget described next (which is the universal safety check over every transport await). The size bounds above stop a hostile directory or file from exhausting memory, but they do not stop a hostile server admin from hanging the operation itself. Every SFTP read awaits a callback the server drives, so the server can make one never terminate. A `list()` can return valid but empty (`count = 0`) non-EOF READDIR responses forever (advancing neither size bound, since no entry accumulates and the end-of-directory status never comes, so the batch loop recurses without end), or simply never invoke a readdir/close callback. A `get()` can hold the read stream open and withhold data, or trickle under-cap bytes without ever ending it, so the transfer never completes. A `createExclusive()` can withhold its open or close callback. Because `list()` and `get()` run on the poll loop - which awaits them with no per-call timeout - and `createExclusive()` drives the rendezvous lock path, any of these is a liveness / non-termination denial of service: the exchange stalls forever (and a directory or file handle opened before the stall is leaked) instead of failing. Each read is bounded by the mechanism its shape allows and reports a single terminal, typed `TransportOperationStalledError` - a `UsageError` subclass, exit 64, the liveness sibling of the memory-bound `DirectoryListingBoundsError` and `FrameSizeExceededError`. The consumers that await these reads, the poll loop and the rendezvous control-file gate (`readControlFileWithGate`, which reads the peer hello over `get()`) alike, therefore treat it as terminal and fail the exchange rather than retrying into the same hang. The gate keys this on the typed `UsageError` rather than a single error class, so a stalled hello read is terminal there exactly as an over-cap `FrameSizeExceededError` is - without it, a server that stalls the hello `get()` would be retried at the polling cadence until the one-hour peer budget instead of failing in a minute. The streamed `list()` has a **16,384 readdir round-trip** cap for the empty-batch flood plus a **60-second wall-clock deadline** for the withheld-callback case, and closes the open directory handle on the bounded-failure path. The capped `get()` bounds the **60-second idle gap between chunks** (reset on each chunk), not the total transfer, so a legitimately large but slow-and-progressing read is never failed while a withheld or stalled one is. `createExclusive()` and the rarely used uncapped `get()` - neither of which has a progress loop - have the **60-second whole-operation deadline**. The always-executed write/stat/delete operations are bounded by this same layer, each in the mode its shape allows. The metadata ops `rename()`, `delete()`, and `exists()` - each a single server round-trip with no payload - have the same **60-second whole-operation deadline** as `createExclusive()`, with the same negligible false-fail profile, since a metadata round-trip completes in well under a second on any honest server. `put()` instead has a **60-second progress idle window**, reset on each uploaded chunk. A tight flat deadline is wrong for `put` specifically, because a legitimately large ciphertext upload over a slow link can exceed it while still progressing, so - exactly as the capped `get()` bounds its idle gap rather than its total transfer - `put` bounds the gap between upload-progress chunks. The payload is streamed in bounded chunks so a withheld write acknowledgement stalls the source and trips the window while a slow-but-progressing one keeps resetting it; this uses ssh2-sftp-client's stream interface rather than driving the raw `SFTPWrapper`, so it adds no new internal-API coupling. The bounded source accepts either a single `Buffer` or the message send path's `[header, payload]` chunk list (streamed part-by-part, never concatenated in memory -- see [FILE_SYNC.md](FILE_SYNC.md)), so the same window and retry cover the largest, hottest binary frame; a chunk list is re-iterable, so the source is rebuilt per retry attempt exactly as it is from a `Buffer`.

The bounds are derived, not round numbers, and all comfortably exceed any legitimate operation. The **16,384 round-trip** cap is twice the 8,192-entry size cap, so the two move together. A compliant server sends at least one name per non-EOF READDIR response (an empty non-EOF response is not protocol-conformant - a server out of names sends end-of-directory instead), so a legitimate listing makes at most 8,192 batches before the entry-count bound would already refuse it, and only in the pathological-but-legal case of one entry per batch. An honest server packs many entries per packet and finishes a normal rendezvous directory in a single batch, so the cap only ever fails a progress-free flood. The **60-second** budget is a single coarse "the server has gone silent" threshold, applied as a whole-operation deadline for `list()`, `createExclusive()`, the metadata write/stat/delete ops `rename()`/`delete()`/`exists()`, and uncapped `get()`, and as a progress-reset idle window for the capped streaming `get()` and for `put()`. It sits well above any legitimate operation - a normal listing, a lock-file create, and each chunk of a healthy transfer all complete in well under a second. It runs at roughly twice this project's 30-second per-attempt connect bound (`serverConnectTimeoutMs`, applied as ssh2's `readyTimeout` even when the operator leaves it unset; ssh2's own default `readyTimeout` is 20 seconds), so a transiently slow but live server is not cut off. Yet it sits more than an order of magnitude below the one-hour (3,600-second) peer-inactivity budget, so a withheld response fails the exchange in a minute rather than after an hour. Applied as an idle window it never rejects a slow-but-progressing large transfer, only one that stops sending. All bounds are fixed constants, not configurable, for the same reason as the other bounds: a configurable budget risks an operator raising it high enough to reintroduce the denial of service. These per-operation bounds are on the SFTP adapter, whose every call crosses the network to the in-scope server admin; they cover its reads and its write/stat/delete operations alike. They do not cover the local-filesystem adapter, whose reads face a local kernel (`fs.opendir`/`fs.stat`) that exhibits none of these failure modes - an assumption a stalled NFS/CIFS hard mount breaks. That remaining gap is closed not here but by the whole-exchange budget described next.

## Whole-exchange budget

A fourth liveness control is the **whole-exchange budget**: the universal safety check beneath the per-operation bounds above, and the *only* per-operation-free liveness bound for the local-filesystem adapter. The per-operation bounds fast-fail a stalled SFTP read or write in 60 seconds; the budget is the layer they were added *beneath*, not in place of. The always-executed critical-path write/stat/delete operations - `put` (every message and every hello/sentinel write), `rename` (every durable publish), `delete` (message consumption and rendezvous cleanup), and `exists` (the lock-path race check) - each have their own 60-second per-operation bound (above). This budget is what stands beneath them against a hostile or dead server that withholds any of their callbacks and hangs the exchange for an hour. Absent it that hang is silent: `synchronize()` and `send()` await the call directly so it never returns, and the poll loop's reschedule sits in a `finally` a hung await never reaches, so the poller stops with no error, while the peer-inactivity budget (`peerTimeoutMs`, default one hour) is a between-iterations check that never sees an in-flight await at all. The connection therefore races **every** transport await - reads, writes, stat, delete, and the local-filesystem path alike - against that budget at the single consumer call site they all flow through, reporting the same terminal, typed `TransportOperationStalledError` on expiry. Because it wraps the transport interface rather than any one operation, it is op-agnostic (it covers operations not individually enumerated and any added later) and adapter-agnostic (it bounds the SFTP adapter and the local-filesystem `LocalFSClient` identically, closing the stalled-mount gap). It bounds a stalled await against a *fresh* budget per await (silence from the peer), not the total exchange duration, so it never caps a healthy long-running exchange. The budget is the same single coarse setting an operator already tunes, and it stays coarse as the safety check: the tight, false-fail-safe per-operation bound a slow `put` needs is the progress idle window above, not a flat budget timeout, which is exactly why the budget itself can remain one coarse setting rather than being split per operation. The capped `get()` slow-drip (under-cap bytes trickled forever, which resets the per-chunk idle window and so never trips the 60-second read bound) is caught here too, since total elapsed eventually crosses the budget - as is the symmetric `put` slow-drip, whose progress idle window the budget likewise covers.

## Send-window liveness guard

A fifth liveness control makes the four bounds above effective in a window none of them covered on its own. Every liveness timer among them - the per-operation SFTP deadlines and the whole-exchange budget (and the connect-probe bounds below) - is `.unref()`'d, by design, so a completed or cancelled exchange exits promptly rather than lingering until a safety timer expires. The consequence is a subtlety the fourth control's "races **every** transport await" glosses: an `.unref()`'d timer can only *fire* while some **other, ref'd** handle is holding the Node event loop open. A parked `receive()` supplies one - `QueuedMessageConnection` (`@psilink/core`) arms a **ref'd** inactivity timer (the same `peerTimeoutMs` budget) while a receive waits on an empty queue - so a peer that goes silent mid-read is caught and the unref'd whole-exchange budget behind it gets to fire. The sender's encrypt-then-send window parks no `receive()`: it builds and encrypts the next frame, then awaits the outbound `send()` (a `put` then a `rename`). A connection dropped in exactly that window - the motivating incident was an SFTP server dropping the link in reaction to an over-aggressive poll cadence, but an idle timeout or a network blip is identical - leaves the in-flight write's callback unfired. Every timer that would reject it is `.unref()`'d, and with no ref'd handle left the event loop drains and the process exits **0**, mid-log, indistinguishable from a crash: the awaited `send()` never returns, so no `catch`, `finally`, or teardown line runs.

The guard is one **ref'd** timer, armed in `QueuedMessageConnection.send()` across the in-flight transport hand-off (`sendWithLiveness`) and cleared the instant it settles. Being ref'd it holds the loop open, which lets a lower, faster `.unref()`'d per-operation deadline (the 60-second SFTP `put` idle window) or the whole-exchange budget fire first and reject the write. That rejection - a `TransportOperationStalledError` naming the server's withheld acknowledgement - is re-tagged by `send()` as a `transport` `ConnectionError` (its message and cause preserved) so the operator sees the real cause. Absent any per-operation bound (a transport that has none), the guard is itself the transport-agnostic safety check: on expiry (the connection's `inactivityTimeoutMs`, the peer budget) it rejects the send with a `transport` `ConnectionError` that names the lost connection, so the awaited call returns instead of orphaning. Either way a mid-exchange drop in the send window terminates **non-zero** (a `transport` `ConnectionError` maps to exit 69 / `EX_UNAVAILABLE`) rather than a silent exit 0. It lives in core, not the SFTP adapter, so it covers every transport (`sftp`, `filedrop`, and the web WebRTC channel) at the one `send()` call site they share. Every terminal path (`fail`/`finish`/`close`) *rejects* an outstanding send -- not merely cancels its timer -- as well as clearing it on the hand-off's own settlement. This is critical, since a terminal transition (an inbound-overflow `fail`, a peer half-close via `finish`, or a signal-driven `close`) can race an in-flight hand-off, and a hand-off orphaned in exactly that window would, if the guard were only cancelled, leave the awaited `send()` hanging forever -- the same silent stall, relocated. Rejecting it there (as the terminal error, or a cancelled `closed` on a deliberate close, the send-side twin of the parked-receive rejection) makes the "terminates rather than orphans" guarantee hold in the racing case too, and keeps the same "never hold a healthy process open at teardown" property the `.unref()`'d timers have. That guarantee is reached here by settling every guard rather than by `unref`, because this one timer must, uniquely, hold the loop open just long enough to reject the orphaned write, then release it. Its message has no `inactivityHint`: that receive-side guidance ("the peer... has sent nothing since") misdescribes a stalled outbound write.

## Connect-probe bound

A sixth liveness control bounds the connect probe itself, the one transport call outside the whole-exchange budget's reach. `connect()` runs before the exchange begins and is wrapped by neither the per-operation bounds nor the whole-exchange budget - it passes through `boundTransport` unwrapped - so each adapter bounds its own connect attempt instead. The SFTP adapter bounds it by ssh2's `readyTimeout`, which tears down the socket on expiry and strands nothing. An unresponsive SFTP connect is retried, so its total caller-visible latency stacks to roughly `maxReconnectAttempts + 1` such per-attempt windows - bounded wait, not accumulating resource, since each expiry strands nothing - unlike the local-filesystem timeout below, which is terminal at one window. The local-filesystem adapter bounds it by a per-attempt `withTimeout` deadline around its `fs.access` reachability probe. On the local-filesystem adapter a stalled NFS/CIFS hard mount turns that probe into the same liveness hazard the post-connect bounds address, with a sharper resource cost. `fs.access` blocks a libuv thread-pool worker (not the event loop), and nothing in-process can cancel an already-dispatched blocking syscall - `fs.access` does not honor an `AbortSignal`, and libuv's `uv_cancel` only removes still-queued work, never work a pool thread is already executing - so the worker stays pinned until the OS releases the syscall, minutes on a hard mount. The per-attempt timeout fires on the event loop and fails the attempt, but retrying it would launch a fresh probe each time. So under the default `maxReconnectAttempts` of 3, up to four such probes could stack, exhausting the default four-thread pool and starving every other `fs`/DNS/crypto operation in the process - a process-wide denial of service induced by a single unreachable mount. The connect therefore treats a per-attempt timeout as terminal: it fails fast after one timeout window, reporting a `TimeoutError` (which extends `Error`, not `UsageError`, so it classifies exit 69 / `EX_UNAVAILABLE` like any transport-unavailable failure), rather than dispatching further probes. A fast-returning transient error - `EACCES`/`ENOENT` while a share or its permissions are still settling - still retries under `max_reconnect_attempts`. For the local-filesystem adapter that budget governs only this initial connect: `filedrop` holds no persistent session, so it has no mid-exchange reconnection. The SFTP adapter is the exception - it holds one long-lived session that a server can drop mid-exchange - so the same budget also bounds each of its mid-exchange re-dial bursts (see [SFTP mid-exchange session recovery](#sftp-mid-exchange-session-recovery)). This bounds concurrent stalled workers to one and the caller-visible latency to roughly one `serverConnectTimeoutMs` window. It does not bound the lifetime of that one worker, which only the OS reclaims, because no in-process mechanism can free a thread wedged in a single blocking syscall - only a killable worker thread or child process could, which is disproportionate for a connect pre-check.

On the SFTP channel that per-attempt window covers only part of an attempt. ssh2 clears `readyTimeout` the moment authentication succeeds, and the `subsystem sftp` request that follows has no deadline of its own, so a server that authenticates the operator and then never answers it leaves the dial with nothing to end it. The adapter arms its own deadline over that second phase - at ssh2's `'ready'` event, for the same `serverConnectTimeoutMs` window the first phase ran under, so one operator-facing setting governs both. Its expiry destroys the socket beneath the abandoned dial and waits the ssh2 `Client`'s `'close'` for it out before reporting, because that socket is still writable, the one state a later `Client.connect()` defers behind forever, and a dial issued while that `'close'` is owed is failed by the library instead of reaching the server (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md#upgrading-the-sftp-stack-ssh2--ssh2-sftp-client)); it reports a `TimeoutError` naming the phase. It is terminal at one window rather than retried: the request went unanswered on a connection the server had already authenticated, so re-issuing it puts the same request to the same server for the rest of the reconnect budget. A stalled SFTP attempt therefore ends within roughly two `serverConnectTimeoutMs` windows plus a forced-close wait of at most one second, rather than one. Both halves of the assumption behind the bound - where the phase begins, and that nothing in the pinned stack ends it - are driven against a real server in `apps/cli/test/integration/sftpStackPremises.test.ts`, and the bound itself in `apps/cli/test/integration/subsystemOpenBound.test.ts`.

The per-attempt windows above bound each connect attempt; the *count* of attempts has a ceiling of its own, because a `max_reconnect_attempts` validated only as a non-negative integer (up to `Number.MAX_SAFE_INTEGER`) bounds nothing. Against an endpoint that refuses fast - `ECONNREFUSED` on `sftp`, `EACCES`/`ENOENT` on `filedrop`, exactly the fast transients the retry budget exists to ride out - the retry loop spaces attempts with a fixed one-second inter-attempt delay, and the fast-fail attempts themselves are near-instant. The wall clock is therefore essentially the delay total (the `maxReconnectAttempts` delays across the `maxReconnectAttempts + 1` attempts above) - about that many seconds, a linear self-inflicted hang. The count is therefore capped at `MAX_RECONNECT_ATTEMPTS = 604800` (defined in `packages/core/src/config/connection.ts`), derived as the CLI's seven-day timeout ceiling `MAX_TIMEOUT_SECONDS` divided by the one-second delay (`604800 s / 1 s = 604800`): the largest count whose fast-fail delay total stays within the same seven days the duration flags already cap. A value past it is rejected with a flag-named `UsageError` (exit 64) at both validation boundaries that already agree on this field - the connection schema's `.max()` and the CLI's `nonNegativeIntFlag` parse guard, which imports the constant - so an over-ceiling value is refused whether it arrives from `psilink.yaml` or `--max-reconnect-attempts`. This bounds a proxy: the count equals wall clock only at the one-second floor (the fast-fail case), so it does not tightly bound a slow-but-answering endpoint, whose attempts each run up to `serverConnectTimeoutMs` and are already bounded per attempt by it. A direct wall-clock deadline on the whole connect phase is the stronger control left for if that case ever proves to matter. This is a usability/self-DoS sanity bound, not a cross-party control - the operator only hangs their own command - in the same class as the `MAX_TIMEOUT_SECONDS` duration-flag cap.

## Consumer-side terminal-error rule

These transport bounds share one consumer-side rule. Every one is reported as a `UsageError` subclass - the memory bounds as `FrameSizeExceededError` and `DirectoryListingBoundsError`, the liveness bounds as `TransportOperationStalledError` - and any consumer that awaits a transport call must treat a `UsageError` as terminal: it propagates the rejection and never retries it, swallows it, or proceeds as if the call had succeeded. This binds the read consumers (a `list()`/`get()`/`createExclusive()` in the poll loop or the rendezvous gate) and the write consumers too - the `put`/`rename` publish in `send()`, the rendezvous lock-path `createExclusive`/`exists`, the consume-`delete` that signals a message consumed, and the retain-mode ack-write (`writeAck`'s `put`/`rename`) that signals it on a transport that never deletes. Retrying loops straight back into the hang or the over-allocation the bound exists to prevent, and swallowing-then-proceeding turns a stalled consume into a re-emitted duplicate - a swallowed bound is no bound. So the only effective response is to fail the exchange, which is why the poll loop stops on a `UsageError` (including from the consume-`delete`, which rethrows it rather than swallowing it as it does a transient delete failure), the rendezvous control-file gate (`readControlFileWithGate`) rethrows it, and the `send()`/joiner write paths propagate it. The terminal behavior keys off the `UsageError` base class rather than each subclass, so a future bound added to the family inherits it. This consumer rule is what makes the transport-layer bounds effective end to end. The consumers are pinned by behavioral tests in `packages/core/test/connection/fileSyncConnection.test.ts` that drive each with a `UsageError` from a transport call - a stalled read in the poll loop and the gate, a stalled consume-`delete` in the poll loop, and a stalled retain-mode ack-write in the poll loop. Each assertion checks that it is reported once and propagated (the exchange fails), never retried at the poll/gate cadence and never swallowed into a duplicate delivery. A new transport-call consumer must uphold the same rule; it is not enforced automatically, so adding one is a change to review against this rule.

## Slow-operation warning

Distinct from both controls is a non-fatal **slow-operation warning**, which is observability, not a security control. At a fixed, generous elapsed-time threshold (30 seconds, below the 60-second read fast-fail) the SFTP adapter logs one warning naming the operation, the elapsed time, and - where a cheap progress signal already exists - the observed progress (bytes-so-far and rate for a `get`, entries-so-far for a `list`, the payload size for a `put`; elapsed-only for the atomic operations). It then lets the operation continue unchanged. It needs no duration estimate: a slow-but-honest transfer and an intentionally slow or withholding server are observationally identical (intent is not on the wire), so a false warning is cheap and the line reports observed signal for a human to judge. It does nothing on a headless run with no human watching - the whole-exchange budget defends that run - and it stays entirely outside the terminal-error paths, so it can never affect correctness or the liveness gate. It introduces no new required configuration.

## Authenticated abort marker

A distinct channel control is the **authenticated cross-party abort marker**, the one mechanism here that is not a bound on a hostile operation but an authenticated signal between the two honest parties. On the file-sync transports a failed exchange gives the waiting peer no in-band notice that its partner has given up, leaving it to wait out the full peer-inactivity budget (default one hour) and then print a generic peer-silence hedge. The marker closes that gap: when a party fails terminally with its directory still writable, it writes a best-effort `<id>-abort.json` holding a 32-byte token `HKDF(sessionKey, "psilink-abort-token-v1:<role>")`; a waiting peer that reads a `<peerId>-abort.json` whose token verifies against its own locally-derived peer token fails fast with a definitive `PeerAbortError` (exit 69) instead. The token is the authentication: a hostile filedrop/SFTP admin can write or rename any file in the rendezvous directory, but cannot produce a token that verifies without the per-session session key, so cannot forge an abort against a live peer. The label is domain-separated from the other session-key derivations - exact-distinct and prefix-free from the AEAD `psilink-aead-v1:<context>` and the `psilink-shared-secret-rotation-v1` labels - so an abort token can never collide with or substitute for an AEAD key or the rotation secret. The comparison is constant-time and length-safe, and the read fails closed on every absent, oversized, malformed, wrong-version, or non-matching input. The per-direction (role) binding makes a captured marker renamed to the other party's name verify under the wrong token and fail; the per-session ephemeral key makes a marker captured from one exchange inert in another.

The marker is best-effort and has no cause, both deliberate. Its absence is strictly uninformative: a deleted, withheld, or forged marker simply degrades to the peer-silence timeout and hedge - it is never treated as success - so a hostile admin can at most *suppress* the fast-fail, never forge an abort or turn a failure into an apparent success. It has no cause because the cause is not actionable to the waiting party - which holds no local error and must contact its partner regardless - and a plaintext cause on the untrusted channel would only widen disclosure; the token itself is a one-way HKDF output that reveals nothing about the session key or any other derived key. Because the marker is re-read every poll cycle, it is capped small - a pre-`get()` listed-size refusal and a bounded `get()`, both at 1 KiB rather than the ~512 MiB frame maximum - so an admin-plantable file cannot become an availability vector. The write is short-budgeted on both its `put` and `rename` (a few seconds each) so a sick directory cannot hang teardown. The mechanism is file-sync only: the connectionless file transport is the only one with a parked-waiter problem, since a WebRTC peer's death drops the DTLS data channel and is reported promptly; a future cross-transport abort would instead state a protocol-layer error kind rather than an on-disk marker.

## SFTP session heartbeat and TCP keepalive

Distinct again, and opposite in direction to the bounds above: those cap how long a **hostile** server can make an operation hang; this keeps a **friendly** server from dropping a session that has gone legitimately quiet. An SFTP server enforcing a strict idle timeout closes the control connection when no SFTP command has arrived within its window - Azure Blob SFTP's window is a **fixed two minutes**, not operator-adjustable. A single-pass PSI round spends long stretches with no file traffic on the side that is computing rather than polling (the receiver polls for the reply, so its session stays warm; the sender computes the reply and issues no SFTP command meanwhile). On weak hardware (old agency laptops) that masking can run for minutes even on the native backend (see [PROTOCOL.md](PROTOCOL.md)). The masking runs in a worker thread rather than on the event-loop-owning thread, so the loop stays free across such a round and this heartbeat can fire during it; run on the event-loop-owning thread, a multi-minute round would block every timer outright and no heartbeat could fill the gap.

The heartbeat is a self-rescheduling timer on the SFTP adapter that issues a real no-op SFTP command - `realPath(".")`, the cheapest single REALPATH round-trip (a path the server always resolves) - once the session has been idle for the interval. It must be a real **SFTP** command, not an SSH-transport or TCP keepalive: a server keys idleness on the last SFTP protocol **request**, so transport-level traffic does not reset its timer. The interval is **60,000 ms (60 s)**, half of the tightest idle timeout it must survive (Azure's fixed two minutes), so a beat always lands with a full interval of margin even if one is delayed. The idle window is measured from the last observed activity, so a beat never fires more than one interval after the session actually went quiet. It is a **fixed constant, not operator-configurable**, for the same reason as the liveness bounds above - a setting set too high silently stops defeating the timeout, with no upside a fixed sub-timeout value lacks.

A beat is suppressed while any adapter operation is in flight (real traffic is already keeping the session alive) and while a previous beat has not settled, and only fires after a full interval of genuine idleness. Overlap itself is not the hazard that suppression covers: two operations in flight on one client at once is unsafe only in the narrow respect below. Measured against a real server, overlap on a **healthy** session is safe: over the operation pairs driven, the beat's own among them, each member returned its own correct result with no cross-talk and no mis-routed error, and a non-fatal failure of one member left the other undisturbed. What overlapping operations do cross is the **session-loss rejection**, which the library hands to the operation issued last while suppressing the earlier one's - so issuance order decides which of two concurrent operations takes which path out of a loss, and the two paths do not have the same outcome. That crossing is not the beat's to close. The adapter issues concurrent operations of its own with no suppression of any kind - a `send()` resuming from the protocol continuation runs its `put`/`rename`/`safeDelete` alongside the poll cycle's `list`/`get`/`delete`, and core's connection cleanup and rendezvous orphan sweeps fan `safeDelete` out with `Promise.all`. So the suppression covers the beat and nothing else, and is not a control over concurrent operations generally. Leaving them unsuppressed is the posture rather than a gap for the beat's suppression to grow into, and what gets them through a session loss is the recovery re-dial's transport retirement. An operation outstanding when a concurrent operation's recovery runs is settled by the transport close that retirement waits out -- and, against a partner that withholds it, drives itself -- rather than being left for its own per-operation liveness deadline. A drop that tears several operations at once therefore costs the exchange one tear, not one deadline per operation, and every torn operation inside the recovery chokepoint is re-issued with its own correct result. What it is still worth is narrower: it keeps the beat off a session that already has an operation on it, so the beat - whose own outcome is swallowed - never takes a session-loss rejection away from a real operation in flight beside it. The one residual overlap - a real operation that begins in the same event-loop turn a just-issued beat is still on the wire - is covered by the healthy-session measurement, and at a loss the rejection reaches that operation rather than the beat, which was issued first. (The library mechanism, the measured numbers, and the pairs and states the runs did not cover are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md), re-verified there on any ssh2 / ssh2-sftp-client upgrade.) The `realPath` itself is bounded by the same 60-second per-operation deadline as the metadata ops, so a dead or hostile session cannot leave a beat hanging; a beat's outcome is swallowed (logged at trace), never reported to the exchange, so a failing keepalive can never itself fail a round. The heartbeat timer is cleared on **every** terminal path - session `end()` and the fatal-'error' guard (a dead channel needs no keepalive) - and is `.unref()`'d, holding to the unref'd SFTP-liveness-timer teardown contract so it never holds a winding-down process open.

Beneath the heartbeat, the adapter enables kernel **TCP keepalive** on the underlying socket (`net.Socket.setKeepAlive(true, 30_000)`, reached through the ssh2 Client's `_sock` since ssh2 exposes `setNoDelay` but not `setKeepAlive`, the same access-past-the-public-API assumption the fatal-'error' guard rests on). This is a transport-layer safety check, **not** a substitute for the heartbeat: it keeps NAT/firewall flow state warm and lets the kernel detect a silently dead peer, but because it rides below the SFTP protocol it does not reset the server's SFTP-command idle timer. The **30,000 ms (30 s)** initial delay (Node sets only `TCP_KEEPIDLE`; the probe interval and count keep their OS defaults) sits below common NAT idle windows and below the application heartbeat interval, so probes keep the flow alive between beats. Both settings are re-applied on every reconnect (a fresh socket per attempt) and both are guarded and non-fatal, exactly like the existing `setNoDelay`: an upstream that relocates the socket degrades to no-keepalive, never to a failed connect.

# SFTP session lifecycle

## SFTP mid-exchange session recovery

The heartbeat above keeps a *friendly* server from dropping a quiet session, but some servers enforce a **max-session or idle cap the operator cannot change** (observed at ~10 minutes) and drop the one long-lived session regardless. Under the persistent-single-session model this adapter runs by default, that drop would otherwise be terminal: the next operation fails and the exchange aborts. Mid-exchange session recovery is the robustness floor beneath that model: on a **clean session loss** the adapter transparently re-dials and re-issues the operation before failing terminally. It is adapter-local - core's rendezvous, `fileSyncConnection`, and `send()` are unchanged. The `connection_per_poll` mode is a separate thing that composes with it, releasing the session at the poll loop's idle boundaries rather than holding one for the whole exchange; when that mode's session exists, and the idle stretches one still spans, are in [FILE_SYNC.md](FILE_SYNC.md#session-lifetime-across-an-idle-boundary). What is counted, capped, exempt and bounded is this section's, and the tables below hold it: a new bound, trigger or exemption appends a row rather than a clause to a paragraph.

See [sftp-adapter-state-machine.md](../notes/sftp-adapter-state-machine.md) for the state-machine model these rows project from -- what a session, an idle boundary and an operation each are, and the design decisions behind the accounting.

### What is re-dialed, and what stays terminal

**Trigger, by post-state not error text.** Recovery re-dials only on a clean loss, read off the connection state after an operation rejects: ssh2-sftp-client clears its internal `sftp` session property on a clean close/end (both its per-operation temp listeners and its global `'close'`/`'end'` listener null it), so a cleared property is the reliable "the session dropped" signal. It unifies the adapter's own `!sftp` throw in `list()`/`createExclusive()` with ssh2-sftp-client's `ERR_NOT_CONNECTED` ("No SFTP connection available") on a high-level `get`/`put`/`delete`/`rename`/`exists` issued against a session already gone, and with the `Unexpected end event` those same per-operation listeners deliver when a drop tears one in flight. These stay **terminal, never re-dialed**: a fatal SFTP protocol error (the wrapper is destroyed and cannot recover -- the `fatalSftpError` guard); any liveness **stall** (`TransportOperationStalledError`), both over a transport still live and on a cleared session whatever the transport reads, since re-dialing on a timeout would hand a withholding server a free liveness reset. The one stall that is a trigger is the withheld-close loss below, a session still set over an ended transport. The memory bounds (`FrameSizeExceededError`, `DirectoryListingBoundsError`) also stay terminal, as does a host-key mismatch on the re-dial itself.

**A session still set over an ended transport is a loss, not a live session.** The session property alone does not determine the reading, because one partner class leaves it set over a session that is gone. A server that drops the SFTP session and then withholds its connection close leaves the transport half-open -- this side's write half ended, and no `'close'` for ssh2-sftp-client's global listener to clear the property from -- so the operation on the wire cannot complete and rides the per-operation deadline to a terminal stall. The trigger therefore reads the transport alongside the property: a session still set over a transport either half of which has ended is the loss it is, whatever the operation rejected with. It is recovered exactly as a clean loss is -- one re-dial, one re-issue, counted in `reconnects` and its mid-exchange sub-count, and warned and charged on the terms its own row in the trigger table below states. Reaching that re-dial means clearing the dead session first, which the recovery does by forcing the ended transport closed -- the mechanism the `connection_per_poll` release uses, with its own call-site resolution and none of its accounting, so a drop is never reported as an idle release. Every way that forced close can fail (a relocated call site, a destroy that raises, a session that does not clear, a transport that does not close) warns naming what broke and the upgrade checklist, then leaves the operation to fail with the loss it already had -- the outcome it had before recovery reached it at all. The internals and the measurements are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md).

**The two operation routes are torn a full event apart, and at the pinned versions both read as the clean loss they are.** A raw-wrapper operation (`list`, `createExclusive`, which drive the `SFTPWrapper` directly) is failed by ssh2, which fails outstanding channel requests only from the socket's `'close'` handler -- the socket's `'end'` emits and cleans the protocol up but leaves them outstanding. It does so after its own `emit('close')` has already run, by which point both ssh2-sftp-client listeners that emit reaches (the per-operation temporary `closeListener` and the constructor's global one) have cleared the `sftp` property; such an operation therefore reaches recovery with the whole sequence run. One of ssh2-sftp-client's own high-level operations (`get`, `put`, `delete`, `rename`, `exists`) does not wait for any of that: its per-operation listeners settle the operation, and clear the same property, from the `Client`'s `'end'`, so it is treated as the clean loss it is a full event earlier, with the transport's `'close'` still owed. Which side of the `'close'` an operation lands on is a property of the route rather than of the drop, and a route can still settle late -- the chunked `put`'s bounded source is a further hop, which can settle past the `'close'`. A tear of a counted outstanding operation is the partner's doing or the terminal close's, never a boundary's, and this ordering determines how the loss is treated, never what a dial may safely follow. The terminal "not a loss" readings -- the adapter's own stall deadline over a session and a transport both still live, and a stall on a cleared session whatever the transport reads -- stay reachable by both routes; what the idle boundary's own precondition closes is the boundary case, which rests on the ordering not at all.

**A cleared session can still leave a transport a re-dial must not be issued over.** A dial issued while the `'close'` is owed is failed by ssh2-sftp-client's own connect-time listeners -- they fail a dial on any lifecycle event that reaches them mid-handshake -- while the handshake it started keeps running, unowned, at the server, whose later events fail the next dial in turn. So the re-dial retires the transport whether or not the session property is still set: the same forced close as above, then a wait for the `'close'` to land, and only then the dial. Nothing on the socket separates the two states -- a torn high-level operation rejects over a socket that already reads destroyed with both halves ended, which is what it reads once the whole sequence has run too -- so the reading comes from the `Client`'s own `'end'`/`'close'` pair, watched by one listener pair attached once per adapter. Where nothing is owed the retirement drives nothing and returns, so the raw-wrapper class pays no wait for it. A transport that cannot be retired refuses the dial and leaves the operation the loss it already had, warning for its own cause, on the same terms as the withheld-close paragraph above. A `Client` that exposes no `on()` to watch leaves no reading to take at all, which the retirement treats as *cannot tell* rather than as *nothing owed* -- the flag's unwritten default is the same value a delivered sequence leaves, so the two are separated by whether the watch attached. It warns for the lost reading, naming the call site and the upgrade checklist, and retires the transport rather than dialing into a window it cannot see: a drop that would have recovered still recovers, at the cost of the forced close's bound on a transport whose `'close'` had already landed. Where the same relocation took the forced close's own call sites with it there is nothing left to retire, and the dial is refused on the terms above. The ordering assumption, the measurements behind it and their bound, and what a version bump must re-verify are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md).

**Re-dial goes through `connect()`, never a bare `client.connect()`.** The adapter retains the full original connect options (including the pinned host key and stored credentials) and re-invokes its own `connect()`, so the re-dial re-runs the entire post-connect sequence on the fresh wrapper. It re-attaches the guarded fatal-`'error'` listener (a listener-free wrapper would turn the next malformed packet into a process crash - see the crash-safety control below), clears `fatalSftpError`, re-runs the enforcing fail-closed host-key verifier that rides the options, re-verifies the raw `sftp` methods, advances the heartbeat epoch, and re-applies `setNoDelay`/keepalive. There is **no re-prompt**: the pinned fingerprint and credentials are reused. A host-key mismatch on the re-dial is terminal for free via `connect()`'s existing "Host denied" retry predicate. (Residual: a mid-exchange host-key mismatch is reported as a raw transport error rather than the security-kind `ConnectionError` that `fileSyncConnection.open()`'s catch produces via `hostKeyVerifier.refusal()` on the initial connect - the exchange still fails closed, but the error kind is coarser on the re-dial path.)

### What each bound protects

**One recovery round per operation invocation.** Re-dial once (that one `connect()` internally makes up to `max_reconnect_attempts` dial attempts), re-issue once; if the re-issued operation also hits a clean loss it rejects terminally rather than looping. The whole operation-plus-re-dial is enclosed by `boundTransport`'s per-operation `peerTimeoutMs` budget in core (a `Promise.race`), so no bespoke total-time timer is added here. Core's three tight teardown budgets - the terminal-frame drain and the connection's own final close, both specified in [FILE_SYNC.md](FILE_SYNC.md#phase-3----cleanup-and-close), plus the abort-marker write (`ABORT_MARKER_WRITE_BUDGET_MS`, ~5 s) - are `Promise.race` bounds of the same kind, so a re-dial during teardown cannot overrun them. The close is the last of the three to run, and short enough to abandon core's wait on a teardown re-dial still in flight; and `end()` latches a `closing` flag that suppresses any further re-dial once teardown has begun.

### What the accounting counts

**The accounting unit is one lost session, not one interrupted operation.** A session is a generation: established by a dial, ended by exactly one recorded cause, and never replaced while it is still live. A drop tears every operation the adapter has on the wire, so a concurrent fan of them -- a `send()` resuming from the protocol continuation alongside the poll cycle's own operations, or the rendezvous sweep in core fanning the rejecting `delete` out -- all enter recovery together over the one session they lost. The transition queue serializes their re-dial requests: the first to reach the front finds that generation still live and charges it, the rest find it already ended and charge nothing, and the drop costs one handshake whichever of them dialed. The charge is made by the transition that ends a generation and never by an operation arm that merely observes one gone. This side's own ends -- the `connection_per_poll` idle release, the connection's terminal close, a fatal SFTP protocol error -- are each charged where they happen, and a generation still live when a recovery re-dial reaches its critical section is one the partner took. An accounting per arm would spend an operator's configured budget at N times the configured rate and report one survived drop as N; an accounting keyed to a high-water mark over the generations already charged would do the opposite and report two genuine losses of two sessions as one.

**The cumulative budget bounds sessions lost.** It is read and spent in the same critical section that charges the loss, under the transition lock, so no further drop can land between the read and the charge. What that means for an operator: a drop whose recovery re-dial fails, and a drop the exhausted budget refuses, each spend their unit exactly as a recovered drop does. That is what the exhaustion message says, in the unit the budget spends rather than in re-dials it cannot promise were made (`the mid-exchange reconnection budget is exhausted: 4 sessions lost over the whole exchange against a max_reconnect_attempts=3 budget, and every session lost spent one whether its re-dial succeeded, failed, or was refused` at the default budget). The tally is the ledger's count read at the refusal -- the same counter the end-of-run summary line reports, so the two lines cannot disagree -- and the terminal loss is itself charged before the refusal, which is why the tally can read one past the budget. A budget of zero has no allowance to describe as spent, so its own clause names the first drop terminal instead. The count is strictly cumulative and never resets on a successful operation, because a server enforcing a session-lifetime cap makes progress every cycle and a reset-on-progress budget would never bound it. Once it is spent the next loss raises a terminal `UsageError` naming the exhausted budget and its two remedies instead of re-dialing. Measured against a partner dropping every session it opens: a fan of 40 concurrent deletes bought no more handshakes than the budget allowed, the arms draining the transition queue behind the one dial.

**A sibling arm that reaches the check on the unit its own loss spent is refused, not given the dial.** The state is reachable only at the cap boundary, and only once the arm that charged their shared loss has failed to re-establish the session: a sibling arriving over a session that charge's re-dial restored never reaches the check at all, finding the session live and re-issuing on it. The refusal is what keeps one lost session worth exactly one re-dial round however many operations the drop tore, a dial for the sibling being a second handshake on a unit already charged. It costs the operator nothing against reaching the same boundary serially, which is measured rather than argued. With one unit left and its re-dial failing, the fan's charging arm reports the dial's own error and the sibling the terminal one. Serially the same failure is reported on the operation that charged it and the terminal error on the next operation issued - the same one charged loss, the same dials spent, and no dial past the budget in either. What a fan changes is which operation hears the refusal. Both readings are consistent with a cumulative bound on sessions lost; the fail-closed one ships, on a budget whose purpose is to bound a partner that keeps taking sessions, and the pair of adapter unit cases that drive the two shapes at a budget of one is what pins it.

**Two exemptions keep that cap from cutting where it should not**, each for a measured reason the table's row cannot hold. `connection_per_poll` is exempt in every phase because the rendezvous that precedes its loop holds one un-heartbeated session across its wait for the partner, so a server cap cuts it there on a wait long enough to outlive the cap. The exemption is what lets the rendezvous survive such a drop (measured: the rendezvous re-dials as often as the cap cuts it and the exchange completes, where the held-session default in the same scenario exhausts the budget and fails terminally). A teardown re-dial - the authenticated abort-marker write and the terminal-frame drain, marked by core's `beginTeardown()` signal at `close()` and at the marker write itself - is exempt so the fast-fail marker still lands when the budget is exactly what was just exhausted.

No reading that a release took the session may stand over a session that is still live, and a transition that raises leaves the reading it found. So a release that ended nothing, and a dial that established a session and then failed its own post-connect verification (whose failure the cycle-start reconnect reports as a skipped cycle rather than a raise), both leave the next drop classifiable as the drop it is. ### Re-issuing an operation

**Per-operation idempotency, applied only on the re-issue.** The relaxations below never touch the first attempt, so genuine lock-conflict and absence detection are unchanged. `list`/`get`/`exists`/`put` re-issue verbatim (`put`'s `flags:"w"` truncate-overwrite is effect-idempotent, and its bounded source is rebuilt from the retained Buffer/chunk list; a one-shot stream source is never re-issued). `delete` maps a source-absent re-issue (`SSH_FX_NO_SUCH_FILE`) to success, since a pre-drop delete that landed reports the source gone. `rename` treats a re-issue whose source is gone (or a code-4 dest-exists) as success when `exists(dest)` confirms the destination, sound because every rename destination is self-prefixed and so unambiguously this party's own landed attempt. The converse does not hold and is not relied on: an absent destination is not evidence the rename failed. In delete mode the partner's consume-delete removes exactly this party's own self-prefixed publish, so a rename that landed durably and was consumed inside the recovery window reports the state a rename that never landed reports -- source gone, destination absent, `SSH_FX_NO_SUCH_FILE` -- and no reading the adapter can take separates them (see "A publish the transport cannot resolve" below). `createExclusive` resolves its own normalized `EEXIST` on re-issue as success, reusing the existing code-11 / code-4-via-`exists()` normalization; the narrow rendezvous-phase "two winners" race this admits is documented at the call site and verified benign (roles commit from hello-filename order before the lock, which only gates eager cleanup).

**A publish the transport cannot resolve is rejected as undetermined, never as a determined non-delivery.** One state survives the recovery above unresolved. A `rename` torn after its filesystem work landed at the server but before its reply was written is a durable publish the sender never learned of. If the partner consumes it inside the sender's recovery window -- in delete mode, the consume-delete of a message is the partner's normal receipt path -- the re-issue then reports `SSH_FX_NO_SUCH_FILE` over an absent destination, which is exactly what a publish that never landed reports. A source still on the server is the one signal that does separate them, and the adapter probes for it: a re-issue whose source survived is a publish that never landed, classified determinately. Once the source is gone the two converge, and measurement found no adapter-observable signal that separates them there. The torn first attempt's error text and code are identical either way, the re-issue's SFTP status is `SSH_FX_NO_SUCH_FILE` in both, `exists(destination)` is false in both, and the consumption leaves no durable trace in delete mode (after the remove the receiver writes nothing). Probing earlier within recovery does not help either, since the replacement session's first operation is a full SSH handshake behind the consumption, and the adapter's own knowledge that a drop occurred with a rename in flight identifies the class, not the outcome. The runs behind that reach the source-absent state by the landed-and-consumed route; a never-landed publish whose source some third party then removed is the same state by another route, and is not staged. Separating them would take a durable artifact created by the publish or by the consumption -- a change to the publish shape or the protocol, not to this recovery. So the adapter rejects that state with a distinct error type (`TransportPublishIndeterminateError`) with the re-issue's own error as its `cause`, rather than resolving it (which would report an unpublished message as sent) or propagating the raw `SSH_FX_NO_SUCH_FILE` (which states a non-delivery it cannot know). Every neighbouring state is unchanged: a confirmed destination resolves, a re-issue failing with the source still on the server propagates its own error, and a non-`SSH_FX_NO_SUCH_FILE` failure -- including the code-4 generic failure, the server's answer that the rename did not take effect -- propagates unchanged. A server reporting a missing rename source as code 4 rather than `SSH_FX_NO_SUCH_FILE` would therefore be classified determinate; the pinned stack does not (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)). The rejection is caller-neutral by design: `rename` is shared machinery, and four publishes reach it -- the message loop's `send()`, its ack, the rendezvous `joining` -> `hello` rename, and the abort marker -- which share no recovery. So its message names a *publish* rather than a message, prescribes no next step, and has no `psilinkRecoveryHintEmitted` tag; a caller whose recovery is established restates it as its own tagged error holding this one as the `cause`. The consumer-side consequence is in [FILE_SYNC.md](FILE_SYNC.md) (I8): the sequence number such a publish spent is not reusable, the next `send()` is refused rather than writing a second message under a sequence number the peer may already have delivered one under, and `send()` is the one caller that does restate this rejection with a remedy.

### Operations concurrent with a re-dial or a release

**Issuance is not serial, and the re-dial does not rest on its being so.** Within one operation the first attempt's promise has settled before its recovery catch fires the re-dial -- that catch is where it settled. Other operations are not serialized against it, though: a `send()` resuming from the protocol continuation issues its operations alongside the poll cycle's own, so a second adapter operation can be unsettled while a re-dial runs. The re-dial neither waits for one nor is made unsound by one, and the measurement says where such an operation goes rather than only that it is harmless. The retirement that precedes the dial waits out -- and against a withholding partner drives itself -- the transport close that tears it, so it is settled ahead of the dial with a drop-shaped rejection of its own and re-issued through its own recovery round, rather than left to ride the per-operation liveness deadline. Where a route settles later than that -- the chunked `put`'s bounded source -- it is fenced instead: it was issued against the session being torn down, and the heartbeat epoch that `connect()`'s re-arm advances is what keeps its late settlement off the fresh session's in-flight count. That is measured against a real partner, driven for a raw-wrapper `list` alongside a high-level `get` in both issue orders, for a forty-way `Promise.allSettled` `delete` fan-out (the rendezvous orphan sweep's shape), for the never-reject `Promise.all` `safeDelete` fan-out beside it, and for a keepalive parked on the wire under both partner classes. Three shapes are stated limits rather than covered ones. The `safeDelete` fan-out never reaches this window at all, sitting outside the recovery chokepoint by its never-reject contract, and what covers a cleanup delete that did not take effect is the record the adapter keeps for it (below). A partner that drops the SFTP session while withholding its connection close produces no tear to settle anything, so both operations ride to the first deadline that expires and the forced close that follows settles the rest, which is the withheld-close path above rather than this one. And core's own `send()`-alongside-`poll()` interleaving, driven across a sweep of cut points, put two operations on the wire at the tear in only some of them and reached this window in none, so what the shapes above measure is the adapter's behavior under such concurrency and not a demonstration that the poll loop produces it at a drop. The numbers, the cut positions, and the pairs the runs did not reach are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md).

A second concurrency is core's per-operation `peerTimeoutMs` budget (a `Promise.race` in `boundTransport`), which can reject a stalled operation to the caller while the adapter operation keeps running, so an abandoned operation may still be inside its re-dial's `connect()` when the aborting caller reaches `close()` -> `end()`. Both share the one `Ssh2SftpClient`, and a fresh handshake must never overlap `end()`'s `client.end()`. Two guards close that. (1) Both take the adapter's session-transition lock (below), so `end()` runs behind the re-dial rather than under it; the post-re-dial `closing` check then reports the original loss rather than re-issuing into a closing adapter, and teardown's own place in the queue is what ends whatever session that re-dial established, so none outlives the close. That wait takes whatever bounds the dial itself (`connect()` has its own retry budget and each attempt its `readyTimeout`), and above it `end()` inherits the ceiling of whoever called it, which for a teardown is core's teardown budget. (2) The re-dial stops the heartbeat before calling `connect()`, so the dropped session's still-armed keepalive timer -- which a clean drop, unlike a fatal error, does not stop -- cannot post a `realPath` on the client mid-handshake; `connect()` re-arms a fresh heartbeat at the end of its sequence.

**The `connection_per_poll` idle boundary is a third such concurrency, and is serialized the same way.** Its release drives the ssh2 `Client`'s `end()` and awaits the `'close'`, and it is that `'close'` -- not the `end()` -- that clears ssh2-sftp-client's `sftp` property. Between the two the session can still read live, over a transport that `end()` has already ended, so an operation rejecting in that window rejects against a session that reads live and is not -- the transport reading above resolves that as the loss it is, while the boundary the release recorded is what decides the accounting. After the window it rejects against a cleared one, which without further information is treated as a server drop. An operation reaching the transport at a boundary is driven by the protocol continuation, not by the poll cycle, so it can land on either side of it. The release does not leave the end of that window to the partner: a server that accepts the disconnect and never closes the connection leaves the transport ended with the session still reading live, so past its bound the release destroys the socket itself and the resulting `'close'` clears the session (the internals and the measurements are in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)). The window spans that forced close, and the release holds the transition lock across it, so an operation arriving inside it is serialized on exactly the terms below rather than being admitted by a session that can no longer answer.

An operation issued once the release is running is held off both readings at the adapter's recovery chokepoint -- the entry point of the recovery-wrapped operations, which is all of them but the never-reject cleanup delete (covered instead by the record below) and a `put` whose source cannot be re-issued. With a release in flight, or a boundary still standing that says a release took the session, the operation re-establishes the session before its first attempt, queued behind the release so it runs on the far side of the close rather than racing it. The precondition is adapter-owned rather than spread across the calling sites in core, because the release that opens the window is adapter-owned; a per-call-site precondition would be an invariant held by discipline, which any future operation issued outside the poll cycle would silently break. The re-establishment is best-effort: a dial failure there resolves rather than rejecting, because the gate is a precondition and not the operation -- the attempt that follows is what decides the outcome, and its own recovery round reports a transient failure with the real error. A host-key rejection still fails the operation closed one step later through the recovery path's own `connect()`. Both readings are written from inside the release's own transition -- the in-flight reading when it reaches the front of the queue, the boundary just before it drives the close -- so "running" is the operative moment, not the call to `releaseForIdle()`. An operation issued while that release is still queued behind another transition reads neither and is issued against the session that is still live. It is on the wire by the time the release enters, and the outstanding-operation precondition below is what covers it.

**A recovery re-dial and a release are serialized against each other wherever the two meet.** The re-dial queues behind the release on the transition lock, so neither a teardown nor a handshake overlaps the release's own close. A handshake started inside that window resets ssh2-sftp-client's event flags and installs its own temporary listeners, so the release's stale `'close'` would land on the fresh handshake and reject it, charging the exchange a re-dial retry (or, at `max_reconnect_attempts=0`, a terminal failure) for a session the adapter closed on purpose. Where they meet is the boundary held for the arm's own outstanding operation (below), a boundary reached anywhere inside the arm being held rather than closed: the release enters ahead of the arm and closes, and the arm's re-dial then parks on the lock with that release's `'close'` still owed. The unit case drives exactly that meeting, and measures both halves of it -- the dial not taken while the release holds, and the operation resolving on the session dialed once it lets go. The release queues behind an in-flight dial for the mirror reason: a dial that lands after the boundary would hold its session across the whole idle gap.

### The outstanding-operation hold on an idle boundary

**An operation the adapter has issued and not settled holds the boundary: no release closes over a counted one.** No gate at operation entry can cover an operation already on the wire, so the precondition is the release's own. The adapter counts the server-driven operations issued and not yet settled at the single entry point every one of them passes through, which opens one span per operation from where it is issued to where it finally settles, a recovery arm included. That span includes the two the recovery chokepoint does not reach, and excludes three round trips issued outside it (the heartbeat's keepalive, the best-effort handle close a listing fires once it has settled, and the cleanup drain's re-issue below). The release reads it once, inside its own transition, with the queue held and nothing yet driven. A non-zero reading returns without closing: the session stays up for the operation it was issued against, and the first boundary past that operation's settlement releases as usual. The count is the adapter's own rather than the SFTP heartbeat's, which the release itself stops as its first statement and which this mode never arms. It is a hold and not a drain -- the release does not await the operation -- so nothing gains a wait: the release's own bounds stand unchanged, a teardown queued behind it cannot be parked past them, and the drained-boundary path still drives the ssh2 `end()` synchronously with the call. The precondition applies to the idle release and to no other transition: a teardown closes over whatever is outstanding by design, and a recovery re-dial that waited would park behind the very class of operation that drove it. A held boundary is ordinary rather than anomalous -- a concurrent `send()` straddling a boundary produces it -- so no occurrence is warned, and it is in particular not a declined release, which reports a transition that did not complete within the release's wait.

**What a held boundary costs, and what the run reports.** It costs the mode one idle gap per boundary the operation straddles, and the run's total is accounted rather than left silent. Two adapter counters cover it: `heldBoundaryCount` (every boundary a release holds) and `heldBoundaryStretchCount` (the unbroken stretches those boundaries fall in, a stretch opening at a held boundary with none open and closing when the outstanding count next reaches zero). Both are reported together as one end-of-run operator line at default verbosity, the stretch sub-count only where it is strictly below the boundary count. Both stay out of the reconnect total and out of the machine `metrics` event, because nothing was closed and so nothing was lost. What the stretch measure separates is one unbounded transfer holding twenty boundaries (20 boundaries, 1 stretch) from twenty straddling `send()`s that each settle between boundaries (20 and 20) -- the first says the mode has stopped delivering per-cycle sessions for the rest of the run, the second that it is working. Its stated limit is that it measures unbroken hold and not operations: operations that overlap continuously, never letting the outstanding count reach zero, read as one stretch however many of them there were.

**The exclusion set is a check rather than a claim.** Two sibling analyses parse the adapter with the TypeScript compiler API over one shared definition of a request-issuing call site (`scripts/lib/sftpAdapterSites.mjs`, so the two cannot come to cover different sets). `scripts/sftp-tracked-round-trips.test.mjs` fails on any site the per-attempt bracket does not cover and its three allowances do not name. `scripts/sftp-operation-spans.test.mjs` fails on any site no outstanding span encloses and its two allowances do not name, so a data-plane entry added later that reaches the client without the entry point above it fails there rather than passing unnoticed. Their common reach is what they can follow syntactically: a call written as a property access (`receiver.member(...)`) on the client, on the raw `SFTPWrapper`, or on a local aliasing either, with coverage traced through the adapter's promise plumbing and its spans through the private single-attempt methods a `runOperation` body calls. Each header states that reach exactly, and with it where its analysis falls short of a proof. A callee or a receiver written outside the reach is not decided at all, and a best-effort call that merely names a settler is credited with the bracket. And the span analysis decides lexical enclosure rather than enclosure in time. That is why the listing's post-settle handle close -- outside the span in time, inside the body that issues it -- is named by the bracket's allowances and not by the span's, and why the converse direction, the per-attempt layer being reachable only through the entry point, is not decided either.

**What the count is, and what bounds the hold.** Issued-and-unsettled is not the set that is on the wire, and departs from it in both directions. An adapter bound that expires settles the operation on this side while the library request it raced is still outstanding at the server -- every one of these bounds is a race that abandons rather than a cancellation -- so the count returns to zero and the next boundary closes over that request. Symmetrically, an operation the server never answers is never settled from this side at all: core's whole-exchange budget is the same kind of race, so the operation the adapter counted stays counted. The hold therefore lasts exactly as long as the operation is unsettled, and the bound on that is the operation's own: the per-operation deadline where it has one, and nothing where it does not. Two shapes have none -- a `put` from a string or stream source, which has no per-operation bound at all, and a progress-reset window (the chunked `put`'s idle window, the capped `get`'s sink) that a server trickling acknowledgement re-arms rather than trips -- and a session held for one of those stays held for the rest of the exchange. Both directions are pinned by adapter unit tests, so a change to either fails a check rather than silently contradicting this paragraph. A third departure is the recovery arm, which the same span covers rather than a second one nested inside it. The span opens where the operation is issued and closes when it finally settles, so the first attempt, the re-dial, the re-issue and (for `rename()`) the destination probe that confirms a landed pre-drop rename all fall within one span, while the per-attempt heartbeat brackets open and close inside it. There is therefore no point in an operation's life at which the count reads it settled while it is not. Each of the two boundaries that would cost a landed publish is covered by construction rather than by placement: between the re-issued attempt's rejection and the probe it drives, where a boundary would tear the probe and an unanswered probe confirms nothing, so a rename that did land would be reported as the undetermined outcome above. And between the re-dial and the re-issue, where a boundary would close the very session the re-dial established and the re-issue would reject with a dead-session error that no per-operation resolver reads at all. Both are pinned by adapter unit tests that sweep a boundary across the whole arm rather than placing it at one named point, since with one span there is no reading of the count that names either boundary.

**The heartbeat's activity accounting stays at the per-attempt bracket rather than moving to the span.** It answers a different question -- whether a round trip is on the wire, which across a recovery arm none of this operation's is -- and widening it to the span would leave the re-issue unmarked. The arm's own re-dial re-arms the heartbeat from scratch and zeroes whatever in-flight count preceded it, so a keepalive could then be posted alongside the very round trip the bracket exists to keep one away from. `connection_per_poll` arms no heartbeat at all, so the question does not arise in the mode the outstanding count serves.

### The deferred cleanup-delete record

**A cleanup delete of this party's own in-flight temp file, issued into the idle gap, is recorded and re-issued.** The never-reject cleanup delete is the one operation that reaches no gate at all: its contract puts it outside the recovery chokepoint, so a delete issued with a release in flight, or with a boundary standing that says a release took the session, reaches no session and removes nothing. It resolves all the same, so its caller in core cannot tell that from a delete that landed. Only the adapter can, which is why the record lives there, on exactly the terms the recovery chokepoint's precondition states: a per-call-site check in core would be an invariant held by discipline. What it costs otherwise is a file no later mechanism in the run sweeps -- the in-flight `temp-<uuid>.tmp` a failed `send()` removes from its own catch, which is tracked in no responsible-file set and so never reaches `cleanup()` (see [FILE_SYNC.md](FILE_SYNC.md)). The path is recorded on two readings, either sufficient on its own: the release readings the gate above takes, read before the delete is issued, and the delete's own rejection, which additionally covers a cleanup that failed for a reason of its own. It is re-issued at the tail of each re-establishment (`ensureConnected`), with the session-transition lock released -- the one call site that covers both the cycle-start re-dial and the re-establishment `close()` drives ahead of the terminal-frame drain. A re-issue that fails is offered back to the record -- so a server briefly unreachable at one boundary is swept at the next -- against a bounded per-recording budget rather than for the life of the run, and on the same cap the first record ran. It is not retain-gated and must not become so: a `temp-*.tmp` is a failed in-flight write and never transcript, so a retain-mode run leaves none behind either.

**Only the protocol's own in-flight temp shapes -- `temp-<uuidv4()>.tmp` and the hello publish's `temp-hello-<uuidv4()>.tmp` -- are admitted to the record, and that is what makes deferral sound.** `safeDelete` is a general transport method: core calls it with the shared rendezvous lock path, and with names read back from a listing of the directory the peer writes into. A record is keyed on a path and re-issued at an arbitrary later point, so admitting one of those would let a transiently-failed delete remove whatever has since come to occupy that name -- a fresh authenticated abort marker the peer wrote in the interim, say, turning a fast `PeerAbortError` into a wait to the peer-inactivity ceiling. Both temp shapes have a per-file v4 UUID, so the path a re-issue reaches is the file it was issued for or nothing at all. The recognizer is core's own (`isProtocolTempName`, which spans both shapes), not a copy in the transport, so the two cannot drift; the basename is what decides. (The entry sweep applies a narrower predicate -- it excludes the hello shape, which may belong to a concurrently starting peer; see [FILE_SYNC.md](FILE_SYNC.md). So the only hello temp that ever reaches this record is one this party wrote itself, from the publish's own failure path, never a name read back from a listing.) Every other path `safeDelete` is handed keeps the plain best-effort behavior -- issued once, never recorded -- which is also what bounds what an adversary can do to the record: the only names that consume it are protocol temps.

**Each re-issue has a teardown-scale deadline, and that is what bounds the whole drain.** The re-issues go out concurrently, and each is held to **5 s** in place of the 60 s per-operation deadline every other round trip has, so the drain costs one such wait rather than one per record and needs no ceiling of its own above them. The value is teardown-scale because of where the drain's wait lands: core forwards `ensureConnected` unwrapped and `close()` awaits it with no budget above, and the recovery gate's first attempt after an idle gap waits behind it too. Without it a server that accepts delete requests and withholds their callbacks would add a whole per-operation deadline (60 s) to every close -- an order of magnitude above the teardown bounds beneath it. Cutting a re-issue short there loses nothing real: against such a server the delete was not going to take effect, and the expiry is a rejection like any other, so the path is offered back to the record on the terms below. The drain resolves rather than rejecting, and its result is fenced out of `ensureConnected`'s: core's poll loop treats an `ensureConnected` rejection as a terminal dial error, so a best-effort cleanup sweep must not be able to end an exchange. The dial's rejection is not fenced -- a host-key verification failure still fails the exchange closed through this same method.

**The re-issue is the one unsettled round trip an idle release may tear, and is left uncounted.** Of the round trips this mode leaves the adapter waiting on, every one but the drain's re-issue passes through the outstanding-operation bracket whose count is the idle release's precondition -- the heartbeat's keepalive is unbracketed as well, and this mode arms no heartbeat -- and that exclusion is what preserves the mode's own guarantee. The third unbracketed round trip is not this case: the best-effort handle close a listing fires once the listing has already settled, which a boundary falling there tears too, at the cost a withheld close callback has anyway -- a handle leaked until session teardown, which under `connection_per_poll` is that boundary. Already-settled work needs nothing from the release's guarantee; the re-issue is the round trip for which that guarantee had to be reasoned about at all. Counted, a re-issue against a server that accepts DELETE and withholds its callback would hold every idle boundary for its whole bound -- and a boundary that closes nothing leaves the session live, so the next re-establishment finds one, re-runs the drain and regenerates the operation, `connection_per_poll` silently reverting to a held session for the rest of the run. That needs no failed publish to reach: the entry sweep hands every listed `temp-<uuidv4()>.tmp` from a server-supplied listing to the cleanup delete. Two properties make the tear sound. The record survives it -- the torn delete rejects, which offers the path back to the record -- so the release defers the work rather than losing it, which is the very thing the record exists to do. And a torn DELETE of this party's own temp leaves no state its re-issue can misread: the server either performed the unlink or did not, and the re-issue reads the first as the success it is (`notFoundOK`). The bracket's other duty does not reach it either -- the record and the drain exist only in `connection_per_poll`, which arms no heartbeat.

**What bounds the record: a cap on entries, and a re-issue budget per recording.** The record is capped at `MAX_DEFERRED_CLEANUP_DELETES` (**64**), and overflow refuses the new record rather than evicting an older one: refusing degrades the overflowing cleanup to exactly the behavior it had before the record existed, while evicting would turn a cleanup this adapter had already promised to re-issue into a silent loss. Each recorded path additionally has a budget of `MAX_DEFERRED_CLEANUP_REISSUES` (**3**) re-issues: a re-issue that fails records the path again with one fewer, and a spent budget gives up on that recording. Without it the only thing that ever clears a record is a delete this side saw succeed, so a delete that can NEVER succeed -- a peer-owned temp under a sticky-bit directory, which the entry sweep still attempts -- is retried at every re-establishment for the life of the exchange. With the record full that is a whole record's worth of extra DELETE round trips per poll cycle against the partner's server. A spent budget degrades that cleanup to the pre-record behavior exactly as overflow does, and is logged at debug for the same reason. Re-recording a failed re-issue runs through the same capped, shape-narrowed path a first record does, so a re-record made while the record is full is refused like any other. What the drain guarantees is that a path it could not perform is offered back, not that it is always kept -- refuse-not-evict applies to a re-issue's own path as much as to a newcomer's.

**What the budget is a bound on, and the amplification that leaves.** It is per recording and not per path per connection: giving up ends that recording and remembers nothing about the path, so a path that reaches the cleanup delete again is recorded afresh with the whole budget, by either route into the record. A path re-recorded while its own re-issue is still in flight likewise keeps the budget the re-record wrote, the record leaving an entry that already stands untouched rather than applying the failing re-issue's decrement to it. What that costs a run turns on which call site offers the path, and for the case above -- a temp this party can never delete -- only one does. Core sweeps orphaned temps in the rendezvous entry scan, which runs once per exchange rather than once per poll cycle, and the poll loop tolerates a protocol temp without ever sweeping one. Such a temp is therefore recorded once and costs that sweep's own attempt plus `MAX_DEFERRED_CLEANUP_REISSUES` re-issues spread over the re-establishments that follow -- a few round trips for the whole run. The per-cycle reading is what a caller re-offering the same path every cycle would pay, each re-offer being a fresh recording; no call site does that today, and this is the assumption to re-check before one is added. The amplification is bounded either way: a drain issues one re-issue per recording, and the cap above bounds how many recordings stand at once, so what a re-establishment can cost is one bounded sweep of the record. Remembering a given-up path -- a tombstone that would make the budget per path per connection -- is not done, because it would consume a cap slot, which is how a peer would crowd the send path's own cleanups out of the record. What the budget does not cover is the mode's per-cycle session: what keeps an idle release from being pinned off is the re-issue's exclusion from the outstanding-operation bracket, and the budget does not stand in for that exclusion. Counted, a re-issue holds the boundary of every cycle its budget reaches, measured against a server that accepts DELETE and withholds its callback as four handshakes over seven poll cycles where the uncounted re-issue delivers seven.

**The five states that drain nothing, and two stated limits.** The refusals above are logged at debug rather than warned -- they fire only where a drain has repeatedly failed to reach the server, which the operations that needed that server already report. The drain does nothing in five states, each for its own reason:

- the default held-session mode, which keeps no record and issues no drain at all;
- a fatal SFTP protocol error, where a request posted to the destroyed wrapper never calls back -- the very thing the cleanup delete's own short-circuit refuses to do -- so a cleanup recorded before that error is not reintroduced at teardown after it;
- a latched teardown, where `end()` is already closing the client;
- no live session, the record keeping for the next re-establishment;
- an empty record, the mode's healthy path, which costs no round trip.

Two limits are stated rather than closed. The first is the run: a record left when no further re-establishment happens is never re-issued, so the guarantee is that a cleanup deferred across an idle boundary is performed later in the same run, not that the adapter eventually reconciles the directory. The second is the cap, whose bite the re-issue budget bounds rather than leaving to stand for the run. A directory holding many protocol temps this party cannot delete -- peer-owned files under a sticky-bit directory, which the entry sweep still attempts and whose number is therefore peer-influenced -- can fill the record before the send path needs it, and a send-path cleanup offered while the record stands full is refused. Such a fill clears itself, because the drain clears the record before issuing, each failed re-issue re-records at one below the budget it ran with, and a spent budget is given up on rather than recorded again. A fill made entirely of undeletable temps survives the `MAX_DEFERRED_CLEANUP_REISSUES - 1` re-establishments that follow it, standing full again at the end of each, and is gone by the end of the `MAX_DEFERRED_CLEANUP_REISSUES`th, which admits the send path again. Measured at the cap against a server whose own `unlink` refuses for real: the record stands full and refuses a send-path cleanup after each of the first two drains, and is empty and admits one after the third and after every drain past it. What a refusal inside that window costs is exactly the pre-record behavior -- that cleanup is issued once, never re-issued, and its temp survives the run, which the first limit already excludes from the guarantee -- and it is that degradation, rather than any claim about how hard a peer-influenced fill is to produce, that the cap is accepted on.

### The session-transition lock

**Every session transition runs under one FIFO lock the adapter owns, teardown included.** The five -- the first dial, the cycle-start reconnect, the recovery re-dial, the idle-boundary release, and `end()` -- acquire it through one helper, taking their queue slot synchronously at the call, so they run in the order they were requested in and a microtask inserted anywhere on a transition path cannot reorder them. The teardown latch is read at exactly one place, inside that helper, once per transition: `end()` sets it synchronously before enqueuing, so a transition queued behind teardown does not run its body (it returns its caller's stated "nothing to do" value, or refuses a re-open) while one already running is waited out by teardown's own position in the queue. `end()` therefore has no privileged entry and pre-empts nothing. Without that ordering a handshake would run alongside `end()`'s `client.end()` and, because ssh2-sftp-client's `end()` short-circuits on a cleared session, that `end()` would resolve without ending the ssh2 `Client` at all -- `close()` returning over a ref'd socket. The mechanisms driven past the public API -- ssh2-sftp-client's `connect()` and `end()`, the ssh2 `Client`'s own `end()`, and the forced socket destroys -- each present the transition they run inside and check its identity against the one holding the client. So the chokepoint is a check rather than a reading of the call graph, and it cannot be satisfied by a transition that merely happens to be running. Its single exemption is named and narrow, and is the subject of the paragraph below. The lock also covers the release boundary above: the helper is its only writer, it restores what it found when a transition raises, and it takes any reading that a release took the session back from a transition that leaves a session still live.

The lock is not mode-gated, and two orderings in the default held-session mode follow from that. A teardown concurrent with the first dial never runs ssh2-sftp-client's `end()` under that handshake -- the overlap this whole control exists to stop, and the one that motivated it. It waits the handshake out only as far as the acquire bound below, past which it destroys the transport and cuts the handshake short (measured against a real ssh2 server that stalls its handshake: `end()` returned about 10.0 s after the teardown was requested and the parked first dial rejected `ERR_GENERIC_CLIENT` 3 ms later). A `connect()` issued while a teardown is in flight parks for that teardown's own bounds before refusing the re-open rather than refusing at once; the refusal and its wording are the same either way. Short-circuiting it on a pre-acquire reading of the teardown latch would restore the second, out-of-lock reading that the single in-lock read exists to replace, buying a faster failure on a path no caller in this repository takes (core's `open()` and `close()` are not concurrent). A `connect()` after a teardown has settled does not park at all: the queue is drained, so its transition enters its critical section in the same tick and the refusal is immediate. What core layers above is not uniform: it wraps a data-plane operation in a fresh `peerTimeoutMs` budget and `end()` in the much shorter teardown budget below, but forwards `releaseForIdle` and `ensureConnected` unwrapped, neither being a peer round trip -- and a bound there would abandon core's wait alone in any case, since it cannot close anything the transport owns. What bounds each transition's own wait is the adapter's, next.

**The wait for the transition ahead is bounded by one fixed adapter-owned ceiling, and an expired wait never proceeds.** `TRANSITION_ACQUIRE_TIMEOUT_MS` (10 s) bounds every queued acquire, so no transition can park behind another indefinitely. The two unattended failures that motivates are a teardown parked behind an abandoned operation's recovery re-dial, which leaves a finished run alive on a ref'd socket, and an idle release parked behind a concurrent `send()`'s re-dial, which stops the poll loop until the hour-scale parked-receive ceiling misattributes it to peer silence. It bounds the wait and not the transition being waited on. A ceiling on the dial would make a teardown's wait the dial's whole budget -- `(max_reconnect_attempts + 1)` attempts at `server_connect_timeout_ms` plus the inter-attempt delays, about two minutes at the defaults and unbounded above as the operator raises that timeout. It would also rest on an assumption about when ssh2 arms its connect deadline rather than on a number the adapter owns. The value sits above the 6 s a legitimate release can spend (`CLIENT_CLOSE_TIMEOUT_MS` then `FORCED_CLOSE_TIMEOUT_MS`), so a teardown queued behind a normal release does not give up on it -- a relationship between three constants, held by a unit test that drives a release's whole close budget with a teardown queued behind it rather than by the arithmetic. It owes nothing to the budget `end()`'s caller holds, which can sit on either side of it: core's own `min(CONNECTION_CLOSE_TIMEOUT_MS, peerTimeoutMs)` is under this bound exactly where `peer_timeout_ms` is below 10 s and above it at `peer_timeout_ms = 10_500` (`CONNECTION_CLOSE_TIMEOUT_MS` being 30 s), and `peer_timeout_ms` is validated only as a positive integer, which leaves both sides of that crossover reachable. Abandoning core's wait closes nothing in any case: the destroy is what closes the transport, and it runs off the abandon's own timer whether or not anything is still waiting on `end()`, so a caller that gave up is still left an exited process rather than a half-open socket. That timer is left ref'd as the safe default and pinned as such by a unit case, so the ref cannot be dropped silently; unlike the forced close's ref, though, no process-exit difference behind it is measured, the transition being waited on being itself parked on a ref'd socket handle in every state driven.

No waiter proceeds into its own session action when the wait expires -- not the dial, not the ssh2 client's `end()`, not the socket destroy -- because the transition it gave up on still holds the client. Each abandons its own transition through the transient-failure path it already owns, and a new transition kind appends a row:

| transition | what its expired acquire reports |
| --- | --- |
| cycle-start dial | a cycle to skip |
| idle release | that it released nothing, under a warning paced like the forced release's |
| recovery re-dial | that no session is live for the re-issue |
| the first dial | a rejection, there being no value that could mean "no session was established" |
| teardown | nothing: it is the one kind whose expiry still closes something, below |

A waiter also gives up its turn without resolving its own queue slot, which stays chained to the transition actually holding the client: resolving it would admit that waiter's successor alongside a holder that has not settled, which is the overlap the lock exists to prevent. Teardown is the one exception and only in the narrow form: it may give up ssh2-sftp-client's `end()` -- which a live handshake beneath it resolves having closed nothing -- and destroy the transport itself, which needs nothing from the peer and settles the very dial being waited on. That destroy is the one mechanism driven from outside the transition holding the client, exempt from the identity check above, and what makes it safe is the teardown latch rather than the destroy's own harmlessness. Every transition behind the teardown skips its body, so the holder ahead of it is the only one that can be running, and the exemption checks that latch rather than asserting it. Because destroying the socket cuts an in-flight handshake short, `connect()`'s retry loop reads the teardown latch between attempts as well: without that it re-dials on a fresh socket and keeps a torn-down connection, and a process that exits by drain, alive for the remainder of the dial budget. Both halves are measured against a real ssh2 server (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)). Cutting that handshake short also settles it with the exact error a genuine peer close produces, so nothing riding the settled dial may report this side's close as the partner's. The cycle-start re-dial reads the teardown latch before warning (a closing run has no next tick to retry on either), and an operation whose recovery re-dial was the dial destroyed reports the session loss it was recovering from rather than that rejection. Both read adapter state -- the latch, and whether an abandoned teardown closed the transport itself -- and neither matches on the error text, which cannot tell the two apart.

### The connection's terminal close

**The connection's terminal close is bounded on the same terms, in both session modes.** ssh2-sftp-client's `end()` settles only from the ssh2 `Client`'s `'close'`, so a partner that accepts the disconnect and then goes quiet leaves it pending indefinitely -- a hang after a fully successful exchange, in the default held-session mode as much as under `connection_per_poll`, since nothing on that path is mode-gated. `end()` therefore races that one call against `CLIENT_CLOSE_TIMEOUT_MS` and, past it, drives a destroy of the socket beneath it, which settles the pending call rather than abandoning it; a second, ref'd `FORCED_CLOSE_TIMEOUT_MS` bound covers the destroy, and the socket's own `destroyed` flag is read back where it is driven. Resolving is the only outcome that means the partner closed the connection: a rejecting call closed nothing (ssh2-sftp-client raises it from a temporary `'error'` listener whose end/close listeners are gated off), so it takes the same forced-close path, and the rejection is re-raised only behind it. Destroying rather than merely bounding the wait is the point of the control: the half-open socket is a ref'd handle and the CLI's success path exits by event-loop drain, so a bound that abandoned the client would return the caller over a process that never exits. The forced path requires only the one member it drives, `_sock.destroy`, not the wider set the idle release resolves, so a bump relocating a member this path never calls cannot silently disable it.

**Both of that close's operator-facing guarantees are conditional on the destroy landing.** The informational line, and the property that no caller -- including one sharing the memoized close -- sees a rejecting `end()` over a socket still alive, hold on the fully successful path alone. Three degraded branches stand in their place, each warning and returning:

- the one member this path drives is not available after `connect()`, so nothing is destroyed at all;
- the bounded destroy raises;
- the socket does not report itself `destroyed` afterwards.

Each warning names what broke and the "Upgrading the SFTP Stack" checklist in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md), and each names the same operator consequence: the connection is left to the operating system, may stay half-open, and a half-open connection can keep this process from exiting. None of the three emits the informational line, which reports the close in the past tense and follows the close for exactly that reason. A rejecting `end()` is re-raised behind every one of them too, so on the member-unavailable branch it is re-raised over a socket this side never closed. Nothing on the forced path throws: core treats `end()` as best-effort and logs that rejection at debug, and the exit code is untouched either way. The one informational line at default verbosity is the successful outcome's alone, and the close is not counted as a lost session and not folded into the idle release's forced-release total, which measures that mode's per-cycle boundary instead. Core keeps a safety check of its own: `end()` is the one transport call wrapped by the short teardown budget [FILE_SYNC.md](FILE_SYNC.md#phase-3----cleanup-and-close) specifies, rather than a fresh peer-inactivity budget. That safety check bounds core's wait for a transport it does not own; it cannot close anything, which is why the adapter-side destroy is what the guarantee rests on.

## SFTP fatal-packet crash safety

The size and liveness bounds above turn a hostile server's behavior into a bounded failure, but they leave one behavior unbounded: a process crash, which is neither a memory nor a time exhaustion. The SFTP adapter drives the raw ssh2 `SFTPWrapper` directly (for `list()`, `createExclusive()`, and the streamed `get()`), and after the session connects that wrapper has no `'error'` listener of its own - ssh2's `Client.sftp()` attaches a setup-time listener but strips it before handing the wrapper back, and `ssh2-sftp-client` attaches `'error'` handlers only to the SSH `Client` object and to per-operation read/write streams, never to the wrapper. So a server that returns a malformed SFTP reply packet, or faults the framing layer itself with an over-long packet, reaches ssh2's fatal-error path, which emits `'error'` on a listener-free `EventEmitter`. Node escalates that to an uncaught exception, crashing the CLI outright, before the lock-file and temp-file cleanup and the typed exit-code mapping that an orderly failure runs. The malformed reply packets are a malformed NAME, HANDLE, or DATA packet, an unknown packet type, and a duplicate VERSION packet after the session is already ready; a malformed *first* VERSION instead rejects `connect()`, whose setup-time listener is still attached then, so it never reaches this listener-free state. An over-long packet trips the length-prefix check before any request id is consumed. The adapter closes this by attaching a single guarded `'error'` listener to the wrapper at connect time (once per wrapper instance, so a reconnect's fresh wrapper is re-guarded and a repeated connect does not duplicate the listener), so a fatal protocol error is handled rather than fatal.

A handled fatal error leaves the session dead but the process alive. ssh2's `doFatalSFTPError` emits the `'error'`, destroys the wrapper, then calls `cleanupRequests`, which fails the callback of every request still registered. What bounds an *in-flight* `list()` or `get()` depends on which request received the fatal packet, and the realistic case is not `cleanupRequests`: when the malformed packet is the reply to the in-flight request itself, ssh2 has already deleted that request from its pending table by the time `doFatalSFTPError` runs. The `NAME` and `DATA` handlers delete it unconditionally up front, *before* the parse/check that triggers `doFatalSFTPError`; the `HANDLE` handler deletes it inside its own malformed branch (on a defined request id), immediately before triggering it. The placement differs but the net effect is the same: `cleanupRequests` finds nothing left to fail for that request and the in-flight callback never fires - the operation is bounded by the adapter's 60-second wall-clock deadline (`list()`'s deadline, the capped `get()`'s idle window, or the uncapped `get()`'s whole-operation deadline), not by `cleanupRequests`. `cleanupRequests` does fail an in-flight callback promptly only in the other cases: a fatal error that arrives on a *different* request id, or a connection-level fault (such as an over-long packet, which faults the framing/length-prefix layer before any request id is consumed), leaves the in-flight request registered for it to fail. Either way the in-flight operation is bounded - the 60-second deadline is the bound that covers the realistic in-flight case, so it is required and must not be removed on the assumption that `cleanupRequests` covers in-flight operations. The listener also captures the cause, which bounds the *next* operation: every server-driven method consults this captured error at entry and short-circuits before issuing a request the dead channel can never answer. `list`, `get`, `createExclusive`, `put`, `delete`, `rename`, and `exists` reject promptly with the same terminal `TransportOperationStalledError`; `safeDelete`, whose contract forbids rejecting (callers run it in `catch` blocks), instead resolves promptly as a best-effort no-op. This entry guard matters beyond saving a deadline wait. After a fatal error ssh2 destroys the SFTP channel but the underlying TCP/SSH socket stays up, because a hostile server keeps it alive. So an unguarded write, stat, or delete would buffer its request on the closing channel and hang until its own per-operation bound fires (60 s) rather than failing at once - a teardown that stalls for the full bound, since `FileSyncConnection.close()` drives `safeDelete`/`delete` during cleanup. The guard converts that stall into a prompt, orderly failure.

This bounds the malformed/fatal-packet crash and, once a fatal error is known, every server-driven operation: the entry guard short-circuits the next read or write rather than buffering a request the dead channel can never answer. The one behavior the guard cannot catch is a hostile server that withholds a write, stat, or delete callback *without* any protocol error, so no fatal `'error'` fires and `put`/`delete`/`rename`/`exists` never short-circuit at entry. It is not left unbounded: each of those operations has its own per-operation bound (the 60-second deadline for `rename`/`delete`/`exists`, the 60-second progress idle window for `put`) that fails the withheld callback terminally, with the whole-exchange budget beneath it as a fallback. The best-effort `safeDelete` has the same 60-second deadline so a teardown delete cannot be the soft target left on the coarse budget while every other write op fast-fails, but - because its contract forbids rejecting - it swallows the deadline's stall error and resolves rather than reporting it, bounding the wait without breaking the never-reject guarantee its `catch`-block callers rely on. The entry guard's role is to spare the 60-second wait once a fatal error is already known, not to be the sole thing standing between the call and an indefinite hang.

The bounds above reach past the public `ssh2-sftp-client` API and drive ssh2 internals directly, so they rest on assumptions about ssh2's internal behavior that an upgrade can silently break. Before raising either `ssh2` or `ssh2-sftp-client`, follow the upgrade checklist in [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md#upgrading-the-sftp-stack-ssh2--ssh2-sftp-client), which names the internal assumptions, the source files to re-read, and the contract-assertion test that fails red on a lifecycle change.

## SFTP host-key verification

The controls above defend against a hostile administrator of the server a party has correctly reached; a distinct control defends against reaching the wrong server. On the SFTP channel an operator may pin the server's host key by setting `connection.server.host_key_fingerprint` to its OpenSSH SHA256 fingerprint -- or to a non-empty list of them (see *Multiple pinned fingerprints* below) -- and every connection then verifies the presented host key against the pinned fingerprint(s) before authentication, aborting unless it matches one. This is the SFTP analogue of the certificate pinning the signing identity uses (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#receipt-signing-identities)): trust comes from a fingerprint rather than a certificate authority. And it replaces SSH's *silent* trust-on-first-use with an explicit, enforced pin -- supplied out-of-band, or established by a confirmed first-use prompt (below) and then verified on every subsequent run -- so a man-in-the-middle or a substituted server presenting its own host key is detected rather than silently trusted.

The fingerprint is `SHA256:` followed by the unpadded *standard* base64 (alphabet `[A-Za-z0-9+/]`, not base64url) of the SHA-256 digest of the raw SSH host-key wire blob -- byte-identical to what `ssh-keygen -lf` and OpenSSH clients display, so an operator pins exactly the value those tools print. It is validated at config-parse time by `HOST_KEY_FINGERPRINT_REGEX` (`/^SHA256:[A-Za-z0-9+/]{42}[AEIMQUYcgkosw048]$/`): the final character's class is restricted because the last 6-bit base64 symbol of a 32-byte (256-bit) value has two low bits that are zero in the canonical encoding, so only those sixteen symbols are valid there. A bare 43-character base64url value -- the shape of a signing `partner_fingerprint` -- is detected separately and rejected with a message naming that confusion, since the two fingerprints use different alphabets and one is easily pasted for the other.

Verification runs in ssh2's `hostVerifier` callback, which the SSH handshake invokes with the raw host-key blob before authentication. psilink always installs a callback (in one of three forms below) and installs it *after* applying `provider_options`, so a provider option can neither override nor disable it; the `provider_options` allowlist is in any case default-deny and drops `host_verifier`/`hostVerifier` and `host_hash`/`hostHash`. `hostHash` is never set: setting it would make ssh2 pre-hash the key before the callback, destroying the raw bytes the fingerprint is computed over. The three forms: with a pin set, an *enforcing* verifier computes `SHA256:` + base64(SHA-256(blob)) once and compares it against each pinned fingerprint with a constant-time byte comparison over the decoded digests, accepting on the first match. Nothing secret is compared -- a host key and its fingerprint are both public -- so the constant-time comparison is house-style hygiene for digest comparisons, not a timing-oracle defense, and the short-circuit on the first match is likewise not a timing concern. With no pin, a *fail-closed* verifier computes the presented fingerprint into the error and refuses (see the no-pin default below). And on the deliberate first-use probe, a *capture* verifier records the presented fingerprint and refuses, so the probe learns the key without authenticating (see first-use trust below).

**Multiple pinned fingerprints.** `host_key_fingerprint` accepts either a single fingerprint or a non-empty list, validated entry by entry at config parse (each against `HOST_KEY_FINGERPRINT_REGEX`, with the signing-`partner_fingerprint` confusion detected per entry; an empty list is rejected, since it would pin no key while reading as "pinned"). The enforcing verifier accepts a presented key matching *any* listed fingerprint, which gives zero-downtime host-key rotation: an operator stages the incoming key alongside the current one for the rekey window so either is accepted with no failed exchange in between, then drops the old entry after the cutover. The single-fingerprint form is the one-element case and behaves identically. The verifier records the *matched* pin as the observed host key (`FileSyncConnection.observedHostKey`) -- the one fingerprint the server actually presented, not the whole set -- so the cross-party reconciliation below still compares one observed key per party even when each party pins several. The set membership lives in one tested primitive (`matchHostKeyFingerprint`, `packages/core/src/utils/sshHostKey.ts`), so there is a single decode-and-compare implementation. On a mismatch the error's own message names the presented fingerprint and how many pins were compared against; the set itself rides a labelled cause link of its own, so a many-pin config spends its own link's budget rather than the re-pin instruction's (see [Display sanitization escape format](#display-sanitization-escape-format)).

The control is fail-closed on every path. A mismatch, a malformed or empty blob, or any error inside the callback results in `verify(false)`, which ssh2 raises as a fatal handshake error whose message contains `Host denied (verification failed)` -- before authentication, so no credential is presented to an unverified server. The CLI adapter treats that rejection as terminal and does not retry it: retrying would only re-run the key exchange against the same untrusted host. The `Host denied` message fragment is an ssh2 internal assumption recorded in the [SFTP-stack upgrade checklist](DEPENDENCY_PINS.md#upgrading-the-sftp-stack-ssh2--ssh2-sftp-client); even if a future version renamed it, core re-wraps the same rejection into an `SFTP host-key verification failed:` message and the outcome is unchanged, only slower. The mismatch message names the presented fingerprint and key type so an operator can distinguish a legitimate key rotation from an attack. The key type is the server's choice within the bound below, so it rides a labelled cause link of its own (see [Display sanitization escape format](#display-sanitization-escape-format)) and is escaped at the display boundary before it reaches the operator's terminal or log. A changed key is never auto-accepted -- there is no standing always-accept flag (which would be permanent trust-on-first-use disguised as protection). The recovery for a legitimate rotation is a deliberate re-pin, modeled on ssh's `known_hosts` flow: verify the new fingerprint out-of-band, then add it to `connection.server.host_key_fingerprint` (alongside the current pin for a staged rotation, or in place of it) or remove that field and re-run interactively to re-establish trust on first use (which overwrites the stored pin).

**The presented key type is bounded before it is shown.** Every surface that names the server's key type -- both refusals above, the first-use trust prompt, and `probe-host-key`'s human and `--json` output -- takes it from `keyTypeFromBlob`, which reads the blob's leading length-prefixed string and returns it verbatim only when it is **at most 64 bytes** and every byte is in **`[A-Za-z0-9._@-]`**. That charset is the SSH algorithm-name charset plus the `.` and `@` a certificate type uses. Every type in real-world use conforms with room to spare -- the longest names are the certificate forms, around 40 bytes (`ecdsa-sha2-nistp521-cert-v01@openssh.com`) -- and the length matches the bound a partner's advertised key type is parsed under (see *Cross-party fingerprint reconciliation* below), so an accepted type is always one this party can advertise. A type outside either bound is *replaced* by `(unknown:<hex>)` -- the lowercase hex of its first 24 bytes, at most 58 characters; a blob naming no type at all (a bad, zero, or past-the-end length prefix) is `(unknown)`.

Three properties of that replacement are critical. It encodes the offending bytes rather than discarding them, so two rejected types that differ within those first 24 bytes do not collapse into one value that the reconciliation below would read as *the same* key type on both sides. Its parentheses fall outside the accepted charset, so a server cannot name its key type a string that passes for this first-party framing. And it fits the partner's 64-character bound, so advertising it does not read as a malformed advertisement and drop the reconciliation. Replacing rather than refusing the connection is deliberate: of the sites that read the type, all but one already refuse, and the exception is the pin-matched success path -- where trust rests on the fingerprint the operator verified out-of-band, not on the type. So refusing there would cost availability on the one path that works while the bound already contains the bytes. The bound sits under the display-boundary escaping rather than replacing it: the type is still escaped where it is rendered.

The replacement has three limits. Past the 24 bytes it encodes, the distinction above stops: two rejected types sharing a 24-byte prefix and differing only after it collapse to one placeholder, which the reconciliation below treats as *the same* key type on both sides. So a divergence between the two parties is described with the narrower rekey-or-interception wording instead of the wording that also offers the benign multiple-host-key explanation. The warning still fires either way -- it is triggered by fingerprint inequality alone, never by the key type -- and an adversary who wants the two observed types to compare equal needs no prefix collision at all, since naming the presented key `ssh-ed25519` does it. The collapse is therefore a limit to state rather than a defect to close. The other two limits are unchanged by this bound. The console never sees the replacement: `probe-host-key --json` emits the placeholder, but the console re-validates that field against the same length and charset at its own trust boundary (see *`probe-host-key` and console probe-to-fill* below), and the placeholder's framing is itself outside that charset. So a non-conforming type is reported there as a generic probe error rather than as the replacement text -- exactly as it did before the bound, since such types failed that boundary already. And the composition-site redaction still passes a charset-conforming lookalike: a type such as `-----BEGIN-OPENSSH-PRIVATE-KEY-----` is inside the accepted charset, so it is returned verbatim and rendered on a refusal, and on the log and prompt lines that name a key type. What that costs is operator confusion, not disclosure -- the bytes are the server's own choice, capped at 64 characters, on a cause link of their own, and no operator secret can reach this field.

Each pinned fingerprint may be supplied as an `@`-file reference (`@/path/to/fingerprint`) for operators who keep it in a read-only secrets mount; in a list, entries may freely mix literals and `@`-file references. Because `@`-file resolution runs after parsing, a literal `@path` -- which cannot match the `SHA256:` format -- is exempt from the parse-time format check, and each resolved file's contents are re-validated against `HOST_KEY_FINGERPRINT_REGEX` at resolution: a malformed or empty secrets file fails as a `UsageError` (exit 64) naming the offending reference, rather than as a confusing host-key mismatch at connect time.

Verification applies to the CLI `sftp` channel only. A file-drop makes no SSH connection, and the browser/proxy SFTP path does not run ssh2's `hostVerifier`. An attacker cannot induce the unpinned state to inject their own key, because the pin is configured out-of-band (or established on first use, below) and the invitation endpoint schema rejects a `host_key_fingerprint` field outright (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#transport-layer-authentication)).

**No-pin default: fail-closed.** When no fingerprint is pinned, `FileSyncConnection.open` installs the fail-closed verifier, which refuses the connection before authentication (so no credential reaches an unverified server) with an error naming the presented fingerprint to pin. An unpinned connection is never warn-and-proceed: a key nothing has verified is never trusted, and the recovery from the refusal is the first-use flow below, which is what makes a pin obtainable for an operator who has none.

**First-use trust (ssh-style).** An operator who cannot obtain the fingerprint out-of-band can still reach the verified-on-every-subsequent-run state by establishing the pin on a deliberate first connection. Every CLI command that opens an `sftp` connection -- `exchange`, the online `invite`/`accept`, and a zero-setup exchange -- runs this flow before the real, enforcing connection (a shared `establishHostKeyTrust` step):

- On a TTY (interactive), it *probes* the server: a throwaway connection whose capture verifier records the presented host key and immediately refuses, so the key is learned without presenting a credential and without waiting on a user prompt inside the handshake (which would race ssh2's `readyTimeout`). It then shows the fingerprint and key type, prompts for confirmation, and on a yes pins the fingerprint into `connection.server.host_key_fingerprint` in memory and proceeds with a real, now-enforcing connection. Because that real connection re-verifies the just-pinned key, a key swapped between the probe and the connect is still caught (the same brief TOCTOU window as `ssh-keyscan`-then-`ssh`).
- Non-interactively (no TTY -- an automated run, or one piping its CSV through stdin), it does not prompt and does not auto-accept: it fails closed with an actionable error naming the recovery (run once interactively to pin, or set `host_key_fingerprint` out-of-band). That recovery reaches the operator because the refusal is partitioned by chooser -- the configured host and the config path each ride a labelled cause link of their own, so neither can spend the recovery's display budget (see [Display sanitization escape format](#display-sanitization-escape-format)). This is the same fail-closed posture as the no-pin default, reported earlier and with CLI-specific guidance.

How the confirmed pin reaches disk depends on the command: `exchange` reads an existing `psilink.yaml` and does not re-write it, so the pin is written there in place (preserving comments). The online `invite`/`accept` and a zero-setup run with `--save` include the in-memory pin in the configuration they write after the handshake. A zero-setup run without `--save` trusts the key for that one exchange and persists nothing. The probe reuses the exact connect options (algorithms included) the real connection uses, so both negotiate the same host-key type and the pinned key is the one later runs verify.

**`probe-host-key` and console probe-to-fill.** The same capture verifier is exposed as a standalone CLI command, `psilink probe-host-key <sftp-url> [--json] [--connect-timeout <dur>]`: it builds a minimal `{channel: "sftp", server: {host, port?, username}}` connection from the URL -- no credential, and no operator- or URL-supplied username. ssh2 requires a username string to `connect()`, so a fixed placeholder is set, and because the capture verifier calls `verify(false)` at host-key verification (before the SSH userauth phase), that placeholder is never sent to the server. It runs `probeHostKeyFingerprint`, validates the result against `HOST_KEY_FINGERPRINT_REGEX`, and prints it. `--json` emits exactly one stdout line `{"fingerprint":"SHA256:...","key_type":"..."}` (snake_case, the machine form); the human form escapes the server-controlled key type through `sanitizeForDisplay` as `sftpSession.ts` does. On the exit-69 path `--json` emits instead a one-line diagnosis of a peer that never identified itself, discriminated on a `diagnosis` key the success line does not have (see [CLI.md](../CLI.md#when-something-other-than-an-ssh-server-answers-the-port)); its `excerpt` field is bytes the peer chose, encoded as a JSON string value and re-validated, capped, and escaped at the console's own trust boundary exactly as `key_type` is. Exit codes mirror `exchange`: a transport failure (unreachable, refused, timeout) is `69`, a usage error (a non-sftp scheme, a malformed URL) is `64`. The command establishes no trust and pins nothing: it only reads a key over the same untrusted network the exchange will use.

**The machine lines are emitted as printable ASCII.** `--json` exists so a script reads it, and what a script does with a line it cannot classify is print it -- to a terminal, or into a log a human later reads. Bare `JSON.stringify` does not make a line printable: it escapes `U+0000`-`U+001F`, the quote and the backslash, which keeps a line one line, but passes DEL, the whole C1 range, and `U+2028`/`U+2029` through unescaped, and the peer's excerpt is a latin1 decode of adversary-chosen bytes, so each of those is reachable. Both lines therefore go through one encoder (`asciiSafeJsonLine`, `apps/cli/src/util/jsonLine.ts`), which rewrites every UTF-16 code unit outside `U+0020`-`U+007E` in the encoded text to the `\uHHHH` escape JSON already defines for it. Matching by code unit rather than code point is what makes an astral character escape as the surrogate pair `JSON.parse` recombines rather than as a code point JSON has no escape for. That encoder handles every machine-readable stdout line psilink prints -- the opt-in fd-3 NDJSON event stream sits outside it, held instead by composition-time display escaping (`apps/cli/src/util/jsonLine.ts` names the exclusion and the test that pins it) -- the `doctor --json` verdict included, whose checks interpolate the operator's own `SMB_*` values, validated against the C0 controls and DEL alone. So the same bytes are reachable there, alongside an `smbclient` NT_STATUS token that is ASCII by construction (see [CLI_DOCTOR.md](CLI_DOCTOR.md#the-line-is-printable-ascii)).

Three properties follow, and they are what the encoder is for. The keys and value types are unchanged, so the machine contract is the one specified above. The document the text parses to is exactly the document `JSON.stringify` alone would have produced, so **this is not a second escaping altitude**. A consumer that renders a parsed field to a human -- the console, at `parseProbeDiagnosis` -- receives the peer's bytes as it always did and escapes them once, at its own display sink (see [Display sanitization escape format](#display-sanitization-escape-format) and CONTRIBUTING.md, Operator-facing escaping). And it is an encoding rather than a redaction, so material that must not be shown at all is still stripped where the excerpt is produced: `classifyPeerAnswer` takes `redactPrivateKeyMaterial` over the whole retained read and clips the excerpt out of what that leaves, so both routes hold the same already-stripped bytes, and neither route strips again where it interpolates. The human route's per-link render pass remains behind it as a no-op safety check. The order is the one the strip is written for, and the same one the `doctor` detail excerpt takes (see [CLI_DOCTOR.md](CLI_DOCTOR.md#what-the-verdict-withholds)): a clip taken first can cut a `BEGIN ... PRIVATE KEY` marker in half, leaving a fragment neither the block rule nor the fail-closed dangling rule matches, and a consumer redacting the clipped excerpt then strips nothing. The pair is driven end to end -- a listener writing DEL, a C1 control and a `BEGIN ... PRIVATE KEY` marker on a real socket, asserted on the emitted line's bytes, in `apps/cli/test/integration/backendAgnostic/hostKeyProbePeerIdentification.test.ts` -- and the console boundary's single pass is held by driving a spawned child with the same answer in both encodings in `apps/web/test/unit/jobs/jobSftpProbe.unit.test.ts`.

**Diagnosing a peer that never identifies itself.** An SSH server sends its identification string before anything else, so a dial that never reaches host-key verification saw something that is not one. The pinned stack reports a proxy answering with an HTML page, a TLS service, and a firewall closing the connection in front of the server all as the same `Connection lost before handshake`, with the peer's own bytes discarded (recorded as a measured assumption in the [SFTP-stack upgrade checklist](DEPENDENCY_PINS.md)). Every dial therefore reaches one diagnosis step (`apps/cli/src/connection/sftpPeerIdentification.ts`), which on that rejection opens **one** further connect attempt -- a single `net.connect` call to the same endpoint, which for a dual-stack hostname may race address families within that one call, exactly as the dial it follows does -- and reports what the peer sends. It runs at exactly one layer, the transport adapter's dial sequence -- the one path to `ssh2`'s connect, so the connect loop, the connection-per-poll cycle-start re-dial, the mid-exchange recovery re-dial, the teardown's, and the credential-free host-key probe (which dials the same adapter as its raw client) all pass through it. Both probe entry points therefore add no diagnosis of their own. One classifier over one read: a caller that wrapped its own would diagnose a rejection already diagnosed -- the gate walks the cause chain, so the rejection kept under the probe's host-key message still matches -- and read the peer a second time. Six constraints hold it:

- It is **credential-free by construction**: the socket only reads. Nothing is written on it -- no credential, no identification string, no SSH traffic -- which is the same assumption the probe itself rests on, held here by a socket that has no write path rather than by a verifier that refuses in time.
- It is **time-bounded** by one deadline over connect and read together, at most 2 s and clamped to the dial's own `serverConnectTimeoutMs`, so it cannot outlast the budget the operator already granted the connect. It runs once, after the dial's retries are spent, not per attempt.
- It is **spent once per connection**, and one diagnosed failure opens exactly one further connection whatever the entry point -- driven, and counted at the endpoint, in `apps/cli/test/integration/dialPeerIdentification.test.ts`. The connection-per-poll mode dials at every cycle start, so an unbounded diagnosis would re-dial a peer that is already answering wrongly once per tick for as long as the condition stands; the first dial failure that reaches the read spends the connection's whole budget for it, and every later one keeps the rejection the stack raised. A dial issued once the connection's teardown has begun is not diagnosed at all: an abandoning teardown destroys the transport beneath a dial in flight and that dial rejects with the very wording the gate rests on, so diagnosing it would read a peer about a close of psilink's own making.
- It is **byte-bounded**: at most 512 bytes are retained -- each delivery truncated to that bound before it is held -- and at most 128 of them are included into the diagnostic, so a peer answering with megabytes neither holds memory here nor spends the operator's output. The bound is on what is retained, not on what transits: the socket is never paused, so a single delivery of up to the stream's high-water mark (64 KiB, measured) reaches the read callback before the stop rule fires, and 512 bytes of it survive that callback.
- Its **verdict comes from the read**, never from the rejection's text, which decides only whether to look. A peer that turns out to be an SSH server, and a connection that cannot be made at all, are reported as nothing: the operator keeps the rejection they already had. So a stack that reworded its rejection degrades to the undiagnosed failure, never to a wrong diagnosis.
- It **changes no dial's classification**. A rejection the adapter already treats as terminal -- a host-key refusal, a key exchange this process cannot perform -- is left with the message that classification reads, checked before the diagnosis rather than assumed disjoint from it. A peer-identification failure is itself no verdict: it stays the transient dial failure it was, retried on the connect loop and skipped-and-retried on the cycle-start path, because it is derived from bytes the peer chose and no party that answers the port may end an unattended exchange by answering it wrongly.

What the operator is told partitions by chooser, as the refusals above do: the diagnosis sentence and its recovery step are first-party links, the configured endpoint is a link of its own (unbounded in the config schema and, on the acceptor route, copied from the partner's invitation). **The peer's excerpt is a link of its own** -- adversary-chosen bytes, which the display boundary escapes and caps within that link alone (see [Display sanitization escape format](#display-sanitization-escape-format)). The stack's own rejection stays the last link, so the wording that distinguishes a clean close from a reset survives. Two shapes are named in the copy, an HTTP status line and a TLS alert record; anything else is described as non-SSH data and shown. The copy **claims only what the read establishes**: it states what the peer's first bytes held and names the middlebox cause as a likelihood, rather than asserting that the peer is not an SSH server. RFC 4253 lets an SSH server send lines ahead of its identification string, so a real one whose preamble runs past the retained bound -- or whose identification string arrives after the deadline -- is classified non-SSH here; the recovery step names that bound so an operator whose server has a long banner recognizes their own case. Both sides of the bound are driven in `apps/cli/test/unit/connection/sftpPeerIdentification.test.ts`, and every dial path -- the connect loop, the cycle-start re-dial, and both probe entry points -- in `apps/cli/test/integration/dialPeerIdentification.test.ts`, against listeners that are not SSH servers with the real test server as the control. A peer that accepts and then closes having sent **nothing** takes its own message naming the likely cause -- a firewall or IP allowlist ahead of the server -- and has no excerpt, there being none; a peer that accepts and merely stalls is not given that message, since a slow server is indistinguishable from it here.

The console repurposes it as *probe-to-fill*, the browser analogue of first-use for an SFTP connection authored in-app. The console's Node server cannot probe SSH in-process -- core has no SSH implementation and the `ssh2` stack is exact-pinned to `apps/cli` only, which the web app must not import. So it spawns this command (the image already spawns the CLI for every SFTP op) and re-validates every field at the trust boundary: the fingerprint against the same regex, the `key_type` against a length (<= 64) and charset bound (server-controlled bytes, encoded as a JSON string). It discards the child's stderr entirely (it can hold server-controlled bytes) and drives a watchdog (SIGTERM at ~15 s, SIGKILL after a grace) so the endpoint's latency is bounded above the child's 10 s `readyTimeout`. The reconciled outcome is a typed result -- `ok` / `unreachable` (exit 69) / `timeout` (watchdog kill) / `error` -- reported over `POST /api/jobs/sftp/probe` (the SSRF-bounded, single-flight, stateless endpoint specified in [SERVER_JOB_API.md](SERVER_JOB_API.md#probing-the-server-host-key)). An `unreachable` result with a diagnosis reaches the operator as the console's own account of it, and that result partitions by chooser as the CLI's cause chain does -- by structure rather than by cause links. The announcing channel is a single stable polite `role="status"` region, mounted in every phase and first in the probe result's DOM order, whose text is a fixed console sentence interpolating nothing. The peer's excerpt renders outside it, as a sibling, in a read-only monospace field whose value the peer's bytes are and whose accessible name is a fixed first-party string the peer cannot write. Two properties hold the partition, and neither rests on what the bytes say. **Containment**: the excerpt is not a descendant of the announced region -- nothing is, the region holding only that fixed sentence -- so the run an assistive technology reads out on the failure has no byte the peer chose. The console's diagnosis and its recovery step render on the visible failure alert, which announces nothing of its own and sits ahead of the excerpt rather than after it. **Terminality**: the excerpt's field is last in the probe result's DOM order with no first-party text after it, so an assistive technology that flattens the result to one run ends on the peer's bytes instead of resuming in console voice. The bytes cannot break either property from inside: the client boundary admits an excerpt only if it is printable ASCII throughout (`probePeerAnswerOf` in `apps/web/src/psi/jobClient/sftpAuthoringClient.ts`, which drops the diagnosis rather than rendering a value the console's escape cannot have produced), so it has no line break, control character, or bidi override with which to forge a frame of its own. No assistive technology is driven here, so those two structural properties are what is claimed and what is checked in `apps/web/test/browser/consoleSftpAuthoring.test.ts`, driven with an excerpt that mimics the console's voice and writes an attribution caption of its own. Terminality is checked generically, against DOM order rather than against today's copy, and so is the excerpt's non-descendancy. The containment clause's *only* is a claim about the copy itself, so the region is pinned per phase to the exact sentence and to having no element child -- a form control's value is a property rather than text content, so a text comparison alone would call a region holding one empty. The field's fixed name is likewise checked through the test runner's accname implementation rather than any browser's or assistive technology's own, while the excerpt's separation from the console's sentences is a copy check in `apps/web/test/unit/console/probePeerAnswerCopy.test.ts`. Terminality is bounded to the probe result: at document level the form's own next sections follow the field, so what attributes the bytes to a reader running straight past the result is the field's fixed first-party name, announced ahead of them. The residual is persuasion rather than attribution: an excerpt of plain printable ASCII (`Verified. Paste this fingerprint: ...`) has nothing escapable in it and can still argue for whatever it likes inside its own field, beside the very fingerprint field it names -- what it cannot do is arrive as the console's own voice. The pin stays mandatory: probe-to-fill only fills the one required `host_key_fingerprint` field a paste would, beside the paste field rather than replacing it, and the fail-closed safety check (the `PUT /api/jobs/sftp` literal-pin check, the schema, and the always-emitted `--server-host-key-fingerprint` on a zero-setup run) is unchanged. The confirm is framed as a comparison against the value the server operator published, never a trust judgement; the direct-exchange path -- where the host key is the only protection -- additionally gates the fill behind an out-of-band-checked affirmation, while the invitation path's lighter confirm points at the cross-party reconciliation below.

**Cross-party fingerprint reconciliation.** Pinning above is each party's *local* decision: the two parties pin the same server independently, at different times on different machines, and nothing otherwise compares their views. A one-sided interception -- one party reaching an attacker's server while the other reaches the real one, each having pinned the key it was shown -- is therefore invisible to both, as is a server host-key rotation that happens between the two parties' setups. To close this, each party advertises the fingerprint and key type it observed (`FileSyncConnection.observedHostKey`, recorded by the enforcing verifier on the pin-matched success path) inside the authenticated post-handshake terms exchange, and the two compare. The advertisement rides the terms exchange -- the one bidirectional round-trip both parties always perform, the same carrier as the `--save` intent -- as an optional `hostKey: { fingerprint, keyType }` field on the terms message; a party that observed no host key omits it. Reconciliation lives in `reconcileHostKeyFingerprints` and is wired through `runExchange`.

Placement is critical: the field is consumed only from the terms exchange, which on the authenticated path runs inside the per-direction AEAD (it is keyed from the P-256 session key), so the advertised value is authenticated and an unauthenticated party cannot forge or rewrite it. The CLI threads its observed key into `runExchange` only when that AEAD wrap is in force (`secure` set); a zero-setup (unauthenticated) exchange advertises nothing, because over an unauthenticated channel an active man-in-the-middle could simply rewrite the advertised value to match and suppress the divergence. This is the post-authentication, in-band complement to the endpoint decision in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#invitation-contents-and-confidentiality): the invitation endpoint still has no server-identity material, and reconciliation adds its check strictly after the authenticated handshake instead.

The comparison is a verbatim string equality on the fingerprint (a host key and its fingerprint are both public, and the result drives only a warning, not a trust decision, so no constant-time compare). It reports a divergence -- never an abort, in keeping with the honest-but-curious model -- as a warning naming *both* observed fingerprints, with wording that distinguishes the two cases the difference can represent: when the key *types* match, the difference is narrowed to a server rekey between the two setups or a one-sided interception. When the key types differ, the message additionally reports the benign multiple-host-key case, because a server that presents more than one host key may legitimately show each party a different one, so a type difference alone is not evidence of an attack. A party that observed no host key (a file-drop mount or the browser/proxy SFTP path) advertises nothing, and a one-sided absence reconciles to no divergence rather than a false positive. The advertised field is fail-soft: a malformed or over-bound `hostKey` (reachable only from a non-conforming or future-versioned peer, since the field rides the AEAD) is read as absent rather than aborting the linkage, so this advisory check can never turn a valid exchange into a hard failure. That drop is silent toward the protocol, but `exchangeTerms` still distinguishes a present-but-malformed advertisement (a `hostKey` on the wire that fails validation) from a genuine absence and reports it out as `partnerHostKeyMalformed`. The CLI logs the malformed case at debug, so an operator can tell a non-conforming peer from one that simply observed no host key (a file-drop or proxy path), while the benign no-host-key path stays quiet and the level stays low enough that a version-skew does not warn on every exchange. The dropped bytes are not logged -- they are unusable and partner-controlled, so echoing them would widen disclosure and risk log injection. Both parties' key types are the server's choice and are routed through `sanitizeForDisplay` before they enter the warning: the locally observed one has passed the charset and length bound above, while the partner's advertised one is bounded in length alone. As net-new security behavior layered on the host-key control, this reconciliation is in scope for the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

# Parsed-input and display bounds

## Application-layer parsed-input bounds

The transport bounds above stop a hostile *server admin* from exhausting memory or hanging the link; a distinct control stops the authenticated *exchange counterparty* - a mutually-distrusting peer (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)) - from exhausting CPU or crashing the parser with a pathological-count message. The linkage terms (held in an invitation token and re-parsed off the post-handshake wire by `protocolSetup`) and every post-handshake wire message are validated with Zod, and a frame within the ~512 MiB frame-size cap above can still pack millions of *invalid* elements into a partner-controlled collection. On Zod 4.4.3 that drives one of two `RangeError`s as Zod accumulates one issue per invalid element: a collection nested two or more array/record/tuple frames deep overflows the call stack while Zod spreads that issue array up through the frames (`Maximum call stack size exceeded`, at ~130k elements). A flat collection with no such frame instead makes Zod throw `Invalid string length` while it builds the error string (the `ZodError` message is `JSON.stringify`-d eagerly in the constructor, exceeding V8's maximum string length at ~3.5M issues, after a multi-second CPU burn). A plain `z.array(element).max(N)` closes neither: Zod v4 validates every element *before* the length check, so the issues accumulate before `.max()` can fire.

Two strategies bound the complete set of partner-parsed collections, chosen per field by whether a legitimate value is large:

- A collection legitimately in the millions - the PSI association-table indices, the payload rows / row indices, a partner's original-index list - has a single-issue validator (`packages/core/src/utils/singleIssueArray.ts`): it validates the element type in one `every` pass that emits at most one issue regardless of count. So an arbitrarily large *valid* message still parses while a hostile one fails as a clean, bounded rejection. A count cap is unusable here - any bound low enough to forestall the `RangeError` would reject a real result.
- A collection whose legitimate count is small - the linkage fields and keys, each constraint's `exclude` denylist, a transform step list, a key's elements, the payload `send`/`receive` column lists, the abort-reason list - has a count gate (`packages/core/src/utils/boundedArray.ts`). A permissive `z.array(z.unknown())` first stage accepts the array unvalidated, a count refine rejects an over-count array with one issue *before* per-element validation runs, and a `.pipe` re-validates the now count-capped array against the real element schema, preserving every per-element check and its issue path for an in-range array. The refine is `abort`, so an over-count value stops rather than letting the still-raw `unknown[]` flow on to a cross-field refine (which would dereference an unvalidated element). The `transform.params` record's key count is bounded by the same permissive-stage + count-refine + pipe shape, but with a bare **key count** (`packages/core/src/utils/objectKeyCount.ts`, `MAX_PARAMS_ENTRIES`) in place of the array length check. That count is still O(n) in the record's key count - a materialized `JSON.parse` object offers no sub-linear own-key count, and `for...in` enumerates eagerly - but it is the *cheapest* O(n) pass, and `for...in` avoids the result array `Object.keys(rec).length` would allocate and stops its body once the bound is passed. For this record the gate also closes a distinct linear event-loop burn, not the `RangeError` class above: a millions-key `params` record otherwise burns multiple seconds *twice* before its count is even checked, once in the snake->camel `camelizeKeys` pre-pass that runs ahead of Zod (`parseLinkageTerms`) and once in the permissive record stage. Each of those is an expensive per-key pass (a snake->camel rewrite, a per-key Zod parse); the gate replaces both with the single cheap key count. `parseLinkageTerms` hands the same bound to the camelize pre-pass, which leaves an over-count `params` value verbatim (handing it to the schema's refine, which rejects it) instead of rewriting every key. So the over-count record is counted but neither rewritten by the camelize pass nor per-key-validated by the record stage - cutting the multi-second burn to roughly one key enumeration rather than eliminating it (it stays O(n), bounded above by the frame cap). The `camelizeKeys` pre-pass walks arrays too, so the count-gated arrays above would incur an analogous pre-pass walk this per-record skip does not address; a global node budget in the walker (next paragraph) closes that, bounding the total the pre-pass rewrites rather than only this one record's width. The per-field count constants - 256 to 4096, each far above any real config and far below the `RangeError` thresholds - live beside their schemas in `packages/core/src/config/linkageTermsSchema.ts` and `packages/core/src/protocolSetup.ts`.

Independently of the count/CPU-burn class above, the partner-supplied payload **column names** have a per-element length bound (`MAX_NAME_LENGTH` = 256, in `config/linkageTermsSchema.ts`), folded into the same single-pass `columns` validator (`payloadExchange.ts`) so it adds no per-element issue accumulation. This is not a DoS control - the frame cap and the single-issue validator already bound a `columns` array of any size - but a data-hygiene one: a received column name flows verbatim into this party's local exchange-record file (the `governance.payloadReceived` categories of the audit artifact in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md)). So the wire bounds its length to the same `MAX_NAME_LENGTH` ceiling the operator's own `terms.payload.receive` names have. Both that upper bound and the `.min(1)` floor those local-terms names also have are enforced on the wire. The floor is safe to enforce there because `inferMetadata` rejects an empty column name at intake (the disclosure-surface change in [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md)), so an honest sender never emits one -- not even from the trailing-comma CSV header that would otherwise produce a `""` column -- and the wire floor therefore cannot fail an honest exchange. What it refuses is a partner who hand-crafts a `[""]` column to suppress this party's exchange record - an empty name would otherwise reach the non-fatal record-build guard, which skips the record while the exchange still completes and discloses, erasing the audit of a disclosure that happened. The exchange-record schema (`RecordPayloadColumn.name`) applies both the `.min(1)` floor and the same `MAX_NAME_LENGTH` ceiling independently, so neither an empty nor an over-long name can reach the on-disk record by any path - the write path rejects it at record build (the non-fatal build guard then skips the record, leaving the exchange result unaffected) and the read path rejects it at parse. The ceiling is safe against an honest sender for the reason the floor is, and by a matching gate rather than by luck: `assertDisclosedNamesCarriable` (`payloadExchange.ts`) refuses a disclosed column name longer than `MAX_NAME_LENGTH` at the local prepare step and again at the run boundary (`prepareForExchange` and `runExchange`), before any credential, terms, or data are sent. So a `PreparedExchange` assembled outside prepare is refused too - gated on `output.shareWithPartner`, the same output gate `assertPayloadSendDisclosed` applies to its empty case, since a party whose partner is entitled to no result transmits no column and has no name. That is what keeps the wire bound from being the first enforcement for a name the sender's own CSV header supplied -- inferred metadata passes through no schema -- so the ceiling refuses a crafted partner rather than failing an honest exchange mid-frame. Both mint boundaries read the same `overlongDisclosedColumnPositions` predicate (`config/metadata.ts`) over the metadata they publish a disclosed set from, so neither `psilink invite` nor the web inviter mints a token naming a column the exchange it commits to could not hold. Both counts are UTF-16 code units (Zod `.max()` over a string), on the wire, in the record, and at that send-side gate, so the three cannot disagree about which names are carryable; the web app's display cut on a column name counts code points and bounds only what paints (`apps/web/src/components/ColumnName.tsx`).

Three acceptance surfaces bound a partner-declared name list by count as well as by length. The acceptor's confirm-columns step states a payload-declaration conflict by listing the columns the invitation declares that the operator's marks do not send. The acceptor's consent screen renders the invitation's declared `payload.send` and `payload.receive` lists one item per entry behind its details disclosure. The CLI accept prompt emits those same two declared directions one indented line per name, above the consent decision it stops at. Every one of those lists is the partner's: `MAX_PAYLOAD_ENTRIES` (**4096**) names, each escaping to `DEFAULT_MAX_DISPLAY_LENGTH` (**256**) plus the truncation marker, is roughly a megabyte of printable text. That text sits above the metadata grid and the launch control on the one screen that holds the gate, behind the details disclosure on the one screen that holds the consent decision, and between the operator and the question on the terminal that asks it. The result is usability denial rather than injection, the names being escaped. That megabyte is the ceiling's arithmetic rather than a delivered size. All three surfaces take their declaration from `decodeInvitation`, which refuses an encoded invitation above `MAX_ENCODED_INVITATION_LENGTH` (**64 KiB**) before it parses, so a declaration that arrives at any of them reaches roughly 346 such names - about 93 KB of painted text and a thousand-odd terminal rows, measured through the CLI prompt. The cap is sized to the schema ceiling because the schema admits it; what it forecloses in practice is that 93 KB. Each surface therefore paints at most `MAX_DECLARED_NAMES_SHOWN` (**10**) names per list and closes a bounded list on the sentence stating how many it did not paint, all three reading that constant and that sentence from one module (`packages/core/src/consent/declaredNameBound.ts`), applied in `apps/web/src/exchange/AcceptorColumnsStep.tsx`, `apps/web/src/components/InvitationTerms.tsx`, and `apps/cli/src/invitationDisplay.ts`. The module sits in `@psilink/core` rather than in either app because `apps/` consumes `packages/` and never the reverse, so a bound two app workspaces share has no home inside one of them. The cap is on what is painted only. The remedies the conflict notice offers, the refusal itself, the direction labels with the declared total each of them states and their `(none)` cases, the count-only cross-check the CLI prompt runs over both declared directions, and the always-visible direction counts the consent screen states beside its lists are all derived from the whole declared set. On the CLI the bound is applied at the two declared-payload call sites rather than inside the shared `logList` renderer, which also emits the already-bounded `transform.params`, the declared data standards, and this party's own outbound-send columns - none of them a partner-reachable `MAX_PAYLOAD_ENTRIES` list. The count bound closes the declared-payload vector only: every other list on these surfaces is bounded at its schema source rather than capped at the render, and the linkage-key block - `MAX_LINKAGE_ENTRIES` (**256**) keys of up to `MAX_KEY_ELEMENTS` (**256**) elements, each element painting several lines through the uncapped `logList` path - stays the larger partner-controlled render on the same surface. Each rendered bound is driven at `MAX_PAYLOAD_ENTRIES` with every name at the escape's own cut (`apps/web/test/browser/acceptDeclaration.test.ts`, `apps/web/test/browser/invitationTerms.test.ts`, `apps/cli/test/unit/commands/accept.test.ts`). One residual is distinguished rather than removed: `sanitizeForDisplay` passes printable ASCII verbatim, so a declared name can read exactly as the unshown-count sentence for its direction, and what tells the first-party line apart from such a name differs by surface. On the web it is list placement - the name paints as a bulleted item inside that direction's list container while the count line renders outside it, and the always-visible direction counts state the whole declared magnitude either way (`apps/web/test/browser/invitationTerms.test.ts`). A line-oriented terminal has no such container, so on the CLI it is the bullet prefix, and the claim is at the level of the lines the prompt emits. Every painted name is emitted as `- <name>` at the list indent and cannot break its own line to shed that prefix (the escape neutralizes every control code point), while the count line is emitted at the same indent with no bullet (`apps/cli/test/unit/commands/accept.test.ts`). What the terminal's rows show is a stated limit rather than a claim: soft wrap starts a continuation row at column 0 and `sanitizeForDisplay` passes an ASCII space verbatim, so a name padded to the wrap boundary reproduces the bare count row byte for byte at a matching width (measured at 80 columns). That residual is left open - any printable prefix would be equally fakeable, the renderer cannot know the terminal's width, and the genuine count line still prints exactly once per bounded direction, which is the signal the true remainder is recoverable from. The CLI's heading for each declared direction states that direction's whole declared count beside the label's basis marker - first-party text no partner string precedes, read from the declared set rather than from the painted subset - so the magnitude the count line states is corroborated from a position the wrap residual does not reach (`apps/cli/test/unit/commands/accept.test.ts`).

The `camelizeKeys` pre-pass has its own global width bound, the running-total analogue of the per-record `params` skip and of the pre-pass's existing `MAX_NESTING_DEPTH` = 256 depth bound. The snake->camel rewrite is O(total nodes) and runs ahead of all Zod validation, so a partner payload wide enough - within the frame and decode-layer caps - would burn multiple seconds before any count gate fires. For a wide object placed under an unknown top-level key the non-strict schema then silently strips it, so the parse succeeds after the burn rather than rejecting (worse than a rejection, since nothing is reported). A single node counter threaded across the whole walk - `MAX_NODE_COUNT` = 262144, one object member or one array element per node - rejects such a payload with a clean, terminal `NodeCountExceededError` (a `UsageError` like the depth bound, fixed message with no input bytes) before the rewrite completes. An over-wide array is refused by its O(1) length before `.map`, and an over-wide object by a streaming own-key count before `Object.entries` materializes it, so neither the burn nor the materialization runs. A running total, not a per-container cap, is required to catch both a single wide object (path a) and width spread across many small ones - the count-gated arrays of objects, each walked in full before its `boundedArray` refine could fire (path b). 262144 (2^18) sits far above any realistic operator `ExchangeSpec` - low tens of thousands of nodes at most (the single widest object is a `transform.params` record at `MAX_PARAMS_ENTRIES` = 256, collections cap at 256 to 4096 entries) - and far below the burn, which reaches a multi-second cost only past ~1M nodes (measured). Rejecting at this budget caps the wasted walk well under a second. Like the rest of this family it is defense-in-depth, not a semantic limit: the per-collection caps do compose to a schema-valid maximum above the budget (256 `linkageFields`, each with a 4096-entry `exclude`, is ~1M nodes), so a pathological-but-schema-valid config could trip it - but no real operator config comes within an order of magnitude. It composes with the per-record `params` skip without double-counting - a skipped subtree (an opaque value, or an over-count width-bounded value) is not recursed into and so never counts toward the budget. A massively over-count partner collection is therefore refused by this budget before Zod (the boundedArray count gate still rejects a moderate over-count that stays under the budget), and the throw is caught by the same `parseLinkageTerms` parse-error path that already handles the depth bound.

The `MAX_NESTING_DEPTH` = 256 depth bound the `camelizeKeys` pre-pass applies is enforced on all three linkage-terms parse paths, the invitation decode path included. `decodeInvitation` normalizes `transform.params` to camelCase through the bounded `camelizeKeys` chokepoint (the camelize pre-pass in `packages/core/src/config/invitation.ts`) as it validates the token against `InvitationTokenSchema` -- folding before the per-step length and dialect screens so they run on the normalized form. A partner-controlled one-key-per-level `params` - bounded otherwise only by the 64 KiB `MAX_ENCODED_INVITATION_LENGTH` cap and `parseBoundedJson`'s `MAX_JSON_NESTING_DEPTH` = 4096 decode ceiling, both above the ~2000-level native call-stack limit - is rejected at decode with a terminal `NestingDepthExceededError` (a `UsageError`, CLI exit 64 / a clean web decode error via `describeDecodeError`) before it reaches any downstream consumer. The normalization MUST use the bounded `camelizeKeys` walk for exactly this reason: a raw snake->camel recursion over the schema-opaque (`z.unknown()`, decode-unbounded) `params` value would itself overflow the stack. Because the field is normalized at the decode chokepoint, every consumer of a decoded invitation's terms - the canonical comparison, the reconcile, the agreed-terms hash, the standardization runtime - inherits both the camelCase form and this depth bound, rather than each having to re-impose it. The CLI's invitation-vs-config reconcile (`apps/cli/src/config.ts`, `withoutUndefinedDeep` reached via `diffLinkageTerms`) nonetheless threads its own depth counter and rejects at the same 256 as a safety check. `withoutUndefinedDeep` is an independent recursive walk that must not couple its safety to its callers having pre-bounded the input, and an unguarded deep value would otherwise overflow it with a `RangeError` the CLI command boundary maps to a generic internal-error exit (69) - catchable and non-fatal, but ungraceful, and distinct from the uncatchable `JSON.parse` aborts the decode-layer bound below guards. With decode and config load both bounding their own side, that safety check is not normally reachable; it stays as defense-in-depth. The bound fires far below the overflow and far above any real config (the deepest schema path is under a dozen levels, and `params` legitimately holds shallow scalars).

A further bound sits *upstream* of the entire Zod/`camelizeKeys` family above, at the JSON-decode layer, and is enforced as a single chokepoint. Every parse of untrusted JSON in the core routes through `parseBoundedJson` (`packages/core/src/utils/boundedJson.ts`), which checks the body's structure against a per-object key ceiling, a per-array element ceiling, and a nesting-depth ceiling (`MAX_JSON_OBJECT_KEYS` = 65536, `MAX_JSON_ARRAY_ELEMENTS` = 16777216, `MAX_JSON_NESTING_DEPTH` = 4096) *before* handing it to `JSON.parse`. A lint rule forbids a raw `JSON.parse` elsewhere in the package, so a new parse site cannot silently reopen the hole. Unlike the rest of the family this is not a CPU-burn or `RangeError` guard. A single object made wide enough, or a single array made long enough, drives `JSON.parse` into a process-terminating internal limit of the JSON engine - a per-object property ceiling, or the array backing-store length limit - that is *not* a thrown exception, so a `try`/`catch` around the parse cannot intercept it. The only defense is to refuse the body before the parse can reach either limit, not to catch its failure. The check is a single O(n) pass over the raw UTF-8 bytes (or the already-decoded string a transport hands over) - the JSON structural markers are unambiguous ASCII in either representation (a single byte in UTF-8, a single non-surrogate code unit in UTF-16). It counts each object's members (by colon) and each array's elements (by comma) against its own ceiling, with early exit. On the byte path an over-budget body is refused without even allocating the decoded string.

This chokepoint covers both threat-model adversaries, not only the counterparty. The post-handshake `TYPE_JSON` frame is decoded through it after AEAD decryption (the *counterparty*'s reach); but the file-sync transport's own reads - the peer-hello control file and every message body - are JSON-parsed off the raw inbound file *before* decryption, so they are shaped by the hostile *server admin*, and the invitation token is parsed from attacker-influenced bytes a victim opens. All route through the same chokepoint, so a wide-object or long-array body from any source is refused rather than crashing the process. Each caller maps the refusal to its own terminal error - a `ConnectionError("security")` on the wire, a `UsageError` on a transport file, a rejected invitation - with no attacker bytes.

The unit is per *container*, not per byte or per total count, because that is what fits the data *at this layer*: a decoded-byte or total-count budget here would have to sit below the largest legitimate message and so would reject it, yet no single legitimate container is pathological. (The `camelizeKeys` total-node budget above *can* be a running total precisely because it sees only the small parsed-config family - linkage terms and the like - never these large set frames, which are parsed by other schemas the pre-pass does not touch.) The widest legitimate object is the `transform.params` record at `MAX_PARAMS_ENTRIES` = 256; the longest legitimate array is an association-index, payload-row, or mapped-pair list, one entry per matched record and so transport-bounded to a few million (a larger set cannot reach this layer - the binary set frame itself exceeds `MAX_FRAME_SIZE_BYTES` first). So `MAX_JSON_OBJECT_KEYS` sits far above any real object and far below the per-object engine limit, and `MAX_JSON_ARRAY_ELEMENTS` sits above any real array and well below the array-length limit - each fires only on a pathological container and never pre-empts a schema-layer rejection or a legitimate large message. The depth ceiling sits far above any real nesting (the parsed-config ceiling is `camelizeKeys`' `MAX_NESTING_DEPTH` = 256) and exists chiefly to bound the scan's own per-container stack against a degenerate all-`{`/`[` body, which would otherwise exhaust memory in the pre-pass. This bound composes with rather than overlaps the post-parse `camelizeKeys` bounds. It caps any single container's width before the walker ever sees it, while the walker's own `MAX_NODE_COUNT` budget (above) caps the total it then rewrites - a width the per-container ceiling does not bound (a body within every per-container limit can still hold far more nodes in aggregate than the walker should rewrite).

The severity is defense-in-depth, not a live vulnerability: the counterparty is authenticated and can already abort the exchange trivially, and most of these sites already caught the `RangeError` harmlessly - a `receiveParsed` / `parseOrProtocolError` wrap reports a `ConnectionError("protocol")`, and the linkage-terms parse-error catch aborts cleanly. So the bound turns an ungraceful internal exception and a one-shot CPU burn into a clean, bounded rejection rather than closing a memory or correctness break. The decode-layer chokepoint is the sharper of the set - it forestalls an uncatchable process crash, an availability loss the others do not reach, rather than a recoverable burn - but rests on the same reasoning. The crash kills only a session its instigator already controls - the counterparty it is party to, or the transport a hostile server admin already mediates and can disrupt at will - so it too is defense-in-depth against a self-limited adversary, not a live vulnerability. The set of accepted messages is unchanged: each single-issue predicate mirrors the element schema it replaces, and each count gate's `.pipe` re-runs the original element schema, so a legitimate exchange parses to a byte-identical structure (the cross-party receipt hash is preserved).

## CSV-read single-line byte ceiling

`CSV_LINE_BYTE_CEILING` (8 MiB, `packages/core/src/file.ts`) is the one bound in this application-layer parsed-input family with no adversary. Every bound above answers a specific attacker -- the authenticated counterparty or a hostile server admin -- and the section's framing turns on which one. This bound answers none of them: it guards the operator's own local CSV, an input no partner or transport supplies, so it is operator-local input robustness, low severity and non-gating, not a partner- or transport-reachable bound and not a threat-model control like the partner-parsed bounds it sits among. It is recorded here only so a parse-surface audit finds it beside the input bounds it belongs with rather than as the lone undocumented one; read it as defense-in-depth on the operator's own file, not as a control any threat-model adversary reaches. The two streamed CSV reads share the one constant: `loadCSVColumnSample` (the `init` column- and date-format inference read) and `loadCSVFile` (the whole-row invite/accept/exchange read). PapaParse must buffer one whole logical line -- a data row, or the entire header -- before it can yield a chunk, so an input whose first terminator is far from the start (a no-newline file, one enormous field, or a multi-megabyte header) would drive memory, and CPU quadratically via repeated re-splitting of that partial line, with the span. The ceiling bounds the bytes pulled between row terminators so those shapes fail fast with a clear, operator-readable error. **8 MiB** sits above any realistic operator CSV's single line -- even a pathologically wide file of tens of thousands of columns is a header of low single-digit MiB and a data row far smaller -- and below the hundred-MiB-plus spans that drove the gigabyte-scale memory growth it guards against.

The enforcement mechanics stay in the code and are not reproduced here: the JSDoc on `loadCSVFile`, `guardStreamLineByteCeiling`, and `assertLeadingLineWithinByteCeiling` (all `packages/core/src/file.ts`) describes the split. The Node stream's `data`-event byte counter (`guardStreamLineByteCeiling`) bounds every line by destroying the source past the ceiling; the browser-`File` pre-read (`assertLeadingLineWithinByteCeiling`) bounds only the leading line before parsing because a `File` exposes no `data` events to scan.

What the spec states, because it is classification rather than mechanics, is the one shape this bound does not cover. Both enforcement points scan raw bytes and treat any LF or CR (`0x0a`/`0x0d`) as a line terminator -- including a byte inside an RFC 4180 quoted field. That is the deliberate fail-safe direction: ignoring quoting can only let a pathological line slip past (a false negative), never wrongly reject a valid file (the false positive a quoting-aware scan could produce on a legitimate quoted newline). The cost is one unbounded shape -- a single logical CSV row that is one enormous quoted field containing embedded newlines: the scan resets its run at each embedded newline and never trips, while PapaParse buffers that whole quoted field as one logical row, memory proportional to the field with quadratic re-split CPU. That shape is bounded not by this ceiling but by the input being operator-local (the CLI sets no file-size cap) or, on the web, by the web app's `MAX_CSV_FILE_BYTES` intake cap; it is not a regression, since the read was unbounded for that shape before this ceiling existed too. Being operator-local and non-gating rather than a partner- or transport-reachable vulnerability, it is recorded openly here, not withheld. The caveat also lives in the code (the `guardStreamLineByteCeiling` JSDoc and an inline comment in `assertLeadingLineWithinByteCeiling`); this note exists so spec and code agree on what the bound does not cover. Unlike the partner-parsed bounds in this family, the ceiling is not net-new security behavior gated on the explicit security review -- it is operator-local robustness, so it has no such gate.

## Web linkage-terms import bounds

The web editor's expert tier lets an operator paste a JSON or YAML linkage-terms document to load the editor (`importLinkageTerms` in `apps/web/src/psi/linkageTermsIO.ts`). That document is untrusted free text - an operator could paste a credential into it by mistake, and a partner-supplied terms file could be hostile - so it has the same parsed-input bounds as the core wire paths, plus two import-specific ones. The raw parse routes through the shared secret-redacting chokepoint (`parseSensitiveJson` / `parseSensitiveYaml` in `packages/core/src/sensitiveFile.ts`), never a raw parser, so a parse error reports a path-only label and never echoes the document's bytes (the leak channels are enumerated in that module's header). The JSON path runs through `parseBoundedJson`, so the structural ceilings above (`MAX_JSON_OBJECT_KEYS` / `MAX_JSON_ARRAY_ELEMENTS` / `MAX_JSON_NESTING_DEPTH`) apply. The parsed value is validated only by `safeParseLinkageTerms` - the same schema, with the same `camelizeKeys` depth/node bounds, that the Generate gate runs - so an import cannot smuggle a value past the schema into a minted invitation.

The two import-specific bounds:

- A pre-parse length cap, `MAX_IMPORT_CHARS` = 1000000 (UTF-16 code units, in `linkageTermsIO.ts`), refuses an oversized paste before either parser runs, so a pathological document cannot drive the parser ahead of the schema's own structural bounds. It sits far above any real linkage-terms document - the invitation token path itself caps at 64 KiB, and a GUI-exported document with every key and transform is well under this - and is sized for an operator workstation, not a constrained tab; tunable.
- The YAML parser's alias-expansion bound, `maxAliasCount` = 100, is pinned explicitly in the chokepoint's parse options (`SAFE_YAML_OPTIONS` in `packages/core/src/sensitiveFile.ts`) rather than left to the `yaml` library default. 100 is the library's current default, so pinning is behavior-preserving; pinning it makes the alias-bomb (billion-laughs) bound an enforced constant here rather than an implicit reliance on a default a future `yaml` release could raise. It would only need revisiting if a legitimate document required more than 100 alias references - none does.

## Signaling-server inbound frame bound

The bound above lives in `@psilink/core` and covers the AEAD application channel and the file-sync transport - a self-limited adversary (the authenticated counterparty, or a hostile server admin). The web app's bundled PeerJS signaling server is a separate surface with a broader adversary: it runs in production under `/api/` to broker the WebRTC rendezvous, and its only authentication gate is the well-known default key `peerjs` (the id and token are free strings), so its inbound parse is reachable by ANY unauthenticated internet client. Its `socket.on("message")` handler in `packages/peerjs-broker/src/contrib/services/webSocketServer/index.ts` decodes each frame as JSON, the same uncatchable-V8-abort class as the core bound above - a single wide-enough object or long-enough array drives `JSON.parse` into a process-terminating internal engine limit that no `try`/`catch` can intercept. Because the broker process is shared by every peer, that abort is an availability loss for all of them, not one self-controlled session; and even short of the crash ceiling, a single oversized frame is independently a memory pin.

The bound has two halves. The byte half sits at the idiomatic `ws` layer, ahead of the parse: the `ws` `Server` is constructed with an explicit `maxPayload` (`MAX_SIGNALING_PAYLOAD_BYTES` = 262144, i.e. 256 KiB) rather than the 100 MiB `ws` default. `ws` enforces it in the receiver as each frame's length header is read, refusing an over-cap frame with a 1009 close (`WS_ERR_UNSUPPORTED_MESSAGE_LENGTH`) before the payload is buffered and before the message handler parses it - the error surfaces as a handled `error` event the server already routes, not a crash. The cap sits far above any legitimate signaling frame: this server brokers only small control messages - the PeerJS OPEN / OFFER / ANSWER / CANDIDATE / HEARTBEAT family, SDP and ICE that are KB-scale - while the PSI payload itself flows peer-to-peer over the WebRTC data channel and never crosses this socket. It sits far below both the 100 MiB default and the ~109 MB a single 2^23-key object needs to reach the per-object ceiling, so it closes the single-frame crash outright rather than only shrinking the window, and caps each inbound frame against the single-frame memory pin. Like the file-sync frame-size cap above it is a fixed constant, not a configurable option: a configurable bound risks an operator raising it high enough to reintroduce the DoS. It would only need revisiting if the signaling protocol began carrying a legitimately large payload through this socket - it does not, and a redesign that routed bulk data through the broker rather than the data channel would be the change to re-evaluate against. As net-new security behavior on an internet-facing surface, this control is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

The structural half is core's chokepoint: the handler decodes each frame through `parseBoundedJson`, so the per-object key, per-array element and nesting-depth ceilings of the section above bound a signaling frame as they bound a core wire message. Only those ceilings do. The handler passes an already-decoded string (`data.toString()`), which takes the chokepoint's string arm, so its byte-arm properties do not apply here: there is no UTF-8-fatal decode, and the structural scan runs on the decoded string rather than ahead of any decode. A frame whose bytes are not valid UTF-8 is decoded with replacement characters and is then accepted or refused on its structure and syntax, not on its encoding.

Under the 256 KiB byte cap the two halves overlap only in part:

- `MAX_JSON_OBJECT_KEYS` = 65536 is out of reach: the smallest body exceeding it is 320 KiB (65537 members of `"":1,`).
- `MAX_JSON_ARRAY_ELEMENTS` = 2^24 is out of reach: the smallest body exceeding it is about 32 MiB (16777218 elements of `1,`, that is 2^24 + 2 - the scan counts an array's elements by its separating commas, so 2^24 + 1 elements do not reach it).
- `MAX_JSON_NESTING_DEPTH` = 4096 is exceeded in 8194 bytes (4097 nested `[` and their closers), so the depth ceiling is what the structural half adds over the byte cap today.

The structural half is where the bound belongs regardless of that arithmetic: it holds whatever the byte cap is later set to, and it puts the broker inside the same ESLint ban on a raw `JSON.parse` that `packages/core/src` and `apps/web/src` sit inside (`eslint.config.mjs`), so a parse added to this server later is bounded by default rather than by being noticed. Two vendored paths sit outside that ban, exempted by the repo-wide lint ignores so their history against upstream stays readable: `packages/peerjs-broker/src/contrib/messageHandler/` and `packages/peerjs-broker/src/contrib/models/message.ts`. They are pinned instead by a check that scans them for a parse call in any shape the ban refuses and fails if one appears (`scripts/eslint-broker-parse-bans.test.mjs`). A structural refusal throws `JsonStructureBoundError`, whose message holds no input bytes, and the handler routes it to the `client-frame` diagnostic with every other parse failure. The relay's reconnect queue reconstitutes a held payload through the same chokepoint (`packages/peerjs-broker/src/contrib/models/messageQueue.ts`), so the delivery leg is bounded as well as the receive leg.

## Transform-regex linear-time dialect

A second control against the same mutually-distrusting counterparty bounds the *complexity*, not the count, of one partner-supplied field: the regular-expression pattern in a linkage-key element transform. The four regex step functions (`replace_regex`, `extract_regex`, `filter_regex`, `split_on`) compile their pattern and run it per row over the acceptor's full dataset (`packages/core/src/standardization.ts`); `parse_date` likewise *expands* its partner-controlled `inputFormat` into a per-row regex whose adjacent `(\d{1,2})` groups (one per `MM`/`DD` token) are a catastrophic-backtracking construct - a ~48-character format reaches a hang. On the JavaScript `RegExp` engine a catastrophic-backtracking (ReDoS) pattern would hang the single, non-interruptible thread. The pattern cannot be rewritten - PSI requires byte-identical keys and the terms are canonically hashed into the exchange-agreement receipt, so a unilateral rewrite both breaks matching and is reported as a terms mismatch.

The control is by construction: these patterns execute under a **linear-time regex engine** (re2js, an RE2-semantics Thompson NFA / lazy DFA - `packages/core/src/utils/linearRegex.ts`) instead of `new RegExp`. Matching is linear in the input length with no backtracking, so the catastrophic-backtracking blow-up is *impossible*, not merely screened for. This includes `parse_date`'s expanded regex, which moves onto the same engine, so its adjacent-group construct is bounded by construction rather than by a separate analysis. The engine is pure JavaScript, so the same build runs in the CLI (Node) and the web (browser): both parties and both build targets derive byte-identical keys, with no second engine build whose semantics could diverge on an adversarial pattern. The permitted pattern syntax - the **dialect** - is pinned normatively in [PROTOCOL.md](PROTOCOL.md#transform-regular-expression-dialect); both parties MUST evaluate patterns under it.

What remains at validation is a dialect-conformance gate: a refine on `LinkageTermsSchema` (`packages/core/src/config/transformRegexDialect.ts`), so it covers every path that parses partner terms at once - the initiator/joiner `parseLinkageTerms`, the invitation-token decode (`InvitationTokenSchema`), and `ExchangeSpecSchema`. The refine walks every raw-pattern step (the function-to-pattern-param map `REGEX_STEP_PATTERN_PARAM`, `split_on` keying on `delimiter` rather than `pattern`, kept in parity with the `tier: "regex"` function descriptors by a test). It coerces the param to a string exactly as the engine would (`coerceToPatternString`, so a non-string JSON value that stringifies to a pattern is screened as the literal it executes as). It rejects - fail closed, before any row runs - a pattern the engine cannot compile: a backreference, a lookaround, or an unsupported escape, exactly the features RE2 drops. `parse_date` is not screened here: it is not a raw-pattern step and its library-generated regex is always in-dialect; its safety is the engine, not the gate. There is **no fallback to `new RegExp`** - a pattern outside the dialect is refused, never silently re-run on the backtracking engine, which would reopen the hole. A total wall-clock budget across one validation (`REGEX_DIALECT_TOTAL_BUDGET_MS`, 2000 ms) bounds the gate's own cost so a terms set packed with patterns - the per-collection count caps above still permit a large product - cannot turn validation itself into a denial of service; on exhaustion the remaining patterns reject closed. A separate per-step length cap on the raw pattern (`MAX_TRANSFORM_PATTERN_LENGTH`, 1000) caps the source-parse and one-time compile cost (`applyElementTransform` compiles each step once per distinct transform array, memoized, rather than per row). These constants live beside the code in `transformRegexDialect.ts` and `linkageTermsSchema.ts`.

The bundled default standardization patterns - including the email filter `^[^\s@]+@[^\s@]+\.[^\s@]+$` - are all in-dialect and need no allowlist; a checked-in cross-build vector file (`packages/core/test/vectors/transform-regex-vectors.json`) pins each default pattern's output, on the inputs it covers, as byte-identical to the previous `new RegExp` engine, and asserts the Node and browser builds agree. The few code points where RE2 and JavaScript regex semantics diverge - `\s` is ASCII-only under RE2 but Unicode-broad in JavaScript, `.` excludes only `\n` under RE2 but also `\r` and Unicode line separators in JavaScript, and `.` spans a code point rather than a UTF-16 code unit - are documented in [PROTOCOL.md](PROTOCOL.md#transform-regular-expression-dialect) and are outside that vector domain. They are not cross-party divergences (both parties run the same engine) and, in the bundled defaults, the email filter is preceded by `remove_non_ascii`, so no such code point reaches it.

The severity addressed is a denial of service bounded to the availability of the acceptor's own session - its browser tab or CLI process, on the acceptor's own (typically isolated, periodically-run) hardware - with no data disclosure, no code execution, and no effect on the counterparty or the privacy guarantee. Standardization is local key-building, before and independent of the PSI rounds, so a hang neither leaks a non-intersection member nor reaches the peer, and the worst outcome is that the run produces no result and is re-run. The realistic trigger is a mistake - a catastrophic-backtracking pattern an operator reuses from a JavaScript engine or mistakenly authors, which a human reviewing the agreed terms cannot reliably vet for cost. The linear-time engine prevents that class by construction, and is the critical control here; because the linkage terms are agreed once and reused, with any later modification raised for manual review, it also covers the residual hostile-or-tampered pattern (an attacker would have to subvert the one-time terms agreement for a non-escalating local hang). An in-dialect-but-expensive pattern crafted on purpose remains possible but is bounded - its source length is capped (`MAX_TRANSFORM_PATTERN_LENGTH`, applied to the coerced source the factory compiles), RE2 caps any single and nested repeat count, and matching stays linear in the input - and non-escalating, so it is accepted under this threat model rather than further bounded with complexity caps. No best-effort static screen stands beside the engine, and none should be added: a heuristic analyzer can only estimate the class the linear-time engine eliminates outright, at the cost of an allowlist and a dependency of its own. As net-new security behavior that adds a security-relevant dependency (re2js) and pins a wire-level dialect, this control is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

## Name-constraint character class

One more partner-controlled regular expression reaches the local party outside the transform pipeline: a name field's `allowedCharacters` constraint (`NameConstraints`, `packages/core/src/config/linkageTermsSchema.ts`), a regex character class. It differs from the transform patterns above in two ways that lower its stakes but not its ReDoS exposure: it is **not** key-building and **not** hashed into the agreement receipt, so it has no cross-party determinism requirement. The value-level check that evaluates it is a **local advisory that warns and does not block** - the web cleaning editor flags a cleaned value whose characters fall outside the class, before any exchange round and with no effect on what is sent. It is still partner-authored (it arrives in the invitation token), so a crafted class is the same ReDoS hazard and takes the same by-construction control. The check compiles `^[allowedCharacters]$` under the linear-time engine (`compileLinearRegex`) and tests one code point at a time, each as a full (whole-input) match rather than an unanchored find, after escaping a leading `^` to a literal (so a leading caret is the allow-list the operator wrote, not a class negation that would invert the advisory). A class that breaks out of the brackets therefore can neither backtrack catastrophically nor suppress the warning by matching a multi-character span or by an alternation branch that matches only a zero-width or leading span. What this does **not** defeat is a class that genuinely admits the code point - a character-class shorthand (`\w`, `\p{L}`, `[:alpha:]`) or an alternation breakout whose branch matches a single code point (`a]|.|[b`, effectively allow-all). The effective set diverges from a plain reading, but neutralizing it would take a full character-class parser and would false-flag a legitimately permissive class (`\p{L}` is the natural constraint for international names, indistinguishable at the engine level from a smuggle). Because the check warns and does not block, this is an accepted, documented limit - a suppressed advisory badge, never a data-filtering, match-correctness, or ReDoS effect. `NameConstraintsSchema` validates the class under that **same engine** at parse time - not `new RegExp` - on every path that decodes partner terms, so a class it accepts is guaranteed to compile at check time and the advisory cannot fail open on a native-versus-RE2 dialect gap; the degenerate empty class, which the engine cannot compile, is rejected there with the existing character-class message. `MAX_NAME_LENGTH` (256) is a critical pre-compile length gate on that validation, the compile-cost bound the sibling `MAX_TRANSFORM_PATTERN_LENGTH` is for the transform patterns above. Because Zod does not short-circuit chained checks, the refine that compiles `[allowedCharacters]` under re2js runs even on an over-length value, and re2js compile cost is super-linear in source length, so the refine tests the length first and defers an over-length class to the `.max()` rejection rather than ever compiling it. The value-level check is web-local (core's `validateStandardizationAgainstTerms` checks names only); promoting it to core for CLI reuse must keep it on this engine. Because this path builds no keys and feeds no receipt, it needs no cross-build vector and is exempt from the dialect's byte-identical requirement - here the linear-time engine is purely the ReDoS control, not a determinism guarantee. The display complement to that accepted limit: because the effective set can diverge from a plain reading, the operator-facing consent summary (`describeConstraints`, `packages/core/src/consent/invitationSummary.ts`) does **not** paraphrase the class as a vetted "characters limited to X" allow-list. It labels it as the partner-supplied, unverified regular expression it is (naming the trust boundary, not just the regex syntax family) and shows the raw (sanitized) class, so a crafted class - a leading-`^` negation, a `\p{L}`/`[:alpha:]` shorthand, or a bracket breakout - is not *presented* to the operator as a plain-language guarantee. A non-regex-literate operator can still misread a crafted class, but the copy asserts no promise the value cannot back. One bounded residual remains: the class body is itself partner-controlled display text rendered as a suffix, so a value that is a valid character class of printable letters and spaces (e.g. `A-Za-z (checked by our compliance team`) renders as trailing prose after the label - the accurate "not verified by psilink" note can be followed by a contradicting partner sentence. It is confined to this advisory display surface (the note always precedes the value, and the value is sanitized and length-capped, so it can neither displace the note nor break the constraint list), an accepted residual rather than a hole; a rendering that binds the raw class as a visually distinct, bounded element would close it. Both acceptance surfaces render the class from that one summary - the web consent screen in its own bounded element, the CLI accept prompt on its own line after the fixed label - so the residual is the same one on each, not a second shape. The CLI's separate advisory still prints a fixed "disallowed characters" label with a count, not the pattern.

## Unbounded transform-parameter rejection

A third control against the same mutually-distrusting counterparty bounds the *magnitude* of the partner-supplied transform-param values whose size drives unbounded per-row work - the `transform.params` values typed `z.unknown()` above, whose entry count the count gates bound but whose content they do not reach into. It has four members: a per-function cap on each of the two params whose magnitude drives work in a shape a string length does not describe. Beneath them is a uniform content bound on every string-valued param, and beside all three is a ceiling on the value a row produces, since a bound on what the partner may write is not a bound on what a row derives from it. The first is the `length` of a `pad_left` linkage-key element transform. `pad_left` runs per row over the acceptor's full dataset (`packages/core/src/standardization.ts`, `applyElementTransform` driven by `buildKeyStrings`) and allocates `String.prototype.padStart(length, char)` for each row, so an unbounded `length` - a crafted `1e9` - makes every row allocate a ~1 GB string and exhausts memory, hanging or crashing the acceptor (the web acceptor's browser tab, the CLI acceptor's process). It is the memory-allocation analogue of the ReDoS regex above: the same fail-open denial of service reachable from the authenticated counterparty, in the same partner-influenced-terms-executed-at-the-local-party model, driven by an unbounded numeric param rather than a pattern. The value cannot be rewritten - PSI requires byte-identical keys and the terms are canonically hashed into the exchange-agreement receipt, so a unilateral clamp both breaks matching and is reported as a terms mismatch - so the control rejects an out-of-range value at validation, before any row runs.

Enforcement is a per-step refine on `TransformStepSchema` within `LinkageTermsSchema` (`packages/core/src/config/linkageTermsSchema.ts`), so - like the dialect-conformance refine - it covers every path that parses partner terms at once: `parseLinkageTerms`, the invitation-token decode (`InvitationTokenSchema`), and `ExchangeSpecSchema`. The cap must live on this wire schema rather than on the editor-facing `STANDARDIZATION_FUNCTION_DESCRIPTORS`, which an attacker-authored token never passes through: the partner-supplied `transform.params` values are typed `z.unknown()`, with no per-function shape at all - their entry count (above) and their string content (below) are what the wire schema gates. A `pad_left` step whose `length` is a positive integer above `MAX_PAD_LEFT_LENGTH` (**256** - far above any legitimate left-pad, which is tens of characters for a zero-padded SSN or phone, and far below an allocation that matters) is rejected. Only a positive-integer `length` ever reaches `padStart` - `padLeftFactory` throws on a non-number, non-integer, or non-positive value before allocating, and that runtime check remains as the safety check for the operator-local `standardization` path, which never reaches this schema - so bounding positive integers above the ceiling closes the whole allocation vector. A malformed value is left to that runtime check, whose clean-abort path is unchanged. A legitimate `pad_left` parses and runs unchanged, preserving the cross-party receipt hash.

The second is `parse_date`'s `inputFormat` and `outputFormat`. `parse_date` builds a regex from `inputFormat` (compiled once per distinct transform array, memoized like the other steps) and assembles its output from `outputFormat` once per matched row. The size of those values still drives cost: a long `inputFormat` compiles a larger regex, and a long `outputFormat` allocates a larger output per matched row, so a per-step refine on `TransformStepSchema` caps each format string at `MAX_DATE_FORMAT_LENGTH` (**256** - far above any real date layout like `MM/DD/YYYY` or `YYYY-MM-DD`, yet small enough that the compile and per-row output stay cheap). Only a string value drives this cost; the factory treats a non-string as an empty/absent format, so a non-string is left to it unchanged, as a malformed `pad_left` length is. The format's shape - the adjacent `(\d{1,2})` groups its `MM`/`DD` tokens expand into, which catastrophically backtrack on `new RegExp` at a length well under this cap - is not a separate control: `parse_date` compiles its regex under the linear-time engine (see [Transform-regex linear-time dialect](#transform-regex-linear-time-dialect)), which bounds the shape by construction. `parse_date` is not screened by the dialect gate (its library-generated regex is always in-dialect); its safety is the linear-time engine plus the 256-character format cap, which keeps the generated regex small and low-ambiguity by construction (only bounded `\d` quantifiers, never an unbounded quantifier over a sub-expression), so its per-row cost stays sub-millisecond on realistic input. This length cap is therefore a pure work-size bound, not a safety check against a backtracking blow-up.

The third is uniform rather than per-function: every string-valued transform param, whatever function and param name it sits under, is capped at `MAX_TRANSFORM_PARAM_LENGTH` (**1000**), the same threshold as the raw pattern beside it. So no string param in a `params` record is more generous than the pattern it accompanies, and far above any legitimate authoring, which runs to a few characters or a few hundred for a replacement literal, a `coalesce` default, or a `null_if` value. A string param's length is per-row work whichever function reads it, because it sizes what the rest of the element pipeline holds: `replace_regex`'s `replacement` is substituted into the operator's own cell at every match, and every later step of that element takes the result, which the `generateFuzzyComparisons` expansion replicates across the row's candidates. Enforcement is the `params` record's value stage rather than a per-step refine, so it holds for a param no per-function refine covers and for a function this build does not implement - a per-amplifier bound would be dodged by routing content through a param no measurement covered. The offending step and param are located by the issue path (`linkageKeys[i].elements[j].transform[k].params.<name>`, escaped segment by segment by `describeDecodeError`) rather than echoed into the message, as with the referential-integrity and dialect refusals. An over-bound param is refused, never truncated: a truncated param silently changes the derived keys and so breaks matching, the same reason the `pad_left` length is refused rather than clamped. The bound reaches a string value of the record, not a string nested inside an array- or object-valued param, because nothing derives a per-row value from a nested string. `null_if` compares its `values` entries against the cell and emits the cell or `null`, every other factory reading a string param falls back to its default for a non-string, and an array a regex factory would render into a compile source is bounded on the coerced source by `MAX_TRANSFORM_PATTERN_LENGTH` above. What the bound removes is the partner's ability to size a row's value independently of the operator's data: a crafted megabyte constant over a ten-character cell is refused at validation rather than assembled per row.

What that bound does not deliver by itself is a ceiling on the transformed value, which is the fourth member's job. It caps a param's content length, not the size of what a row derives from it, and three mechanisms amplify past the naive "cell plus one capped replacement per position" figure a 1000-character replacement suggests. First, a replacement is a substitution template rather than a literal: the `` $` `` and `$'` sequences re-insert the match's leading and trailing context (`packages/core/src/utils/linearRegex.ts`, `CompiledLinearRegex.replaceAll`), and an in-dialect pattern matching the empty string matches between every character, so the transformed value grows quadratically in the operator's own cell. A replacement of `$'` repeated 500 times is exactly 1000 characters and parses; against `a*` it takes a 10-character cell to 27,510 characters, a 200-character cell to 10,050,200, and a 500-character cell to 62,625,500 (~125 MB UTF-16, ~125x the naive figure). `$&` re-inserts only the match itself and stays under the naive figure; `` $` `` and `$'` are the amplifying pair. Second, steps compose: an element has up to `MAX_TRANSFORM_STEPS` steps and each is fed the previous step's output, so a two-step element with both params inside the bound reaches 3,630,120 characters from that same 10-character cell. Third, `replaceRegexFactory` NFC-normalizes the replacement before substituting it, and normalization can lengthen it - 1000 `U+0344` code units normalize to 2000, which takes the 10-character cell to 22,010 with no substitution sequence involved at all. Each of those three shapes is pinned as bounded in `standardization.test.ts`, with the schema half - an amplifying replacement parsing at the content bound, its sequences keeping their wire meaning - in `linkageTermsSchema.test.ts`.

The ceiling that bounds them is `MAX_TRANSFORMED_VALUE_LENGTH` (**4096** UTF-16 code units - the unit the engine allocates in, and far above any legitimate key element, which is a name, a date, an identifier, or an address: tens of characters, a few hundred at the outside). It is one magnitude invariant enforced at three points on the partner-authored path (`packages/core/src/standardization.ts`), which is the element transform the agreed terms state and not the operator's own local standardization pipeline, whose config and data are both the operator's. Inside `applyElementTransform` it is checked on the value the element reads - ahead of the no-steps early return, which is what bounds a zero-transform element with a huge raw cell - and on every step's output, which is what keeps every step's input bounded so a composed pipeline cannot compound past it. In `buildKeyStrings` it is checked again on the row's projected assembled key-string length, `MAX_ASSEMBLED_KEY_LENGTH_PER_ROW` (**4,194,304** - `MAX_KEY_STRINGS_PER_ROW` times the per-value ceiling, so a row may hold the equivalent of one ceiling-sized element replicated across the full width the count cap allows). Every combination of the cross-product concatenates one candidate per element, so the assembled total is computed exactly from the candidate counts and lengths already in hand, before `cartesianProduct` materializes anything - the same projection discipline the count limb uses, and the limb that also bounds the fuzzy expansion's replicated bytes recorded below, which get no byte cap of their own.

The third point is that same `MAX_ASSEMBLED_KEY_LENGTH_PER_ROW` total, measured as the candidates accumulate rather than on the finished projection - because a projection is reachable only once every candidate exists. A step runs element-wise over an expanded candidate set (`applyStep`), so it allocates one output per candidate and the per-value ceiling reads the finished set: a transient N times that ceiling, with N unbounded until assembly. A running total of the characters each candidate retains - a duplicate the set collapses retains none, because a candidate the set does not keep is included in no key string - is therefore kept at both places candidates accumulate, a step's output set in `applyStep` and the row's candidates in `buildKeyStrings`. Once a total crosses, the row is settled before the next candidate is produced: dropped where a declared fan-out producer accounts for the crossing, and the exchange refused otherwise (the fate rule below).

Charging what is retained is what keeps the bound on the row's live bytes rather than on the work that produced them. A partner-authored transform that collapses a multi-value cell onto one candidate (a `replace_regex` whose pattern matches everything, over a cell of 2,200 values) makes the element retain one 2,000-character candidate whatever the cell's width, and a total charging each realized candidate would refuse at 4,400,000 characters a row whose key string is 2,008. The `buildKeyStrings` total is the row's, held across the key's elements rather than restarted at each. The elements' candidate sets are all live together when the cross-product is projected, so a per-element total would bound the row at the cap times the element count (`MAX_KEY_ELEMENTS`, 256) - measured at 42 elements binding one 1,000-value cell, 172,032,000 characters retained where the cap is 4,194,304, and 1,048,576,000 at the full 256. What is left live when a total crosses is three charges, each held to `MAX_ASSEMBLED_KEY_LENGTH_PER_ROW` by a check of its own. The three are the row's retained candidates across the elements already built and the earlier values of the element in progress; the set the crossing step is reading, which is the previous step's output under that step's own charge (or, for an element's first step, its incoming value under the per-value ceiling); and the set that step is filling. The bound on a row's live retained bytes is therefore three times `MAX_ASSEMBLED_KEY_LENGTH_PER_ROW` - **12,582,912** UTF-16 code units - plus the value in flight when the total crosses, for the row as a whole and not for each element of it. That figure is a code-unit count and not a memory bound. The short-candidate shape this limb exists for has the same per-string overhead the `split_on` measurement below records (12-17x for short tokens), so at the cap in short candidates the heap cost runs roughly 5-10x what a code-unit reading suggests. One charge of 1,048,576 distinct four-character candidates (exactly 4,194,304 charged code units) measures 44.0 MB heapUsed / 84.8 MB RSS, putting three charges near 130 MB heap / 250 MB RSS. Size an acceptor against the heap figure rather than the code-unit one, the browser's ~512 MiB ceiling above included. The figure is measured on the non-fuzzy path, which is the one `APPLIED_SETTINGS.fuzzyComparisons` leaves live. The accumulation charge counts an element's pre-expansion candidates, while the element list retains the post-expansion set for every element already built, so with that flag flipped a row charged at the cap retains whatever the fuzzy expansion multiplied those earlier candidates into - a factor this limb does not see and does not bound. What holds the fuzzy case is the assembled projection above, which is exact but reachable only once every element exists, and the per-(record, key) candidate cap that projection is measured against; bounding fuzzy retention as it accumulates, before the last element exists, is still unclosed and belongs with the flag flip.

Where the two limbs meet: a row whose retained candidates alone cross the cap never reaches the assembled projection, so the accumulation limb determines its fate - the drop where a declared fan-out producer accounts for the crossing, the refusal otherwise (the fate rule below). The assembled byte limb keeps the far larger class it was set for - a row whose bytes appear only in the cross-product's replication of in-bound candidates - and drops it where the provenance says to.

The assembled projection is an upper bound on what a row materializes rather than the exact figure. It is computed pre-join, while the key strings are NFC-normalized and deduplicated on assembly, so a combining mark composing across an element boundary and two combinations concatenating to the same string both count more into the projection than the row retains: measured, 16 projected against 12 materialized on a two-element key whose second element's candidates open with a combining acute. The direction is fail-closed, and it is the direction the count limb's own projection takes too, for the same reason: neither collapse is measurable without the allocation the limbs exist to prevent.

An over-ceiling value is refused, never truncated: both parties must derive byte-identical keys, so a unilateral clamp would break matching and be reported as a terms mismatch against the canonically hashed agreement - the same reason the `pad_left` length and the param content are refused rather than trimmed. Where a declared fan-out producer accounts for the row's multiplicity the fate is the drop instead, which is that producer's normative exceedance behavior ([PROTOCOL.md](PROTOCOL.md#fan-out-matching-multi-value-key-candidates)): the transforms are partner-authored while the values expanded are this party's own rows, so a refusal there would let a partner end an exchange by authoring a delimiter that shatters one local value. Both assembled limbs take that fate from the row's realized provenance, which is complete where they run - after every element exists - so one row cannot take two different fates depending on which limb of one projection fired.

The accumulation limb runs while the row is still being built, so it decides its fate per (record, key) before the key's first element runs, from the compiled steps of the key's elements and of the fields feeding them (`keyAccumulationFate`), and applies that one decision at both of its charges. A raw cell is one string and a compiled step is fixed for the run, so every producer that can expand the record is knowable there; the drop binds to whether the key declares one, not to what the elements read so far have realized. The classification is `drop` when every producer that can expand the key is in `FAN_OUT_FUNCTION_NAMES` - covering both authoring surfaces, an element transform's own step and a fan-out in the standardization of a field the key reads - and `refuse` otherwise. A producer outside that list is outside the width bound's rules and stays fail-closed at every width, wherever in the key it sits and whether or not the crossing reaches it, and a key no producer can expand at all names none to bind the drop to, so it takes that same default. The no-producer arm is the classification's fail-closed default rather than a fate a row reaches through this limb: nothing expands a value there, so what holds such a key is the per-value ceiling applied to each element it holds, and the aggregate a row can accumulate under it is that ceiling times the key's element count (`MAX_KEY_ELEMENTS`). The invariant this buys, pinned by tests driving permuted element orders and crossings forced at the first element and the last: for one record and one key the accumulation fate is identical wherever the crossing lands and whichever of the two charges it lands at. The runtime provenance is retained beside it as a fail-closed safety check only - a step that expands a value while unlisted under a `drop` classification is a producer that classification did not see, which is a fault in the classification rather than a fate the record earned, and the crossing refuses. That is what a Set-returning standardizing function added without an entry in the multi-value classification produces where its expansion lands before the crossing. An expansion a resolved drop never reaches is invisible to the safety check, so the safety check narrows the window such an addition opens rather than closing it, and the entry in the classification is what states the guarantee.

Classifying a key compiles every element's transform before the first element is read, so terms whose element transform names a function this build does not recognize end the exchange as that key's first row is read - whether or not any row realizes a value for the element declaring it, and whether or not the accumulating bound is ever charged. That reach is the deliberate posture: an element the agreed terms declare and this build cannot run is a fault in the terms rather than of the row that happened to reach it, and a refusal waiting for a row to realize a value for that element would let one dataset complete an exchange the next aborts. The `function` a partner may author there is a bounded string rather than one of the names this build knows, so that refusal narrows the name to a literal this build recognizes before interpolating it, as the step refusal below narrows its own.

The listed producer that reaches the expansion charge is one whose expansion retains more than it was handed: splitting itself never grows a total, since the parts hold no more than the value they came from, so the charge crosses on `split_on` keeping the original beside its parts (`include_original`) or on the NFC normalization it applies before splitting. A listed producer added without either property leaves that charge unreached rather than fails open - the crossing lands on the row's aggregate instead and takes the same key fate. A row dropped at any of the three limbs contributes no candidate for that key round, is warned to the operator, and stays eligible for later keys, exactly as an absent realization is; the expansion stops at the crossing either way, since finishing a row already known to be unassemblable is the allocation the bound exists to prevent.

What a refusal names depends on where it fired; none of them interpolates the value, which is the operator's PII, or the key's partner-authored `name`. The two refusals that name only an element - the value-read refusal and the accumulation refusal - locate it by the issue path the terms-validation refusals use (`linkageKeys[i].elements[j]`, the key index taken from the exchange's own key list; a caller holding one key alone roots the path at the element) plus the row index. The accumulation refusal's path names the element the total was accumulating at when it crossed, and its total is the row's across the key's elements, so it states the key rather than attributing that total to the one element. The step refusal extends that path with `.transform[k]` and the step's function name, narrowed to a literal this build recognizes before it is interpolated, as the fan-out refusals narrow theirs. The two assembly refusals, count limb and byte limb, name the key alone (`linkageKeys[i]`) with no element, step, or row - the projection is the row's rather than any one element's - and the row index appears on that path only in the warning a dropped row logs. A row dropped at the accumulation limb logs that same warning shape rather than an issue path: the row index, the total, and the key's partner-authored `name` escaped at that sink, which is what every drop warning states. On the receiver of a key declaring `swap` the position that reads a column and the position that declares it are different ones, since the swap moves the field references and leaves each element's name and transforms in place. A refusal on the value read names the position whose `field` is the offending column, so its remedy - bind the element to a shorter column - points where that column is written. A refusal on a step names the position the step is declared at. The accumulation refusal takes whichever of the two produced the candidates it was charging: the step-declared position where the element declares a transform, and the column-declaring position where it declares none and the candidates are the field's own realized values, so both parties name the same position for the same offending column.

The closer is the unilateral, local one. Neutralizing the amplifying `$`-sequences in a partner-supplied replacement was the other candidate and is not adopted: it changes what a `replacement` means on the wire, a `PROTOCOL_VERSION` and cross-implementation-vector question, where the ceiling changes no wire semantics at all. Five limits are stated rather than closed. First, the per-step check reads a step's output, so one candidate's amplification is allocated before it is refused. What bounds that transient is the ceiling on that step's input, and above it the engine's own maximum string length. Measured on this build's Node, a 1000-character cell under the `$'` replacement allocates 500.5 MB in 107 ms, and a 2048-character cell raises `RangeError: Invalid string length` in 73 ms with no heap growth. Where the step runs over an expanded candidate set it allocates one such value per candidate, which is what the accumulation bound above holds: the live total is that bound's three charges, `3 x MAX_ASSEMBLED_KEY_LENGTH_PER_ROW` code units, plus the value in flight when it crosses, at the heap multiplier and in the non-fuzzy scope recorded with that figure. Either way the allocation stops at that row rather than compounding across the dataset - the exchange ends there where the crossing refuses, and where a declared fan-out producer accounts for it the row is dropped and every further row is held to the same per-row bound. Second, the bound is per row, so a dataset's total is that ceiling times the row count: what the control removes is the partner's ability to size a row's value independently of the operator's data, leaving a bounded constant-factor amplification (at most the ceiling over the honest cell length) where there was no bound at all. Third, the ceiling fires on the operator's own data, which the parameter controls never do, so an honest free-text cell above 4096 characters ends the exchange. The refusal names the element, the step position, the row, and the remedy - bind the element to a shorter column, or shorten the field in this party's own standardization, which the ceiling does not reach. Fourth, on the paths that refuse a partner can still tune an amplifier so that a run aborts deterministically, and learns one coarse bit about the local data's magnitude per consented exchange from whether it does. That availability trade is accepted: an abort is visible and attributable, where an unannounced narrowing is neither. Where a declared fan-out producer accounts for the row's width the same tuning buys the warned drop rather than the abort, which is the width bound's own trade rather than a second one. Fifth, the accumulation charge counts retained characters, so what it bounds is the bytes a row holds live and not the work that produced them - the second limit's "bounded constant-factor amplification" is a statement about a value's size and does not apply to CPU. A step that expands its candidates toward the cap and then collapses them onto one string charges the row about one character while spending the cap's work, and that shape repeats per step and per element of a row the bound accepts. Measured on this build, schema-valid linkage terms of 59,062 bytes - inside the 64 KiB invitation cap - burn 2.8 seconds of CPU for one accepted row at flat memory (~28 MB heapUsed), and the cost repeats on every row of the dataset, with nothing warned and nothing aborted. What bounds that work is only the per-value ceiling times the step and element counts the schema admits (`MAX_TRANSFORM_STEPS`, `MAX_KEY_ELEMENTS`), which at the maxima extrapolates to minutes of CPU per row. Charging realized rather than retained candidates is not the closer - it refuses legitimate collapsing transforms, which is why this limb charges what it does - so closing it means a work or step budget of its own.

The severity mirrors the ReDoS sibling: a fail-open denial of service reachable from the authenticated counterparty, bounded to DoS (no data, no code execution), and not meaningfully self-inflicted. A human reviewing the consent screen cannot vet a numeric `length`, a date-format string, or a replacement literal for an allocation or compile blow-up, and the handshake authenticates identity, not that the authored terms are benign. The bound is fixed defense-in-depth, fail-closed, not a semantic limit. The sibling numeric and expansion vectors audited alongside it are latent, not live, and hold their bound in their own implementation: `substring` reads a partner `length` but slices with `String.slice`, which cannot exceed its input. The `split_on` fan-out cross-product is matched on under the single-pass strategy alone, and it has the per-(record, key) candidate cap specified in [PROTOCOL.md](PROTOCOL.md#fan-out-matching-multi-value-key-candidates). A record above the cap contributes no candidate for that key round, so the cap holds by construction rather than by a refusal, and a cross-product too wide to assemble takes that same drop rather than the refusal below. The cap bounds the retained candidate set, not the split that assembles it: `splitOnFactory` materializes the full parts array and `Set` before the cap is consulted, with no per-value length guard analogous to `MAX_FUZZY_EXPANSION_INPUT_LENGTH`. That transient cost is linear in the value split_on receives, and the string-param content bound above (`MAX_TRANSFORM_PARAM_LENGTH`) does not bound that value - a partner-authored `replace_regex` step preceding `split_on` in the same element sizes the retained candidate the split assembles, and that bound removes only the partner-chosen constant. What bounds it is the produced-value ceiling above: the preceding step's output is checked before `split_on` is handed it, so the value entering the split is at most `MAX_TRANSFORMED_VALUE_LENGTH`. The measurement that established the vector - a 1 MB `replace_regex` replacement over a 10-character operator cell, producing a 1,000,000-character retained candidate at ~12 MB peak, held only by the ~512 MiB frame ceiling - is refused at terms validation by that bound. The measured worst shape for a genuinely operator-sized cell -- ~1.2 MB, short tokens -- is 15-20 MB live (12-17x; the full standardization pipeline needs ~40 MB), dominated by per-string overhead scaling with the part count the delimiter chooses; the cost stays linear in the input length regardless of shape. The amplification is not `split_on`'s: `replace_regex` alone, with no `split_on` downstream, amplifies identically, which is why the bound sits on the param rather than on the split. The `generateFuzzyComparisons` expansion (`transpositions` / `edit_distances` / `adjacent_years` / `day_month_swaps`) is now implemented and has its bounds: each expanded value is refused past `MAX_FUZZY_EXPANSION_INPUT_LENGTH` before any candidate is built, and `buildKeyStrings` refuses a row whose candidate-array product exceeds `MAX_KEY_STRINGS_PER_ROW` before materializing it, counted ahead of allocation. A fuzzy element multiplies its kind's candidate ceiling into the width its key declares in [PROTOCOL.md](PROTOCOL.md#the-width-bound-a-per-key-candidate-cap-the-terms-declare), and `buildKeyStrings` refuses a row a fuzzy expansion widened past that width, so the count the single-pass strategy uses is bounded by the declared width. Terms declaring a width above `MAX_KEY_CANDIDATE_WIDTH`, which is `MAX_KEY_STRINGS_PER_ROW` itself, are refused where the width is derived, so the two bounds coincide rather than one sitting above the other. `transpositions` enumerates all pairs of positions rather than adjacent ones alone, so its candidate count is quadratic in the value's width and its allocation cubic in it; what holds that is the declared width rather than the input limit, since an element bounded to more than 45 characters declares a width above `MAX_KEY_CANDIDATE_WIDTH` and is refused before any row is read ([PROTOCOL.md](PROTOCOL.md#which-party-expands-full-variant-and-deletion-neighbourhood-expansions)). The expansion itself stays inert behind `APPLIED_SETTINGS.fuzzyComparisons`, so the vector remains latent, with its bounds in place rather than deferred to the flip. Two properties of that bound are recorded for whoever flips the flag. The count cap bounds key strings, not bytes: a non-fuzzy element's full local cell is replicated across the fuzzy product, so a row's byte total scales with that element's transformed cell length times the cap. That total measures near 1 GB for one row at the cap with a 1 MB cell, a cell length the produced-value ceiling above does not admit. Those replicated bytes are not tied to the operator's raw input any more than split_on's retained candidate is (above): the string-param content bound does not cap what a transform can multiply a non-fuzzy element's cell by before it is replicated, and `MAX_FUZZY_EXPANSION_INPUT_LENGTH` does not reach that cell at all. The guard checks only the value the fuzzy element itself expands, after that element's own transform runs, never a sibling non-fuzzy element's transformed value. What holds them is the byte limb above, `MAX_ASSEMBLED_KEY_LENGTH_PER_ROW`, measured on the same projection as the count cap and covering both producers rather than fuzzy alone. And edit-distance-1 semantics make a one-character element vacuous: `edit_distances` is the kind both parties expand ([PROTOCOL.md](PROTOCOL.md#which-party-expands-full-variant-and-deletion-neighbourhood-expansions)), a single deletion of one character is the empty string, so any two distinct one-character values at such an element match each other and the element contributes no discrimination -- a matching-precision and disclosure property to weigh before declaring `edit_distances` on initials or single-digit codes.

## Display sanitization escape format

The display sanitizer escapes a string for operator-facing output by replacing every byte or code point that is not printable ASCII - C0 and C1 control characters, DEL, and any non-ASCII code point - with a hex escape: `\xHH` for a code point <= 0xFF, `\uHHHH` for a code point <= 0xFFFF, and `\u{HHHHH}` for an astral code point above 0xFFFF. A literal backslash is doubled (`\\`), and printable ASCII (0x20 to 0x7E) is otherwise left unchanged. The output is truncated to a bounded maximum length with a visible truncation marker. It is a one-way display transform: the escaped form is never parsed back, never used to build a filesystem path, and never used in an equality or hash comparison - those always use the original bytes - so escaping changes only what an operator sees, not how a value matches or routes.

The transform is applied once per value, at the sink that shows it, on every route the assignment below governs; the routes that do not yet meet it are enumerated at the end of this section rather than left implicit. Every escape doubles a literal backslash, so a value escaped at two altitudes reaches the operator with a backslash count that no longer matches the bytes it names - one backslash in a partner filename shown as four, in a message telling the operator to go and delete that file. The two altitudes are therefore assigned rather than left to each call site: a fragment interpolated into an `Error` message or `cause` is composed raw and escaped once by `sanitizeErrorForDisplay` where the error is rendered (which also caps each cause-chain link and strips PEM/OpenSSH private-key blocks). A value that reaches a log, a console, or a UI element without ever becoming an `Error` is escaped by `sanitizeForDisplay` at that call site, which is its sink. A fragment bound for a log or prompt sink takes both halves in one call, `redactAndSanitizeForDisplay`, which redacts and then escapes -- the same single escape, not a second altitude.

The private-key strip has a second, separate assignment, because it is not escaping and does not double. A whole `BEGIN`..`END` block is replaced where it sits; a truncated block -- a `BEGIN` with no `END`, which is what a key sliced into an error looks like -- is replaced from the marker to the end of the unit the pass runs over: a cause-chain link at the error renderer, one log argument at the log sink. That reach is fail-closed: a key that reaches an error has whatever structure the thing that held it left behind, and the separators are not predictable -- real line breaks from a file read, single spaces from a folded or plain multi-line YAML scalar, backslash escapes from a JSON scalar, or no separator at all. So a rule that consumes only armor organised into lines leaks the entire body of every other delivery. The reach stops at that unit's boundary: each cause-chain link, and each log argument, is redacted independently, so a marker in one cannot reach the next. The cost of failing closed is that the replacement also consumes first-party text composed after the marker in the same link. That cost is paid off at the composition site rather than by narrowing the reach: a partner- or server-controlled fragment is passed through `redactPrivateKeyMaterial` where it is interpolated, so a planted marker is replaced inside its own fragment and no longer exists when the link is rendered. The function is idempotent and never lengthens its input, so the later per-link pass is a no-op on an already-redacted fragment and a display budget fitted over raw fragments still holds. Redacting per fragment narrows the reach in one measured case, recorded here rather than left implicit: where two adversary-controlled fragments are adjacent in one link, a `BEGIN` marker ending the first and the key body opening the second are no longer one string when the rule runs, so that body survives where the per-link pass alone would have consumed it. Adjacent fragments under different parties do occur - a partner-derived peer id beside this party's own configured id, a partner-seedable inbound path beside the operator's outbound path. So what bounds the loss is not common provenance but what the surviving bytes are: in every composition reachable today they are that party's own or the operator's own path or id, never a psilink secret. The safety check exists for an unanticipated sink, and a key split across two fragments of one link is where its reach stops. Applying it at a composition site is redaction, not a second escaping altitude: the fragment is still interpolated raw and still escaped exactly once, at the sink. The assignment is a convention over composition sites, not a mechanism that enforces itself -- the renderer cannot tell a first-party span from a partner one -- so it is stated here rather than checked. How much of it a test can hold varies by site, and at the two refusals of the CLI first-use host-key flow (`establishHostKeyTrust` in `apps/cli/src/hostKeyTrust.ts`) it is not pinnable at all. Each chooser's fragment is last on a labelled cause link of its own and the renderer redacts every link before truncating, so removing either of those composition-site calls changes no rendered byte and reddens no test. Fitting a fragment at its composition site takes it out of that unpinnable class, because the clip is what makes the order of the two transforms observable. The stalled-transport builder (`transportOperationStalledError` in `apps/cli/src/connection/sftpLivenessGuard.ts`) fits each of its three fragments -- its stall detail, its path, and the dead-session arm's server-reported one -- to its link's budget after redacting it, so a key block wider than that budget renders as the replacement plus whatever followed it. Dropping the redaction leaves the clip cutting the block's `END` off, and the renderer's own per-link pass then consumes the dangling remainder to the end of the link, taking the truncation marker and the bytes composed behind it with it. `apps/cli/test/unit/connection/transportRefusalBudget.test.ts` pins that ordering at the rendered boundary. What a test does hold is five sites, each pinned at its rendered sink by a marker planted in the fragment its adversary chooses: the cross-party host-key divergence warning, the same flow's trust warning, confirm prompt, and its `write-now` and `ephemeral` pin lines, and the `probe-host-key` summary. That is a sample of the composition sites the assignment governs, not a roster of them -- the sweep covers the log-bound fragments that already ran through the display escape in `packages/core/src` and `apps/cli/src`, and the rest are held by the convention plus the sink pass behind it rather than by a marker test of their own. Those are not every fragment a log line interpolates. An operator's own configuration and key-file paths still reach several CLI log calls raw, composed ahead of the guidance on the same argument -- `apps/cli/src/commands/accept.ts`, `apps/cli/src/commands/invite.ts`, `apps/cli/src/onlineBootstrap.ts`, `apps/cli/src/fileUtils.ts`, and `apps/cli/src/recordFile.ts`, whose keys-file warning composes the path ahead of the one instruction telling the operator to delete or protect that material. Those names are the class, not a roster of it: what identifies the class is an operator-chosen path reaching a log call without the escape the sweep followed, and a site that acquires one later joins it silently. So a path an operator names with a `BEGIN` marker loses that guidance to the fail-closed pass, including the ACL-restriction instruction on the key-file permission warning. The host-key flow redacts that same class of value (`persistence.configPath` in `apps/cli/src/hostKeyTrust.ts`), so the boundary sits where the escape already ran rather than where the hazard stops. What makes the residue tolerable is that the operator chooses those bytes themselves and is trusted, not that the sweep reached them. A site whose fragment is composed ahead of first-party text and whose call is dropped therefore reddens nothing; that is the cost of the assignment being a convention, and it is why the sweep is uniform rather than fitted to where text happens to follow today.

Uniformity costs something of its own at three operator surfaces that run no sink pass, and so had nothing needing containment: the interactive host-key trust prompt (`promptConfirm` in `apps/cli/src/hostKeyTrust.ts`, written by readline rather than through a prefixed logger), the browser consent screen the web app renders from `invitationSummary.ts`, and the CLI's outbound-consent column list (`writePromptLine`, below). A partner-seeded host, a partner-declared identity or column name, or one of this party's own header columns, shaped like armor displays as `[redacted private key]` at the very surface where the operator decides whether to trust a host key, accept the terms, or send those columns, where the escape alone would show it whole. Each composition also takes a log route, which is what the redaction is there for; showing the operator one string on both routes is the trade. The cost is display fidelity at a decision point, recorded here rather than left to be discovered at the prompt; where the decision is what to send, fidelity is not the whole of it, and the outbound-consent column list below holds the rest. Rendering a raw error at a sink is banned by an ESLint rule over `packages/core/src` and `apps/cli/src` (excepting the three parse chokepoints those blocks already ignore, which have no display sink). The CLI integration console sentinel fails on any captured line with a byte outside printable ASCII once the `\ncaused by: ` framing the cause-chain renderer emits between links is removed - the framing is removed before the test rather than exempted from it, so a forged log line of printable ASCII plus a bare newline still fails. Both halves are bounded. The rule matches the raw error where it sits directly in a sink argument and does not follow it through an intermediate local, a method call on the message, or a container the sink unpacks, since that would need taint analysis TypeScript cannot run. The sentinel observes only `console` calls, so a direct `process.stderr.write` is outside it, as is a dependency that writes the file descriptor itself. The sentinel's framing strip is also a literal one with no notion of who emitted the sequence, so a line whose unescaped payload itself contains `\ncaused by: ` passes the byte test. Neither is a claim about every byte that lands on the terminal.

The strip therefore has three sinks, and the unit it runs over differs at each. At the error renderer it runs per cause-chain link (`sanitizeErrorForDisplay`). At the diagnostic log it runs per argument, in core's log prefixer (`setLogPrefixer` in `packages/core/src/utils/logger.ts`) rather than in a consumer's diagnostic sink. The prefixer sits upstream of both CLI routings (stderr and `--log-file`) and of the browser console the web app keeps, and it also covers a line logged before a consumer installs its sink, which a sink-side pass would miss entirely. The prefixer is handed raw `unknown[]` and the sink owns its own formatting, so the pass rewrites only the members that are already strings and passes every other member through by reference - an object argument prints exactly as it would without the pass. The CLI's fd-3 warning event is the third (`buildWarningEvent` in `apps/cli/src/eventStream.ts`), because that stream is a persisted machine sink whose terminal error event is already redacted through `sanitizeErrorForDisplay`; leaving its one other free-text field unredacted would make the stream the exception. That event's display cap is sized for a composition rather than for one value: the host-key divergence warning is the whole reason a supervisor that discards stderr reads the stream, and the per-value default cuts that warning mid-explanation, taking its re-pin instruction with it.

Each unit boundary is also a reach limit, stated rather than closed. Key material split across two cause-chain links is not seen by the per-link pass, and key material split across two arguments of one `log.warn(a, b)` call is not seen by the per-argument one. Joining first would close either, at the cost this whole assignment exists to avoid: a dangling marker in the first unit would then consume every unit behind it, which is how the party a warning is about deletes the warning about itself. The composition-site rule is what makes that trade the right one - a fragment redacted where it is interpolated holds no marker by the time either pass runs, so the wider reach of a sink pass costs nothing that the composition sites have not already paid. The third limit is which sinks have a pass at all: the three above are the error renderer, the diagnostic logger, and the fd-3 warning event, so an operator-facing sink that does not route through the prefixed logger runs none of them. The receipt-verification report (`apps/cli/src/commands/verifyReceipt.ts`) and the argument-parser rejection (`apps/cli/src/cliParser.ts`) write `console.log` and `console.error` themselves, and are escaped at composition without being redacted. None of them can suppress first-party text, because no pass runs there to fail closed; what they lack is the safety check, and closing that means moving them onto a logger or giving each its own pass. The CLI's plain-line sink (`LogSink.writePlain` in `apps/cli/src/util/logging.ts`) belongs to that class for a different reason and is the one that reaches a persisted destination: it feeds the same writer the prefixed lines go through, so a `--log-file` captures it, but it bypasses the prefixer and therefore the per-argument strip. Its only caller is the `doctor` verdict rendering (`apps/cli/src/commands/doctor.ts`), which includes an NT_STATUS token and `smbclient`'s own output. For that sink the composition is the only place a pass can run, and the rendering runs three of them, with the unit differing between them as it differs across the three sinks above. The first runs on the whole tool output before the rendering splits it into lines (`clampDetail` in `apps/cli/src/doctor/verdict.ts`): a tool hands a key block over in its canonical multi-line form, so a pass over the lines that come out matches its `BEGIN` line alone and renders every body line verbatim. The second runs on the whole of a check's meaning or action text before the rendering re-flows it under its label (`wrapLabelled`, below). The third runs per rendered line, where the rendering escapes (`emit`), and the first two are what make it a no-op over the tool output and the wrapped blocks. That third pass is not free: a summary line composes an operator-supplied value -- the SMB server name, or the mounted directory -- ahead of its own predicate, so an operator who names one with a `BEGIN` marker reads `OK: [redacted private key]` and loses the predicate to the fail-closed rule. The marker filename is composed the same way but cannot reach it: `MARKER_PATTERN` admits no space, and every redaction pattern requires one, so a marker-shaped `SMB_MARKER` is refused as a usage error before any check runs. Those bytes are the operator's own and no partner reaches them, which is why the cost is recorded here rather than closed by redacting each fragment before composition; all three passes are pinned by marker tests rather than resting on the convention.

The wrap is why the second of those passes exists, and it is the one shape in this assignment where the strip could fail OPEN rather than closed. `wrapLabelled` re-flows a check's meaning and action text on whitespace at 76 columns, and every marker the rule matches contains spaces, so a `BEGIN` straddling a wrap would reach the per-rendered-line pass as two lines, neither matching a pattern that requires the whole marker, leaving the material behind it to render verbatim. Redacting the whitespace-normalized text ahead of the re-flow closes that, exactly as `clampDetail` closes the same shape ahead of its split -- and normalizing before redacting is critical: the re-flow collapses every whitespace class to ASCII spaces, so a marker whose internal separators are non-ASCII whitespace would otherwise be re-formed by the normalization after a raw-text redaction had run. The unit is one labelled block -- meaning and action are wrapped separately -- and the label is composed outside the redacted text, so a dangling marker takes the rest of its own block and reaches neither the label nor the sibling block. What the wrap holds is the operator's own `SMB_SERVER`, `SMB_SHARE`, and `SMB_PATH`, the `SMB_MARKER` filename `MARKER_PATTERN` already confines to a space-free charset, and smbclient's own NT_STATUS token, whose `NT_STATUS_[A-Z_]+` shape admits no space either; the server-controlled `detail` is redacted whole before the split and its lines are never wrapped. The replacement is prose to the wrap like any other phrase and can itself be broken across two rendered lines, a legibility cost of the ordering rather than a disclosure one. The property is pinned at the rendered boundary by a marker planted so the wrap splits it, alongside a marker-shaped control string rendered at the same offset, which is what establishes that the wrap falls inside such a run rather than leaving it whole.

One more site is on the sweep for exactly the split the sweep exists to prevent: the outbound-consent column list (`displayOutboundColumns` in `apps/cli/src/outboundPayloadConsent.ts`) sends each line to `writePromptLine`, which runs no pass, wherever a prompt follows. It also sends each line to `log.info`, where the prefixer's pass redacts, wherever the log is what records it -- under a `--log-file`, and on the non-interactive arm that asks nothing. So a name left to the sinks would read verbatim at the prompt and as the replacement in the log, the disagreement `invitationSummary.ts` was swept to avoid. Redacting each column name where it is interpolated is what makes the two byte-identical, and the check asserts the two sinks against each other on one run rather than each against its own expectation. The names are this party's own CSV header, so what the composition-site pass costs is the display fidelity recorded above: an operator whose header names a column like armor reads the replacement where the question is asked. Two mechanisms render distinct names as one line here, and the replacement is only the first -- two columns shaped like armor read as the same replacement line, and the escape's own output cap collapses names that hold no marker at all. `sanitizeForDisplay` bounds the characters it emits at `DEFAULT_MAX_DISPLAY_LENGTH` (**256**) rather than the code points it reads, and a code point above U+00FF escapes to six characters, so a header of 43 of them already overruns the budget and truncates. Two such names sharing a long non-Latin prefix therefore render as the same truncated string while both sit far under the `MAX_NAME_LENGTH` ceiling (**256** code points) that decides which names an exchange can hold at all. That collapse is driven where a treatment turns on it, at the web app's grid (`apps/web/test/browser/accept.test.ts`, "two long headers sharing a prefix stay distinct in the grid"). What an indistinguishable line costs here is more than fidelity, because this is the surface the send is answered on: an operator who reads two of the listed names as one and answers yes has consented over a set they cannot tell apart -- a send they did not mean, rather than a name they could not read. The answer is set-level, one question over the whole list with no per-name mark, so the remedy is the refusal rather than a correction at the prompt: decline, change what the input file discloses (rename the header, drop the column, or mark it not transmitted), and run again. The web app's acceptor screen forgoes this escape for its own column names and records that trade and the residual it leaves there -- [COMMUNICATION.md](../COMMUNICATION.md) and `apps/web/src/components/ColumnName.tsx`. The same surface's non-interactive arm is not yet on the sweep: the refusal thrown when no prompt can be asked composes the column names raw into its error message, so a marker-shaped name costs that message's explanation and recovery instruction to the error renderer's fail-closed pass. Those bytes are again the operator's own CSV header, so the cost is legibility rather than disclosure; it stands recorded here until that composition site is redacted.

The per-link cap is a second bound on the same output, independent of redaction, and it falls wherever it lands: on a link that mixes first-party text with a fragment somebody else chose, the chooser spends the budget and the operator loses the instruction.

That per-link budget is **not** the per-value default. A cause-chain link is a composition -- first-party explanation and recovery text with fragments interpolated raw into it, by the single-altitude assignment above -- where `DEFAULT_MAX_DISPLAY_LENGTH` (**256**) is sized for one value. So charging a whole link to it cuts the composition's own instruction with no fragment involved at all: the connection-endpoint locator rejection in `packages/core/src/config/invitation.ts` is 348 characters of fixed guidance before its prefix and its list of rejected keys. `sanitizeErrorForDisplay` therefore caps each link at `COMPOSED_MESSAGE_MAX_DISPLAY_LENGTH` (**1024**, `packages/core/src/utils/sanitizeForDisplay.ts`), sized to admit the longest fixed guidance psilink composes into one message together with the bounded values that message names, and left well under the **4096** of `WARNING_MESSAGE_MAX_DISPLAY_LENGTH`, whose four re-escaped fragments crossing three boundaries are a larger shape. The whole rendered chain stays bounded without a separate total-length cap: at most `MAX_ERROR_CAUSE_DEPTH` (**8**) links at that budget each. The budget bounds what any single link can spend; whose bytes spend it is decided by the partition below, which is why a wider link is not a wider flood allowance. The two SFTP host-key refusals (`installEnforcingVerifier` in `packages/core/src/connection/sftpSession.ts`) are therefore composed as a partition by provenance - one link per party that chose the bytes on it - rather than as one string, the same remedy `entryGuardRefusal` applies in `packages/core/src/connection/fileSyncRendezvous.ts`. The refusal itself, the presented fingerprint (base64, of fixed length), and the operator's pin or re-pin instruction ride the error's own message plus, where they exceed one budget, further first-party cause links. Each fragment somebody else chose then takes a labelled cause link of its own - the configured host and the presented key type on the no-pin refusal, the pinned set and the presented key type on the pinned-mismatch one. `FileSyncConnection.open` folds those links in ahead of the transport error the connect rejected with, so the cause-depth bound can never drop a detail in favour of ssh2's opaque `Host denied`.

Splitting by chooser rather than into refusal-plus-detail is what keeps the fix from reproducing the defect one level down. The host and the key type are chosen by different parties: on the acceptor route the host is the partner's, copied verbatim out of the invitation endpoint into the written config (`connectionFromEndpoint` in `apps/cli/src/onlineBootstrap.ts`), and `SFTPServerSchema` bounds `connection.server.host` neither in length nor in format, while the key type is decoded from the server's blob under no bound at all. So a shared trailing link would let either delete the other's disclosure. The pinned set is the operator's own rather than an adversary's, but `SFTPServerSchema` bounds each pin's format and not the array's length, so a many-pin config would eat the re-pin instruction from a shared link; its own link is the right place for it. The property this buys is that the cap can only ever consume a chooser's own bytes, and it is pinned by test at the rendered boundary. Each refusal renders its fingerprint in full and its instruction whole under a benign key type, an over-length one, one holding a PEM `BEGIN` marker, a configured host at the full 256 characters the invitation schema admits (which the link budget delivers whole), and one past that budget, where the cut falls on the host's own link and no other. Reachability differs between the two refusals and the partition does not rest on it: the pinned-mismatch form is reachable from any CLI run, while the no-pin form is core's fail-closed safety check for a direct library caller, ahead of which the CLI's own first-use trust flow normally pins. Nothing enforces that ordering, so the no-pin refusal is composed to the same standard as its sibling rather than treated as unreachable.

The cap is not removed, only kept off first-party text: a fragment that overruns still truncates on its own link, and the whole rendered chain stays within the cause-depth bound times the per-link budget plus the separator the renderer emits between links - also pinned by test, with each branch's live fragments flooded at once. Enforcement is untouched throughout: the connection is refused and a changed key is never auto-accepted. One residual bound remains: each first-party link fits its budget by measurement, not by construction, so growing the fixed copy past the cap would put the cap back on the operator's text. That residual is held by a check rather than by this paragraph - rendered with every variable fragment at its ordinary size, no link of either refusal truncates at all, so any growth past a budget fails there.

The cause-depth bound is the same kind of bound one level up -- over links rather than characters -- and it discloses its cut the same way. A walk that stops at `MAX_ERROR_CAUSE_DEPTH` with the chain still running appends `CAUSE_DEPTH_ELISION_MARKER` (`...[further causes elided]`) to the last link it renders, so a chain the bound cut displays as cut rather than as the whole failure; a chain that ends on its own, or that the cycle guard stops on a link already rendered, holds no marker. Neither marker is authenticated, and neither can be: both are plain printable ASCII the escape passes through unchanged. So a link whose own message ends with the marker's text renders byte-identically to one the bound really cut -- the same shape the transport-refusal checks work around for `DISPLAY_TRUNCATION_MARKER` by expressing "this link truncated" as a length comparison against the cap rather than as a marker search. The cost is one-directional and bounded: a copy of the marker claims a loss that did not happen, and cannot conceal one that did, because the renderer appends its own after the escape whatever the link held. So what an operator can rely on is the marker's absence, its presence saying detail MAY be missing rather than that it is. Both directions are pinned by test at the rendered boundary, a partner message holding the marker's text driven alone, at the depth cut, and against a genuinely cut chain it renders identically to. The marker has no count, because counting the remainder means walking the rest of the chain -- the walk this bound exists to refuse, and unbounded in exactly the adversarial case it is defensive against. A composition site whose link count is driven by a list length therefore states its own overflow, where the count is free: `checkLinkageSatisfiability` (`apps/cli/src/commands/linkagePreflight.ts`) gives each unsatisfied field a labelled link, and `LinkageTermsSchema` bounds `linkageFields` only at `MAX_LINKAGE_ENTRIES` (**256**). So it fits the enumeration to the links the renderer reaches -- the summary and the remedy chained ahead of the names take one each -- and spends the last of them on `and N more unsatisfied fields (M in total)` rather than on one more name. What puts a site in that class is the count of links it asks for, not the length of any one of them: a many-valued fragment on one link (the pinned-fingerprint set above) spends that link's character budget and truncates where an operator sees it, while a list given a link per element runs off the end of the walk. Both are pinned by test at the rendered boundary, the enumeration at more names than the walk admits and at the widest count that needs no overflow link at all.

The CLI's own first-use trust flow (`establishHostKeyTrust` in `apps/cli/src/hostKeyTrust.ts`) composes its two refusals to the same partition, and reaches the operator through the same renderer: `exitWithError` and `runOrExit` (`apps/cli/src/util/exit.ts`) and the last-resort catch in `apps/cli/src/index.ts` all call `sanitizeErrorForDisplay`. The partition moves the recovery step off the error's own message, so that routing is what delivers it, and the routing is held by a check of its own (`apps/cli/test/unit/util/errorSinkCauseChain.test.ts`). A table drives a synthesized error of this shape - a summary wide enough to truncate on its own link, the recovery sentence on a cause link - through each CLI error sink and fails unless that whole sentence reaches the sink's captured output. The table names five sinks rather than the three this flow reaches: `parseOrExit` (`apps/cli/src/util/flags.ts`), `exitWithError` and `runOrExit` (`apps/cli/src/util/exit.ts`), the last-resort catch in `apps/cli/src/index.ts`, and the `--event-stream` terminal error event (`apps/cli/src/eventStream.ts`). So what is asserted is the serialized line rather than the built event. Two limits are the check's, not the property's: it covers the sinks that terminate a run, so the mid-run diagnostics that render a caught error into a log line (`apps/cli/src/protocol.ts`, the SFTP adapter) are outside it. And nothing enumerates the sinks from source, so a sixth terminal sink is covered when it is added to that table and not before. The declined-trust refusal is the same shape with the configured host as its only fragment link. So a link with either one beside the recovery would delete it - and the link with both did, at every host, because the recovery sentence alone filled a whole budget. The ephemeral shape (a `zero-setup` run without `--save`) names no path and grows no link for one; its recovery points at a saved configuration instead. Testing also spans a host and a config path each past every budget. They also have the same residual check core's pair does: with every fragment at its ordinary size, no link truncates at all. That pin is the armor replaced on that fragment's own link, the label and the first-party links intact, and the reach stopping at the link boundary rather than consuming the link behind it. What those deliveries pin is that rendered outcome, not the composition-site calls: in this composition each chooser fragment is last on its own link and the sink redacts every link before it truncates, so removing either call changes no rendered byte and reddens no test - measured across every host and config-path delivery this flow admits. The three bounded-transport refusals above -- `FrameSizeExceededError`, `DirectoryListingBoundsError`, and `TransportOperationStalledError` (`packages/core/src/errors.ts`) -- have the same partition, and reach it from the other direction: what a shared link deletes here is not a chooser's victim but first-party text that simply does not fit. A labelled link of one's own bounds whose bytes may fill it, not how many. The three CLI guards fit each adversary-chosen value -- the directory-listing guard's directory path, the frame-size guard's inbound path, and the liveness guard's path and, on its dead-session arm, the server-reported error, none of them bounded anywhere upstream -- to `DEFAULT_MAX_DISPLAY_LENGTH` (**256**), label included, where they compose it (`clipToRenderedCost`). The liveness guard fits its first-party stall detail the same way, so its three links share one rule. The clip measures the rendered cost of a raw fragment and appends the truncation marker itself, so the fragment still takes its single escape at the sink and a planted `BEGIN` marker cannot consume the marker that says it was cut. The fragment is bounded after that measurement, not before it. One value per link is the critical half of that assignment, not a tidiness rule: two values with first-party glue between them share one budget. The accept-time reconcile refusal (`reconcileConflictMessage` in `apps/cli/src/config.ts`) takes the same partition on one link rather than on a chain, because what a cut deletes there is a single recovery sentence rather than a step several links down. That budget's residuals are two, recorded rather than closed. ## Compatibility diagnostic value delimiting

The escape above governs which bytes an operator can be shown. A second, orthogonal control governs which clauses: the cross-party compatibility diagnostics (`validateCompatibility`, `packages/core/src/linkageTermsNegotiation.ts`) are first-party prose whose structure an operator treats as psilink's own -- `legal agreement reference mismatch: local is X, partner is Y` -- around values a mutually-distrusting partner chooses. Both sides of that sentence can be the partner's, since `deriveAcceptedLinkageTerms` adopts the inviter's `legalAgreement` and `linkageRuleSet` verbatim into the acceptor's terms ("local" names provenance in the exchange, not trust in the bytes). The escape does not reach this class: it rewrites what is not printable ASCII, and a reference of `A", partner is "B`, a rule-set name of `hmis-keys 9.9.9 over baseline-pii`, or a payload column named `a,b` is printable ASCII throughout. What answers it is delimiting, applied once at composition.

Every value one of these diagnostics names passes through one module (`packages/core/src/config/compatibilityMessage.ts`) in one of two forms. `quoteTermsValue` wraps the value in `"` and doubles every `"` inside it: reading from the opening delimiter, a doubled delimiter is one literal character and a single one closes the run, so the encoding is injective and no value can terminate its own run early or spell a clause of its own. `bareTermsValue` renders undelimited the values the terms schema constrains to a shape no clause boundary is made of -- a semver string or an ISO date -- and RE-CHECKS that shape on the value in hand: the charset `BARE_TERMS_VALUE_PATTERN` matches letters, digits, `.`, `_`, and `-`, at least one of them a digit. Since that pattern bounds no length, a `MAX_BARE_TERMS_VALUE_LENGTH` of **64** characters `bareTermsValue` checks beside it. It falls back to the quoted form for anything else. The re-check is what makes it a second safe constructor rather than an override: `validateCompatibility` takes two `LinkageTerms` objects and nothing in its signature makes them schema-parsed, so the assumption is executed rather than asserted. The shape excludes the delimiter and the `,`/`[`/`]` the payload list is built from; the digit is what stops a bare value spelling a connective. Excluding the space makes a bare value exactly one whitespace-delimited token, which on its own does not keep it out of a connective position, because the template supplies the spaces around a bare slot -- the rule-set clause renders `<name> <version> over <name> <version>`, so a letters-only version would stand in that sentence as undelimited as the `over` beside it. Every value these diagnostics render bare has a digit and no connective or label their templates are built from does, which leaves the two vocabularies in disjoint shapes; the digit-free half of that is executed rather than asserted, `packages/core/test/config/compatibilityMessage.test.ts` reading the templates out of their own module and failing if any token of first-party copy meets the bare shape. A value with no digit -- an algorithm or strategy enum member, say -- takes the quoted form instead, which costs the reading nothing. A payload column list quotes per element (`quoteTermsValueList`), so the rendered `["a","b"]` shows the same partition the byte-exact element-wise comparison used to decide the mismatch, rather than the `[a,b]` a single column named `a,b` would also print.

Doubling rather than a backslash escape is what keeps the control orthogonal to the escape at the sink: the module adds only printable ASCII, which `sanitizeForDisplay` passes through unchanged, so a run's boundaries survive the display boundary byte for byte and neither transform doubles the other's work. On the `warnings` route, which escapes at composition, the escape runs before the delimiting, so that transform's truncation can never take the closing delimiter off a run.

Beside the delimiting, `quoteTermsValue` replaces every control character in the value (Unicode `Cc`, so U+0000-U+001F and U+007F-U+009F) with a printable marker naming its code point in two lowercase hex digits inside angle brackets -- `<0a>` for a line break, the same four characters wide the escape's own `\x0a` is. So a budget measured over a treated fragment is the budget the untreated one asked for (`replaceControlCharactersForDisplay`, `packages/core/src/utils/sanitizeForDisplay.ts`). Delimiting bounds what a value can do in the message's printable structure; this bounds what it can do in the bytes a composition builds structure out of one level up. A message whose own structure is a control character -- a block separating its lines with `\n`, escaped whole where it is shown -- reaches the operator with that structure rendered as the escape's `\xHH`, which is what an untreated value's own line break would reach them as too, with neither a delimiter nor a doubling between the two readings. Treated, that token is the composition's alone. The marker has no backslash and nothing outside printable ASCII, so the sink's single pass finds nothing to rewrite: this is a composition-site treatment, the same shape as the private-key redaction above, not a second escaping altitude. On the `warnings` route the escape again runs ahead of the module, so nothing is left there for the treatment to act on and a value's control character instead arrives one backslash wider than a composition's own would -- the observable doubling that route already has, standing as the same distinction. Being printable, the marker is not authenticated and cannot be: a value that spells it renders as one that held the character it names, the same open class `DISPLAY_TRUNCATION_MARKER` has; what an operator relies on is the converse, that a control character psilink itself composed renders as the escape's `\xHH` and no value can produce that. `packages/core/test/utils/sanitizeForDisplay.test.ts` drives the whole control class through the marker and fails if any of it renders as a token the escape writes for a control character, or if a marker costs the display more than the character it replaced; `packages/core/test/config/compatibilityMessage.test.ts` and `apps/cli/test/unit/config.test.ts` assert the property where each renderer shows it.

The enumeration is held by type rather than by a list. `validateCompatibility` accumulates `CompatibilityMessageFragment` -- a `string` intersected with a phantom property keyed by a `unique symbol` private to that module, the same brand construction the invitation consent summary uses for `Displayable` -- and the only ways to obtain one are the two constructors above and the `compatibilityMessage` tagged template, whose fixed spans only the compiler produces. A terms value interpolated into a diagnostic without passing the module does not compile, for a message edited later as much as for a mismatch check added later. `packages/core/test/config/compatibilityMessage.test.ts` is the runtime half: it drives every value slot of every diagnostic that names one -- both sides of a two-slot comparison, and each of the four the rule-set clause renders -- twice, once with a value it legitimately holds and once with an adversarial shape built around that same value. These are: one with the delimiter, one with every clause connective these messages are built from, one reading as the `<name> <version>` pair the rule-set clause renders, and two the bare charset admits, a connective spelled outright and a digit-carrying value that stays bare. It asserts the two runs produce the identical clause skeleton and that the value is kept whole, inside one run or, where the checked bare shape let it through undelimited, verbatim in the clause. The last two are what reach the bare branch at all, the first three each with a space or a comma that delimits them whatever slot they land in. Both then have to hold again on what the diagnostic's own route renders, which is not one pipeline: an `errors` diagnostic composes raw and is asserted through the `Error` its caller throws and the single escape at the error renderer, while a `warnings` one is asserted through the escape it already took at composition and the further pass its sink applies. The pass count is asserted rather than assumed, and asserting it takes the negative: a second pass doubles the first pass's backslash, so the once-escaped form is a substring of the twice-escaped one and looking for it alone cannot tell them apart. The single-pass route is pinned by the absence of the doubled form and the warnings route by its presence -- reachable there because `validateCompatibility` takes two `LinkageTerms` objects its signature does not make schema-parsed, which is the same assumption `bareTermsValue` re-checks; a date that arrived through the terms schema has no byte either pass rewrites, which is what keeps that route inert above.

The same module composes the payload-disclosure refusal (`assertPayloadSendDisclosed`, `packages/core/src/payloadExchange.ts`). That one is not a cross-party comparison -- it holds this party's own `payload.send` dictionary to what its metadata actually transmits -- but it names the same class of value, because on the accept side both the dictionary and the terms around it are the inviter's, adopted by `deriveAcceptedLinkageTerms`. Its problem and remedy clauses accumulate `CompatibilityMessageFragment` and its name lists render through `quoteTermsValueList`, so the bracketed list an operator reads shows the same element partition the membership comparison used, and no column name can spell a clause of the refusal's own. `packages/core/test/payloadExchange.test.ts` drives each of the three lists that message renders -- the over-declared list, the under-declared list, and the under-declared list under an empty `send`, whose remedy is prose of its own -- with a delimiter-carrying name, a name spelling the message's own clause separators, and a name forging an extra element into the list. It asserts each produces the clause skeleton the benign run did: on the composed message, and again through the single escape at the error renderer that delivers the `UsageError` to the operator. The reader those assertions invert is the one the module's own suite pins against the constructor (`packages/core/test/utils/compatibilityMessageReader.ts`), shared rather than restated so the two suites cannot drift apart on what a run is.

The same module delimits the rule-set citation the CLI acceptance consent surface prints (`displayRuleSetCitation`, `apps/cli/src/invitationDisplay.ts`) -- not a diagnostic at all, but the invitation's own terms rendered where the acceptor's decision is taken. Each half of the citation is a partner-chosen set name beside that half's content version, both behind a fixed first-party label, so the name is the value with a boundary to hold: it is free text admitting a space and a delimiter of its own, which the escape passes through as printable ASCII. So it renders as one delimited run and cannot close that run early to stand in the line as the name and version of a citation the invitation does not make. The version renders through the checked bare form, re-testing the semver shape on the value in hand rather than trusting the decode that produced it. The terms schema admits a version up to its 256-character bound while the bare form re-checks its own 64, so a schema-valid version past that length renders as one delimited run rather than bare -- the fallback, not a refusal. `apps/cli/test/unit/commands/accept.test.ts` renders a name and a version each crafted to those shapes, asserts the crafted name's doubled form appears on both citation lines with neither imitated line anywhere in the rendering, and asserts the out-of-shape version displays as the delimited run. The enumeration is by site here rather than by type, because this surface composes plain strings, so nothing obliges a line added beside it to pass the module. None of the three limits below reaches it. Every value arrives already escaped and redacted from `summarizeInvitation`, the consent summary's single display boundary, so the display cap's truncation runs ahead of the delimiting rather than over a composed run. # Web signaling surface bounds

The bounds above harden the CLI's file-sync transport against a hostile server admin. The web application's bundled PeerJS-compatible signaling server is a separate surface with a different model: it is untrusted by design (see the **Channel security** and **Third parties** overviews in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security)), relaying only opaque rendezvous-setup messages between two browsers that authenticate each other directly. So the residual exposure on its WebSocket upgrade surface is resource exhaustion, not access to any party's data. The guards below are defense-in-depth against that nuisance, enforced in the application unconditionally; the deployment-dependent Origin and per-address controls are the reverse proxy's responsibility and are described operationally in [DEPLOYMENT.md](../DEPLOYMENT.md#hardening-the-signaling-surface), not here. All values are fixed constants, not configurable, for the same reason as the file-sync bounds: a configurable bound risks an operator raising it enough to reintroduce the denial of service.

**Upgrade-handshake timeout.** The shared HTTP server bounds a pre-101 upgrade handshake with a **10-second** header timeout (`SIGNALING_HEADERS_TIMEOUT_MS`) and a **15-second** request timeout (`SIGNALING_REQUEST_TIMEOUT_MS`), set in `apps/web/server/upgradeHardening.ts`. A client that opens a connection and dribbles -- or never finishes -- its request headers is closed server-side rather than held open. The entry attaches its own `clientError` handler to perform the close rather than relying on Node's built-in default close-on-`clientError`, because that default is silently disabled the moment any other `clientError` listener is attached (an embedding framework, or under test a loaded `ws`, may attach one). Node checks the header and request timeouts on a periodic sweep (default 30 seconds), so the effective close is the bound plus up to one sweep interval -- coarse, which is sufficient for a resource-exhaustion guard.

Those two timeouts only arm once HTTP request parsing has begun, so they do not cover the cheapest hold of all: a peer that completes the TCP handshake and then sends nothing, which has no request for them to bound and would otherwise sit until the OS reaps the idle socket. A **10-second** per-socket idle timeout (`SIGNALING_PREHANDSHAKE_IDLE_MS`, applied on each new connection) closes that case, on its own precise timer rather than the periodic sweep.

The standalone broker runner (`packages/peerjs-broker/src/standalone.ts`) applies the same three bounds to the server it owns, from constants of its own package (`STANDALONE_HEADERS_TIMEOUT_MS`, `STANDALONE_REQUEST_TIMEOUT_MS`, `STANDALONE_PREHANDSHAKE_IDLE_MS` in `standaloneUpgradeBounds.ts`), since a package does not import from an app. It terminates no TLS, so the TLS handoff the shared server needs has no counterpart there.

All three bounds cover the window in which the socket still owes the server a request. Arrival is the whole request, not its headers: a client that completes its headers, announces a body and then sends none of it still owes the server bytes, and stays under the idle bound rather than falling through to `requestTimeout` on the periodic sweep. What arrives decides what governs the socket next. An upgrade request is released outright by `ws`, which resets the socket timeout to `0` the instant a socket completes the 101, handing the established WebSocket to the `ws` close timer and the liveness reaper below. An ordinary request is weighed by the reap itself: a `request` hook the harden installs records the request the socket is delivering, and when the idle timer next fires the reap destroys the socket unless that request's `complete` flag says the whole of it is in hand -- a request wholly in hand lets that window pass, and every window after it. Node destroys a timed-out server socket itself unless the request, the response, or the server has a `timeout` listener, so the same hook attaches a placeholder listener to the response, which is what leaves the decision with the reap for as long as a response is in flight. That listener is scoped to the response rather than to the server: Node's own keep-alive reaping of a finished, idle connection acts once the response is done and must not be suppressed along with it (a unit check pins that it still fires). No matching hook is installed on `upgrade`: the signaling server decides whether to release an unhandled upgrade at once by testing that it is the sole `upgrade` listener, which a second listener here would silently flip into the co-resident path below (a unit check pins that the harden adds none). Both paths act on the socket object the HTTP layer hands them, which under TLS -- the deployment shape the entry builds when `NITRO_SSL_CERT` and `NITRO_SSL_KEY` are set -- is the `TLSSocket` wrapping the accepted connection rather than that connection itself. So a bound left on the wrapped socket would be reached by neither while Node's own timer refresh keeps it armed through the wrapper's traffic: that is a live connection reaped mid-response or mid-exchange. The harden therefore hands the bound from the accepted socket to the `TLSSocket` on `secureConnection`, which leaves the accepted socket holding it only for the window before a handshake completes -- the one window no `TLSSocket` exists to hold. HTTPS tests pin both halves: a slow response and an established WebSocket outlive the bound, while a connection that opens and never starts its handshake is still reaped. Until the request is in hand the idle timer is what it says -- a peer that dribbles actual request bytes resets it with each byte and, having delivered no request, remains under it as well as under the header and request timeouts above, whose deadlines are absolute from the start of the request. This guard would need revisiting only if a real client could legitimately take longer than the bound to send its upgrade request, which a single small WebSocket handshake never does, or if `ws` stopped resetting the socket timeout on upgrade. A regression test pins that an established connection outlives the bound, and further tests pin that a slow response, a quiet streaming response and a response whose request body was delivered but never read outlive it too, while a client that stalls the body it announced is still reaped on the bound's own clock.

**Limits of the upgrade-handshake bounds.** All three stop at the moment a request is in hand, and the response phase is outside them by design. Nothing here measures whether -- or how fast -- a client takes the response it asked for, so a peer that stops reading holds the connection and the bytes queued for it until the deployment closes them. Node's own timeouts cover what they name, receiving a request and an idle connection between requests. Draining a response belongs to the reverse proxy in front of the application, which buffers a response away from it and applies its own send and read timeouts to a stalled reader (see [DEPLOYMENT.md](../DEPLOYMENT.md#hardening-the-signaling-surface) for the operator's side of that split, including what a directly-exposed deployment does not get). The scoping is what keeps a legitimate response safe: a handler that takes its time, a long-lived response such as the console's job event stream quiet between frames, and a client draining a large body slowly are the shapes an in-application response bound cuts first. Unit checks pin a withheld response, a quiet event stream, and a response whose request body arrived but went unread each outliving the bound, with an HTTPS check pinning the withheld response over TLS as well. The bound is also armed once per connection, when it is accepted and again on the TLS handoff above, and the reap never puts it back. Once a response finishes Node replaces the socket timeout with its own `keepAliveTimeout` (measured on Node 26 as that value plus 1,000 ms of grace), and when the next request on that connection begins Node resets it to `server.timeout`, which is `0` here. So `SIGNALING_PREHANDSHAKE_IDLE_MS` and its precise clock cover the first request on a connection, the keep-alive timeout covers the idle gap between requests, and a later request on a reused connection is covered by the header and request timeouts on the periodic sweep -- coarser than the idle bound's own clock, and the coverage that pair gives on its own. A unit check pins that the harden leaves no bound of its own on a socket Node's keep-alive reaping has taken, and another that a connection handling request after request accumulates no per-request `timeout` listener.

**Per-message size cap.** Each inbound frame is capped at the `ws` layer so an over-cap frame is refused (close code 1009) before the message handler parses it. This control and its constant (`MAX_SIGNALING_PAYLOAD_BYTES`, in the vendored `services/webSocketServer/index.ts`) are specified above under [Signaling-server inbound frame bound](#signaling-server-inbound-frame-bound), alongside the file-sync frame-size bound; it is one of this surface's bounds, closing the single-oversized-frame crash and memory pin from an unauthenticated peer.

**Structural parse bound.** Within that byte cap, each frame is decoded through `@psilink/core`'s `parseBoundedJson`, which refuses a body whose structure exceeds the per-object key, per-array element or nesting-depth ceiling before `JSON.parse` sees it. The relay's reconnect queue reconstitutes a held payload through the same chokepoint. Specified above under [Signaling-server inbound frame bound](#signaling-server-inbound-frame-bound), which states which of the three ceilings a within-cap frame can reach.

**Two-tier liveness reaping.** A registered client that has not yet sent any inbound frame is reaped after **20 seconds** (`unconfirmed_timeout` in the vendored `config/index.ts`); once it sends its first frame it is marked confirmed and governed by the **90-second** `alive_timeout`, refreshed by each heartbeat. The split ties reaping to liveness rather than a flat wall-clock: a socket that registers under the public realm key and then goes silent -- an abandoned or junk registration -- is cleared in 20 seconds instead of squatting a slot for 90, while a real peer is never cut short however slow the human-paced exchange. The reap is keyed on the WebSocket heartbeat, which is independent of and far faster than WebRTC pairing: the PeerJS client sends its first heartbeat one cadence interval after the socket opens and then every interval, so even an inviter that waits minutes for its partner has long since graduated to the generous window. The cadence is psilink-owned, not a transitive dependency default: the web client sets `pingInterval` explicitly to **5 seconds** (`PEER_PING_INTERVAL_MS` in `apps/web/src/psi/transport/rendezvous.ts`) rather than relying on the `peerjs` default, a default parameter inside a bundled file that an upstream version change could shift (an exact-pinned, review-gated `peerjs` bump rather than a silent caret drift -- see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md#upgrading-the-peerjs-stack-peerjs--peerjs-js-binarypack)). The 20-second value is four times that 5-second first-heartbeat cadence, leaving margin for a slow socket open and one missed heartbeat. The unconfirmed window must stay comfortably above the first-heartbeat delay so a real peer always graduates before it fires; that `unconfirmed_timeout >= 4x PEER_PING_INTERVAL_MS` relationship is pinned by a unit check (`test/unit/signalingReaping.test.ts`), so a change to either value -- the reap window or the cadence -- that narrows the margin fails CI rather than only the weaker `unconfirmed_timeout < alive_timeout` invariant. Because the cadence is set explicitly, a `peerjs` minor bump cannot shift it out from under the window; tracking a future upstream default change is a deliberate edit to `PEER_PING_INTERVAL_MS`, which the same check then re-validates against the window. The check guards the numeric margin but not the *meaning* of the cadence. As with the SFTP-stack internal assumptions, a `peerjs` bump must still re-confirm two behavioral assumptions this control rests on: that `pingInterval` remains the sole client-originated liveness signal (the reaper keys only on observed inbound frames, and on an otherwise-idle registered peer the heartbeat is what produces them). A field rename instead is reported as a TypeScript error on the `PeerOptions` literal. It must also confirm that no upstream WebSocket-layer keepalive was introduced that would hold a socket open independently of that heartbeat -- either change would decouple liveness from the cadence the window is sized against, which neither the type check nor the margin check would catch. The check runs on the existing 300 ms sweep (`checkBrokenConnections`), so the effective reap is within ~20.3 seconds. This bounds the cheap fire-and-forget / register-and-idle flood; a flood that keeps each socket alive with heartbeats is bounded instead at the reverse proxy (per-address limiting, see [DEPLOYMENT.md](../DEPLOYMENT.md#hardening-the-signaling-surface)), since the application cannot distinguish it from a live peer. The only in-application ceiling on such a maintained flood is the global `concurrent_limit` (default 5,000 registered clients), which is shared across all clients, so on a deployment with no proxy a maintained flood degrades to global connection exhaustion rather than per-address throttling -- the reason per-address limiting is delegated to the proxy rather than attempted here.

**One socket per registered client.** Registration is keyed on the `id` and `token` an upgrade holds, so a peer that upgrades again under credentials already in the realm attaches to the client that is already there rather than taking a second slot. That attach detaches whatever socket the client was holding, and every in-application close path -- the liveness reaper above, and the per-socket `close` handler that deregisters the client -- acts on the socket the client currently points at, so the attach is where a detached socket's teardown belongs and is where `services/webSocketServer/index.ts` performs it. It terminates rather than closes: a close handshake releases the socket once the peer answers the close frame or, for a peer that never answers, once `ws` gives up on its own close timer -- measured at 30 seconds of retained socket per detach on the pinned `ws`. The detached socket is being replaced by that same peer's newer one and so has nothing to negotiate. The invariant is that no registered client retains more than one socket, so the sockets this surface holds on behalf of registered clients are bounded by the `concurrent_limit` the realm enforces rather than by how many times a peer chooses to attach. Two unit checks pin it (`test/unit/signalingServer.test.ts`): repeated attaches under one id and token leave the live socket set at one and the registration intact -- the registration belongs to the client rather than to any one socket, so a detached socket's close leaves it alone. A detached socket is no longer relayed as its client, the server stamping every relayed frame with the client's id.

**Bounded release of a refused or unanswered socket.** Every other exit that leaves this server holding a socket it will not go on to serve releases it within **1 second** of the point that socket becomes nobody's (`SOCKET_RELEASE_TIMEOUT_MS`, in the vendored `services/webSocketServer/index.ts`) -- a bound on the window the exit opens, not on the connection that brought the peer there. That point is the exit itself, unless the exit leaves a response of this server's still being written on the socket -- the pipelined upgrade covered below -- where it is instead the moment that response detaches. Two shapes reach that bound. The first is a refusal -- a missing or over-length handshake parameter, a wrong realm key, an id claimed under another token, or a registration past `concurrent_limit`. Each writes the peer the frame that tells it why it was refused (the `ERROR` payload naming the refusal, or `ID-TAKEN`) and then closes, so a peer that answers the close frame is released on the handshake; the bound is the deadline on that handshake, past which the socket is terminated. A refused peer is precisely the one with nothing to negotiate and no reason to answer, and without the deadline its socket is held for the `ws` close timer -- the same 30 seconds measured for the detach above -- so an unauthenticated peer that opens refusals and answers nothing occupies each socket 30x longer than the refusal itself takes. One second sits far above the round trip an answering peer needs, having already been written its error frame. The second shape is an upgrade on a path that is not this server's, which it declines so that a co-resident `upgrade` listener -- Vite's HMR handler at `/` on the shared dev server -- can answer it. Node stops auto-destroying an unhandled upgrade once any `upgrade` listener exists, so a declined socket nobody answers is leaked, and the deployment connection idle-timeout is at best a far coarser safety check. Where this server is the sole `upgrade` listener -- the production shape, which the harden above keeps sole by adding no listener of its own -- nothing else can answer and the socket is destroyed at once. Where a co-resident listener exists the socket is left for it and the assumption that it answers is then tested rather than assumed, against what the window itself produced. The socket's written-byte count is snapshotted as the upgrade is declined, and a socket that has written nothing past that snapshot when the bound expires was answered by nobody, so it is destroyed and the broken assumption raised as a server `error`. That counter runs for the life of the TCP connection rather than the window, and this server writes on that connection itself, so two sequences reach the window with the count already holding bytes of this server's own. An upgrade arrives on a connection it has already answered an ordinary request on -- HTTP keep-alive, which any raw client can drive -- so the count is non-zero before the window opens. An upgrade pipelined behind a request in a single write reaches the decline while the response ahead of it is still being written, because Node emits `upgrade` as soon as its parser sees one rather than when the response ahead of it finishes. So the count goes on rising by this server's own bytes for as long as that response runs. Reading either as this upgrade's answer would leave precisely that socket held past the bound with the window's error watch taken off it, which is at once the leak this release exists to close and an unwatched socket for the peer to reset the process out from under. The answer is therefore measured as movement past the count the socket holds once no answer of this server's is being written on it. The count is snapshotted at the decline and snapshotted again if a response of this server's detaches after it, and the bound does not start while one is in flight -- a socket this server is still writing to is its own rather than nobody's, and the decline cannot leak it. Discounting that whole stretch costs an adopter nothing it could have used, an answer written into a response still writing being interleaved with it on the one TCP stream. Whether a response is in flight is asked of Node's HTTP server through the outgoing message it assigns to the socket it is writing on, an internal reference rather than a documented API, so the checks below drive a real server through the whole sequence: a Node that stops setting it fails them rather than quietly restoring the misread. The bound is far above the same-tick answer a real co-resident listener gives, so a socket one has adopted is never taken back from it -- cutting an adopted socket is the HMR teardown the `noServer` wiring exists to avoid. That window is equally the one stretch in which the socket is nobody's -- declined by this server, not yet adopted by any listener, and so having no `error` listener of anyone's. A raw socket that emits `error` with none attached terminates the process, which a peer causes by no more than resetting the connection: being killed, or dropped by its network. It is therefore watched from the decline to the bound. An error in that stretch destroys the socket, which is that socket's release, so the bound behind it has nothing left to reclaim and reports no unanswered upgrade against a peer that merely hung up. The watch runs to the bound rather than to an adopter's answer, so an adopted socket that errors in the residual stretch between the two -- most of a second, an adopter answering in the same tick as the decline -- is destroyed and reported by this server rather than left to the listener that adopted it. Both reports -- the unanswered upgrade, and an error the watch catches -- are raised on this server's own `error` event, each naming the path that raised it as a second event argument. The single instance builder every entry point goes through (`CreateInstanceWSOnly`, which the web app's mount and the standalone broker runner reach alike) attaches the sink that attributes, escapes, caps and rate limits them, and writes each one to the diagnostic sink that builder was handed. Where the lines go is the embedding's -- the runner writes them to stderr, the web app's mount through a prefixed logger -- but whether they are written is not: the sink is a required argument of that builder rather than an option, so an embedding that names none does not typecheck, and both shipped wirings pass one with no flag in front of it. Attaching a listener is critical before the sink is, an `error` emitted with no listener at all being thrown rather than dropped -- which would end the process over the very peer hang-up the watch exists to survive. So the listener absorbs the event whatever the sink does with it, a sink that throws being caught there rather than allowed back out through `emit`. The attribution is what makes the line readable rather than merely present: an unanswered upgrade, an error the release window caught, an error on a socket this server serves, a frame that did not parse, a fault raised dispatching one that did, and a fault the `ws` server itself raised all reach the sink as the same `Error` otherwise. A raise naming none of the six is written under an unattributed arm rather than dropped -- `emit` is untyped, so what arrives as the source is whatever the raise passed, and a source of another type, or a string naming none of the six, is a diagnostic to read rather than a reason to lose one. The source is resolved to one of this module's own tags before it is written, so no byte a raise chose reaches the line at all. The parse and the dispatch behind it are separate attributions because only the first is the peer's. The `try` that reports a client frame covers reading the peer's bytes and nothing further -- the `JSON.parse`, and the stamping of the sending client's id onto its result, which throws on a frame that parsed to a null or a primitive -- while a fault raised once that frame is handed to this server's own `message` listeners is this server's. That second one is reachable rather than theoretical, the relay sizing a frame it holds for an absent destination and throwing on a non-string field, and it is absorbed exactly as the first is -- `ws` calls the message handler from inside its own receiver, where a throw is an uncaught exception and the end of an internet-facing broker. But it is reported as its own attribution, since read as a parse failure it sends an operator looking for a peer sending garbage instead of at the fault. The unanswered-upgrade report can arise only where a co-resident `upgrade` listener sits beside this server, which is the shared dev server and any future embedding that mounts the broker alongside another WebSocket route. That same event holds peer-controlled text, which is why the sink escapes and rate limits rather than writing what it is handed. The frame parser quotes the bytes it choked on, so a registered client chooses part of that line: it is escaped where the line is written (`redactAndSanitizeForDisplay`, at **256** characters), which is the one altitude that escapes. It is placed last, so no byte of it can be read as a field ahead of it or open a line of its own. A client can also loop that failure, so the sink writes at most **10** diagnostics per **60-second** window; the eleventh is shed under a single notice saying so, and the number shed is written with the first diagnostic of the following window, which holds the sink to 12 lines a window without letting a flood pass as quiet. That budget is one budget across the attributions rather than a reservation per attribution, so a client looping parse failures spends the whole of it on `client-frame` and leaves an unanswered upgrade raised in the same window shed. Both notices therefore hold the shed counts by source -- the class the budget ran out on where the shedding starts, the window's whole breakdown where it resumes -- so an alarm a flood starved is named once a later diagnostic writes the resumed notice. A flood that stops and is followed by nothing leaves the starved classes unnamed as well as uncounted, since the resumed notice is the line that holds the breakdown. The window is read off the clock as a diagnostic arrives rather than held open by a timer, so the sink adds no handle to a broker that sits idle between rendezvous; a clock stepped backwards holds the window open until the clock has caught back up, which sheds for longer rather than handing a flood a fresh budget. Every handle the window installs comes off with the window, whichever way it ends: the watch and the close handler that retires it come off at the bound -- where the window concludes the socket was adopted, rather than at the earlier moment the adopter answered. So past the bound an adopted socket holds that listener's bookkeeping and none of this server's. The deadline itself is armed as a handle disposed of exactly once -- expiring or cancelled, never both -- so no release path retires a timer another already retired. Unit checks pin every refusal path, both co-resident outcomes, a declined upgrade on a connection the server had already answered an ordinary request on, one pipelined behind a response the server was still writing, a peer resetting inside the window, and a peer resetting in the residual stretch, once an adopter has answered and before the bound (`test/unit/signalingServer.test.ts`). Each drives a hand-rolled socket that answers nothing at all, so what they measure is the server's own release rather than a `ws` client's cooperation. A further check counts the socket's listeners across a hand-off: past the bound an adopted socket holds the adopter's own and nothing the window added. The sink behind those reports is pinned separately (`test/unit/signalingDiagnosticsSink.test.ts`): a real unanswered upgrade and a real reset inside the window arrive through `CreatePeerServerWSOnly` under their two attributions and not each other's, and a peer's frame reaches the log with its ESC and CR/LF escaped and its forged context trailing the first-party fields. It also pins that a `message` listener that throws on a frame that parsed is reported apart from the parse while a malformed frame from the same client is still the peer's, and that a thousand-report flood raised alongside two released sockets is shed to the budget with its shed counts written per source on the following window. It pins that a clock stepped a whole window backwards goes on shedding until it has caught back up, and that a raise having a source of another type is written under the unattributed arm on the budget slot it spent rather than dropped. It also pins that one having a hostile string source is written with no control byte and none of that source's own bytes on the line. It pins that a single detail of 100,000 escape-expanding code points is written truncated rather than at six times its own length, and that the listener still absorbs the event under a sink that throws. That the diagnostics reach stderr alone, leaving the standalone runner's stdout ready-line protocol clean, is held beside the CLI's broker-process harness (`apps/cli/test/signaling/brokerProcess.ts`) rather than in the web unit suite, where vitest intercepts `console` above the streams and an assertion would be vacuous. The harness watches the spawned runner's stdout for the child's whole life rather than up to the ready line, since a diagnostic arrives only once a peer has given the broker something to report. Anything on that stream which is not the one `psilink-broker <port>` line -- or a leading part of it a chunk boundary split -- fails the start, and fails the suite on the harness's stop if it arrived after it. What keeps that from passing on a broker that logged nothing at all is a check in the CLI's broker suite (`apps/cli/test/integration/webrtc/broker.test.ts`) that has a registered peer raise a real parse failure first, then reads it off stderr with stdout still holding its one line.

**Relay queue bounds.** When a client addresses a signaling message to a destination id that is not currently registered, the relay holds it briefly in a per-destination queue for a reconnect. Left unbounded, a registered client could spray messages to arbitrarily many made-up destination ids -- each allocating a queue -- or grow one queue without limit. The realm caps the number of distinct queued destinations at **1,000** (`MAX_OUTSTANDING_QUEUES`) and the depth of any one queue at **100** messages (`MAX_MESSAGES_PER_QUEUE`), both in `models/realm.ts`; a message past either bound is dropped. Both sit far above any legitimate rendezvous, which queues at most a handful of frames for a momentarily-absent peer, so a drop only ever affects a spammer or a peer already far past needing a reconnect hold.

The message-count cap alone, though, leaves a queue's resident ceiling high: a frame is capped at 256 KiB on the wire (`MAX_SIGNALING_PAYLOAD_BYTES`), but V8 stores a JavaScript string as two bytes per character whenever it holds any non-Latin1 character (>= U+0100). So one buffered frame can occupy roughly **512 KiB** of heap -- about **50 MiB** per queue (100 frames), **50 GiB** across the full 1,000 -- since a flood of max-size frames is bounded only in count, not bytes. A third bound, **524,288 bytes** (512 KiB, `MAX_QUEUE_BYTES` in `models/realm.ts`), caps each queue's total buffered bytes directly: before a frame is queued, its resident size is added to the queue's running total, and the frame is dropped if that would exceed the cap. The size is measured as UTF-16 code units times two, not UTF-8 -- a UTF-8 measure would undercount a non-Latin1 payload by up to 2x and let it occupy roughly twice its measured size, so counting the worst-case two-byte residency bounds the real heap regardless of payload charset. This holds the per-queue ceiling at 512 KiB and the global ceiling at about **512 MiB** (1,000 queues x `MAX_QUEUE_BYTES`). The cap is twice the wire frame cap, which holds a frame whose payload arrived as a string exactly up to a 33-character `src`: it is held exactly as it arrived. So its accounted residency is at most twice its wire size only within that bound, and the largest wire-legal one between two 32-character rendezvous ids accounts to 524,286 bytes, two under the cap. `src` is stamped after the wire cap is checked, so a longer legitimate id pushes the same frame over -- 6 bytes over with a 36-character UUID `src`, 446 over with a 256-character one -- and it is dropped, benignly costing only that sender's own reconnect hold. A structured payload is held by its serialized form instead, whose length the wire cap does not bound, so holdability there is not exact: re-serializing what a peer sent can inflate it (an array of `1e21` literals re-serializes about 1.2x, since each is reprinted as `1e+21`, so accounted bytes can reach roughly 2.4x the wire bytes). Even the maximal 262,144-byte wire-legal object frame between two 32-character rendezvous ids accounts to 524,290 bytes against the 524,288-byte cap and is dropped. That is a stated limit at the size extreme rather than a bound on real traffic: real signaling payloads are KB-scale, so a queue still holds dozens, and a drop costs only that sender's own reconnect hold, never the accounting's integrity. A queue drained by a reconnecting peer releases the read frames' bytes from the running total, so it accepts fresh frames again rather than staying wedged at the cap. The ~5-second read-cold expiry (the `MessagesExpire` prune) still clears an unread queue regardless, so these caps bound the transient peak within a window rather than a permanent residency.

**Structured payloads.** Every real signaling payload -- an SDP offer or answer, an ICE candidate -- reaches the relay as a parsed JSON object rather than a string, and a parsed object's heap residency runs a large multiple of the bytes that held it, so a queue holding parsed frames would be bounded by `MAX_QUEUE_BYTES` in name only. The queue therefore holds each frame in **serialized form**: `serializeFrame` (in `models/messageQueue.ts`) stringifies the payload once, on the way in, and accounts the frame at the UTF-16 residency of the four strings it then holds -- `type`, `src`, `dst`, and the serialized `payload`. A payload that arrives already a string is the one exception: it is held exactly as it arrived rather than JSON-quoted, because the two quote characters are residency it never held on the wire. The largest wire-legal frame addressed between two 32-character rendezvous ids accounts to within two bytes of `MAX_QUEUE_BYTES` -- charging it for quotes it did not hold would refuse it and break the holdability property above. Each held frame records which of the two forms its payload took, and delivery reconstitutes it accordingly. The accounted bytes are the held bytes, so `MAX_QUEUE_BYTES` bounds the memory a queue actually retains and the per-queue and global ceilings above (512 KiB and about 512 MiB) are the real ones. That pairing is confirmed rather than trusted: `addMessage` re-measures the frame it is handed and refuses a caller-supplied size the frame does not match, so no enqueue can charge a queue a size other than the residency it goes on to hold. The relay path passes what `serializeFrame` measured and so agrees by construction; the refusal binds the enqueue call site alone -- `getMessages` returns the live frames array, so an out-of-tree caller that mutates it directly moves residency without charge, a stated limit of the export surface no inbound frame can reach. Only those four protocol fields are held, so an extra property hung off a peer's frame is neither retained nor uncounted. The parsed form exists transiently and one frame at a time: at receive, where the wire cap (`MAX_SIGNALING_PAYLOAD_BYTES`) bounds it, and at delivery, where a frame held as JSON text is parsed back before it is relayed -- so a peer draining a hold receives what a directly relayed frame would have contained. Serializing at the queue boundary changes nothing observable: the direct relay path serializes the frame on its way out regardless, so JSON's coercions reach a held frame exactly as they reach a relayed one. Two frames never reach the queue at all -- one whose `type`, `src`, or `dst` is not a string (those are ids, and a non-string one would key a queue or poison the running total), and one whose payload has no JSON form and so no residency to account. Each is refused before it is queued, and the refusal is reported as a `frame-dispatch` diagnostic; the three id fields are checked before the payload is serialized, so a frame refused for one of them never pays a quarter-megabyte serialization first and the refusal names the `dst` the peer chose. A frame that instead clears the id checks and is only later dropped for the byte cap has already paid that serialization -- measured at about 0.76 ms for a 261 KB frame, roughly +44% atop the receive path's existing parse cost, with no new amplification. The drain is guarded the same way: reconstituting a held frame is a parse, and a frame whose held text does not parse is dropped down that same diagnostic route while the rest of the hold is still delivered, rather than throwing out of a connection handler `ws` calls with nothing between it and the socket. Only the `dst` leg of that refusal is reachable from the wire: `dst` rides inside the peer's own frame and is whatever its JSON put there. The others are defense-in-depth invariants of the enqueue call site rather than paths a peer can drive -- `src` is stamped by the server from the length-capped handshake id, a non-string `type` matches no entry in the handler registry and so never reaches the relay at all, and a payload parsed out of an inbound frame is JSON-serializable by construction.

**Peer-id length cap.** The per-queue byte cap above sizes a queued frame by its string fields' resident bytes, `src` included -- and the server overwrites `src` with the connecting client's own id (the `message.src = client.getId()` stamp in `services/webSocketServer/index.ts`). That id arrives as the `id` query parameter of the WebSocket upgrade request and, left to itself, is bounded only incidentally by Node's ~16 KiB HTTP header-size limit on the upgrade URL, not by any application bound. So a peer that registers a multi-KiB id and then addresses a near-maximum-payload frame to an absent destination produces a single frame whose `src` alone pushes it past `MAX_QUEUE_BYTES`. The string-payload holdability above rests on a queued frame's residency staying within twice its wire size, and an unbounded `src` breaks that for a frame of any payload kind rather than only at the size extreme. The same unbounded id is also retained in the realm `clients` map, a standing per-client memory surface (up to the `concurrent_limit` default of 5,000 ids x the incidental ~16 KiB ~= ~80 MiB). Each upgrade-handshake parameter -- `id`, `token`, and `key` -- is therefore length-bounded to **256 characters** (`MAX_HANDSHAKE_PARAM_LENGTH`, in the vendored `services/webSocketServer/index.ts`) where it is parsed in `_onSocketConnection`, before the id is stored in `clients` or used as `src`; an over-length parameter is refused with the same error-frame-and-close (`WS_PARAMETER_TOO_LONG`) as a missing one. The cap sits far above any legitimate id -- psilink's rendezvous ids are 32 hex characters (`deriveRendezvousPeerId`) and a PeerJS default id is a UUID (~36), so 256 is ~7x any real id and refuses no legitimate peer -- and well over an order of magnitude below the incidental header limit (~64x).

The `id` bound is the critical one: it holds the `src` contribution to a queued frame at most `2 x MAX_HANDSHAKE_PARAM_LENGTH` = 512 resident bytes, a negligible fraction of the 512 KiB queue cap, so a real KB-scale frame from any accepted id stays holdable. (The byte cap's drop of an *adversarial* near-256-KiB frame is unaffected and stays benign: it loses only that peer's own reconnect-hold frame, never desyncing the accounting or amplifying memory.) `token` and `key` are bounded at the same parse point for a uniform "no handshake parameter is unbounded" invariant: `token` is likewise retained per-client in the `clients` map (the same standing-memory surface the id presents, which the cap cuts to ~5,000 x 512 bytes ~= ~2.5 MiB), while `key` is only compared against the realm key and never stored, bounded for symmetry. The addressed destination id (`dst`) is left unbounded here, not an overlooked sibling: unlike `src` -- which the server appends after the wire-frame cap is checked -- `dst` rides inside the client's own frame and is therefore already within the 256 KiB wire cap. Its residency both as a queue-map key and as a counted frame field is already governed by `MAX_OUTSTANDING_QUEUES` and `MAX_QUEUE_BYTES` with the read-cold expiry, so a separate length bound would be redundant. As net-new security behavior on an internet-facing surface, this control is subject to the explicit security review required by [CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy) before release.

# WebRTC data-channel inbound bound

The bounds above cover the signaling *socket* -- the broker the two browsers rendezvous through. The PSI payload itself never crosses that socket: it flows peer-to-peer over the WebRTC *data channel*, which is the surface this bound covers. The adversary here is the exchange counterparty, a mutually-distrusting peer (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model)) -- authenticated by the P-256 handshake, but free to be hostile or buggy thereafter. The data channel is end-to-end confidential under DTLS, so neither the broker nor a TURN relay is in scope; the peer is.

No existing control reaches this transport. The web path discards the rotated key and declines the application-layer AEAD wrap under DTLS (`apps/web/src/psi/authenticateExchange.ts`, `requestEncryption: false`), so core's `EncryptedMessageConnection` and its ~512 MiB `MAX_FRAME_SIZE_BYTES` envelope -- a file-sync transport control -- never bind on the web path. (If deferred web-encryption work ever forces the AEAD wrap on, that envelope would come into scope and could subsume part of this need; while the wrap is declined, this control stands on its own and waits on no encryption rework.) The only inbound limiters that do apply are core's count/structure bounds on the *parsed* payload-exchange message (the web wire is BinaryPack, not JSON, but those bounds act on the deserialized structure either way) and the `QueuedMessageConnection` message-count capacity -- none a byte-size bound. The large raw PSI set frame -- one party's full encrypted set as raw elliptic-curve points, **35 bytes per element** on the wire (see [PROTOCOL.md](PROTOCOL.md#the-memory-ceiling-and-the-csv-intake-cap)) -- is sent as a single binary `Uint8Array` that, left unbounded, PeerJS reassembles with no byte cap.

The control is in two halves. Its transport-agnostic half -- the fixed constants below and the `scanFrameStructure` structural pre-scan they parameterize -- lives in `@psilink/core` (`packages/core/src/connection/binaryPackBounds.ts`), so every WebRTC transport enforces one implementation of them rather than a per-transport re-derivation. Its transport-coupled half -- the wrapping of a specific reassembler's internals, which is where the bounds are actually applied -- lives with that transport: for the web that is `apps/web/src/psi/transport/boundedReassembly.ts`. The control bounds the receive path on several axes, each a fixed constant (not a configurable option, since a configurable bound risks being raised to reintroduce the denial of service) and each fail-closed with a terminal `protocol` `ConnectionError` -- the same class as core's inbound-buffer overflow, since every bound sits far above any legitimate frame so an over-bound frame is never benign. Each refusal names the rule that fired -- the retained-byte budget, the nesting-depth cap, the per-string cap, the byte-backed-elements check, or the map-key rule -- so the failure an operator (or a support thread) reads identifies the control that refused the frame. The wording of those five rules is rendered once in `@psilink/core` (`describeFrameStructureRefusal`), so both transport halves word each of them identically, and is composed from that rule's own fixed limit: no length, count, depth, or byte the peer chose reaches an operator through it. (The wire-byte and chunk-count caps below compose their own predicates at each transport, from the same fixed limits.) PeerJS chunks a binary frame larger than its ~16 KiB MTU into slices and reassembles them in `_handleChunk` (accumulating slices keyed by message id, `_chunkedData`), and `unpack`s every frame -- an unchunked one directly, or the reassembled buffer on completion -- into a JS structure in `_handleDataMessage`. It has no cap on any of total wire bytes, deserialized structure size, retained chunk count, or concurrent reassemblies, and no eviction of a never-completed partial. `boundChunkReassembly` wraps *both* methods to add all of these *before* delegating to the original, so the offending chunk is never stored and the offending frame is never unpacked. Wrapping `_handleDataMessage` -- the sole unpack point, which both an unchunked frame and the reassembled-completion path flow through -- rather than only `_handleChunk` is critical: the deserialized-structure attack below needs only a tiny frame, which is sent unchunked and never reaches `_handleChunk`.

**Wire-byte cap.** A running total of bytes across all in-flight reassemblies is bounded by **`MAX_WEBRTC_FRAME_BYTES` = 268,435,456 (256 MiB)**; a slice that would push it over fails closed rather than allocating proportional to the peer-chosen size. The total spans every in-flight reassembly, so this single bound caps a single oversized frame, a single big never-completed partial, and the aggregate of concurrent partials alike. Like the file-sync frame-size cap it is a chosen memory bound rather than a derived platform ceiling, but sized against a different envelope: this one is a browser-tab *memory envelope*, in the spirit of the directory-listing cap -- above the realistic largest legitimate frame, below a tab-crashing allocation. The largest legitimate inbound frame is the raw set frame above, sent as binary with no base64url 4/3 inflation (both this wire and the file-sync wire send a frame as raw bytes). The 100 MiB CSV upload cap (`MAX_CSV_FILE_BYTES`) bounds a set to at most a few million unique key values, tens to low-hundreds of MiB at 35 bytes per element. So 256 MiB -- which at that element size admits about 7.67 million elements -- sits above any realistic set while half the file-sync 512 MiB cap in deference to the tab's smaller heap. This counts *wire* bytes; the deserialized structure those bytes unpack to is bounded separately, next.

**Deserialized retained-byte budget.** The wire-byte cap alone is insufficient, because BinaryPack `unpack`s a frame into a JS structure *synchronously, before delivery and before any schema validation*, and that structure can be far larger than the wire. BinaryPack encodes an empty object or array in one byte but `unpack` allocates a real JS value per element, and the *retained* cost of that value varies by kind. Worse, an `array32` header eagerly allocates `new Array(N)` for its declared count *even when the elements are absent*, because `unpack` reads past the end of the buffer as zero rather than throwing. So a tiny wire frame of object/array headers -- an in-protocol shape, since the association-table and mapped-element frames are arrays of numbers/objects -- could deserialize to many GiB, and a flat per-value count would charge the heaviest kind no more than the lightest.

Before delegating to `unpack`, `scanFrameStructure` scans the frame's BinaryPack bytes and **sums each declared value's per-kind weight** (`WEBRTC_VALUE_WEIGHTS`):

| Kind | Retained weight charged |
| --- | --- |
| object | 64 bytes |
| array | 40 bytes |
| scalar -- one backing slot, charged per declared child at its container's header (an integer, boolean, or null allocates nothing beyond it) | 8 bytes |
| boxed number -- a number marker wider than 16 bits (`float`, `double`, `uint32`, `int32`, `uint64`, `int64`), charged on top of the container slot the value already occupies. A number the slot cannot hold -- a fractional value, or an integer past the engine's small-integer range -- is held in a heap number beside it, measured ~24 bytes with its slot, and a numeric array that would store its numbers unboxed is forced to per-element boxing by one non-number mixed in. The charge is decided by the marker rather than the decoded value, so the model reads the wire alone rather than resting on where an engine draws that range (the narrower number markers are inside it on any engine); it over-charges a small value written in a wide marker, the conservative direction | 16 bytes |
| string | `16 + 2/byte` (a SeqString header plus its UTF-16 characters) |
| `bin`/`raw` -- the fixed overhead of the per-value copy `unpack_raw` slices from its input (a `Uint8Array` view on the chunked and CLI paths, a bare `ArrayBuffer` on the browser's unchunked path), charged on top of the container slot the value already occupies. The payload that copy wraps is charged nothing here: it is ~1x the value's wire bytes, so the wire-byte cap bounds it (as it does a set frame, which is one such value). The overhead does not vary with the payload: the copy measures ~232 bytes resident at its view-shape worst (~104 as a bare buffer) even for a one-byte payload, the view shape sharing its floor with the retained chunk below | 256 bytes |

It rejects if the running cost would exceed **`MAX_WEBRTC_FRAME_STRUCTURE_BYTES` = 1,073,741,824 (2^30, 1 GiB)**, the structure nests deeper than **`MAX_WEBRTC_REASSEMBLY_DEPTH` = 256**, or any map key is not a string (below). The scan reads only container headers and scalar length prefixes -- never materializing the payload, so it skips a large binary set frame in O(1). As it walks, it enforces the running weighted cost (the root plus all containers' children, so a value already committed by an ancestor or earlier sibling is counted, not just the current container's). It also enforces that no container declares more elements than the bytes that follow it can encode (each element needs at least one byte, so this ties the value count to the wire size). An over-budget frame is caught at the offending header before `unpack` allocates; a read past the end (a truncated frame that passed both checks) is delegated, since its committed structure is already bounded and PeerJS's unpack errors on it.

One of those charges falls where `unpack` allocates rather than where the wire spends bytes, because the two diverge:

- **A container's backing slots are charged at its own header, from its declared count.** `unpack_array` sizes its store from that count before reading a single element (`new Array(size)`), and `unpack` reads past the end of the buffer as zero rather than throwing, so a declared array child that no wire byte backs still costs its slot. `unpack_map` builds a plain object by per-entry assignment with no upfront reservation (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)), so its header-time charge is a conservative bound on the store it grows rather than the reservation itself. The charge therefore sits at one header rather than on each child, which is where the wire may or may not spend bytes. The "elements are backed by the bytes that follow" check is a separate and weaker tie between a declared count and the wire size, not a substitute for this one.

- **A map key that is not a string is refused, not costed.** `unpack_map` assigns `map[key] = value`, so a key that is not already a string is retained as its *coerced string form*: a container key coerces to the joined string forms of every value below it, including the declared descendants `unpack` zero-fills past the end of the buffer. That name's size therefore grows with what the frame *declares*, not with the bytes it spends, so no charge taken as the scan walks bounds it -- a sub-megabyte frame of nested `array32` headers at a key position coerces into a property name of hundreds of megabytes. The scan therefore rejects the frame outright, at any budget, the moment it reads a map key whose marker is not a string marker, and it decides on that marker byte alone, before descending into the key -- so a truncated frame cannot get one past the check. A string key needs no charge of its own: it *is* the property name, and its string weight already charges it in full.

Refusing is safe because no legitimate frame holds such a key: the pinned packer emits a map only for a plain JS object, whose own keys are strings by construction, and refuses a `Map` or `Set` outright. That is a dependency assumption, so it is enforced as a check rather than recorded here alone -- the differential suite packs every value psilink sends on the data channel with the real packer and requires the scan to accept each (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)).

*Why this budget value.* The budget is derived from the largest legitimate frame's *retained* cost. That is the mapped-element frame (`Array<{theirIndex, iteration}>`, one entry per matched record), which `unpack`s per record to one object (64) + its slot in the root array (8) + the object's four declared slots (8 each) + two key strings ("theirIndex" 16+20, "iteration" 16+18) ~= 174 bytes under the weights above. It adds the boxed-number weight (16) once `theirIndex` passes 65,535 and the packer writes it in a `uint32`. That is a per-record cost a unit test pins against the real frame shape, and an index width the differential suite pins against the real packer. `MAX_WEBRTC_FRAME_STRUCTURE_BYTES` = 2^30 therefore admits a mapped-element frame of about 5.65 million matched records at that 190-byte cost, and more of the narrower-indexed records below it. This path enforces that budget and the wire-byte cap above, and no element-count ceiling: the two are independent bounds, and no headroom relation between them holds at the measured per-element size. At the 35 bytes an encrypted element occupies on the wire (see [PROTOCOL.md](PROTOCOL.md#the-memory-ceiling-and-the-csv-intake-cap)), a set frame filling the 256 MiB wire cap holds about 7.67 million elements, whose mapped-element frame would reach about 1.36 GiB and be rejected here -- so an exchange the wire cap admits is not thereby guaranteed acceptance on a downstream frame.

*Why the weights are set high.* Each weight is set high where the retention it stands for is understood -- every object key string is charged in full, though V8 internalizes repeated property keys to one shared string, and every wide number marker its boxed cost, though a small integer written in one is held in the container's slot. That is because a model an auditor can check is worth more than one resting on V8 interning/representation choices an engine update could change. How closely each weight tracks what `unpack` really retains for its kind is a separate question, left open and stated as such in the residual below.

*Residual.* The budget bounds what the scan *charges* a frame, so the per-frame worst case for the deserialized structure is the budget itself under the weights above -- a modelled envelope, not a measured ceiling on the heap. The differential suites pin the scan to that model rather than the model to the heap: each requires the scan's charge to equal the modelled cost of the real unpacker's own value inventory, both sides scoring by the same weights, so a weight set below what `unpack` retains for its kind is not something they can see. No check here compares a decoded frame's retained bytes against the weight charged for it, and how closely a weight tracks that retention is an open limit of this control, backed only where a measurement is recorded for the kind in question. Under the weights, the frame that reaches the refusal on the least wire (~4.07M declared `bin`/`raw` views, charged 264 bytes each with their array slot) is rejected at the budget after ~4 MB of proportional wire, retaining ~0.79x the budget with empty payloads since the charge exceeds the copy's measured fixed cost. It retains ~1.09x at the family's measured worst (60-63-byte payloads at the same count), the excess being the payloads' ~1x-wire addition below. An all-empty-object frame needs ~16.7M elements and ~16 MiB of wire to meet the same refusal (the per-container byte check ties cost to wire, so a pathological frame is no cheaper than a legitimate one of the same retained size), and either is freed once the schema layer rejects it. A `bin`/`raw` value is charged 256 bytes for the view it decodes to, above the ~232 bytes of fixed cost that view and its buffer have beyond the payload, so the number of views a frame may declare is bounded here. What those views wrap the budget charges nothing for: a payload is ~1x the wire bytes declaring it, so the wire-byte cap is what bounds it. The *modelled* envelope for an admitted frame is therefore this budget plus that payload addition -- under 1.25 GiB at a 256 MiB frame, transient in every case -- a figure the weights yield rather than a bound on what the heap holds. A number-heavy frame is bounded here rather than at the wire cap: the cheapest boxed number is five wire bytes charged 24 with its slot, so a frame filling the budget with them spends ~213 MiB of wire, inside the wire cap, and meets this refusal first. A tighter budget overall would require charging less than these weights do (crediting key-string internalization, or charging a wide number marker by the value it holds rather than by its width). How aggressive to make them, and how far to close the distance between a weight and the retention it stands for, is a security-review judgment, weighed with the queue residual below.

**String-size cap.** The structural budget charges a string its *resident* weight (`16 + 2/byte`), but `unpack_string` builds that string via a per-code-point concatenation whose transient cons-string tree is several times larger again (a ~250 MiB-wire `str32`, whose resident weight stays within the structure budget, measured into the multiple-GiB range *during the build*). The scan therefore refuses any string whose declared length exceeds **`MAX_WEBRTC_STRING_BYTES` = 1,048,576 (1 MiB)**. Binary set frames are `bin` (whose `unpack_raw` copies ~1x its wire size, bounded by the wire-byte cap, not a string), and every legitimate string a PSI frame holds -- the `{theirIndex, iteration}` keys, a `status` value, a payload cell -- is far shorter, so the cap rejects no legitimate frame. The value is orders of magnitude above any of them yet keeps the worst-case build transient in the tens of MiB.

**Retained chunk-count cap.** PeerJS retains each chunk as its own `Uint8Array` (measured ~232 bytes resident even for a one-byte slice), an overhead the wire-byte cap -- which counts only payload bytes -- undercounts, so a flood of tiny chunks could exhaust memory while staying under the byte cap. Each chunk is therefore charged at least **`MIN_CHUNK_RESIDENT_BYTES` = 256** against the byte cap, and the chunks per reassembly are bounded by **`MAX_CHUNKS_PER_REASSEMBLY` = 131,072 (2^17)** -- ~8x the ~16,500 chunks a 256 MiB frame produces at the ~16 KiB (16,300-byte) MTU, so a legitimate frame is never rejected while a tiny-chunk flood is bounded. Legitimate chunks (~16 KiB) far exceed the 256-byte floor, so it never affects them.

**Concurrent-reassembly cap.** The number of concurrent incomplete reassemblies is bounded by **`MAX_CONCURRENT_REASSEMBLIES` = 8**; a new message id beyond the cap evicts the oldest incomplete partial (deleting its `_chunkedData` entry and releasing its bytes). The PSI protocol is strictly lockstep (see [PROTOCOL.md](PROTOCOL.md)) and the data channel is reliable and ordered, so at most one frame is ever mid-reassembly on an honest exchange. 8 is generous headroom, and the cap bounds a flood of partials from many distinct ids -- the metadata-overhead case the byte running-total does not catch, since many tiny partials stay under it. Eviction is silent and non-fatal: a legitimate exchange never has a second partial, so eviction only drops adversarial data, and logging per eviction would itself be a spray-amplified log-flood vector.

**Delivered-frame safety check.** Finally, at the stable `data` event (`checkDeliveredFrameBound`): a fully delivered binary frame (a `Uint8Array`/`ArrayBuffer`) over the byte cap is refused there too, regardless of how -- or whether -- PeerJS chunked it, so the bound holds at the public layer even if the internal reassembly assumption below ever breaks. A parsed object/array is not byte-measured here (the reassembly bounds above govern it before delivery, and core's count/structure bounds after); only binary frames are, which is exactly the raw set frame this is sized for.

The bounds above are *per frame*. A delivered frame is then queued in core's `QueuedMessageConnection`, whose capacity is a message *count* (`DEFAULT_CAPACITY` = 1024), so the aggregate retained across queued-but-unconsumed frames is in principle the per-frame budget times that depth. The queue is **a count bound** rather than a byte one: the lockstep protocol drains one frame before sending the next, so the queue sits at depth ~1 in practice, and a peer that floods frames out of turn trips the count capacity (a `protocol` failure) rather than accumulating. So the theoretical per-frame x depth aggregate requires both proportional wire bytes per frame *and* the consumer to stall, and is the count capacity's concern rather than this control's. A byte-aware queue bound (or a smaller web-transport capacity) would close the theoretical multiplier but buys little against a practical depth of ~1. Unlike the per-frame scan, whose constants are WebRTC-specific, it would land on `QueuedMessageConnection`, which every transport shares, so it is a decision about all of them rather than this one, better made when a transport actually needs it. The per-frame budget is therefore the byte envelope; the queue stays bounded by count.

The wrap reaches past the public `DataConnection` API into PeerJS internals, so it rests on two dependency assumptions a `peerjs`/`peerjs-js-binarypack` upgrade could silently break. The first is the reassembly/unpack shape on the binary/chunked connection class (the one `peer.connect` and an incoming connection use by default): `_handleChunk` reassembling slices keyed by `__peerData` into `_chunkedData` and deleting the entry on completion, and `_handleDataMessage` as the sole point each frame is unpacked (an unchunked frame directly, the reassembled buffer via the completion recursion). This is encoded as a runtime check, not a comment: `assertChunkReassemblySupported` (called before any listener is attached) throws at install time if any of those internals are absent, so the live browser exchange test -- which installs the guard on every web exchange -- fails loud rather than running with no inbound bound. The second is the BinaryPack wire format the structural scan parses (the marker dispatch in `peerjs-js-binarypack`'s `Unpacker.unpack`: fixint/fixraw/fixstr/fixarray/fixmap and the `0xc0`-`0xdf` markers, with maps declaring two child values per pair). A format change there would not silently disable the bound -- a misparse either over-charges (rejecting early, fail-closed) or runs the cursor off the end (treated as a malformed frame and delegated to PeerJS, which would itself error) -- but it would weaken the scan's precision, so re-verify the marker table on a `peerjs-js-binarypack` bump. On a `peerjs` bump, re-verify both assumptions.
