# PSI-Link protocol

This document describes the PSI and PSI-C algorithms, how they are composed to produce a privacy-preserving record linkage, and the wire-level P-256 authenticated key exchange. It does not cover the exchange agreement format that parameterizes the protocol (see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md)), the threat model and authentication design (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md)), or the network layer over which the protocol runs (see [COMMUNICATION.md](../COMMUNICATION.md)). Intended readers are security auditors, external implementors, and developers.

# Privacy preserving record linkage

The PPRL protocol utilizes a base PSI function to repeatedly reveal the size of the sets of shared statistical linkage keys. This reveals to the parties an association map between their shared members and nothing about elements they do not have in common.

## PSI base function

The PSI base function is a lightly modified version of OpenMined's [PSI](https://github.com/OpenMined/PSI). That package implements private set intersection layering over the encryption in Google's [Private Join and Compute](https://github.com/Google/private-join-and-compute) (itself using OpenSSL), written in C++ that is compiled into WebAssembly. The base function divides the two participants into "server" and a "client" roles. At a high level, the steps of the protocol are:

1. Both client and server generate their own private keys which live only in memory for the duration of the exchange. Keys are random scalars in the P-256 elliptic curve group and are generated using OpenSSL.
2. The client initializes the exchange by encrypting their own data with their own private key using a commutative encryption algorithm and then sends it to the server.
3. The server commutatively encrypts both their own data and the client's data with their own private key and then sends both datasets to the client.
4. The client can then remove their own key from their own data, leaving them with client and server datasets encrypted only by the server.
5. A straightforward string comparison allows the client to see which elements they have in common. They can then choose to share the association table back with the server.

The terminology of "server" and "client" derives from OpenMined's PSI implementation and is used here to be consistent with their documentation. However, "server" and "client" are disfavored throughout the rest of this project as there are many other instances of servers and clients, and OpenMined's PSI includes no networking coding. Most often we will want to execute the protocol so that both parties learn the outcome. When it is necessary to distinguish between the two roles, we will instead use *receiver* and *sender* respectively. Both parties state their declared record counts on the terms exchange that opens every exchange, and the role assignment is a deterministic, work-minimizing function computed locally from those counts -- no separate round-trip. The rule, its optimality for both linkage strategies, and how the counts ride the terms exchange are specified in [Role resolution and work minimization](#role-resolution-and-work-minimization) below.

## Linkage keys

Statistical linkage keys are data elements that combine several other inputs into a single value that uniquely represents an individual with an extremely high probability. In this application, the most common data types for linkage keys are social security number, first name, last name, and date of birth. An example linkage key is the last four digits of the social security number concatenated with last name and date-of-birth as a character string.

Linkage keys can be designed to produce links even in the place of data quality errors, for instance by exhaustively generating all transpositions of two digits in a Social Security Number (SSN) or comparing all single-character edits of strings of a fixed length. By repeatedly executing the PSI base function on such keys, two parties execute a fuzzy PPRL. The two examples are not one mechanism: which party expands, and how many candidates the expansion costs, follow from the shape of the expansion rather than from the field it reads. [Which party expands](#which-party-expands-full-variant-and-deletion-neighbourhood-expansions) specifies both cases.

In order to preserve the guarantee that no information is revealed about individuals not in the intersection, linkage keys must be designed to be precise enough (high positive-predictive value) that any match is definitive.

## Matching Algorithms

### PSI

The way in which links are decided depends on whether both parties will receive output. If both do, they can communicate directly and optimize the procedure. For one-to-one mappings, linkage keys are applied in sequence, forming a cascade of deterministic matches: keys are ordered from most to least precise, and at each round only records that match uniquely on that key are accepted as pairs and removed from the candidate set -- the pool of records not yet definitively matched. Inputs without a match, or without a unique linkage key, continue to the next round.

If only one party receives the output, a compromise is necessary. The deterministic cascade above can run with only one party resolving the final association between each party's elements. In that case the other party learns how many records match each linkage key and how many match overall, and learns which of its own records match -- but not the identifiers of the records they match to. Alternatively, the cascade can be enacted entirely by a single party with the other receiving no output at all; then all of both datasets must be processed and sent to the receiver every round, which discloses to that party the existence of matches on less precise keys that the cascade would otherwise have filtered out.

A linkage can also hold several links per record. Which multiplicity an exchange may produce is fixed before the rounds begin by the two parties' [`deduplicate`](../EXCHANGE_REFERENCE.md#linkage_termsdeduplicate) terms: rather than being asked to describe the multiplicity of the exchange, operators are asked whether they want to *deduplicate* their data, since they effectively use their partner's data to group their own. The resolved cardinalities, their matching procedures, and the disclosure a deduplicating match adds are specified in [Deduplicating cardinalities: many-to-X matching](#deduplicating-cardinalities-many-to-x-matching) below.

Unlike traditional PPRL, blocking under PSI is neither necessary nor appropriate. The PSI base function's computational complexity is O(n log n) in the total number of elements rather than quadratic in their product, so there is no cross-product comparison to reduce. Blocking would also compromise the privacy guarantee, by revealing to each party how many of the other's records fall into each partition.

### The memory ceiling, and the CSV intake cap

The practical upper limit on records for browser-based execution is set by available memory, not computation. An encrypted element serializes to **35 bytes** on the wire -- a 33-byte compressed curve point plus two bytes of protobuf tag and length framing -- but its resident footprint during the comparison step is larger. For the non-streaming single-pass strategy that resident cost -- not the wire size -- sets the binding dataset ceiling (see [The single-pass dataset ceiling](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) below). The only part of the algorithm that requires WebAssembly is the commutative encryption, which can be streamed and parallelized over the data.

Ahead of that algorithmic ceiling, the web app applies a CSV intake cap of 100 MB (`MAX_CSV_FILE_BYTES`, `apps/web/src/components/csvIntake.ts`) -- roughly one to two million identifier rows. This is a per-tab *intake* memory budget, separate from the comparison-step cost above: the two coexist during an exchange and are not added to one another. Intake's dominant cost is the parsed row array, retained by reference for the whole exchange (it backs `rawRows` through preparation and the output table), so at typical object-overhead inflation a 100 MB file resolves to a few hundred MB resident, plus a transient parse-time spike. The modern-workstation execution target absorbs that comfortably; a constrained tab would not. The cap is therefore a deliberate, tunable choice against the intake budget -- not a protocol or wire-format limit -- and can be raised as that intake profile is measured.

A browser file larger than `CSV_WORKER_FILE_BYTE_THRESHOLD` (4 MiB, `apps/web/src/psi/csvParseController.ts`) is parsed off the main thread in a Web Worker the app owns (`apps/web/src/psi/csvParse.worker.ts`, constructed via `new Worker(new URL(..., import.meta.url), { type: "module" })`). So the parse itself -- the dominant CPU: tokenizing, splitting, and building the row objects -- runs off the main thread and the tab stays interactive while a large intake parses. The worker does not post the whole parsed row array back in one message: it streams the rows back in batches, so the main thread deserializes the reply in many small, interruptible steps rather than one uninterruptible structured-clone of the whole array. This does not lower the total receive-time cost, only spreads it across many small stalls, so the tab stays responsive even receiving a near-cap intake and the intake stall (the parse-time freeze and the receive-time deserialization alike) is gone rather than merely shortened. The worker derives the batch size from a target source-byte budget per message, so each batch is a bounded slice of the file regardless of row width; the granularity has no protocol or wire-format consequence -- the reassembled `data` and `meta.fields` are identical to a single post however the rows are split. A smaller file -- and the CLI's Node stream, which is not worker-cloneable -- parses inline, where the worker's spawn and structured-clone hand-off would cost more than they save. The worker wraps core's `loadCSVFile` rather than reimplementing the parse, so the non-string-header guard and the `data`/`meta.fields` contract hold identically whichever thread runs it. The parse is accumulated across PapaParse chunks either way, so a file spanning more than one `Papa.LocalChunkSize` chunk yields its complete row set rather than the silently truncated final chunk (which, on a record-linkage input, would be a wrong intersection with no error). PapaParse's own `worker: true` is not used: it spawns its worker by reading the running script's URL, which a Vite production build breaks (the bundled worker mis-applies `header: true`, leaking the first data row into the header). A worker Vite bundles and serves as its own asset survives that build; one PapaParse constructs from the running script's URL does not -- so the off-main-thread parse is restored through the former, and the threshold is a tunable UX budget, not a protocol or wire-format limit. The resulting payload then rides the WebRTC data channel under PeerJS's own message chunking, which already fragments and reassembles payloads far larger than a single frame at any cap in this range -- so the cap has no transport or wire-format consequence.

### Linkage strategies: cascade and single-pass

The cascade above can be realized on the wire in two ways, chosen by the mandatory-consistency [`linkage_terms.linkage_strategy`](../EXCHANGE_REFERENCE.md#linkage_termslinkage_strategy) term (both parties must agree, like `algorithm`; the schema default is `cascade`). Both produce the byte-identical association table; they differ only in how the per-key PSI exchanges are sequenced, and in what one party discloses to the other.

**`cascade`** runs one dependent PSI base-function exchange per linkage key, in sequence: each round's candidate set is the records not yet matched by an earlier key, so a round cannot begin until the previous round's matches are known. The number of network round trips therefore grows with the number of keys. This is the established default, and the strategy the disclosure description above assumes.

**`single-pass`** batches every key into one PSI exchange and has the receiver reconstruct the cascade locally, so the round-trip count does not grow with the number of keys -- which is what makes a multi-key linkage practical over a high-latency channel (file-sync), where a chain of dependent rounds is prohibitively slow. The receiver is the [PSI base function](#psi-base-function) client; the sender is the server. Each party first forms the union of its distinct linkage-key values across all keys and encrypts each distinct value once. Because the reconstruction only ever compares values within a single key's round, a value appearing under more than one key maps to the same encrypted form with no ill effect, and values are not tagged by which key they came from (no per-key domain separation). This would only need revisiting if the reconstruction were changed to compare a single encrypted value across keys.

The two strategies are not interchangeable across every term: a fan-out (`split_on`) is realized under `single-pass` alone. No cascade realization of one is specified, and linkage terms declaring a fan-out under `cascade` are refused at validation rather than narrowed to a single candidate or promoted to the other strategy (see [Fan-out runs under single-pass only](#fan-out-runs-under-single-pass-only)).

The exchange is at most three frames, one per message, regardless of key count -- message 3 is suppressed entirely in the one blindness case below, leaving two. Message 2 packs everything the sender owes into a **single binary frame**: on a high-latency channel each frame costs a round trip (file-sync gates each send on the peer consuming the previous one), so combining the sender's reply into one frame holds the whole exchange at three round trips rather than one per piece. The transport holds one binary blob or one JSON object per frame, never the two mixed, so the record count is packed into the binary frame rather than sent as its own JSON frame.

1. **receiver -> sender** -- the receiver's PSI request over its distinct-value union (encrypted once under the receiver's key).
2. **sender -> receiver** -- a single binary frame packing four parts in order (all integers little-endian):
   - (a) a `uint32` setup length, then the **setup message** -- the sender's distinct-value union, each value encrypted once under the sender's key;
   - (b) a `uint32` response length, then the **response** -- the receiver's request re-encrypted under the sender's key;
   - (c) a `uint32` containing the sender's record count;
   - (d) the **distinct-value index table**, the remaining bytes: an `Int32` array in key-major order (one row per key) of length `keyCount * senderRecordCount`. Each entry, for a (key, record), is the index of the value that record holds for that key -- an index into the sender's distinct values -- or `-1` if the record has no value for that key. The indices are in the setup message's sorted order (see the remapping below). That is the layout for a sender whose records hold at most one value per key; a sender that declares a fan-out ships the same `Int32` array in the ragged, count-prefixed layout specified in [Fan-out matching](#fan-out-matching-multi-value-key-candidates), which is the only part of any frame fan-out changes.
3. **receiver -> sender** -- the resolved association table for the sender's side. This frame is conditional: it is suppressed entirely when the sender is a non-receiving helper (`output.expects_output: false`) that also discloses no payload, so a blind helper never receives -- and so never learns -- its own membership. See **Withholding the sender's table from a blind helper** below.

The sender remaps its distinct-value index table into the setup message's sorted order before sending, so the sorting permutation the setup holds internally never crosses the wire and the receiver's match result indexes the table directly. From the setup and response the receiver works out which of its values equal which of the sender's. It then replays the cascade locally -- over the sender's index table and an equivalent table it builds from its own records, applying the same within-round uniqueness rule and key order the step-by-step rounds use -- to produce the same matched pairs, and returns the sender's half in message 3.

**Withholding the sender's table from a blind helper.** Message 3 exists so the sender learns its half of the association table -- which of its records matched. A non-receiving helper (`output.expects_output: false`) needs that half only to build the payload it discloses for the overlap (`preparePayload` reads its matched rows); a helper that discloses no payload needs nothing back at all, so returning it would leak the helper's own membership -- which of its records the receiver also holds -- for no purpose. In exactly that case, a non-receiving helper disclosing no payload, the receiver suppresses message 3 **entirely** and the sender skips awaiting it, so the helper's process never receives the table and stays blind. The frame is omitted, never sent empty: an empty-versus-populated table would leak the match count by the frame's presence and size, so only suppressing it closes the channel. Both parties derive the decision from the same authenticated session state -- the resolved sender's output entitlement and its payload-intent flag `disclosesPayload`, held on the terms-exchange envelope beside the record count (payload disclosure is per-party-local and lazy, so the receiver cannot infer it and instead reads the sender's advertised flag). So the receiver's suppression and the sender's skip always agree and neither side blocks awaiting a frame the other will not send. A helper that does disclose payload still receives the full table (it reads its matched rows to enrich the overlap -- an intrinsic membership disclosure the honest-but-curious model accepts), and any party entitled to output receives it as before. The full table is delivered to any payload-disclosing helper rather than trimmed to the sender's own row numbers, since the receiver's opaque row numbers are the least-sensitive layer and a helper that already learns its membership gains little from withholding them. This realizes, for the one closeable case, the send-everything pole's ideal that a no-payload helper stays blind; the membership disclosure remains intrinsic and accepted for the cascade and for a payload-disclosing helper (see [docs/notes/one-sided-disclosure.md](../notes/one-sided-disclosure.md)).

**Why the full index table, and the disclosure it implies.** The index table is transmitted in full -- every record, not a pre-filtered set of within-key-unique values -- because whether a value is unique depends on which records earlier keys already matched. A value shared by two records over the whole dataset can become unique once an earlier, more precise key matches one of them, so the receiver needs the complete per-record structure to replay the key order. This is the key disclosure difference between the two strategies. Single-pass hands the receiver the sender's full per-key duplicate structure and complete (encrypted) value set, so the receiver's reconstruction observes matches on less precise keys that the lockstep cascade would have filtered out before they were ever exchanged -- the same disclosure as the single-party variant above ("all of both datasets must be processed and sent to the receiver"). Only the cascade-equivalent table is emitted as the result; the weaker-key matches are visible to the receiver's process but never reported. Single-pass therefore trades this additional disclosure -- plus the extra bandwidth of the full index table and the extra encryption work, since it cannot skip records an earlier round would have removed -- for the constant round-trip count. Because the term is mandatory-consistency (above), that trade is one both parties agree to before any data is exchanged.

**The frame ceiling.** Single-pass cannot stream, and its single frame imposes a much tighter dataset ceiling than the streaming cascade. The cascade processes one key per round, so its working set is a single key's column at a time; single-pass holds every key's values in memory at once and ships message 2 as one frame -- the encrypted setup and response plus the index table's `keyCount * senderRecordCount * 4` bytes. The frame travels as raw bytes (the AEAD and file-sync envelopes do not base64-expand it), so the on-wire frame is essentially its raw size plus a small fixed envelope. That frame is not bounded by the static transport cap: the single-pass reply is bounded by a per-exchange cap **derived from the exchanged record counts and the agreed key count**, identical on both parties, up to a fixed maximum dataset size -- specified, with its two enforcement points, in [The single-pass dataset ceiling](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) below.

**What dominates.** The dominant size term is the encrypted sets, not the index table: with `D` the distinct key-values pooled across all keys, the reply is about `35 * (D_sender + D_receiver) + 4 * keyCount * senderRecordCount` bytes, each distinct key-value costing the 35 bytes given above against 4 bytes per (key, record) cell. What actually binds a single-pass exchange, and the cap derived for it, are in [The single-pass dataset ceiling](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) below.

**Exceeding the ceiling aborts cleanly.** The abort mechanics are specified under [The single-pass dataset ceiling](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) below. The pre-flight gate (`prepareForExchange`) is a coarse one-party shadow of that check, run locally from this party's own row count alone, before any credential, terms, or data are sent; the authoritative two-party check runs in `linkViaSinglePassPSI` once both counts are exchanged. Choose single-pass when the round-trip saving outweighs the ceiling and the additional disclosure; otherwise cascade.

The reference implementation is `linkViaSinglePassPSI` (`packages/core/src/psi/link.ts`); the four PSI base-function operations it composes are on `PSIParticipant` (`packages/core/src/psi/participant.ts`).

#### Partner-supplied index tables are checked against local state

Both strategies exchange association tables, and the cascade additionally exchanges mapped-element lists. Every index one of those contains addresses a position the receiving party owns or counts: its own rows, the per-round candidate set it just encrypted, the partner's rows as counted on the terms exchange, or the partner's masked set for a round, whose element bound is derived from the agreed key count and those same record counts. Each such list is validated before it drives the match set, the payload columns this party discloses, or its [self-attested record](#self-attested-record). The checks:

- the two halves of an association table must contain the same number of entries;
- every entry must be a whole number within the range its side authenticates -- this party's own row count, the size of the set it encrypted for that round, the element bound derived for the partner's masked set, or the partner's row count held on the terms exchange. No entry may repeat, which is what caps a list's length at the count of positions it can address.
- the partner's mapped-element list -- the cascade's inbound list naming which of this party's records the partner matched -- must name exactly this party's own matched records, one entry each, on the round it matched them. The exchange is symmetric, so a round pairs the same number of records on both parties and pairs this party's record only if the partner's corresponding record names it in that same round.
- the returned mapped-element list -- this party's own list handed back with each entry translated into the partner's row space -- must contain one entry per record this party matched, each a distinct row within the partner's counted rows. The round each entry names is not re-checked on the way back, since only the translated row index is read from it;
- at the single-pass boundary where the sender receives the resolved association table, the local half must additionally arrive in ascending order. The cascade produces that order structurally and the receiver sorts this table into it, and the result rows and the exchange record's reconstruction of them read the table in it, so it is enforced at this boundary (`linkViaSinglePassPSI` in `packages/core/src/psi/link.ts`, through the `ascending` rule in `packages/core/src/utils/partnerIndices.ts`) rather than assumed. Under a deduplicating cardinality one of the two halves repeats and the other anchors the length; the rule is in [Deriving one table from the exchanged association maps](#deriving-one-table-from-the-exchanged-association-maps).

Every bound is derived from this party's own data or from a count held on the authenticated terms exchange, never from the frame being checked. A list failing any check is a protocol violation: the exchange aborts with a classified `protocol` error and produces no result, rather than continuing on an index that addresses nothing or a record set the exchange did not produce. The reference implementation is `packages/core/src/utils/partnerIndices.ts` and its call sites in `link.ts` and `participant.ts`.

#### The single-pass dataset ceiling: receiver memory and masking compute

Single-pass exists to collapse a many-round-trip exchange over a minute-scale-latency channel (a 15-minute directory poll, times one dependent round per key, is hours of waiting) into one sweep, at the cost of more disclosure (the receiver sees the sender's full per-key duplicate structure and the weaker-key matches the cascade filters out, above). It is therefore an operator opt-in, agreed up front in the `linkage_strategy` term -- never a default, never selected automatically.

**What was measured.** The harness at `scripts/single-pass-bench.mjs` measures what bounds single-pass. Its `sweep` mode runs a real `linkViaSinglePassPSI` over a relayed pipe with each side in its own process, so peak resident set is isolated per side; its `rates` mode times each masking operation directly. Both also report the WebAssembly linear heap directly -- the harness wraps `WebAssembly.instantiate` before the module instantiates and reads the exported `WebAssembly.Memory` byte length, since `process.memoryUsage().arrayBuffers` does not capture it. And `sweep --gc` forks the children under `--expose-gc` (the same flag the shipped CLI sets, turning on the phase-boundary relief above) and reports the post-GC live heap, so the WASM-heap, live-retained, and transient-peak terms are read off the same run. The measurements drive near-unique keys -- every cell a distinct value, so the pooled distinct count `D = keyCount * rows`, the worst case the ceiling must hold for. The per-value constants below were measured on one workstation-class core (aarch64, single-threaded). The row ceilings derived from them are linear projections of a fit whose measured range tops out near 16k rows (224k distinct values), not measured points, and the constants themselves move as the implementation's allocation churn is reduced (below). The cap therefore does not project receiver RSS at runtime from these constants; it sets a single fixed, conservative budget on the per-party (key, record) cell count derived from them (`MAX_SINGLE_PASS_CELLS`, below), which is non-configurable -- a configurable maximum reintroduces the memory DoS -- and revisited as a one-line change when the per-value peak moves.

**Receiver memory binds single-pass, but as a transient peak, not live data.** The receiver must hold both parties' full encrypted sets resident to run the match -- it decodes the reply, builds its own and the sender's distinct-value index tables, and replays the cascade -- so single-pass is `O(total distinct values)` resident and cannot stream. Two quantities differ by more than an order of magnitude here and must not be conflated:

| Quantity | Scale | Notes |
| --- | --- | --- |
| Live retained memory | a few hundred bytes per distinct value | ~60 B of psilink JS plus ~74 B of transport/IPC wire-buffer copies of the ~35-byte encrypted point (the `arrayBuffers` term). A separate grow-only WebAssembly linear heap (`emmalloc`, never returned to the OS) adds ~100-300 B/value in chunked, super-linear steps, read from the WASM byte length as above. Even summed, ~1.4M distinct values (100k rows at the ~14-key default template) stays well within a 16 GB machine (the grow-only WASM term is super-linear and must be measured directly at that scale). |
| Lifetime peak RSS | ~2-4 KB per distinct value | Transient allocation churn, not retained state. This is the practical ceiling; it moves as the churn is reduced (next paragraph). |

Because the bound is on distinct values, the same live memory reaches millions of rows at 1-2 keys. The practical single-pass ceiling is set by the transient peak, so it moves as the churn is reduced; the live-data wall is far higher.

**Why the peak is kilobytes per value while live data is a few hundred bytes.** The `~2-4 KB/value` is the high-water mark of transient garbage churned during the per-element work, captured because neither V8 nor the WebAssembly allocator (`emmalloc`, grow-only under `-s ALLOW_MEMORY_GROWTH=1`) returns freed pages to the OS. The transient peak is GC-collectable V8 garbage from the per-element marshalling across the JS-to-native boundary, not native WASM memory. It is generated inside the `@openmined/psi.js` binding layer reached through `createServerSetup`/`createClientRequest`/`computeValueMatches`, plus the smaller per-key reconstruction maps `linkViaSinglePassPSI` builds itself, so it sits in V8's heap and answers to GC pressure (an explicit `gc()` at the phase boundaries, or `--max-semi-space-size`), not to `--max-old-space-size`. Direct measurement (forked sender and receiver, GC forced at each phase boundary, `D` of 14k and 56k) shows it: the transport/IPC wire buffers (the `arrayBuffers` term) grow only ~74 B/value and the post-GC V8 heap stays nearly flat, while the lifetime peak grows ~2-4 KB/value. The WebAssembly linear heap grows ~100-300 B/value (a permanent floor, a minority of the peak at this scale). A component decomposition confirms it: at `D` = 14,000, a single process running the four masking ops with no reconstruction holds the WebAssembly linear heap flat at ~16 MB and the post-GC live JS heap at ~20 MB, while RSS climbs ~70 MB above its idle base in pages V8 freed but did not return to the OS.

`linkViaSinglePassPSI` calls `relieveTransientMemory` -- a no-op unless a global `gc` is exposed -- at the coarse phase boundaries (after each masking phase's transients become collectable and after the cascade replay). The CLI launches Node with `--expose-gc` (its Docker entrypoint and the `apps/cli` dev script) so the relief is active there: a measured ~15-18% lower receiver peak RSS at the benched sizes (`D` = 14,000: ~163 -> ~138 MB; `D` = 28,000: ~202 -> ~165 MB). It targets the masking-phase transients, the dominant term; forcing a collection at every cascade key as well recovers a little more but is not done, since the cascade is light integer work beside the curve operations. A browser never exposes `gc`, so the web app does not get the relief and its single-pass ceiling rests on the same conservative cap. The complementary `packages/core` lever -- trimming psilink's own per-key reconstruction churn (`reduceToSingletons` keeps one map plus a recurring-value set rather than three) -- is backend-agnostic and byte-identical, but a minor slice of the peak beside the boundary marshalling, so it does not move the measured RSS on its own.

The live floor the peak cannot drop below is small and `O(total distinct values)` -- the receiver's match is a full sort-merge join over both sets -- but at a few hundred B/value that floor stays well under a GB even at millions of values, far below the memory wall.

**Masking compute is a wall-clock expectation, not a cap.** Masking is one elliptic-curve scalar multiplication per distinct value, exactly linear in `D` (confirmed `D` from 14k to 224k). The rates below are the single-threaded **WebAssembly** backend -- what the browser runs and what `scripts/single-pass-bench.mjs` measures:

| Operation | Rate per distinct value |
| --- | --- |
| First-encrypt a set | ~0.45 ms |
| Re-encrypt | ~0.36 ms |
| Match | ~0.37 ms |

On the WebAssembly backend the two-party critical path is therefore about `1.2 ms * keyCount * rows` -- about 28 minutes for 100k rows at 14 keys, hours at a million. That is the figure the **browser** (WASM-only) has. **The CLI defaults to the native N-API backend, which lowers the per-value curve cost by roughly an order of magnitude even single-threaded (measured ~36x apples-to-apples -- about 12 us versus about 445 us per first-encrypt on one workstation-class core) and is additionally parallelized across cores. So a native CLI run's wall-clock sits well below the WASM figure.** The CLI also runs this masking in a worker thread off the event-loop-owning thread, so a long round does not starve the connection's keepalives and timers; even so, a large round on weak hardware can outlast a strict server idle timeout, which the SFTP session heartbeat defeats (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md)). The web app runs the same masking in a Web Worker off the browser's UI thread, the browser sibling of the CLI offload: it wires a Vite `new Worker(new URL("./psiCrypto.worker.ts", import.meta.url), { type: "module" })` into the same runtime-agnostic PSI worker boundary in `packages/core` (the host-side `WorkerPsiEngine` + the worker-side `servePsiWorker` dispatcher) that the CLI's `worker_threads` worker uses. This keeps the tab responsive and the WebRTC peer keepalives firing during a round, instead of the round freezing the interface. The worker loads its own WASM engine (`@openmined/psi.js/psi_wasm_worker`, the worker-context sibling of the main thread's `psi_wasm_web`) and the exchange's secret key is generated inside it (by `servePsiWorker`'s `createWithNewKey`) and never leaves it; only bytes, value lists, and index lists cross the boundary, so the exchange result is byte-identical to the in-process path. WebRTC has its own liveness, so the browser needs no SFTP-style heartbeat, and a browser never exposes `gc`, so it runs the unrelieved memory peak (above). For a batch or scheduled exchange the wall-clock is tolerable, so it should not *refuse* a dataset -- it sets the operator's expectation and sizes the run window. With receiver memory not the binding wall at target scale (above), this masking compute is the practical limiter past ~100k rows. The cost is shared with the cascade (same primitive; the cascade does *less* curve work when match rates are high, since it drops matched records each round, and about the same at low overlap), so it is not a single-pass-versus-cascade discriminator. It remains the target of a possible curve/library replacement.

**The cap: a (key, record) cell-count budget plus a derived byte cap.** The single-pass ceiling is gated on the receiver's projected memory, which the exchanged record counts and the agreed key count bound -- never on a static frame size. (A "cell" is one (key, record) pair; a party's cell count `keyCount * recordCount` is the worst-case upper bound on its count of distinct (deduplicated) linkage-key values `D`, which is itself never computed or exchanged.) Two quantities, both in `packages/core/src/connection/frameSize.ts`, computed identically on both parties:

- **`MAX_SINGLE_PASS_CELLS` = 3,000,000** -- the per-party budget on the cell count `keyCount * recordCount`. It is **the real ceiling**. An exchange exceeds it (and aborts, below) when either party's `keyCount * recordCount` exceeds the budget. It is a cell-count budget, not a bare row count, because a rows-only cap is off by ~14x between a 1-key and a 14-key linkage at the same memory; it admits ~214k rows at the ~14-key default template and ~3M rows at a single key. **Methodology and value.** The budget is derived from a near-ceiling measurement -- a forked-process run of the real linkage with the phase-boundary churn relief (above) active, at `D` ~= 2M distinct values (the worst-case `keyCount * rows`), not extrapolated from a low-`D` fit. That run put the binding peak -- the *heavier* party, which at scale is the sender (it holds its own encrypted setup plus the re-encrypted request resident at once) -- at ~3.0 GB relieved, the receiver at ~2.0 GB. That sits over a directly-measured grow-only WASM linear-heap floor of ~0.8 GB and ~0.1 GB of retained JS (a live floor near 1 GB, well under the box). Projected to the 3M ceiling the sender peak is ~4.4 GB -- comfortable headroom on a 16 GB target. With the relief active the binding constraint is not receiver memory but the **WebRTC per-frame envelope**: the cap is shared and transport-agnostic. The derived reply byte cap at the ceiling (~251 MiB, below) must stay below `MAX_WEBRTC_FRAME_BYTES` (256 MiB) so a legitimate single-pass reply is never rejected mid-exchange on the WebRTC path. 3M is the largest round value that keeps that envelope from binding. A browser, which never exposes `gc` and so runs the *unrelieved* peak, is expected to hit its own memory wall near the same scale (estimated from the relief factor, not separately measured), so raising further would benefit only file-sync and would require decoupling the cap per transport (a separate change). The true `D` is lower for sparse or repeating keys and is never exchanged (it would leak each key's duplication and sparsity structure -- see [Role resolution and work minimization](#role-resolution-and-work-minimization) below), so gating on the cell-count upper bound is conservative by construction. It is a **fixed constant, not operator-configurable** -- a configurable maximum reintroduces the memory-exhaustion denial of service -- and may be raised only after a further measured reduction of the transient peak, re-derived from fresh measurement (and, past the point where the derived reply cap reaches the WebRTC envelope, the WebRTC reassembly path reworked to fail closed rather than mid-frame).

- **`singlePassReplyByteCap(keyCount, sender, receiver)`**, over each party's authenticated `{ effectiveKeyCount, recordCount }` -- the accepted byte size of the reply frame, a defense-in-depth tightening of the read gate derived from the same authenticated counts so a hostile transport admin cannot pad a small exchange's frame up to the static ceiling. Operation order and rounding are fixed so two independent implementations produce the bit-identical integer. For a width-free exchange, where each party's `effectiveKeyCount` is the agreed `keyCount`, and with `sCells = keyCount * senderRecordCount` and `rCells = keyCount * receiverRecordCount`, the cap is:

  ```
  (40 + 4 + 4) * sCells + 40 * rCells + 256
  ```

  in exact integer arithmetic. Coefficients and their meaning:

  | Term | Coefficient | Rationale |
  | --- | --- | --- |
  | Sender masked value | 40 bytes | Deliberate upper bound on the 35-byte serialized encrypted element (above) |
  | Sender index-table cell | 4 bytes | One `Int32` per (key, record) |
  | Sender candidate-count prefix | 4 bytes | One `Int32` per (key, record), charged on every exchange because a sender's own standardization can put it in the ragged layout with nothing in the agreed terms to show it ([The width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare)) |
  | Receiver masked value | 40 bytes | Same as the sender's masked value |
  | Overhead (`+ 256`) | 256 bytes | Three `uint32` length/count prefixes plus the AEAD and file-sync message envelopes the read gate measures around it |

  Each coefficient is an upper bound, so the cap never rejects a legitimate frame. The receiver enforces it at its transport read gate (`fileSyncConnection`'s `get()` `maxBytes`, threaded via `setInboundFrameCap`), and the sender checks its built reply against the same value before sending -- one computation. It is **transport-aware via per-transport clamps**: file-sync uses the derived cap up to `MAX_FRAME_SIZE_BYTES`; the WebRTC data channel keeps its fixed browser-tab envelope `MAX_WEBRTC_FRAME_BYTES` (256 MiB) at its reassembly read gate (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md)). At the cell-count ceiling the derived reply frame is about 251 MiB -- below both envelopes, though the 256 MiB WebRTC envelope is the nearer one -- so the per-transport clamp does not bind there, and the cell-count budget is what gates first.

Under a declared width a record can hold several values for one key, which falsifies the `keyCount * recordCount` assumption both quantities rest on. The generalization -- the (key, record) cell becomes a **value slot**, `keyCount` becomes the `effectiveKeyCount` both parties derive from the agreed terms, and `recordCount` becomes the count each party declared -- is specified with the width bound in [Fan-out matching](#fan-out-matching-multi-value-key-candidates), with the cell-count budget unchanged in value. It leaves every number in this section unchanged for a width-free exchange.

The receiver additionally validates every count it decodes from the reply against authenticated state before it drives any allocation: the sender's row count packed into the reply must be no greater than the record count the sender held on the terms exchange, and must divide it into a whole fan-out factor. And the index table the frame actually holds must have exactly `keyCount * senderTableRows` entries -- or, from a sender shipping the ragged layout, the cell structure that layout's own checks require ([Fan-out matching](#fan-out-matching-multi-value-key-candidates)).

**Declared PSI element counts are bounded by a wire-format scan before deserialization**, on both the single-pass and the cascade decode paths. `@openmined/psi.js` `deserializeBinary` allocates one JS byte-slice object -- measured ~211 bytes -- per declared repeated `bytes` entry, so a frame within the byte cap yet packed with minimal (~2-byte) entries (up to ~frameBytes/2 of them) would exhaust memory inside `deserializeBinary` itself, before any post-deserialize count could run. The participant (`packages/core/src/psi/participant.ts`) therefore scans the protobuf wire format and counts the declared elements without materializing them (`countDeclaredPsiElements`, `connection/psiElementScan.ts`), rejecting an over-declared frame before `deserializeBinary` is called; the scan stops once the count exceeds the ceiling, so it costs O(ceiling), not O(frame). The ceiling is the smaller of the authenticated `keyCount * recordCount` bound for the relevant party -- the sender's set for a setup, the receiver's for a request or the response that re-encrypts it, via `psiElementBounds` in `frameSize.ts` -- and the absolute `MAX_PSI_DECODE_ELEMENTS` = 16,777,215 (`MAX_FRAME_SIZE_BYTES` / 32, floored). It reads only authenticated session state, so both parties compute it identically and no legitimate frame is rejected. This binds a cascade frame whose partner over-declares its record count and caps the worst-case deserialize allocation at ~3.3 GiB. The scan reads only the stable protobuf wire format but assumes the element list's nesting depth per message kind, pinned by a scan/library equivalence test to re-verify on a library upgrade. See [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md).

**The exact-integer precision of the cell-count gate is a check, not an implicit dependency.** The gate above decides `keyCount * recordCount > MAX_SINGLE_PASS_CELLS`, sound only while that product is exact -- below `Number.MAX_SAFE_INTEGER` (2^53). Every decoded record count has an explicit `MAX_RECORD_COUNT` (1,000,000,000,000) upper bound at its wire schema (`recordCountField` on the terms-exchange envelope, `packages/core/src/protocolSetup.ts`) that guarantees it: with the key count bounded at `MAX_LINKAGE_ENTRIES` (256), the product at both maxima is 2.56 x 10^14, about 35x below 2^53, so it is always exact. The bound is astronomically above any legitimate dataset (the frame cap admits ~15M curve points; the cell budget is 3M), so it never rejects a real count; it makes the gate's exact-product dependency an executable check that survives a future migration to BigInt or a wider numeric type, rather than resting silently on the schema's `.int()` safe-integer ceiling.

**Exceeding the ceiling aborts; it does not route to cascade.** `linkage_strategy` is mandatory-consistency (above), so it cannot change unilaterally mid-exchange. An over-ceiling exchange therefore fails closed with actionable guidance that does **not** recommend cascade (reduce the key or record count, or split the dataset); re-agreeing on cascade is a separate out-of-band step. Because the ceiling is computed from authenticated counts, both parties abort in lockstep before any single-pass frame moves, so neither hangs. The budget is per party, so the guidance is **attributed**: it states each over-budget party's own declared width, record count, and their product -- the quantities the gate multiplied -- names whether this party's own declaration, the partner's, or both reached the budget, and offers the dataset remedies only to a side that can apply them. A party within the budget is told so and is not sent to its own configuration for a limit the partner's declared width reached. The attribution is a label on a verdict both parties compute identically, so the two orientations mirror each other and the abort itself stays symmetric. (Cascade also discloses less, so a silent downgrade would not be a privacy hazard in itself -- the blocker is the consent invariant, that both parties agreed to single-pass specifically, plus the added round trips.) An in-protocol consented fallback remains possible future work, not the default.

This ceiling refuses where the `many-to-many` pair table only [warns above its advisory bound](#deriving-one-table-from-the-exchanged-association-maps), and the difference is what each binding quantity is bounded by rather than a difference in tolerance: nothing in the specified checks bounds the receiver memory this ceiling defends, while the returned-list checks already bound that table at one party's own product. The comparison is stated in full there.

### Matching multiplicity: the (record, value) incidence

A [PSI base function](#psi-base-function) round matches values; an association table pairs records. What joins them is the round's **incidence**: the set of `(record, value)` pairs a party contributes to one linkage key's round, where the record is a row of that party's dataset and the value is a realized linkage-key string that row holds for that key. Both matching multiplicities this document specifies are properties of that incidence, and naming them apart is what lets each be specified once:

- **Values per record** -- how many distinct values one record contributes to one key's round. One in the plain case, zero for a `NULL`/absent realization ([Key input data](#key-input-data)), and more than one where a producer fans the record out: `split_on` today ([Fan-out matching](#fan-out-matching-multi-value-key-candidates)), and `generate_fuzzy_comparisons` when its matching lands.
- **Records per value** -- how many of one party's records contribute the same value to one key's round. More than one is what [`deduplicate`](../EXCHANGE_REFERENCE.md#linkage_termsdeduplicate) asks for ([Deduplicating cardinalities](#deduplicating-cardinalities-many-to-x-matching)). A value several of a party's own records hold is exactly what a one-to-one round cannot attribute to a single record, which is why one-to-one drops it.

**The attribution rule.** A round yields **value-level matches**: pairs of equal values, one contributed by each party. Each is lifted through the incidence on both sides into the **record-level candidate pairs** it implies -- `(s, r)` is a candidate pair when sender record `s` and receiver record `r` each contributed the matched value to that round. Several equal value pairs between the same two records collapse to one candidate pair. Every cardinality and every fan-out rule in this document is a rule about which of a round's candidate pairs are accepted into the association table and which records leave candidacy; none of them changes this lift.

**The two axes are bounded separately, and only one reaches a frame's shape.** A widening on the values-per-record axis raises a party's distinct-value count above the `keyCount * recordCount` assumption every derived single-pass bound rests on, so a producer on that axis owes a per-`(record, key)` width bound and the slot arithmetic derived from it ([The width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare)). It also changes what a frame must be able to express: one cell holding several values. A widening on the records-per-value axis cannot raise a distinct-value count at all -- it only stops values being dropped, and a record still holds its one value per key -- so it moves no derived bound and needs no new cell shape. What it owes instead is a statement of which side holds the multiplicity and how each side's within-round uniqueness rule differs.

The axes are independent and compose: a party may both fan out and deduplicate. Each producer fixes its own width, resolution, and cap; this section fixes only the incidence and the attribution rule they share.

### Fan-out matching: multi-value key candidates

A **fan-out** is a standardization step or linkage-key element transform that realizes one record's value for one linkage key as several candidate values rather than one. Every rule in this section binds `split_on` ([EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#fan-out-multi-value-fields)) and it alone. Both of its authoring surfaces fan out: a fan-out inside a key element's transform contributes its candidates to that element's position in the key's cross-product, exactly as a fan-out on the field feeding the element does, so one semantics and one bound cover both surfaces. `generate_fuzzy_comparisons` is a second producer of per-record candidate sets, expected to reuse this candidacy and resolution machinery when its own matching lands. It already contributes its own factor to the width its key declares and is held to that width, on the exceedance fate of its own ([The width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare)); the candidacy and resolution rules below stay `split_on`'s. The rules below are parameterized by the resolved cardinality ([`deduplicate`](../EXCHANGE_REFERENCE.md#linkage_termsdeduplicate) resolves it, `resolveLinkageCardinality` in `packages/core/src/exchange.ts`) and specify the `one-to-one` case only; a deduplicating cardinality relaxes the resolution's acceptance clause through that same boundary ([Deduplicating cardinalities](#deduplicating-cardinalities-many-to-x-matching)). The design rationale, the alternatives set aside, and what stays open are in [fan-out-matching-resolution.md](../notes/fan-out-matching-resolution.md).

#### Fan-out runs under single-pass only

Fan-out matching is specified for [`linkage_strategy: single-pass`](#linkage-strategies-cascade-and-single-pass). Linkage terms that declare a fan-out under `linkage_strategy: cascade` MUST be refused, at each of the three points the [psi-c refusals](#psi-c) use. Those points are: when the terms are authored or an invitation over them is minted; at the local prepare step, before any credential, terms, or data are sent; and at the agreed-terms run boundary, the first point at which both parties' values are known. `linkage_strategy` is a mandatory-consistency agreed term, so the run-boundary check is a symmetric function of the agreed pair and both parties refuse in lockstep. The refusal is fail-closed: a cascade fan-out is never narrowed to matching on one candidate, never silently promoted to single-pass (the strategy is what both parties consented to), and never run.

One half of that refusal is asymmetric, and where it fires decides what the partner sees. A field-level fan-out is authored in a party's own [data standardization](../EXCHANGE_REFERENCE.md#data-standardizing-transformations), which is per-party and local -- no invitation includes one -- so the partner cannot derive the refusal from the agreed terms, while an element-transform fan-out rides those terms and both parties refuse it in lockstep. The local half MUST therefore be refused at the prepare step, before any connection is opened, so the ordinary case is a configuration failure in front of the operator rather than a partner left waiting. A party that reaches the run boundary still holding it aborts the exchange with the reason, before any linkage frame moves, rather than proceeding into rounds the partner would run alone.

Because [psi-c](#psi-c) is cascade-only, fan-out and psi-c are mutually exclusive by construction: a count-only terms document declaring a fan-out step is refused by the rule above, on top of psi-c's own refusal of `single-pass`.

The single-pass receiver holds the sender's whole per-key candidate structure and replays the cascade locally, so it is the only resolver in the exchange and divergence between the two parties' association tables is structurally impossible rather than mitigated. Why the cascade cannot reproduce these semantics on its existing frames, and what a future cascade realization would have to extend, are in the note above.

#### Value-level round participation

Fan-out widens the values-per-record axis of the round's [(record, value) incidence](#matching-multiplicity-the-record-value-incidence), and the attribution rule that lifts a value-level match back to records is fixed there. Each candidate value is one PSI set entry, and every entry keeps the original row index it came from, so a match resolves back to its source record.

- A record's candidate set for a key is a set: two candidates that realize to the same string collapse to one entry, so a record contributes each distinct value once.
- The within-dataset uniqueness rule applies per value, not per record: a value held by two or more of this party's candidate records in that round is ambiguous and is dropped from the round, while those records' other candidate values remain in it. A record therefore participates with the subset of its candidates that are unique within the round.
- A record whose candidate set for a key is empty -- the `NULL`/absent realization -- sits out that round and remains eligible for later keys, unchanged.
- A record whose every candidate is a within-dataset duplicate participates with nothing, which is the single-valued rule's behavior reached value by value.
- The empty string `""` remains a fully supported candidate value, subject to the same uniqueness rule (see [Key input data](#key-input-data)).
- The single-pass distinct-value union pools candidates across keys exactly as it pools single values today, so a candidate value appearing under more than one key is encrypted once and has no per-key tag.

Because uniqueness is evaluated over the records still in candidacy, a value that is ambiguous in one round can become unique in a later one once the record holding the other copy has left candidacy -- the property the cascade already relies on, restated for candidacy rather than for matches.

#### Removal on a potential match

Round `j` produces a set of value-level matches, which the [attribution rule](#matching-multiplicity-the-record-value-incidence) lifts into the round's **record-level candidate pairs** -- here, `(s, r)` is a candidate pair when some participating candidate value of sender record `s` for key `j` equals some participating candidate value of receiver record `r`.

Every record appearing in any of round `j`'s candidate pairs leaves candidacy for every round after `j`, whether or not the resolution below pairs it. A record that fans out therefore gets one chance to match, on the most precise key any of its candidates matches under, and cannot double-match on a less precise key. A record whose candidates matched but which resolution left unpaired ends the exchange unmatched: the evidence was contradictory, and the cascade's rule is that contradicted evidence does not continue.

#### Record-level resolution: canonical order and tiebreak

The resolution is a deterministic greedy sweep. For each linkage key `j` in the agreed key order:

1. Form round `j`'s record-level candidate pairs as above.
2. Order them lexicographically ascending by (sender row index, receiver row index).
3. Sweep in that order, accepting a pair when neither of its two records has already been accepted in this round, and discarding it otherwise.
4. Accepted pairs enter the association table, attributed to round `j`.
5. Every record in any of the round's candidate pairs -- accepted or discarded -- leaves candidacy for rounds after `j`.

The order is fixed normatively because it decides which of two ambiguous matches wins. Both of its components are role-derived rather than local: sender and receiver are fixed for the exchange by [role resolution](#role-resolution-and-work-minimization), so the order is the same one whichever party evaluates it, and it is the order message 3's local half already holds (that half is the sender's own rows in ascending order, enforced at the single-pass boundary). Nothing in the rule reads a hash-map iteration order, a value's bytes, or an encrypted element's position, so an independent implementation reproduces the same table from the same frames.

The exchange record is unaffected by design: its commitments cover the association table's row-index pairs and the payload values, never key strings ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#commitment-scheme)). The record-level table stays the only committed matching artifact, which is why the determinism of this rule -- not the candidate structure underneath it -- is the critical property.

#### Equivalence with the single-valued cascade

On inputs where every (record, key) candidate set holds exactly one value, the rules above reduce to the existing semantics: each round's candidate pairs form a partial one-to-one correspondence, so the sweep accepts every pair and removal on a potential match coincides with removal on a match. A fan-out-free exchange therefore produces the byte-identical table it produces today, and the two strategies' equivalence claim in [Linkage strategies](#linkage-strategies-cascade-and-single-pass) is unchanged.

For fan-out inputs, single-pass is the only realization specified. The obligation that remains is that any future cascade realization MUST produce the identical table to single-pass on the same inputs -- which is why the resolution rule is fixed here, ahead of that work, rather than left to whichever strategy implements fan-out second.

#### The width bound: a per-key candidate cap the terms declare

One record contributes at most `w[j]` candidate values to linkage key `j`'s round, where `w[j]` is the width the agreed terms declare for that key. Both parties derive the same vector from terms they have both agreed, so no width is exchanged, no party reads the other's declaration, and each holds its own rows to the number the other will hold its frame to. The bound is on the assembled candidate count for one (record, key) -- the cross-product across the key's elements, after the deduplicating set -- and it is enforced by each party on its own rows.

**How a key's width is derived.** `w[j]` is the product over key `j`'s elements of each element's own candidate factor:

- **20** for an element whose `transform` declares a fan-out function (`split_on`). The value is a normative constant, not operator-configurable, for the same reason the single-pass budget is not: it is what a partner-supplied frame's bounds are derived from.
- The kind's **fuzzy ceiling** for an element declaring `generate_fuzzy_comparisons`: the most candidates that kind can realize from one value, counting the value itself. Every kind's count is a function of the width `w` of the value it is handed: `adjacent_years` = 3 (the value and the year either side, whatever its width), `edit_distances` = `w + 1` (one deletion per code point, plus the value), and `transpositions` = `w(w - 1)/2 + 1` (one swap per pair of positions, plus the value). Each is taken at the width the element's own transforms bound its value to (below). An element whose transforms bound no width takes `MAX_FUZZY_EXPANSION_INPUT_LENGTH` = 128, the longest value the expansion accepts at all, and a bound above that is clamped to it, since a wider value is refused rather than expanded.
- An element declaring both contributes their product; an element declaring neither contributes 1.
- **2** for a key declaring `swap`, whatever its elements declare: the receiver assembles the key in the authored order as well as the exchanged one ([Swapped keys](../EXCHANGE_REFERENCE.md#swapped-keys)), so a record contributes at most twice the product above.

**How an element's width bound is derived.** The bound is read off the element's `transform` chain, walked in order, since each step is handed the previous one's output; the last step to fix a width governs. A `substring` with a positive `length`, a `phonetic` code, and a `parse_date` output layout each fix a width from their declared params alone, whatever value they are handed, so each replaces the width handed to it. A `pad_left` fills up to its length and truncates nothing, so it raises a width already handed to it and fixes none by itself. A `null_if` or `filter_regex` returns the value it was handed or drops it, so it passes a width through. Every other step clears the bound, because its output width is not a function of the terms: a `replace_regex` replacement re-inserts the matched context at every match position, a case fold can emit more code points than it read, and Unicode normalization is not length-preserving either. An element left with no derivable maximum takes the 128-character limit above. Both parties read the same agreed terms, so both derive the same bound and the same ceiling from it, with nothing exchanged.

The factors compound rather than taking the larger of the two. The key builder assembles a key from the cross-product of its elements' candidate lists, so a key whose elements both expand realizes their product; declaring the larger would under-declare against what the row builder assembles and refuse honest rows at the width bound.

A party declares the fuzzy factor for a key regardless of the PSI role it goes on to resolve, including for an expansion only one of the two parties executes. The width is fixed by the agreed terms, before either party holds the other's record count, so no party knows its role when the number is fixed and each derives the widest case. The cost is stated rather than closed: a party that does not widen over-declares its slots and can refuse at its own single-pass ceiling an exchange that would in fact have fit -- a permissiveness and frame-size cost, not a correctness one.

**Two ceilings bound the derivation.** A single key's width MUST NOT exceed `MAX_KEY_CANDIDATE_WIDTH` = 1,024, and the sum over the agreed keys MUST NOT exceed `MAX_EFFECTIVE_KEY_COUNT` = 5,120. Terms crossing either are refused where the width is derived -- before any row is read -- rather than dropping or refusing every row later. The per-key ceiling is the count limb of the key-string assembly cap (`MAX_KEY_STRINGS_PER_ROW` = 1,024, recorded in [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md)), so a key the terms declare wider than one row can be assembled for is refused rather than left to drop every row. The sum ceiling is what keeps the slot arithmetic's exact-integer assumption where it has always been (below).

**A party's own standardization declares no width at all.** Cleaning that fans out is per-party and local: the partner cannot see it, and a party that pre-fanned its file outside psilink would present the same wire behavior. Such a party therefore multiplies its declared record count by the fan-out factor and declares no extra width. The factor is 20 when a linkage field read by at least one element of an agreed linkage key is cleaned by a pipeline declaring a fan-out step, and 1 otherwise; a fan-out on a field no key reads contributes no candidates, so it declares nothing. Its per-(record, key) bound is `w[j]` times that same factor, so the two multiply back to exactly the value slots its declared record count buys it. The one consequence to state is that [role resolution](#role-resolution-and-work-minimization) reads the fanned count, so a fanning party declares the larger of the two counts and trends toward sender -- proportionate to the work its fan-out actually costs, and the direction that keeps the declaration safe (below).

**The two producers take different fates on exceedance.** For a fan-out the cap is a drop, specified in the paragraph below. For `generate_fuzzy_comparisons` it is a refusal when no declared fan-out also widened the row: the exchange ends, and the row is neither narrowed to part of its candidate set nor dropped. The drop check runs first, so a row a declared fan-out also widened keeps that warned-drop fate instead of the refusal. What separates them is what the terms declare. A fan-out's candidates are one record's several legitimate values, and dropping the record from that key's round leaves it eligible for the rest. Every candidate a fuzzy element declares, by contrast, is one the consent surface states matches independently. So a row contributing part of its set, or none of it, would match on less than the terms describe, with nothing said. The refusal is also what keeps the declared width accurate: the width the terms declare for a fuzzy key is the cap, so a wider row has no slot to occupy.

A record whose candidate count for a key exceeds that key's width contributes no candidate for that key round, exactly as an absent (`NULL`) realization does, and remains eligible for later keys; the drop is warned to the operator. It is not a run refusal: the transforms are partner-authored while the values expanded are this party's own rows, so failing the run would let a partner end an exchange by authoring a delimiter that shatters one local value. The separate resource refusal on the key-string cross-product (`MAX_KEY_STRINGS_PER_ROW` = 1024) stays where it is: it bounds the allocation of one row's cross-product and binds the candidate producers the width-bound drop does not cover. That gap is multiplicity that reaches the refusal from a producer unlisted in `FAN_OUT_FUNCTION_NAMES` (latent until a registry edit adds one); such multiplicity reaches this refusal rather than the drop, so it stays fail-closed. Where the two meet -- a fan-out whose cross-product is too wide to assemble at all -- the drop wins over the refusal, and it is taken on the projected combination count rather than the assembled set, because the assembled count is not knowable without the allocation that cap exists to prevent.

**How the drops are warned.** A drop is taken per (record, key) on the shape of the terms rather than the size of the data, so terms that put every row over the cap drop every row of an arbitrarily large dataset. A key's round therefore warns at most `MAX_DROP_LINES_PER_KEY_ROUND` = 5 of its drops individually -- each naming the row index, the key, and the bound crossed -- and suppresses the individual line for every drop after that. The round's consumer closes it once it has read as far as it ever will. The rows a round is asked for are the consumer's to know rather than the round's (the cascade reads only the rows still unmatched after the previous key). The close emits one line that states that key's dropped total and how many of those rows the individual lines did not cover. A round that dropped nothing, or few enough that every drop was reported individually, closes silently, and a close repeated with no further drops emits nothing. A round that drops further rows after a close reports them at its next close as a count of additional rows against the total the previous line stated, the individual-line allowance being already spent. The coalescing covers the drop warning alone: the advisory raised for a wide per-record expansion that is not a drop -- the same count reported for a record no declared fan-out producer widened, which stays in the round -- keeps its per-row shape, one line per record. No line names a value from either party's rows.

**Why the bound is not optional hygiene.** Every derived single-pass bound rests on the assumption that `keyCount * recordCount` upper-bounds a party's count of distinct linkage-key values (see [The single-pass dataset ceiling](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute)). A width falsifies that assumption: a record can hold several values for one key. The cap restores it in a form still derivable from the agreed terms and the exchanged counts, by replacing the (key, record) cell with a **value slot** -- one candidate value one record contributes to one key round:

- `effectiveKeyCount` is `sum(w[j])` over the agreed keys. It equals `keyCount` exactly when no key's elements declare an expansion, and it is the same number on both parties, since both derive it from the same agreed terms.
- `slots = effectiveKeyCount * recordCount` is a party's authenticated upper bound on its distinct-value count `D`, over the record count that party declared. It replaces `keyCount * recordCount` in every derived bound: the per-party single-pass budget (`MAX_SINGLE_PASS_CELLS`, a budget on value slots, unchanged in value), the per-message PSI element bounds (`psiElementBounds`: the sender's slots bound a received setup, the receiver's bound a received request or response), and the reply byte cap below.

The budget therefore buys width with rows, and what it admits depends on the whole template rather than on the widened key alone. In the ~14-key default template, one key with a fan-out element gives `effectiveKeyCount` = 33 and admits ~90k rows where that same template fan-out-free admits ~214k, and a fan-out element on all 14 of its keys admits ~10k. In a one-key template whose single element declares a fan-out, `effectiveKeyCount` = 20 and it admits ~150k rows; whose single element declares `edit_distances` with no transform bounding its width, `effectiveKeyCount` = 129 and it admits ~23k. An element declaring both multiplies the two factors, so its width turns on how tightly its transforms bound the value. An element that splits its cell and then takes a `substring` of 10 characters declares 20 x 11 = 220 and admits ~14k, while the same element with no width bound would declare 20 x 129 = 2,580. That is above the per-key ceiling, so those terms are refused where the width is derived rather than admitting any rows at all. Every row figure here is `MAX_SINGLE_PASS_CELLS` divided by the effective key count beside it. A party whose own standardization fans out declares 20 times its rows, so it reaches the same ceiling at 20 times fewer of them. That is the real cost of a bound that must hold on the worst case, since the true per-record candidate count is data-dependent and is never exchanged (it would disclose the same duplication and sparsity structure the distinct-value count does, [Role resolution and work minimization](#role-resolution-and-work-minimization)).

The reply byte cap becomes, with `sSlots` and `rSlots` the two parties' slot counts and `sCells = keyCount * senderRecordCount`:

```
(40 + 4) * sSlots + 40 * rSlots + 4 * sCells + 256
```

in exact integer arithmetic. The last term is the per-cell candidate-count prefix the ragged index table below holds, and it is charged on every exchange rather than only where the agreed terms declare a width. A party whose own standardization fans out ships the ragged layout while those terms show no width at all, so no function of them can tell in advance which layout a legitimate sender will ship. A read gate that undershot would reject a legitimate frame, where overshooting only loosens defense-in-depth. At the slot ceiling the cap reaches about 251 MiB, still below the 256 MiB `MAX_WEBRTC_FRAME_BYTES` envelope, so the per-transport clamp does not bind and a legitimate reply is never rejected mid-exchange.

**The exact-integer assumption holds where it was.** The cell-count gate's soundness depends on its product being exact ([the ceiling section](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute)). The ceiling binds the sum of the per-key widths at `MAX_EFFECTIVE_KEY_COUNT` = 5,120, so the product with `MAX_RECORD_COUNT` (10^12) is 5.12 x 10^15, still below 2^53 (about 9.01 x 10^15) and so still exact, with about 1.8x headroom. Bounding the per-key width alone would not do: 256 keys at `MAX_KEY_CANDIDATE_WIDTH` would be 262,144, whose product with `MAX_RECORD_COUNT` is 2.6 x 10^17 and loses precision. The invariant that pins the headroom is therefore pinned against the effective key count, and raising `MAX_EFFECTIVE_KEY_COUNT` requires re-deriving it.

#### Which party expands: full-variant and deletion-neighbourhood expansions

A `generate_fuzzy_comparisons` kind, and the `swap` directive beside it, are one of two mathematically distinct expansions, and which of the two a kind is decides how many parties execute it. The classification is total over the kinds, a function of the kind alone, and identical on both parties (`expandsOnReceiverOnly`, `packages/core/src/fuzzyComparisons.ts`). The model, the alternatives weighed, and the involution argument in full are in [one-sided-fuzzy-expansion.md](../notes/one-sided-fuzzy-expansion.md).

**Full-variant enumeration: exactly one party expands.** `transpositions` enumerates every two-position transposition of the value -- all pairs, not adjacent positions alone -- `adjacent_years` enumerates the year either side, and a key's `swap` enumerates the two orders of its named pair. Each is the whole set of values at that distance from the record's own, so a partner holding any one of them meets it on that partner's exact value, with no expansion of the partner's own. A second party enumerating adds no match the first does not already reach: a shared candidate needs one variant from one side, not one from each. What it does add is its own candidate count -- work, value slots, and additional strings that can collide with a third record -- so a full variant is executed on one party alone.

**Deletion neighbourhood: both parties expand.** `edit_distances` enumerates the single-character deletions of the value, which are the values within one edit distance that are shorter than it -- a neighbourhood, not the full variant set. A substitution or an insertion between two records is reached only where each side's deletions meet in the middle, so expanding one side alone would match on less than the terms declare. Enumerating the full variant set instead is not an option at any width: it is the alphabet times the length.

**The expanding party is the resolved PSI receiver.** Where an expansion is one-sided, the party that executes it is the receiver role resolution already determines from the exchanged record counts ([Role resolution and work minimization](#role-resolution-and-work-minimization)) -- the same party the `swap` directive has always been keyed on. This is a local execution choice, not an agreed term: it moves no term, no terms hash, and no wire byte, and both parties compute the classification from the agreed kind. A party that does not expand contributes its exact value for that element.

**The intersection does not depend on which party is the receiver.** Each full-variant expansion is an involution on the pair it relates: `b` is a transposition of `a` exactly when `a` is a transposition of `b`, and the same holds for a one-year shift and for the two orders of a swap. So `a`'s variants contain `b` exactly when `b`'s variants contain `a`, and the two parties' intersection is the same set whichever of them expanded. A recurring exchange whose record counts move may therefore resolve the opposite role between runs and still match the same records. Nothing is built to hold the role steady across runs, and nothing needs to be.

**The width is declared for the receiver case by both parties**, which is where the cost of the asymmetry lands rather than in the matching; that rule and its trade are stated in [The width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare) above and not restated here.

**Two stated limits of the all-pairs enumeration.** First, `transpositions` grows quadratically with the width its element's transforms bound its value to, so an element bounded to more than 45 characters -- an element whose transforms bound nothing included, which takes 128 -- declares a width above `MAX_KEY_CANDIDATE_WIDTH` and is refused where the width is derived, before any row is read. Declaring `transpositions` in practice means bounding the element's value with a `substring`, `phonetic`, or `parse_date` transform. Second, the factors of a key's elements compound, so two all-pairs elements in one key cross the same ceiling at 9 characters each (37 x 37 = 1,369 above 1,024) even though either alone is admissible. Both refusals are on the declared width and so are decided from the terms alone; a row that outgrows an admissible width at run time is refused rather than dropped, because the exceedance is a fuzzy expansion's and the drop is reserved for the declared fan-out producers ([The width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare)). Both declared-width refusals are enforced where the width is derived -- at exchange preparation (`prepareForExchange`) and again at key-read planning in `runExchange`, before any row's keys are built and before anything is written to the wire -- not by the terms schema, which accepts such terms at parse time. A row's overflow on a key that also declares a fan-out producer takes that producer's drop path instead of this refusal, the record contributing no candidate to the key's round; the refusal above is the fuzzy-only key's. No machinery is added for the stacked case: the arithmetic is the author's to satisfy with a narrower bound or a second key.

#### Wire-format deltas: existing frames only, and no version bump

Fan-out changes the content of one frame the exchange already sends. It adds no frame, no field, no round, and no message ordering.

1. **The terms-exchange envelope holds no width.** Every per-key width, and the `effectiveKeyCount` derived from it, is a function of the agreed terms, which both parties hold once the terms exchange returns -- so each derives the other's without a further field or round-trip, and neither is held to a number the other chose. The envelope's per-party integer is `recordCount` alone ([Role resolution and work minimization](#role-resolution-and-work-minimization)), and it is the party's declared count: its rows times the fan-out factor its own standardization declares. That discloses a configuration fact (this party's cleaning fans out, at some scale) rather than a data fact, exactly as a party that pre-fanned its file outside psilink would. A peer that still puts an `effectiveKeyCount` on the frame has it stripped by the non-strict envelope schema and the exchange proceeds on the derived widths: the field held nothing the agreed terms do not, so there is nothing for a refusal to protect.

2. **Single-pass message 2, part (d)** -- the distinct-value index table -- takes a ragged layout when a record may hold several candidates for a key, and is byte-identical to today's fixed-width table otherwise. Two things put a sender into that layout: an `effectiveKeyCount` above `keyCount`, which both parties read off the agreed terms; and the sender's own standardization fan-out, which the receiver recovers as the ratio between the record count the sender declared on the terms exchange and the number of rows the reply itself holds. The frame stays one little-endian `Int32` array; only its interpretation changes. In key-major order, then row order, each (key, record) cell is a `count` word `c` (`0 <= c <= w[j] * f`, with `f` that recovered factor) followed by `c` value-index words, each an index into the sender's distinct values in the setup message's sorted order and strictly ascending within the cell. There is no `-1` marker in this layout: a record with no value for the key is `c = 0`.

3. **The reply's own record count is an upper bound rather than an equality.** Message 2 part (c) states the number of rows the sender's table covers. A sender whose cleaning does not fan out declares the same count it exchanged on the terms exchange; one that fans out declares the rows it holds, against the larger count it declared for them. The receiver therefore refuses a reply declaring more rows than the sender exchanged, rather than any inequality, and recovers the factor as the quotient of the two counts. Cleaning declares one whole step's factor or none at all, so the only quotients an honest sender produces are 1 and 20 and every other reading is refused: a fraction, a factor between them, one above 20, and a reply declaring no rows against a positive exchanged count, which no factor multiplies up to. A sender holding no rows exchanged no records either, and that pair takes the unfanned factor. Every allocation downstream stays sized from the exchanged count, which the over-ceiling gate has already bounded, so the relaxation widens no allocation.

The receiver validates the ragged table against authenticated state before it drives any allocation, in the same order as the fixed-width checks it replaces. The table MUST declare exactly `keyCount * senderTableRows` cells. Each `count` MUST lie in `0 .. w[j] * f`. The running total of counts MUST NOT exceed the sender's slot bound, `effectiveKeyCount` times the record count it exchanged. Each cell's indices MUST be strictly ascending (which is also what rejects a repeated index) and below that same slot bound. The frame MUST end exactly at the last index word, with no trailing bytes. The index bound is the slot bound rather than the sender's actual distinct-value count because that count is readable only from the setup message -- the frame under check -- and every bound here is derived from authenticated session state alone ([Partner-supplied index tables are checked against local state](#partner-supplied-index-tables-are-checked-against-local-state)). It upper-bounds the distinct-value count, so it rejects no legitimate frame; an index between the two addresses no value and simply matches nothing.

Nothing else on the wire changes. Message 1, message 3 (the resolved association table, whose entries are record-level row-index pairs), the withholding rule for a blind helper, and every cascade frame are untouched.

**The ragged layout takes no version bump.** `PROTOCOL_VERSION` holds at 1. A bump is reserved for a wire-incompatible change made once the software is published; pre-publication there are no deployed peers for the [version reconcile](#protocol-version-reconcile-at-the-terms-exchange) to hold apart, so a wire-format delta -- the ragged table included -- ships within version 1, and the existing-frames-only-and-no-bump discipline this section states binds from the first published deployment onward.

That obligation falls due long after this paragraph was written, so it is enforced by a check rather than by the paragraph alone. `npm run check:protocol-version-bump` is inert while the canonical release version (`apps/cli/package.json`) names no release above the pre-publication `0.1.0`. From the release that does, it fails a change to the pinned wire format -- the conformance vectors covering what the linkage rounds put on the wire -- that includes no `PROTOCOL_VERSION` bump, naming this paragraph so the change takes the version decision. Which vectors it pins, and what it cannot see, are in the script's own header; the pin recorded per published version is `scripts/protocol-version-pins.json`.

**What no version gate separates.** A build predating the delta advertises this build's version, and a width-free exchange with it is wire-compatible at the frame level: it includes no field this build refuses, and any `effectiveKeyCount` it still sends is stripped by a schema that does not declare the key. A sender under no width and no local fan-out ships a message 2 byte-identical to the fixed-width frame. An element-transform fan-out rides the agreed terms, which a build predating the capability refuses through its own terms validation. A fan-out authored in a party's local standardization rides no agreed term that validation could refuse, so a peer that cannot read the ragged table meets it as a frame-parse failure mid-exchange rather than as the version diagnosis. Both builds advertising 1, the reconcile separates no such peer: what it separates is a peer advertising a version other than this build's, or none it can read at all ([Protocol-version reconcile](#protocol-version-reconcile-at-the-terms-exchange)). Pre-publication there is no such peer in the field to meet, which is what makes holding at 1 free; a delta of this shape landing after publication takes a bump.

#### The disclosure delta fan-out pays

Single-pass already hands the receiver the sender's full per-key structure and complete encrypted value set (**Why the full index table** in [Linkage strategies](#linkage-strategies-cascade-and-single-pass)). Fan-out extends that disclosure and widens the intersection surface. The rows a consent surface points at:

- **Candidate structure.** The ragged table names, for every (key, sender record), how many candidates that record contributes and which of the sender's distinct values co-belong to it -- for all records, not only matched ones, since the table is unfiltered by construction. The receiver therefore learns each of the sender's records' fan-out width per key. This is strictly more than the single-valued table's duplicate structure, and more than a matched-values-only disclosure would be; it is the price of the strategy that has one resolver.
- **Intersection surface per individual.** Each candidate value can independently reveal co-possession, so an individual is revealed as shared when any of its up to 20 candidates matches. A match on a fragment of a value (one part of a hyphenated name) is weaker evidence of identity than a match on the whole value, and the removal rule then takes that individual out of every later, less precise round on the strength of it.
- **Strategy coupling.** `cascade` is the schema default and the web application's ordinary path, so authoring a fan-out means opting into single-pass as well: its larger disclosure (the full index table and the weaker-key matches the lockstep cascade filters out) and its tighter dataset ceiling, further tightened by the slot arithmetic above. The two disclosures are consented together, in the same mandatory-consistency terms, before any data moves.
- **Exchange record.** No delta. Commitments cover the association table's row-index pairs and the payload values, never key strings, so fan-out adds no committed artifact and changes no record row.

### Deduplicating cardinalities: many-to-X matching

> **Reachable, the both-sided row on one strategy:** every row of the table below runs end to end from agreed terms, and the surfaces that table feeds hold the multiplicity with it -- the payload frame, the [result file](#output), and the [exchange record](EXCHANGE_RECORD.md#result-size-under-a-deduplicating-cardinality) with its re-supply path. The `many-to-one` and `one-to-many` rows run under both linkage strategies (`linkViaPSI` and `linkViaSinglePassPSI`, `packages/core/src/psi/link.ts`); `many-to-many` runs under the cascade, the one strategy that pairs it, and each strategy's verdict on it is an entry of `MANY_TO_MANY_IMPLEMENTED_BY_STRATEGY` (`packages/core/src/linkageTermsPolicy.ts`). An agreed `(true, true)` pair naming a strategy whose entry says it pairs no both-sided cardinality is refused before matching begins, rather than silently matched to less than the terms declare: `assertBothSidedDeduplicateImplemented`, reached from `resolveLinkageCardinality` (`packages/core/src/exchange.ts`) after the terms exchange and before the first round. It reads both parties' documents, so the refusal is symmetric in the pair, and it names the strategy rather than the cardinality -- the pair itself is what the cascade runs. The per-party guard beside it, applied at the local prepare step (`prepareForExchange`) among other points, refuses a party's own `deduplicate: true` under a strategy that matches no deduplicating cardinality at all, which neither shipped strategy is. A strategy in that position would be refused earlier still, at the accept boundary as well (`deriveAcceptedLinkageTerms`, `packages/core/src/linkageTermsNegotiation.ts`), reading the inviting party's terms, since `linkage_strategy` is a mandatory-consistency term and the accepting party's derived `deduplicate: false` would otherwise hide the pair from every check until the terms exchange. No strategy this document specifies is in that position. Below that boundary a direct caller of `packages/core/src/psi/link.ts` meets each strategy's own fail-closed half. `linkViaSinglePassPSI` throws on `many-to-many`, reading the same strategy entry the run boundary reads, its call site holding the resolved table to a length taken from the half that keeps its distinctness where a both-sided multiplicity leaves neither half distinct. `linkViaPSI` pairs the cardinality by the [per-side rules](#the-per-side-rules) and the run-grouped returned-list rule [below](#deriving-one-table-from-the-exchanged-association-maps).

A deduplicating cardinality is a widening on the records-per-value axis of the round's [(record, value) incidence](#matching-multiplicity-the-record-value-incidence), and every rule below is a consequence of that. The design rationale, the alternatives set aside, and what stays open are in [deduplicate-matching-semantics.md](../notes/deduplicate-matching-semantics.md).

#### The declaring party is the "many" side

[`deduplicate: true`](../EXCHANGE_REFERENCE.md#linkage_termsdeduplicate) on a party's linkage terms declares that several of that party's records may link to the same partner record. The declaring party is the "many" side of the resolved cardinality. That direction is normative and is stated here once, because it is the direction the operator-facing term takes: a party is asked whether to deduplicate its own inputs, which it does by using the partner's data to group them, so several of its own rows that turn out to name one partner record are one individual recorded more than once.

The term is per-party and has no consistency requirement: each party declares its own side of the cardinality, and the two values need not agree.

**The resolved cardinality.** After the terms exchange and before the first round, each party resolves the cardinality from the agreed pair -- its own `deduplicate` setting and the partner's. The resolution is a function of that pair alone, computed from the same authenticated state on both parties, so the lockstep rounds cannot diverge on it:

| this party's `deduplicate` | the partner's | resolved cardinality | which side holds the multiplicity |
| --- | --- | --- | --- |
| `false` | `false` | `one-to-one` | neither |
| `true` | `false` | `many-to-one` | this party |
| `false` | `true` | `one-to-many` | the partner |
| `true` | `true` | `many-to-many` | both |

The label is read from the resolving party's own side, which is why the pair `(true, false)` gives the declaring party `many-to-one` and its partner `one-to-many`. The two labels name one cardinality and one matching procedure, mirrored; what both parties must agree on is which side holds the multiplicity, and they do, because each derives it from the same agreed pair.

**An accepted invitation binds the value its author presents.** The term has no cross-party consistency requirement, but where a party reached the run by accepting an invitation, the value that invitation declared for the inviting party's own side is the value that party consented to, and it is the one the consent surfaces stated. The accepting party retains the declaration and MUST refuse a partner presenting any other value at the terms exchange, before any key or payload moves (`assertPresentedDeduplicateMatchesInvitation`, `packages/core/src/exchange.ts`), since a presented `true` against a declared `false` widens what the accepting party's own records disclose beyond the terms it agreed to. The binding is scoped to that path: an exchange authored from two parties' own configuration files has no declaration between them, and the differing pair that makes one of them the "many" side runs unaffected. The refusal is one-sided by construction -- only the accepting party holds the declaration -- so it aborts that party's run rather than both parties in lockstep. The guarantee is one-sided in scope as well as in enforcement: nothing holds an accepting party's presented value to one the inviting party expected, since an inviter consented to no document of its partner's. An inviting party therefore relies on no more than the per-side rules below already give it -- its partner's presented value governs that partner's side of the resolved cardinality -- and the residual exposure that value creates for the inviting party's own records has no symmetric binding to refuse it.

**A deduplicating party must receive the output.** Any party declaring `deduplicate: true` must also declare [`output.expects_output: true`](../EXCHANGE_REFERENCE.md#linkage_termsoutput). An output with multiple links per input imparts meaning to the data holder through entity resolution: the grouping is what a deduplicating exchange produces, and it exists only in the output. A "many" party entitled to no output would have widened its own match, disclosed to its partner how its records group (below), and received nothing the widening produced. The requirement is enforced by the cross-party `output` consistency check rather than by a check of its own.

#### The per-side rules

Stated for `many-to-one`; `one-to-many` is its mirror, and `many-to-many` applies the "many" side's rules to both parties.

- **The "one" side's within-round uniqueness rule is unchanged.** A value two or more of its records hold in that round is ambiguous and is dropped from the round, exactly as under `one-to-one`, and those records stay eligible for later keys. This is what holds the `-to-one` half of the cardinality: with the one side's contributed values unique within its dataset, each of the many side's records can match at most one of the one side's records.
- **The "many" side does not drop its within-dataset duplicates.** It contributes each distinct value once, and a match on that value is attributed to every one of its candidate records holding it. That is the whole of the widening: the round's incidence holds several records per value on the many side, and the [attribution rule](#matching-multiplicity-the-record-value-incidence) lifts one value-level match into one candidate pair per record in that group. Because the widening is on the records-per-value axis, it adds no PSI set entry and no value slot, so no derived frame or dataset bound moves.
- **Multiplicity is within-round.** Every record on either side that appears in any of round `j`'s candidate pairs leaves candidacy for every round after `j`, accepted or not -- the same [removal on a potential match](#removal-on-a-potential-match) fan-out states. A matched record on the "one" side is therefore not a candidate in a later round, and a later, weaker key cannot add a link onto a group an earlier key formed. A group is the set of the many side's records that shared one value with one partner record, on the most precise key any of them matched under.

  The one carve-out is the [single-resolver drop](#deriving-one-table-from-the-exchanged-association-maps): where the resolving "many" party drops a value two or more of the partner's records hold, the group standing behind that value is attributed nothing and its rows stay eligible for later keys, exactly as a value that party dropped before the round. The pairs are discarded as a set rather than resolved, so the round attributes the group no match to be removed on, and removing it anyway would cost those rows a later key over a partner fault they had no part in. The carve-out is reachable only against a partner that does not apply its own within-round uniqueness rule; under conforming partners no value reaches the resolver twice.
- **Resolution.** Round `j`'s candidate pairs are resolved by the deterministic greedy sweep in the canonical (sender row, receiver row) order [fixed for fan-out](#record-level-resolution-canonical-order-and-tiebreak), with one clause relaxed: a pair is accepted when the record on the many side has not already been accepted in this round, whether or not the record on the "one" side has. Under `many-to-many` every candidate pair is accepted. Where neither side fans out the sweep accepts every pair whatever the order, because each many-side record then holds one value for the key and the one side's contributed values are unique within its dataset, so each many-side record has exactly one candidate.
- **Both linkage strategies support it.** A deduplicating cardinality needs no strategy restriction, unlike a fan-out ([Fan-out runs under single-pass only](#fan-out-runs-under-single-pass-only)), and the axis distinction is the reason. Grouping a party's own records by value is computable from that party's own data, so each party computes its own removals locally in each round and the two cannot diverge. Fan-out is restricted because resolving it needs the partner's grouping of matched values into records, which the cascade's per-round frames do not deliver in time. Under `single-pass` the receiver is the sole resolver and applies these rules in its local replay, over the fixed-width index table unchanged: one value per (key, record) is all a deduplicating party's records ever hold, and the table already names which of a party's records hold the same value, which is the whole of what the widening reads. Nothing single-pass derives from authenticated state moves with it either. A party's value slot count and every bound taken from it ([The width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare)) count (key, record) cells, which duplication does not add to. So the ceiling, the per-message element bounds, and the reply byte cap are the same figures a `one-to-one` exchange of the same two datasets derives.

#### Deriving one table from the exchanged association maps

Both parties end the exchange with the same association table, and under the cascade that table is exchanged rather than derived from the intersection alone: a round's PSI output names positions in that round's two candidate sets, and only each party knows how its own positions map back to its own rows. The reconciliation is the pair of mapped-element passes the `one-to-one` cascade already performs (`exchangeMappedElements`, `packages/core/src/psi/link.ts`):

1. Each party sends one entry per record it matched, naming the round and the position that record matched within the partner's candidate set for that round.
2. Each party translates the list it received into its own row space and returns it. The originating party reads its partner's row index off each returned entry.

A deduplicating cardinality extends that in exactly one place: on the many side, a candidate-set position stands for a group of its rows rather than for one row. Three consequences follow. No entry gains a field, no frame is added, and a `one-to-one` exchange's passes are unchanged.

- The many side's outbound list still holds one entry per matched record, so several of its entries may name the same position in the one side's candidate set -- one per record in the group.
- The two outbound lists need not be the same length. A round pairs the same values on both parties but not the same number of records, so the count equality the `one-to-one` checks rest on is replaced by the rules below.
- Translating an entry whose position stands for a group expands it into one entry per record in that group -- emitted in ascending record order, though no receiving check reads that order (the within-run order paragraph below states what the freedom reaches) -- with the groups left in the order of the list being translated. The returned list is therefore longer than the list sent -- by exactly a multiplicity the originating party can count for itself, since the partner's inbound list of pass 1 names each of this party's own matched positions once per record in the group behind it.

The [index checks](#partner-supplied-index-tables-are-checked-against-local-state) generalize with it, and every bound stays derived from this party's own data or from a count declared on the authenticated terms exchange:

- every entry MUST name a round this exchange ran and a position within that round's candidate set that this party matched in that round -- unchanged;
- a list arriving from the many side MUST name every position this party matched in that round at least once and no other position; entries naming one position may repeat, which is the widening itself, and the list's length is bounded by the partner's row count declared on the terms exchange;
- a list arriving from the one side MUST name each such position exactly once, as under `one-to-one`;
- a returned list MUST contain exactly the entry count the receiving party computed for it above, each entry a row within the partner's counted rows. Where the receiving party is the many side and its partner the "one" side, several of its records name the same partner row. So the flat no-repeat rule that caps a `one-to-one` list's length gives way to that computed count and to injectivity modulo the grouping that party itself sent: two entries whose outbound entries named the same (round, position) MUST name the same row, and two that named different positions MUST name different rows. Both halves are checkable against state that party holds: it kept the position every one of its own entries named, distinct positions in a round are distinct values held by distinct rows of the "one" side, and a row matched in round `j` has left candidacy for every later round. So the returning party can neither merge two of its partner's groups onto one row nor split one across two;
- under `many-to-many` a returned list arrives as runs rather than entry for entry, both parties keeping their within-dataset duplicates, so each entry the checking party sent comes back as the whole partner group behind the position it named. The list is the concatenation of one run per entry sent, in the order sent. The run for an entry has the length that party accumulated from the partner's pass-1 list: the number of that list's entries naming the position the entry's record matched, which is the size of the partner group behind it. So the run lengths sum to exactly the entry count the whole list is held to, and every quantity the runs are read against is one the checking party computed rather than one read off the frame under check. Injectivity modulo the grouping reads over runs. Two entries that named the same (round, position) MUST come back with identical runs, element for element and in order. Two that named different positions MUST come back with disjoint runs. And the rows within one run MUST be distinct, a row named twice for one record being a repeated pair no consumer can read. That leaves the partner able neither to merge two of the checking party's groups nor to split one, exactly as the entry-for-entry form does. The two forms are alternatives -- a list is held one way or the other, never both -- and which applies follows the resolved cardinality both parties hold. The order of the rows within a run is the partner's own and is unpinned; run identity across a group makes that choice one consistent arrangement, so it is membership-preserving -- which partner rows a record pairs with is fixed however a run is arranged (the within-run order paragraph below states what the freedom reaches);
- at the single-pass boundary where the sender receives the resolved association table, the half naming the "one" side's rows admits a repeat, several of the many side's records linking to each of them. Which half that is follows the resolved cardinality, which both parties hold: where the sender is the "one" side its own half is non-decreasing rather than strictly ascending -- the distinctness the ascending rule enforces is what is relaxed -- and where the receiver is, the partner half repeats while the sender's own stays strictly ascending. The remaining half keeps its distinctness, so it is the one whose range check caps the table's length, and the other is then held to that count: the bound is the many side's row count, which is the sender's own where it deduplicates and the count declared on the terms exchange where its partner does.

A list failing any check is a protocol violation: the exchange aborts with a classified `protocol` error and produces no result.

**The both-sided expansion has no ceiling of its own.** Under `many-to-many` the only bound the checks above put on a returned list's length -- and so on the pair count of the table derived from it -- is this party's declared record count times the partner's, both declared on the terms exchange. The product is the honest shape of the pairing rather than an adversarial one: a value held by `m` of one party's rows and `n` of the other's contributes `m * n` pairs, so a table over two duplicate-rich datasets grows quadratically in them. No derived frame or dataset bound narrows it, since a widening on the records-per-value axis adds no PSI set entry and no value slot ([The per-side rules](#the-per-side-rules)), which leaves the channel's per-frame size bound on the frame holding the list as the only thing beneath it ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md)). It takes no ceiling of its own, by design: the worst case is projectable before any round runs -- this party's own row count times the partner's record count, both declared on the terms exchange. So a ceiling would refuse an exchange whose bound the operator could have read off the agreed terms, and failing fast on a table that is merely large buys little where the alternative is the same failure a moment later. A partner overstating its per-value multiplicity moves the table within that same bound (the many side's per-value multiplicity is not independently bound, below), which costs result size and adds no disclosure the consent surfaces did not already cover, so what a ceiling would defend is the operator's own patience rather than a confidentiality property. The quadratic term is also narrower than it looks: it is the derived pair table and the [result file](#output), never the rounds, since by the same reasoning the encryption cost is values-only. The [entity closure](#the-many-to-many-entity-closure) adds no term of its own -- it is one local pass over the pairs that table already holds, taken alongside the block label each pair was built with -- so it costs what the table costs and adds no frame, no round, and no disclosure beside the pairing that produced it. An advisory warning naming the pair count a run projects -- that projectable bound, and what each side's declared count contributes to it -- is admissible, and is a front end's discretion; a refusal is not. The bound that advisory reads is below.

**The advisory bound is 10,000,000 projected pairs.** `PAIR_TABLE_ADVISORY_MAX_PAIRS` (`packages/core/src/pairTableProjection.ts`), read against the product above -- this party's declared record count times the partner's, both declared on the terms exchange. **Derivation.** The [result file](#output) holds one row per pair under every cardinality, so a projected pair count converts to a result size through the writer's bytes per pair. Measured over the real writer (`buildOutputTable` plus the comma join both front ends serialize it with), the narrowest result an exchange can produce -- two columns, this party's identifier and the partner's row index, with no partner payload -- costs 6 to 15 bytes per pair. The range spans an absent identifier column through a six-digit one, and index columns addressing a thousand rows through three million. It is a range rather than a constant because the digits each column holds grow with the table. A result holding a UUID identifier or three payload columns costs 32 to 41 bytes per pair on the same measurement. Ten million pairs is therefore where that narrowest shape crosses order 100 MB -- 60 to 150 MB across the range -- and every wider shape crossed it well before. 100 MB is also the web app's CSV intake cap (`MAX_CSV_FILE_BYTES`, `apps/web/src/components/csvIntake.ts`), so the bound sits at the size a result stops being one the browser will read back. Rounded to one significant figure, and revisable as a one-line change: the number decides only whether a string is shown.

**The advisory is composed in core and raised by the front ends.** `describeResolvedRunShape` (same module) takes what `runExchange` hands its `onProtocolConfirmed` callback at this point -- after the terms exchange, before the first round -- and returns the strings; the run path itself raises nothing, since a warning emitted there would decide a front end's discretion for every seat. Two strings, and the first is not about size at all: a run whose resolved cardinality is a deduplicating one names that cardinality, whatever the projection, because the consent surfaces state each party's declared `deduplicate` and nothing else states what the pair resolved to. The second is the projection, raised only above the bound, naming the projected pair count and each side's contribution to it so an operator can tell which side drives it.

**The callback holds the entitlements as well as the cardinality, because neither string follows from the label alone.** A resolved cardinality determines whose duplicates match, not who holds what the matching produces, so the shape holds this party's own `output.expectsOutput` and whether this run [withholds](#linkage-strategies-cascade-and-single-pass) the partner's half of the table. Both readings turn on them. Only the declaring "many" party is [required to expect output](#the-declaring-party-is-the-many-side), so a `one-to-many` party can receive no result at all -- and naming "your result file" to it would contradict the completion the same run ends on; where it holds none its partner does, `validateCompatibility` refusing a pair in which neither expects output. And the key-group multiplicity a `many-to-one` run discloses is read by every partner except the single-pass blind helper, whose half is suppressed entirely and which therefore reads neither the group sizes nor its own membership ([The disclosure delta a deduplicating match pays](#the-disclosure-delta-a-deduplicating-match-pays)). The composition distinguishes both rather than stating the common case, so no configuration meets copy the run then contradicts.

**This is not the `single-pass` refusal, and the two differ in what exists to enforce.** The [single-pass dataset ceiling](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) aborts an over-budget exchange because the quantity that binds it -- the receiver's resident memory -- has no protocol bound at all: nothing in the specified checks caps it, so a fixed budget is imposed, non-configurable, and enforced as a fail-closed refusal in lockstep on both parties. The both-sided pair table has a protocol bound, stated above and enforced by the returned-list checks: this party's own row count times the partner's declared record count, every factor read off authenticated state. So the advisory imposes nothing; it names a bound already in force. The asymmetry is therefore in what each cardinality's binding quantity is bounded by, not in how tolerant each is of a large run.

**The many side's per-value multiplicity is not independently bound.** The checks above bind the aggregate and the positions -- a repeated position must name a value this party itself matched in that round, and a list's length is capped by a record count declared on the authenticated terms exchange -- but not the size of the group standing behind any one position. That size is the many side's own declaration throughout: the expanded return of pass 2 is checked against the count the many side's pass-1 list already implied, not against any quantity the receiving party derives from its own data or from the agreed terms. A many side that overstates a group therefore satisfies every check specified here, to the limit of its declared row count, and its partner reads a multiplicity that side's data does not hold. The values-per-record axis binds its comparable quantity -- the ragged index table's per-cell width is checked against a bound the receiver derives from authenticated session state ([Wire-format deltas](#wire-format-deltas-existing-frames-only-and-no-version-bump)) -- and the records-per-value axis has no counterpart.

**The injectivity clause is stated for the resolver shape this cascade implements.** Its two halves read structure that shape holds: the "one" side's within-round uniqueness rule makes a position one value held by one row, and [removal on a potential match](#removal-on-a-potential-match) keeps a row matched in round `j` out of every later round's candidate set, so two entries naming different `(round, position)` pairs name different rows. Under `many-to-many` the halves read with the group in place of the row, over the same structure: a position stands for the partner group holding one value, distinct positions in a round are distinct values held by disjoint groups, and removal takes every row of a matched group out of the later rounds. So runs answering different positions are disjoint, and the runs answering one position are the one group. The single-resolver variant below holds neither by construction: the "one" party there contributes its whole dataset every round, and the obligation the "many" party takes on for it is the uniqueness rule, not that party's removals. One of its rows therefore stands behind a position in more than one round, and a conforming return would be refused as a merge of two groups. That variant is sanctioned and unbuilt; building it means re-deriving this check against what its resolver actually holds, rather than reusing the clause unchanged.

**What is unbound is one-directional.** It is the many side declaring the size of its own group to its partner, and it should not be read as the pair of freedoms it resembles. The other direction -- the "one" side deciding which of the many side's records fall into one group -- is bound, by the injectivity modulo the grouping above: the many side holds the position each of its own entries named, and refuses a returned list that merges two of its groups onto one row or splits one across two. The grouping a deduplicating result holds is always that party's own. Under `many-to-many` each party stands in both roles at once -- declaring its own group sizes and holding its partner's return to the grouping it sent -- so the asymmetry holds twice over rather than cancelling.

**The residual is recorded, not closed.** There is no authenticated quantity to bind a group size against. The agreed terms say nothing about how a party's own rows duplicate, and the only figure that would is the duplication structure the protocol keeps off the wire ([Role resolution and work minimization](#role-resolution-and-work-minimization)), so any bound would be advertised by the party it binds -- a self-declaration again. What overstating buys is correspondingly small, and is stated here so a later change that widens it is recognizable as one. Which of the reading party's records matched is fixed by the coverage rule above, over positions that party itself matched, so an overstated group adds no matched record, no disclosed column, and no membership fact about that party, and the payload it discloses is for rows it already pairs. What the overstatement adds beyond that follows the shape the return takes. Entry for entry, every entry of one group names the same partner row, so it repeats a row the reading party already pairs and already discloses payload for, and inflates the overstating party's own result table with pairs naming its own rows. Under runs distinctness within a run rules that repeat out, so the entries an over-declared run adds must be filled with further partner rows: an over-declaration within the declaring party's counted rows can put in the reading party's table a partner row appearing nowhere in the honest one. That is the same self-declared multiplicity read through the run shape rather than a further admission -- the size of the group behind a position is the declaring party's own word either way, and the reading party holds nothing to weigh it against. Either way one group's inflation is bounded by the overstating party's row count declared on the terms exchange, which bounds the payload rows it can make its partner repeat with it, and the whole list by the product above. This would need revisiting if the multiplicity ever decided something the receiving party discloses -- a new column, a new row, or a matched-record set read from the returned list rather than from that party's own round output.

**Within-run order is the arranging party's own, at both boundaries.** At the single-pass boundary the freedom lives in one of the two configurations. Where the repeating half is the sender's own -- the receiver deduplicates -- the non-decreasing rule leaves the pairs sharing one of its row indices contiguous, as a run, and which pair takes which position inside a run is bound by nothing. The checks reach each entry's range, the two halves' equal length, and each half's order and distinctness rules as stated above, and the sender -- which receives that table rather than resolving it -- holds nothing to derive the arrangement from either. Where the repeating half is the partner's -- the sender deduplicates -- no order rule reaches that half, and none is needed: the sender's own half is strictly ascending and distinct, which pins every position, so the arrangement holds nothing beyond the pairing itself. The cascade's returned list holds a freedom of the same kind wherever an expansion produces it. Checked flat -- the reading a party takes when it keeps no duplicates of its own, under `one-to-many` -- distinctness alone reaches the list, and the arrangement inside each expanded run is the returning party's own. Checked entry for entry it is one row per entry, held to the grouping the party checking it sent. Checked run for run, the arrangement inside a run is again the returning party's own, constrained to be the same arrangement in every run of one group -- one consistent arrangement per group, so no pair is added, dropped, or re-attributed by the ordering. Whether the rows of a run are the honest group behind the position is the self-declared multiplicity recorded above, which no arrangement rule reaches.

What that leaves open is an ordering rather than a pairing, and it stays inside the artifacts of the party receiving the table or the run-grouped return: a run holds the same pairs whatever order they arrive in, so none is added, dropped, or re-attributed. What moves with the order is the order of that party's [result file](#output) rows within one run, and its record's association-table commitment is computed over the table those rows were written from -- both per-party, local, and self-attested. A record's commitments are never compared against the partner's, and the pairing is not part of the [signed receipt](EXCHANGE_RECORD.md#signed-receipt) ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#commitment-scheme)), so the result file, the record, and the re-supply path that reopens that commitment agree with one another on whatever order arrived.

**Where the "one" party receives no output.** A cascade can run with only the receiving party resolving the final association ([above](#psi)). A `deduplicate: true` party is always entitled to output while its partner may not be, so in a deduplicating exchange that sole resolver is the "many" party, and it has one extra obligation. Where the "one" party does not itself apply the within-round uniqueness rule to its own values -- the variant in which one party contributes its whole dataset each round and the other resolves -- the "many" party MUST apply that rule on the partner's behalf, dropping from the round any value two or more of the partner's records hold. Omitting it would silently promote the exchange to `many-to-many`, delivering a match multiplicity neither party's terms declared.

`single-pass` is that shape by construction, and it is where the obligation is discharged structurally rather than taken on. Its receiver is the only resolver whatever the output entitlements, and [role resolution](#role-resolution-and-work-minimization) makes the party entitled to output the receiver -- so in a deduplicating exchange whose "one" party expects none, the "many" party is the receiver, and it applies the "one" side's within-round uniqueness rule to that party's index table as part of the replay. The helper's own [table withholding](#linkage-strategies-cascade-and-single-pass) composes with it unchanged: the helper needs its half back to build a result (it has none) or to enrich a payload it discloses, and the multiplicity bears on neither condition. A "many" party can never be on the withheld side, since it must be entitled to output.

#### The disclosure delta a deduplicating match pays

- **Key-group multiplicity.** The many side's within-dataset duplicate values participate in a round instead of being dropped, and the mapped-element passes name the one side's matched position once per record in the group. The "one" party therefore learns, for each of its records that matched, how many of the many party's records share that linkage-key value, and which of the many party's rows they are -- the same opaque row-index layer the association table already holds for a one-to-one match, several rows against one of its own. Under `one-to-one` none of that is disclosed at all: the value is dropped before the round, so the partner learns neither that it matched nor that a group holds it. The disclosure is bounded to matched groups -- a group whose value the partner does not hold matches nothing and is never counted -- and it is a count and a set of row indices, never the key value behind them.
- **What a round's element count summarizes.** A deduplicating party's per-round set holds one entry per distinct candidate value for that key, where a `one-to-one` party's holds one per value occurring exactly once among its candidates. Set beside the raw row count the terms exchange already holds ([Role resolution and work minimization](#role-resolution-and-work-minimization)), the two are slightly different summaries of the same dataset; neither is the intersection, and which one is being read is itself fixed by the agreed terms.
- **No delta from the single-resolver obligation.** The variant in which the "many" party applies the "one" side's uniqueness rule on its behalf is the one that already sends both datasets whole every round, whose disclosure is stated [above](#psi). Applying the rule reads structure the resolver already holds.
- **Under `single-pass` one direction is already paid.** That strategy hands the receiver the sender's whole per-key index table, which names which of the sender's records hold one value ([Why the full index table](#linkage-strategies-cascade-and-single-pass)). So where the "many" side is the sender, the key-group multiplicity above is not a delta of the cardinality at all: the receiver held that structure under `one-to-one` too. What the cardinality adds is what comes back -- where the "many" side is the receiver, the sender reads the size and rows of the group its own record took off the resolved table's repeated half, which is the first row's disclosure and no more. A helper whose table is [withheld](#linkage-strategies-cascade-and-single-pass) reads neither.
- **Exchange record.** No delta. Commitments cover the association table's row-index pairs and the payload values, never key strings ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#commitment-scheme)), and a repeated row index on one side of a pair is still a pair. The recorded result size reads that table as pairs for the same reason, so both parties' records state one figure ([Result size under a deduplicating cardinality](EXCHANGE_RECORD.md#result-size-under-a-deduplicating-cardinality)).

#### The `many-to-many` entity closure

The `(true, true)` pair resolves to `many-to-many`, and the per-side rules above give its round-level pairing directly: both sides keep their within-dataset duplicates, and every candidate pair a round produces is accepted. A table where both sides hold multiplicity links records transitively -- two of one party's records reach each other through a partner record, and a partner record through them -- so it means something to either party only once that multiplicity is resolved into single **entity clusters**. A **cluster** is a connected component of the bipartite graph whose vertices are the two parties' matched records and whose edges are the association table's pairs: a set of this party's records together with the set of the partner's records they link to. A record that matched stands in exactly one cluster; a record that did not stands in none.

**Each party computes the closure locally, from the table it already holds.** No frame holds it, no round is added, and nothing is exchanged for it. Both output-entitled parties end the cascade holding the same association table ([Deriving one table from the exchanged association maps](#deriving-one-table-from-the-exchanged-association-maps)), so both derive the same clusters from it, and that agreement is a property of the one table rather than of a further reconciliation. Every `many-to-many` party is entitled to output, a deduplicating party being required to receive it ([The declaring party is the "many" side](#the-declaring-party-is-the-many-side)), so no party is left holding a multiplicity it cannot resolve. The reference implementation lives in core (`entityClusters`, `packages/core/src/psi/entityClosure.ts`), internal to that package rather than part of its API; a consumer that wants clusters recomputes them from the result file's pairs by the rules this section states.

**In the scope this cardinality runs in, the closure is block-diagonal.** Three rules already specified put it there. `many-to-many` is matched by the cascade alone (`MANY_TO_MANY_IMPLEMENTED_BY_STRATEGY`, `packages/core/src/linkageTermsPolicy.ts`, which both the agreed-terms refusal and `singlePassResolves` in `packages/core/src/psi/link.ts` read). The cascade refuses a fan-out at the round that would consume it ([Fan-out runs under single-pass only](#fan-out-runs-under-single-pass-only)), so a record holds one value per key round. And every record on either side that appears in any of round `j`'s candidate pairs leaves candidacy for every round after `j` (Multiplicity is within-round, in [The per-side rules](#the-per-side-rules)). A record therefore contributes one value to at most one matched round, and the table is the disjoint union of its per-(round, value) **blocks** -- one block per matched value, holding every pair between the `m` records of one party and the `n` of the other that hold it. **Each cluster is exactly one such block.** The conditions establishing it: no cluster spans two blocks, each cluster is the whole `m x n` product, and no block is split across two clusters.

**The block claim is held by a check, not by the paragraph above.** The cascade runs it over every both-sided table before returning it (`assertBlockDiagonalClosure`, `packages/core/src/psi/entityClosure.ts`), labelling each pair with the block it was built from and requiring the three conditions of the clusters it computes. A table failing any of them aborts the run as an internal inconsistency and produces no result. The structural assumptions are separately revisable: a fan-out reaching the cascade would falsify the one-value-per-round assumption the block shape rests on. And the check reads a label per pair rather than per record, so a later producer that labels one record's pairs apart is held to the same block shape rather than having its two blocks arrive flattened into one label the check could not see past. The producer the cascade runs today derives one label per matched record and replicates it across that record's pairs, which excludes that shape structurally; reading the built table through per-pair labels is what keeps the check standing over a changed derivation. A closure over some later table that is not block-diagonal is a different procedure with a disclosure question of its own, and this is what makes that a visible change rather than a silent one.

**The closure discloses nothing further.** It reads one artifact this party already holds and puts nothing on the wire, so a `many-to-many` exchange discloses what its pairing discloses ([The disclosure delta a deduplicating match pays](#the-disclosure-delta-a-deduplicating-match-pays), which each party pays in both directions here). The disclosure a general closure would add -- two of a party's records grouped through a partner record that no linkage key links them through -- does not arise while the closure is block-diagonal: a cluster's members all share one value under one key, so every grouping is evidenced by exactly the rule that formed it. That is a property of the check above rather than of consent copy.

**A cluster is not written as a cluster.** The [result file](#output) holds one row per association pair under every cardinality, so a cluster of `m` of this party's records and `n` of the partner's writes `m * n` rows: each of this party's records repeated `n` times down the first column, each row holding one partner record's row index and payload values. The payload frame is unmoved -- one row per matched record of the sender, whatever the cardinality ([Output](#output)) -- so the multiplicity stays on the association table's side of the join. The attested result size is the pair count ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#result-size-under-a-deduplicating-cardinality)), which under the closure is the sum of `m * n` over the clusters; it is neither party's matched-record count and neither party's cluster count, and both parties derive the one figure from the one table. No column names the cluster: the pairs are what the record's commitments bind, a cluster id would move every value column's offset for every reader of every result, and a reader that wants clusters computes them from the pairs.

**Choosing linkage keys under closure.** A cluster is the set of records that shared one value under one key, so a cluster is only as good as the key that formed it. A key that is not near-unique where it is present ([Linkage keys](#linkage-keys)) groups records that are not one individual, and the closure hands that grouping to both parties as a single entity. Three consequences an operator authoring a `many-to-many` template weighs:

- The key a cluster forms on is the most precise one any of its members matched under, removal being within-round. A weaker key later in the cascade can form clusters of its own but cannot widen a cluster an earlier key formed, so adding one never regroups what a precise key already decided.
- A key whose value names a household, a site, or an episode rather than an individual produces exactly the cluster that key describes -- everyone at the address, everyone at the clinic -- and the result states it as an entity grouping.
- The cluster size distribution is the diagnostic an operator reads off its own result, needing nothing from the partner: a template whose clusters are mostly `1 x 1` matched as a near-one-to-one exchange, while a cluster spanning a large share of either dataset is the signature of a key that identified a group rather than a person.

**The `(true, true)` pair runs on the cascade, and only there.** `resolveLinkageCardinality` (`packages/core/src/exchange.ts`) resolves the agreed pair after the terms exchange and before the first round, so an exchange whose two parties both declare `deduplicate: true` on `cascade` runs the pairing, the closure, and the accounting above. The same pair on a strategy that pairs no both-sided cardinality is refused at that point instead ([the note opening this section](#deduplicating-cardinalities-many-to-x-matching)), naming the strategy that stands in the way rather than the cardinality.

**The invitation route reaches the pair from the accepting side only.** Acceptance derives the accepting party's own `deduplicate` as `false` whatever the invitation declared, and the declaration it retains records the inviting party's side alone (`expected_partner_deduplicate`, [Terms-binding consent](EXCHANGE_FILE.md#terms-binding-consent)). No field records an inviting party's expectation of the acceptor's value, so an accepting party that later declares `deduplicate: true` in its own configuration resolves the both-sided pair with no inviter-side declaration to hold it to: the terms exchange is where the inviting party's implementation sees the widened pair, and under the cascade the run proceeds from there. It is the one-sided scope stated [above](#the-declaring-party-is-the-many-side), at the cardinality where both parties' records group.

### Role resolution and work minimization

Both parties send their record counts on the terms exchange, then resolve locally which is the [PSI base function](#psi-base-function) receiver and which is the sender -- with no separate round-trip. Both the count's placement and the assignment are specified here. The reference implementations are `exchangeTerms` (which puts the counts on its messages) and `resolveRole` (the local decision over them), both in `packages/core/src/protocolSetup.ts`.

**The counts ride the terms exchange.** Each party's record count travels on its terms-exchange message envelope -- beside `linkageTerms`, like the `save` flag, the observed-host-key advertisement, the payload-intent flag (`disclosesPayload`, whose one consumer is the single-pass table withholding above), and the protocol version ([Protocol-version reconcile](#protocol-version-reconcile-at-the-terms-exchange) below) -- on every exchange, both- and one-sided-output alike. So by the time the terms are agreed each party holds its own count and the partner's, and the role follows from a purely local computation with no additional messages. The count is per-party, per-run role and element-bounds metadata held on the envelope, never inside `linkageTerms`: it differs per party and per run, so folding it into the terms would make two honest parties compute different canonical/agreed-terms hashes -- it is kept out of them. This count is independent of the linkage rounds and is a separate quantity from the sender's record count packed into the single-pass reply (part (c) above), which is that party's own row count embedded so the receiver can size the index table. The integer sent is the party's declared record count -- its raw row count times the fan-out factor its own standardization declares ([the width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare)), so the two are the same number for a party whose cleaning does not fan out. It is the quantity the role assignment below uses, the single-pass pre-flight checks locally, and the data-dependent single-pass frame cap derives its bound from (see [The single-pass dataset ceiling](#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) above). It stays on the wire even in the one-sided case, where the role decision does not consume it -- precisely because the frame cap and PSI element bounds do, on every exchange. (The quantity that actually drives that frame's size is the distinct-value count, which is not exchanged; the cap bounds it from the row and key counts.)

**The assignment.** It is chosen to minimize total work -- total communication bytes plus total per-party compute -- for the densely-populated near-unique keys linkage typically uses:

- When exactly one party expects output, that party is the receiver regardless of the counts -- it is the only party that learns the result.
- When both parties expect output, the assignment is free. The rule is: **the party with the smaller declared record count becomes the receiver**; an equal-count tie is work-neutral and broken deterministically in favour of the initiator.

This is one rule for both linkage strategies; the rest of this section derives it, including the regime where a row-count rule cannot be optimal.

**What a local fan-out does to the assignment.** The count the rule weighs is the declared one, so a party whose own cleaning fans out is compared at 20 times its rows and trends toward sender, not receiver -- and toward it on a declaration only that party can make, which no partner can check ([the width bound](#the-width-bound-a-per-key-candidate-cap-the-terms-declare)). Under `single-pass` the receiver is the sole resolver: it holds the sender's whole per-key value structure and replays the match locally ([Why the full index table](#linkage-strategies-cascade-and-single-pass)). A unilateral, unverifiable inflation of one's own declared count therefore moves the declaring party onto the side that is READ, never onto the side that reads: it cannot be used to reach the resolver's seat, and it buys nothing a party could not get by pre-fanning its file. The behaviour is driven, not asserted: the fan-out role case in [`packages/core/test/derivedKeyWidth.test.ts`](../../packages/core/test/derivedKeyWidth.test.ts) runs a fanning party against a larger partner and pins the resolved role to `sender`.

**Why the receiver is the heavier side.** In the PSI base function the receiver (client) encrypts its distinct-value set under its own key and sends it; the sender (server) encrypts its own set under its key and *re-encrypts the receiver's set*, returning both. So the receiver's set crosses the wire twice -- once as its request, once re-encrypted in the reply -- while the sender's crosses once, and the receiver's set drives more of the expensive curve operations (its own encryption, the sender's re-encryption, and the receiver later stripping its own key from the reply) than the sender's does. Writing `D_recv` and `D_send` for the two parties' pooled distinct-value counts, and at the 35 bytes per encrypted element given above, the dominant communication cost is `35 * (2*D_recv + D_send)` bytes; both that and the curve-operation count are larger for whoever is the receiver, by an amount that grows with the receiver's distinct count. Total work is therefore minimized by putting the smaller set on the receiver.

**The two strategies' cost terms.** The cascade is one base-function round per key over a shrinking candidate set; every round has the `2*D_recv + D_send` asymmetry above and nothing that opposes it. For the cascade, smaller-as-receiver is optimal, and the win over the other assignment is up to about `35 * (D_large - D_small)` bytes (plus the matching curve operations); the per-round candidate set shrinks as the cascade proceeds, so the realized gap is at most that bound. The single-pass reply adds one term the cascade has no analogue for: the distinct-value index table, `4 * keyCount * senderRecordCount` bytes (defined above), which scales with the *sender's row count* and is the one term that favours the opposite assignment -- making the smaller-row party the sender shrinks it. So single-pass has two asymmetric terms pulling against each other:

| Term | Approx. size | Favours |
| --- | --- | --- |
| Masked-set / re-encryption | about `35 * (D_large - D_small)` bytes | smaller-as-**receiver** |
| Index table | `4 * keyCount * (rows_large - rows_small)` bytes | smaller-as-**sender** |

where `D_large` / `D_small` and `rows_large` / `rows_small` are the two parties' distinct-value and row counts.

**Why the single rule serves single-pass too.** A linkage key earns its place by being near-unique where present (high positive-predictive value; see [Linkage keys](#linkage-keys)), and a value repeated within a dataset is dropped from its round, so where a key is also densely populated -- present on most records, with comparable density on both sides -- the participating distinct values track the row count: `D ~= keyCount * rows`. Under that assumption both terms have the same `keyCount * (rows_large - rows_small)` factor and reduce to the ratio of their coefficients, **35 to 4** -- the masked-set term outweighs the index table by about nine to one. Smaller-as-receiver wins, by a net of up to about `31 * keyCount * (rows_large - rows_small)` bytes, reinforced by the curve-operation saving (which the index table, being integer work, does not offset). So in the typical case single-pass agrees with the cascade: one rule serves both.

**When the rule is not optimal, and why it still stands.** The index table can dominate whenever distinct participating values fall well below row counts (`D` much less than `keyCount * rows`), because the index table counts every record (a `-1` for each absent value) and so scales with total rows, while the masked sets scale only with distinct *participating* values. That happens not only for a heavily-repeating low-precision key (bad design), but also for a precise key that is *sparsely populated* -- present on only a fraction of records, such as an SSN available for a minority of rows. Such a key is legitimate and exactly the kind the cascade combines with denser ones. It happens too for two parties whose per-key density differs markedly. In those cases the cheaper assignment can flip to smaller-rows-as-sender; the crossover is roughly when populated `(key, record)` cells average below `4 / 35` (about 11%) of the table. The decisive point is that all of these are invisible to a row-count rule: the quantity that distinguishes them is the distinct-value count -- and that count is not exchanged, because unlike the raw row count (mere dataset-size metadata) it would disclose data content: how much a party's key values repeat, and how sparsely a key is populated. Given only the row counts, smaller-rows-as-receiver is the best fixed rule for the typical case (near-unique, densely and comparably populated keys) and is the one implemented. It is not optimal on every input, and the residual gap on sparse or asymmetrically-dense keys is accepted, not closed. Closing it would mean exchanging distinct-value counts, trading away the privacy of each key's duplication and sparsity structure for a modest bandwidth saving -- a trade this protocol does not make.

### Protocol-version reconcile at the terms exchange

Both parties advertise a build-level protocol version on their terms-exchange message, beside `linkageTerms` and the record count, and reconcile the partner's before weighing the terms. That version is `PROTOCOL_VERSION` (`packages/core/src/protocolSetup.ts`), an integer bumped only on a wire-incompatible protocol change, and only once the software is officially published (pre-release deltas hold it at 1: there are no deployed peers to reconcile). It rides the one bidirectional round-trip both parties already perform (message 1 for the initiator, message 2 for the responder), so the check adds no round trip; on the authenticated path it rides the AEAD channel and cannot be forged.

The reconcile is **fail-closed**: a partner advertising anything other than this build's exact version aborts the exchange with the actionable `the partner is running an incompatible psilink version; both parties must run the same version` -- sent to the partner as the abort reason and thrown locally, so both sides name the real cause before the linkage rounds begin, instead of failing later with a cryptic frame-parse error. Any present value that is not the exact version is a mismatch: a different integer, or a garbled/wrong-typed value from a non-conforming or corrupted peer -- the field is read as `unknown` rather than a typed number precisely so such a value reconciles to the named skew instead of a generic "linkage terms failed to parse". This matches the mode-flag fast-fail precedent, not the fail-soft observed-host-key advisory. A partner advertising no readable version -- an absent field, a frame that is not an object, or a value the lenient probe below cannot read -- is refused on exactly the same terms. Pre-publication no build predating the field is deployed, so an unversioned advertisement identifies a non-conforming peer rather than an older psilink, and admitting one would leave a leg of this reconcile open. The refusal is the same on both message paths and in both directions. The durable, forward-looking guarantee is that a partner not running this exact build fails cleanly, naming the cause, before the linkage rounds begin.

The responder's message-2 ABORT frame includes the version as its proceed frame does -- the one field spread onto an abort, where the `save` intent is not. The initiator reconciles that frame's version before it reads the decision, so an abort omitting the version would reach a same-version partner as a version skew and bury the reason the responder stated. The initiator's decision-only message 3 closes an exchange whose versions both parties have already reconciled, and no reconcile reads it, so it includes none.

Two ordering notes bound that guarantee. First, the version is read from a lenient probe over the raw frame before the strict envelope parse, on both message paths, so it is available to the reconcile independently of whether any other field parses. A future bump that reshapes a sibling field (a required `recordCount`, an optional `save`, ...) therefore does not bury the skew diagnosis behind a generic parse error: the older peer still reads the version, reconciles the mismatch, and reports the actionable "run the same version" message (and best-effort sends the abort) before the strict parse throws. This is a structural guarantee rather than a prose requirement that every field stay backward-parseable across a bump. Second, on the file-sync transport the terms exchange rides binary-envelope message frames (see [FILE_SYNC.md](FILE_SYNC.md)), so for a skew that changes the envelope itself the file-sync reader's envelope-version-byte hint fires on the first frame before this terms reconcile is reached. This reconcile is the transport-agnostic check for skews whose envelope stays readable, and the only check on the WebRTC/filedrop paths, which have no such byte.

This marker is distinct from three neighbouring identifiers. The operator-authored linkage-terms [`version`](../EXCHANGE_REFERENCE.md#linkage-terms) is compared for equality between the two parties' authored values and is not bound to the build a party runs (two parties can declare the same `version` while running different psilink releases; see [Versioning](#transform-regular-expression-dialect) under the transform dialect). The file-sync `MESSAGE_ENVELOPE_VERSION` is the transport frame-format byte ([FILE_SYNC.md](FILE_SYNC.md)); a foreign value there is the retroactive reader-side half of this same robustness work, translated into the same "likely incompatible partner version" hint at the read path rather than at the terms exchange. The KEX protocol-name tag (the **Protocol-version tag** under [P-256 authenticated key exchange](#p-256-authenticated-key-exchange) below) is the cryptographic-suite version hashed into the handshake transcript. `PROTOCOL_VERSION` is the additive terms-layer marker; a future runtime version-reconciliation mechanism may subsume it.

### PSI-C

PSI-C ([`linkage_terms.algorithm: psi-c`](../EXCHANGE_REFERENCE.md#linkage_termsalgorithm)) reports the size of the intersection and nothing else: no identifier, no matched pairing, no payload, no per-record result. It is the pre-agreement feasibility instrument -- the exchange two parties run to find out whether a linkage is worth negotiating at all -- so it runs at the point in a partnership where the least trust has been established, which is what fixes the scope of the claim it makes (see [Threat-model scope of the count-only claim](#threat-model-scope-of-the-count-only-claim) below).

**One key, one round, cascade only.** A count-only exchange is exactly one [PSI base function](#psi-base-function) round over exactly one linkage key, under [`linkage_strategy: cascade`](#linkage-strategies-cascade-and-single-pass). There is no count-only cascade over several keys and no count-only single-pass: a multi-key count is not specified here, and terms declaring one are refused rather than narrowed to the first key. Why a round-consistent multi-key count is not offered is recorded in [psi-c-count-only.md](../notes/psi-c-count-only.md).

**Refusals.** A psi-c terms document declaring any of the following MUST be refused:

- more than one entry in [`linkage_keys`](../EXCHANGE_REFERENCE.md#linkage-terms);
- [`linkage_strategy: single-pass`](../EXCHANGE_REFERENCE.md#linkage_termslinkage_strategy);
- [`deduplicate: true`](../EXCHANGE_REFERENCE.md#linkage_termsdeduplicate) on either party;
- payload in either direction -- a non-empty [`payload.send`](../EXCHANGE_REFERENCE.md#linkage_termspayload) or `payload.receive`, or [input metadata](../EXCHANGE_REFERENCE.md#input-metadata) that would transmit a column (`is_payload: true` on a column whose `role` is not `ignored`).

Each MUST be refused at three points, so that no combination of authoring path and partner reaches a run: when the terms are authored or an invitation over them is minted; at the local prepare step, before any credential, terms, or data are sent; and at the agreed-terms run boundary once the terms exchange has completed, which is the first point at which both parties' values are known. The run-boundary check is a symmetric function of the agreed pair, computed identically on both parties, so the lockstep round cannot begin on one side and be refused on the other.

The refusal is fail-closed at all three: an over-broad psi-c term is never silently narrowed to the specified shape, never derived and then discarded, and never downgraded to a `psi` run. Narrowing would deliver a disclosure the operator did not agree to; downgrading would reveal matched identifiers under terms that asked for a count -- the exact substitution the count-only algorithm exists to prevent.

**The round.** The wire shape is the cascade round's, unchanged. The sender is the base function's server and the receiver its client, assigned by the ordinary rule ([Role resolution and work minimization](#role-resolution-and-work-minimization)): when exactly one party expects output that party is the receiver, and when both do the smaller declared count is. Three frames:

1. **sender -> receiver** -- the sender's setup message over the values it contributes, each encrypted once under the sender's key, as a `Raw` data structure.
2. **receiver -> sender** -- the receiver's request over the values it contributes, each encrypted once under the receiver's key.
3. **sender -> receiver** -- the response: the receiver's request re-encrypted under the sender's key.

The sender does not need the setup message's internal sorting permutation, because there is no pairing to map back to rows.

**The reveal flag is cleared, and it is not a local preference.** Both parties MUST construct their base-function objects with the library's reveal-intersection flag cleared, where a `psi` run sets it. Three properties follow, and together they are what makes the mode count-only rather than a convention:

- **The flag rides the receiver's request.** Of the three messages only the request holds it, as a field of its own; the setup and the response have no mode marker. So the mode the receiver ran under is on the wire rather than asserted, and it is the sender that reads it.
- **Mismatched parties cannot complete the round.** The sender enforces agreement when it processes the request: a request whose flag differs from the sender's own throws rather than producing a response, in both orientations. A count-only sender therefore refuses to serve a revealing receiver, and a revealing sender refuses to serve a count-only one, so a completed round implies the two flags agreed. The mismatch fails; it never resolves silently to either mode.
- **The identifier-revealing operations are unavailable.** With the flag cleared, the client operations that return the matched positions or the association table throw instead of returning. The receiver's own software cannot produce a pairing out of a count-only round even if it asks for one.

The response also does not positionally name the matches: its encrypted elements are emitted in an order the library fixes from the ciphertext bytes rather than in the request's order, and the receiver cannot re-derive the correspondence, since doing so would require encrypting its own value under the sender's key. What that does not do is make the attribution unavailable to a receiver that chooses its input set -- see the threat-model scope below.

**Computing the count.** The receiver computes the count locally from the setup and the response, with the library's cardinality operation over the two. The sender computes nothing and learns nothing about the count from the round itself.

**`Raw` is required.** The setup message MUST use the `Raw` data structure, as every round of this protocol already does (a received setup that is not `Raw` is refused as a protocol error). It is what makes the count exact. The probabilistic structures the library also offers -- a Bloom filter and a Golomb-coded set -- admit false positives, so the figure they yield is an upper bound on the cardinality rather than the cardinality. Under `psi` such a false positive would be reported as a spurious pair an operator could notice; a count-only run reports no identifiers at all, so neither party can detect an inflated count, let alone correct it. The exactness requirement is therefore stricter for psi-c than for psi, not weaker.

**Within-dataset value handling, and comparability with `psi`.** A count-only round applies the same rule every cascade round applies ([Key input data](#key-input-data)): a record with no value for the key is omitted from the round, and a record whose key value is duplicated within its own party's dataset is omitted too, since an ambiguous match cannot be attributed to a single record. Each party therefore contributes exactly the key values that occur exactly once in its own dataset.

Applying that filter is normative, not an optimization inherited from the cascade, because the library's cardinality operation does not reproduce it. That operation reports the size of the multiset intersection: a value repeated on both sides contributes the smaller of the two multiplicities, where the cascade rule drops such a value from the round entirely. A party that passed its raw column through would therefore report a figure that can exceed the number of records that actually match -- and a count-only run reports no identifier that would contradict it.

With the filter applied on both sides every contributed value is unique within its own dataset, so the multiset question does not arise and the psi-c count equals the size of the association table a single-key `psi` run over the same key and the same data would produce. That equality is what makes a count-only feasibility run comparable to the linkage it is used to justify. It is not comparable to a multi-key `psi` run, which matches records a single key alone misses.

**Count reporting and entitlement.** The receiver alone computes the count. Whether it travels back is decided by the agreed terms' [`output`](../EXCHANGE_REFERENCE.md#linkage_termsoutput) entitlement, derived identically on both parties before the round runs:

- **Both parties entitled** (`expects_output` true on both). After the round the receiver sends a single **count-report** frame holding its tally to the sender over the authenticated channel. Only the receiver sends; the sender receives it and sends nothing back.
- **Exactly one party entitled.** By the role rule the entitled party is the receiver, so it already holds the count and there is no count-report frame at all. The non-receiving sender receives nothing -- not the count, not an empty frame. Suppressing the frame entirely, rather than sending a placeholder, is the same discipline the single-pass table withholding follows: a frame that is present but empty would still mark, by its presence, that a count existed to report.

Both parties derive that decision from the same agreed terms, so the receiver never sends a frame the sender will not read and the sender never blocks awaiting one the receiver will not send. The reference implementations are `linkViaCountOnlyPSI` (`packages/core/src/psi/link.ts`), which runs the round and this leg, and `reportsCountToSender` (`packages/core/src/protocolSetup.ts`), the entitlement predicate both parties evaluate.

**What each party learns, and on what basis.** Stated in the vocabulary the consent surfaces use -- `enforced` is a claim about the run (either it holds or the exchange aborts), `trust-contingent` is a claim about the partner, whom psilink does not stop (`CONSENT_BASIS_MARKERS`, `packages/core/src/consent/consentFacts.ts`):

- **A party's own count-only outcome is enforced.** With its flag cleared its software cannot produce a pairing, and a round that completes at all is one both parties ran with the flag cleared. Neither the partner's cooperation nor its honesty is required for this.
- **A party's view of what its partner receives is enforced at the wire, and bounded by the model.** A partner cannot run a revealing round against a count-only one: the flag mismatch refuses it. What that does not bound is a partner that runs the count-only round faithfully and recovers membership from its own choice of inputs, below.
- **The sender's knowledge of the count is trust-contingent.** In the both-entitled case the number the sender holds is the receiver's report; a receiver that reports a different one is not stopped by psilink. This is the same posture as the `psi` association-table return leg, where the sender's half of the pairing likewise arrives as the receiver's word. A sender that needs the figure to be independently checkable does not get that from psi-c.

**What the rounds still disclose.** Each party's setup or request contains one encrypted element per value it contributed, so the frame's element count is that party's number of distinct, non-repeating values for the key. Set beside the raw row count the terms exchange already states ([Role resolution and work minimization](#role-resolution-and-work-minimization)), that tells the partner how well the key covers the dataset -- a smaller figure for a sparsely populated key. Neither number is the intersection, and neither is hidden by the count-only mode.

#### Threat-model scope of the count-only claim

The count-only claim holds in the semi-honest (honest-but-curious) model this project adopts; see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model). It protects the sender against a receiver that contributes a genuine dataset. It does not protect the sender against a receiver that chooses its input set, and the choice is enough on its own:

- **A crafted set.** A receiver whose input is one live candidate padded with values it knows the sender cannot hold reads that candidate's membership straight off a count of 0 or 1. Nothing distinguishes a crafted set from a genuine one on the wire: both are opaque encrypted elements, and only their number is visible.
- **Differencing across runs.** Two count-only runs whose input sets differ in one value name that value's membership by the difference of their counts. This is the differencing attack SECURITY_DESIGN.md already names for linkage keys, applied to the count, and psi-c's one-round shape makes it cheap to repeat.

Both routes tamper with an input rather than merely observing one, so both sit a step beyond honest-but-curious -- the same category as the record-count manipulation SECURITY_DESIGN.md records for role assignment -- and both are accepted rather than prevented. Preventing them would require binding a party's contributed set to a dataset it cannot choose per run, which nothing in this protocol does.

Neither route is a wire deviation, and the asymmetry runs one way. A receiver cannot weaken the round from its own side: it cannot make the sender return a response in request order, and the flag mismatch stops it from running a revealing round. The only party positioned to waive the count-only property on the wire is the sender -- the party the property protects -- by returning a response whose element order the receiver can attribute. A deviating sender therefore reduces only its own protection, which is why the enforcement above is stated as holding without the partner's cooperation.

Two consequences follow, rather than being left to be derived. First, the count-only property is a property of the algorithm, not of the partner: it says the protocol hands the receiver only a number, not that the receiver cannot arrange for that number to be an answer about one record. Second, psi-c has this scope where it bites hardest. It is the algorithm run to decide whether a data-sharing agreement is worth having -- which is exactly when the signed agreement the honest-but-curious assumption leans on does not yet exist. A count-only run is a disclosure to be weighed on its own terms, not a free look before the real decision.

# Datasets

## Raw data

Data is input as a csv or other tabular data format. These files include rough metadata such as column names and storage types, which can be augmented with [metadata](../EXCHANGE_REFERENCE.md#input-metadata) from the exchange specification. Thus raw data consists of one or more columns, metadata for each column, and a record count.

## Standardized data

A standardized dataset bridges between raw data and the fields expected as inputs to linkage keys. It is an abstraction over the application of [data standardizing](../EXCHANGE_REFERENCE.md#data-standardizing-transformations) transformations. As noted in that section, there can be zero, one, or more than one standardized record for any input, so a standardized data element is essentially a mapping between an index into the raw dataset and a set of strings. These mappings are lazily evaluated and their results are cached. A standardized dataset is a collection of these mappings and the names of the linkage key fields they provide.

## Linkage participation: the role axis

A column participates in matching -- its standardized value is hashed into a PSI set element -- only when the operator roled it `linkage`. There is one binding rule, shared by the dataset builder, the satisfiability pre-flight, and the default-standardization derivation so they cannot drift. A declared [linkage field](../EXCHANGE_REFERENCE.md#linkage-terms) binds to a column when either (1) an explicit data standardizing transformation names the field as its `output` and names as its `input` a column that is not roled something other than `linkage`, or (2) absent such a transformation, the first `role: linkage` column whose semantic `type` equals the field's type. Rule (1) covers two cases beyond the plain one: a named column absent from the metadata still binds the field, which is then reported as unsatisfiable by presence downstream rather than falling through to rule (2); and a named column that is present but roled `identifier`, `payload`, or `ignored` resolves the field to no column at all. So a column roled other than `linkage` is never bound -- even as the only column of its type, and even when an explicit transformation names it: the `role` wins over a contradictory transform, and that contradictory transform *suppresses* the type fallback rather than re-enabling it. A field that binds to no column produces no key input and is reported as unsatisfiable by the satisfiability pre-flight; it is never silently dropped.

This keeps matching participation a separate axis from transmission. Transmission is governed by `is_payload` (a column is sent to the partner when `is_payload` is true and its role is not `ignored`); matching is governed by `role: linkage`. Neither implies the other: a column that both matches and is transmitted is `role: linkage` with `is_payload: true`. Keeping the axes disjoint is what prevents a column the operator marked sent-to-partner, or as a local row identifier, from also being hashed into a cross-party match key without an explicit linkage designation.

This rule would only need revisiting if a disclosure model wanted a column to participate in matching without an explicit `linkage` role -- for example re-deriving participation from semantic `type` alone. The explicit role is required because a matchable `type` is not consent to match: a column roled for another purpose could otherwise be hashed into a key as a side effect of its type, on every linkage path and in the from-scratch authoring defaults, not only on a crafted import.

## Transform regular-expression dialect

Some standardizing transformations include a partner-authored regular expression: the `pattern` of `replace_regex`, `extract_regex`, and `filter_regex`, the `delimiter` of `split_on`, and the pattern `parse_date` builds from its `input_format` (each `MM`/`DD` token expands to `(\d{1,2})`, each `YYYY` to `(\d{4})`, each `YY` to `(\d{2})`, every other character a literal, anchored `^...$`). Tokens are matched greedily longest-first, so `YYYY` consumes its `YY` prefix and `MM/DD/YYYY` never tokenizes a two-digit year. These patterns are compiled and run per row over the other party's data. Because both parties MUST derive byte-identical keys, and the linkage terms are canonically hashed into the exchange-agreement receipt, both parties MUST evaluate every such pattern under one normative dialect; a pattern is otherwise meaningless across implementations (the protocol would inherit "whatever the running engine does"). The dialect is also a security boundary: it admits only patterns that match in time linear in the input, eliminating the catastrophic-backtracking denial of service a backtracking engine allows (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#transform-regex-linear-time-dialect)).

**Engine and semantics.** Patterns MUST be evaluated under an RE2-style engine: a Thompson NFA / lazy DFA that performs leftmost-first matching in time linear in the input length, with no backtracking. The reference implementation uses `re2js` (a pure-JavaScript RE2 port), the same build in the CLI (Node) and the web (browser). Matching is over Unicode code points of the NFC-normalized value. No flags are set: matching is case-sensitive, `.` matches any code point except newline (`\n`), and `^` and `$` anchor the start and end of the whole value (not lines); inline flag groups (`(?i)`, `(?s)`, `(?m)`) within a pattern are permitted. The predefined classes `\d` and `\w` use their ASCII definitions, as JavaScript's do. `\s` is ASCII-only (`[\t\n\f\r ]`) -- note this is narrower than JavaScript's `\s`, which matches Unicode whitespace (a no-break space, a vertical tab, a line/paragraph separator) regardless of the `u` flag; likewise RE2's `.` excludes only `\n`, where JavaScript's `.` also excludes `\r` and the Unicode line separators. These are deliberate consequences of the engine, normative for both parties (who run the same engine, so they agree); an operator bringing a pattern over from a JavaScript engine should account for the narrower `\s` and broader `.`.

**Permitted syntax.** The dialect is the RE2 syntax this engine accepts with no flags: literal characters and escapes, character classes `[...]` (and negated `[^...]`), the predefined and Unicode-property classes (`\d \w \s` and `\p{...}`), anchors (`^ $ \b \B \A \z`), greedy and lazy quantifiers (`* + ? {n} {n,} {n,m}` and their `?` forms), grouping (`(...)`, non-capturing `(?:...)`, named `(?P<name>...)` or `(?<name>...)`), and alternation `|`. The product of the nested counted-repetition bounds applied to any subexpression MUST NOT exceed 1000 (RE2's repeat-count limit): a single `{n}` may range up to 1000, but a nested repetition such as `(x{100}){11}` is rejected because the product of its bounds (1100) exceeds 1000 even though each individual bound is under it. A flat (non-nested) concatenation of repetitions such as `a{1000}b{1000}` is not bounded by this rule -- the engine caps repeat counts, not total program size, so overall pattern size is bounded only by the per-pattern source-length cap of **1000 characters**, enforced at terms validation.

**Excluded.** The dialect MUST NOT include the features RE2 omits, because they require backtracking: backreferences (`\1`, `\k<name>`) and lookaround (`(?=)`, `(?!)`, `(?<=)`, `(?<!)`). The JavaScript `\uHHHH` / `\u{...}` escape is also excluded; use RE2's `\x{...}`. A pattern using any excluded feature, or otherwise not compiling under the engine, MUST be rejected at terms validation, before any row is processed (fail closed); an implementation MUST NOT fall back to a backtracking engine.

**Operation semantics.** `replace_regex` replaces every match (global). The replacement string recognizes `$n` and `$nn` (numbered groups), `$<name>` (named groups), `$&` (the whole match), `` $` `` (the text preceding the match), `$'` (the text following the match), and `$$` (a literal `$`); every other `$`-sequence is emitted literally, INCLUDING a reference with a leading zero (`$01`) and a `$<name>` naming no group in the pattern. Those two are where the rule departs from JavaScript `String.prototype.replace`, which resolves `$01` to group 1 and substitutes the empty string for an unknown `$<name>`: an implementation built on a JavaScript `RegExp` MUST special-case them, or the two parties derive different keys from the same terms. A numbered reference is resolved greedily by digit count where a two-digit group exists (`$12` is group 12 when the pattern has twelve groups, otherwise group 1 followed by a literal `2`), and a reference to a group the pattern does not have is literal. `extract_regex` yields the first capturing group when the pattern has one and it participated in the match; otherwise it yields the whole match. That covers both a pattern with no capturing group and one whose first group did not participate (an unmatched optional group such as `a(z)?` on input `a`). A selected value that is the empty string, or no match at all, yields `null`. `filter_regex` tests for a match anywhere in the value. `split_on` splits the NFC-normalized value on the delimiter; unlike JavaScript `String.prototype.split`, capturing groups in the delimiter are NOT emitted as output elements, and empty parts are discarded. When fewer than two non-empty parts remain, the whole unsplit value is emitted instead, so a leading or trailing delimiter is not stripped: with delimiter `-`, `"SMITH-"` yields `{"SMITH-"}` and `"-SMITH"` yields `{"-SMITH"}`. `parse_date` matches the NFC-normalized value against the anchored pattern built from `input_format`; on no match it yields `null`. From a match it resolves the four-digit year, zero-pads each `MM` and `DD` group to two digits, and requires all three components: if `input_format` has no year token (`YYYY` or `YY`), no `MM`, or no `DD`, it yields `null`. A `YYYY` group is taken verbatim as the year. A `YY` group is resolved to a four-digit year against a fixed protocol pivot: a two-digit `yy <= 68` maps to `2000 + yy`, otherwise to `1900 + yy`, so the window is 1969-2068 (the POSIX two-digit-year convention). So `68` maps to 2068, `69` to 1969, `00` to 2000, and `99` to 1999. The pivot is a normative CONSTANT, identical on both parties by construction: there is no reference year, no agreed-terms date, and no clock read in this path, so two parties resolve every `YY` to the same century and derive byte-identical keys with nothing to agree on. The trade is a fixed cutoff rather than a moving one: a two-digit year can resolve to a year not yet reached (e.g. `50` -> 2050), which does not affect linkage because both parties resolve it identically. The `YY` token appears in an `input_format`; in an `output_format` it is not a substitution target (only `YYYY`/`MM`/`DD` are replaced, below), so a literal `YY` there collapses the year to a constant. It then applies a calendar check through the platform date parser in two parts. First, the assembled `YYYY-MM-DD` is parsed as an ISO 8601 date-only (UTC) value, and a string the parser cannot represent -- a coarse structural failure, a month outside 1-12 or a day outside 1-31 (e.g. month 13, day 32, month or day 0) -- yields `null`. Then the parsed UTC year, month, and day are round-tripped against the captured components, and any mismatch yields `null`. The round-trip is what rejects a day out of range for its specific month: the platform parser rolls such a date over internally, so `02/29` in a non-leap year, `02/30`, and `04/31` each parse to a valid later date whose components no longer equal the captured digits, and the value is dropped rather than passed through. A reimplementation MUST match this exactly -- reject month not in 1-12 and day not in 1-31, and additionally reject any date whose parsed UTC components (year, month, day) do not equal the captured input digits, which is what catches a day its specific month does not have -- to derive identical keys. The result is `output_format` with **every** occurrence of each of `YYYY`, `MM`, and `DD` replaced by its (padded) value, substituted in that order -- all `YYYY`, then all `MM`, then all `DD` -- and every other character left literal. So an `output_format` of `MM-MM-YYYY-DD-DD` over `03/04/2021` yields `03-03-2021-04-04`. An `output_format` that is the empty string MUST be rejected at terms validation, before any row is processed (fail closed), because it would render every date to the empty string; the rejection is on every path partner-authored terms are parsed, and states a fixed message interpolating nothing the partner wrote.

**Versioning.** A change to the permitted syntax, the flag set, the Unicode mode, or the engine's match/replace/split semantics is a wire-compatibility event: it changes what a pattern means or whether it is valid, and two parties running different dialects would silently derive different keys. The linkage-terms [`version`](../EXCHANGE_REFERENCE.md#linkage-terms) field does not by itself prevent this -- it is an operator-authored schema version, compared only for equality between the two parties' authored values, and is not bound to the engine or dialect a party actually runs (two parties can declare the same `version` while running different psilink releases). A dialect change therefore MUST be accompanied by a `version` bump in this specification and requires the two parties to run releases that implement the same dialect; the protocol does not currently negotiate or hash an engine/dialect version at runtime, so this is a process obligation rather than a guarantee the handshake enforces. Binding the dialect to a runtime-negotiated version is tracked as follow-up work.

## Key input data

As defined in [linkage terms](../EXCHANGE_REFERENCE.md#linkage-terms), linkage fields are the inputs that are typically transformed to create the character strings that are concatenated to form statistical linkage keys. The linkage algorithm attempts to connect individuals - not just character strings - represented by their indices in the original dataset. Consequently, key inputs are realizations of linkage fields and are, like standardized data elements, maps between indices and sets of character strings of arbitrary size. In order to realize a complete linkage key, the set of all combinations of all key inputs is computed each and each combination is concatenated together into a string.

When that set has zero elements, i.e. one of the elements is `NULL`, it is omitted from the linkage protocol. When that set has more than one element the record **fans out**: it has several candidate values for that key, each of which enters the round as its own PSI entry, and the record-level pairing is resolved locally, from what the existing message flow already holds. No additional message, frame, or round is exchanged to prune a record whose candidates match more than once. For example, if one party has a member named "Mary Shaye-Smith" and another two members named "Mary Thorne" and "Mary Smith", both of the partner's records are record-level candidates for the same individual. A deterministic resolution rule accepts exactly one of them under a one-to-one cardinality, and the individual leaves the candidate set for every later key either way, so it cannot double-match on a less precise key. The normative rules -- value-level round participation, removal on a potential match, the resolution order and its tiebreak, the width bound, and the one linkage strategy fan-out runs under -- are specified in [Fan-out matching: multi-value key candidates](#fan-out-matching-multi-value-key-candidates).

Fan-out widens what an exchange reveals about one individual, because each candidate value can independently reveal co-possession on a match, and a match on any single candidate is treated as sufficient evidence that two records represent the same person. That is a disclosure an operator opts into rather than one the protocol conceals: the per-(record, key) width is bounded normatively, the disclosure delta it pays is stated with the rules above, and an operator authoring one of these transformations is warned about the consequence.

**Where a candidate set is refused.** A linkage-terms element transform or a standardization step declaring a fan-out function is refused before the exchange runs under any strategy but single-pass (`assertFanOutImplemented`, at the three points [Fan-out runs under single-pass only](#fan-out-runs-under-single-pass-only) names). A candidate set that reaches a strategy is checked there: `linkViaPSI` (the cascade) and the count-only round run one value per record and refuse the set outright, while `linkViaSinglePassPSI` matches a set the party's declared slot width admits and refuses one wider than that declaration. What reaches the strategy check on a single-pass party is therefore a producer its declared width does not account for: multiplicity from a function unlisted in `FAN_OUT_FUNCTION_NAMES`. Each producer the declared factors know -- a fan-out, a `generate_fuzzy_comparisons` -- is accounted for by construction, its element's factor multiplying into the width its key declares. The pre-wire half of that bound covers only what the linkage terms declare -- a prepared exchange retains its built dataset rather than its standardization spec, so a cascade exchange with a standardization-authored fan-out, assembled outside `prepareForExchange`, is refused at the strategy, which is after the terms exchange has run. That refusal is data-dependent: it fires when a row actually splits (a fan-out whose delimiter matches no row runs to completion and narrows nothing), and on a multi-key cascade it fires at the affected key's round, after earlier rounds' elements have been built and exchanged. A splitting row escapes it exactly when realization disposes of its multiplicity first, which happens four ways. A record realizing more candidates than the width bound admits is dropped from that key's round by the bound itself, which is normative behavior rather than a refusal, so an exchange whose every splitting row is over-width runs to completion with those records sitting out the affected keys. A record whose fan-out projects past the assembly cap is likewise dropped, on the projected combination count rather than the assembled set (the width bound's own paragraph records that divergence) -- including a row whose combinations would have collided under the width bound had they been assembled. A record whose realized candidates collapse to a single distinct key string -- two candidates deduplicating to one, or an element transform filtering all but one -- is not refused: its realized set is a singleton, which matching honors as it honors any single-valued key, so matching on it narrows nothing. And a record whose every candidate is filtered away realizes the NULL/absent sentinel and sits the round out, the single-valued rule's own behavior. The collapse and empty realizations are deliberate non-refusals rather than escapes; the two drops do withhold candidates the terms declare, and are the normative exceedance behavior. Every candidate set that survives realization with two or more distinct values reaches the strategy's check: the cascade's refusal, or the single-pass declared-width bound.

The `NULL`/absent omission above is distinct from a realized key that is the *empty string* (`""`). A `NULL`/absent key (the realized set has zero elements) is the "no key" sentinel and the record is omitted from the round; a record whose realized set is the singleton `{""}` has a present, matchable key value and participates in matching like any other single-valued key. It is subject to the same within-dataset uniqueness rule, so a column in which every value standardizes to `""` matches nothing (every `""` is a within-dataset duplicate and is dropped from the round), while a lone `""` on each side matches. This distinction would only need revisiting if `""` were to regain a special meaning at the linkage layer. Because operators author and export their own standardization, `""` is a fully supported key value in matching, and the blank-cell hazard -- a lone blank cell on each side matching spuriously -- is prevented explicitly at the standardization layer (the default per-type cleaning chains map an empty value to `NULL`) rather than silently in the matching code.

# P-256 authenticated key exchange

PSI-Link authenticates every recurring exchange with a P-256 authenticated key exchange: the key-agreement primitive that produces the exchange session key (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#key-agreement-design) for the decision and its rationale). It performs an ephemeral P-256 ECDH keyed together with the pre-shared secret, plus an explicit, role-asymmetric mutual key confirmation, and yields a 32-byte session key with forward secrecy and mutual authentication. The handshake also includes a per-party request-encryption flag and returns a transcript-bound `applyEncryption` decision (`own request OR peer request`) that tells the caller whether to wrap the connection in the application-layer AEAD; see the **Request-encryption flag** discussion below. `authenticateConnection` (in `auth.ts`) runs it immediately after the connection opens and uses the resulting session key to key the application-layer AEAD and the shared-secret rotation. It is implemented as `runKex` in `packages/core/src/kex.ts` and exported from `@psilink/core`. This section specifies the primitive and its wire format.

**Primitive selection.** The governing rule is to prefer a well-respected, ideally audited, dual-platform primitive and to hand-roll only the minimal glue. No production-ready, audited Noise Protocol Framework library with dual Node.js/browser support exists in the JavaScript ecosystem, so none qualifies. Every cryptographic operation in the handshake is therefore a platform `crypto.subtle` call: the ephemeral key generation (`generateKey`), the Diffie-Hellman (`deriveBits` over ECDH), the Noise chaining HKDF and the application HKDF (`deriveBits` over HKDF), SHA-256, and HMAC-SHA-256. No key-establishment path calls a third-party curve library, and no dependency is added. The only hand-written layer is the minimal NNpsk0 glue: the Noise key-schedule mixing and the two confirmation tags. The full Noise framework is not implemented. The Diffie-Hellman is a platform call, never hand-rolled curve math.

**Construction.** The handshake is pinned to the Noise NNpsk0 pattern over P-256 -- no static keys, the pre-shared secret mixed in at position 0, and ephemeral-ephemeral Diffie-Hellman -- followed by an explicit key-confirmation round whose construction is modelled on the bilateral key confirmation of [NIST SP 800-56A Rev. 3](https://doi.org/10.6028/NIST.SP.800-56Ar3) section 5.9.2 -- role-distinct MAC tags over the handshake transcript. The resemblance is to that construction and not to the scheme it is specified for: section 5.9.2 offers the feature for "any key-agreement scheme in which each party is required to own a static key-establishment key pair", and this handshake has no static keys at all, taking its authentication from the pre-shared secret instead. No other section of that publication reaches this handshake either -- section 6.1.2.3 records that "key confirmation is not incorporated for the C(2e, 0s) key-agreement schemes", the ephemeral-only category the Diffie-Hellman here belongs to -- so the citation names a construction the round is modelled on, never one it conforms to. Keying material comes from the Noise chaining key schedule specified below, not from an SP 800-56A / SP 800-56C key-derivation method: [SP 800-56C Rev. 2](https://doi.org/10.6028/NIST.SP.800-56Cr2) section 2 (Scope and Purpose) scopes that document's derivation methods to a shared secret produced by an SP 800-56A or SP 800-56B key-establishment scheme, and its sections 4 and 5 specify the one-step and two-step methods themselves; the chaining schedule is neither, though each of its steps is a single [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) extract-and-expand (see **Key schedule** below).

Every Noise citation in this section is to [the Noise Protocol Framework](https://noiseprotocol.org/noise.html), revision 34 of 2018-07-11. That document specifies the pattern and the processing rules this handshake follows; it does not offer P-256 as an instantiation. Its section 12 defines DH functions for 25519 and 448 and no others, and the `DHLEN` of its section 4.1 is a single constant for both the public-key encoding and the DH output, which a 65-byte uncompressed point and a 32-byte shared secret cannot both be. So the framework is what the construction is built from and not a specification it conforms to; the divergences from a stock NNpsk0 session are enumerated under **Test vectors and interoperability** below.

**Curve and point encoding.** The curve is P-256 (`secp256r1` / `prime256v1`), whose domain parameters -- the field prime, the coefficients, the base point `G`, the order `n`, and the cofactor `h = 1` -- are published in [SP 800-186](https://doi.org/10.6028/NIST.SP.800-186) section 3.2.1.3. [FIPS 186-5](https://doi.org/10.6028/NIST.FIPS.186-5) states no curve parameters of its own: it specifies ECDSA and refers the recommended curves to SP 800-186. An ephemeral public key is encoded on the wire as the **uncompressed** point `0x04 || X || Y` of [SEC 1](https://www.secg.org/sec1-v2.pdf) Ver. 2.0 section 2.3.3: 65 bytes, `X` and `Y` each a 32-byte big-endian field element. That encoding is pinned, not merely preferred. A share of any other length, or of length 65 with any prefix other than `0x04`, is rejected without being decoded -- the compressed (`0x02` / `0x03 || X`, 33 bytes) and hybrid (`0x06` / `0x07 || X || Y`, 65 bytes) encodings of the very same point included. Only the compressed form is SEC 1's alongside the uncompressed one: for a point other than the identity, section 2.3.3 emits those two and no third, and section 2.3.4 admits a leading octet of `0x00`, `0x02`, `0x03` or `0x04` and rejects every other. The hybrid form belongs to IEEE Std 1363-2000 (informative Annex E.2.3.2, which admits `0x06` and `0x07` beside them) and to ANSI X9.62; it is named here because platforms decode it, not because SEC 1 defines it. Two reasons, either sufficient. The transcript binds the wire bytes rather than the decoded point, so a second admissible encoding of one point would let an in-path attacker re-encode a share and desynchronize the two sides' transcripts. And `crypto.subtle.importKey` does not answer the encoding question consistently across platforms (Node decodes compressed and parity-correct hybrid, Chromium decodes compressed and refuses hybrid), so a share's acceptance would otherwise depend on which peer received it. The shared secret is the 32-byte `X` coordinate of the shared point -- the `Z` that SP 800-56A Rev. 3 section 5.7.1.2 outputs from the ECC CDH primitive, which for a cofactor-1 curve is plain ECDH -- and is what `deriveBits` returns for ECDH over this curve.

**Module boundary.** The key schedule is composed in application JavaScript above primitive calls, and sits outside any validated cryptographic module boundary. Where a validated module is configured, it performs every cryptographic operation the handshake makes, all of which reach it through `crypto.subtle` -- the shared-secret computation as `KAS-ECC-SSC` per SP 800-56A Rev. 3 over P-256, and each extract-and-expand as the module's approved HKDF key-derivation function -- `KDA HKDF Sp800-56Cr1`, CAVP certificate A4603, on certificate 5021, the module the FIPS variant image holds ([CONTAINER_IMAGES.md](CONTAINER_IMAGES.md#what-certificate-5021-attests) states both rows and points at the conditions that certificate attaches to them). It does not perform the mixing order, the domain-separation labels, the transcript binding, or the confirmation round, none of which any module certificate attests. In the browser there is no module beneath the platform at all. A composition of this shape yields validated primitives and never a validated protocol -- what a scoped claim may and may not say is in [COMPLIANCE.md](../COMPLIANCE.md#fips-140), and the decision behind the boundary is recorded in [key-establishment-fips-boundary.md](../notes/key-establishment-fips-boundary.md).

**Protocol-version tag.** The Noise "protocol name" is the version tag and is hashed into the initial handshake hash, binding every derived key and confirmation tag to it:

```
protocol_name = "psilink-kex-v2:NNpsk0_P256_SHA256"
```

**A mismatched tag fails the handshake closed, and does so by construction.** The tag is the entire input to `h0`, and `ck0 = h0` (see **Key schedule** below), so two peers on different tags diverge at the first step of both the hash chain and the chaining-key chain. Every later value -- the handshake hash, the chaining key, the session key, and both confirmation tags -- differs, so the confirming peer's tag does not verify and the handshake aborts before any non-handshake frame is sent. There is no path on which two peers on different tags agree on a session key. The previous version, `psilink-kex-v1:NNpsk0_25519_SHA256`, ran the exchange over X25519; a v1 peer and a v2 peer therefore fail closed on this mechanism rather than negotiating, which is the intended and only outcome -- wire compatibility across the curve migration is not offered.

A future authenticated mode (for example a certificate-chain variant) is an additive new version selected out of band on the same mechanism, so the door stays open without any pluggable-auth framework today. The version tag is reserved for a genuine cryptographic-suite change and is not bumped for an additive transcript payload such as the request-encryption flag described below. That flag is a required field on the wire schemas, so a flag-aware and a flag-unaware peer already fail closed at parse -- the flag-aware side rejects a message that omits the required field, and the strict (`.strict()`) schema rejects a message that includes the unrecognized field -- before any transcript is computed.

The four `psilink-kex-v1:` domain-separation labels below keep their own namespace version, which does not track the suite tag: the tag already separates one suite's transcript from another's totally, so re-versioning the labels would change derived bytes without separating anything the tag has not.

**Key schedule** (a minimal subset of the Noise `SymmetricState`: a chaining key `ck` and a handshake hash `h`). `protocol_name` is longer than the 32-byte hash output, so the Noise `InitializeSymmetric` reduces to `h0 = SHA-256(protocol_name)`, and `ck0 = h0`. The NNpsk0 tokens (`-> psk, e` then `<- e, ee`, with an empty prologue) are then processed in order:

```
MixHash("")                       # empty prologue
MixKeyAndHash(psk)                # psk token at position 0
MixHash(e_initiator_public)       # initiator's e: MixHash ...
MixKey(e_initiator_public)        #                ... and MixKey (PSK mode)
MixHash(initiator_flag_byte)      # msg1 payload: initiator's request-encryption flag
MixHash(e_responder_public)       # responder's e: MixHash ...
MixKey(e_responder_public)        #                ... and MixKey (PSK mode)
MixHash(responder_flag_byte)      # msg2 payload: responder's request-encryption flag
MixKey(dh)                        # ee: dh = ECDH(e_self_private, e_peer_public)
```

Each `e_*_public` enters the schedule as its 65-byte wire encoding. Noise states its HKDF's input keying material as zero, 32, or `DHLEN` bytes (section 4.3), an enumeration a 65-byte share sits outside; what makes the schedule well defined anyway is that the RFC 5869 extract beneath it takes an input of any length. `dh` is 32 bytes, so every derived length below is unchanged from a 32-byte-share construction.

Each `*_flag_byte` is a single byte, `0x01` if that party requests the additional application-encryption layer and `0x00` otherwise, MixHash'd as that message's handshake payload right after the party's `e` token. Noise handles a payload differently, in two ways: its `WriteMessage` (section 5.3) takes the payload after every token of the message pattern, which in message 2 is after `ee` rather than after `e`, and it passes the payload through `EncryptAndHash` (section 5.2), which encrypts under the key the `psk` token has already established and MixHashes the ciphertext. The position difference does not change a derived byte, because `MixHash` and `MixKey` touch disjoint state (below); the plaintext-for-ciphertext difference does, and is one of the divergences listed under **Test vectors and interoperability**. It is MixHash only -- the flag need not be confidential and enters `h` alone, so the chaining key (and the confirmation key derived from it) stays flag-independent while `h`, the session key, and both confirmation tags depend on both flags. See the **Request-encryption flag** discussion below.

In a PSK handshake, Noise (rev 34 section 9.2) processes each `e` token with `MixKey(e.public)` in addition to `MixHash(e.public)`, folding the ephemeral public keys into the chaining key as well as the hash; this implementation does both, so the mix chain is faithful NNpsk0. (`MixHash` touches only `h` and `MixKey` only `ck`, so their order within an `e` token does not affect the result, and the flag MixHashes likewise commute with the surrounding MixKey calls; the chaining-key order `psk -> e_initiator -> e_responder -> ee` and the hash order `e_initiator -> initiator_flag -> e_responder -> responder_flag` are what matter, and are preserved.) Here `MixHash(x)` sets `h = SHA-256(h || x)`; `MixKey(ikm)` sets `ck = HKDF-Noise(ck, ikm, 2)[0]`; and `MixKeyAndHash(ikm)` sets `(ck, temp_h) = HKDF-Noise(ck, ikm, 3)[0..1]` then `MixHash(temp_h)`. `HKDF-Noise(ck, ikm, n)` is the Noise chaining HKDF (Noise rev 34 section 4.3): `temp_key = HMAC(ck, ikm)`, then `output_i = HMAC(temp_key, output_{i-1} || byte(i))` for `i` in `1..n` (with `output_0` empty). This equals RFC 5869 HKDF with `salt = ck` and an empty info string, and is issued as exactly that: one `crypto.subtle` HKDF `deriveBits` call for `n * 32` bytes, split into the `n` blocks. The equality is what makes the two forms interchangeable, and the vector generator writes out the HMAC chain while the implementation issues the single call, so the two are checked against each other on every run.

After the tokens, the session key and a distinct confirmation key are derived, and the two confirmation tags computed, using the application HKDF (`hkdfDerive`: HKDF-SHA-256, 32-byte zero salt, named info):

```
session_key       = HKDF(ck || h, "psilink-kex-v1:session", 32)
confirm_key        = HKDF(ck,      "psilink-kex-v1:confirm", 32)
initiator_confirm  = HMAC(confirm_key, "psilink-kex-v1:initiator-confirm" || h)
responder_confirm  = HMAC(confirm_key, "psilink-kex-v1:responder-confirm" || h)
```

Deriving `session_key` over both `ck` (which holds the pre-shared secret and the ECDH shared secret) and `h` (which holds the protocol-version tag, both ephemeral public keys in role order, and both request-encryption flags) is the critical invariant. The session key depends on the ephemeral DH output, so it is neither the pre-shared secret alone -- which would have no forward secrecy -- nor the raw ECDH output alone, which would not be transcript-bound. The confirmation key is independent (distinct input keying material and a distinct label), and the two confirmation tags are role-asymmetric (distinct labels) and each binds the full transcript hash `h`. All labels here are namespaced `psilink-kex-v1:`. **The domain-separation label space.** The system's derivation labels form one disjoint space, enumerated here and cited from the sections that use each family: `psilink-kex-v1:*` (the session and confirmation derivations above), `psilink-aead-v1:*` (the application-layer AEAD), `psilink-shared-secret-rotation-v1` (the rotation below), `psilink-abort-token-v1:*` (the file-sync abort marker), `psilink-webrtc-peerid-v1:*` (the rendezvous peer ids below), and the `psilink-signing-*` labels (the certificate, receipt-content, and receipt-payload derivations). No derivation under one family can collide with one under another.

**Message flow** (initiator sends first; all messages are JSON objects; `e` is a base64url-encoded 65-byte uncompressed P-256 point, 87 base64url characters unpadded; `confirm` is a base64url-encoded 32-byte HMAC-SHA-256 tag, 43 characters; and `reqEnc` is the party's request-encryption boolean):

1. Initiator -> Responder: `{ kexMsg: "1", e: e_I, reqEnc: req_I }`
2. Responder -> Initiator: `{ kexMsg: "2", e: e_R, confirm: responder_confirm, reqEnc: req_R }`
3. Initiator -> Responder: `{ kexMsg: "3", confirm: initiator_confirm }` or `{ kexMsg: "abort" }`

The responder confirms first (in msg2); the initiator verifies `responder_confirm` before sending its own confirmation in msg3, and the responder verifies `initiator_confirm` on msg3. A mismatched pre-shared secret therefore fails closed on both sides before any non-handshake frame is sent. Each side sends the tag for its own role and verifies the tag for the opposite role, so a reflected or echoed confirmation does not verify.

**Request-encryption flag.** Each party declares, on its own handshake message (`req_I` on msg1, `req_R` on msg2), whether it wants an additional application-encryption layer over the post-handshake connection. The flag is a required field on the strict message schemas. Both parties therefore hold both flags before the key schedule runs, so both compute the same negotiated decision `apply_encryption = req_I OR req_R` and bind both flags into the transcript hash `h` (as the per-message handshake payload, above) with no extra message or round-trip. Because `h` feeds both confirmation tags, a flag flipped on the wire makes the two sides derive different transcripts and the confirmation fails closed: the handshake cannot be downgraded to an encryption decision the parties did not agree on. The negotiation is a single fixed-meaning boolean, not an extensible options block -- open-ended in-handshake negotiation is the historical home of downgrade bugs. `runKex` returns `apply_encryption` as `KexResult.applyEncryption`; the caller applies the AEAD layer (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security)) when it is true and a session key is in hand. File-sync transports (SFTP, file-drop) request it unconditionally; a transport already end-to-end confidential against any in-path party (for example WebRTC over DTLS, except under a DTLS-terminating WebSocket relay) declines it.

**Peer-share validation.** A peer's `e` is validated in two layers before it reaches the Diffie-Hellman, and the split between them is deliberate:

1. **Encoding, in application code.** The decoded share must be exactly 65 bytes with the `0x04` prefix (see **Curve and point encoding** above). Anything else is rejected without being decoded.
2. **Point validity, by the platform.** The share is then imported through `crypto.subtle.importKey`, which rejects a point that is not on the curve, a coordinate at or above the field prime, and both byte strings a peer might send for the identity element. Those two strings are SEC 1's single `0x00` octet, which is the only encoding it gives the point at infinity (section 2.3.3 step 1), and the all-zero uncompressed string `0x04 || 0^32 || 0^32`, which SEC 1 section 2.3.4 reads not as the identity but as the point `(0, 0)`, off the curve. Driving the real API is what establishes this, on each platform, rather than assuming it; `packages/core/test/kex.test.ts` and the browser suite each make the measurement on their own platform.

P-256 has cofactor 1, so there is no small-order subgroup for a share to land in and the point at infinity is the whole of the degenerate case -- the contributory-check rationale behind the X25519 construction does not transfer. [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748) section 7 states that rationale for the curves that document defines and rests it on their cofactors of 8 and 4, which let an input point of small order eliminate the other party's contribution. The all-zero check it points at (Section 6, whose detection prose sits in 6.1 with 6.2 cross-referencing it) is the detection for exactly that case, and neither the cofactor assumption nor the check it motivates applies to a cofactor-1 curve. An all-zeros shared secret is nonetheless still rejected, as a stated safety check rather than as the validation: the platform's rejection of the identity is a measured behavior rather than one this project controls, and a platform that admitted such a share would otherwise yield a shared secret an attacker knows, costing the handshake its forward secrecy silently.

**Failure handling.** All wire schemas use strict (`.strict()`) Zod parsing, so an unexpected field fails the parse. Tag comparison is constant-time. Every authentication failure throws a single generic, non-oracular error (`"key exchange authentication failed"`) that does not reveal which check failed; a silent peer reports the distinct `"key exchange handshake timed out"` after a 30 s per-message bound. Every receive-side failure before the final message sends a best-effort `{ kexMsg: "abort" }` so the peer stops waiting immediately rather than blocking until the timeout.

**Test vectors and interoperability.** The chaining-key chain above -- `psk`, then each `e`, then `ee` -- is faithful Noise NNpsk0, but the overall handshake is pinned by psilink's own checked-in known-answer vector (`packages/core/test/vectors/kex-vectors.json`) rather than being wire-compatible with generic Noise. Four things diverge from a stock Noise NNpsk0 session. The Diffie-Hellman is over P-256, which the framework's section 12 does not specify. The protocol name differs, so the initial `h` differs. Each message's payload is a flag byte MixHash'd in the clear where Noise would `EncryptAndHash` it. And instead of Noise `Split()` the session key uses a custom KDF over `ck || h` with an added explicit confirmation round. So no end-to-end Noise vector corresponds. What does correspond is the underlying machinery, cross-checked against published references in `packages/core/test/kex.test.ts`: the Noise chaining HKDF against [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) test case 3, and the P-256 scalar multiplication and ECDH against the key pair published in [RFC 6979](https://www.rfc-editor.org/rfc/rfc6979) section A.2.5 over the base point [SP 800-186](https://doi.org/10.6028/NIST.SP.800-186) publishes. There `ECDH(d, G)` and `ECDH(1, U)` must both produce the published `U` X coordinate, so a wrong curve, a wrong base point, or a wrong shared-secret convention breaks the anchor. The vectors fix the pre-shared secret and both ephemeral private keys and record, for all four `(initiator, responder)` request-encryption flag combinations, the handshake hash, session key, and both confirmation tags (the chaining key and confirmation key are flag-independent and recorded once). They are reproduced by the independent generator at `packages/core/test/vectors/generate-kex-vectors.mjs`, which composes the schedule from Node's OpenSSL-backed `crypto` rather than from WebCrypto. The same file is run against the browser build in real Chromium by `apps/web/test/browser/kex.test.ts`, so a CLI peer and a web peer are shown to derive an identical session from an identical transcript.

## Shared-secret rotation

The pre-shared secret that authenticates a recurring exchange is a 32-byte value encoded as unpadded base64url (43 characters). Two mechanisms mint one, differing only in how the 32 bytes are produced:

- **Invitation tokens** are generated directly from a CSPRNG (`crypto.getRandomValues`), giving 256 bits of entropy.
- **Rotation tokens** are derived from the 32-byte session key (above) with the application HKDF (`hkdfDerive`: HKDF-SHA-256, 32-byte zero salt). The session key mixes the pre-shared secret with the ephemeral P-256 Diffie-Hellman, so a rotated secret is a full 32-byte value that stays secret against any party that does not hold both inputs; against a party that holds the superseded secret, its confidentiality rests on the ephemeral exchange alone, the ~128-bit P-256 forward-secrecy level:

```
rotated_secret = HKDF(session_key, "psilink-shared-secret-rotation-v1", 32)
```

The rotation runs after every successful handshake and before the data exchange begins: both parties recompute it independently from the shared `session_key`, so it adds no message or round-trip, and each persists the result as the secret for the next exchange. The `psilink-shared-secret-rotation-v1` info string is a single fixed label, not a per-party or per-context family, and sits in the disjoint [domain-separation label space](#p-256-authenticated-key-exchange) above, so a rotated secret can never collide with a session, AEAD, abort-marker, peer-id, or signing derivation.

The operator-facing rotation policy -- that the secret is never reused, that a rotated token has no expiry by default, and the recovery path when the two parties' tokens desynchronize -- is in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#recurring-exchange-authentication).

### `expires` enforcement and the 'expiring soon' advisory

A `.psilink.key` token may hold an `expires` instant written by either of two mechanisms: an invitation setup lifetime or the `token_max_age_days` policy. Enforcement is kind-agnostic by construction: it reads only the stored `expires`, never its origin, and the same recovery (re-invite) applies to both. So no consumer branches on origin and no provenance marker is stored. A marker would add state to the key file without changing any decision taken from it, and could be present on one party's key file and absent on the other's, in a model whose recoverability depends on both parties holding uniformly-interpreted key files. The operator-facing policy is in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#token-age-and-rotation-policy).

**Enforcement sites.** Four checks read `expires`. Three are kind-agnostic and abort on any `expires` at or before the current time, directing both parties to re-invite: the load-time check before an exchange, the pre-handshake check, and the post-handshake check (which catches a token that lapses during the key-exchange round-trip). The fourth, the accept-time invitation check, is the only single-kind site -- unavoidably, since it validates the encoded invitation, which holds only an invitation lifetime. An invitation whose expiry cannot be compared -- the `expires` string does not parse, or the local clock does not -- is treated as expired there rather than accepted. There is no expired state in which the two kinds call for different recovery, so the expired-side message is uniform by intent rather than branched on origin.

**'Expiring soon' threshold.** The advisory fires when the loaded `expires` is within `token_max_age_days / 3` days of the current time -- a fraction of the configured age rather than a fixed number of days, so it scales with the policy (a 90-day age warns with 30 days remaining, a 30-day age with 10) and is silent unless a policy is configured. It is suppressed when the exchange that reports it succeeds (rotation then stamps a farther-out `expires`) and shown only when no successful rotation refreshed the token -- a failed exchange.

**Invitation token flagged 'expiring soon'.** Because the advisory does not consult origin, a freshly minted invitation token can be flagged. This is reachable only on the offline re-invitation path (the inviter's key file is the only one that persists an invitation `expires`; the acceptor's offline key file holds none, and the online flow persists only the rotated token), before the first exchange rotates the token, and it survives only past a *failed* first exchange. The notice is accurate and its guidance is correct for either kind, so it is accepted rather than suppressed; suppressing it for invitation tokens alone would require persisting a per-file origin marker -- the invisible cross-party state the unified representation avoids.

**Design rationale.** The unification rests on the two sources sharing one recovery. No migration arises: an existing key file holds a bare `expires`, which is exactly what the uniform interpretation reads. It would need revisiting only if an expired max-age token were ever made recoverable without re-invitation, so that the expired-side action diverged by origin -- not the case today.

## WebRTC rendezvous peer-id derivation

The WebRTC transport meets its peer with no coordination backend: both parties derive their PeerJS rendezvous peer ids deterministically from the invitation's 32-byte shared secret, so each side computes the other's id locally and they rendezvous on the PeerJS signaling broker without exchanging an id out of band. This precedes and is independent of the P-256 handshake above -- it places the two parties on the same WebRTC connection, over which the handshake then runs.

The derivation is HKDF-SHA-256 over the decoded 32-byte shared secret as input keying material, with a 32-byte zero salt (matching the application `hkdfDerive` above) and a role-separated info string:

```
inviter_info  = "psilink-webrtc-peerid-v1:inviter"
acceptor_info = "psilink-webrtc-peerid-v1:acceptor"
peer_id       = hex(HKDF-SHA-256(ikm = secret, salt = 0x00 * 32, info = role_info, 32)[0..15])
```

The peer id is the first 16 bytes of the HKDF output, encoded as lowercase hex. Hex (not base64url) is used because the PeerJS client rejects an id with a leading, trailing, or doubled `-` or `_`, which base64url output can contain. The inviter listens on its derived id (`inviter_info`) and the acceptor dials it.

This is a cross-implementation contract: both implementations compute the same ids from the same shared secret, which is what lets a CLI party and a browser party rendezvous with each other (see [`cli-webrtc-stack.md`](../notes/cli-webrtc-stack.md)). On the CLI the role half of the derivation comes from the connection's `role` field, stamped by `psilink invite` and `psilink accept`; the browser takes it from which rendezvous function runs. The `psilink-webrtc-peerid-v1:` labels sit in the disjoint [domain-separation label space](#p-256-authenticated-key-exchange) above.

**Conformance vectors.** The contract is pinned by a checked-in known-answer vector at [`packages/core/test/vectors/webrtc-interop-vectors.json`](../../packages/core/test/vectors/webrtc-interop-vectors.json), on the precedent of `kex-vectors.json` above. It fixes one shared secret and records both derived ids, the encoded invitation a browser inviter mints from it (the whole base64url string, plus the canonical JSON body the checksum covers), and the signaling locator that invitation holds. It also records the locators a CLI inviter mints from a `ws:`/`wss:` URL together with the broker location both applications must resolve each of them to, and each side's pairing of rendezvous role to key-exchange handshake role and request-encryption flag. Both mint directions are recorded because each application resolves an absent locator field to a default of its own (see [WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#broker-socket)), so a locator is a contract only where what it omits is pinned as well as what it states. `generate-webrtc-interop-vectors.mjs` beside it reproduces the derivations from Node's OpenSSL-backed `crypto` rather than from WebCrypto, and restates the invitation body's key order literally rather than reading it off the schema. The divergence this guards against lives in each application's own call sites rather than in the shared library. So every application asserts its own construction against the file from its own suite -- the ids it registers and addresses, the token it consumes, the role and flag it hands the handshake -- rather than one test computing both sides through a single path. Each flow that reads the side-to-role table is driven through its own entry point rather than through the table. The derivations that run on `crypto.subtle` -- the peer ids and the invitation checksum -- are additionally run against the browser build in real Chromium by `apps/web/test/browser/webrtcInterop.test.ts`, as `kex-vectors.json` is, since which bytes a platform produces is a property of that platform.

# Post-linkage steps

## Third-party-verifiable proof of a data flow

> **Implemented (certificate mode, CLI):** The signing identity that certificate-backed receipts rest on -- key generation, the self-signed certificate, fingerprint pinning, and the identity binding -- is implemented and specified under [Signing identity and certificate pinning](#signing-identity-and-certificate-pinning) below. The signing/exchange step -- both parties signing the same canonical receipt content and swapping signatures over the live channel to produce one dual-signed record -- is implemented for the CLI's authenticated file-sync exchanges when a `signing` block with `mode: certificate` is configured; see [The signed-receipt step](#the-signed-receipt-step) below and, for the signed byte layout and the dual-signed record format, [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#signed-receipt). Verifying a stored dual-signed record is implemented too, in `@psilink/core` and behind both `psilink verify-receipt` and the web app's "Verify a receipt" page; see [Verifying a stored dual-signed record](#verifying-a-stored-dual-signed-record) below. The session-derived MAC mode is not implemented; only the certificate mode is.

A receipt is produced at the conclusion of a successful exchange, after the result - and any payload columns - already exist on both sides. The receiver learns the intersection during the PSI rounds themselves: the association map is computed and shared as a step of the matching algorithm, and payload columns are transmitted immediately afterward. By the time a receipt could be assembled both parties already hold the result, so the receipt is a post-exchange audit artifact recording that the exchange occurred. It does not gate, withhold, or otherwise condition delivery of the result; the result is already in hand on both sides.

Each receipt records the timestamp, a hash of the exchange agreement, each party's `identity` (the self-asserted [`linkage_terms.identity`](../EXCHANGE_REFERENCE.md#linkage-terms) field), and the size of the result if that information was learned by both parties. That field is optional in the terms, and a receipt is the one artifact an unnamed party cannot take part in: the identity is what the certificate must authorize, so a party with none has nothing to be authorized against. A run with signing configured and either side unnamed is refused rather than producing an artifact whose identity binding could not be checked, and it is refused at terms agreement -- the first point at which both sides' identities are in hand -- so no linkage key and no payload row moves under a run that cannot finish. The hash of the agreement and the signature over the receipt are computed over a canonical byte serialization ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785), JSON Canonicalization Scheme) so that both parties - and an independent third party using a different implementation - derive byte-identical input and the hash and signature verify across implementations. That serialization is specified in [CANONICAL_ENCODING.md](CANONICAL_ENCODING.md). The two parties then swap signed receipts and each retains the other's. A receipt can be signed in one of two modes, which differ sharply in what they prove:

- **Session-derived (symmetric).** The signature is a MAC under the shared key-exchange session key. Both parties hold the same key, so either can forge a MAC the other could have produced. A session-derived receipt is therefore not evidence against a denying counterparty and is not verifiable by any third party; it yields only a tamper-evident local record - a party can later detect that its own stored copy was altered, but cannot use it to hold the partner to the exchange. This mode does not provide non-repudiation.
- **Certificate-backed (asymmetric).** The signature is made with a party's long-lived signing private key, whose self-signed certificate the partner has pinned by fingerprint out-of-band at setup. Only the holder of that key could have produced the signature, and the pin ties the key to the partner, so the signature is verifiable by anyone who holds (or is given) the pinned fingerprint -- it does not depend on a certificate-authority chain. This is the only mode that provides non-repudiation, and the only mode in which the `identity` field has evidentiary weight: the certificate binds the asserted identity to the pinned key, whereas a session-derived receipt leaves it an unverified label. The signing identity, certificate format, fingerprint pinning, and the identity-binding rule are specified under [Signing identity and certificate pinning](#signing-identity-and-certificate-pinning) below.

Because the receipt is collected after the result already exists on both sides, the signature swap is best-effort evidence, not a fairness or atomicity guarantee. Two limitations follow directly. First, the swap is not a fair exchange: a party may receive the partner's signature and then decline to send its own, and no protocol step can compel the second signature once the first has been handed over. Second, aborting does not undo the data exchange: because both parties already hold the result, terminating the program and restarting does not roll the data back. An aborting party can capture the partner's signature, withhold its own, and still keep the intersection. Restarting the exchange is not a remedy for data already transferred; it only repeats the work.

Even under the certificate-backed mode, a receipt proves narrowly. It evidences only that a specific data set flowed between these two parties -- the agreement and result it commits to, produced third-party-verifiable in that mode. It does not prove where either party's data came from (provenance), that the data is accurate, or that either party satisfied a legal or contractual obligation; those remain matters outside what the receipt can attest.

Retention, access controls, and log integrity beyond the receipt remain each party's internal compliance obligation.

## Signing identity and certificate pinning

**Error surface and exit codes.** A local signing failure -- an identity file that is malformed, unreadable, holds a key that is not a valid P-256 point, or whose private key is not its certificate's -- raises `SigningError`, a usage-error subclass, so the CLI exits 64 (EX_USAGE); these are genuine usage and configuration errors. Partner-trust failures (a mismatched pinned fingerprint, a partner certificate whose self-signature does not verify, a certificate that does not authorize the agreed-terms identity) are security events and are not reported that way. [The signed-receipt step](#the-signed-receipt-step) wraps them in `ReceiptVerificationError`, a security-kind `ConnectionError`, which the CLI reports as a failed exchange (exit 69) rather than as an exit code indistinguishable from a malformed flag.

Certificate-backed receipts rest on a long-lived **signing identity**: an asymmetric keypair and a self-signed certificate that states the party's `identity`. Each party generates one (`psilink fingerprint`, configured by the [`signing`](../EXCHANGE_REFERENCE.md#signing) block), persists it, and reuses it across every exchange and every partner -- it is not a per-exchange credential. It is therefore a distinct credential from the shared secret in the key file, which rotates every exchange: the signing key must be stable for its whole life so that a fingerprint a partner pinned once keeps verifying later receipts. Regenerating the identity is a deliberate act (`psilink fingerprint --force`) that produces a new key and a new fingerprint and invalidates any fingerprint a partner has already pinned.

The trust model is **pinned self-signed**: there is no certificate-authority chain and no revocation. A self-signed certificate proves only possession of its own key, not who the holder is; the binding to a real partner is established out-of-band, the same way the parties already exchange the invitation and shared secret. The certificate's **fingerprint** -- an unpadded base64url `SHA-256` over the domain-separated canonical encoding (RFC 8785) of the certificate body -- is shared with the partner over a trusted channel and pinned in the partner's `signing.partner_fingerprint`. The fingerprint is not secret (it is a hash of a public certificate), so the channel must be authentic, not confidential. This is the SSH-host-key / certificate-pinning model, not the web-PKI model. The rationale for choosing it over X.509 + CA for v1, and the point by which an authority-backed mode could layer on later, are in [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#receipt-signing-identities).

The certificate is a small canonical-JSON document rather than an X.509 structure, so the bytes that are signed and fingerprinted reuse the project's single canonicalization primitive (the same one the agreed-terms hash and the record commitments use) and reproduce across implementations; that serialization is specified in [CANONICAL_ENCODING.md](CANONICAL_ENCODING.md).

**Certificate body.** The body has a format `version` (`psilink-signing-cert/v2` -- the single recognized literal, rejected rather than migrated if unrecognized, and also the format discriminant a future authority-backed representation would extend), the signature `algorithm` (`ecdsa-p256-sha256`), the party's `identity`, and the public key as a JWK. The on-disk signing identity -- the private key plus the certificate it issued -- has its own discriminant, `psilink-signing-identity/v2`. Both move together with the signature scheme and the public-key representation, so a document written under either earlier version is refused outright rather than reinterpreted. The `identity` a presented certificate states is bounded in length when the certificate is read but is not held to the [terms document's control-character rule](../EXCHANGE_REFERENCE.md#linkage-terms); display escaping at the surface that shows it governs how it renders.

**Public key.** An EC JWK -- the key format of [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517), whose elliptic-curve members are specified in [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518#section-6.2) section 6.2 -- with `kty` `EC`, `crv` `P-256` (section 6.2.1.1), and the two affine coordinates `x` and `y` (sections 6.2.1.2 and 6.2.1.3). Each coordinate is **exactly 32 bytes in canonical unpadded base64url** (43 characters), left-padded to the field size. The fixed length is the RFC's own requirement -- each coordinate octet string "MUST be the full size of a coordinate for the curve" -- and unpadded is what base64url means in JOSE, a term RFC 7518 section 2 takes from the JWS specification (RFC 7515) rather than defining. The encoding is pinned, not merely preferred: the fingerprint a partner pins is a hash over the body's literal JWK strings, so a second encoding of one point would be a second fingerprint for one key. A coordinate with a leading zero byte (33 bytes) and a coordinate written with base64 padding are each rejected, though `crypto.subtle.importKey` decodes both to the same point. Below that pin, the load rejects a point that is not on the curve, a coordinate at or above the field prime, and the identity element -- which, P-256 having cofactor 1, is the whole of the degenerate case, so there is no small-order subgroup to reject separately.

**Signature.** ECDSA over P-256 with SHA-256, over the domain-separated canonical bytes of the body under the body's own public key, encoded as the **fixed-length 64-byte raw `r || s`** of IEEE Std 1363-2000, unpadded base64url. That standard's own signature output is a pair of integers; the octet-string form cited here is its informative Annex E.3.1, which converts each of the pair to an octet string of the group order's length -- leading zeros kept -- and concatenates them, and which offers the DER structure beside it as the other option. So the citation names a format, not a requirement, and the requirement is this document's. The encoding is pinned to that form: a signature field that decodes to any other length is rejected on load with a message naming the length seen, and a DER `SEQUENCE` of the same two field elements is refused on its length rather than decoded. `crypto.subtle` emits and accepts only this encoding, so the DER latitude that makes ECDSA a canonicalization hazard elsewhere does not arise through this call surface.

**Fingerprint.** A SHA-256 over the body encoded under a distinct domain label, so a signature and a fingerprint can never be confused for one another. It covers the body and never the signature, which is what keeps it a known answer for a given key and identity: ECDSA signing is randomized, so two certificates over one body have different signatures and the same fingerprint.

**Properties of the scheme.** ECDSA over P-256 is chosen because it is on the approved-algorithm list of the FIPS 140-3 certificate this project targets and is reachable through `crypto.subtle`, so where a validated module is configured it performs the operation. Three properties an EdDSA scheme would supply are not available and are not relied on anywhere. Signing is **randomized** (WebCrypto exposes no RFC 6979 deterministic mode), so a signature is not a known answer and the checked-in vectors are verify-only. Signatures are **malleable** in `s`: a holder can negate it and produce a different 64-byte signature that still verifies. That is why nothing in this project hashes, commits to, dedupes, or identifies by a signature, and why [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#dual-signed-record-file) states the two parties' artifacts agree by copying rather than by re-derivation. And key generation is **unseedable**, so a reproducible identity is built from a fixed private-key JWK rather than a seed. The single canonical signature encoding is retained by the pin above.

**Module boundary.** Both signing operations -- this certificate self-signature and the receipt signature specified below -- run through `crypto.subtle`, so key generation, signing, and verification are platform calls that a validated module configured beneath the platform performs. ECDSA is on the approved-algorithm list of the FIPS 140-3 certificate this project targets; a claim naming the curve and hash is written by reading that certificate's tested parameter set at the time the claim is made. Two limits stand regardless. The browser build of `@psilink/core` has the same signing path with no module beneath it at all. And the bytes being signed are an application composition that no certificate attests: the canonical encoding, the domain separation between the signature and fingerprint labels, and the per-signer binding below. What a scoped claim may and may not say is recorded in [receipt-signing-fips-boundary.md](../notes/receipt-signing-fips-boundary.md).

No per-runtime adapter is needed for either operation. ECDSA over P-256 is universally available in browser WebCrypto and `apps/web` runs the same core code, so the web app follows the CLI by rebuild alone; the browser cross-implementation suite is what holds that.

Two checks gate accepting a certificate-backed receipt, and both must pass before the receipt is accepted:

- **Pinning.** A presented partner certificate is trusted only if its self-signature verifies and its fingerprint matches the configured `signing.partner_fingerprint`. A certificate presented when no fingerprint is pinned, one whose self-signature does not verify, and one whose fingerprint does not match the pin are each rejected with a clear error. The fingerprint comparison is constant-time.
- **Identity binding.** A receipt is accepted only if the identity asserted for the presenting party is the one the certificate authorizes. In the signed-receipt step the asserted identity is the partner's *agreed-terms* identity (`partnerTerms.identity`), so the pinned certificate must authorize the identity the partner used in the terms it agreed -- not merely restate the certificate's own stated identity, which would make the check a tautology. Because `identity` is self-asserted free text (`Consistency: none`, and single-line by the schema rule that refuses a control character -- a line break included -- when the terms are parsed), the rule is an exact match of the full identity. It is compared over the same canonical `identity` bytes the record commits to and the receipt signs, so the certificate check and the signed record agree on what "identity" is. A party that uses a different identity string needs a different certificate (a deliberate regeneration); the certificate authorizes exactly the identity it states. A pair either side of which states no identity in its agreed terms is refused at terms agreement, before any linkage key, payload row, certificate, or signature crosses the channel: there is no asserted identity for the binding rule to compare, and substituting one would make the check vacuous. The same condition is held again at the swap itself, so the binding rule is never reached with a side unnamed.

## The signed-receipt step

The step runs at the conclusion of a successful exchange, after the payload exchange, and only when a signing identity and the session key are both present -- an exchange with no key exchange (the web app) or no signing identity takes the unsigned-record path alone. Both parties sign one set of canonical **receipt-content** bytes and swap signatures over the live channel, producing a single **dual-signed record** that holds both parties' certificates and signatures. The step is evidence collection over the completed exchange, not a gate: the result and payloads already exist on both sides, so it neither withholds nor conditions the result. The dual-signed record's byte layout and file format are in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#signed-receipt).

**What is signed.** The receipt content covers only facts *both parties derive byte-identically*, so a signature over them is checkable against either party's view. Those facts are the agreed-terms hash (both compute the same value), a **session-keyed MAC** of the committed payload that flowed in each direction (keyed by the fixed initiator/responder direction under a per-direction key derived from the session key -- each party holds both directions and the session key, so both reproduce both MACs), and the per-exchange binder below. Keying the directional payload values off the session key -- not a bare hash -- keeps a third-party receipt holder, who has neither the session key nor the flowing data, from recomputing a MAC or brute-forcing a low-entropy payload from it, and keeps the no-data direction from being a public constant that would leak payload presence. The MAC keys are derived at sign/verify time and never stored in the receipt. One-party-only facts (a party's `records_exposed`, its retention pointer) and the *salted* record commitments (per-party fresh salts, so not byte-identical across parties) are excluded; the association-table pairing is excluded too, because a one-sided exchange leaves the helper without it, so it is not a fact both parties hold. The exact byte layout is specified in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#signed-receipt).

**Per-signer binding.** Each party signs bytes that bind its *own* certificate fingerprint and handshake role alongside the shared content, so the two `{ certificate, signature }` blocks are **not interchangeable**: a holder cannot swap them to re-attribute a direction's payload to the wrong party. A verifier reconstructs the partner's signed bytes from the shared content, the partner's *pinned* fingerprint, and the partner's role (the opposite of the local role), so a swapped block fails. The shape is therefore shared content plus per-signer binding, not byte-identical bytes signed twice; the exact byte layout is specified in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#signed-receipt).

**Replay binder.** The content includes a per-exchange **binder**: a 32-byte tag derived one-way from the session key via `HKDF-SHA-256` with the info string `psilink-signed-receipt-binder-v1:<role>` (`<role>` being `initiator` or `responder`), matching the derivation discipline of the AEAD keys and the abort token. Both parties fold in the *initiator-role* binder, so they compute the same value with no extra messages, and neither party unilaterally controls it (it is a one-way function of the mutually-derived session key). Because a different exchange has a different session key and hence a different binder, a receipt from one exchange does not verify against another: a signature over this exchange's content cannot be presented as evidence of a different one.

**Certificate check before signature, fail-closed.** Each party transmits its self-signed certificate in-band alongside its signature. On receiving the partner's frame, the receiver first trusts the certificate by pin: self-signature valid, fingerprint matches the configured `signing.partner_fingerprint`, and the certificate authorizes the identity the partner used in the *agreed terms* (`partnerTerms.identity`, not the certificate's own stated identity, which would make the check a tautology). *Only then* does it verify the signature over the locally-recomputed content bound to the partner's role. A missing pin, a self-signature that does not verify, a fingerprint mismatch, or a certificate that does not authorize the agreed-terms identity each terminates the exchange *before* the signature is examined. So a partner whose certificate is not the pinned identity, or whose pinned certificate is bound to a different identity than the one it agreed terms under, is rejected without its signature ever being trusted. A pin/signature failure raises a security-kind `ConnectionError` (a `ReceiptVerificationError`), distinct from a plain transport drop, which the CLI reports as a failed exchange (exit 69).

**Wire ordering.** The signature swap follows the existing control-frame convention (see the payload exchange above): deterministic sender ordering -- the initiator sends its `{certificate, signature}` frame then receives and verifies the partner's; the responder receives and verifies first, then sends its own terminal frame. The responder verifies *before* it sends, so a fingerprint or signature failure terminates without disclosing its own signature. The receipt content itself is never on the wire: both parties recompute it locally from state they already hold, so a partner that signed different content simply fails verification.

**An unpinned certificate-mode configuration is refused before the exchange runs.** A `signing` block in `certificate` mode that has no `signing.partner_fingerprint` is refused as an operator configuration error, before any credential, terms, or data are sent, on every front end -- the same class of refusal an unimplemented `signing.mode` takes, and enforced once in `prepareForExchange` so both applications inherit it. The outbound-consent prompt may precede the refusal on any CLI leg; host-key trust establishment may precede it on the sftp leg. The two paragraphs above are the reason. The swap is the last step of a *successful* exchange, so such a run discloses this party's keys and payload, reaches the swap, and terminates there against the missing pin -- with no result and no receipt written locally, since those are written after the exchange returns. And by the wire ordering, on the leg that sends its frame first the partner also holds this party's signed receipt when the run stops. What the run does leave is the [self-attested record](#self-attested-record) of the disclosure it already made, marked as a terminated run's. Nothing about the partner or the network can make the run finish, and no invitation or acceptance path supplies the pin later -- the `signing` block is only ever the local party's own configuration -- so the outcome is settled while the operator is still configuring. The requirement is *not* part of the block's schema. Keeping the cross-field rule out of it lets a partially-authored config -- no partner fingerprint yet -- still parse wherever the schema is used, and a reader that needs only `identity_file`, such as `psilink fingerprint`, reads it from the raw config text rather than through the schema. The gate itself is the exchange path's own assertion. The same gate covers the other locally-knowable way a `certificate`-mode run cannot finish -- local terms stating no `linkage_terms.identity`, which the swap refuses for the reason given under **Identity binding** above -- refused in `prepareForExchange` on the same footing and with the same remedies (name the party, or run unsigned). The partner's half is settled where it first becomes knowable. A run that will sign holds the agreed pair to both parties being named the moment the partner's terms arrive, and ends there -- before the bootstrap frame, any linkage key, and any payload row -- sending the partner an abort so a peer that derives no refusal of its own fails fast rather than waiting out its inactivity budget. That refusal is one-sided: only the signing party derives it from the agreed terms, so only its own sends stop at terms, decision, and abort. The unnamed partner, deriving no refusal of its own, may already have sent its masked PSI element set for the round before it processes the abort. That is within the threat model, since a masked set discloses nothing beyond the record count already advertised at terms, though on a file-sync channel those bytes still reach the drop directory until the next sweep removes them.

**A certificate bound away from its own agreed terms is refused too, where it first becomes knowable.** The third locally-knowable way a `certificate`-mode run cannot finish is a signing certificate bound to an identity other than the one this party's own agreed terms state. `prepareForExchange` cannot settle it, because the `signing` block holds only a path to the identity file and no certificate is in hand there. So the front end that loads that file refuses at the load instead -- still before any credential, terms, or data are sent, as the same class of operator configuration error, and with two remedies of its own (rebind the certificate, or edit the terms to the bound value). The outbound-consent prompt may precede the refusal on any CLI leg; host-key trust establishment may precede it on the sftp leg. It is refused rather than reported because the run cannot finish either way, and the refusal at the load is the only one that spares the connection, the credentials it presents, and the terms it puts on the wire.

The exchange holds the same binding on the local side, at the two points the naming binding above is held. The first is the terms exchange. The identity the run signs under is this party's own agreed terms', settled before the run opened, and the certificate is in hand. So a diverging run -- a caller threading a signing identity past that front end -- is refused the moment the terms are agreed, before the bootstrap frame, any linkage key, and any payload row, sending the partner the same one-sided abort for the same reason. The second is the swap itself, the point of use, where a certificate is about to reach the wire. A run arriving there by another route terminates before its certificate or signature goes out and whichever leg the handshake gave it. That refusal sends the abort too, reaching a partner parked on the receipt frame it will never get, which refuses the arriving frame as a `protocol` connection error instead of waiting out its transport inactivity budget -- the wait that on a file-sync channel also holds the drop directory's bytes. Both points read one predicate over one pair of values, so the earlier refusal admits exactly the runs the later one does; the value held against is the identity this party's own agreed terms state, the same one its partner will authorize the presented certificate against, so neither leg's outcome depends on the role it drew. Both values that disagree are this party's own and nothing about the peer is consulted, so the refusal is an operator configuration error (the CLI's exit 64, and the `config` category of its [event stream](CLI_EVENTS.md#error-categories)) rather than the security-kind `ReceiptVerificationError` the swap's partner-side refusals raise -- a caller must not read it as the peer having failed a trust boundary. Neither point yields a result or a receipt; a run refused at the terms exchange has disclosed nothing and leaves nothing, while one refused at the swap keeps the [self-attested record](#self-attested-record) of what it disclosed.

**Known limitation (accepted, not mitigated).** This is post-result evidence, not a fair exchange. Because the result already exists on both sides, a party may capture the partner's signature and decline to send its own; any failure terminates the run, which must be restarted, and restarting does not undo the data already exchanged. A terminated swap persists no partial receipt: a partner signature received without completing the local swap is not written as a valid dual-signed record. It does leave the [self-attested record](#self-attested-record) of the disclosure that already happened, which is a separate artifact and no part of the receipt -- exactly because the data cannot be undone, the disclosure is one an operator's accounting must contain.

## Verifying a stored dual-signed record

The live step above verifies the partner's certificate and signature as they arrive. A stored dual-signed record is verified again, later and offline, by whoever holds it: either party re-checking its own exchange, or a third party the record was handed to. Verification is **read-only** -- it never mutates or re-signs the artifact -- and, for any record of the shape the parse produces, it never throws: every field value in it may be hostile (an identity the canonical encoder refuses, a malformed signature, a public key that is not a valid point) and each check still yields a status. The guarantee covers the values, not the shape: a hand-built record missing a structural member is a programming error, not an input class, and an unrecognized `version` is refused at parse rather than reinterpreted (see [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#dual-signed-record-file)). Four checks run per party, and none of them short-circuits another, so the verdict states every finding rather than the first.

- **Receipt signature.** The signed bytes are re-derived from the record's shared content, the fingerprint of the certificate held in that party's slot, and that slot's role, then checked under the certificate's public key. Because each party's signed bytes name that party, a swapped pair of `{ certificate, signature }` blocks fails.
- **Certificate identity binding.** The certificate's self-signature covers the body -- version, algorithm, identity, and public key -- so it is what ties the identity string the record displays to the key that signed. A certificate that does not self-verify binds nothing, and is reported as its own failure rather than as a bad signature.
- **Certificate anchoring.** Every value the verifier holds that ties a certificate to a party known outside the record -- a fingerprint pinned out-of-band, and the fingerprint of the verifier's own signing identity -- is compared (constant-time, over the decoded digest) against both certificates. Each value anchors *at most one* certificate: the values are assigned to the slots as a matching, and values with the same digest count once, so one pinned value, two spellings of it, or a pin equal to the verifier's own identity can never anchor both. A pinned value matching *neither* certificate means the record is not the pinned party's, and fails. The verifier's own identity matching neither fails only when the verifier *named* it, which asserts the record is one it signed; an identity psilink resolved on the verifier's behalf is reported instead and leaves the slot unanchored, since it says only that this is not the verifier's own exchange. A failure is attributed to the value that did not match, so a rotated local identity never recasts a correctly pinned partner slot as a mismatch.
- **Asserted identity.** When the verifier can state which two identities this exchange was between -- from its own exchange record, or from both parties' terms -- each certificate must authorize one of them. The pair is matched in either order: no artifact outside the dual-signed record says which party held which handshake role, and the per-signer signature binding above is what fixes a certificate to its role.

Two further checks are whole-record rather than per-party. The record's agreed-terms hash is compared against the value the verifier holds (or re-derives from both parties' terms), which is what ties the signatures to a specific set of agreed terms. The per-exchange binder is compared against the `receiptBinder` of the exchange record for the run, when the verifier holds that record, which is what ties them to one *run* of those terms. The agreed-terms hash and both certificates repeat byte for byte across recurring runs of a partnership, and the two payload MACs that do vary are not recomputable offline, so nothing else in the bundle separates one run from the next. A record holding a different binder fails the verification, a record holding none says its exchange produced no receipt at all and likewise fails, and no record at all leaves the pairing unchecked -- `incomplete`, never `verified`. The four outcomes and what each means for a holder of one artifact are specified in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#pairing-a-receipt-to-one-run).

The binder is still never **recomputed**: it is derived from the session key, which only the two parties ever held and neither retains, so an offline verifier confirms that the signers signed a receipt holding *this* value and that the run's own record holds it too, without being able to derive it. A binder substituted into both artifacts at once is therefore detectable only during the live step, where both parties derive it independently.

**What a pass means: both certificates anchored.** The verdict is tri-state -- verified, incomplete, or failed -- so "not checked" is never reported as "it checked out". A record holds two certificates and a verdict speaks for both, so `verified` is reached only when **each** of them is anchored, and it names what anchored each one. Where the anchors come from:

- **A party to the exchange** anchors the partner's certificate with the fingerprint it pinned out-of-band, and its own certificate with its own signing identity -- *derived* from the certificate half of the identity file it holds, or from the certificate it exported from that file, never restated. A typed self-pin would be a value the verifier could only copy off the record it is checking. Only the certificate half is ever used: verification signs nothing, so no private signing key is imported on any path, and the browser surface takes the exported certificate alone rather than a file that holds a key. Certificates are public either way, so this anchor -- like a pinned fingerprint -- says whose certificate occupies the slot and nothing more: an assembler can place the verifier's certificate in a slot the verifier never signed, and what refuses that record is the receipt signature in the slot, which verifies only under the private key the verifier holds.
- **A verifier that was party to no exchange** has no identity to derive and anchors each slot with a fingerprint held out-of-band for that signer. Supplying one such value anchors one slot, and this is the general mechanism: it is the only one open to a verifier with no signing identity of its own.
- **Anything short of both anchors** is `incomplete`, never `verified`, and the verdict names the unanchored slot. That includes the third-party auditor with no pinned value at all, and the party that pinned its partner but could not anchor its own slot. `incomplete` already means "nothing contradicted the record, but not everything could be checked", which is exactly what an unanchored slot leaves; it is not a failure, and does not change the exit code. A run that anchored both slots but paired the receipt to no exchange record is `incomplete` on the same rule, for the same reason.

That an unpinned run cannot reach `verified` is by design rather than a gap: a dual-signed record is self-consistent by construction, so signature verification alone proves only that whoever holds the two embedded certificates' keys signed this content -- which anyone can arrange with two certificates of their own. The signatures, the identity bindings and (given the data) the record's commitments are still checked and reported; what is reported as not established is certificate *trust*.

**What an unanchored certificate leaves open.** An unanchored certificate is checked only against itself -- its self-signature, its signature over the shared content, and the expected identities the verifier supplies. Whoever assembled the record can satisfy all three with a certificate it minted itself, since the expected identities come from the verifier's own record or terms rather than from anything the certificate is bound to out-of-band. A verdict over one anchored slot therefore establishes that the *anchored* party signed this exchange and says nothing about who the other signer is, which is why the top-line `verified` is withheld until both slots are anchored rather than qualified in prose beside it.

A self-signed certificate's third-party assurance is weaker than a CA-backed one either way; the authority-backed mode that would close that gap is deferred (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#receipt-signing-identities)).

## Self-attested record

Once an exchange has disclosed, on every path, each party produces a self-attested record of what it disclosed -- a local, unsigned audit artifact that stands on its own as a disclosure-log entry, so an operator can populate a HIPAA accounting of disclosures or a FERPA disclosure record without separately retaining and re-matching the original linkage-terms config. It is built from data both sides already hold, so it needs no private key and adds no protocol round-trip. It is explicitly **not** a signed or non-repudiable receipt and **not** evidence against the partner. The record is unsigned: a session-derived MAC is not non-repudiation (see the two signing modes above), so an unsigned record is an accurate, local audit artifact rather than one that overstates what it proves. Non-repudiation is the [signed receipt](#the-signed-receipt-step)'s job, and the receipt is a separate artifact produced alongside this one.

**The durability point is the payload exchange.** A record is owed from the moment this party's payload exchange completes -- the point at which the disclosure it attests has provably occurred -- and not from the moment the run finishes. Two steps run after that point: the received-payload check that holds the partner's transmitted columns to the set this party consented to receive, and then the [signed-receipt step](#the-signed-receipt-step). The rule covers both: a run that terminates in either still leaves this party the record of what it had already disclosed, and the exchange hands that record to its caller on the failure exactly as it returns one on success. What is refused is the reverse reading -- a terminated run's record passing for a completed run's. Every record has a mandatory `outcome` stating which it is, so a reader of the artifact alone tells them apart and can see that no receipt accompanies a terminated one. The values, the properties that fix how the row is read (the cause of the termination among the things it does not state), and the reason a terminated record keeps its run binder are in [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#when-a-record-is-owed). A failure before that point produces no record and owes none. The boundary is the payload exchange's return, not its first frame. The initiator sends its payload before it receives the partner's, so a failure inside the exchange can leave this party's payload already across and still leave no record -- a stated limit of where the durability point sits, with the failure reported through the run's error and the [machine-readable event stream](CLI_EVENTS.md) rather than through a record.

The receipt's own all-or-nothing rule stands beside this untouched. A terminated swap persists no partial or unverifiable dual-signed record, and the self-attested record is not one: it is the separate, unsigned artifact, and it attests only what this party itself disclosed.

The record format itself -- the record and verification-keys file shapes, the format version, the agreed-terms hash, the HMAC commitment scheme, the readable governance metadata, the result-size and per-direction disclosure framing, and the record's privacy properties -- has its own specification: [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md). The signed receipt reuses that record's commitment scheme and on-disk format.

## Output

The basic output is an association table between each party's element. As noted above, if parties supplied identifier columns with their inputs and flagged them in their metadata, the association table will be between each party's identifiers. Otherwise, the table references the row indices of each dataset.

The result file identifies our matched record in its first column (the identifier value, or the local row index when no identifier column exists), followed by a `row_id` column holding the partner's 0-based row index for that match. This partner row-index column is written for every match, not only for identifier-free exchanges, because it is the partner side of the association-table pairing the exchange-record commitment binds -- writing it keeps the result sufficient to reproduce (and so verify) that commitment from the holder's own retained files (see [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#commitment-scheme)). The column is headed `row_id`, disambiguated to `their_row_id` (then `their_row_id_2`, ...) if that name collides with the local column or a partner payload column.

The result file has one row per association pair. Under `one-to-one` that is one row per matched record, the two readings coinciding. Under a [deduplicating cardinality](#deduplicating-cardinalities-many-to-x-matching) they part, and the pair reading is the one the file takes. Where several of the partner's records link to one of this party's, that party's first-column value repeats down the column, once per partner record, each row holding its own partner row index and that partner record's payload values. Where the multiplicity runs the other way, the one partner record's row index and payload values are written against each of this party's records in the group. Where both sides have it the two readings compose, and one [entity cluster](#the-many-to-many-entity-closure) of `m` of this party's records and `n` of the partner's writes `m * n` rows -- each of this party's records once per partner record in the cluster, in this party's row order. No column marks a cluster's boundary; the pairs are what the file holds and what the record's commitments bind. The count the exchange record attests over the same table is fixed separately, at [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#result-size-under-a-deduplicating-cardinality).

If parties elected to transmit payload data, the relevant columns for the appropriate rows will be transmitted in-band over the secure connection and appended to the output in-the-clear, after the partner row-index column. Each partner payload column keeps its original name, prefixed `their_` only when that name equals the local first column's name (the identifier column, or `row_id` when there is none). That single local column is the whole collision set, and the prefix is never numbered -- so a partner column literally named `their_<local name>` arriving alongside `<local name>` produces two identically headed columns. Only the partner row-index column above is disambiguated by numbering.

A payload frame has one row per matched record of the sender, not one per pair, whatever the cardinality. A payload row is addressed by the sender's own 0-based row index and those indices MUST be distinct within a frame -- a repeat names two payload rows for one record without saying which is the record's -- so a sender transmits each of its own matched rows exactly once and the receiver joins every association entry naming that row back to it. The multiplicity a deduplicating cardinality creates therefore lives on the association table's side of that join and never on the frame, which is what keeps the two parties' payload commitments over byte-identical data ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#commitment-scheme)).

A payload frame's rows are positional against the columns it names: each row contains exactly one value per named column, in that order, and one row index per row. A received frame whose rows do not is a protocol violation, refused where the frame is parsed -- the exchange aborts with a classified `protocol` error and produces no result and no record, like every other malformed frame -- rather than at the stage that reads it. That is what keeps a party's [self-attested record](#self-attested-record) coherent in both halves: the committed payload binds the column names and the row values together, while the readable governance list holds the names alone, so a record that commits row values names the columns those values came from ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#commitment-scheme)). The reference implementation is the payload wire schema in `packages/core/src/payloadExchange.ts`.

Every header and value in the result file is an RFC 4180 field: a value containing a comma, a double quote, CR, or LF is wrapped in double quotes with its embedded quotes doubled, and any other value is written bare. Escaping happens once, where the table is formatted -- the writers that emit it (the CLI's file and stdout branches, the web app's download blob) join the formatted fields and add nothing. A matched value therefore round-trips: re-parsing the result yields the value the exchange committed to, which is what lets a holder re-supply the result to reproduce the record's commitments (see [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#commitment-scheme)). A committed null and a committed empty string are the one exception, both written as an empty cell and both read back as an empty string.
